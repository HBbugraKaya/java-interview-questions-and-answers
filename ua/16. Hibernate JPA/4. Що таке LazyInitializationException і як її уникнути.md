# Що таке LazyInitializationException і як її уникнути

---

## 🟢 Junior Level

### Що таке LazyInitializationException

**`LazyInitializationException`** — це виняток часу виконання (`RuntimeException`), який викидається Hibernate при спробі звернутися до неініціалізованого лінивого поля або колекції (`FetchType.LAZY`), коли **сесія Hibernate (`Session` / `EntityManager`) вже закрита**.

```
1. Сервіс: @Transactional
   Order order = orderRepository.findById(1L); // Сесія відкрита. order.items = проксі
   return order;                               // Вихід із методу: ТРАНЗАКЦІЮ ЗАВЕРШЕНО, СЕСІЮ ЗАКРИТО!

2. Контролер / Мапер:
   order.getItems().size();                    // ПОМИЛКА: Сесія закрита, з'єднання з БД повернено в пул!
   └──> org.hibernate.LazyInitializationException: could not initialize proxy - no Session
```

### Чому це відбувається

Для реалізації лінивого завантаження (`LAZY`) Hibernate підставляє замість реальних об'єктів проксі-класи (`ByteBuddy`) або обгортки колекцій (`PersistentBag`). 
- Проксі зберігає всередині ідентифікатор сутності та посилання на поточну активну сесію `Session`.
- При першому виклику будь-якого бізнес-методу або гетера проксі намагається виконати SQL-запит `SELECT` через цю сесію.
- Якщо сесія вже закрита (`session.isOpen() == false`), проксі не має фізичного з'єднання з базою даних і аварійно викидає `LazyInitializationException`.

### Базові способи вирішення

1. **Використовувати `JOIN FETCH` у запиті репозиторію:** Пов'язані дані завантажуються відразу в тому ж самому SQL-запиті, поки транзакція активна.
2. **Використовувати `@EntityGraph`:** Декларативно вказати поля, які потрібно підвантажити для конкретного методу.
3. **Використовувати DTO-проєкції:** Зчитувати відразу готові DTO або Java Record на рівні бази даних, не вивантажуючи важкі керовані сутності.

## 🟡 Middle Level

### Стан Detached та життєвий цикл PersistenceContext

У Spring-застосунках межа сесії Hibernate за замовчуванням збігається з межею транзакції `@Transactional`:

```
HTTP Запит ──> Controller ──> Service (@Transactional) ──> Repository
                                       │
                         [Транзакція почалася: Сесія ВІДКРИТА]
                         Сутність перебуває в стані MANAGED (L1-кеш)
                                       │
                         [Транзакцію завершено: Сесія ЗАКРИТА]
                         Сутність переходить у стан DETACHED (Від'єднана)
                                       │
HTTP Відповідь <── Controller <────────┘
```

Коли сутність переходить у стан **DETACHED**:
- Вона більше не прив'язана до контексту збереження (`PersistenceContext`).
- Усі поля, які встигли завантажитися під час транзакції, залишаються в оперативній пам'яті й доступні для читання.
- Усі незавантажені ліниві проксі стають «мінами уповільненої дії»: будь-яке звернення до них за межами `@Transactional` методу гарантовано призводить до `LazyInitializationException`.

### Типові місця виникнення помилки

1. **Jackson / JSON-серіалізація у `@RestController`:**
   Контролер повертає Entity безпосередньо. Серіалізатор Jackson рекурсивно обходить усі поля через гетери. Коли Jackson викликає `order.getItems()`, сесія вже закрита $\rightarrow$ `LazyInitializationException` з HTTP статусом `500 Internal Server Error`.
2. **Мапінг у DTO на шарі контролера:**
   Сервіс повертає Detached Entity, а виклик `orderMapper.toDto(order)` відбувається в контролері поза транзакцією.
3. **Асинхронні потоки (`@Async`, `CompletableFuture`):**
   Сутність передається в інший потік виконання. Сесія не передається між потоками, тому в новому потоці сесія спочатку відсутня.

### Шаблони усунення помилки

#### 1. Вибірка через `JOIN FETCH`
```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    @Query("SELECT o FROM Order o LEFT JOIN FETCH o.items WHERE o.id = :id")
    Optional<Order> findByIdWithItems(@Param("id") Long id);
}
```

#### 2. Декларативний графовий план (`@EntityGraph`)
```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    @EntityGraph(attributePaths = {"items", "user"})
    Optional<Order> findWithDetailsById(Long id);
}
```

#### 3. Мапінг на DTO всередині транзакції (Best Practice)
```java
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orderRepository;
    private final OrderMapper orderMapper;

    @Transactional(readOnly = true)
    public OrderResponseDto getOrderById(Long id) {
        Order order = orderRepository.findById(id).orElseThrow();
        // Мапінг виконується ВСЕРЕДИНІ транзакції, поки сесія відкрита:
        return orderMapper.toDto(order);
    }
}
```

## 🔴 Senior Level

### Фатальний антипатерн: `hibernate.enable_lazy_load_no_trans`

Серед налаштувань Hibernate існує параметр:
```properties
# НІКОЛИ НЕ ВМИКАЙТЕ В PRODUCTION!
hibernate.enable_lazy_load_no_trans=true
```

Розробники іноді вмикають його, щоб «раз і назавжди позбутися `LazyInitializationException`».

#### Як працює цей параметр під капотом:
1. Коли код поза транзакцією звертається до лінивого проксі, проксі не падає з помилкою.
2. Замість цього він тимчасово **відкриває абсолютно нову короткочасну сесію Hibernate**, бере з пулу HikariCP фізичне з'єднання з БД, виконує один SQL-запит, закриває сесію і віддає конект назад у пул.

#### Чому провідні інженери вважають це катастрофою:
- **Миттєве виснаження пулу з'єднань (Connection Starvation):** Якщо на сторінці відображається 100 замовлень, цикл `for-each` виконає 100 послідовних захоплень і звільнень фізичних JDBC-конектів. Пул HikariCP блокується, викликаючи таймаути в усьому застосунку.
- **Некерований прихований N+1:** Проблема N+1 маскується і стає невидимою в кодовій базі.
- **Порушення транзакційної ізоляції:** Дані вичитуються поза вихідною транзакцією короткими сесіями з рівнем автокоміту. Якщо в цей момент паралельна транзакція змінює БД, застосунок вичитує неузгоджений стан (Non-Repeatable Read / Phantom Read).
- **Неможливість відкату:** Запити виконуються в режимі autocommit, їх неможливо відкотити при збої.

### Антипатерн Open Session in View (OSIV)

У Spring Boot налаштування `spring.jpa.open-in-view: true` увімкнено за замовчуванням.
- Перехоплювач `OpenEntityManagerInViewInterceptor` тримає `EntityManager` відкритим протягом усього життєвого циклу HTTP-запиту, включаючи шари фільтрів та серіалізації в JSON.
- **Наслідки в Highload:**
  Фізичне з'єднання з базою даних утримується потоком сервлета весь той час, поки клієнт отримує HTTP-відповідь. Якщо клієнт перебуває на повільному мобільному з'єднанні або мережа затримує пакети, конект до БД висить заблокованим секундами. При навантаженні у 200–500 RPS пул з'єднань повністю паралізується.
- **Продакшн-правило:** Завжди явно вказувати в `application.yml`:
  ```yaml
  spring:
    jpa:
      open-in-view: false
  ```

### Повторне приєднання Detached сутностей (Reattaching)

Якщо сутність уже від'єднана (`detached`), чи можна прив'язати її до нової сесії, щоб прочитати ліниві поля?

```java
@Transactional
public void processDetachedOrder(Order detachedOrder) {
    // 1. entityManager.merge(detachedOrder):
    // УВАГА: Сам detachedOrder НЕ стає managed!
    // merge() повертає НОВУ копію об'єкта, яка прив'язана до сесії:
    Order managedOrder = entityManager.merge(detachedOrder);
    
    // Тепер managedOrder може безпечно ініціалізувати зв'язки:
    managedOrder.getItems().size(); // SQL SELECT буде виконано успішно
}
```

> **Нюанс:** Метод `merge()` виконує `SELECT` у БД, щоб завантажити поточний стан рядка, а потім накатує поверх зміни з `detachedOrder`. Це створює додатковий оверхед, тому краще проєктувати сервіси так, щоб не передавати `detached`-сутності між транзакціями.

## 4 Tricky Questions

### 1. Що робить метод `Hibernate.isInitialized(object)`, і чи можна викликати його поза транзакцією, не побоюючись `LazyInitializationException`?

**Відповідь:**
**Так, метод `Hibernate.isInitialized()` абсолютно безпечний для виклику поза транзакцією.**
1. Метод приймає як аргумент будь-який об'єкт або колекцію.
2. Він перевіряє, чи є об'єкт екземпляром `HibernateProxy` або `PersistentCollection`.
3. Якщо так — метод зчитує внутрішній булевий прапорець (наприклад, `proxy.getHibernateLazyInitializer().isUninitialized()`) без спроби звернутися до закритої сесії і без виконання SQL-запитів.
4. Повертає `true`, якщо об'єкт уже завантажений, і `false`, якщо це «холодний» неініціалізований проксі.
5. Це ідеальний інструмент для написання безпечних утилітарних маперів.

### 2. Чому анотація `@Transactional(readOnly = true)` не запобігає `LazyInitializationException`, якщо звернення до поля відбувається в контролері?

**Відповідь:**
1. Анотація `@Transactional(readOnly = true)` повідомляє Spring відкрити транзакцію і прив'язати до неї сесію Hibernate, а також активує оптимізацію: Hibernate вимикає механізм відстеження брудних станів (**Dirty Checking**) і забороняє скидання змін (`flush`), що прискорює вибірку.
2. Проте час життя транзакції суворо обмежений **виконанням методу сервісу**.
3. Щойно потік виходить із методу сервісу, позначеного `@Transactional(readOnly = true)`, транзакція завершується, а асоційована з нею сесія закривається точно так само, як і при звичайній транзакції на запис.
4. Коли контролер отримує сутність, вона вже перебуває в стані `DETACHED`, тому будь-яка спроба прочитати лінивий зв'язок за межами методу сервісу неминуче викине `LazyInitializationException`.

### 3. Як зв'язка Jackson і Bidirectional Relationship перетворює `LazyInitializationException` на `StackOverflowError`?

**Відповідь:**
1. Якщо сутність `Order` має колекцію `@OneToMany List<OrderItem> items`, а `OrderItem` має зворотне посилання `@ManyToOne Order order`.
2. Якщо сесія залишилася відкритою (наприклад, увімкнено OSIV) або зв'язок був жадібним:
   - Jackson серіалізує `Order`, бачить гетер `getItems()` і починає серіалізувати `OrderItem`.
   - Усередині `OrderItem` Jackson бачить гетер `getOrder()` і знову починає серіалізувати `Order`.
   - Виникає нескінченна взаємна рекурсія, яка вичерпує стек викликів JVM і призводить до фатальної помилки `java.lang.StackOverflowError`.
3. Якщо ж сесія була закрита (OSIV вимкнено), то перший же виклик `getItems()` обірветься на `LazyInitializationException`.
4. **Рішення:** Використовувати DTO, або анотації `@JsonIgnore` чи комбінацію `@JsonManagedReference` + `@JsonBackReference`.

### 4. Чому виклик `order.getUser().getClass()` на неініціалізованому лінивому полі `@ManyToOne` не викликає `LazyInitializationException`, але повертає неочікуваний результат?

**Відповідь:**
1. Метод `getClass()` визначений у класі `java.lang.Object` як `final`.
2. Бібліотека ByteBuddy генерує проксі-клас як підклас цільової сутності (`class User$ByteBuddy$Proxy extends User`), але **не може перевизначити `final`-методи** `Object` (такі як `getClass()`, `wait()`, `notify()`).
3. Тому виклик `order.getUser().getClass()` не перехоплюється проксі-перехоплювачем Hibernate і не ініціює завантаження з БД. Виняток не викидається.
4. Проте метод повертає `User$ByteBuddy$Proxy.class` замість `User.class`. Якщо в коді є наївна перевірка вигляду `if (user.getClass().equals(User.class))`, вона поверне `false`.

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь (Elevator Pitch)
> «**`LazyInitializationException`** виникає в Hibernate, коли застосунок намагається звернутися до неініціалізованого проксі-об'єкта або колекції (`FetchType.LAZY`) після закриття сесії (`Session` / `EntityManager`), коли фізичне з'єднання з базою даних уже розірвано. Головні причини — звернення до лінивих зв'язків у контролерах, Jackson-серіалізаторах або фонових потоках після виходу з `@Transactional` методу сервісу. Стандартом вирішення проблеми є вибірка даних у межах вихідної транзакції через **`JOIN FETCH`**, **`@EntityGraph`** або мапінг у **DTO-проєкції на межі сервісного шару**. Увімкнення обхідних шляхів на зразок `enable_lazy_load_no_trans` або `open-in-view` у продакшені вважається критичним антипатерном».

### Ключові метрики для Production-мониторингу
- Частота появи `org.hibernate.LazyInitializationException` у системах збору логів (Sentry, Grafana Loki).
- `HikariCP: Connection Timeout Rate`: індикатор витоків конектів при увімкненому OSIV.
- Час відповіді HTTP-ендпоінтів на етапі серіалізації відповідей (Jackson serialization time).

### Червоні прапорці (Чого говорити НЕ МОЖНА)
- ❌ *«Я лікую LazyInitializationException, виставляючи FetchType.EAGER скрізь, де падає»* — Найгрубіший антипатерн, що призводить до лавини N+1 запитів і переповнення пам'яті.
- ❌ *«Найкращий спосіб позбутися помилки — увімкнути hibernate.enable_lazy_load_no_trans=true»* — Це руйнівне налаштування, що викликає виснаження пулу з'єднань БД і прихований N+1.
- ❌ *«Контролер може спокійно повертати Entity в JSON, якщо увімкнено open-in-view»* — OSIV тримає з'єднання відкритими під час передачі пакетів мережею, блокуючи базу даних.
- ❌ *«@Transactional(readOnly = true) тримає сесію відкритою нескінченно»* — Сесія закривається відразу ж при виході з методу сервісу.
