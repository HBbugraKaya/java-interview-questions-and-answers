# Що таке bridge methods і навіщо вони потрібні

---

## 🟢 Junior Level

**Bridge method (мостовий метод)** — це синтетичний метод, який компілятор `javac` автоматично генерує в байткоді класу для збереження механізму поліморфізму при використанні дженериків та коваріантних типів повернення.

### Навіщо він потрібен: проблема стирання типів
Розглянемо простий приклад наслідування:

```java
public class Node<T> {
    public void setData(T data) {
        System.out.println("Node.setData");
    }
}

public class StringNode extends Node<String> {
    @Override
    public void setData(String data) {
        System.out.println("StringNode.setData: " + data);
    }
}
```

Що відбувається після компіляції (Type Erasure):
1. У базовому класі `Node` параметр `T` стирається до `Object`:
   ```java
   public void setData(Object data) // Дескриптор: (Ljava/lang/Object;)V
   ```
2. У підкласі `StringNode` програміст оголосив метод із суворим типом:
   ```java
   public void setData(String data) // Дескриптор: (Ljava/lang/String;)V
   ```

Для віртуальної машини JVM методи з дескрипторами `(Ljava/lang/Object;)V` та `(Ljava/lang/String;)V` — це **два абсолютно різні методи**. Без втручання компілятора поліморфний виклик через посилання базового типу `Node n = new StringNode(); n.setData("test");` викликав би метод `Node.setData(Object)`, повністю проігнорувавши перевизначення в `StringNode`!

### Як компілятор вирішує проблему
Щоб поліморфізм працював, компілятор додає в `StringNode` невидимий для вихідного коду мостовий метод:

```java
// Згенеровано компілятором у StringNode.class:
public void setData(Object data) {
    // Приводить тип і делегує виклик користувацькому методу
    this.setData((String) data); 
}
```

## 🟡 Middle Level

### Внутрішня будова: Прапорці байткоду `ACC_BRIDGE` та `ACC_SYNTHETIC`

У байткоді мостовий метод позначається двома спеціальними модифікаторами доступу (JVMS §4.6):
- **`ACC_BRIDGE` (`0x0040`)**: Вказує віртуальній машині та інструментам аналізу, що метод був згенерований компілятором для вирішення конфлікту типів.
- **`ACC_SYNTHETIC` (`0x1000`)**: Позначає, що метод не був присутній у вихідному коді Java.

Подивитися структуру класу можна за допомогою утиліти `javap -v -p StringNode.class`:

```bytecode
public void setData(java.lang.String);
  descriptor: (Ljava/lang/String;)V
  flags: (0x0001) ACC_PUBLIC
  Code: ...

public void setData(java.lang.Object);
  descriptor: (Ljava/lang/Object;)V
  flags: (0x1041) ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
  Code:
     0: aload_0
     1: aload_1
     2: checkcast     #2 // class java/lang/String
     5: invokevirtual #3 // Method setData:(Ljava/lang/String;)V
     8: return
```

### Другий сценарій: Коваріантні типи повернення (Covariant Return Types)

Починаючи з Java 5, метод, що перевизначає, може звужувати тип повернення:

```java
public class Parent {
    public Number getValue() { return 1; }
}

public class Child extends Parent {
    @Override
    public Integer getValue() { return 2; }
}
```

У мові Java тип значення, що повертається, не входить до сигнатури методу. Однак **у байткоді JVM дескриптор методу включає тип повернення**:
- `Parent.getValue`: дескриптор `()Ljava/lang/Number;`
- `Child.getValue`: дескриптор `()Ljava/lang/Integer;`

Оскільки інструкція байткоду `invokevirtual` шукає метод з точним дескриптором предка, компілятор генерує в класі `Child` мостовий метод:
```bytecode
public java.lang.Number getValue();
  flags: ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
  Code:
     0: aload_0
     1: invokevirtual #2 // Method getValue:()Ljava/lang/Integer;
     4: areturn
```

У байткоді класу `Child` співіснують два методи з однаковим ім'ям `getValue` та однаковими аргументами (порожніми), але різними типами повернення (`Number` та `Integer`). Для мови Java це неприпустимо, але для байткоду JVM — абсолютно легально!

## 🔴 Senior Level

### Проблеми з Reflection API та фреймворками (Spring, Hibernate)

При скануванні методів через Reflection API мостові методи стають джерелом прихованих багів:

```java
Method[] methods = StringNode.class.getDeclaredMethods();
for (Method m : methods) {
    System.out.println(m.getName() + " -> " + m.getParameterTypes()[0].getSimpleName() 
                       + " [bridge=" + m.isBridge() + "]");
}
// Виведе:
// setData -> String [bridge=false]
// setData -> Object [bridge=true]
```

#### Чому це критично:
1. **Втрата анотацій:** Якщо програміст ставить анотацію (наприклад, `@Transactional`, `@Valid` або `@Secured`) на метод у вихідному коді, компілятор поміщає її на оригінальний метод `setData(String)`. На мостовий метод `setData(Object)` ця анотація **не переноситься**!
2. **Дублювання викликів:** Якщо фреймворк або кастомний проксі перебирає методи і не фільтрує `m.isBridge()`, один і той самий метод може бути оброблений двічі.

#### Як це вирішується в Spring Framework
У складі Spring Framework є спеціальний утилітний клас `BridgeMethodResolver`:
```java
Method originalMethod = BridgeMethodResolver.findBridgedMethod(bridgeMethod);
```
Він досліджує ієрархію типів і зіставляє мостовий метод із оголошеним у вихідному коді користувацьким методом, витягуючи оригінальні анотації та типи.

### Продуктивність та JIT-оптимізації

Мостовий метод містить лише 3–4 інструкції байткоду: `aload`, `checkcast`, `invokevirtual` та `return`.  
При профілюванні в JVM HotSpot (C1/C2 JIT-компілятори):
- Мостові методи мають крихітний розмір байткоду і тривіальну структуру графа потоку керування (Control Flow Graph).
- JIT практично гарантовано **інлайнить** мостовий метод на першому етапі компіляції.
- Накладні витрати в runtime дорівнюють суворо **0 наносекунд** (Zero-cost abstraction).

## 4 Tricky Questions

### 1. Чи може виклик методу в коректно скомпільованій програмі викинути `ClassCastException` всередині мостового методу?
**Відповідь:**  
Так, при використанні «сирих» типів (Raw Types) або обході перевірки типів через рефлексію:
```java
StringNode sn = new StringNode();
Node rawNode = sn; // Використання сирого типу
rawNode.setData(Integer.valueOf(42)); // 💥 ClassCastException!
```
Викликається метод `setData(Object)`. Всередині нього першою операцією виконується інструкція байткоду `checkcast java/lang/String`. Оскільки передано `Integer`, інструкція негайно викидає `ClassCastException`. Це класичний приклад того, як стирання типів проявляється в runtime.

### 2. Скільки мостових методів згенерує компілятор для класу `class Box implements Comparable<Box>`?
**Відповідь:**  
Один мостовий метод.  
Інтерфейс `Comparable<T>` містить метод `int compareTo(T o)`. Після стирання в `Comparable` метод перетворюється на `int compareTo(Object o)`. У класі `Box` оголошено `int compareTo(Box o)`. Компілятор згенерує синтетичний мостовий метод:
```java
public int compareTo(Object o) {
    return this.compareTo((Box) o);
}
```
Він перевіряє тип об'єкта через `checkcast #Box` і передає керування користувацькому методу `compareTo(Box)`.

### 3. Чому в Java заборонено мати два методи з однаковими параметрами, але різними типами повернення, а в байткоді JVM це дозволено?
**Відповідь:**  
У специфікації мови Java (JLS §8.4.2) сигнатура методу визначається лише ім'ям методу та типами його формальних параметрів. Тип повернення виключений із сигнатури мови, щоб уникнути неоднозначності виклику, коли значення, що повертається, ігнорується: `myMethod();` — компілятор не міг би визначити, яку версію викликати.  
Однак у специфікації віртуальної машини JVM (JVMS §4.3.3) дескриптор методу включає в себе тип повернення. Інструкції виклику (`invokevirtual`) оперують повним дескриптором із constant pool, що робить методи з різним типом повернення помітними для рантайму JVM. Компілятор використовує цю гнучкість байткоду для створення bridge-методів коваріантного повернення.

### 4. Як перевірити в коді, чи є метод мостовим або синтетичним?
**Відповідь:**  
За допомогою методів класу `java.lang.reflect.Method`:
- `method.isBridge()` — повертає `true`, якщо у методу виставлено прапорець `ACC_BRIDGE`.
- `method.isSynthetic()` — повертає `true`, якщо у методу виставлено прапорець `ACC_SYNTHETIC`.  
Будь-який мостовий метод одночасно є синтетичним (`isBridge() => isSynthetic() == true`), але зворотне не завжди вірно (наприклад, синтетичними є згенеровані поля `$SWITCH_TABLE$` або методи доступу до private-членів зовнішнього класу).

## 🎯 Шпаргалка для інтерв'ю

- **Що це:** Синтетичний метод, створюваний компілятором `javac` у байткоді з прапорцями `ACC_BRIDGE` та `ACC_SYNTHETIC`.
- **Навіщо потрібен:** Щоб зберегти поліморфізм ООП після стирання типів (Type Erasure) та для підтримки коваріантних типів повернення (Covariant Return Types).
- **Як працює:** Мостовий метод приймає тип батьківського методу (наприклад, `Object`), робить `checkcast` до конкретного типу підкласу і викликає цільовий користувацький метод.
- **Підводний камінь з рефлексією:** `Class.getDeclaredMethods()` повертає обидва методи (оригінальний та мостовий). Анотації вішаються на оригінальний метод, а мостовий метод залишається без них! У Spring для цього використовується `BridgeMethodResolver`.
- **Продуктивність:** Накладні витрати відсутні — C2 JIT-компілятор повністю інлайнить тіло мостового методу.
