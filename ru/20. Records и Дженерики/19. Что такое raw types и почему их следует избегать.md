# Что такое raw types и почему их следует избегать

---

## 🟢 Junior Level

**Raw Type (сырой тип)** — это использование параметризованного класса или интерфейса **без указания аргументов типов**.

До появления дженериков в Java 5 все коллекции были «сырыми». Сырые типы оставлены в Java исключительно для совместимости со старым legacy-кодом.

```java
// ✅ Параметризованный тип (безопасно):
List<String> safeList = new ArrayList<>();
safeList.add("Hello");
String s1 = safeList.get(0); // Тип гарантирован компилятором

// ❌ Raw type (опасно!):
List rawList = new ArrayList(); // Предупреждение компилятора: raw type
rawList.add("Hello");
rawList.add(42); // Компилятор пропускает число в коллекцию строк!

String s2 = (String) rawList.get(1); // 💥 ClassCastException во время выполнения!
```

### 3 причины избегать Raw Types

1. **Полная потеря типобезопасности**: компилятор отключает проверки типов при вставке элементов.
2. **Риск `ClassCastException` в production**: ошибка проявляется не в момент добавления испорченных данных, а позже — при попытке их прочитать.
3. **Необходимость ручного приведения типов (`cast`)**: код загромождается небезопасными приведениями.

## 🟡 Middle Level

### 1. Каскадное стирание членов класса (Erasure of Member Types)

Малоизвестный, но критически опасный эффект сырых типов (JLS §4.8): **при использовании raw type стираются возвращаемые типы ВСЕХ методов класса**, даже если они явно не зависят от переменной типа $T$!

```java
public class Box<T> {
    private T value;

    // Метод ВООБЩЕ не использует тип T:
    public List<String> getTags() {
        return List.of("tag1", "tag2");
    }
}

// 1. Использование с параметром типа:
Box<Integer> typedBox = new Box<>();
List<String> tags = typedBox.getTags(); // ✅ Тип сохранен: List<String>

// 2. Использование через Raw Type:
Box rawBox = new Box();
// ❌ Ошибка компиляции или Unchecked warning:
// Метод getTags() вернул СЫРОЙ List, а не List<String>!
List<String> rawTags = rawBox.getTags(); 
```

Использование сырого типа «отравляет» весь класс, превращая даже строго типизированные методы в их до-дженериковые аналоги.

### 2. Принципиальная разница: `List` (Raw) vs `List<?>` (Wildcard)

Многие разработчики ошибочно считают, что сырой тип `List` и подстановочный тип `List<?>` эквивалентны. **Это принципиально не так:**

```java
// ❌ Raw Type: контроль типов отключен
List raw = new ArrayList<String>();
raw.add(12345); // ✅ Компилируется (с warning). Безопасность разрушена!

// ✅ Unbounded Wildcard: контроль типов ВКЛЮЧЕН
List<?> wildcard = new ArrayList<String>();
// wildcard.add(12345);   // ❌ Ошибка компиляции! Запись запрещена!
// wildcard.add("hello"); // ❌ Ошибка компиляции! Тип неизвестен!
wildcard.add(null);       // Разрешен только null
```

- **`List` (raw)**: *«Мне плевать на типы, клади что угодно»* (небезопасно).
- **`List<?>`**: *«Здесь лежит список некоторого конкретного типа, но мы его не знаем, поэтому не разрешаем ничего записывать во избежание сбоев»* (100% типобезопасно).

## 🔴 Senior Level

### Единственные законные сценарии использования Raw Types

Спецификация языка Java (JLS §4.8) допускает использование сырых типов только в двух синтаксических конструкциях:

#### 1. Классовые литералы (Class Literals)
Синтаксис литералов класса не разрешает указывать параметры типов:
```java
Class<?> clazz1 = List.class; // ✅ Единственно верный синтаксис

// ❌ Ошибки компиляции:
// Class<?> clazz2 = List<String>.class; 
// Class<?> clazz3 = List<?>.class;
```

#### 2. Оператор `instanceof` (до появления Pattern Matching)
Из-за стирания типов JVM в рантайме не способна проверить параметр типа:
```java
if (obj instanceof List) { // ✅ Легально: проверяется только тип List
    List<?> list = (List<?>) obj;
}

// ❌ Ошибка компиляции: Cannot perform instanceof check against parameterized type
// if (obj instanceof List<String>) { ... }
```
*(Примечание: Начиная с Java 16+, в операторе `instanceof` рекомендуется использовать неограниченный wildcard: `if (obj instanceof List<?> list)`).*

### Происхождение Heap Pollution через Raw Types

Сырые типы являются главным источником **Heap Pollution (загрязнения кучи)**:

```java
public class PollutionDemo {
    public static void main(String[] args) {
        List<String> strings = new ArrayList<>();
        corrupt(strings); // Передаем безопасный список в метод с сырым типом

        // Код падает здесь, хотя в этом классе не было ни одного некорректного действия!
        String s = strings.get(0); // 💥 ClassCastException: Integer cannot be cast to String!
    }

    private static void corrupt(List rawList) {
        rawList.add(42); // Загрязнение памяти кучи
    }
}
```

## 4 Tricky Questions

### 1. Что происходит со всеми остальными методами класса, если обратиться к объекту через Raw Type?
**Ответ:** 
В соответствии с JLS §4.8 происходит каскадное стирание типов (Erasure of Member Types): **сигнатуры абсолютно всех методов и полей класса стираются до их базовых типов**. 

Если внутри обобщенного класса `class Box<T>` объявлен метод `public List<String> getTags()`, который никак не использует переменную типа $T$, то при вызове `rawBox.getTags()` компилятор вернет **сырой `List`**, а не `List<String>`. Использование сырого типа снимает дженерик-типизацию со всего интерфейса класса целиком.

### 2. В чем фундаментальная разница между сырым типом `List` и подстановочным типом `List<?>`?
**Ответ:** 
- `List` (сырой тип) **полностью отключает систему проверки типов**: в него разрешено добавить объект любого типа (`rawList.add(123)`), порождая риск загрязнения кучи (Heap Pollution) и отложенных `ClassCastException`.
- `List<?>` (unbounded wildcard) **строго соблюдает типобезопасность**: он сообщает компилятору, что коллекция типизирована определенным, но неизвестным типом. Компилятор блокирует добавление любых элементов (кроме `null`), гарантируя, что испортить данные невозможно.

### 3. В каких случаях спецификация языка Java предписывает использовать Raw Types?
**Ответ:** 
Существуют два места, где использование параметров типов синтаксически запрещено языком:
1. **В классовых литералах (Class Literals)**: спецификация требует писать `List.class`. Выражения `List<String>.class` или `List<?>.class` не компилируются.
2. **В операторе проверки типов `instanceof`**: из-за стирания типов в рантайме доступен только тип класса, поэтому проверка пишется как `obj instanceof List` (либо `obj instanceof List<?>`).

### 4. Почему сырые типы (Raw Types) до сих пор не удалили из языка Java?
**Ответ:** 
Из-за непоколебимого принципа **обратной совместимости (Backward Compatibility)** экосистемы Java. 

В мире до сих пор эксплуатируются легаси-библиотеки, скомпилированные во времена Java 1.4, а также масштабные кодовые базы, взаимодействующие со старыми модулями. Полное удаление сырых типов сделало бы невозможным использование старых `.jar` файлов без их переписывания. Однако компилятор по умолчанию помечает использование сырых типов предупреждениями `[rawtypes]` и `[unchecked]`.

## 🎯 Шпаргалка для интервью

### Главное о Raw Types за 30 секунд

- **Что это**: Использование параметризованного класса без типов: `List list = new ArrayList()`.
- **Зачем существуют**: Исключительно ради обратной совместимости с кодом Java 1.4.
- **Главные опасности**:
  - Отключает проверку типов при записи $\rightarrow$ риск `ClassCastException` в рантайме.
  - Порождает **Heap Pollution**.
  - Каскадно стирает возвращаемые типы **всех** методов класса (JLS §4.8).
- **Разница с `List<?>`**: В `List` можно положить любой объект (опасно); в `List<?>` нельзя положить ничего, кроме `null` (безопасно).
- **Где разрешены**: Только в классовых литералах (`List.class`) и `instanceof List`.

### Антипаттерны
- ❌ *Использование сырых типов в новом коде*: заменяйте на `List<?>` или точные типы.
- ❌ *Подавление `@SuppressWarnings("rawtypes")` без крайней необходимости*: маскирует потенциальные падения в продакшене.
