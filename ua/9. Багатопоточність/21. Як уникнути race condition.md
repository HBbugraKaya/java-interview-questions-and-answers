# Як уникнути race condition

---

## 🟢 Junior Level

### Коротка відповідь для співбесіди (30 секунд)
Для запобігання **Race Condition (стану гонки)** в Java застосовуються чотири фундаментальні архітектурні стратегії:

1. **Взаємне виключення (Mutual Exclusion):** захист критичних секцій за допомогою блокувань (`synchronized`, `ReentrantLock`), які гарантують, що складені операції виконуються лише одним потоком одночасно.
2. **Атомарні неблокуючі операції (Lock-Free):** використання класів пакета `java.util.concurrent.atomic` (`AtomicInteger`, `AtomicReference`, `LongAdder`), які спираються на апаратні інструкції процесора CAS (`Compare-And-Swap`).
3. **Незмінність (Immutability):** проєктування незмінних об'єктів даних (у Java 21 ідеально підходять `record` із `final`-полями). Якщо стан об'єкта неможливо змінити після створення, стан гонки неможливий за визначенням.
4. **Ізоляція потоків (Thread Confinement):** усунення розділення даних між потоками через локальні змінні стека або `ThreadLocal` (кожен потік оперує власною ізольованою копією).

---

### Порівняльна таблиця стратегій

| Стратегія | Інструменти в Java 21 | Плюси | Мінуси |
|---|---|---|---|
| **Песимістичне блокування** | `synchronized`, `ReentrantLock` | Захищає будь-які складні складені транзакції | Накладні витрати на context switch, ризик Deadlock |
| **Оптимістичний Lock-Free** | `AtomicInteger`, `LongAdder` | Максимальна швидкість (~5–10 ns), немає Deadlock | Застосовно лише до окремих полів/змінних |
| **Незмінність** | `record`, `Collections.unmodifiable*` | Абсолютна потокобезпечність «з коробки» | Навантаження на GC через створення нових копій при записі |
| **Ізоляція потоків** | Стек методу, `ThreadLocal`, `ScopedValue` | Нульова конкуренція за пам'ять, 100% ізоляція | Ризик витоків пам'яті в пулах потоків (`ThreadLocal`) |

---

### Приклади на Java 21

```java
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.ConcurrentHashMap;

public class RaceConditionPreventionDemo {

    // 1. Усунення гонки через Atomic-клас (Lock-free інкремент)
    public static class SafeCounter {
        private final AtomicInteger count = new AtomicInteger(0);
        public void increment() { count.incrementAndGet(); }
        public int get() { return count.get(); }
    }

    // 2. Усунення гонки через Immutability (Java 21 Record)
    public record UserProfile(long id, String name, String email) {
        // Компактний конструктор (Compact Constructor)
        public UserProfile {
            if (name == null) throw new IllegalArgumentException();
        }
    }

    // 3. Усунення гонки Check-Then-Act через ConcurrentHashMap
    public static class CacheService {
        private final ConcurrentHashMap<String, String> cache = new ConcurrentHashMap<>();

        public String getOrCompute(String key) {
            // Атомарна перевірка та вставка: функція викличеться рівно один раз!
            return cache.computeIfAbsent(key, k -> "ComputedValueFor_" + k);
        }
    }
}
```

## 🟡 Middle Level

### Безпечна публікація об'єктів (Safe Publication)

Одним із найпідступніших різновидів Race Condition є **гонка публікації (Publication Race)**, коли інший потік бачить посилання на створений об'єкт, але його поля ще не встигли ініціалізуватися (читання частково сконструйованого об'єкта).

#### 4 способи гарантовано безпечної публікації за специфікацією JMM:
1. **Ініціалізація у `final`-полях:** специфікація JLS (§17.5) гарантує «заморозку» (`freeze action`) значень усіх `final`-полів об'єкта при виході з конструктора, якщо посилання `this` не витекло під час конструювання.
2. **Ініціалізація у статичному ініціалізаторі класу:** гарантія ClassLoader JVM (потокобезпечна лінива ініціалізація через `Holder Pattern` / `Bill Pugh Singleton`).
3. **Запис посилання у `volatile`-поле:** виставляє бар'єр пам'яті `StoreStore`, гарантуючи завершення ініціалізації всіх полів об'єкта до публікації посилання.
4. **Публікація через монітор `synchronized` або `ReentrantLock`:** гарантує відношення Happens-Before між виходом із блокування в одному потоці та входом в іншому.

```java
// Ідіома потокобезпечної лінивої ініціалізації без синхронізації (Initialization-on-demand holder):
public class GlobalServiceRegistry {
    private GlobalServiceRegistry() {}

    private static class Holder {
        // ClassLoader гарантує неподільну і потокобезпечну ініціалізацію!
        private static final GlobalServiceRegistry INSTANCE = new GlobalServiceRegistry();
    }

    public static GlobalServiceRegistry getInstance() {
        return Holder.INSTANCE;
    }
}
```

### Атомарні композитні методи колекцій

Типова помилка розробників — використання роздільних методів у потокобезпечній колекції:

```java
// ГОНКА: два потоки можуть одночасно пройти перевірку containsKey!
if (!map.containsKey(key)) {
    map.put(key, value);
}

// РІШЕННЯ 1: Атомарна вставка при відсутності
map.putIfAbsent(key, value);

// РІШЕННЯ 2: Атомарне ліниве обчислення (ідеально для важких об'єктів)
map.computeIfAbsent(key, k -> createHeavyResource(k));

// РІШЕННЯ 3: Атомарне злиття (лічильник слів / агрегація)
map.merge(word, 1, Integer::sum);
```

### Ізоляція потоків (Thread Confinement)

Якщо дані доступні суворо одному потоку, синхронізація взагалі не потрібна:
1. **Stack Confinement (Ізоляція на стеку):** змінні, створені всередині методу, зберігаються у стековому фреймі конкретного потоку і фізично недоступні іншим потокам.
2. **ThreadLocal Confinement:** зберігання стану в `ThreadLocal`. Обов'язково вимагає виклику `remove()` у блоці `finally` при роботі з пулами потоків.

## 🔴 Senior Level

### Апаратний рівень: Архітектура ARM проти x86

Багато станів гонки, що залишаються непоміченими на ноутбуках з Intel x86, миттєво вибухають при деплої у хмару на сервери з процесорами **ARM64 (AWS Graviton, Apple Silicon, Ampere)**.

#### Причина в моделі пам'яті процесорів:
- **x86 (TSO — Total Store Order):** апаратно сувора модель пам'яті. Процесор x86 апаратно забороняє майже всі види перевпорядкування інструкцій (заборонені `StoreStore`, `LoadLoad`, `LoadStore`), допускаючи лише `StoreLoad`. Багато некоректних програм без синхронізації випадково працюють на x86 стабільно!
- **ARM64 / Apple Silicon (Weak Memory Order):** слабковпорядкована модель пам'яті. Процесор агресивно перевпорядковує будь-які незалежні читання та записи пам'яті для максимального паралелізму мікрооперацій. Несинхронізований код на ARM миттєво читає застарілі значення та пошкоджені посилання.

---

### Java 21 Scoped Values (JEP 446 / JEP 429)

У Java 21 представлено заміну застарілому механізму `ThreadLocal` — **`ScopedValue`**, розроблену спеціально для роботи з мільйонами віртуальних потоків (Virtual Threads):

```java
public class SecurityContextHolder {
    // Незмінне значення, прив'язане до скоупу виконання
    public static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

    public void processRequest(User user) {
        // Контекст безпечно та ефективно прокидається у виклики:
        ScopedValue.where(CURRENT_USER, user).run(() -> {
            doStep1();
            doStep2();
        }); // Автоматично очищається при виході зі скоупу!
    }

    private void doStep1() {
        User user = CURRENT_USER.get();
    }
}
```

#### Переваги перед `ThreadLocal`:
1. **Імутабельність:** значення `ScopedValue` неможливо мутувати зсередини задачі, виключаючи гонки змін.
2. **Обмежений час життя:** прив'язане до лексичного блоку виконання; виключає витоки пам'яті (Memory Leaks) у повторно використовуваних пулах потоків без необхідності виклику `remove()`.
3. **Оптимізація під Virtual Threads:** займає мінімум пам'яті та легко успадковується мільйонами дочірніх віртуальних потоків у Structured Concurrency.

### Архітектурні парадигми без змінюваного розділюваного стану

Senior-розробники прагнуть уникати Race Condition на рівні системного дизайну:
1. **Actor Model (Акторна модель):** сутності не ділять спільний стан у пам'яті, а обмінюються асинхронними незмінними повідомленнями через поштові скриньки (Mailbox).
2. **Event Sourcing & CQRS:** стан системи відновлюється з ланцюжка незмінних подій (Events), виключаючи паралельні перезаписи однієї сутності в оперативній пам'яті.
3. **Copy-On-Write (Копіювання при записі):** структури `CopyOnWriteArrayList` оптимізовані під сценарій: 99% швидких читань без блокувань, 1% записів зі створенням нової копії базового масиву.

## 🎯 Шпаргалка для інтерв'ю

### 1. 30-секундний есенс (Elevator Pitch)
Уникнути Race Condition можна через: взаємне виключення (`synchronized`/`ReentrantLock`), неблокуючі CAS-структури (`Atomic*`, `LongAdder`), архітектурну незмінність (`record` із `final`-полями) та ізоляцію даних на стеку потоку або в `ThreadLocal`/`ScopedValue`. При використанні `ConcurrentHashMap` критично застосовувати атомарні методи (`computeIfAbsent`, `merge`) замість парних викликів `containsKey()` + `put()`. На процесорах ARM64 зі слабкою моделлю пам'яті (AWS Graviton) помилки синхронізації проявляються значно агресивніше, ніж на x86.

### 2. 4 каверзних питання з глибокими відповідями

#### Питання 1: Чому ключове слово `final` гарантує потокобезпечну публікацію об'єкта без блокувань, і за якої умови ця гарантія порушується?
**Відповідь:**
Специфікація моделі пам'яті Java (JSR-133 / JLS §17.5) вводить правило **«Final Field Freeze»**: до моменту завершення конструктора об'єкта JVM вставляє процесорний бар'єр пам'яті `StoreStore`, який скидає значення всіх `final`-полів із регістрів та буферів запису в пам'ять до того, як посилання на новий об'єкт стане доступним іншим потокам. Читаючі потоки гарантовано побачать актуальні значення `final`-полів навіть при читанні посилання через несинхронізоване звернення.  
*Умова порушення:* якщо посилання `this` «витікає» з конструктора до його завершення (наприклад, передача `this` у слухач подій, статичний список або запуск потоку прямо з конструктора). У цьому випадку гарантія JMM повністю анулюється.

#### Питання 2: У чому архітектурна перевага `ConcurrentHashMap.computeIfAbsent()` перед традиційною зв'язкою `get()` + `synchronized` + `put()`?
**Відповідь:**
1. **Атомарність без глобального блокування:** `computeIfAbsent()` блокує лише конкретний кошик (bucket / вузол хеш-таблиці) через тонкий замок на рівні першої ноди, не блокуючи інші кошики мапи.
2. **Гарантія одноразового обчислення (Single Execution):** передана лямбда-функція обчислення ресурсу гарантовано виконається **рівно один раз** для заданого ключа, запобігаючи дублюванню важких ініціалізацій (наприклад, з'єднань із БД).
3. **Усунення гонки Check-Then-Act:** перевірка наявності ключа та вставка нового вузла об'єднані в єдину неподільну операцію під контролем внутрішнього механізму колекції.

#### Питання 3: Чому помилки Race Condition значно частіше проявляються на процесорах архітектури ARM (Apple Silicon, AWS Graviton), ніж на Intel x86?
**Відповідь:**
Процесори архітектури x86 реалізують модель пам'яті **TSO (Total Store Order)**, яка апаратно гарантує збереження порядку практично всіх читань і записів (за винятком `StoreLoad`). На x86 компілятор JIT опускає багато бар'єрів пам'яті, оскільки залізо саме впорядковує інструкції.  
Процесори ARM64 використовують модель зі **слабким порядком пам'яті (Weak Ordering)**. Ядро процесора активно переставляє місцями незалежні інструкції читання та запису для максимальної утилізації обчислювальних конвеєрів. Якщо в Java-коді пропущено синхронізацію або `volatile`, процесор ARM негайно здійснить перевпорядкування, спричинивши читання застарілих даних.

#### Питання 4: Як механізм `ScopedValue` у Java 21 вирішує проблеми продуктивності та витоків пам'яті традиційного `ThreadLocal`?
**Відповідь:**
1. **Захист від витоків:** `ThreadLocal` живе в карті потоку `threadLocals` до явного виклику `remove()`. У пулах потоків забутий `remove()` призводить до витоків пам'яті в Metaspace та забруднення контексту між задачами. `ScopedValue` прив'язаний до лексичного блоку виконання (`where().run(...)`) і очищається середовищем виконання автоматично при виході зі скоупу.
2. **Незмінність:** значення `ScopedValue` не можна перезаписати після прив'язки до скоупу, що гарантує безпеку передачі контексту.
3. **Масштабованість:** `ScopedValue` оптимізований для мільйонів віртуальних потоків (Project Loom): дочірні потоки можуть розділяти контекст батька за посиланням без дублювання хеш-таблиць.

### 3. Типові помилки та Red Flags

❌ **"Використання `Collections.synchronizedList()` робить будь-який обхід списком потокобезпечним."**  
*Правильно:* Синхронізовані лише окремі методи (`add`, `get`). Ітерація через цикл `for (Item x : list)` поверх `synchronizedList` **зобов'язана** бути явно огорнута в `synchronized(list)`, інакше паралельна модифікація списку викине `ConcurrentModificationException`.

❌ **"Витік `this` у конструкторі за наявності `final`-полів."**  
*Правильно:* Передача `this` у зовнішні структури до завершення конструктора позбавляє об'єкт гарантій потокобезпечної публікації JMM.

❌ **"Використання `CopyOnWriteArrayList` у колекціях із високою частотою запису."**  
*Правильно:* Кожна операція додавання або видалення копіює весь базовий масив у купі (`Arrays.copyOf`), що створює колосальне навантаження на збирач сміття при частих мутаціях.
