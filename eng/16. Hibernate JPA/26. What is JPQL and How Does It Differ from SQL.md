# What is JPQL and How Does It Differ from SQL

**JPQL (Java Persistence Query Language)** is an object-oriented, declarative query language defined by the JPA specification. While standard SQL operates on physical relational tables, rows, and database columns, JPQL queries **Java entity classes, their fields, and object associations**, abstracting application business logic from underlying database engine dialects.

---

## 🟢 Junior Level

### Core Difference: Java Entities vs. Relational Tables

In native SQL, queries are coupled to physical database schemas. In JPQL, queries operate directly on Java classes and attributes:

```java
// SQL (Coupled to physical table and column names):
// SELECT * FROM app_users WHERE user_age >= 18;

// JPQL (Operates on Java Entity classes and heap properties):
TypedQuery<User> query = entityManager.createQuery(
    "SELECT u FROM User u WHERE u.age >= :minAge", 
    User.class
);
query.setParameter("minAge", 18);
List<User> adults = query.getResultList();
```

---

### Comparison Matrix: JPQL vs. SQL

| Feature | JPQL (Java Persistence) | SQL (Structured Query Language) |
| :--- | :--- | :--- |
| **Target Unit** | Java Entity class (`User`) | Physical database table (`app_users`) |
| **Attributes & Fields** | Java properties (`u.birthDate`) | Physical column names (`birth_date`) |
| **Association Traversal** | Dot navigation (`o.user.address.city`) | Explicit relational constructs (`JOIN ... ON ...`) |
| **Portability** | Dialect-agnostic (Translated by ORM) | Bound to specific vendor SQL dialects |
| **Polymorphism** | Native hierarchy querying (`FROM Payment`) | Requires manual `UNION` or `CASE` expressions |
| **Case Sensitivity** | Keywords case-insensitive; **entity/field names case-sensitive** | Determined by database collation settings |

---

### Basic Syntax and Parameters

```java
// 1. Filtering and Named Parameters (SQL injection safe):
String jpql1 = "SELECT u FROM User u WHERE u.email = :email";

// 2. Object-oriented JOIN via relationship property (No ON condition needed):
String jpql2 = "SELECT o FROM Order o JOIN o.items i WHERE i.price > 1000";

// 3. Aggregate Functions:
String jpql3 = "SELECT COUNT(u), AVG(u.age) FROM User u WHERE u.active = true";

// Parameter binding:
User user = entityManager.createQuery(jpql1, User.class)
    .setParameter("email", "alex@example.com")
    .getSingleResult();
```

## 🟡 Middle Level

### Advanced JPQL Features

#### 1. DTO Constructor Expressions (`SELECT new ...`)
Bypasses entity snapshot allocation in the First-Level Cache by projecting query columns directly into immutable Java Records or DTOs:
```java
public record UserSummaryDto(Long id, String fullName, String email) {}

List<UserSummaryDto> dtos = entityManager.createQuery("""
    SELECT new com.example.dto.UserSummaryDto(u.id, u.name, u.email)
    FROM User u
    WHERE u.active = true
    """, UserSummaryDto.class).getResultList();
```

#### 2. Polymorphic Queries with `TYPE` and `TREAT`
Given an abstract `Payment` parent entity with `CardPayment` and `CryptoPayment` subclasses:
```java
// Polymorphic retrieval of all payment types:
List<Payment> all = entityManager.createQuery("FROM Payment", Payment.class).getResultList();

// Subclass filtering via TYPE:
List<Payment> cardsOnly = entityManager.createQuery(
    "SELECT p FROM Payment p WHERE TYPE(p) = CardPayment", 
    Payment.class
).getResultList();

// Downcasting via TREAT:
List<Payment> visaPayments = entityManager.createQuery(
    "SELECT p FROM Payment p WHERE TREAT(p AS CardPayment).cardNumber LIKE '4%'", 
    Payment.class
).getResultList();
```

---

### Implicit vs. Explicit JOINs

A common trap in JPQL is relying on dot-navigation across associations:
```java
// Implicit Join (Dot navigation):
List<Order> orders = entityManager.createQuery(
    "SELECT o FROM Order o WHERE o.user.address.city = 'London'", 
    Order.class
).getResultList();
```
- Hibernate automatically compiles `o.user.address.city` into two nested SQL `INNER JOIN` statements.
- **Risk:** Because implicit joins always generate `INNER JOIN`s, any `Order` where `user` is null or `address` is null will be silently omitted from query results.
- *Best Practice:* Always use **explicit `JOIN`** (`LEFT JOIN` / `INNER JOIN`) to maintain full visibility and control over relational join semantics.

## 🔴 Senior Level

### The Hibernate 6 SQM Compilation Pipeline

In Hibernate 6, the query compilation engine was completely re-architected on top of the **SQM (Semantic Query Model)** subsystem:

```
                  HIBERNATE 6 QUERY TRANSLATION ARCHITECTURE
                  
  [ JPQL / HQL String ]
           │
           ├──► 1. Lexical & Syntax Parsing (Antlr 4)
           ▼
  [ SQM AST (Semantic Query Model) ] ──► Validated against JPA Metamodel
           │
           ├──► 2. SqlAstTranslator (Informed by Database Dialect)
           ▼
  [ SQL AST ] 
           │
           ├──► 3. SQL Text Generation & Parameter Binding
           ▼
  [ Native SQL: SELECT t0.id... FROM app_users t0 ... ] ──► JDBC Driver Execution
```

---

### JPQL Execution, L1 Cache Hydration, and Smart Auto-Flush

1. **JPQL Always Hits the Database:** Unlike `find()`, a JPQL query cannot be satisfied solely from in-memory heap caches. It always generates and executes a physical SQL `SELECT` statement.
2. **Identity Map Hydration:** When rows return from the database, Hibernate inspects the `PersistenceContext` entity cache (`entitiesByKey`). If an entity with that primary key is already `Managed`, the raw database row is discarded and the existing in-memory instance is returned, preserving reference equality.
3. **Query-Space Auto-Flush:** Before running a JPQL query, Hibernate inspects the current session's dirty state. If modified entities intersect with the tables referenced by the JPQL query ("query spaces"), Hibernate triggers an automatic `flush()` to synchronize database state prior to query execution.

---

### Window Functions and CTEs in Hibernate 6 HQL/JPQL

Historically, developers were forced to resort to native SQL (`createNativeQuery`) for analytical queries. Hibernate 6 elevates HQL/JPQL to support modern SQL-99/2003 analytical specifications natively:

```java
// Window functions directly in JPQL/HQL:
List<Object[]> rankedOrders = entityManager.createQuery("""
    SELECT o.id, o.amount, 
           ROW_NUMBER() OVER (PARTITION BY o.user.id ORDER BY o.amount DESC) 
    FROM Order o
    """, Object[].class).getResultList();

// Common Table Expressions (CTE):
List<User> topUsers = entityManager.createQuery("""
    WITH UserTotals AS (
        SELECT o.user.id as userId, SUM(o.amount) as total
        FROM Order o
        GROUP BY o.user.id
    )
    SELECT u FROM User u JOIN UserTotals ut ON u.id = ut.userId
    WHERE ut.total > 100000
    """, User.class).getResultList();
```

## 4 Tricky Questions

### 1. We load `User(id=1)`, mutate its name via `user.setName("Updated")`, then execute JPQL `SELECT u FROM User u WHERE u.id = 1`. What name does the returned object have, and does an SQL SELECT run?

**Answer:**
1. A physical SQL `SELECT` **will be sent to the database** (JPQL queries always execute database queries).
2. Prior to the query execution, Hibernate's `Auto-Flush` mechanism detects a dirty state on the `User` table and issues an SQL `UPDATE users SET name = 'Updated' WHERE id = 1`.
3. The returned instance has the name **"Updated"**. Furthermore, it is the exact same Java object reference (`assert user == result;`) due to First-Level Cache identity management.

---

### 2. What is the fundamental difference between `JOIN` and `JOIN FETCH` in JPQL?

**Answer:**
1. Plain `JOIN` (`SELECT o FROM Order o JOIN o.items i`) is used exclusively for filtering, projection, or aggregation. The associated child collection `items` **remains uninitialized** (lazy proxy). Calling `order.getItems().size()` subsequently triggers $N+1$ secondary SQL queries.
2. `JOIN FETCH` (`SELECT o FROM Order o JOIN FETCH o.items i`) instructs Hibernate to perform the SQL join and **eagerly hydrate the child collection in memory** in a single SQL statement, eliminating the $N+1$ query problem.

---

### 3. Why does a bulk mutation query (`UPDATE/DELETE` in JPQL) bypass `@PreRemove`/`@PreUpdate` lifecycle callbacks and risk stale L1 data?

**Answer:**
1. Bulk JPQL queries (`entityManager.createQuery("DELETE FROM User u WHERE u.status = 'INACTIVE'").executeUpdate()`) translate directly into a single SQL statement executed on the database server.
2. Individual entity instances are never instantiated or loaded into JVM memory; therefore, JPA lifecycle event listeners (`@PreRemove`, `@PostRemove`) **never fire**.
3. If any affected entities are currently managed within the First-Level Cache, their in-memory snapshots are not invalidated, causing the persistence context to diverge from actual database state unless explicitly cleared (`em.clear()`).

---

### 4. Why does `SELECT COUNT(u) FROM User u` return a `java.lang.Long` rather than a `java.lang.Integer`?

**Answer:**
1. The JPA specification explicitly defines aggregate return types to prevent overflow on large datasets:
   - `COUNT` unconditionally returns **`java.lang.Long`** (supporting tables exceeding 2.14 billion rows).
   - `AVG` unconditionally returns **`java.lang.Double`**.
   - `SUM` returns the numeric type corresponding to the evaluated field (`Long` for integer primitives, `BigDecimal` for floating/exact numerics).
2. Attempting to cast the result to `(Integer) query.getSingleResult()` results in a runtime `ClassCastException`.

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
> "JPQL is JPA's object-oriented query language that queries Java entity classes and attributes rather than relational tables and columns. It provides database portability, type-safe associations via dot notation, polymorphic inheritance querying (`TYPE`/`TREAT`), and DTO constructor projections (`SELECT new ...`). Unlike `find()`, JPQL queries always issue physical SQL queries to the database while preserving entity identity via the First-Level Cache. In Hibernate 6, the SQM engine provides native support for window functions and CTEs, eliminating the historic need for Native SQL in complex reporting scenarios."

---

### Key Production Metrics & Indicators
- **`QueryPlanCache` Hit Ratio**: Monitored via Hibernate statistics (`generate_statistics=true`). A low plan cache hit ratio indicates high CPU overhead from repeated JPQL AST parsing.
- **Implicit Cartesian Product Joins**: Generated queries containing unintentional multiple cross/inner joins resulting from excessive dot-navigation.
- **Bulk Update Stale State Incidents**: Data divergence caused by executing bulk JPQL mutations without `@Modifying(clearAutomatically = true)`.

---

### Red Flags (What NOT to Say)
- ❌ *"JPQL reads entities directly from the L1 cache without issuing SQL queries."* — JPQL queries always execute database SQL statements.
- ❌ *"I use physical database table names in JPQL queries."* — JPQL strictly references Java entity class names.
- ❌ *"Concatenating user input into JPQL strings is safe because JPQL isn't raw SQL."* — False. String concatenation in JPQL is completely vulnerable to JPQL injection attacks.
- ❌ *"JPQL cannot execute window functions or CTEs."* — Starting with Hibernate 6, HQL/JPQL natively supports both window functions and CTEs.
