# Чи можна змінити вміст String через рефлексію

---

## 🟢 Junior Level

**Технічно у старих версіях Java (до Java 16) це було можливо, але в сучасній Java (Java 17, 21+) віртуальна машина типово це категорично забороняє.**

Клас `String` спроєктований як **абсолютно незмінний (immutable)**. Проте механізм Java Reflection історично дозволяв обійти інкапсуляцію, отримати доступ до приватних полів через `setAccessible(true)` і змінити внутрішній масив символів.

### Суть у 30 секундах
1. **У Java 8 і нижче:** Можна було отримати приватне поле `value` через `getDeclaredField("value")`, викликати `setAccessible(true)` і напряму перезаписати символи в масиві.
2. **У Java 17 та 21+:** Сильна інкапсуляція модульної системи (JEP 403: Strongly Encapsulate JDK Internals) **забороняє доступ до внутрішніх деталей `java.lang.String`**. Спроба виклику `setAccessible(true)` негайно завершиться фатальним винятком `java.lang.reflect.InaccessibleObjectException`. Обійти цей захист можна лише примусовим прапорцем запуску JVM: `--add-opens java.base/java.lang=ALL-UNNAMED`.

```java
// Приклад коду (працює в Java 8 або в Java 17+ суворо з прапорцем --add-opens):
String greeting = "Hello";

Field valueField = String.class.getDeclaredField("value");
valueField.setAccessible(true); // У Java 17+ без прапорця впаде з InaccessibleObjectException!

byte[] value = (byte[]) valueField.get(greeting);
value[0] = 'J'; // Підміняємо 'H' на 'J'

System.out.println(greeting); // Надрукує "Jello"!
```

**Категоричний висновок:** Робити це в продакшені суворо заборонено. Мутація рядків руйнує безпеку JVM, ламає `String Pool` і призводить до пошкодження колекцій `HashMap` та `HashSet`.

## 🟡 Middle Level

### Катастрофічні наслідки модифікації String

1. **Зараження пулу рядків (String Pool Contamination):**
   Рядкові літерали зберігаються в пулі в єдиному екземплярі. Якщо ви зміните вміст літерала `"admin"`, **усі посилання на `"admin"` у всій JVM зміняться**:
   ```java
   String s1 = "admin";
   // Мутуємо s1 через рефлексію на "guest"
   
   String s2 = "admin"; 
   System.out.println(s2); // Надрукує "guest"!
   // Будь-яка авторизаційна перевірка if (user.getRole().equals("admin")) зламана в усьому застосунку!
   ```

2. **Руйнування контракту `HashMap` та `HashSet`:**
   Геш-код рядка кешується в приватному полі `private int hash` при першому виклику `hashCode()`.
   Якщо рядок був ключем у `HashMap`, а потім його масив `value` змінили через рефлексію:
   - Поле `hash` **не перераховується** і залишається старим.
   - Спроба знайти ключ за новим значенням `map.get("Jello")` поверне `null` (оскільки геш обчислюється наново від нового тексту і потрапляє в інший кошик/bucket).
   - Спроба знайти за старим значенням `map.get("Hello")` також поверне `null` (оскільки метод `.equals()` побайтово порівнює новий вміст і не знайде збігу).
   - **Результат:** Запис назавжди застряє в `HashMap` як мертве некероване сміття (Memory Leak).

3. **Порушення узгодженості кодування (`coder` mismatch у Java 9+):**
   Якщо рядок мав `coder = LATIN1` (1 байт на символ), а через рефлексію в масив `byte[]` записали байти кирилиці (що вимагають 2 байти і `coder = UTF16`), рядок незворотно ламається: методи `charAt()`, `length()` та `getBytes()` починають повертати зіпсоване сміття.

## 🔴 Senior Level

### Еволюція обмежень: JEP 261, JEP 396 та JEP 403
Розробники платформи Java планомірно закривали шпарини обходу інкапсуляції:
- **Java 9 (JEP 261):** Введено модульну систему JPMS (Project Jigsaw). Пакет `java.lang` модуля `java.base` оголошено закритим для глибокої рефлексії (deep reflection), але за замовчуванням виводилися лише попередження (Illegal Reflective Access Warning).
- **Java 16 (JEP 396):** Сильна інкапсуляція увімкнена типово (Deny by default).
- **Java 17 (JEP 403):** Остаточне видалення прапорця `--illegal-access`. Тепер доступ до приватних полів ядра JDK через `setAccessible(true)` **жорстко заблокований**. Єдиний спосіб пробити захист — передача аргументу JVM під час запуску процесу:
  `--add-opens java.base/java.lang=ALL-UNNAMED`

### JIT-оптимізації, анотація `@Stable` та константний колапс
Поле `value` у класі `String` позначено внутрішньою анотацією HotSpot `@Stable`:
```java
public final class String {
    @Stable
    private final byte[] value;
    ...
}
```
**Що робить `@Stable` для C2 JIT-компілятора?**
Вона повідомляє компілятору, що після ініціалізації об'єкта елементи масиву ніколи не будуть змінені:
1. Якщо рядок є константою часу компіляції (Compile-Time Constant) або глобальною статичною константою, компілятор C2 виконує **Constant Folding**: він безпосередньо вбудовує байти рядка в машинний асемблерний код або зберігає їх у регістри CPU.
2. Якщо після цього ви зміните масив `value` у пам'яті купи через рефлексію або `sun.misc.Unsafe`, **JIT-скомпільований машинний код не помітить цих змін!** Він продовжить використовувати старе заінлайнене значення.
3. Виникає фатальна розсинхронізація: у режимі інтерпретатора Java бачить змінений рядок, а в скомпільованому C2 коді — старий!

### Порушення моделі пам'яті Java (JMM §17.5 Final Field Semantics)
Специфікація мови Java (JLS §17.5) гарантує безпеку публікації (Safe Publication) для `final` полів: потік, що отримує посилання на створений об'єкт, гарантовано бачить коректно ініціалізовані значення всіх його `final` полів без явної синхронізації та бар'єрів пам'яті.
Модифікація `final` полів через рефлексію:
- Порушує семантику freeze-action наприкінці конструктора.
- Позбавляє операцію відношення *happens-before*.
- Інші потоки багатопотокового застосунку можуть побачити частково записані байти, неініціалізовану пам'ять або розірвані стани перегонів (Data Race).

## 4 Tricky Questions

### 1. Що станеться при спробі виконати `String.class.getDeclaredField("value").setAccessible(true)` у Java 17/21 за замовчуванням?
**Відповідь:**
Буде викинуто виняток:
`java.lang.reflect.InaccessibleObjectException: Unable to make field private final byte[] java.lang.String.value accessible: module java.base does not "opens java.lang" to unnamed module`
Починаючи з Java 17 (JEP 403), модульна система суворо інкапсулює внутрішні елементи модуля `java.base`. Вимкнути цей захист зсередини самого Java-коду неможливо; це може зробити виключно системний адміністратор під час старту JVM через параметр командного рядка:
`--add-opens java.base/java.lang=ALL-UNNAMED`.

### 2. Якщо зловмисник змінив вміст рядка-ключа в `HashMap` через рефлексію, чому виклик `map.get("нове_значення")` поверне `null`?
**Відповідь:**
Тому що метод `String.hashCode()` кешує обчислене значення в полі `private int hash`:
1. Під час першого розміщення рядка в `HashMap` було розраховано та закешовано початковий геш. За ним елемент було покладено у певний кошик (bucket) таблиці.
2. Мутація масиву `byte[] value` через рефлексію **не скидає поле `hash`**.
3. Під час виклику `map.get("нове_значення")` аргумент обчислює правильний новий геш і звертається в зовсім інший кошик `HashMap`, де елемента немає $\to$ повертається `null`.
4. Під час виклику `map.get("старе_значення")` кошик збіжиться, але при посимвольному порівнянні метод `equals()` поверне `false` $\to$ також повернеться `null`.

### 3. Чому після мутації рядка через рефлексію скомпільований C2 JIT метод може продовжувати повертати старе значення?
**Відповідь:**
Через внутрішню анотацію `@Stable` на полі `byte[] value`.
Компілятор HotSpot C2 довіряє цій анотації та вважає масив незмінним після конструювання. Під час оптимізації методу компілятор виконує Constant Folding і вбудовує значення байтів або довжину рядка безпосередньо в машинний код як константи процесора. Мутація масиву в купі не інвалідує скомпільований машинний код C2, внаслідок чого метод продовжує повертати старе значення.

### 4. Чи можна обійти обмеження модульної системи Java 17 без прапорця `--add-opens`, використовуючи клас `sun.misc.Unsafe`?
**Відповідь:**
Технічно через `Unsafe` можна було записати байти напряму в нативну пам'ять за зміщенням поля:
```java
// Отримання зміщення поля value:
long valueOffset = unsafe.objectFieldOffset(String.class.getDeclaredField("value"));
// Прямий запис у пам'ять в обхід reflection checks:
unsafe.putObject(str, valueOffset, newBytes);
```
Проте в сучасних версіях Java (Java 17+) метод `objectFieldOffset` для полів класів пакета `java.lang` також заблокований або викидає виняток `UnsupportedOperationException`, а в Java 21+ клас `Unsafe` активно виводиться з експлуатації (JEP 471). Використовувати цей механізм неможливо без явних попереджень та прапорців деградації.

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь
> «У Java 8 змінити рядок через рефлексію (`Field.setAccessible(true)` на полі `value`) було можливо, але в сучасних версіях (Java 17, 21+) це заблоковано модульною системою (JEP 403) і викидає `InaccessibleObjectException`. Обійти блокування можна лише явним прапорцем `--add-opens java.base/java.lang=ALL-UNNAMED`. У реальних проєктах модифікація рядків категорично заборонена: вона руйнує безпеку JVM, ламає `String Pool`, корумпує ключі в `HashMap` та ламає JIT-оптимізації компілятора C2 через анотацію `@Stable`».

### Ключові тези для Senior-інтерв'ю
1. **JEP 403 (Java 17+):** Примусова інкапсуляція ядра JDK; рефлексивний доступ до приватних полів `java.lang.String` заблоковано на рівні JVM.
2. **Прапорець `--add-opens`:** Єдиний спосіб відкрити пакет `java.lang` для рефлексії під час старту JVM.
3. **Анотація `@Stable`:** Повідомляє JIT-компілятору про незмінність елементів масиву; мутація призводить до розсинхронізації інтерпретатора та машинного коду C2.
4. **Псування `HashMap`:** Поле `hash` не перераховується автоматично, роблячи ключі нечитабельними за будь-яким значенням.
5. **String Pool Impact:** Зміна літерала мутує його для всіх класів і потоків у всій JVM.

### Червоні прапорці (Чого говорити категорично не можна)
- ❌ Стверджувати: «У Java 17/21 можна легко змінити рядок звичайним `setAccessible(true)`» (забуваючи про `InaccessibleObjectException` та модулі).
- ❌ Заявляти, що модифікація рядка через рефлексію — прийнятний патерн в архітектурі.
- ❌ Вважати, що `hashCode()` рядка автоматично перераховується під час мутації масиву байтів.
- ❌ Не знати про вплив анотації `@Stable` на C2 JIT-компілятор.
