# What is blocking code and how to distinguish it from non-blocking

---

## 🟢 Junior Level

**Blocking code** is code whose execution suspends (freezes) the current operating system thread until an external operation completes (e.g., disk I/O, database queries, socket reads, or awaiting a mutex lock). During this wait period, the thread is parked in a wait state and cannot execute any other work.

**Non-blocking code** initiates an operation and **immediately returns control** to the caller. The thread remains free to execute other concurrent tasks. When the asynchronous operation finishes, the result is delivered via a callback, a `CompletableFuture`, or a reactive stream.

### Direct Code Comparison

```java
// BLOCKING CODE:
// Thread freezes for ~200ms awaiting incoming network bytes.
// The OS thread sits idle, holding ~1MB of stack memory.
InputStream in = socket.getInputStream();
int data = in.read(); 

// BLOCKING INVOCATION IN ASYNC CODE:
CompletableFuture<String> future = service.fetchAsync();
String result = future.get(); // CALLER THREAD IS BLOCKED WAITING FOR RESPONSE

// NON-BLOCKING CODE:
// Request is dispatched; the caller thread is immediately released.
// The callback runs only when bytes actually arrive on the socket.
httpClient.sendAsync(request, HttpResponse.BodyHandlers.ofString())
    .thenAccept(response -> System.out.println("Payload: " + response.body()));
```

## 🟡 Middle Level

### Catalog of Common Blocking Operations in Java

Many developers mistakenly believe blocking only occurs during explicit `Thread.sleep()` or `future.get()` calls. In enterprise Java systems, blocking occurs across multiple layers:

1. **Classic Java I/O (`java.io.*`)**: `FileInputStream`, `FileOutputStream`, `BufferedReader.readLine()`, `Socket.getInputStream()`.
2. **Relational Database Access via JDBC**: `Connection.prepareStatement()`, `Statement.executeQuery()`, Hibernate/JPA queries (traditional JDBC drivers synchronously block the calling OS thread).
3. **Synchronization Primitives**: Entering a `synchronized` block, acquiring `ReentrantLock.lock()`, `CountDownLatch.await()`, `BlockingQueue.take()`.
4. **Synchronous Logging**: Standard Logback or Log4j appenders (`FileAppender`, `ConsoleAppender`) acquire internal synchronized locks and perform synchronous disk or console writes.
5. **DNS Lookups**: `InetAddress.getByName(host)` blocks the calling thread during remote DNS resolution.

### Distinguishing Blocking from Non-Blocking Code

| Characteristic | Blocking Code | Non-Blocking Code |
| :--- | :--- | :--- |
| **Control Return** | Only after operation finishes | Immediately (returns `Future`, `Stage`, or `void`) |
| **Thread State in OS** | `WAITING`, `TIMED_WAITING`, `BLOCKED` (or `D-state` in Linux) | `RUNNABLE` (actively executing CPU instructions) |
| **Network Clients** | `java.net.Socket`, Apache HttpClient, `RestTemplate` | Java 11 `HttpClient.sendAsync()`, Netty, Spring `WebClient` |
| **Database Access** | JDBC, Spring Data JPA, MyBatis | R2DBC, Vert.x Reactive SQL, Mongo Reactive Streams |

> [!WARNING]
> A method returning `CompletableFuture<T>` **does not guarantee** that the method is non-blocking!

```java
// THE FAKE ASYNC ANTI-PATTERN:
public CompletableFuture<User> getUser(Long id) {
    // Blocking JDBC executed directly on the calling thread before returning!
    User user = jdbcTemplate.queryForObject("SELECT ...", id); 
    return CompletableFuture.completedFuture(user);
}
```

## 🔴 Senior Level

### OS Kernel Mechanics: `read()` Syscalls vs `epoll()` Multiplexing

The distinction between blocking and non-blocking I/O is rooted in OS kernel system calls:

1. **Synchronous Blocking I/O (`read` / `recvfrom`)**:
   - The thread invokes `read(fd)`.
   - The Linux kernel transitions the process into sleep (`TASK_UNINTERRUPTIBLE` or `TASK_INTERRUPTIBLE`), placing it on the socket's wait queue and context-switching to another thread.
   - Each thread retains its full call stack (~1 MB via `-Xss`).
   - Sizing limit: 10,000 concurrent sockets require 10,000 OS threads (~10 GB RAM just for thread stacks, accompanied by severe context-switching overhead).
2. **Non-Blocking Multiplexed I/O (`epoll` / `kqueue` / Java NIO)**:
   - Sockets are registered with an `epoll` selector.
   - A single EventLoop thread (as in Netty) invokes `epoll_wait()`, polling readiness across thousands of file descriptors.
   - When packets arrive on the network interface card (NIC), the kernel wakes the EventLoop, which reads the ready bytes and triggers downstream `CompletableFuture` stages.
   - Sizing limit: A single EventLoop thread comfortably handles 50,000+ active concurrent connections.

### Automated Detection of Hidden Blocking: BlockHound

In reactive and non-blocking architectures, manual code reviews cannot catch every blocking call. Project Reactor provides **BlockHound**, a Java bytecode agent that intercepts blocking system calls and throws an exception if a non-blocking thread is blocked:

```java
// Initialize during application startup or in test suites:
BlockHound.install();

// If code inside ForkJoinPool or a Netty EventLoop thread calls Thread.sleep() or JDBC,
// BlockHound immediately fails fast:
// reactor.blockhound.BlockingOperationError: Blocking call! java.io.FileInputStream#readBytes
```

## 4 Tricky Questions

### 1. Is standard logging via `log.info("Order: {}", id)` considered a blocking operation? What risk does it pose to asynchronous pipelines?

**Answer:**
**Yes, in standard configurations, it is blocking!**
Default Logback and Log4j appenders (`ConsoleAppender`, `FileAppender`) synchronously format the log message, acquire an internal synchronization monitor lock (`synchronized`), and perform I/O writes to disk or the OS stdout buffer. In high-concurrency `CompletableFuture` pipelines, heavy logging can induce severe thread contention and disk I/O wait states across shared worker threads.
*Solution:* Always configure asynchronous loggers (`AsyncAppender` in Logback or LMAX `Disruptor`-based logging in Log4j2).

### 2. If a method is declared as `public CompletableFuture<String> getDataAsync()`, how can you prove conclusively that it does not block the caller thread?

**Answer:**
1. **Source Code Inspection**: Verify that no blocking I/O (JDBC, sockets, files) occurs prior to returning the future, and that tasks are dispatched to non-blocking drivers (Netty, WebClient) or offloaded via `supplyAsync(..., dedicatedExecutor)`.
2. **Dynamic Instrumentation**: Run the code under **BlockHound** with the calling thread marked as non-blocking.
3. **Thread ID & Latency Sampling**: Measure `Thread.currentThread().getId()` and execution duration across the method call. If the method takes more than a few microseconds to return to the caller, blocking initialization code is executing inline.

### 3. What are the differences between thread states `BLOCKED`, `WAITING`, and `TIMED_WAITING` in thread dumps?

**Answer:**
- **`BLOCKED`**: The thread is waiting to acquire an intrinsic monitor lock (`synchronized`) that is currently held by another thread.
- **`WAITING`**: The thread voluntarily yielded the CPU and is waiting indefinitely for an explicit notification from another thread (`Object.wait()`, `Thread.join()`, or `LockSupport.park()` as used in `CompletableFuture.get()`).
- **`TIMED_WAITING`**: The thread is waiting with a defined timeout and will automatically unpark when the duration expires: `Thread.sleep(ms)`, `Object.wait(timeout)`, or `CompletableFuture.get(timeout, unit)`.

### 4. How did Java 21 Virtual Threads radically redefine the relationship between blocking code and scalability?

**Answer:**
Prior to Java 21, blocking code blocked an **expensive native OS thread (carrier thread)**, pinning ~1 MB of stack memory and wasting kernel scheduling time.
In Java 21, when a **Virtual Thread** encounters a blocking operation (socket read, file I/O, `LockSupport.park()`), the JVM runtime **unmounts** the virtual thread from its underlying OS carrier thread. The carrier thread immediately executes other virtual threads. Blocking on a virtual thread becomes virtually free, achieving reactive-level scalability using simple, sequential, imperative blocking code.

## 🎯 Interview Cheat Sheet

### Summary in 60 Seconds
- Blocking code halts the OS thread (via `read`, `recv`, or `park`), putting it in a wait state where it consumes memory but does no CPU work.
- Non-blocking code initiates work and immediately returns, utilizing OS multiplexing (`epoll`) or callbacks.
- Common blocking operations: traditional `java.io`, JDBC, `Thread.sleep()`, `future.get()`, `synchronized` monitors, and synchronous file logging.
- `CompletableFuture` return types can disguise blocking operations if blocking code executes prior to returning or within the caller thread.
- Java 21 Virtual Threads unmount from carrier threads during blocking I/O, rendering traditional blocking code non-blocking at the OS level.

### Common Interview Mistakes
- Equating blocking exclusively with `Thread.sleep()`.
- Assuming wrapping blocking code in `CompletableFuture.supplyAsync()` makes the code non-blocking (it merely shifts the block to a pool worker thread).
- Overlooking the blocking overhead of synchronous logging and JDBC drivers.
