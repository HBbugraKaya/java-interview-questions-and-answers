# Какие типы наследования поддерживает JPA

Объектно-ориентированная парадигма Java поддерживает полиморфизм и наследование классов, в то время как реляционная модель баз данных оперирует плоскими таблицами и внешними ключами (проблема Object-Relational Impedance Mismatch). Спецификация **JPA** определяет три фундаментальные стратегии отображения иерархий наследования на таблицы СУБД (**`SINGLE_TABLE`**, **`JOINED`**, **`TABLE_PER_CLASS`**), а также шаблон переиспользования общих свойств **`@MappedSuperclass`**.

---

## 🟢 Junior Level

### 3 стратегии наследования JPA

Стратегия задается аннотацией **`@Inheritance(strategy = InheritanceType...)`** на корневом классе иерархии:

```
               3 СТРАТЕГИИ ОТОБРАЖЕНИЯ ИЕРАРХИИ В БАЗУ ДАННЫХ
               
   1. SINGLE_TABLE (По умолчанию)     2. JOINED                     3. TABLE_PER_CLASS
      ┌─────────────────────────┐       ┌──────────────────────┐      ┌──────────────────────┐
      │     payments            │       │   payments (Общая)   │      │    card_payments     │
      ├─────────────────────────┤       ├──────────────────────┤      ├──────────────────────┤
      │ id, dtype, amount,      │       │ id, amount           │      │ id, amount, card_num │
      │ card_num, cash_date     │       └──────────┬───────────┘      └──────────────────────┘
      └─────────────────────────┘                  │ PK/FK                    ┌──────────────────────┐
      (Все классы в 1 таблице)          ┌──────────┴───────────┐      │    cash_payments     │
                                        │    card_payments     │      ├──────────────────────┤
                                        ├──────────────────────┤      │ id, amount, cash_date│
                                        │ id (FK), card_num    │      └──────────────────────┘
                                        └──────────────────────┘      (Изолированные таблицы)
```

#### Базовый пример настройки:
```java
// Корневой класс иерархии:
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "payment_type", discriminatorType = DiscriminatorType.STRING)
public abstract class Payment {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private BigDecimal amount;
}

// Подкласс 1: Оплата картой
@Entity
@DiscriminatorValue("CARD")
public class CardPayment extends Payment {
    private String cardNumber;
}

// Подкласс 2: Оплата наличными
@Entity
@DiscriminatorValue("CASH")
public class CashPayment extends Payment {
    private String cashierName;
}
```

## 🟡 Middle Level

### Детальный анализ стратегий и их компромиссов

#### 1. `InheritanceType.SINGLE_TABLE` (Одна таблица на всю иерархию)
Все поля всех классов иерархии хранятся в одной физической таблице. Для различения типов используется колонка-дискриминатор (`DTYPE` по умолчанию).
- **Плюсы:** 
  - Максимальная производительность на чтение и запись (отсутствуют `JOIN` и `UNION`).
  - Полиморфные запросы выполняются молниеносно: `SELECT * FROM payments`.
- **Минусы:**
  - Разреженность данных (обилие колонок со значением `NULL`).
  - **Невозможность добавить ограничение `NOT NULL`** в СУБД на поля подклассов (колонка `card_number` обязана быть `NULL`, иначе нельзя будет вставить `CashPayment`).

#### 2. `InheritanceType.JOINED` (Нормализованная таблица на каждый класс)
Корневой класс отображается в базовую таблицу с общими полями, а каждый подкласс — в отдельную таблицу со своими специфическими полями, связанную с базовой таблицей по первичному/внешнему ключу.
- **Плюсы:**
  - Строгая нормализация схемы (3NF).
  - Поля подклассов могут иметь ограничения целостности **`NOT NULL`**.
- **Минусы:**
  - Чтение требует выполнения `LEFT OUTER JOIN` со всеми дочерними таблицами иерархии.
  - Вставка требует двух последовательных SQL `INSERT` (сначала в базовую таблицу, затем в дочернюю).

#### 3. `InheritanceType.TABLE_PER_CLASS` (Таблица на каждый конкретный класс)
Каждый подкласс маппится в полностью независимую таблицу, содержащую как свои поля, так и дублирующие колонки базового класса.
- **Плюсы:** Каждая таблица самодостаточна, нет лишних `NULL` и нет `JOIN` при выборке конкретного подкласса.
- **Минусы:** Полиморфный запрос к базовому классу (`SELECT p FROM Payment p`) генерирует тяжелый **`UNION ALL`** по всем таблицам, блокирующий использование индексов.

### Сравнительная матрица для архитектора

| Критерий | `SINGLE_TABLE` | `JOINED` | `TABLE_PER_CLASS` |
| :--- | :--- | :--- | :--- |
| **Нормализация БД** | ❌ Низкая (много `NULL`) | ✅ **Высокая (3NF)** | ⚠️ Средняя (дубли колонок) |
| **Ограничения `NOT NULL`** | ❌ Невозможны для подклассов | ✅ **Полностью поддерживаются** | ✅ **Поддерживаются** |
| **Скорость `INSERT`** | ⚡ **1 запрос** | 🐢 2+ запроса | ⚡ 1 запрос |
| **Скорость полиморфного чтения** | ⚡ **1 запрос (без JOIN)** | 🐢 Тяжелый `LEFT JOIN` | 🚨 Медленный `UNION ALL` |
| **Колонка дискриминатора** | Обязательна (`@DiscriminatorColumn`) | Опциональна | Не используется |
| **Рекомендация** | По умолчанию для 2–4 подклассов | Для нормализованных корпоративных БД | Редко (только при отсутствии полиморфизма) |

## 🔴 Senior Level

### `@MappedSuperclass` против полиморфного наследования

Очень частая ошибка на собеседованиях — путать `@MappedSuperclass` со стратегиями наследования:

```java
// Базовый класс для переиспользования полей аудита:
@MappedSuperclass
public abstract class BaseAuditableEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @CreationTimestamp
    private Instant createdAt;
}

@Entity
public class User extends BaseAuditableEntity { ... }

@Entity
public class Order extends BaseAuditableEntity { ... }
```

#### Фундаментальные отличия `@MappedSuperclass`:
1. Класс с `@MappedSuperclass` **НЕ является сущностью JPA** (`@Entity`).
2. Для него **нет отдельной таблицы в базе данных**.
3. **Не поддерживает полиморфные запросы:** Запрос `SELECT b FROM BaseAuditableEntity b` выбросит ошибку компиляции JPQL, так как такой сущности для Hibernate не существует.
4. Другие сущности **не могут ссылаться** на него через `@ManyToOne BaseAuditableEntity base`.

### Проблема полиморфных ассоциаций при `TABLE_PER_CLASS`

Если сущность `Order` ссылается на абстрактный класс платежа:
```java
@Entity
public class Order {
    @Id
    private Long id;

    @OneToOne
    @JoinColumn(name = "payment_id")
    private Payment payment; // Payment использует TABLE_PER_CLASS
}
```

#### В чем неразрешимый реляционный тупик:
- Колонка `order.payment_id` должна ссылаться на первичный ключ.
- Но таблицы `Payment` не существует! Есть две изолированные таблицы: `card_payments` и `cash_payments`.
- Реляционная СУБД **не позволяет создать Foreign Key, который одновременно ссылается на две разные таблицы**!
- Чтобы загрузить заказ, Hibernate вынужден опрашивать каждую возможную таблицу дочерних классов. 
- *Вывод:* Использование `@ManyToOne` или `@OneToOne` к базовому классу с `TABLE_PER_CLASS` — опасный антипаттерн.

## 4 Tricky Questions

### 1. Как при стратегии `SINGLE_TABLE` обеспечить валидацию обязательности полей подкласса (например, `cardNumber` не должен быть пустым), если на уровне базы данных колонка обязана быть `NULLable`?

**Ответ:**
1. На уровне СУБД колонка обязана разрешать `NULL`, иначе вставка строк других подклассов упадет с ошибкой.
2. **Способ 1 (СУБД Check Constraint):** Добавить проверочное ограничение в таблицу БД:
   ```sql
   ALTER TABLE payments ADD CONSTRAINT chk_card_number 
   CHECK (payment_type != 'CARD' OR card_number IS NOT NULL);
   ```
3. **Способ 2 (Bean Validation с группами):** Повесить аннотацию `@NotNull` на уровне Java-кода в подклассе `CardPayment`. Валидатор Hibernate Validator перехватит пустое значение на фазе `PrePersist` до отправки запроса в СУБД.

### 2. Что произойдет, если выполнить полиморфный запрос с пагинацией `SELECT p FROM Payment p` при стратегии `TABLE_PER_CLASS`?

**Ответ:**
1. Hibernate сгенерирует SQL-запрос с конструкцией `UNION ALL`:
   ```sql
   SELECT p.id, p.amount, p.card_num, NULL AS cash_date, 1 AS clazz_ FROM card_payments p
   UNION ALL
   SELECT p.id, p.amount, NULL AS card_num, p.cash_date, 2 AS clazz_ FROM cash_payments p
   LIMIT 10 OFFSET 20;
   ```
2. СУБД вынуждена сначала выполнить полное сканирование и объединение строк обеих таблиц во временную таблицу в памяти, и только потом применить сортировку и `LIMIT/OFFSET`.
3. Это приводит к колоссальной деградации времени ответа при росте объемов данных.

### 3. Как проверить точный конкретный подкласс сущности в JPQL-запросе при стратегии `JOINED` или `SINGLE_TABLE`?

**Ответ:**
1. В JPQL используется специальная функция **`TYPE(e)`**:
   ```java
   List<Payment> cards = entityManager.createQuery(
       "SELECT p FROM Payment p WHERE TYPE(p) = CardPayment", 
       Payment.class
   ).getResultList();
   ```
2. Для приведения типа (Downcasting) атрибутов подкласса в условиях `WHERE` используется оператор **`TREAT`**:
   ```java
   List<Payment> visa = entityManager.createQuery(
       "SELECT p FROM Payment p WHERE TREAT(p AS CardPayment).cardNumber LIKE '4%'", 
       Payment.class
   ).getResultList();
   ```

### 4. Допустим, мы загрузили `Payment` через ленивую связь `order.getPayment()`. Сработает ли проверка `if (order.getPayment() instanceof CardPayment)`?

**Ответ:**
1. Если прокси еще не был инициализирован, Hibernate создает динамический прокси базового класса: `Payment$ByteBuddy$...`.
2. Поскольку прокси является наследником класса `Payment`, оператор `instanceof CardPayment` вернет **`false`**, даже если реальная строка в базе данных — это оплата картой!
3. Это классическая ловушка полиморфизма ленивых прокси в JPA.
4. **Решение:** Извлечь реальный класс через `Hibernate.unproxy(order.getPayment())` или использовать встроенный метод Hibernate:
   `Hibernate.getClass(order.getPayment()) == CardPayment.class`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «JPA поддерживает 3 стратегии наследования: **`SINGLE_TABLE`** (все классы в одной таблице с колонкой дискриминатора `DTYPE` — самая быстрая, но требует nullable-колонок), **`JOINED`** (базовая таблица с общими полями + дочерние таблицы со специфическими — нормализована, поддерживает `NOT NULL`, но требует `JOIN`), и **`TABLE_PER_CLASS`** (независимые таблицы с дублированием полей — порождает тяжелые `UNION ALL`). `@MappedSuperclass` не является стратегией наследования, а служит шаблоном переиспользования общих полей аудита без отдельной таблицы и без поддержки полиморфизма. В 80% проектов лучшим выбором по соотношению производительность/простота остается `SINGLE_TABLE`».

### Ключевые метрики для Production-мониторинга
- **Длительность полиморфных запросов**: мониторинг выполнения запросов к корневым сущностям с `JOINED` и `TABLE_PER_CLASS`.
- **Количество колонок в `SINGLE_TABLE`**: разрастание свыше 40–50 колонок сигнализирует о необходимости перехода на `JOINED` или разделения агрегатов.

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«@MappedSuperclass — это еще одна стратегия наследования JPA»* — Нет, `@MappedSuperclass` не создает сущности и не поддерживает полиморфные запросы.
- ❌ *«SINGLE_TABLE позволяет вешать ограничение NOT NULL на колонки подклассов в БД»* — В СУБД колонка обязана быть nullable для совместимости с другими потомками.
- ❌ *«TABLE_PER_CLASS — отличная стратегия для связей @ManyToOne»* — СУБД не умеет строить внешние ключи к нескольким таблицам одновременно.
- ❌ *«instanceof всегда надежно работает с полиморфными ленивыми прокси»* — Прокси базового класса не пройдет проверку `instanceof SubClass`, требуется `Hibernate.unproxy()`.
