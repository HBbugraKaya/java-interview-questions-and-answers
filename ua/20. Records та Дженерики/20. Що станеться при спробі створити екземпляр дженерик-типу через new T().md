# Що станеться при спробі створити екземпляр дженерик-типу через new T()

---

## 🟢 Junior Level

Спроба створити екземпляр типу дженерика через `new T()` **призведе до помилки компіляції**: `cannot instantiate the type T` (або `unexpected type, found: type parameter: T`).

```java
public class Box<T> {
    private T value;

    public Box() {
        // Помилка компіляції: Type parameter 'T' cannot be instantiated directly
        this.value = new T(); 
    }
}
```

### Чому компілятор забороняє `new T()`?
1. **Стирання типів (Type Erasure):** У процесі компіляції інформація про тип `T` стирається і замінюється верхньою межею (зазвичай `Object`). Байткод віртуальної машини JVM не знає, який реальний клас буде передано в момент виконання.
2. **Невідомість конструктора:** Компілятор не може гарантувати, що фактичний тип-аргумент має публічний конструктор без параметрів (no-arg constructor). Тип `T` може виявитися інтерфейсом (`Runnable`), абстрактним класом (`Number`) або класом без конструктора за замовчуванням.

### Стандартні способи вирішення

1. **Фабрика через `Supplier<T>` (рекомендований сучасний спосіб):**
   ```java
   public class Box<T> {
       private final T value;

       public Box(Supplier<T> factory) {
           this.value = Objects.requireNonNull(factory).get();
       }
   }

   // Використання з посиланням на конструктор:
   Box<User> userBox = new Box<>(User::new);
   ```

2. **Передача метаоб'єкта `Class<T>` (Reflection):**
   ```java
   public class Box<T> {
       private final T value;

       public Box(Class<T> clazz) throws ReflectiveOperationException {
           this.value = clazz.getDeclaredConstructor().newInstance();
       }
   }

   // Використання:
   Box<User> userBox = new Box<>(User.class);
   ```

## 🟡 Middle Level

### Внутрішні механізми: чому інструкція JVM `new` несумісна з дженериками

Інструкція байткоду JVM `new` приймає як аргумент 16-бітний індекс у пулі констант (`constant_pool`), що вказує на запис типу `CONSTANT_Class_info`. 

```bytecode
// Як виглядає звичайний new:
0: new           #2    // class com/example/User
3: dup
4: invokespecial #3    // Method com/example/User."<init>":()V
```

Параметр типу `T` — це артефакт компілятора, що існує лише в сигнатурах вихідного коду. У нього **немає і не може бути статичного запису в constant pool**. Якби компілятор підставив туди стертий тип (`Object`), згенерований байткод створив би порожній екземпляр `java.lang.Object`, що порушило б безпеку типів.

### Порівняння підходів до створення `T`

| Підхід | Приклад виклику | Плюси | Мінуси / Ризики |
| :--- | :--- | :--- | :--- |
| **`Supplier<T>`** | `new Box<>(User::new)` | Максимальна швидкість (inline C2 JIT), повна типобезпека, підтримка будь-яких конструкторів з аргументами | Вимагає явної передачі лямбди або посилання на метод від викликаючого коду |
| **`Class<T>` Reflection** | `new Box<>(User.class)` | Інтуїтивний API, можливість інтроспекції полів та анотацій | Повільніше, вимагає конструктора без аргументів, викидає перевірювані рефлексивні винятки, проблеми з JPMS (модулями) |
| **`MethodHandle`** | `lookup.findConstructor(...)` | Швидше за стандартну рефлексію при кешуванні дескриптора | Складна обробка винятків та ініціалізація |
| **`(T) new Object()`** | `(T) new Object()` | Компільовано з попередженням | **Fatal:** Гарантований `ClassCastException` у місці виклику! |

### Ілюзія кастингу: `(T) new Object()`

Іноді розробники намагаються обдурити компілятор через каст до стертого типу:

```java
public class SneakyBox<T> {
    @SuppressWarnings("unchecked")
    public T createInstance() {
        return (T) new Object(); // Компілятор пропускає з Unchecked Warning!
    }
}
```

Що відбувається насправді:
```java
SneakyBox<String> box = new SneakyBox<>();
// Компільовано успішно, але падає в runtime:
String str = box.createInstance(); // 💥 ClassCastException: class java.lang.Object cannot be cast to class java.lang.String
```

**Чому виняток виникає не всередині методу, а зовні?**  
Всередині методу `createInstance()` тип значення, що повертається, стерто до `Object`. Інструкція `(T)` не генерує жодних перевірок типів (NOP). Однак у місці виклику `box.createInstance()` компілятор очікує `String` і вставляє опкод байткоду `checkcast java/lang/String`. Спроба привести екземпляр `Object` до `String` призводить до негайного `ClassCastException`.

## 🔴 Senior Level

### Архітектурні обмеження та тонкощі рефлексії

#### 1. Застарівання `Class.newInstance()` в Java 9
До Java 9 часто писали `clazz.newInstance()`. Цей метод був оголошений `@Deprecated(since="9")` з двох критичних причин:
1. **Обхід контролю перевірюваних винятків (Checked Exceptions):** Якщо конструктор класу викидав checked exception (наприклад, `IOException`), метод `Class.newInstance()` прокидав його назовні безпосередньо без загортання, порушуючи специфікацію обробки винятків компілятора javac (механізм sneaky throws).
2. **Ігнорування приватних конструкторів:** Він викликав тільки публічний no-arg конструктор і не дозволяв отримати доступ до `protected` або `package-private` конструкторів.

Сучасний стандарт:
```java
// Коректний підхід:
Constructor<T> ctor = clazz.getDeclaredConstructor();
ctor.setAccessible(true); // якщо конструктор не public
T instance = ctor.newInstance(); // checked exceptions загортаються в InvocationTargetException
```

#### 2. Інкапсуляція модулів (JPMS, Project Jigsaw)
Починаючи з Java 9, виклик `ctor.setAccessible(true)` завершиться винятком `InaccessibleObjectException`, якщо цільовий клас знаходиться в іншому іменованому модулі, який явно не відкрив (`opens`) свій пакет для вашого модуля.

#### 3. Шаблон Super Type Tokens (Gafter Pattern)
Коли потрібно зберегти інформацію про тип з усіма дженерик-параметрами (наприклад, `List<User>`), використовується патерн супер-типу через анонімні підкласи:

```java
public abstract class TypeReference<T> {
    private final Type type;

    protected TypeReference() {
        Type superClass = getClass().getGenericSuperclass();
        if (superClass instanceof ParameterizedType parameterized) {
            this.type = parameterized.getActualTypeArguments()[0];
        } else {
            throw new IllegalArgumentException("TypeReference must be parameterized");
        }
    }

    public Type getType() {
        return this.type;
    }
}

// Використання (як у Jackson / Guava):
TypeReference<List<String>> token = new TypeReference<>() {};
```
> [!IMPORTANT]
> `TypeReference` зберігає метадані про тип `List<String>` в атрибуті `Signature` байткоду анонімного класу, проте **він все одно не дозволяє виконати `new T()`**. Якщо фактичний аргумент — інтерфейс (`List`), створити його екземпляр напряму неможливо.

## 4 Tricky Questions

### 1. Чому `(T) new Object()` компілюється без помилки (тільки з попередженням), а `new T()` не компілюється зовсім?
**Відповідь:**  
`new T()` порушує граматику Java Language Specification (§15.9), яка вимагає в якості типу створення екземпляра конкретний клас або перерахування (`ClassType`). Параметр типу `T` є типовою змінною (`TypeVariable`), яка не має конструкторів.  
У той же час `(T) new Object()` — це операція приведення типу (cast expression, JLS §15.16). Приведення дозволено між будь-якими посилальними типами, якщо існує ймовірність їхньої сумісності. Через стирання типів `(T)` перетворюється на приведення до верхньої межі (до `Object`), що є валідним, але компілятор видає `unchecked cast warning`, попереджаючи про потенційний `ClassCastException` у runtime.

### 2. Чи спрацює `TypeReference<T>` всередині узагальненого методу `public <T> void create(TypeReference<T> ref)`?
**Відповідь:**  
Ні, якщо передати `new TypeReference<T>() {}`, де `T` — не розв'язаний параметр типу викликаючого методу.  
```java
public <T> void test() {
    TypeReference<T> ref = new TypeReference<>() {};
    System.out.println(ref.getType()); // Надрукує "T", а не реальний клас!
}
```
Анонімний клас захоплює в метадані те, що відомо компілятору в місці створення. Якщо там стоїть змінна `T`, у сигнатурі залишиться `TypeVariable "T"`, а не конкретний тип. `TypeReference` працює **тільки** тоді, коли тип заданий явно літералом на етапі компіляції: `new TypeReference<List<String>>() {}`.

### 3. Як створити generic-масив заданого розміру для типу `T`?
**Відповідь:**  
Синтаксис `new T[10]` заборонений з тієї ж причини (відсутність `Class` у runtime для алокації компонентів масиву в купі JVM).  
Існує два рішення:
1. **Через `Array.newInstance(Class<T>, int)` (повноцінний типобезпечний масив):**
   ```java
   @SuppressWarnings("unchecked")
   T[] array = (T[]) Array.newInstance(clazz, size);
   ```
   У купі створюється реальний `T[]` (наприклад, `String[]`).
2. **Через `Object[]` та unchecked cast (підхід `ArrayList`):**
   ```java
   Object[] elementData = new Object[size];
   // Повернення конкретного елемента через каст:
   @SuppressWarnings("unchecked")
   T element = (T) elementData[index];
   ```
   Сам масив у купі залишається `Object[]`, але назовні віддаються типізовані елементи `T`.

### 4. У чому різниця в часі виконання між створенням через `Supplier<T>` та `Constructor.newInstance()`?
**Відповідь:**  
`Supplier<T>` при передачі `User::new` компілюється через `invokedynamic` (лямбда-метафабрика) і являє собою звичайний віртуальний виклик методу `get()`, який C2 JIT-компілятор легко інлайнить (вартість ~1–3 нс).  
`Constructor.newInstance()` виконує інтроспекцію, перевірку прав доступу (`checkAccess`), створення копії масиву параметрів та загортання винятків у `InvocationTargetException` (вартість ~20–100 нс, поки JIT не оптимізує рефлексивний виклик через інфляцію аксесорів `ReflectionFactory`).

## 🎯 Шпаргалка для інтерв'ю

- **Пряма відповідь:** `new T()` викликає **помилку компіляції**. JVM не знає тип `T` у runtime через Type Erasure, і у `T` немає запису `CONSTANT_Class_info` у constant pool.
- **Два найкращі рішення:**
  1. `Supplier<T> factory` -> `factory.get()` (швидко, гнучко, без рефлексії).
  2. `Class<T> type` -> `type.getDeclaredConstructor().newInstance()` (рефлексія, вимагає no-arg конструктор).
- **Чому `Class.newInstance()` deprecated:** Проковтує перевірку checked exceptions та ігнорує приватність конструкторів; замінений на `getDeclaredConstructor().newInstance()`.
- **Пастка з `(T) new Object()`:** Метод скомпілюється з попередженням, але викине `ClassCastException` у точці виклику через інструкцію `checkcast`.
- **Масиви дженериків:** `new T[]` теж заборонений; створюються через `(T[]) Array.newInstance(type, size)` або внутрішній `Object[]`.
