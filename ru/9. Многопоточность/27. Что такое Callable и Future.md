# Что такое Callable и Future

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**`Callable<V>`** и **`Future<V>`** — это базовые интерфейсы пакета `java.util.concurrent`, появившиеся в Java 5 для преодоления фундаментальных ограничений классического `Runnable`:

1. **`Callable<V>`** представляет собой задачу, которая, в отличие от `Runnable.run()`, **возвращает типизированный результат** типа `V` через метод `V call()` и способна пробрасывать проверяемые исключения (**checked exceptions**).
2. **`Future<V>`** выступает асинхронным дескриптором («обещанием» / квитанцией на результат) запущенной задачи. Через `Future` вызывающий поток может:
   - Проверить статус выполнения задачи (`isDone()`, `isCancelled()`);
   - Попытаться отменить задачу (`cancel()`);
   - Получить вычисленный результат с блокировкой (`get()`) или с ограничением по таймауту (`get(timeout, unit)`).

---

### Сравнительная таблица: Runnable vs Callable vs Future vs CompletableFuture

| Характеристика | `Runnable` | `Callable<V>` | `Future<V>` | `CompletableFuture<V>` |
|---|---|---|---|---|
| **Роль** | Задача без результата | Задача с результатом | Дескриптор результата | Реактивный конвейер задач |
| **Сигнатура метода** | `void run()` | `V call() throws Exception` | Методы инспекции (`get`, `cancel`) | 60+ методов трансформации |
| **Checked Exceptions** | ❌ Запрещены | ✅ Разрешены (`throws Exception`) | Пробрасываются в `ExecutionException` | Оборачиваются в `CompletionException` |
| **Получение результата** | Невозможно | Возвращается из `call()` | Блокирующий вызов `get()` | Неблокирующие колбэки (`thenApply`) |
| **Появился в версии** | Java 1.0 | Java 5 | Java 5 | Java 8 |

### Компилируемый пример на Java 21

```java
import java.util.concurrent.*;

public class CallableAndFutureBasicsDemo {
    public static void main(String[] args) {
        // 1. Определение задачи, возвращающей значение и способной бросить исключение
        Callable<Integer> heavyCalculation = () -> {
            System.out.println("Вычисление начато в потоке: " + Thread.currentThread().getName());
            Thread.sleep(500); // Имитация долгих вычислений
            return 42 * 2;
        };

        // 2. Запуск через ExecutorService
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            // submit() немедленно возвращает Future (неблокирующая операция)
            Future<Integer> future = executor.submit(heavyCalculation);

            System.out.println("Задача отправлена. Завершена ли она сразу? " + future.isDone());

            try {
                // 3. Получение результата с защитным таймаутом (Best Practice!)
                Integer result = future.get(2, TimeUnit.SECONDS);
                System.out.println("Результат успешно получен: " + result);
            } catch (TimeoutException e) {
                System.err.println("Превышен таймаут ожидания! Отменяем задачу...");
                future.cancel(true); // Посылаем сигнал прерывания
            } catch (ExecutionException e) {
                // Если внутри call() упало исключение, оно упаковано в getCause()
                System.err.println("Ошибка внутри задачи: " + e.getCause().getMessage());
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                System.err.println("Текущий поток был прерван при ожидании");
            }
        }
    }
}
```

## 🟡 Middle Level

### Методы интерфейса `Future<V>` и управление отменой

Интерфейс `Future` определяет пять ключевых методов:

1. **`V get()`:** блокирует вызывающий поток до завершения задачи, возвращая результат либо выбрасывая исключение.
2. **`V get(long timeout, TimeUnit unit)`:** блокирует вызывающий поток максимум на указанное время. Если задача не успела завершиться, выбрасывается `TimeoutException`.
3. **`boolean isDone()`:** возвращает `true`, если задача завершена (успешно, по ошибке или отменена).
4. **`boolean isCancelled()`:** возвращает `true`, если задача была отменена до своего естественного завершения.
5. **`boolean cancel(boolean mayInterruptIfRunning)`:** пытается отменить выполнение задачи.

#### Механика отмены: `cancel(true)` vs `cancel(false)`
- **`cancel(false)`:** если задача еще ждет в очереди пула потоков, она удаляется из очереди и никогда не запустится. Но если рабочий поток уже начал выполнять `call()`, его выполнение **не прерывается**, хотя результат будет проигнорирован.
- **`cancel(true)`:** если задача уже выполняется, JVM посылает потоку-исполнителю сигнал **`Thread.interrupt()`**.
  > [!IMPORTANT]
  > Сигнал `interrupt()` не «убивает» поток мгновенно. Задача обязана сама проверять флаг `Thread.currentThread().isInterrupted()` или вызывать стандартные блокирующие методы (`sleep`, `read`), иначе она продолжит работу до конца!

### Массовые операции: `invokeAll()` vs `invokeAny()`

Интерфейс `ExecutorService` предоставляет удобные методы для работы с коллекциями `Callable`:

```java
import java.util.List;
import java.util.concurrent.*;

public class BatchExecutionDemo {
    public static void main(String[] args) throws Exception {
        try (var executor = Executors.newFixedThreadPool(4)) {
            List<Callable<String>> tasks = List.of(
                () -> { Thread.sleep(200); return "Fast"; },
                () -> { Thread.sleep(500); return "Medium"; },
                () -> { Thread.sleep(800); return "Slow"; }
            );

            // 1. invokeAll: блокирует вызывающий поток, пока ВСЕ задачи не завершатся
            // Всегда рекомендуется указывать таймаут!
            List<Future<String>> results = executor.invokeAll(tasks, 1, TimeUnit.SECONDS);
            for (Future<String> f : results) {
                if (!f.isCancelled()) {
                    System.out.println("Получено: " + f.get());
                }
            }

            // 2. invokeAny: возвращает результат САМОЙ БЫСТРОЙ успешно завершившейся задачи!
            // Все остальные задачи автоматически отменяются (получают cancel(true))
            String fastest = executor.invokeAny(tasks);
            System.out.println("Самый быстрый ответ: " + fastest);
        }
    }
}
```

### Обертывание исключений в `ExecutionException`

Когда метод `Callable.call()` выбрасывает проверяемое или непроверяемое исключение (например, `SQLException`), вызывающий поток не может поймать его напрямую, так как выполнение происходило в другом потоке ОС.

`Future.get()` упаковывает реальное исключение в **`ExecutionException`**:
```java
try {
    future.get();
} catch (ExecutionException e) {
    Throwable cause = e.getCause(); // Извлекаем первопричину сбоя
    if (cause instanceof SQLException sqlEx) {
        log.error("Сбой БД: {}", sqlEx.getSQLState());
    } else {
        log.error("Неизвестная ошибка", cause);
    }
}
```

## 🔴 Senior Level

### Архитектура HotSpot: Устройство `FutureTask<V>` под капотом

Когда вызывается `executor.submit(callable)`, задача упаковывается в стандартную реализацию — **`java.util.concurrent.FutureTask<V>`**, которая одновременно реализует интерфейсы `Runnable` и `Future` (`RunnableFuture<V>`):

```
                        [ RunnableFuture<V> ]
                                 ▲
                     ┌───────────┴───────────┐
                     │                       │
              [ Runnable ]              [ Future<V> ]
```

#### Машина состояний `FutureTask`:
Внутри `FutureTask` синхронизация построена на атомарном поле `volatile int state` без использования тяжелых блокировок (`synchronized`). Переходы между состояниями осуществляются через процессорные инструкции CAS:

```
           ┌──► COMPLETING ──► NORMAL (Результат записан в outcome)
           │
  NEW (0) ─┼──► COMPLETING ──► EXCEPTIONAL (Исключение записано в outcome)
           │
           ├──► CANCELLED (Отменен без прерывания)
           │
           └──► INTERRUPTING ──► INTERRUPTED (Отменен с Thread.interrupt())
```

- **`NEW = 0`:** задача создана, еще не завершена;
- **`COMPLETING = 1`:** переходное состояние: результат вычисления уже получен, но еще записывается в поле `Object outcome`;
- **`NORMAL = 2`:** задача успешно завершена, `outcome` содержит значение;
- **`EXCEPTIONAL = 3`:** задача завершилась сбоем, `outcome` содержит `Throwable`;
- **`CANCELLED = 4`:** отменена через `cancel(false)`;
- **`INTERRUPTING = 5`:** переходное состояние при вызове `cancel(true)` до отправки прерывания;
- **`INTERRUPTED = 6`:** поток прерван.

---

### Механика ожидания: Очередь Treiber Stack (`WaitNode`)

Если поток вызывает `future.get()`, а задача находится в состоянии `NEW` или `COMPLETING`, поток должен уснуть:

1. `FutureTask` не использует `Object.wait()`. Вместо этого он организует **бессерверный стек ожидания Трейбера (Treiber Stack)** из объектов `WaitNode`.
2. Поток создает узел `WaitNode`, атомарно через CAS помещает его на вершину стека `waiters` и засыпает с помощью **`LockSupport.park(this)`**.
3. Когда рабочий поток завершает выполнение задачи внутри метода `FutureTask.run()`, он переводит статус в `NORMAL`/`EXCEPTIONAL`, записывает результат в поле `outcome`, а затем вызывает приватный метод `finishCompletion()`:
   - Проходит по стеку `waiters`;
   - Вызывает **`LockSupport.unpark(node.thread)`** для каждого ждущего потока;
   - Освобождает ссылки для сборщика мусора.

### Архитектурный антипаттерн «Синхронный `Future.get()` в Web-контейнерах»

Классическая ошибка проектирования Middle-разработчиков: создание асинхронных задач в фоновом пуле с немедленным синхронным ожиданием `future.get()` в потоке HTTP-обработчика:

```java
// ❌ АНТИПАТТЕРН: Двойная блокировка ресурсов
public UserResponse handleRequest(Long id) {
    Future<User> f1 = pool.submit(() -> fetchUser(id));
    Future<Orders> f2 = pool.submit(() -> fetchOrders(id));

    // Поток сервлета Tomcat заблокирован на get(), а два потока pool заняты расчетом!
    return new UserResponse(f1.get(), f2.get());
}
```

#### Почему это приводит к каскадному сбою:
1. Задействуются 3 потока ОС вместо одного (1 поток сервлета + 2 потока пула);
2. При высокой нагрузке потоки сервлета виснут в ожидании `get()`, а очередь пула задач переполняется, вызывая Thread Starvation и исчерпание пула потоков.

#### Современные решения:
1. **Java 8+:** переход на неблокирующий конвейер `CompletableFuture.thenCombine()`;
2. **Java 21+:** переход на **Virtual Threads** и **Structured Concurrency** (`StructuredTaskScope`), где блокирующий `join()` размонтирует виртуальный поток, не отнимая физические потоки ОС.

## 🎯 Шпаргалка для интервью

### 1. 30-секундный эссенс (Elevator Pitch)
`Callable<V>` — это функциональный интерфейс параметризованной задачи («что выполнить»), возвращающий значение `V` и декларирующий `throws Exception`. `Future<V>` — дескриптор жизненного цикла этой задачи («квитанция на результат»), позволяющий проверить готовность (`isDone`), отменить исполнение (`cancel`) и получить значение (`get`). Внутри `FutureTask` построен на неблокирующей машине состояний (CAS над переменной `state`) и стеке ожидания Трейбера с примитивом `LockSupport.park()`. В современном коде блокирующий `Future.get()` уступает место неблокирующему `CompletableFuture` или виртуальным потокам со `StructuredTaskScope`.

### 2. 4 каверзных вопроса с глубокими ответами

#### Вопрос 1: Что происходит внутри `FutureTask.run()`, если метод `Callable.call()` выбрасывает исключение?
**Ответ:**
Метод `FutureTask.run()` перехватывает любое исключение (`catch (Throwable rx)`). Он не дает потоку-исполнителю упасть, а сохраняет ссылку на пойманное исключение во внутреннем нетипизированном поле `Object outcome`. После этого статус задачи атомарно через CAS переводится в `COMPLETING`, а затем в `EXCEPTIONAL`. Далее вызывается `finishCompletion()`, который будит все потоки, ждущие на `get()`. Когда вызывающий поток обращается к `get()`, метод проверяет статус, видит `EXCEPTIONAL` и пробрасывает сохраненное исключение, обернув его в `ExecutionException(cause)`.

#### Вопрос 2: В чём разница между вызовами `future.cancel(true)` и `future.cancel(false)`?
**Ответ:**
Оба метода переводят задачу в статус отмененной, если она еще не завершилась.
- Если задача еще находится в очереди пула и не начала выполняться, оба вызова одинаково предотвратят ее старт.
- Если задача **уже исполняется** рабочим потоком:
  - `cancel(false)` не прерывает исполнение потока; задача доработает до конца, но результат будет отброшен.
  - `cancel(true)` вызывает `Thread.interrupt()` на рабочем потоке, выполняющем задачу. Если код задачи проверяет статус прерывания или находится в блокирующем вызове (`sleep`, `wait`, сокет), он немедленно прервется через `InterruptedException`.

#### Вопрос 3: Почему вызов `future.get()` на задаче, у которой `isDone() == true`, выполняется со скоростью чтения обычной переменной?
**Ответ:**
Потому что в `FutureTask` состояние `state` является `volatile`-переменной. Если `state >= NORMAL`, метод `get()` сразу переходит к вызову `report(s)`, минуя создание узла `WaitNode` и системный вызов `LockSupport.park()`. Значение извлекается прямо из памяти поля `outcome` за несколько тактов процессора благодаря гарантиям Happens-Before модели памяти Java.

#### Вопрос 4: Как `FutureTask` защищает от гонки между отменой задачи (`cancel()`) и ее одновременным завершением (`run()`)?
**Ответ:**
Защита реализована на базе атомарных CAS-операций над полем `state`. Перед тем как записать результат или выбросить исключение, метод `run()` выполняет:
```java
UNSAFE.compareAndSwapInt(this, stateOffset, NEW, COMPLETING)
```
Метод `cancel()` точно так же пытается выполнить CAS из `NEW` в `CANCELLED` или `INTERRUPTING`. Победителем становится ровно один поток:
- Если `cancel()` успел первым, `run()` проваливает CAS и не публикует результат;
- Если `run()` успел перевести состояние в `COMPLETING`, вызов `cancel()` проваливает CAS и возвращает `false`, так как задачу уже невозможно отменить.

### 3. Типичные ошибки и Red Flags

❌ **"Вызов `future.get()` без указания таймаута в продакшен-коде."**  
*Правильно:* Неограниченный `future.get()` может намертво подвесить вызывающий поток навсегда, если внешняя служба зависнет. Всегда следует указывать таймаут: `future.get(5, TimeUnit.SECONDS)`.

❌ **"Предположение, что `future.cancel(true)` принудительно убивает поток."**  
*Правильно:* Метод лишь выставляет флаг прерывания. Если внутри задачи крутится бесконечный цикл `while(true)` без проверки `isInterrupted()`, задача продолжит пожирать CPU.

❌ **"Использование `Callable<Void>` вместо `Runnable` для задач без возвращаемого значения."**  
*Правильно:* Это порождает лишний оверхед и требует явного возврата `return null;`. Для задач без результата предназначен `Runnable`.
