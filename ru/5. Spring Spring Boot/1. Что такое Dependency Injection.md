# Что такое Dependency Injection

---

## 🟢 Junior Level

### 1. Простое определение концепции

**Dependency Injection (DI, Внедрение зависимостей)** — это паттерн проектирования, при котором объект получает необходимые ему внешние ресурсы и сервисы (**зависимости**) извне, вместо того чтобы создавать их самостоятельно с помощью оператора `new`.

DI является конкретной реализацией более общего архитектурного принципа — **Inversion of Control (IoC, Инверсия управления)**.

```
Традиционный подход (Без DI):
[ OrderService ] ──(создает через new)──► [ OrderRepository ]
OrderService жестко привязан к конкретному классу OrderRepository.

Подход Dependency Injection (с DI):
[ IoC Container (Spring) ] ──(создает и внедряет)──► [ OrderRepository ]
                                                                 │
                                                                 ▼
                                                        [ OrderService ]
OrderService зависит только от абстракции и получает экземпляр извне.
```

---

### 2. Сравнение кода: без DI и с DI

#### Без DI (Жесткая связанность):
```java
public class OrderService {
    // ❌ КЛАСС САМ УПРАВЛЯЕТ ЖИЗНЕННЫМ ЦИКЛОМ ЗАВИСИМОСТИ:
    private final OrderRepository repository = new PostgresOrderRepository();

    public void processOrder(Order order) {
        repository.save(order);
    }
}
```
*Проблемы:* невозможно написать изолированный unit-тест (придется поднимать реальную базу данных Postgres), невозможно легко подменить хранилище на InMemory или Mongo.

#### С DI (Слабая связанность):
```java
@Service
public class OrderService {
    // ✅ ЗАВИСИМОСТЬ ПОСТАВЛЯЕТСЯ ИЗВНЕ (ЧЕРЕЗ КОНСТРУКТОР):
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    public void processOrder(Order order) {
        repository.save(order);
    }
}
```
*Преимущества:* в тестах можно легко передать mock-объект `new OrderService(mockRepo)`, класс ничего не знает о создании зависимостей и следует принципу единственной ответственности (SRP).

## 🟡 Middle Level

### 1. Архитектурная триада: DIP vs IoC vs DI

Частый источник путаницы на собеседованиях — разграничение трех понятий:

1. **Dependency Inversion Principle (DIP):** принцип буквы «D» из SOLID. Это абстрактное архитектурное правило: *«Модули верхних уровней не должны зависеть от модулей нижних уровней. Оба должны зависеть от абстракций (интерфейсов)»*.
2. **Inversion of Control (IoC):** поведенческий паттерн («Голливудский принцип: Не звоните нам, мы сами вам перезвоним»). Традиционная программа сама управляет потоком выполнения; в IoC поток выполнения берет на себя фреймворк.
3. **Dependency Injection (DI):** прикладной шаблон проектирования, реализующий IoC в части связывания объектов: контейнер собирает граф зависимостей и проставляет ссылки в нужные поля.

---

### 2. Способы внедрения зависимостей в Spring

В Spring существует три основных способа внедрения зависимостей:

| Тип внедрения | Синтаксис | Иммутабельность (`final`) | Unit-тестирование без Spring | Рекомендация |
| :--- | :--- | :--- | :--- | :--- |
| **Constructor Injection** | Через аргументы конструктора | ✅ **Да (`final`)** | ✅ **Легко (`new Service(mock)`)** | 🟢 **Основной стандарт** |
| **Setter Injection** | Через методы `setRepo(...)` | ❌ Нет | ⚠️ Средне (можно забыть вызвать) | 🟡 Для опциональных зависимостей |
| **Field Injection** | `@Autowired private Repo repo;`| ❌ Нет | ❌ **Сложно (требует рефлексии)** | 🔴 **Антипаттерн** |

```java
// Рекомендуемый современный стандарт (Constructor Injection + Lombok):
@Service
@RequiredArgsConstructor
public class PaymentService {
    private final PaymentGateway gateway; // Внедряется через сгенерированный конструктор
    private final AuditLogger logger;
}
```

## 🔴 Senior Level

### 1. Жизненный цикл DI в ядре Spring Framework

Создание и внедрение зависимостей в Spring ApplicationContext проходит через четко детерминированные фазы:

```
1. Сканирование классов (@ComponentScan, @Configuration)
   │
2. Создание метаданных (BeanDefinition)
   │
3. Модификация метаданных (BeanFactoryPostProcessor)
   │
4. Инстанцирование объекта (Instantiation via Constructor Resolver)
   │  --> Здесь срабатывает Constructor Injection!
   │
5. Внедрение зависимостей (Property Population via AutowiredAnnotationBPP)
   │  --> Здесь срабатывает Setter и Field Injection!
   │
6. Инициализация (BeanPostProcessor.postProcessBeforeInitialization, @PostConstruct)
   │
7. Создание Прокси (AOP, @Transactional via postProcessAfterInitialization)
   │
8. Готовый бин в Singleton Pool (Ready to use)
```

**Критический архитектурный вывод:**
Constructor Injection выполняется на фазе **4 (Instantiation)**. В этот момент бин физически не может быть создан без наличия готовых экземпляров своих зависимостей. 
Field и Setter Injection выполняются на фазе **5 (Property Population)**, то есть уже *после* того, как объект был создан через конструктор по умолчанию.

### 2. Циклические зависимости и решение Spring Boot 2.6+

Когда Бин $A$ требует Бин $B$, а Бин $B$ требует Бин $A$:
- **При Constructor Injection:** Spring не может создать $A$ без $B$, а $B$ без $A$. Контейнер падает сразу при старте приложения с исключением `BeanCurrentlyInCreationException`. Это пример принципа **Fail-Fast**: архитектурная ошибка вскрывается мгновенно.
- **При Field Injection:** В старых версиях Spring обходил эту проблему через создание незаполненных «сырых» объектов с помощью трехслойного кэша синглтонов (`three-level cache` в `DefaultSingletonBeanRegistry`).

> [!IMPORTANT]
> Начиная со **Spring Boot 2.6**, циклические зависимости **запрещены по умолчанию** (`spring.main.allow-circular-references=false`). Попытка запуска приложения с циклом зависимостей приведет к аварийному останову контекста.

**Способы решения циклов:**
1. *Архитектурный рефакторинг (Best Practice):* выделение третьей общей сущности $C$, от которой зависят $A$ и $B$.
2. *Ленивая прокси-инициализация (Workaround):* аннотация `@Lazy` на одном из аргументов конструктора заставляет Spring внедрить динамический CGLIB-прокси, откладывая реальное связывание до первого вызова метода.

### 3. DI против Service Locator

Антипаттерном использования Spring является превращение его в **Service Locator**:

```java
// ❌ АНТИПАТТЕРН SERVICE LOCATOR:
@Service
public class OrderService {
    @Autowired
    private ApplicationContext context; // Внедрение самого контекста!

    public void process() {
        // Скрытая зависимость, динамический поиск по строке/типу:
        PaymentGateway gateway = context.getBean(PaymentGateway.class);
        gateway.pay();
    }
}
```
*В чем опасность:* Класс оказывается жестко связан с API Spring (`ApplicationContext`), зависимости скрыты внутри методов (не видны в контракте конструктора), unit-тестирование требует поднятия тяжелого Spring-контекста.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «`Dependency Injection` — это реализация принципа инверсии управления (IoC), при которой создание и поставка зависимостей делегируются внешнему сборщику (IoC-контейнеру Spring), а сам компонент только декларирует свои потребности. Это обеспечивает слабую связанность (Loose Coupling), соблюдение Single Responsibility и легкую подмену зависимостей моками в тестах. В современной разработке единственным рекомендуемым способом является Constructor Injection, гарантирующий иммутабельность полей через `final`, отсутствие неполноценно сконфигурированных объектов и выявление циклических зависимостей при старте приложения (Fail-Fast)».

---

### 3 каверзных вопроса на интервью с ответами

#### 1. В чём разница между понятиями IoC, DI и DIP?
**Ответ:** 
- **DIP (Dependency Inversion Principle):** архитектурный принцип SOLID высокого уровня, требующий, чтобы модули зависели от интерфейсов, а не от деталей.
- **IoC (Inversion of Control):** общий архитектурный паттерн, передающий управление потоком выполнения и жизненным циклом фреймворку.
- **DI (Dependency Injection):** конкретный шаблон проектирования, реализующий IoC, при котором зависимости передаются объекту извне (через конструктор или сеттер).

#### 2. Почему в Spring Boot 2.6+ запретили циклические зависимости по умолчанию?
**Ответ:** Циклическая зависимость — это явный признак архитектурного запаха (Bad Smell) и нарушения принципа единственной ответственности (SRP). Разрешение циклов маскировало дефекты проектирования, усложняло работу с AOP-прокси (прокси не успевали оборачивать сырые синглтоны) и замедляло старт контекста. Запрет заставляет разработчиков разделять сервисы или применять события (`ApplicationEventPublisher`).

#### 3. На каком этапе жизненного цикла бина создается прокси (`@Transactional`, `@Async`), и как это влияет на DI?
**Ответ:** Прокси создается на этапе инициализации бина внутри `BeanPostProcessor.postProcessAfterInitialization()`. Это происходит **после** того, как в целевой объект были внедрены все зависимости (DI завершен). Внедряемый в другие компоненты бин является уже экземпляром прокси, оборачивающим реальный объект.

---

### Типичные ошибки и Red Flags

- ❌ **Использование Field Injection (`@Autowired` на приватных полях):** Прямое нарушение инкапсуляции, усложняет unit-тесты, невозможность использовать `final`.
- ❌ **Использование `ApplicationContext.getBean()` в бизнес-логике:** Превращение DI в Service Locator и жесткая привязка к Spring.
- ❌ **Попытка сделать бинами структуры данных (DTO, Records, Entities):** Бинами должны быть только stateless-сервисы, компоненты инфраструктуры и конфигурации.
- ❌ **Игнорирование циклических зависимостей:** Решение циклов через `@Lazy` вместо рефакторинга архитектуры.
