# Які наслідки незмінності String

---

## 🟢 Junior Level

### 30-секундна відповідь
Ім'ютабельність класу `String` тягне за собою як фундаментальні переваги, так і критичні накладні витрати:
- **Позитивні наслідки:**
  1. **Потокобезпека «з коробки»:** рядки можна безпечно розділяти між потоками без синхронізації та ризику стану гонитви.
  2. **String Constant Pool:** однакові літерали зберігаються в єдиному екземплярі, заощаджуючи десятки мегабайтів оперативної пам'яті.
  3. **Стабільний `hashCode`:** кешується під час першого обчислення, гарантуючи надійну роботу в `HashMap` та `HashSet`.
  4. **Безпека системи:** запобігає підміні шляхів до файлів, URL та параметрів безпеки (захист від атак TOCTOU).
- **Негативні наслідки:**
  1. **Алокація нових об'єктів при кожній модифікації:** будь-які операції (`concat`, `replace`, `substring`) створюють нові об'єкти в купі.
  2. **Катастрофа продуктивності в циклах:** конкатенація через оператор `+` у циклі перетворює алгоритм на $O(N^2)$ за часом і пам'яттю. Рішення — `StringBuilder`.
  3. **Вразливість конфіденційних даних:** паролі в `String` неможливо затерти програмно; вони залишаються в дампі пам'яті до збирання сміття.

---

### Проблема конкатенації в циклі та рішення
```java
// АНТИПАТЕРН: O(N^2) за часом та величезна кількість сміття в купі
String result = "";
for (int i = 0; i < 10_000; i++) {
    result += i; // Створюється 10 000 проміжних рядків та масивів!
}

// ПРАВИЛЬНИЙ ПІДХІД: O(N) за часом, один масштабований буфер
StringBuilder sb = new StringBuilder(50_000); // Попереднє виділення місткості
for (int i = 0; i < 10_000; i++) {
    sb.append(i);
}
String result = sb.toString();
```

## 🟡 Middle Level

### 1. Механізм генерації сміття (GC Pressure)
При безперервному створенні тимчасових рядків швидко переповнюється область **Eden** молодого покоління (*Young Generation*):
- Кожен новий рядок алокує заголовок об'єкта `String` (16 байтів при 64-bit Compressed OOPs) + масив `byte[]` (16 байтів заголовок + довжина даних).
- Висока частота алокацій призводить до вичерпання буферів локального виділення потоків (**TLAB** — *Thread-Local Allocation Buffers*) та почастішання пауз збирача сміття (**Minor GC**).

---

### 2. Однорядкова конкатенація vs Конкатенація в циклі
Починаючи з Java 9 (JEP 280), однорядкова конкатенація компілюється в байткод через інструкцію `invokedynamic` і метод `StringConcatFactory.makeConcatWithConstants`:
```java
// Компілюється в один invokedynamic: JVM точно обчислює розмір і алокує масив один раз
String message = "User: " + name + ", age: " + age + ", status: " + status;
```
Проте компілятор **не може об'єднати ітерації циклу** через `invokedynamic`, оскільки кількість повторень невідома на етапі компіляції. Усередині циклу `result += i` як і раніше створює новий буфер і новий рядок на кожній ітерації, копіюючи накопичені символи знову і знову ($O(N^2)$).

---

### 3. Безпека та робота із секретами (Паролі, токени)
Оскільки рядки незмінні, виклик методів очищення неможливий:
```java
// НЕБЕЗПЕЧНО: пароль не можна стерти з пам'яті
String password = request.getParameter("password");

// БЕЗПЕЧНО: масив char[] / byte[] можна гарантовано затерти нулями
char[] secret = console.readPassword("Enter password: ");
try {
    processSecret(secret);
} finally {
    Arrays.fill(secret, '\0'); // Фізичне стирання з RAM
}
```
Рядок `"password123"` може залишатися в купі годинами, потрапити в аварійний *heap dump*, логи або бути витісненим операційною системою у файл підкачки (*swap*).

---

### 4. Вплив на дизайн архітектури
Незмінність `String` привчає розробників до **функціонального стилю (чистих функцій)**:
- Методи, що приймають `String`, гарантовано не мають прихованих побічних ефектів (*side effects*).
- Не потрібно робити захисні копії аргументів на вході в метод і на виході з нього.

---

## 🔴 Senior Level

### Вплив на Card Table та бар'єри запису Garbage Collector
Одна з найбільш недооцінених переваг незмінності рядків проявляється в роботі збирачів сміття (G1, Parallel, CMS):
- Коли об'єкт довго живе і переходить у старше покоління (**Old Generation**), посилання з нього на інші об'єкти відстежуються через структуру **Card Table**.
- Модифікація посилального поля мутабельного об'єкта в Old Gen вимагає виконання інструкцій **Post-Write Barrier**: процесор повинен позначити відповідну картку в пам'яті як «брудну» (*dirty card*).
- Оскільки `String` незмінний, посилання всередині нього (`value`) ніколи не перезаписуються. **Old Gen рядки створюють рівно 0 брудних карток пам'яті**, що радикально скорочує фазу сканування Card Table під час *Minor GC* та знижує затримки пауз (*Stop-the-World*).

---

### Уніфікована дедуплікація рядків (Java 18+, JDK-8267186)
Раніше дедуплікація рядків працювала виключно в G1 GC. Починаючи з **Java 18**, опція `-XX:+UseStringDeduplication` інтегрована в уніфікований фреймворк збирачів сміття і підтримується в **G1, ZGC, Parallel та Serial GC**:
1. При досягненні рядком певного віку збирач сміття обчислює геш байтового масиву `value`.
2. Якщо в глобальній таблиці дедуплікації вже є ідентичний масив `byte[]`, посилання `value` перенаправляється на нього.
3. Подібна прозора заміна посилань можлива **тільки тому, що рядки незмінні** і жоден потік не може модифікувати масив паралельно.

---

### Оптимізації JIT C2: Constant Folding та Scalar Replacement
1. **Constant Folding:** Конкатенація констант часу компіляції (`"a" + "b" + "c"`) згортається компілятором `javac` в один літерал `"abc"` ще у `.class` файлі.
2. **Scalar Replacement (Скалярне заміщення):** Якщо проміжний рядок створюється локально і не залишає метод (перевірка через *Escape Analysis*), JIT-компілятор C2 розбирає об'єкт на скалярні примітивні змінні і розкладає їх за регістрами CPU, взагалі оминаючи алокацію в купі!

---

### Зміна поведінки `substring()` (починаючи з Java 7u6)
- **До Java 7u6:** `substring()` повторно використовував вихідний масив символів `char[]`, змінюючи лише зміщення (`offset`) та довжину (`count`). Це працювало за $O(1)$, але спричиняло витоки пам'яті: маленький підрядок із 5 символів утримував у купі масив на 10 МБ від гігантського вихідного документа.
- **Починаючи з Java 7u6 і дотепер:** `substring()` завжди створює **новий масив символів/байтів**, копіюючи лише потрібний діапазон ($O(N)$ за часом). Це захищає від витоків пам'яті великих масивів.

## 4 Tricky Questions

### 1. Чому компілятор `javac` не може оптимізувати оператор `+` всередині циклу `for`, якщо для звичайних рядків він використовує ефективний `StringConcatFactory`?
**Відповідь:**
Механізм `StringConcatFactory.makeConcatWithConstants` (JEP 280) генерує рецепт склеювання на етапі компіляції для фіксованої кількості аргументів відомого типу, що містяться в одному виразі.
Усередині циклу `for (int i = 0; i < N; i++) s += i;` кількість ітерацій $N$ динамічна і невідома на етапі компіляції. Щоб оптимізувати такий цикл, компілятору знадобилося б перетворити весь цикл на роботу з єдиним зовнішнім `StringBuilder`, що порушує межі трансляції окремих виразів у байткоді та семантику видимості проміжних значень `s` всередині тіла циклу (наприклад, якщо в циклі викликається метод, що читає `s`). Тому компілятор транслює кожну ітерацію окремо, породжуючи $O(N)$ алокацій.

---

### 2. Як незмінність рядків впливає на фазу сканування Card Table під час збирання сміття в поколінних GC?
**Відповідь:**
У поколінних GC (наприклад, G1 або Parallel) збирач сміття відстежує посилання зі старого покоління (Old Gen) у молоде покоління (Young Gen) за допомогою масиву карток (**Card Table**).
Коли програма записує посилання в поле мутабельного об'єкта в Old Gen, процесор виконує бар'єр запису (*Write Barrier*), позначаючи картку розміром 512 байтів як «брудну» (*dirty*).
Оскільки `String` незмінний, після потрапляння об'єкта `String` в Old Gen його поле `value` ніколи не змінюється. Отже, рядки в Old Gen **ніколи не генерують бар'єрів запису і не забруднюють Card Table**. Це істотно знижує кількість пам'яті, що сканується під час фази *Young Collection*, і скорочує паузи STW.

---

### 3. Чи створює метод `s.substring(0, s.length())` новий об'єкт у сучасних версіях Java?
**Відповідь:**
Ні. Метод `substring()` у класі `String` містить швидку перевірку:
```java
if (beginIndex == 0 && endIndex == length()) {
    return this;
}
```
Якщо запитаний зріз збігається з усім рядком, метод миттєво повертає `this` — те саме посилання. Це можливо виключно завдяки незмінності: оскільки стан об'єкта незмінний, повертати наявний екземпляр абсолютно безпечно.

---

### 4. Чи підтримується `-XX:+UseStringDeduplication` у ZGC та Parallel GC, чи це фіча лише G1?
**Відповідь:**
Історично (з Java 8u20) дедуплікація рядків дійсно працювала лише в **G1 GC**.
Проте в **Java 18 (JEP / JDK-8267186)** механізм дедуплікації рядків був повністю перенесений з підсистеми G1 в **уніфікований інтерфейс збирачів сміття JVM (GC abstraction layer)**. Починаючи з Java 18, прапорець `-XX:+UseStringDeduplication` повноцінно підтримується в **G1, ZGC (як у Single-gen, так і в Generational ZGC), Parallel GC та Serial GC**. Твердження про підтримку лише в G1 на сьогодні є застарілим.

## 🎯 Шпаргалка для інтерв'ю

### Плюси та мінуси незмінності String
| Категорія | Наслідок незмінності | Інженерний висновок |
| :--- | :--- | :--- |
| **Пам'ять** | Економія через String Pool та дедуплікацію | Літерали перевикористовуються; дублікати масивів усуваються GC |
| **GC** | Інтенсивна алокація в циклах | Використовувати `StringBuilder` із початковою місткістю |
| **Багатопотоковість** | Повна безпека без блокувань | Можна безпечно передавати посилання між воркерами |
| **Безпека** | Захист від атак TOCTOU | Не можна підмінити шлях до файлу; але паролі потрібно зберігати в `char[]` |
| **JIT / HotSpot** | 0 бар'єрів запису Card Table в Old Gen | Зниження навантаження на збирач сміття в enterprise-сервісах |

### Червоні прапорці на співбесіді (Чого говорити не можна)
- ❌ *«Оператор `+` у циклі оптимізується компілятором через StringBuilder так само, як в одному рядку»* — груба помилка: на кожній ітерації створюється новий об'єкт.
- ❌ *«String Deduplication працює тільки в G1 GC»* — застаріло: з Java 18 дедуплікація працює в G1, ZGC, Parallel та Serial GC.
- ❌ *«Метод `substring()` не виділяє пам'ять, а лише зберігає зміщення offset»* — застаріло з Java 7u6: тепер завжди створюється копія фрагмента масиву `byte[]`.
- ❌ *«Зберігати паролі в String безпечно, якщо метод одразу повертає результат»* — ні, пароль залишиться в купі до збирання сміття і потрапить у Heap Dump.
