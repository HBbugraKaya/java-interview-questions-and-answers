# Что такое idempotent producer

---

## 🟢 Junior Level

### Что такое Idempotent Producer простыми словами

**Idempotent Producer (идемпотентный продюсер)** в Apache Kafka — это режим работы клиента отправки сообщений, который математически гарантирует, что **каждая запись будет сохранена в партиции брокера ровно один раз (exactly-once write per partition)**, даже если из-за сетевых сбоев продюсер производит повторные попытки отправки (`retries`).

В распределенных системах потеря сетевых пакетов — обычное явление. Без механизма идемпотентности возникает классическая проблема дублирования данных:

```
Сценарий БЕЗ идемпотентности:
1. Producer ──send(Message A)──> Broker (Записал в лог offset 42)
2. Broker   ──ACK (TCP)──X (Сетевой сбой / потеря пакета ACK)
3. Producer (таймаут) ──retry(Message A)──> Broker (Записал в лог offset 43)
Итог: Сообщение A сохранено дважды! Возникает дубликат бизнес-события (списание денег, создание заказа).

Сценарий С идемпотентностью (enable.idempotence = true):
1. Producer ──send(PID=101, Seq=0, Message A)──> Broker (Записал в лог offset 42, запомнил Seq=0)
2. Broker   ──ACK (TCP)──X (Потеря пакета ACK)
3. Producer (таймаут) ──retry(PID=101, Seq=0, Message A)──> Broker
4. Broker видит: для PID=101 запись с Seq=0 уже существует!
   -> Брокер отвергает дублирующую запись на диск, но отправляет Producer успешный ACK(offset 42).
Итог: В логе ровно одна запись. Дубликатов нет!
```

### Как включить идемпотентность в Java

Начиная с **Kafka 3.0**, идемпотентность продюсера **включена по умолчанию** (`enable.idempotence = true`). Для версий Kafka 0.11–2.8 ее требовалось указывать явно:

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka-broker1:9092,kafka-broker2:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());

// Включение идемпотентности (по умолчанию true в Kafka 3.0+)
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");

// Создание клиента
KafkaProducer<String, String> producer = new KafkaProducer<>(props);
```

### Ключевые идентификаторы

Дедупликация опирается на две служебные метки, прозрачно добавляемые клиентом:
1. **Producer ID (PID):** 64-битный уникальный идентификатор, автоматически выдаваемый брокером продюсеру при инициализации клиента.
2. **Sequence Number (SeqNum):** 32-битный монотонно возрастающий целочисленный счетчик ($0, 1, 2, \dots$), привязанный к паре `(PID, TopicPartition)`.

## 🟡 Middle Level

### Неявные (автоматические) настройки при `enable.idempotence=true`

Когда свойство `enable.idempotence` установлено в `true`, клиент Kafka Producer автоматически валидирует и выставляет обязательные зависимые параметры:

1. **`acks = all` (`acks = -1`):**
   Гарантия записи на все реплики из ISR (In-Sync Replicas). Без подтверждения от всех реплик брокер не может гарантировать целостность порядка номеров последовательности при возможном переключении лидера (Leader Election).
2. **`retries = Integer.MAX_VALUE`:**
   Количество попыток повторной отправки становится фактически бесконечным (ограничивается лишь тайм-аутом `delivery.timeout.ms`). Продюсер не сдается при временных сетевых ошибках, так как повторы теперь абсолютно безопасны.
3. **`max.in.flight.requests.per.connection <= 5`:**
   Количество неподтвержденных сетевых запросов, одновременно находящихся в сокете к одному брокеру. Значение по умолчанию — `5`. Брокер способен корректно дедуплицировать и упорядочивать до 5 параллельных запросов (начиная с Kafka 1.1).

> **Опасная ошибка конфигурации:**
> Если разработчик явно задаст `enable.idempotence=true` и одновременно укажет `acks=1` или `max.in.flight.requests.per.connection=10`, конструктор `KafkaProducer` выбросит `ConfigException`:
> `org.apache.kafka.common.config.ConfigException: Must set acks to all when enable.idempotence is true`.

### Сравнение уровней гарантий доставки

| Режим продюсера | Конфигурация | Гарантия | Поведение при сбое сети | Риск дублей |
| :--- | :--- | :--- | :--- | :--- |
| **At-Most-Once** | `acks=0` или `retries=0` | Сообщение доставляется максимум один раз | Сообщение теряется навсегда | Нулевой (нет повторов) |
| **At-Least-Once** | `acks=1/all`, `retries>0`, `idempotence=false` | Сообщение доставляется минимум один раз | Повторная отправка создает дубликаты | **Высокий** |
| **Idempotent (At-Least-Once + Deduplication)** | `enable.idempotence=true` | Ровно один экземпляр в партиции | Повторная отправка дедуплицируется брокером | **Нулевой** (в пределах сессии) |
| **Exactly-Once Semantics (EOS)** | Idempotence + `transactional.id` + Transactions API | Атомарная запись в несколько топиков/партиций | Транзакция откатывается или фиксируется целиком | **Нулевой** (сквозной end-to-end) |

### Границы возможностей Idempotent Producer

Хотя идемпотентный продюсер полностью решает проблему сетевых дубликатов, он имеет строгие фундаментальные ограничения:
1. **Только в пределах одной партиции:**
   Счетчик `SequenceNumber` ведется независимо для каждой `TopicPartition`. Дедупликация между разными партициями или разными топиками **не работает**.
2. **Только в пределах одной сессии продюсера (Session-Scoped):**
   PID хранится исключительно в памяти процесса `KafkaProducer`. Если JVM перезапустилась (crash, redeploy), новый экземпляр продюсера запросит у брокера **новый PID**. Если предыдущий процесс успел отправить сообщение, но упал до обработки ответа, а новый процесс повторит бизнес-операцию — брокер сочтет это сообщением от нового продюсера и сохранит дубликат.
3. **Не защищает от логических дубликатов приложения:**
   Если внешний пользователь нажал кнопку «Оплатить заказ» дважды в интерфейсе браузера, и бэкенд породил два разных вызова `producer.send()` с новыми объектами — для Kafka это два разных сообщения с разными Sequence Numbers.

## 🔴 Senior Level

### Архитектурное устройство: KIP-98 и ProducerStateManager

На брокере логика проверки идемпотентности реализована компонентом `ProducerStateManager` (пакет `kafka.log`).

```
                Producer RecordBatch (PID: 5042, Epoch: 0, BaseSeq: 10, LastSeq: 14)
                                             │
                                             ▼
                             Брокер: Partition Replica
                                             │
                                             ▼
                                   ProducerStateManager
         ┌────────────────────────────────────────────────────────────────────────┐
         │ Карта состояний в памяти: Map<Long, ProducerStateEntry>               │
         │ Key: PID (5042)                                                        │
         │ Value:                                                                 │
         │   - ProducerEpoch: 0                                                   │
         │   - LastSequence: 9 (Ожидаемый следующий: 10)                          │
         │   - Sliding Queue последних 5 батчей: [Seq 5, Seq 6, Seq 7, Seq 8, Seq 9]│
         │   - LastUpdatedTimestamp: 1711456000000                                │
         └────────────────────────────────────────────────────────────────────────┘
                                             │
                  ┌──────────────────────────┴──────────────────────────┐
                  ▼                                                     ▼
     BaseSeq == LastSequence + 1 (10 == 9 + 1)             BaseSeq <= LastSequence (10 <= 9)
                  │                                                     │
                  ▼                                                     ▼
          [ВАЛИДНЫЙ ПАКЕТ]                                      [ДУБЛИКАТ]
  - Запись в Active Segment File (.log)                - Запись на диск НЕ производится
  - Обновление LastSequence = 14                       - Формируется успешный ACK
  - Сохранение снимка в *.snapshot файл                 с исходным baseOffset
```

#### Инициализация Producer ID (`InitProducerIdRequest`)
Когда продюсер стартует:
1. Он отправляет `InitProducerIdRequest` брокеру (в роли координатора транзакций `Transaction Coordinator`).
2. Брокер генерирует монотонно возрастающий 64-битный `ProducerId` и 16-битный `ProducerEpoch` (начальное значение `0`).
3. Присвоенный PID резервируется за продюсером.

#### Формат пакета RecordBatch (KIP-98)
Каждый отправляемый пакет `RecordBatch` содержит в заголовке:
- `ProducerId` (int64)
- `ProducerEpoch` (int16)
- `BaseSequence` (int32) — номер последовательности первого сообщения в данном батче.

Внутри батча каждое сообщение не хранит полный счетчик, а имеет лишь относительное смещение: `offsetDelta` и `sequenceDelta` ($0, 1, 2, \dots, N-1$). Это минимизирует накладные расходы на байты в сети.

#### Логика проверки на брокере
Когда `RecordBatch` поступает на брокер в лидер-партицию, `ProducerStateManager` сверяет входящий `BaseSequence` с `LastSequence` для данного PID:
1. **$BaseSequence = LastSequence + 1$ (Идеальный порядок):**
   Батч валиден. Брокер аппендит записи в активный сегмент лога `.log`, обновляет `LastSequence` на значение `LastSequence = BaseSequence + recordCount - 1` и возвращает `RecordMetadata` с присвоенными офсетами.
2. **$BaseSequence \le LastSequence$ (Дубликат):**
   Брокер определяет, что батч с этими номерами уже был записан в лог. Батч **игнорируется** (дискового ввода-вывода нет). Брокер возвращает клиенту штатный `ACK` с тем же смещением (`offset`), которое было присвоено оригинальному батчу. Продюсер считает отправку успешной.
3. **$BaseSequence > LastSequence + 1$ (Нарушение порядка / потеря данных):**
   Брокер обнаруживает «дыру» в последовательности (например, ожидал Seq 10, а пришел Seq 12). Это означает, что промежуточный пакет Seq 10-11 был потерян или застрял. Брокер отвергает запрос фатальной ошибкой `OutOfOrderSequenceException`.

### Механизм скользящего окна: почему допустим `max.in.flight.requests.per.connection = 5`

Исторически (в Kafka 0.11) для работы идемпотентности требовалось выставлять `max.in.flight.requests.per.connection = 1`. Если отправлялось несколько запросов параллельно (R1, R2), и R1 падал с сетевой ошибкой, а R2 долетал успешно, происходило нарушение порядка на диске.

В **Kafka 1.1** (KIP-180) брокер научили управлять **очередью из 5 неподтвержденных запросов**:
- Брокер удерживает очередь входящих батчей для каждого PID.
- Если запрос $R_2$ (Seq 5–9) прибыл на брокер раньше, чем завершился повтор запроса $R_1$ (Seq 0–4), брокер временно не аппендит $R_2$ в лог, а ожидает прибытия $R_1$.
- Как только $R_1$ успешно записан, $R_2$ немедленно записывается следом без генерации `OutOfOrderSequenceException`.
- Если размер окна превышает 5, брокеру не хватает метаданных для разрешения перестановок, что и обуславливает жесткий лимит $\le 5$.

### Персистентность состояний и переключение лидеров: `.snapshot` файлы

Что происходит, если брокер перезапустился или сменился лидер партиции?
1. В каталоге партиции рядом с файлами сегментов лога (`.log`) и индексами (`.index`, `.timeindex`) Kafka сохраняет файлы снимков состояний продюсеров: `00000000000000010000.snapshot`.
2. В snapshot сохраняется сериализованное состояние `ProducerStateManager` (активные PID, их эпохи и последние 5 последовательностей) на момент создания каждого сегмента лога.
3. Фоновый процесс репликации копирует записи с сохранением всех заголовков RecordBatch (включая PID и SeqNum).
4. Follower-реплики поддерживают собственный синхронный `ProducerStateManager`. При смене лидера новый лидер мгновенно готов продолжать проверку идемпотентности без потери контекста.
5. Записи о неактивных продюсерах автоматически удаляются брокером по истечении `transactional.id.expiration.ms` / `producer.id.expiration.ms` (по умолчанию 7 дней).

## 4 Tricky Questions

### 1. Может ли вызов `producer.send()` с `enable.idempotence=true` завершиться исключением `DuplicateSequenceException` на клиенте?

**Ответ:**
**Нет, клиент KafkaProducer никогда не выбрасывает `DuplicateSequenceException` в прикладной код.**
Когда брокер обнаруживает дублирующий батч ($BaseSequence \le LastSequence$), он трактует это как штатный сетевой retry после успешной записи. Брокер отбрасывает тело сообщения, находит исходный присвоенный offset и отправляет продюсеру стандартный `ProduceResponse` с признаком успеха. Для клиентского приложения вызов `callback.onCompletion(metadata, null)` или `future.get()` завершается абсолютно прозрачно и успешно.

### 2. Почему перезапуск пода (Pod Restart) в Kubernetes ломает гарантию идемпотентности, и как добиться гарантии после рестарта?

**Ответ:**
1. При перезапуске приложения (Pod Restart / OOM / Deployment) экземпляр `KafkaProducer` уничтожается.
2. Новый созданный инстанс продюсера выполняет `InitProducerIdRequest` и получает **совершенно новый случайный PID**.
3. Брокер ассоциирует новый PID с нулевым `SequenceNumber` и ничего не знает о связи этого инстанса с предыдущим погибшим процессом.
4. Если упавший процесс успел отправить батч в брокер, но не успел зафиксировать это в локальной БД или внешней очереди, новый процесс может повторно сформировать то же бизнес-событие. Для брокера это будут разные PID, и сообщение запишется второй раз.
5. **Решение:** Для дедупликации через рестарты приложения необходим **Transactional Producer**: задается стабильный строковый идентификатор `props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-service-instance-1")`. При старте с тем же `transactional.id` координатор брокера находит старый PID, инкрементирует `ProducerEpoch` (отсекая зомби-инстансы через `ProducerFencedException`) и сохраняет непрерывную транзакционную историю.

### 3. Что произойдет, если продюсер попытается отправить батч с `max.in.flight.requests.per.connection = 7` при включенной идемпотентности?

**Ответ:**
Поведение зависит от версии клиентской библиотеки Kafka:
- Начиная с версии Kafka 2.0+, попытка инициализировать клиент с `enable.idempotence=true` и `max.in.flight.requests.per.connection > 5` приведет к немедленной ошибке конфигурации при старте приложения:
  `ConfigException: Must set max.in.flight.requests.per.connection to at most 5 to use the idempotent producer`.
- Это ограничение обусловлено тем, что структура дедупликации `ProducerStateManager` на брокере выделяет ровно 5 слотов для хранения последних порядковых номеров для каждого соединения. Превышение этого лимита привело бы к ложным `OutOfOrderSequenceException` в случае сетевой пересортировки пакетов.

### 4. Почему при включенной идемпотентности критически важно сохранять `acks=all`, а не `acks=1`?

**Ответ:**
Представим сценарий с `acks=1`:
1. Producer отправляет батч (PID 100, Seq 1) на брокер-лидер.
2. Лидер записывает батч на свой диск и сразу шлет `ACK` продюсеру, не дожидаясь репликации на followers.
3. Продюсер получает `ACK` и увеличивает локальный счетчик до Seq 2.
4. В этот момент лидер физически сгорает (hardware crash).
5. Follower выбирается новым лидером. Но он **не успел получить** запись Seq 1! В его `ProducerStateManager` последней известной записью является Seq 0.
6. Продюсер отправляет следующий пакет (PID 100, Seq 2).
7. Новый лидер видит: $BaseSequence (2) > LastSequence (0) + 1$.
8. Происходит фатальный сбой: брокер возвращает ошибку `OutOfOrderSequenceException`. Продюсер блокируется и больше не может отправлять сообщения в данную партицию без перезапуска.
Поэтому `acks=all` является строгим математическим требованием консистентности распределенного состояния реплик.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «**Idempotent Producer** — это механизм Kafka (включен по умолчанию с версии 3.0), исключающий появление дубликатов сообщений в партициях при сетевых повторах (`retries`). При старте брокер присваивает продюсеру уникальный идентификатор `ProducerId` (PID), а клиент нумерует каждое сообщение монотонным счетчиком `SequenceNumber` в разрезе каждой партиции. Брокер валидирует последовательность через `ProducerStateManager`. Если из-за потери ACK продюсер повторно шлет уже записанный батч, брокер отбрасывает дубликат, но возвращает клиенту успешный ACK. Включение идемпотентности автоматически форсирует `acks=all`, `retries=INT_MAX` и `max.in.flight.requests.per.connection <= 5`. Идемпотентность работает строго в пределах одной партиции и одной сессии процесса продюсера».

### Ключевые метрики для Production-мониторинга
- `kafka.producer:type=producer-metrics,client-id={id} -> record-error-rate`: частота ошибок отправки сообщений.
- `kafka.producer:type=producer-metrics,client-id={id} -> record-retry-rate`: частота повторных попыток отправки. Если retry-rate высокий, но дублей в топике нет — идемпотентность успешно отрабатывает.
- `kafka.network:type=RequestMetrics,name=ErrorsPerSec,request=Produce,error=OutOfOrderSequenceException`: наличие ошибок рассинхронизации последовательностей на брокерах (сигнал о серьезных сетевых проблемах или нештатных сбоях клиентов).

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«Идемпотентный продюсер гарантирует дедупликацию во всем кластере между всеми сервисами»* — Дедупликация работает строго в разрезе одной партиции и одного конкретного инстанса продюсера.
- ❌ *«Если упал сервис, после рестарта идемпотентный продюсер не допустит дублей»* — Допустит, так как новый процесс получит новый PID. Для дедупликации через рестарты нужен `transactional.id`.
- ❌ *«Идемпотентный продюсер требует max.in.flight.requests.per.connection = 1»* — Устарело. Начиная с Kafka 1.1 допустимо значение до `5` включительно.
- ❌ *«При обнаружении дубликата брокер выбрасывает ошибку продюсеру»* — Брокер тихо отбрасывает дубликат и отвечает штатным ACK об успехе.
