# Опишите жизненный цикл Entity в Hibernate

---

## 🟢 Junior Level

### Что такое жизненный цикл сущности (Entity Lifecycle)

В JPA и Hibernate сущность — это не просто стандартный Java-объект (POJO), а объект, чье состояние синхронизируется со строкой в реляционной базе данных через посредника — контекст постоянства (**`PersistenceContext`**, также известный как кэш первого уровня L1).

Жизненный цикл сущности описывается **четырьмя фундаментальными состояниями**:

1. **`Transient` (Новый / Временный):**
   Объект только что создан через оператор `new`. Он существует исключительно в куче (JVM Heap), у него нет первичного ключа (`id == null`), и контекст `PersistenceContext` о нем ничего не знает.
2. **`Managed` / `Persistent` (Управляемый):**
   Объект привязан к текущей сессии (`Session` / `EntityManager`) и имеет присвоенный идентификатор (`id`). Любые изменения полей объекта автоматически отслеживаются механизмом **Dirty Checking** и сохраняются в БД при закрытии транзакции.
3. **`Detached` (Отсоединенный):**
   Объект имеет строку и идентификатор в БД, но его сессия была закрыта (или был вызван `detach()`/`clear()`). Изменения его полей больше не отслеживаются Hibernate.
4. **`Removed` (Помеченный на удаление):**
   Управляемый объект помечен на удаление вызовом `remove()`. При ближайшей синхронизации с базой (`flush`) будет сгенерирован SQL `DELETE`.

```
                    ЖИЗНЕННЫЙ ЦИКЛ СУЩНОСТИ (JPA STATE MACHINE)
                    
                      [ Transient ] (new User())
                           │
                 persist() │ merge()
                           ▼
  ┌─────────────────> [ Managed ] <─────────────────┐
  │                    │       │                    │
  │   detach()/clear() │       │ remove()           │ merge()
  │                    ▼       ▼                    │
  │             [ Detached ]  [ Removed ] ──────────┘
  │                    │       │           persist()
  └────────────────────┘       ▼
                          (SQL DELETE при flush)
```

### Базовый пример перехода по состояниям

```java
// 1. Состояние TRANSIENT: объект в памяти, в БД записи нет
User user = new User();
user.setName("Алексей");

// 2. Переход TRANSIENT -> MANAGED
entityManager.persist(user); 
// Теперь объект отслеживается сессией. 

user.setName("Александр"); // Dirty checking зафиксирует изменение без вызова update!

// 3. Переход MANAGED -> DETACHED
entityManager.detach(user); 
user.setName("Иван"); // Это изменение НЕ попадет в БД, так как объект detached!

// 4. Переход DETACHED -> MANAGED
User managedUser = entityManager.merge(user); // Возвращает НОВУЮ управляемую копию

// 5. Переход MANAGED -> REMOVED
entityManager.remove(managedUser); // В БД уйдет DELETE при коммите транзакции
```

## 🟡 Middle Level

### Карта методов управления состояниями

| Исходное состояние | Метод `EntityManager` | Новое состояние | Действие в базе данных |
| :--- | :--- | :--- | :--- |
| **Transient** | `persist(e)` | **Managed** | Будет выполнен `INSERT` (при `flush`) |
| **Transient** | `merge(e)` | **Managed** (копия) | Выполняет `SELECT`, затем `INSERT` |
| **Managed** | `detach(e)` / `clear()` | **Detached** | Никаких действий с БД |
| **Managed** | `remove(e)` | **Removed** | Будет выполнен `DELETE` (при `flush`) |
| **Managed** | `refresh(e)` | **Managed** | Выполняет `SELECT` и перезаписывает поля из БД |
| **Detached** | `merge(e)` | **Managed** (копия) | Выполняет `SELECT`, затем `UPDATE` |
| **Detached** | `persist(e)` | ❌ **Ошибка** | Выбрасывает `EntityExistsException` |
| **Detached** | `remove(e)` | ❌ **Ошибка** | Выбрасывает `IllegalArgumentException` |
| **Removed** | `persist(e)` | **Managed** | Отменяет удаление |

### Главная ловушка `merge()`: Игнорирование возвращаемого значения

Распространенная ошибка разработчиков:
```java
User detachedUser = getDetachedUser();
detachedUser.setName("Новое имя");

entityManager.merge(detachedUser); // ОШИБКА: Возвращаемое значение проигнорировано!
detachedUser.setEmail("new@test.com"); // НЕ сохранится в БД!
```

**Почему это происходит:**
Метод `merge()` **НЕ делает переданный объект управляемым**! 
- Исходный объект `detachedUser` так и остается в состоянии `Detached`.
- `merge()` находит или создает **новый дублирующий экземпляр** в `PersistenceContext`, копирует в него поля из `detachedUser` и возвращает **ссылку на этот новый managed-объект**:
```java
// ПРАВИЛЬНО:
User managedUser = entityManager.merge(detachedUser);
managedUser.setEmail("new@test.com"); // Сохранится в БД благодаря dirty checking
```

### Жизненные слушатели и колбэки (JPA Entity Callbacks)

JPA позволяет перехватывать изменения состояний с помощью аннотаций прямо в классе сущности:

```java
@Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;

    @PrePersist
    protected void onPrePersist() {
        this.createdAt = LocalDateTime.now();
        this.updatedAt = this.createdAt;
    }

    @PreUpdate
    protected void onPreUpdate() {
        this.updatedAt = LocalDateTime.now();
    }

    @PostLoad
    protected void onPostLoad() {
        // Вызывается сразу после загрузки строки из БД в память
    }
}
```

- `@PrePersist` / `@PostPersist` — до и после вставки в БД (`persist`).
- `@PreUpdate` / `@PostUpdate` — до и после выполнения SQL `UPDATE`.
- `@PreRemove` / `@PostRemove` — до и после удаления строки (`DELETE`).
- `@PostLoad` — сразу после материализации сущности из `ResultSet`.

## 🔴 Senior Level

### Внутренности PersistenceContext: `EntityEntry` и `LoadedState`

Внутри реализации Hibernate Session (`SessionImpl`) контекст постоянства представлен классом `StatefulPersistenceContext`.

В нем хранятся две ключевые карты:
1. `entitiesByKey: Map<EntityKey, Object>` — кэш первого уровня (L1 Cache). Предотвращает дублирование объектов одного ID в памяти.
2. `entityEntries: Map<Object, EntityEntry>` — метаданные отслеживания состояния.

```
StatefulPersistenceContext
├── entitiesByKey: [ User#1 -> User@0x123 ]
└── entityEntries:
    └── User@0x123 -> EntityEntry {
            status: Status.MANAGED,
            loadedState: ["Алексей", "alex@mail.com", 25],  // Первоначальный снимок (Snapshot)
            id: 1,
            version: 0
        }
```

#### Механика работы Dirty Checking при Flush:
1. Во время вызова `flush()` Hibernate обходит карту `entityEntries`.
2. Для каждого объекта со статусом `Status.MANAGED` он сравнивает текущие значения полей Java-объекта со снимком `loadedState`.
3. Если значения различаются, Hibernate формирует SQL `UPDATE` строго по измененным полям (или по всем колонкам, если не включена `@DynamicUpdate`).
4. После подтверждения транзакции снимок `loadedState` обновляется.

### Влияние стратегии генерации ID на момент выполнения INSERT

На собеседованиях сеньоров часто спрашивают: *«Когда именно выполняется физический SQL INSERT при вызове `persist()`?»*.

Ответ зависит от стратегии `@GeneratedValue`:

1. **`GenerationType.IDENTITY` (Вынужденный Immediate INSERT):**
   - Чтобы перевести сущность в состояние `Managed`, Hibernate **обязан знать ее первичный ключ**.
   - При `IDENTITY` первичный ключ генерируется базой данных через автоинкремент (`AUTO_INCREMENT` / `SERIAL`) **только в момент физической вставки строки**.
   - **Следствие:** Вызов `entityManager.persist(user)` **немедленно выполняет SQL `INSERT` в базу данных**, ломая отложенный сброс (Write-Behind) и делая невозможным пакетную вставку (JDBC Batching)!
2. **`GenerationType.SEQUENCE` / `TABLE` (Delayed INSERT):**
   - Hibernate запрашивает следующее число из последовательности через `SELECT nextval('seq_user')` заранее.
   - Идентификатор присваивается Java-объекту в памяти мгновенно.
   - Физический SQL `INSERT` **откладывается до вызова `flush()` или фиксации транзакции**. Пакетная вставка (JDBC Batching) работает на максимальной скорости.

## 4 Tricky Questions

### 1. Что произойдет, если передать объект в состоянии `Detached` в метод `entityManager.remove()`?

**Ответ:**
Спецификация JPA прямо запрещает удаление отсоединенных сущностей.
1. Вызов `entityManager.remove(detachedUser)` немедленно завершится исключением:
   `java.lang.IllegalArgumentException: Removing a detached instance com.example.User#1`.
2. Чтобы удалить сущность, которая пришла из внешнего слоя (например, DTO с ID из REST-запроса), ее необходимо сначала перевести в состояние `Managed`:
   ```java
   // Вариант 1: Через merge (сначала делает SELECT, затем удаляет)
   User managed = entityManager.merge(detachedUser);
   entityManager.remove(managed);

   // Вариант 2: Загрузить ссылку без лишнего SELECT (getReference / find)
   User ref = entityManager.getReference(User.class, id);
   entityManager.remove(ref);
   ```

### 2. Почему в методах жизненных колбэков (`@PrePersist`, `@PreUpdate`) категорически запрещено вызывать `EntityManager` или `Repository`?

**Ответ:**
1. Методы колбэков вызываются Hibernate в критические моменты синхронизации внутреннего состояния (`flush` или каскадный обход дерева объектов).
2. Попытка вызвать методы `entityManager.persist()`, `merge()` или выполнить JPQL-запрос внутри `@PrePersist` приводит к повторному рекурсивному входу во внутренний процессор состояний Hibernate (`ActionQueue`).
3. Это приводит к рассинхронизации карты `entityEntries`, зависанию транзакции или выбросу непредсказуемых исключений вида `AssertionFailure` и `ConcurrentModificationException`.
4. **Правило:** Внутри колбэков разрешено только менять локальные поля самого объекта (таймстемпы, генерация UUID, вычисление хешей).

### 3. Объект находится в состоянии `Managed`. Мы меняем его поле `user.setName("New")`, а затем вызываем `entityManager.refresh(user)`. Что произойдет с объектом и базой данных?

**Ответ:**
1. Метод `refresh()` выполняет принудительную перезагрузку состояния сущности напрямую из базы данных через SQL `SELECT`.
2. Все несохраненные локальные изменения, сделанные в памяти (`user.setName("New")`), **будут безвозвратно стерты и перезаписаны** теми данными, которые физически хранятся в строке таблицы БД.
3. Механизм Dirty Checking не сгенерирует SQL `UPDATE`, так как поля объекта снова станут идентичны снимку `loadedState`.

### 4. В чем разница между вызовом `entityManager.detach(user)` и `entityManager.clear()`?

**Ответ:**
- `entityManager.detach(user)`: отсоединяет **только один конкретный экземпляр** сущности от контекста постоянства. Все остальные объекты в сессии остаются `Managed`.
- `entityManager.clear()`: полностью очищает весь контекст постоянства (`PersistenceContext`). **Абсолютно все сущности**, ранее загруженные в рамках текущей сессии, одновременно переходят в состояние `Detached`. Любые накопленные, но не сброшенные через `flush()` изменения отменяются.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «Жизненный цикл Entity в JPA состоит из четырех состояний: **`Transient`** (новый объект в куче, не привязан к сессии), **`Managed`** (привязан к `PersistenceContext`, имеет ID, отслеживается через Dirty Checking), **`Detached`** (сессия закрыта, объект не отслеживается) и **`Removed`** (помечен на удаление при `flush`). Переходы выполняются методами `persist()`, `merge()`, `remove()`, `detach()` и `refresh()`. Критический нюанс: метод `merge()` не делает исходный объект managed, а возвращает новую управляемую копию. Использование стратегии `GenerationType.IDENTITY` форсирует немедленный `INSERT` в момент вызова `persist()`, в то время как `SEQUENCE` откладывает вставку до фиксации транзакции».

### Ключевые метрики для Production-мониторинга
- Время фазы сброса контекста (Flush Duration в Hibernate Statistics).
- Количество сущностей, одновременно удерживаемых в `PersistenceContext` (риск утечек памяти при отсутствии вызовов `clear()` в батчах).

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«Метод merge(entity) делает переданный объект управляемым»* — Нет, он возвращает новый managed-объект, а старый остается detached.
- ❌ *«Чтобы обновить сущность в БД, нужно обязательно вызвать em.update() или em.merge()»* — Для managed-сущностей это не требуется, работает автоматический Dirty Checking.
- ❌ *«Любой вызов persist() откладывает SQL INSERT до конца транзакции»* — При `GenerationType.IDENTITY` вставка выполняется немедленно.
- ❌ *«Detached-объект можно удалить напрямую через em.remove(detached)»* — Это выбросит `IllegalArgumentException`.
