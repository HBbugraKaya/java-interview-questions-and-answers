# What are raw types and why should you avoid them

A **Raw Type** is the name of a generic class or interface used without any type arguments (e.g., declaring `List` instead of `List<String>`). Retained strictly for backward compatibility with pre-Java 5 (Java 1.4) codebases, raw types disable compiler type safety, induce heap pollution, and defer catastrophic casting failures to runtime.

---

## 🟢 Junior Level

### Definition and Core Hazard
When a generic class is used without specifying type arguments, it reverts to legacy untyped behavior:

```java
// ❌ RAW TYPE: Disables compiler type safety
List rawList = new ArrayList(); // Compiler warning: [rawtypes]
rawList.add("Hello World");
rawList.add(Integer.valueOf(42)); // Allowed by the compiler!

// Later during execution:
String s1 = (String) rawList.get(0); // OK
String s2 = (String) rawList.get(1); // 💥 Throws ClassCastException at runtime!

// ✅ PARAMETERIZED TYPE: 100% Compile-Time Safe
List<String> safeList = new ArrayList<>();
safeList.add("Hello World");
// safeList.add(42); // Compilation Error: incompatible types
String s = safeList.get(0); // No casting required
```

### Three Reasons to Avoid Raw Types (Effective Java Item 26)
1. **Total Loss of Compile-Time Type Safety:** The compiler skips type validation during insertion, allowing arbitrary objects into collections.
2. **Delayed Production Crashes:** Errors do not occur where corrupt data is inserted; they explode far away in unrelated modules when data is read.
3. **Boilerplate and Fragility:** Code becomes cluttered with manual `(Type)` downcasting and `@SuppressWarnings` annotations.

## 🟡 Middle Level

### 1. Cascading Erasure of Member Types (JLS §4.8)
A subtle and dangerous consequence of raw types is **Cascading Member Erasure**:
According to Section 4.8 of the Java Language Specification, **using a raw type erases the return types of ALL methods in that class**, even methods that do not depend on the generic type parameter $T$!

```java
public class Container<T> {
    private T value;

    // This method does NOT use T at all!
    public List<String> getTags() {
        return List.of("alpha", "beta");
    }
}

// 1. Using a parameterized reference:
Container<Integer> typed = new Container<>();
List<String> tags = typed.getTags(); // Compiles cleanly: returns List<String>

// 2. Using a raw reference:
Container raw = new Container();
// ❌ Compilation Warning / Type Mismatch:
// getTags() does NOT return List<String>; it returns a RAW List!
List<String> rawTags = raw.getTags(); // Unchecked conversion warning!
```

Referencing an object via its raw type "poisons" the entire API surface of that instance, stripping generic guarantees from all members.

### 2. The Critical Difference: `List` (Raw) vs. `List<?>` vs. `List<Object>`
Many developers mistakenly assume `List`, `List<?>`, and `List<Object>` are interchangeable:

| Type Declaration | Type Safety | Invariance / Mutability | Permitted Insertions |
| :--- | :--- | :--- | :--- |
| **`List` (Raw Type)** | 🔴 **Unsafe** (Checks bypassed) | Opt-out of generic system | Accepts **any** object (causes heap pollution). |
| **`List<Object>`** | 🟢 **Safe** (Strictly checked) | Invariant (cannot assign `List<String>`) | Accepts **any** object; verified at compile time. |
| **`List<?>` (Wildcard)** | 🟢 **Safe** (Strictly checked) | Covariant read-only container | Accepts **only `null`**; prevents data corruption. |

```java
List raw = new ArrayList<String>();
raw.add(100); // Compiles (with warning); corrupts the list!

List<?> wildcard = new ArrayList<String>();
// wildcard.add(100); // Compilation Error: The compiler protects the list!
wildcard.add(null);   // Only null is permitted
```

## 🔴 Senior Level

### The Only Two Legitimate Use Cases for Raw Types (JLS §4.8)
The Java Language Specification permits raw types in only two syntactic scenarios:

#### 1. Class Literals (`.class`)
Class literals cannot contain generic parameters:
```java
Class<?> c1 = List.class; // Valid: Raw class literal required

// Compilation Errors:
// Class<?> c2 = List<String>.class; 
// Class<?> c3 = List<?>.class;
```

#### 2. The `instanceof` Operator
Because generic parameters are erased at runtime, checking parameterized types via `instanceof` is illegal:
```java
// Valid:
if (obj instanceof List) { ... }    // Legal raw check
if (obj instanceof List<?>) { ... } // Idiomatic modern check (Java 16+)

// Compilation Error: Cannot check erased type parameter at runtime
// if (obj instanceof List<String>) { ... }
```

### The Mechanism of Heap Pollution
Raw types are the primary vector for **Heap Pollution**:
```java
public class PollutionDemo {
    public static void main(String[] args) {
        List<String> strings = new ArrayList<>();
        corrupt(strings); // Passes safe collection to legacy raw method

        // The line below contains ZERO explicit casts and looks completely safe:
        String s = strings.get(0); // 💥 ClassCastException: Integer cannot be cast to String!
    }

    private static void corrupt(List rawList) {
        // Raw list allows adding an Integer without compile-time error:
        rawList.add(Integer.valueOf(42)); // Memory pollution occurs here!
    }
}
```

The danger of heap pollution is that diagnostic stack traces point to innocent read sites (`strings.get(0)`), concealing the defective write operation (`rawList.add(42)`).

## 4 Tricky Questions

### 1. What happens to all other methods of a generic class when accessed through a raw type reference?
**Answer:** In accordance with JLS §4.8, accessing a class via a raw type triggers **Cascading Erasure of Member Types**. 

The signatures of all fields, methods, and constructors within that class undergo full type erasure. Even if a method does not reference the class's type variable $T$ (such as `public List<String> getTags()`), calling it via a raw reference results in the return type being erased to a raw `List`. This strips compile-time generic safety from the entire public contract of the class.

### 2. What is the fundamental difference between raw `List` and unbounded wildcard `List<?>`?
**Answer:** 
- A raw `List` completely **opts out of generic type checking**. The compiler allows adding arbitrary objects (`raw.add("abc")`, `raw.add(123)`), exposing the application to heap pollution and runtime `ClassCastException`.
- An unbounded wildcard `List<?>` **fully preserves compile-time type safety**. It signifies a list of some specific, unknown type. Because the compiler does not know what that type is, it strictly prohibits adding any element (except `null`). `List<?>` is a read-only view that prevents corruption while allowing generic manipulation.

### 3. Under what exact circumstances does the Java Language Specification require or permit the use of raw types?
**Answer:** The Java specification mandates raw types in only two syntactic contexts:
1. **Class Literals:** The `.class` token syntax requires a raw type (`List.class`). Writing `List<String>.class` or `List<?>.class` is a syntax error because all generic instances share the exact same runtime `Class` object (`List.class`).
2. **The `instanceof` Operator:** Because type arguments are erased at runtime, checking `obj instanceof List<String>` is illegal. Developers must check against the raw type `obj instanceof List` or the reifiable unbounded wildcard `obj instanceof List<?>`.

### 4. Why hasn't the Java Language Committee completely removed raw types from modern Java?
**Answer:** Absolute **backward compatibility**. 

Billions of lines of enterprise Java code and thousands of precompiled `.jar` files in Maven repositories rely on binaries compiled prior to Java 5 or interact with legacy raw libraries. Completely deprecating or removing raw types would break existing enterprise infrastructure without recompilation. Instead, the Java compiler emits `[rawtypes]` and `[unchecked]` compiler warnings, guiding developers to adopt parameterized types and wildcards in modern code.

## 🎯 Interview Cheat Sheet

- **Core Rule:** *Effective Java* Item 26: **Do not use raw types**.
- **Definition:** Using a generic type without type parameters (`List` instead of `List<String>`).
- **Primary Hazards:**
  - Bypasses compile-time type checking.
  - Causes **Heap Pollution**, resulting in delayed runtime `ClassCastException`.
  - **Cascading Member Erasure (JLS §4.8):** Erases return types of *all* methods on the instance, even those independent of $T$.
- **`List` vs. `List<?>`:**
  - Raw `List`: Unsafe, allows arbitrary additions.
  - `List<?>`: Completely type-safe, prohibits all additions except `null`.
- **Permitted Exceptions:**
  - Class literals: `List.class` (never `List<String>.class`).
  - Runtime checks: `instanceof List` or `instanceof List<?>`.
- **Compiler Warnings:** Raw types generate `[rawtypes]` and `[unchecked]` warnings. Suppress only at boundaries with legacy libraries using `@SuppressWarnings("rawtypes")`.
