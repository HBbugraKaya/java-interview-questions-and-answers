# Чому слід уникати побічних ефектів в Stream

---

## 🟢 Junior Level

### Коротка відповідь для співбесіди (30 секунд)
Побічних ефектів (side-effects) у Stream API слід уникати з трьох фундаментальних причин:

1. **Руйнування багатопотоковості:** Будь-яка мутація зовнішніх змінних або колекцій (наприклад, `list.add()`) при перемиканні на `parallelStream()` призводить до гонок даних (Race Conditions), пошкодження пам'яті або `ArrayIndexOutOfBoundsException`.
2. **Недетермінізм через лінивість (Laziness):** Проміжні операції (`map`, `filter`, `peek`) виконуються лише тоді, коли це суворо необхідно термінальній операції. Якщо термінальна операція завершиться достроково (short-circuiting) або буде оптимізована рантаймом, побічні ефекти відбудуться не для всіх елементів або не відбудуться зовсім.
3. **Порушення контракту Non-interference:** Спроба змінити вихідну колекцію прямо під час проходу по стріму призводить до негайного падіння з `ConcurrentModificationException`.

Стріми спроєктовані для обчислення нових значень на основі чистих функцій (Pure Functions), а не для виконання процедурних мутацій.

---

### Приклади: Антипатерн проти Чистого коду на Java 21

```java
import java.util.ArrayList;
import java.util.List;

public class AvoidSideEffectsDemo {

    public static void main(String[] args) {
        List<String> source = List.of("яблуко", "банан", "груша");

        // ❌ АНТИПАТЕРН: Накопичення результату через сайд-ефект у проміжному кроці
        List<String> sideEffectList = new ArrayList<>();
        source.stream()
            .map(String::toUpperCase)
            .forEach(sideEffectList::add); // При паралелізмі впаде або втратить дані!

        // ✅ ПРАВИЛЬНО: Результат конструюється самим Stream API
        List<String> cleanList = source.stream()
            .map(String::toUpperCase)
            .toList();

        System.out.println("Чистий результат: " + cleanList);
    }
}
```

## 🟡 Middle Level

### Принцип Non-interference (Невтручання в джерело)

Специфікація `java.util.stream` суворо забороняє модифікацію джерела даних під час обходу:

```java
import java.util.ArrayList;
import java.util.List;

public class NonInterferenceViolationDemo {

    public static void main(String[] args) {
        List<String> mutableList = new ArrayList<>(List.of("alpha", "beta", "gamma"));

        // ❌ Порушення Non-interference: зміна джерела прямо під час стріма
        try {
            mutableList.stream()
                .filter(item -> {
                    if ("beta".equals(item)) {
                        mutableList.add("delta"); // Викличе ConcurrentModificationException!
                    }
                    return true;
                })
                .forEach(System.out::println);
        } catch (Exception e) {
            System.out.println("Спіймано виняток: " + e.getClass().getSimpleName());
        }
    }
}
```

> **Важливо:** Більшість сплітераторів стандартних колекцій (`ArrayList`, `HashSet`) є fail-fast: вони перевіряють лічильник модифікацій `modCount` і при виявленні мутації негайно викидають `ConcurrentModificationException`.

---

### Пастка оптимізацій: зникнення побічних ефектів

У процедурному програмуванні гарантується виклик кожного рядка коду. У декларативному Stream API рантайм має право оптимізувати пайплайн:

1. **Short-circuiting:** Операції `findFirst()`, `findAny()`, `anyMatch()`, `limit()` зупиняють обхід, щойно отримано відповідь. Сайд-ефекти для решти елементів не виконаються.
2. **Stream Pruning (Java 9+):** Виклик `stream.count()` на колекції з відомим розміром (`SIZED`) повністю вирізає проміжні виклики:

```java
List<String> items = List.of("one", "two", "three");

// Очікування: 3 записи в лог.
// Реальність (Java 9+): 0 записів у лог! Метод peek() повністю видалений JIT/рантаймом.
long total = items.stream()
    .peek(s -> System.out.println("Log: " + s))
    .count();
```

## 🔴 Senior Level

### Проблеми з Enterprise-контекстами (`ThreadLocal`, Transactions, MDC)

У реальних Enterprise-застосунках (Spring Boot, Hibernate, Spring Security) інфраструктурний контекст прив'язується до потоку запиту через `ThreadLocal`:
- `@Transactional`: транзакція та з'єднання `Connection` живуть у потоці.
- `SecurityContextHolder`: інформація про поточний токен і користувача.
- `MDC` (Mapped Diagnostic Context): `traceId` та `spanId` для розподіленого трейсингу.

```java
// ❌ КАТАСТРОФА В ENTERPRISE-СЕРВІСІ:
@Transactional
public void processOrders(List<Order> orders) {
    orders.parallelStream()
        .forEach(order -> {
            // Потоки ForkJoinPool не мають @Transactional контексту!
            // Запис піде або в автокоміт-режимі, або впаде з LazyInitializationException!
            orderRepository.save(order);
        });
}
```

Побічні ефекти з викликом сервісів/репозиторіїв усередині паралельних стрімів призводять до витоків транзакцій, втрати аудиту безпеки та вичерпання пулу підключень до БД (HikariCP).

---

### Апаратна деградація: CAS Contention та False Sharing

Спроба розробників обійти проблеми багатопотоковості загортанням зовнішніх змінних в `AtomicInteger` або потокобезпечні колекції (`ConcurrentHashMap`) усередині паралельного стріма створює важкі апаратні просідання:

```java
AtomicLong counter = new AtomicLong();
data.parallelStream().forEach(x -> counter.incrementAndGet());
```

- Постійні атомарні інструкції `LOCK CMPXCHG` на одній змінній призводять до лавиноподібного між'ядерного трафіку по шині процесора (Cache Line Bouncing).
- Усі ядра процесора безперервно скидають свої кеші L1/L2.
- Заміна цього антипатерну на чисту редукцію `mapToLong(...).sum()` прискорює обчислення на порядки, оскільки кожне ядро рахує суму у своєму локальному регістрі CPU без між'ядерних блокувань.

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь
> «Побічних ефектів у Stream API слід уникати, оскільки стріми базуються на принципах чистих функцій. Наявність побічних ефектів ламає паралельне виконання (викликаючи гонки даних і збої кешів CPU), призводить до втрати контекстів Spring Security та `@Transactional`, а також робить логіку нестабільною через лінивість та оптимізації JVM (наприклад, у Java 9+ `peek()` перед `count()` просто не викликається). Єдине місце для побічного ефекту — термінальний метод `forEach()`, коли метою стріма є безпосереднє виведення даних.»

---

### Порівняння функціонального підходу та побічних ефектів

| Критерій | Чистий підхід (`collect`, `reduce`) | Побічний ефект (`forEach(list::add)`) |
|---|---|---|
| **Безпека в `parallelStream`** | 🟢 Повна потокобезпечність | 🔴 Гонки даних, псування пам'яті |
| **Передбачуваність при short-circuiting** | 🟢 Детермінований результат | 🔴 Неповна зміна стану |
| **Оптимізації JVM (Java 9+)** | 🟢 Коректна робота | 🔴 Можливість пропуску операцій |
| **Читабельність коду** | 🟢 Декларативний стиль | 🟡 Приховані процедурні мутації |
| **Збереження транзакцій Spring** | 🟢 Ізольовано в одному потоці | 🔴 Втрата транзакції в пулі воркерів |

### Топ-4 каверзних запитання на інтерв'ю

#### 1. Чому у Java 9+ метод `stream.peek(...).count()` може проігнорувати `peek()`?
- Починаючи з Java 9, реалізація методу `.count()` в інтерфейсі `Stream` перевіряє прапорці сплітератора. Якщо джерело стріма має фіксований відомий розмір (`SIZED`), а в конвеєрі немає операцій, що змінюють кількість елементів (як `filter` або `flatMap`), рантайм повертає `spliterator.getExactSizeIfKnown()` безпосередньо, взагалі не запускаючи конвеєр і відкидаючи `peek()`.

#### 2. Що станеться, якщо лямбда всередині стріма додасть елемент у колекцію-джерело?
- Буде викинуто виняток `ConcurrentModificationException`, оскільки більшість стандартних колекцій Java (наприклад, `ArrayList`, `HashSet`) перевіряють відповідність `modCount` при кожному кроці ітератора або сплітератора. Це пряме порушення вимоги *Non-interference*.

#### 3. Чому в паралельних стрімах виклики зовнішніх баз даних через `forEach(repo::save)` призводять до неконсистентності даних?
- Анотація `@Transactional` у Spring використовує `ThreadLocal` викликаючого потоку. Воркери `ForkJoinPool`, що виконують паралельний стрім, не мають доступу до цього контексту транзакції. Кожна операція запису буде виконуватися поза вихідною транзакцією (у режимі автокоміту), що унеможливлює відкат (rollback) при виникненні помилки.

#### 4. У яких випадках використання побічних ефектів усередині `forEach()` вважається виправданим?
- Виключно в ролі завершальної термінальної дії: відправка готового DTO в чергу повідомлень (Kafka), запис готового рядка в сокет або друк звіту на екран, коли конвеєр уже повністю завершив трансформацію та фільтрацію даних.

---

### Типові помилки та Red Flags
- 🚩 Запис даних у зовнішній список усередині проміжних операцій (`map`, `filter`).
- 🚩 Спроба використовувати `peek()` для реалізації бізнес-логіки сервісу.
- 🚩 Виклики методів збереження в БД усередині `parallelStream()` під анотацією `@Transactional`.
- 🚩 Модифікація вихідної колекції під час виконання стріма по ній.
