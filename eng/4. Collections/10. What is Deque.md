# What is Deque

---

## 🟢 Junior Level

**`Deque` (Double-Ended Queue, pronounced *"deck"*)** is a core interface in the Java Collections Framework (`java.util.Deque`) that models a linear sequence supporting element insertion, removal, and inspection from **both ends**: the front (head) and the back (tail).

### Real-World Analogy
Think of a deck of playing cards in a magician's hands: cards can be drawn from the top or pulled from the bottom; similarly, cards can be placed onto the top or slipped beneath the bottom.

### Deque Unifies Stacks and Queues
The `Deque` interface serves as a comprehensive, modern replacement for both legacy stacks and standard queues:
- **As a FIFO Queue (First-In, First-Out):** Elements are appended to the tail (`offerLast` / `offer`) and retrieved from the head (`pollFirst` / `poll`).
- **As a LIFO Stack (Last-In, First-Out):** Elements are pushed onto the head (`push` / `addFirst`) and popped off the head (`pop` / `removeFirst`).

```java
Deque<String> deque = new ArrayDeque<>();

// 1. Used as a FIFO Queue:
deque.offer("First");
deque.offer("Second");
System.out.println(deque.poll()); // "First"

// 2. Used as a LIFO Stack:
deque.push("Bottom");
deque.push("Top");
System.out.println(deque.pop());  // "Top"

// 3. Explicit dual-ended operations:
deque.addFirst("Front");
deque.addLast("Back");
System.out.println(deque.peekFirst()); // "Front"
System.out.println(deque.peekLast());  // "Back"
```

## 🟡 Middle Level

### 1. The Method Matrix: Head vs. Tail Operations

Every endpoint operation is exposed in two forms: one that throws an unchecked exception when an operation fails (e.g., empty or capacity-restricted), and one that returns a sentinel value (`false` or `null`):

| Operation | Head (Front) — Throws Exception | Head (Front) — Special Value | Tail (Back) — Throws Exception | Tail (Back) — Special Value |
| :--- | :--- | :--- | :--- | :--- |
| **Insert** | `addFirst(e)` | **`offerFirst(e)`** | `addLast(e)` | **`offerLast(e)`** |
| **Remove** | `removeFirst()` | **`pollFirst()`** | `removeLast()` | **`pollLast()`** |
| **Examine** | `getFirst()` | **`peekFirst()`** | `getLast()` | **`peekLast()`** |

#### Queue and Stack Equivalents in Deque

| Queue Method | Equivalent Deque Method | Stack Method | Equivalent Deque Method |
| :--- | :--- | :--- | :--- |
| `add(e)` | `addLast(e)` | `push(e)` | `addFirst(e)` |
| `offer(e)` | `offerLast(e)` | `pop()` | `removeFirst()` |
| `remove()` | `removeFirst()` | `peek()` | `getFirst()` / `peekFirst()` |
| `poll()` | `pollFirst()` | — | — |
| `element()` | `getFirst()` | — | — |
| `peek()` | `peekFirst()` | — | — |

### 2. Why `ArrayDeque` is the Superior `Deque` Implementation

In standard Java SE, two main classes implement `Deque`: `ArrayDeque` and `LinkedList`.

| Criterion | `ArrayDeque` | `LinkedList` |
| :--- | :--- | :--- |
| **Underlying Data Structure** | Resizable circular array (`Object[]`) | Doubly-linked node chain (`Node<E>`) |
| **Endpoint Operations Time Complexity** | **$O(1)$ amortized** | **$O(1)$ strictly** |
| **CPU Cache Locality** | **Optimal** (contiguous block of memory) | Extremely poor (dispersed heap pointers) |
| **Memory Footprint** | Minimal (~$4\text{ to }8\text{ bytes}$ per reference) | High (~$24\text{ to }32\text{ bytes}$ per node overhead) |
| **Garbage Collector Overhead** | Zero during steady-state push/poll | Creates/destroys a `Node` object per operation |
| **`null` Element Support** | ❌ **Strictly Prohibited** (`NullPointerException`) | ✅ Allowed |
| **Concurrency** | Not thread-safe | Not thread-safe |

> [!TIP]
> JMH benchmarks demonstrate that `ArrayDeque` outperforms `LinkedList` by **$3\times\text{ to }10\times$** during iteration and by **$2\times\text{ to }5\times$** in high-throughput push/pop cycles. `LinkedList` should virtually never be chosen over `ArrayDeque` for queue or stack structures.

## 🔴 Senior Level

### 1. Circular Buffer Architecture & Power-of-Two Bitmask Wrapping

`ArrayDeque` implements a dynamic circular buffer using an internal array `Object[] elements` whose capacity is **always enforced as a power of two ($2^k$)**:

```java
// OpenJDK java.util.ArrayDeque implementation excerpt:
public void addFirst(E e) {
    if (e == null)
        throw new NullPointerException();
    // Decrement head counter counterclockwise and wrap using bitwise mask:
    elements[head = (head - 1) & (elements.length - 1)] = e;
    if (head == tail)
        grow(1); // Capacity exhausted -> double buffer size
}

public void addLast(E e) {
    if (e == null)
        throw new NullPointerException();
    elements[tail] = e;
    // Advance tail counter clockwise and wrap using bitwise mask:
    if ((tail = (tail + 1) & (elements.length - 1)) == head)
        grow(1);
}
```

#### Why Bitwise Masking Over Modulo Arithmetic?
In standard integer arithmetic, wrapping an index around an array of size $L$ requires the modulo operator: `index = (index + 1) % L`.
On modern x86/ARM CPU microarchitectures:
- Integer division (`idiv`) costs **10–25 CPU clock cycles** and cannot easily be vectorized.
- When $L = 2^k$, $X \pmod{2^k} \equiv X \ \& \ (2^k - 1)$.
- Bitwise `AND` (`&`) costs **1 CPU clock cycle** with a latency of $\approx 0.3-0.5\text{ ns}$.

```
Example with buffer capacity = 8 (Binary: length = 1000₂, mask = 0111₂ = 7):
Suppose head is at index 0. We invoke addFirst():
  (0 - 1) & 7:
  -1 in two's complement = ...11111111₂
  ...11111111₂ & 00000111₂ = 00000111₂ = 7!
The pointer wraps instantaneously from index 0 to index 7 in a single hardware instruction without branches or division.
```

When the buffer fills (`head == tail`), `grow()` allocates a new array of double the capacity ($2^{k+1}$) and uses `System.arraycopy` (vectorized `memmove` under AVX) to unroll the wrapped chunks into a continuous sequence starting at index 0.

### 2. Work-Stealing Scheduling in `ForkJoinPool`

Double-ended queues are the algorithmic foundation for the **Work-Stealing** pattern utilized by `ForkJoinPool`, parallel streams, and the carrier thread scheduler for Virtual Threads (Project Loom):

```
Worker Thread 1: [Local Task Deque]
  ├── Owner pushes/pops from HEAD (LIFO): push() / pop() (Hot L1/L2 cache)
  │
Worker Thread 2 (Idle "Thief" Thread):
  └── Steals tasks from peer's TAIL (FIFO): pollLast() (Cold task, minimal contention)
```

1. **Owner Access (LIFO at Head):** The owning thread pushes subtasks generated by recursive decomposition (`fork()`) and pops them from the head. Because the most recently created subtask operates on data currently resident in the processor's L1/L2 cache lines, LIFO execution maximizes cache warmth and eliminates DRAM bus traffic.
2. **Thief Access (FIFO at Tail):** When an idle worker exhausts its own deque, it attempts to steal work from the tail of another worker's deque. The task at the tail is the oldest (coarsest-grained) slice of computation, yielding the greatest amount of descendant work upon decompression.
3. **Contention Minimization:** Because the owner operates on the `head` and the thief operates on the `tail`, they rarely access the same memory address or acquire the same lock, reducing lock contention to near zero.

### 3. Java 21 `SequencedCollection` Integration (JEP 431)

Starting with Java 21, `Deque` extends `SequencedCollection`, formalizing first-and-last element access across the entire collection taxonomy:

```java
Deque<String> deque = new ArrayDeque<>(List.of("alpha", "beta", "gamma"));

// Standardized accessors:
String first = deque.getFirst(); // "alpha"
String last  = deque.getLast();  // "gamma"

// Zero-copy reverse view:
SequencedCollection<String> reversedView = deque.reversed();
// Mutating or iterating reversedView operates in reverse order in O(1) space:
reversedView.forEach(System.out::println); // Prints: gamma -> beta -> alpha
```

## 4 Tricky Questions

### 1. Why does `ArrayDeque` strictly prohibit `null` elements while `LinkedList` allows them?

**Answer:**
This is an intentional design choice enforced for API clarity and bug prevention. Methods such as `pollFirst()`, `pollLast()`, `peekFirst()`, and `peekLast()` use `null` as an unambiguous sentinel value signifying that the collection is empty.
If `ArrayDeque` permitted `null` elements:
- An invocation of `deque.poll()` returning `null` would be hopelessly ambiguous: did the operation successfully return an element whose value was `null`, or was the queue empty?
- To disambiguate, callers would be forced to execute a redundant `isEmpty()` check, introducing race conditions in concurrent wrappers and degrading performance.
`LinkedList` allows `null` only because it implemented `List` (from Java 1.2) before retrofitting `Deque` (in Java 6), preserving backwards compatibility at the cost of ambiguity.

---

### 2. What happens inside `ArrayDeque` when `head == tail`? How does it differentiate between an empty deque and a full deque?

**Answer:**
In `ArrayDeque`:
- When the collection is **empty**, `head == tail`.
- However, `ArrayDeque` is designed so that `head == tail` **immediately triggers a capacity doubling**.
Specifically, as soon as an element is inserted and the updated pointer causes `head == tail`, the internal method `grow()` (or `doubleCapacity()`) is invoked immediately *before* the method returns. Therefore, outside of resizing routines, `head == tail` **always and only** indicates an empty deque. Elements are never allowed to sit in a state where the array is 100% full with `head == tail`.

---

### 3. Why is `ArrayDeque` not considered thread-safe, and what should be used instead in high-concurrency environments?

**Answer:**
`ArrayDeque` provides zero synchronization: concurrent invocations of `addFirst()` and `pollLast()` without external synchronization result in data corruption, lost updates, and corrupted `head`/`tail` indices leading to `ArrayIndexOutOfBoundsException` or infinite loops during resizing.
Depending on the concurrency profile, use:
- **`ConcurrentLinkedDeque`:** A lock-free, unbounded double-ended queue based on Michael-Scott style non-blocking CAS (Compare-And-Swap) linked nodes.
- **`LinkedBlockingDeque`:** A bounded or unbounded blocking deque that uses a single reentrant lock with two condition variables (`notEmpty`, `notFull`) for producer-consumer pipelines.
- **`ForkJoinPool.WorkQueue`:** An internal lock-free deque specifically engineered for work-stealing with asymmetric single-producer, multi-consumer access.

---

### 4. What is the semantic and runtime difference between `deque.pop()` and `deque.poll()`?

**Answer:**
Both methods retrieve and remove the element at the head of the deque (representing the top of a stack in LIFO terminology):
- **`deque.pop()`** conforms to the classic stack contract: if the deque is empty, it throws a `NoSuchElementException`.
- **`deque.poll()`** conforms to the queue/special-value contract: if the deque is empty, it returns `null` gracefully without throwing an exception.
Under the hood, `ArrayDeque.pop()` is implemented as:
```java
public E pop() {
    return removeFirst(); // which throws NoSuchElementException if peekFirst() == null
}
```

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
> "`Deque` (Double-Ended Queue) is a linear collection supporting $O(1)$ insertions and removals at both ends, unifying the behavior of a FIFO queue and a LIFO stack. Its premier implementation is `ArrayDeque`, which operates on a continuous, power-of-two circular array buffer. By using bitwise AND masks `(index + 1) & (length - 1)` instead of modulo division, `ArrayDeque` achieves bare-metal efficiency. It avoids the heavy memory bloat (~32 bytes per node) and CPU cache misses of `LinkedList`, making it the industry standard for stacks and queues. In multi-threading, deques are essential for work-stealing algorithms (such as in `ForkJoinPool`), where owners push/pop from the head and thieves steal from the tail."

### High-Impact Architectural Facts
- **Memory Efficiency:** `ArrayDeque` uses a flat `Object[]` array (4 bytes per element reference under Compressed OOPs), whereas `LinkedList` allocates a 24–32 byte `Node` object on every single `add()`.
- **Instruction-Level Speed:** Modulo wrapping via `& (length - 1)` takes 1 CPU cycle ($\sim 0.3\text{ ns}$), compared to 10–25 cycles for `%` (`idiv`).
- **Null Prohibition:** `ArrayDeque` rejects `null` elements (`NullPointerException`) so that `poll()` returning `null` reliably denotes an empty deque.
- **Modern Standards:** `java.util.Stack` is deprecated in architectural practice; `Deque<T> stack = new ArrayDeque<>()` is the standard since Java 6.
- **Java 21 JEP 431:** `Deque` implements `SequencedCollection`, exposing `reversed()`, `getFirst()`, and `getLast()`.

### Common Pitfalls & Red Flags
- ❌ **Using `LinkedList` for stacks or queues:** Demonstrates unawareness of CPU cache line mechanics, node memory overhead, and pointer-chasing GC costs.
- ❌ **Passing `null` into `ArrayDeque`:** Immediately throws `NullPointerException`.
- ❌ **Assuming `ArrayDeque` is thread-safe:** It is completely unsynchronized; multi-threaded code requires `ConcurrentLinkedDeque` or `LinkedBlockingDeque`.
- ❌ **Using `java.util.Stack`:** Demonstrates legacy thinking; `Stack` extends `Vector`, incurs unnecessary lock synchronization overhead on every method, and exposes indexed insertions (`stack.add(1, item)`) which break LIFO guarantees.
