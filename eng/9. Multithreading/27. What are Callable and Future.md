# What are Callable and Future

---

## 🟢 Junior Level

### Short Interview Answer (30 Seconds)
**`Callable<V>`** and **`Future<V>`** are fundamental interfaces in the `java.util.concurrent` package, introduced in Java 5 to overcome the core limitations of classic `Runnable`:

1. **`Callable<V>`** represents an asynchronous task that, unlike `Runnable.run()`, **returns a typed result** of type `V` via its `V call()` method and can declare **checked exceptions** (`throws Exception`).
2. **`Future<V>`** acts as an asynchronous descriptor (a "promise" or receipt) for a running task. Through a `Future`, the calling thread can:
   - Check completion status (`isDone()`, `isCancelled()`);
   - Attempt task cancellation (`cancel()`);
   - Retrieve the computed result synchronously (`get()`) or with a timeout (`get(timeout, unit)`).

---

### Comparison Table: Runnable vs. Callable vs. Future vs. CompletableFuture

| Characteristic | `Runnable` | `Callable<V>` | `Future<V>` | `CompletableFuture<V>` |
|---|---|---|---|---|
| **Role** | Task with no result | Task returning a result | Result descriptor / handle | Reactive task pipeline |
| **Method Signature** | `void run()` | `V call() throws Exception` | Inspection methods (`get`, `cancel`) | 60+ functional composition methods |
| **Checked Exceptions** | ❌ Forbidden | ✅ Allowed (`throws Exception`) | Wrapped in `ExecutionException` | Wrapped in `CompletionException` |
| **Result Retrieval** | N/A | Returned by `call()` | Blocking `get()` call | Non-blocking callbacks (`thenApply`) |
| **Introduced In** | Java 1.0 | Java 5 | Java 5 | Java 8 |

---

### Compilable Java 21 Example

```java
import java.util.concurrent.*;

public class CallableAndFutureBasicsDemo {
    public static void main(String[] args) {
        // 1. Define a task that computes a value and can throw checked exceptions
        Callable<Integer> heavyCalculation = () -> {
            System.out.println("Computation started on thread: " + Thread.currentThread().getName());
            Thread.sleep(500); // Simulate compute or I/O latency
            return 42 * 2;
        };

        // 2. Submit to an ExecutorService
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            // submit() immediately returns a Future handle (non-blocking)
            Future<Integer> future = executor.submit(heavyCalculation);

            System.out.println("Task submitted. Completed immediately? " + future.isDone());

            try {
                // 3. Retrieve result with a safety timeout (Best Practice!)
                Integer result = future.get(2, TimeUnit.SECONDS);
                System.out.println("Result successfully computed: " + result);
            } catch (TimeoutException e) {
                System.err.println("Timeout elapsed! Cancelling task...");
                future.cancel(true); // Send interrupt signal
            } catch (ExecutionException e) {
                // If call() threw an exception, it is wrapped in getCause()
                System.err.println("Error inside task: " + e.getCause().getMessage());
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                System.err.println("Calling thread was interrupted while waiting");
            }
        }
    }
}
```

## 🟡 Middle Level

### `Future<V>` Interface Methods and Cancellation Semantics

The `Future` interface defines five core methods:

1. **`V get()`:** Blocks the calling thread until the task completes, returning the result or throwing an exception.
2. **`V get(long timeout, TimeUnit unit)`:** Blocks the calling thread for at most the specified duration, throwing `TimeoutException` if the task does not finish in time.
3. **`boolean isDone()`:** Returns `true` if the task completed (whether normally, exceptionally, or via cancellation).
4. **`boolean isCancelled()`:** Returns `true` if the task was cancelled prior to completing normally.
5. **`boolean cancel(boolean mayInterruptIfRunning)`:** Attempts to cancel execution of the task.

#### Cancellation Mechanics: `cancel(true)` vs. `cancel(false)`
- **`cancel(false)`:** If the task is still waiting in the executor queue, it is removed and will never execute. If a worker thread is already executing `call()`, execution is **not interrupted**, though its return value will be discarded.
- **`cancel(true)`:** If the task is currently executing, the JVM sends a **`Thread.interrupt()`** signal to the worker thread.
  > [!IMPORTANT]
  > The `interrupt()` signal does not forcibly terminate the thread. The task code must cooperatively inspect `Thread.currentThread().isInterrupted()` or invoke interruptible blocking methods (`sleep`, `read`), otherwise it will run to completion!

### Batch Operations: `invokeAll()` vs. `invokeAny()`

`ExecutorService` provides built-in methods for handling collections of `Callable` tasks:

```java
import java.util.List;
import java.util.concurrent.*;

public class BatchExecutionDemo {
    public static void main(String[] args) throws Exception {
        try (var executor = Executors.newFixedThreadPool(4)) {
            List<Callable<String>> tasks = List.of(
                () -> { Thread.sleep(200); return "Fast"; },
                () -> { Thread.sleep(500); return "Medium"; },
                () -> { Thread.sleep(800); return "Slow"; }
            );

            // 1. invokeAll: Blocks the caller until ALL tasks complete (or timeout expires)
            List<Future<String>> results = executor.invokeAll(tasks, 1, TimeUnit.SECONDS);
            for (Future<String> f : results) {
                if (!f.isCancelled()) {
                    System.out.println("Received: " + f.get());
                }
            }

            // 2. invokeAny: Returns result of the FIRST successfully completed task!
            // All other pending or running tasks are automatically cancelled via cancel(true)
            String fastest = executor.invokeAny(tasks);
            System.out.println("Fastest response: " + fastest);
        }
    }
}
```

### Exception Wrapping in `ExecutionException`

When `Callable.call()` throws an exception (checked or unchecked, such as `SQLException`), the calling thread cannot catch it directly because execution occurred on a separate thread.

`Future.get()` wraps the actual exception inside an **`ExecutionException`**:
```java
try {
    future.get();
} catch (ExecutionException e) {
    Throwable cause = e.getCause(); // Extract underlying root cause
    if (cause instanceof SQLException sqlEx) {
        log.error("Database query failed: {}", sqlEx.getSQLState());
    } else {
        log.error("Unexpected error", cause);
    }
}
```

## 🔴 Senior Level

### HotSpot Architecture: `FutureTask<V>` Under the Hood

When `executor.submit(callable)` is called, the task is wrapped in **`java.util.concurrent.FutureTask<V>`**, which implements both `Runnable` and `Future` (`RunnableFuture<V>`):

```
                        [ RunnableFuture<V> ]
                                 ▲
                     ┌───────────┴───────────┐
                     │                       │
               [ Runnable ]              [ Future<V> ]
```

#### `FutureTask` State Machine:
`FutureTask` manages synchronization via an atomic `volatile int state` field using low-level CAS (Compare-And-Swap) instructions without heavyweight `synchronized` locks:

```
           ┌──► COMPLETING ──► NORMAL (Result written to outcome)
           │
  NEW (0) ─┼──► COMPLETING ──► EXCEPTIONAL (Throwable written to outcome)
           │
           ├──► CANCELLED (Cancelled without interruption)
           │
           └──► INTERRUPTING ──► INTERRUPTED (Cancelled with Thread.interrupt())
```

- **`NEW = 0`:** Task created, not yet executed or finished;
- **`COMPLETING = 1`:** Transient state: computation finished, result is being written to `Object outcome`;
- **`NORMAL = 2`:** Task completed successfully; `outcome` holds the return value;
- **`EXCEPTIONAL = 3`:** Task completed exceptionally; `outcome` holds the `Throwable`;
- **`CANCELLED = 4`:** Cancelled via `cancel(false)`;
- **`INTERRUPTING = 5`:** Transient state during `cancel(true)` before interrupt signal is delivered;
- **`INTERRUPTED = 6`:** Worker thread interrupted.

---

### Wait Mechanism: The Treiber Stack (`WaitNode`)

When a thread calls `future.get()` while the task is still in state `NEW` or `COMPLETING`, it must wait:

1. `FutureTask` does not use `Object.wait()`. Instead, it maintains a lock-free **Treiber Stack** composed of `WaitNode` objects.
2. The calling thread allocates a `WaitNode`, pushes it atomically onto the head of the `waiters` stack via CAS, and parks using **`LockSupport.park(this)`**.
3. When the worker thread finishes task execution inside `FutureTask.run()`, it transitions `state` to `NORMAL` or `EXCEPTIONAL`, stores the result in `outcome`, and invokes `finishCompletion()`:
   - Pops each node from the `waiters` Treiber stack;
   - Calls **`LockSupport.unpark(node.thread)`** for each parked thread;
   - Unlinks nodes to facilitate garbage collection.

---

### Architectural Anti-Pattern: Synchronous `Future.get()` in Web Containers

A common design flaw is submitting asynchronous tasks to a background thread pool and immediately blocking on `future.get()` inside an HTTP servlet thread:

```java
// ❌ ANTI-PATTERN: Double thread reservation / resource starvation
public UserResponse handleRequest(Long id) {
    Future<User> f1 = pool.submit(() -> fetchUser(id));
    Future<Orders> f2 = pool.submit(() -> fetchOrders(id));

    // Tomcat servlet thread blocked on get(); two pool threads busy computing!
    return new UserResponse(f1.get(), f2.get());
}
```

#### Why This Causes Cascading Outages:
1. **Thread Multiplication:** Consumes 3 operating system threads instead of 1 (1 servlet thread + 2 pool worker threads).
2. **Pool Starvation:** Under high concurrency, servlet threads block waiting on `get()`, while the background pool's task queue overflows, resulting in thread starvation and widespread timeouts.

#### Modern Architectural Solutions:
1. **Java 8+:** Migrate to non-blocking pipelines via `CompletableFuture.thenCombine()`.
2. **Java 21+:** Migrate to **Virtual Threads** and **Structured Concurrency** (`StructuredTaskScope`), where blocking on `scope.join()` unmounts virtual threads without tying up physical OS platform threads.

## 🎯 Interview Cheat Sheet

### 1. 30-Second Elevator Pitch
`Callable<V>` is a functional interface representing a parameterized task ("what to execute") that returns a typed result `V` and can throw checked `Exception`s. `Future<V>` is the lifecycle descriptor ("result receipt") for tracking progress (`isDone`), cancelling execution (`cancel`), and blocking for the value (`get`). Under the hood, `FutureTask` uses an atomic volatile `state` machine with CAS operations and a lock-free Treiber stack of `WaitNode`s using `LockSupport.park()`. In modern Java architectures, blocking `Future.get()` is replaced with non-blocking `CompletableFuture` or Java 21 `StructuredTaskScope`.

### 2. 4 Tricky Questions with Deep Answers

#### Question 1: What happens inside `FutureTask.run()` if `Callable.call()` throws an uncaught exception?
**Answer:**
`FutureTask.run()` catches all exceptions (`catch (Throwable rx)`). It prevents the worker thread from crashing by storing the caught exception inside an internal field `Object outcome`. The task state transitions atomically via CAS from `NEW` to `COMPLETING`, then to `EXCEPTIONAL`. Next, `finishCompletion()` unparks all threads waiting on `get()`. When a thread calls `get()`, it checks `state`, observes `EXCEPTIONAL`, and throws an `ExecutionException` wrapping the stored root cause (`throw new ExecutionException((Throwable)outcome)`).

#### Question 2: What is the operational difference between `future.cancel(true)` and `future.cancel(false)`?
**Answer:**
Both methods transition the task to a cancelled state if it has not yet completed.
- If the task is still queued in the executor and has not started, both calls prevent it from starting.
- If the task is **actively running** on a worker thread:
  - `cancel(false)` does not interrupt the thread; the task runs to natural completion, but its computed result is discarded.
  - `cancel(true)` invokes `Thread.interrupt()` on the worker thread executing the task. If task code inspects the interrupt status or blocks on interruptible I/O or sleep, it aborts immediately with `InterruptedException`.

#### Question 3: Why does invoking `future.get()` on a completed task (`isDone() == true`) execute at the speed of a standard volatile read?
**Answer:**
In `FutureTask`, the `state` field is declared `volatile`. When `state >= NORMAL`, `get()` bypasses the creation of a `WaitNode` and the `LockSupport.park()` system call, directly invoking `report(s)`. Thanks to the Java Memory Model (JMM) Happens-Before guarantee established by the write to `volatile state` after writing `outcome`, the caller reads `outcome` directly from CPU cache in a handful of nanoseconds.

#### Question 4: How does `FutureTask` prevent a race condition between `cancel()` and concurrent completion in `run()`?
**Answer:**
Race conditions are eliminated via atomic CAS operations on `state`. Before storing a result, `run()` executes:
```java
UNSAFE.compareAndSwapInt(this, stateOffset, NEW, COMPLETING);
```
Concurrently, `cancel()` attempts a CAS transition from `NEW` to `CANCELLED` (or `INTERRUPTING`). Exactly one CAS operation can succeed:
- If `cancel()` succeeds first, `run()` fails its CAS and discards the computation without publishing results.
- If `run()` successfully transitions state to `COMPLETING`, `cancel()` fails its CAS and returns `false`, because the task has already passed the point of cancellation.

### 3. Common Pitfalls and Red Flags

❌ **"Calling `future.get()` without a timeout in production request handlers."**  
*Correction:* Unbounded `future.get()` will freeze caller threads indefinitely if the downstream task hangs. Always supply a timeout: `future.get(5, TimeUnit.SECONDS)`.

❌ **"Believing `future.cancel(true)` forcibly kills the thread."**  
*Correction:* `cancel(true)` only sets the thread's interrupt flag. If a task runs a `while(true)` loop without checking `isInterrupted()`, it will continue running and consuming CPU.

❌ **"Using `Callable<Void>` instead of `Runnable` for tasks that produce no return value."**  
*Correction:* This introduces unnecessary object allocations and requires explicit `return null;` statements. Use `Runnable` for tasks without return values.
