# What is Singleton

---

## 🟢 Junior Level

**Singleton** is a Creational design pattern that guarantees a class has **exactly one instance throughout the runtime lifecycle** of an application and provides a **global static access point** to that instance.

### Why It Is Needed
Certain system components must exist as a solitary, coordinated entity:
- A global application logging facility.
- A central configuration manager reading `application.properties`.
- A database connection pool or hardware driver interface (e.g., serial port spooler).

If multiple components instantiate their own separate copies, it leads to memory bloat, out-of-sync state, and severe resource contention.

**Simple Real-World Analogy:** The President of a country. A nation has only one active president at any given moment. Whenever any citizen asks *"Who is the President?"*, everyone receives a reference to the exact same individual, not a crowd of conflicting duplicates.

### Structural Anatomy of a Classic Singleton
1. **Private Constructor:** Prohibits direct instantiation via the `new` operator from external classes.
2. **Private Static Field:** Holds the sole instance of the class in heap memory.
3. **Public Static Factory Method (`getInstance()`):** Exposes the single access point returning the shared reference.

```java
public class ConfigurationManager {

    // 1. Static field holding the single instance
    private static final ConfigurationManager INSTANCE = new ConfigurationManager();

    // 2. Private constructor prohibits 'new ConfigurationManager()' from outside
    private ConfigurationManager() {
        System.out.println("Configuration properties loaded into memory.");
    }

    // 3. Global static accessor
    public static ConfigurationManager getInstance() {
        return INSTANCE;
    }

    public String getProperty(String key) {
        return "val_" + key;
    }
}

// Verification:
public class Main {
    public static void main(String[] args) {
        ConfigurationManager config1 = ConfigurationManager.getInstance();
        ConfigurationManager config2 = ConfigurationManager.getInstance();

        // References point to the exact same memory address in the heap
        System.out.println(config1 == config2); // true
    }
}
```

### Singleton vs. Static Utility Class

| Criterion | Singleton Pattern | Static Class (`Math`, `Collections`) |
| :--- | :--- | :--- |
| **Interface Implementation** | Can implement interfaces (`implements ConfigService`) | Cannot implement interfaces with static methods |
| **Lazy Loading** | Supports deferred initialization on demand | Initialized immediately when any member is touched |
| **Object Passing** | Can be passed as an argument (`process(Config c)`) | Cannot be passed as a reference (no object exists) |
| **Polymorphism & OOP** | True heap-allocated object supporting inheritance | Procedural function bag; zero OOP polymorphism |
| **Unit Testability** | Mockable via interface injection | Extremely difficult to mock without bytecode manipulation |

## 🟡 Middle Level

### Java Implementation Strategies

#### 1. Eager Initialization (Thread-Safe, Non-Lazy)
The instance is instantiated by the ClassLoader when the JVM loads the class:
```java
public class EagerSingleton {
    private static final EagerSingleton INSTANCE = new EagerSingleton();
    private EagerSingleton() {}
    public static EagerSingleton getInstance() { return INSTANCE; }
}
```
- **Pros:** Trivially simple; thread safety is guaranteed by the JVM ClassLoader.
- **Cons:** Created eagerly upon class loading even if the application never uses it, consuming memory.

---

#### 2. Naive Lazy Initialization (Thread-Unsafe Anti-Pattern)
```java
// ❌ CRITICAL ANTI-PATTERN in multithreaded environments!
public class UnsafeLazySingleton {
    private static UnsafeLazySingleton instance;
    private UnsafeLazySingleton() {}

    public static UnsafeLazySingleton getInstance() {
        if (instance == null) {
            instance = new UnsafeLazySingleton(); // Race condition!
        }
        return instance;
    }
}
```
- **The Bug:** If two threads evaluate `if (instance == null)` simultaneously, both create separate instances, breaking the singleton invariant.

---

#### 3. Synchronized Accessor (Thread-Safe, Severe Bottleneck)
```java
public class SynchronizedSingleton {
    private static SynchronizedSingleton instance;
    private SynchronizedSingleton() {}

    public static synchronized SynchronizedSingleton getInstance() {
        if (instance == null) {
            instance = new SynchronizedSingleton();
        }
        return instance;
    }
}
```
- **Pros:** Thread-safe and lazily initialized.
- **Cons:** Catastrophic performance penalty. Every single invocation acquires a monitor lock, even though synchronization is only needed during the very first call.

---

#### 4. Double-Checked Locking (DCL with `volatile`)
Synchronizes only during initial construction:
```java
public class DoubleCheckedSingleton {
    // volatile is MANDATORY to prevent CPU instruction reordering!
    private static volatile DoubleCheckedSingleton instance;

    private DoubleCheckedSingleton() {}

    public static DoubleCheckedSingleton getInstance() {
        DoubleCheckedSingleton local = instance; // Micro-optimization: single volatile read
        if (local == null) {
            synchronized (DoubleCheckedSingleton.class) {
                local = instance;
                if (local == null) {
                    instance = local = new DoubleCheckedSingleton();
                }
            }
        }
        return local;
    }
}
```

---

#### 5. Bill Pugh Singleton (Initialization-on-Demand Holder Idiom)
Provides lazy, lock-free thread safety using JVM ClassLoader mechanics:
```java
public class BillPughSingleton {
    private BillPughSingleton() {}

    // Nested static class is loaded into memory ONLY upon first access
    private static class Holder {
        private static final BillPughSingleton INSTANCE = new BillPughSingleton();
    }

    public static BillPughSingleton getInstance() {
        return Holder.INSTANCE;
    }
}
```
- **Mechanics:** When `BillPughSingleton` is loaded, `Holder` remains unloaded. Only when `getInstance()` is called does the JVM load and initialize `Holder`. Class initialization is guaranteed atomic and thread-safe by the Java Language Specification (JLS §12.4.2).

---

#### 6. Enum Singleton (Joshua Bloch's Gold Standard)
```java
public enum EnumSingleton {
    INSTANCE;

    public void doBusinessLogic() {
        System.out.println("Processing business logic safely.");
    }
}
```
- **Pros:** Guaranteed 100% immune to Reflection attacks, Serialization duplicates, and ClassLoader bugs.

---

### Vectors of Attack and How to Defend Against Them

| Attack Vector | How It Breaks the Singleton | Defense Strategy |
| :--- | :--- | :--- |
| **Reflection API** | `constructor.setAccessible(true)` invokes private constructors to create a 2nd instance. | Throw an `IllegalStateException` on second invocation, or use `enum`. |
| **Serialization** | `readObject()` deserializes a brand-new instance in memory without invoking constructors. | Implement `protected Object readResolve() { return getInstance(); }` or use `enum`. |
| **Cloning** | If the class implements `Cloneable`, `super.clone()` duplicates the heap object. | Override `clone()` and throw `CloneNotSupportedException`. |
| **Multiple ClassLoaders** | Independent ClassLoaders (e.g., in Tomcat or OSGi) load the class in separate namespaces. | Use an `enum` or root parent ClassLoader. |

```java
// Hardened Singleton with Reflection and Serialization defenses:
public class RobustSingleton implements Serializable {
    private static final long serialVersionUID = 1L;
    private static volatile RobustSingleton instance;

    private RobustSingleton() {
        if (instance != null) {
            throw new IllegalStateException("Singleton instance already exists! Reflection forbidden.");
        }
    }

    public static RobustSingleton getInstance() {
        // DCL logic...
        return instance;
    }

    // JVM hook: substitutes the deserialized object with the canonical instance
    protected Object readResolve() {
        return getInstance();
    }
}
```

## 🔴 Senior Level

### Double-Checked Locking Internals and the Java Memory Model (JMM)

Why is the `volatile` modifier **strictly mandatory** in Double-Checked Locking?

In bytecode, `instance = new DoubleCheckedSingleton()` is **not an atomic operation**. It decomposes into three distinct steps:
1. **`allocate`:** Allocate memory space on the heap for the new object.
2. **`invokespecial <init>`:** Execute the constructor to initialize object fields.
3. **`putstatic`:** Assign the resulting memory address to the `instance` reference.

```
Without volatile (Speculative Instruction Reordering):
Step 1: Memory allocated at address 0xDEADBEEF
Step 3: instance = 0xDEADBEEF  <-- REORDERED! Reference is now NON-NULL!
Step 2: Constructor initializes fields... <-- Has NOT finished yet!

Thread 2 enters getInstance():
-> Evaluates (instance != null) as TRUE!
-> Returns reference 0xDEADBEEF immediately!
-> Thread 2 reads a PARTIALLY INITIALIZED OBJECT!
-> Results in NullPointerExceptions, garbage values, or data corruption!
```

**The Role of `volatile`:**
Under the JMM (JSR-133), a write to a `volatile` variable establishes a **happens-before** relationship before any subsequent read. The compiler and CPU emit a hardware **Memory Barrier (Fence)**, strictly forbidding Step 3 from being reordered before Step 2.

#### Why Use the Local Variable (`DoubleCheckedSingleton local = instance`)?
Reading a `volatile` variable requires accessing L1/L2/L3 CPU cache with memory fence validation, which is slower than reading a CPU register. Reading into a local variable ensures that once initialized (99.999% of requests), the `volatile` field is accessed **only once**, yielding a measurable throughput boost in hot loops.

### Singleton as an Architectural Anti-Pattern

In modern clean architecture, the classic GoF Singleton is widely regarded as a design smell:

1. **Violates Single Responsibility Principle (SRP):** The class manages both its primary business domain and its own instantiation lifecycle and concurrency.
2. **Hidden Dependencies & DIP Violation:** A method calling `DatabasePool.getInstance()` conceals its dependencies. The class constructor lies about what resources it requires.
3. **Unit Testing Destroyer:**
   - Static methods cannot be substituted with standard mock objects (`Mockito.mock()`).
   - Introduces mutable global state. Test $A$ mutates the singleton state, causing an independent Test $B$ to fail intermittently (**State Bleeding**).
4. **Metaspace Memory Leaks:** In container environments (Tomcat, WildFly), if a singleton loaded by a parent ClassLoader retains references to a web app's classes, the `WebappClassLoader` cannot be garbage-collected during redeployment, causing `java.lang.OutOfMemoryError: Metaspace`.

### Singleton in Distributed Microservice Architectures

In cloud-native systems, "one instance per application" loses physical meaning:

```
                     [Load Balancer / Ingress]
                                 │
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
  ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
  │ Pod 1 (JVM)  │        │ Pod 2 (JVM)  │        │ Pod 3 (JVM)  │
  │  Singleton   │        │  Singleton   │        │  Singleton   │
  └──────────────┘        └──────────────┘        └──────────────┘
         │                       │                       │
         └───────────────────────┼───────────────────────┘
                                 ▼
           [Distributed Coordinator: Redis / ZooKeeper]
```

- When an application scales to 5 Kubernetes pods, there exist **5 independent Singleton instances**.
- For cluster-wide coordination (e.g., executing a scheduled batch job once daily), a Java Singleton is useless. Architects employ **Distributed Locks**:
  - **ShedLock** for periodic scheduled tasks.
  - **Redlock (Redis)** or **ZooKeeper Leader Election** for cluster-wide single-worker coordination.

## 4 Tricky Questions

### 1. Why does Double-Checked Locking fail on multi-core processors without the `volatile` keyword?
**Answer:**  
Due to CPU and compiler instruction reordering. Creating an object involves: 1) memory allocation, 2) constructor execution, and 3) assigning the reference. Without `volatile`, the CPU may reorder step 3 before step 2. A concurrent thread calling `getInstance()` will see that `instance` is not null and immediately return the reference before the constructor finishes, leading to operations on a **partially initialized object**.

### 2. How does an Enum Singleton natively prevent duplicate instances from being created via the Reflection API?
**Answer:**  
The defense is hardcoded into the JVM specification and the implementation of `java.lang.reflect.Constructor.newInstance()`. When `newInstance()` is invoked, it explicitly inspects whether the target class has the `ENUM` modifier. If it is an enum, it throws an unconditional exception:
```java
if ((clazz.getModifiers() & Modifier.ENUM) != 0)
    throw new IllegalArgumentException("Cannot reflectively create enum objects");
```
Reflection cannot bypass this JVM runtime check.

### 3. What happens when a standard Singleton object is deserialized, and how does `readResolve()` fix it?
**Answer:**  
The Java serialization mechanism bypasses normal constructors and creates a brand-new object in the heap via `ObjectInputStream.readObject()`, producing a duplicate instance that breaks the singleton invariant (`deserialized != original`).  
To fix this, the class must declare:
```java
protected Object readResolve() {
    return getInstance();
}
```
During deserialization, the JVM detects `readResolve()` and replaces the newly constructed object with the existing singleton instance.

### 4. How does a classic GoF Singleton fundamentally differ from a Singleton Bean in the Spring Framework?
**Answer:**  
- **GoF Singleton:** Enforces exclusivity via language constructs (`private` constructor and static `getInstance()`). It binds client code statically, is scoped per `ClassLoader`, and cannot be easily mocked in tests.
- **Spring Singleton Bean:** Enforces exclusivity via the **Inversion of Control (IoC) container**. The class remains a standard POJO with a public constructor. Exclusivity is scoped to the **`ApplicationContext`**, enabling seamless dependency injection, interface abstraction, and mock substitution in unit tests.

## 🎯 Interview Cheat Sheet

### Core Concepts (First 30 Seconds)
- **Definition:** Ensures exactly one instance of a class exists within a JVM/ClassLoader and provides a global access point.
- **Best Implementations:**
  - **Bill Pugh Singleton (Holder Class):** Cleanest lazy initialization without synchronization overhead.
  - **Enum Singleton:** Most robust defense against Reflection and Serialization attacks.
  - **Spring Dependency Injection:** Production standard in modern enterprise architectures.
- **DCL Rule:** Double-Checked Locking **must** declare the instance field as `volatile` to prevent instruction reordering bugs.
- **Anti-Pattern Consensus:** Classic static Singletons introduce hidden global state and ruin unit testing; prefer IoC container management.

### Key Architectural Gotchas
- **Distributed Reality:** A Java Singleton is local to one ClassLoader in one JVM; 10 microservice replicas have 10 singletons. Use Distributed Locks (Redis/ZooKeeper) for cluster-wide uniqueness.
- **Attacks:** Classic singletons can be broken by Reflection (`setAccessible(true)`), Serialization (`readObject()`), and multiple ClassLoaders.
- **Volatile Local Variable:** `DoubleCheckedSingleton local = instance;` avoids repeated volatile memory fence reads.

### Red Flags (What NOT to Say)
- ❌ *"A Java Singleton guarantees a single instance across my entire Kubernetes cluster."* (It is strictly local to a single ClassLoader).
- ❌ *"Double-Checked Locking works without volatile on modern Java."* (CPU reordering still causes partially initialized object leaks).
- ❌ *"I write manual Singletons inside Spring Boot microservices."* (Defeats Dependency Injection and testability; use standard Spring `@Service`).
