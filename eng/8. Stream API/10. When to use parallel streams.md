# When to use parallel streams

---

## 🟢 Junior Level

### 30-Second Summary
You should use **`parallelStream()`** **ONLY** when all three of the following preconditions are simultaneously satisfied:

1. **Large Data Volume ($N$):** The source collection contains thousands, tens of thousands, or millions of elements.
2. **Heavy CPU-Bound Computation ($Q$):** The per-element operations involve computationally intensive work (e.g., cryptography, hashing, complex mathematical calculations, image/audio processing, or parsing).
3. **Pure, Independent Operations:** Transformations are completely stateless, thread-safe, and free of side-effects (no mutation of shared variables, no shared locks, and no dependency on thread-local context).

If any of these conditions are missing, parallel streams should **not** be used. In particular, parallel streams must **never be used for I/O-bound tasks** (HTTP client calls, database queries, disk operations), as blocking operations exhaust the JVM-wide `ForkJoinPool.commonPool()`.

---

### Basic Java 21 Examples

```java
import java.math.BigInteger;
import java.util.List;
import java.util.stream.LongStream;

public class WhenToUseParallelDemo {

    public static void main(String[] args) {
        // ✅ EXCELLENT USE CASE: Heavy CPU computation, array-backed range, pure function
        List<BigInteger> heavyPrimes = LongStream.rangeClosed(1_000_000, 1_100_000)
            .parallel()
            .mapToObj(BigInteger::valueOf)
            .filter(n -> n.isProbablePrime(50))
            .toList();

        System.out.println("Discovered primes count: " + heavyPrimes.size());

        // ❌ ANTI-PATTERN: Trivial operation on a small collection
        List<String> words = List.of("apple", "banana", "cherry");
        List<String> upper = words.parallelStream() // Fork/Join thread setup is 10x slower than the actual work!
            .map(String::toUpperCase)
            .toList();
    }
}
```

## 🟡 Middle Level

### The $N \times Q > 10,000$ Decision Heuristic (Brian Goetz Model)

The empirical rule of thumb formulated by Brian Goetz (Java Language Architect) dictates that parallelizing a stream yields a net speedup only when:

$$N \times Q > 10{,}000$$

- **$N$**: Total count of elements in the source collection.
- **$Q$**: Estimated number of CPU clock cycles/instructions required to process each element.

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Scenario Evaluation                                    │ Practical Guidance                                     │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ $N = 100$, Trivial Math ($Q \approx 5$ cycles)         │ ❌ Avoid: $N \times Q = 500 \ll 10,000$ (5x slower)     │
  │ $N = 100,000$, Trivial Math ($Q \approx 5$ cycles)     │ 🟡 Marginal: $N \times Q = 500,000$ (Modest speedup)    │
  │ $N = 500$, Heavy Cryptography ($Q \approx 5,000$ cycles)│ 🟢 Parallelize: $N \times Q = 2,500,000 \gg 10,000$    │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

---

### Data Source Splitting and Pipeline Operation Analysis

#### 1. Splitting Efficiency of Data Sources:
- **Optimal ($O(1)$ Direct Partitioning):** `int[]`, `long[]`, `ArrayList`, `IntStream.rangeClosed()`. They have exact known sizes (`SIZED`), exhibit contiguous memory layouts, and split instantly into halves by index without pointer chasing.
- **Moderate ($O(1)$ Amortized / $O(\log N)$):** `HashSet`, `TreeSet`. Partitioning across hash buckets or balanced red-black trees requires extra coordination.
- **Degraded ($O(N)$ Linear Traversal):** `LinkedList`, `Stream.iterate()`. Splitting a linked list requires traversing $N/2$ pointers linearly just to locate the midpoint, destroying multi-threaded efficiency.

#### 2. Pipeline Operation Characteristics:
- **Stateless Operations (`filter`, `map`, `flatMap`):** Scale near-linearly with available CPU cores because worker threads process their assigned chunks completely independently.
- **Stateful Operations (`sorted`, `distinct`, `limit`, `skip`):** Introduce global synchronization barriers. For example, `sorted()` in a parallel stream must collect and buffer all elements from all threads before initiating a parallel merge sort, stalling pipeline streaming.

## 🔴 Senior Level

### Server-Side Concurrency Architecture

In enterprise server architectures (e.g., Spring Boot, Quarkus), concurrency is already managed at the application layer:

```
Incoming Web Requests (Tomcat Worker Threads)
Request 1  ───> Thread 1 ──┐
Request 2  ───> Thread 2 ──┼──> Invokes parallelStream() inside request handler
Request 3  ───> Thread 3 ──┘           │
                                       ▼
                       ForkJoinPool.commonPool() (CPU Cores - 1)
                       [Worker 1] [Worker 2] [Worker 3] (Saturated / Exhausted)
                       ───> Thread Starvation, CPU Cache Thrashing, Latency Spikes!
```

1. **High-Concurrency Servers:** When an application is already concurrently servicing hundreds of client HTTP requests, launching a `parallelStream()` inside an individual request handler spawns subtasks that compete for the shared `commonPool()`. This causes severe thread starvation, CPU context-switching overhead, and increased tail latency across all requests.
2. **Dedicated Batch / ETL Pipelines:** In standalone batch jobs (e.g., Spring Batch, background CLI processing) where a single process has exclusive ownership of the hardware, `parallelStream()` provides an effortless, high-throughput mechanism to saturate all physical cores.

### Hardware Architecture: Memory Locality and False Sharing

Parallel performance on modern multi-core CPUs is heavily governed by cache coherence:
1. **Cache Misses & Heap Fragmentation:** In collections of boxed reference objects (`List<Integer>`, `List<Record>`), objects are scattered non-contiguously across the heap. Each core repeatedly misses L1/L2 caches, stalling while fetching references from high-latency main memory (DRAM).
2. **False Sharing:** When worker threads concurrently write intermediate reduction values into adjacent memory locations within the same 64-byte CPU cache line, the CPU's hardware cache coherence protocol (MESI) repeatedly invalidates cache lines across cores, causing dramatic slowdowns.
3. **Hardware Prefetcher Superiority:** A simple sequential `for` loop over a primitive array (`int[]` or `long[]`) allows the CPU's hardware prefetcher to stream data directly into L1 cache, frequently outperforming a `parallelStream()` operating on a boxed object collection.

> [!IMPORTANT]
> **JMH Verification Invariant:** Never adopt parallel streams in production without benchmarking under realistic production loads using **JMH (Java Microbenchmark Harness)**. Compilers (JIT C2) apply loop unrolling and SIMD vectorization differently between sequential and parallel bytecodes.

## 4 Tricky Questions

### 1. Why does adding `.parallel()` to request processing inside a Spring Boot controller frequently cause a massive drop in overall server throughput?
**Answer:**
A web server like Tomcat or Undertow already achieves optimal hardware utilization by assigning an independent worker thread to each incoming HTTP request. When multiple concurrent requests simultaneously execute `.parallel()`, each request floods the JVM's single shared `ForkJoinPool.commonPool()` with dozens of subtasks.

This creates severe CPU core contention, excessive context switching, and cache-line invalidation. Furthermore, if the parallel stream blocks or takes too long, worker threads in `commonPool()` are starved, causing subsequent requests across the entire JVM to stall in queue waiting for threads, resulting in skyrocketing p99 latency and degraded throughput.

---

### 2. How do CPU hardware caches (L1/L2/L3) and the hardware prefetcher impact the choice between `parallelStream()` and a sequential primitive loop?
**Answer:**
A sequential loop iterating over a contiguous primitive array (`int[]` or `long[]`) accesses adjacent memory addresses. The CPU's hardware prefetcher recognizes this linear access pattern and pre-loads cache lines into ultra-fast L1/L2 caches before the CPU instructions even execute, enabling vectorization (SIMD) and zero-wait memory access.

In contrast, a parallel stream divides data into separate chunks for different cores. If the data consists of boxed objects (`List<Integer>`), each reference points to a random heap location, triggering constant L1/L2 cache misses. The cost of repeatedly waiting for main memory (DRAM) and coordinating thread queues in `ForkJoinPool` easily outweighs the benefits of multi-core parallelism.

---

### 3. Under what conditions can an operation like `parallelStream().sorted()` trigger an `OutOfMemoryError` on large datasets that fit comfortably in memory sequentially?
**Answer:**
`sorted()` is a stateful barrier operation that cannot stream elements incrementally; it must consume the entire stream before emitting the first sorted element.

In a sequential stream, sorting can often occur in-place on the underlying array or within a single buffer. In a parallel stream, however, each worker thread accumulates chunks into dynamic thread-local buffers (`SpinedBuffer`). Once accumulated, the runtime performs a parallel merge sort (`Arrays.parallelSort`), which allocates auxiliary temporary arrays equal in size to the dataset to merge partitions. For datasets consuming 50% or more of available heap, this dual buffering pushes the JVM past its memory limit, triggering an `OutOfMemoryError`.

---

### 4. Why does a parallel stream over an `ArrayList<Integer>` with $N = 100,000$ frequently lose to a simple sequential loop over a primitive `int[]`?
**Answer:**
1. **Unboxing Penalty:** `ArrayList<Integer>` stores references. Iterating requires reading a 64-bit object pointer, dereferencing the address, reading the 24-byte object header, and extracting the primitive `int` value, churning CPU cycles and stalling on heap memory latency.
2. **Coordination Overhead:** For $N = 100,000$ trivial additions ($Q \approx 1\text{ cycle}$), total computation is roughly $100,000$ cycles—far below the coordination threshold where `ForkJoinPool` overhead (splitting, queue management, thread synchronization) pays off.
3. **Vectorization:** The JIT C2 compiler can vectorize a sequential loop over `int[]` using CPU SIMD instructions (AVX-512 / AVX2), processing 8 to 16 integers per clock cycle in a single core, running orders of magnitude faster than a multi-threaded boxed collection.

### Key Takeaways
- **The $N \times Q > 10,000$ Rule:** Only parallelize when data volume multiplied by computational complexity is substantial.
- **Never for I/O:** Parallel streams are exclusively designed for CPU-bound computations; blocking I/O paralyzes `ForkJoinPool.commonPool()`.
- **Memory Matters:** Primitive arrays and `ArrayList` split instantly ($O(1)$); linked nodes and streams with sequential dependencies (`Stream.iterate`) fail to scale.
- **Java 21 Separation of Concerns:** Use `parallelStream()` for large CPU calculations, Virtual Threads for blocking I/O, and `CompletableFuture` for asynchronous composition.

---

### Red Flags & Anti-Patterns to Avoid
- ❌ **Using `parallelStream()` for database or network calls:** Causes cascading failures across the entire microservice.
- ❌ **Enabling `.parallel()` indiscriminately without JMH benchmarking:** Small collections and simple operations run significantly slower in parallel.
- ❌ **Parallelizing `LinkedList` or `Stream.iterate()`:** Linear pointer traversal destroys multi-core gains.
- ❌ **Using `findFirst()` instead of `findAny()` in parallel:** `findFirst()` forces cross-thread synchronization to preserve encounter order, whereas `findAny()` completes immediately upon the first worker match.
