# В чому перевага незмінних об'єктів для кешування

---

## 🟢 Junior Level

### 30-секундна відповідь
Незмінні (ім'ютабельні) об'єкти є **золотим стандартом для кешування** як у локальній пам'яті застосунку (`ConcurrentHashMap`, `Caffeine Cache`), так і в розподілених сховищах (`Redis`, `Memcached`).

Головні переваги:
1. **Безпечний спільний доступ (Safe Sharing):** один і той самий об'єкт у пам'яті може безпечно читатися тисячами паралельних потоків без блокувань, м'ютексів та ключового слова `synchronized`.
2. **Захист від «отруєння кешу» (No Cache Poisoning):** код, що викликає метод, фізично не може змінити поля отриманого з кешу об'єкта і тим самим непомітно спотворити дані для інших користувачів.
3. **Нульовий оверхед по пам'яті (Zero-Allocation):** кеш повертає пряме посилання на наявний об'єкт за $O(1)$. Немає потреби робити дорогі захисні копії (*Defensive Copies*).
4. **Стабільність ключів:** хеш-код і метод `equals()` незмінні в часі, що виключає втрату елементів у бакетах асоціативних масивів.

---

### Наочна аналогія з життя
Уявіть видачу книг у публічній бібліотеці:
- **Незмінний об'єкт (Друкована книга):** бібліотекар видає один і той самий друкований примірник десяткам читачів по черзі. Ніхто не може стерти друкарську фарбу або дописати свій текст. Книга залишається чистою для всіх наступних читачів.
- **Змінний об'єкт (Спільний аркуш паперу з олівцем):** перший же читач може закреслити абзац або вписати неправдиві дані, **отруївши (зіпсувавши)** інформацію для всіх наступних відвідувачів.

---

### Наочний приклад: Локальний кеш
```java
// Незмінний клас (Record)
public record UserProfile(String userId, String username, List<String> permissions) {
    public UserProfile {
        permissions = List.copyOf(permissions); // Захисна копія в конструкторі
    }
}

// In-Memory кеш
public class UserService {
    private final Map<String, UserProfile> userCache = new ConcurrentHashMap<>();

    public UserProfile getUser(String id) {
        // Потоки безпечно отримують пряме посилання з кешу!
        return userCache.computeIfAbsent(id, this::loadFromDatabase);
    }

    private UserProfile loadFromDatabase(String id) {
        return new UserProfile(id, "alex_dev", List.of("READ", "WRITE"));
    }
}
```

## 🟡 Middle Level

### 1. Запобігання катастрофі «Отруєння кешу» (Cache Poisoning)
Якщо кешувати змінний об'єкт, будь-яка ненавмисна модифікація в бізнес-логіці ламає кеш для всієї системи:

```java
// ❌ КАТАСТРОФА ЗІ ЗМІННИМ ОБ'ЄКТОМ:
MutableUser user = cache.get("user_42");

// Розробник в одному з методів вирішив тимчасово заблокувати користувача для локального розрахунку:
user.setBlocked(true); 

// 💥 КЕШ ОТРУЄНО:
// Тепер усі інші 10 000 користувачів і потоків бачать, що user_42 заблокований!
```
Для незмінних об'єктів (`record UserProfile`) виклик сетера неможливий: компілятор унеможливлює саму можливість отруєння кешу ще на етапі збирання проєкту.

---

### 2. Усунення накладних витрат на Defensive Copying
Якщо в кеші лежать змінні об'єкти, розробник заради безпеки **зобов'язаний робити глибоку копію (Deep Copy) на кожен виклик `get()`**:
- 1000 запитів на секунду = 1000 повних алокацій графа об'єктів у Eden.
- Результат: колосальний *GC Churn*, часті паузи збирача сміття та зростання latency сервісу.
- **З незмінними об'єктами:** `cache.get(key)` просто повертає готове 64-бітне посилання. Час виконання — **$O(1)$**, витрата пам'яті — **$0$ байтів** алокацій.

---

### 3. Патерн Flyweight у стандартній бібліотеці Java (JDK)
Незмінність лежить в основі всіх вбудованих кешів віртуальної машини HotSpot:
- **`IntegerCache`:** кешує екземпляри `Integer` від `-128` до `127` (метод `Integer.valueOf(int)` повертає готові незмінні посилання).
- **`String Constant Pool`:** розділяє літерали між усіма потоками.
- **Константи:** `BigDecimal.ZERO`, `BigInteger.ONE`, `Boolean.TRUE`, `Boolean.FALSE`, `Duration.ZERO`.

## 🔴 Senior Level

### Вплив на Garbage Collector: Card Table та відсутність Dirty Cards
Закешовані дані за своєю природою довговічні: переживши кілька малих збирань сміття, вони просуваються в старше покоління (**Old Generation / Tenured**):
1. У поколіннєвих GC (G1, Parallel, Serial) посилання з об'єктів Old Gen на об'єкти Young Gen відстежуються через спеціальну структуру в оперативній пам'яті — **Card Table** (масив байтів, де 1 байт відповідає 512 байтам купи).
2. **Проблема змінних кешів:** Коли змінний об'єкт в Old Gen оновлює своє поле новим посиланням на тимчасовий об'єкт із Young Gen, процесор зобов'язаний виконати **Post-Write Barrier**: позначити картку в Card Table як «брудну» (*dirty card*). Під час кожного *Minor GC* збирач змушений сканувати всі брудні картки, що **істотно подовжує паузи Stop-the-World (STW)**.
3. **Перевага незмінного кешу:** Незмінний об'єкт в Old Gen **ніколи не перезаписує свої посилання**. Таблиця Card Table залишається чистою, а паузи *Young Collection* скорочуються до абсолютного мінімуму.

---

### Апаратна когерентність процесорних кешів (MESI та NUMA)
У сучасних багатосокетних серверах з архітектурою NUMA (Non-Uniform Memory Access):
- При паралельному читанні незмінного об'єкта рядки кешу L1/L2/L3 на всіх процесорних ядрах переходять у стан **Shared (S)** протоколу **MESI**.
- Жодне ядро не розсилає широкомовних сигналів інвалідації **RFO (Request For Ownership)** по міжпроцесорній шині (UPI / Infinity Fabric).
- Виключається деградація продуктивності через **Cache Bouncing** та хибне розділення кеш-ліній (**False Sharing**), забезпечуючи лінійне зростання RPS при збільшенні ядер CPU від 8 до 128.

---

### Детермінована серіалізація в розподілені кеші (Redis)
При вивантаженні об'єктів у розподілений кеш (Redis / Hazelcast / Kafka):
- Серіалізація змінного графа об'єктів паралельним потоком часто призводить до винятку `ConcurrentModificationException` просто посеред генерації JSON/Protobuf, якщо інший потік викликав `list.add()`.
- Незмінні об'єкти являють собою суворий **незмінний знімок стану (Snapshot)**, гарантуючи цілісність та 100% повторюваність серіалізації без блокувань транзакцій.

## 4 Tricky Questions

### 1. Чому кешування змінних об'єктів із захисним копіюванням (Defensive Copy) у high-throughput сервісах може звести нанівець усю користь від кешу?
**Відповідь:**
Сенс кешу — економити CPU та знижувати затримки. 
Якщо об'єкт змінний, то для запобігання Cache Poisoning кеш зобов'язаний при кожному виклику `get()` створювати глибоку копію (*Deep Copy*). 
Якщо об'єкт складний (наприклад, дерево із сотень підпорядкованих сутностей), то рекурсивне створення копії в оперативній пам'яті:
1. Займає більше процесорного часу, ніж виконання швидкого індексного запиту в локальну БД або читання з Redis.
2. Генерує гігантський обсяг короткоживучого сміття в Eden (сотні мегабайтів на секунду), викликаючи часті паузи GC (Stop-The-World) та деградацію 99-го перцентиля затримки (p99 latency). 
Перехід на незмінні структури даних повертає вартість `cache.get()` до чистих наносекунд без алокацій.

---

### 2. Як використання незмінного об'єкта як ключа кешу запобігає прихованим витокам пам'яті (Memory Leaks) у `ConcurrentHashMap`?
**Відповідь:**
Якщо ключ кешу змінний і змінив свій внутрішній стан після додавання в мапу:
- Його `hashCode()` змінився.
- При наступних викликах `cache.remove(key)` або `cache.get(key)` хеш-код перераховується заново. Мапа починає шукати елемент у зовсім іншій корзині (*bucket*).
- Метод `remove()` не знаходить елемент і повертає `null`.
- Старий об'єкт залишається в початковому бакеті назавжди. При регулярному оновленні таких ключів мапа безкінечно розростається, що призводить до повільного витоку пам'яті та неминучого падіння з `OutOfMemoryError: Java heap space`. Незмінні ключі гарантують стабільність `hashCode()` протягом усього життя JVM.

---

### 3. Як довгоживучі незмінні об'єкти в Tenured (Old) поколінні допомагають оптимізувати фазу сканування Card Table під час збирання сміття?
**Відповідь:**
Поколіннєві збирачі сміття (G1, Parallel) використовують бар'єри запису (*Write Barriers*): щоразу, коли поле посилального типу в Old Gen перезаписується посиланням на об'єкт у Young Gen, відповідний 512-байтний блок пам'яті в **Card Table** позначається прапорцем `dirty` (байт виставляється в 0). 
Під час малих збирань сміття (*Minor GC*) збирач зобов'язаний просканувати всі «брудні» картки в пошуках посилань на вижилі молоді об'єкти. 
Оскільки поля незмінного об'єкта ініціалізуються один раз у конструкторі й більше ніколи не переписуються, об'єкти кешу в Old Gen **генерують рівно нуль бар'єрів запису і ніколи не забруднюють Card Table**, радикально скорочуючи час фази *Young Collection STW*.

---

### 4. Як протокол когерентності кешів MESI поводиться при читанні незмінного кешу сотнею потоків на сервері з кількома процесорами (NUMA)?
**Відповідь:**
У протоколі MESI рядок процесорного кешу з даними незмінного об'єкта переходить у стан **Shared (S)** у локальних L1/L2 кешах усіх процесорних ядер усіх сокетів. 
Оскільки жодне ядро не здійснює запис:
- Процесорні ядра читають дані зі швидкістю L1-кешу (близько 1 наносекунди) без звернень до спільної оперативної пам'яті.
- Міжпроцесорна шина (NUMA interconnect) повністю вільна від широкомовного трафіку інвалідації (сигналів *Invalidate* та запитів *Request For Ownership*). 
Якби кеш мутував, будь-який запис переводив би кеш-лінію в стан **Modified (M)**, інвалідуючи кеші на всіх інших ядрах і викликаючи катастрофічний простій ядер в очікуванні пересилання даних по міжсокетній шині (**Cache Bouncing**).

## 🎯 Шпаргалка для інтерв'ю

### Топ-5 переваг незмінності для кешування
1. **Thread-Safe Read:** вільне паралельне читання без синхронізації та блокувань.
2. **Абсолютний захист від Cache Poisoning:** ніхто не може зіпсувати стан спільного об'єкта.
3. **Zero-Copy / Zero-Allocation:** повернення посилання за $O(1)$ без захисного копіювання.
4. **Стабільний `hashCode`:** ключі кешу ніколи не губляться в бакетах `ConcurrentHashMap`.
5. **Оптимізація GC:** відсутність dirty cards у Card Table знижує паузи Stop-the-World.

### Антипатерни при кешуванні
- ❌ **Змінний об'єкт у кеші:** ризик отруєння кешу та псування даних у всій системі.
- ❌ **Копіювання незмінного об'єкта при читанні з кешу:** безглузда витрата CPU та пам'яті.
- ❌ **Змінний ключ кешу:** гарантований витік пам'яті (*Memory Leak*) у `Map`.

### Червоні прапорці на співбесіді (Чого говорити не можна)
- ❌ *«З ConcurrentHashMap завжди потрібно повертати копію об'єкта, навіть якщо це Record»* — Record незмінний, копіювання не потрібне.
- ❌ *«Для безпечного читання з кешу потрібно огортати cache.get() у synchronized»* — незмінні об'єкти читаються lock-free.
- ❌ *«Змінні ключі в кеші допустимі, якщо перевизначити тільки equals()»* — зміна хеш-коду загубить об'єкт у бакеті.
