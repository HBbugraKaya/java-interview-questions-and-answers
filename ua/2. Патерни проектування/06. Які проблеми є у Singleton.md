# Які проблеми є у Singleton

---

## 🟢 Junior Level

Патерн **Singleton (Одинак)** вирішує завдання забезпечення єдиного екземпляра класу в застосунку. Проте в сучасній розробці класичний Singleton часто вважають **антипатерном**, оскільки він створює більше проблем, ніж користі:

1. **Неможливість повноцінного модульного тестування (Unit Testing):**
   Приватний конструктор і статичний метод доступу `getInstance()` не дозволяють підмінити залежність на mock-об'єкт (заглушку):
   ```java
   public class PaymentService {
       public void processPayment(double amount) {
           // ❌ Прямий виклик реального сервісу. Як протестувати без списання справжніх грошей?
           BankGateway.getInstance().charge(amount);
       }
   }
   ```
2. **Приховані залежності (Hidden Dependencies):**
   Конструктор класу порожній або відсутній, і за публічною сигнатурою класу неможливо зрозуміти, які ресурси йому потрібні для коректної роботи (база даних, мережа, файли конфігурації).
3. **Глобальний змінний стан (Global Mutable State):**
   Якщо Singleton зберігає стан, він стає доступним будь-якій частині коду з будь-якої точки програми. Зміна цього стану одним модулем призводить до непередбачуваних побічних ефектів в інших, абсолютно незалежних модулях.
4. **Взаємний вплив тестів (Flaky Tests):**
   Оскільки Singleton живе в статичній пам'яті впродовж роботи всієї JVM, стан, змінений у `TestA`, перетікає в `TestB`, спричиняючи випадкові падіння тестів залежно від порядку їхнього запуску.

> 💡 **Сучасне рішення:** Замість написання ручних Singleton-класів використовується патерн **Dependency Injection (впровадження залежностей)** за допомогою фреймворків (наприклад, Spring Framework). Компонент зі scope `singleton` управляється IoC-контейнером, легко підміняється моками в тестах і не забруднює глобальну область видимості.

## 🟡 Middle Level

### 1. Порушення інкапсуляції та надмірна зв'язаність (Tight Coupling)

При класичному використанні Singleton класи жорстко зв'язуються з конкретною реалізацією, а не з абстрактним інтерфейсом:

```java
// ❌ Приховані жорсткі залежності
public class OrderService {
    public void processOrder(Order order) {
        DatabaseConnection.getInstance().save(order);
        AuditLogger.getInstance().log("Замовлення збережено: " + order.getId());
        NotificationSender.getInstance().sendEmail(order.getUserEmail());
    }
}

// ✅ Явні залежності через конструктор (Inversion of Control)
public class OrderService {
    private final OrderRepository repository;
    private final AuditLogger logger;
    private final NotificationService notifications;

    public OrderService(OrderRepository repository, AuditLogger logger, NotificationService notifications) {
        this.repository = repository;
        this.logger = logger;
        this.notifications = notifications;
    }

    public void processOrder(Order order) {
        repository.save(order);
        logger.log("Замовлення збережено: " + order.getId());
        notifications.sendEmail(order.getUserEmail());
    }
}
```

---

### 2. Вузьке місце продуктивності (Thread Contention Bottleneck)

Якщо Singleton інкапсулює стан, що змінюється (кеш, пул з'єднань, лічильники метрик), методи доступу до нього неминуче вимагають синхронізації:

```java
public class UserSessionCache {
    private static final UserSessionCache INSTANCE = new UserSessionCache();
    private final Map<String, UserSession> sessions = new HashMap<>();

    public synchronized void put(String id, UserSession session) {
        sessions.put(id, session); // ❌ Критична секція: 10 000 паралельних потоків чекають на один монітор!
    }
}
```
В умовах високого навантаження (Highload) тисячі конкурентних запитів шикуються в чергу до єдиного монітора, спричиняючи різку деградацію часу відгуку (latency spike).

---

### 3. Ілюзія єдиності в розподілених системах і мікросервісах

Патерн Singleton гарантує рівно один екземпляр **на один ClassLoader усередині одного процесу JVM**.
У сучасних хмарних архітектурах застосунки розгортаються в кількох репліках (Kubernetes Pods):

```
Kubernetes Cluster:
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│     Pod #1      │  │     Pod #2      │  │     Pod #3      │
│  JVM Singleton  │  │  JVM Singleton  │  │  JVM Singleton  │
└─────────────────┘  └─────────────────┘  └─────────────────┘
         ▲                    ▲                    ▲
    Counter = 1          Counter = 1          Counter = 1
```

Якщо розробник розраховував, що `SequenceGenerator.getInstance().nextId()` генерує унікальні ідентифікатори на всю систему, у кластері це призведе до дублювання первинних ключів (primary key) і колізій даних.

---

### 4. Витоки пам'яті в сервлет-контейнерах (Metaspace / ClassLoader Leak)

У вебконтейнерах (Tomcat, Jetty) під час процедури гарячого перезапуску застосунку (Redeploy) створюється новий екземпляр `WebappClassLoader`:

1. Статичний Singleton у старому застосунку утримує посилання на класи та об'єкти вебзастосунку.
2. Статичне поле належить об'єкту `Class<?>`, який прив'язаний до `WebappClassLoader`.
3. Збирач сміття (Garbage Collector) не може звільнити старий `WebappClassLoader`, оскільки корінь GC (GC Root) утримує статичне посилання.
4. Після кількох перерозгортань область пам'яті `Metaspace` переповнюється, і JVM падає з критичною помилкою `java.lang.OutOfMemoryError: Metaspace`.

## 🔴 Senior Level

### Архітектурна деградація: Порушення принципів SOLID

Класичний Singleton порушує практично кожен принцип об'єктно-орієнтованого дизайну SOLID:

| Принцип | Характер порушення |
|---|---|
| **S** (Single Responsibility) | Клас бере на себе дві несумісні відповідальності: виконання прикладної бізнес-логіки та примусовий контроль власного життєвого циклу. |
| **O** (Open/Closed) | Singleton закритий для розширення. Приватний конструктор унеможливлює наслідування та поліморфізм. |
| **L** (Liskov Substitution) | Через неможливість коректного наслідування та створення поліморфних підтипів підміна реалізації неможлива. |
| **I** (Interface Segregation) | Класи-клієнти жорстко прив'язуються до монолітного конкретного класу Singleton замість спеціалізованих інтерфейсів. |
| **D** (Dependency Inversion) | Модулі високого рівня безпосередньо залежать від низькорівневої статичної реалізації замість абстракцій. |

### Взаємні блокування під час завантаження класів (Static Initialization Deadlocks)

Специфікація JVM (JLS §12.4.2) регламентує блокування ініціалізації класу (`Class Initialization Lock`). Якщо два класи Singleton циклічно залежать один від одного в статичних блоках або конструкторах, виникає взаємне блокування потоків на етапі завантаження класів:

```java
public class ServiceA {
    private static final ServiceA INSTANCE = new ServiceA();
    static {
        // Потік 1 завантажує ServiceA і запитує ServiceB
        ServiceB.getInstance().init();
    }
    public static ServiceA getInstance() { return INSTANCE; }
    public void init() {}
}

public class ServiceB {
    private static final ServiceB INSTANCE = new ServiceB();
    static {
        // Потік 2 завантажує ServiceB і запитує ServiceA
        ServiceA.getInstance().init();
    }
    public static ServiceB getInstance() { return INSTANCE; }
    public void init() {}
}
```

```
Потік 1: захопив ClassInitLock(ServiceA) ──> намагається захопити ClassInitLock(ServiceB) [BLOCKED]
Потік 2: захопив ClassInitLock(ServiceB) ──> намагається захопити ClassInitLock(ServiceA) [BLOCKED]
===> DEADLOCK на рівні завантажувача класів JVM!
```

Такий deadlock неможливо відстежити стандартними механізмами таймаутів пулів з'єднань, а застосунок намертво зависає ще до завершення підняття контексту.

---

### Відсутність контрольованого життєвого циклу (Lifecycle Management)

Класичний Singleton позбавлений керованого життєвого циклу:
- **Немає точки коректного завершення (Graceful Shutdown):** коли застосунок зупиняється, Singleton не отримує сигналу про завершення роботи, що призводить до незакритих з'єднань із базою даних, нескинутих дискових буферів та витоків дескрипторів файлів.
- **На відміну від Spring Bean:** IoC-контейнер надає повноцінний життєвий цикл із хуками `@PostConstruct`, `@PreDestroy`, інтерфейсом `DisposableBean`, керуванням черговістю запуску (`@DependsOn`) та фазами фазного вимкнення.

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь (Elevator Pitch)
> «Головні проблеми патерна **Singleton** лежать у площині архітектури та тестування. Singleton впроваджує приховані жорсткі залежності замість явних (порушуючи принципи **DIP** та **SRP** із SOLID), створює глобальний спільний стан, який породжує нестабільні тести (flaky tests) через перехресне забруднення пам'яті, та унеможливлює мокування через приватний конструктор. Крім того, Singleton не масштабується в розподіленому середовищі (він унікальний лише в межах одного JVM ClassLoader) і може спричиняти витоки пам'яті в `Metaspace` контейнерів застосунків. У сучасній enterprise-розробці ручні Singleton витіснені **IoC/DI-контейнерами** (наприклад, Spring), де область видимості `singleton` управляється фреймворком без недоліків глобального статичного стану».

### 3–4 каверзних запитання з відповідями

1. **Чому Singleton вважають грубим порушником принципу інверсії залежностей (DIP)?**
   - *Відповідь:* Принцип DIP стверджує: модулі вищих рівнів не повинні залежати від модулів нижчих рівнів, обидва мають залежати від абстракцій. Виклик `MySingleton.getInstance()` намертво прив'язує клієнтський код до конкретного класу, унеможливлюючи впровадження інтерфейсу або поліморфної заміни без повного переписування клієнтського класу.

2. **Що таке Static Initialization Deadlock і як його діагностувати?**
   - *Відповідь:* Це взаємне блокування потоків під час одночасної циклічної ініціалізації класів. JVM захищає ініціалізацію кожного класу внутрішнім блокуванням. Якщо Потік 1 ініціалізує клас А, якому потрібен клас Б, а Потік 2 у цей же час ініціалізує клас Б, якому потрібен А, обидва потоки назавжди зависають на стадії завантаження класів. У дампі потоків (thread dump) потоки перебуватимуть у стані `RUNNABLE` всередині фази ініціалізації класу.

3. **Як Singleton може спричинити OutOfMemoryError: Metaspace під час перезапуску застосунку в Tomcat?**
   - *Відповідь:* Статичні поля класів живуть у завантажувачі класів. Якщо клас Singleton утримує посилання на контекст або класи вебзастосунку, то під час повторного розгортання збирач сміття не зможе вивантажити старий `WebappClassLoader` (він утримується через GC Root статичного поля). Пам'ять метаданих класів (`Metaspace`) невпинно зростає з кожним перезапуском, призводячи до `OOM: Metaspace`.

4. **Як протестувати легасі-клас, усередині якого жорстко зашитий виклик `LegacySingleton.getInstance()`?**
   - *Відповідь:* Якщо рефакторинг на DI неможливий, використовують бібліотеки маніпуляції байткодом (наприклад, Mockito 3.4+ із підтримкою `mockStatic()`, або PowerMock), або огортають виклик Singleton у захищений package-private метод і перевизначають його в тестовому класі-нащадку (патерн Subclass and Override Method).

---

### Типові помилки та Red Flags

- 🚩 **Використання Singleton для розподіленої унікальності** (наприклад, генерація унікальних ID у мікросервісах) — у кластері буде стільки ж синглтонів, скільки інстансів сервісу.
- 🚩 **Створення власних класів Singleton у проєктах на Spring Boot** замість оголошення стандартних бінів `@Service` або `@Component`.
- 🚩 **Зберігання змінного стану без потокобезпечних структур** — створення стану гонки або точок екстремальної конкуренції (lock contention).
- 🚩 **Відмова від модульних тестів** із виправданням «цей код неможливо протестувати через наявність синглтона».
