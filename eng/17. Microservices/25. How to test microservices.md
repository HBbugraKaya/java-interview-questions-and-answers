# How to test microservices

---

## 🟢 Junior Level

Testing microservices is fundamentally more complex than testing a monolith: an application is partitioned across dozens of independent container processes communicating over an inherently unreliable network with distributed databases and message queues.

```
Microservices Test Pyramid:
                 / \
                /E2E\             ── ~5% (Slow, high fragility, full staging cluster)
               /-----\
              /Contract\          ── ~15% (Pact / Spring Cloud Contract)
             /-----------\
            / Integration \       ── ~30% (Testcontainers: Real PostgreSQL, Kafka, WireMock)
           /---------------\
          /      Unit       \     ── ~50% (Fast, isolated business logic, JUnit 5 + Mockito)
         /-------------------\
```

### Core Testing Layers:
1. **Unit Tests:** Verify isolated Java classes and domain logic without starting Spring context or opening network sockets (execution time: $< 50\text{ ms}$).
2. **Integration Tests:** Verify that a microservice communicates correctly with its external infrastructure adapters (database, Kafka topics, Redis cache) using isolated Docker containers (**Testcontainers**).
3. **Contract Tests:** Validate API schema and semantic compatibility between Consumer and Provider services without deploying the entire ecosystem.
4. **End-to-End (E2E) Tests:** Validate end-to-end critical business workflows across a deployed staging environment.

## 🟡 Middle Level

### 1. Modern Integration Testing with Testcontainers & Spring Boot 3

Using an in-memory database (like H2) hides critical production bugs. The industry standard is spinning up **real production-equivalent Docker dependencies** via **Testcontainers**:

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class OrderServiceIntegrationTest {

    // Spins up a real PostgreSQL 16 container in Docker
    @Container
    @ServiceConnection // Spring Boot 3.1+ automatically wires datasource properties
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    // Spins up a real Apache Kafka container in Docker
    @Container
    @ServiceConnection
    static KafkaContainer kafka = new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:7.6.0"));

    @Autowired
    private OrderService orderService;

    @Autowired
    private OrderRepository orderRepository;

    @Test
    void shouldCreateOrderAndPersistToPostgres() {
        OrderRequest request = new OrderRequest("user-101", new BigDecimal("99.50"));

        OrderResponse response = orderService.createOrder(request);

        assertNotNull(response.orderId());
        assertEquals("CREATED", response.status());
        assertTrue(orderRepository.findById(response.orderId()).isPresent());
    }
}
```

### 2. Stubbing Outbound HTTP APIs with WireMock

When testing how a microservice communicates with external third-party HTTP endpoints (e.g., Stripe or Twilio), calling real external servers during builds is forbidden. Use **WireMock**:

```java
@AutoConfigureWireMock(port = 0) // Starts WireMock on an available dynamic port
class PaymentClientIntegrationTest {

    @Autowired
    private PaymentGatewayClient paymentClient;

    @Test
    void shouldHandleBankTimeoutWithCircuitBreaker() {
        // Stub external bank endpoint to delay response by 3 seconds
        stubFor(post(urlEqualTo("/api/v1/charge"))
            .willReturn(aResponse()
                .withStatus(200)
                .withFixedDelay(3000)));

        // Validates that caller's Resilience4j Circuit Breaker catches the timeout
        assertThrows(CallNotPermittedException.class, () -> {
            paymentClient.charge(new ChargeRequest(new BigDecimal("100.00")));
        });
    }
}
```

## 🔴 Senior Level

### 1. Consumer-Driven Contract (CDC) Testing: Pact & Pact Broker

In large ecosystems with 50+ microservices, a common failure mode occurs when a developer on the `Payment Service` team renames JSON field `userId` to `user_id`. When deployed, five downstream consumer services crash in production.
E2E staging environments catch this too late. The enterprise solution is **Consumer-Driven Contract Testing (CDC)**:

```
1. Consumer Service (Order Service) ──► Writes expectation test (Pact)
                                                │
                                                ▼ (Generates pact.json contract)
2. Pact Broker (Central Artifact Repo) ◄── Published during Consumer CI
        │
        ▼ (Provider CI pulls contract)
3. Provider Service (Payment Service) ──► Replays pact contract against its local Controller
                                          (If field is missing -> Provider CI FAILS INSTANTLY ❌)
```

**Architectural Benefit:** The Provider team discovers breaking API changes inside their own Pull Request build in seconds, completely in isolation, without spinning up live consumer instances.

### 2. Eliminating Flaky Tests in Asynchronous Systems (Awaitility)

In event-driven architectures (Kafka/RabbitMQ), using `Thread.sleep(2000)` causes **Flaky Tests**: the test passes on a fast developer machine but randomly times out on a congested GitHub Actions runner.

#### The Solution: Awaitility (Deterministic Polling with Predicates):
```java
@Test
void shouldProcessKafkaMessageAsynchronously() {
    kafkaTemplate.send("order-events", new OrderCreatedEvent(42L));

    // Awaitility polls the database periodically with backoff until the predicate succeeds
    await().atMost(5, TimeUnit.SECONDS)
           .pollInterval(100, TimeUnit.MILLISECONDS)
           .untilAsserted(() -> {
               Optional<Order> order = orderRepository.findById(42L);
               assertTrue(order.isPresent());
               assertEquals("PROCESSED", order.get().getStatus());
           });
}
```

### 3. The "Ice Cream Cone" E2E Anti-Pattern

When engineering organizations fail to invest in Testcontainers and Contract Testing, they fall into the **Inverted Test Pyramid (Ice Cream Cone)**:
- Writing 500 massive, brittle Selenium/Playwright E2E tests requiring 40 microservices to run simultaneously in a shared Staging environment.
- **Consequences:**
  1. Test runs take 3–5 hours.
  2. A transient network hiccup in a third-party service turns all 500 tests red.
  3. Developers lose trust in CI and begin merging code with `-DskipTests`.
- **Senior Remediation:** Reduce E2E tests to 5–10 critical smoke journeys ("User logs in, adds item to cart, and checks out"). Shift 90% of verification down to Unit, Testcontainers, and Pact contract tests.

## 4 Tricky Questions

### 1. Why is using an In-Memory database like H2 for Spring Data JPA integration tests considered dangerous?
**Answer:**
H2 emulates generic SQL syntax, but differs substantially from production database engines (like PostgreSQL or MySQL):
1. **Missing Native Data Types:** H2 lacks native support for PostgreSQL-specific types like `JSONB`, network address types (`INET`), date ranges, and native `UUID[]` arrays.
2. **Proprietary SQL Dialects:** Complex PostgreSQL queries utilizing operators like `->>`, `ILIKE`, window functions, and `ON CONFLICT DO UPDATE` fail in H2 with syntax errors.
3. **Locking and Transaction Isolation:** H2 does not replicate row-level locking semantics (`SELECT ... FOR UPDATE SKIP LOCKED`), deadlock detection, or true `REPEATABLE READ` isolation anomalies.
*Production Standard:* Use **Testcontainers** with the exact PostgreSQL Docker image matching production.

### 2. How can you execute 50+ Testcontainers integration tests in 30 seconds instead of 5 minutes?
**Answer:**
By default, placing `@Container` on each test class causes Testcontainers to start and terminate Docker containers per class, adding 10–20 seconds of container boot overhead per test file.
*Optimization:* **The Singleton Containers Pattern**:
1. Define a shared base abstract class `AbstractIntegrationTest` where containers are declared as static variables without `@Container` and started manually in a static initializer block:
   ```java
   public abstract class AbstractIntegrationTest {
       static final PostgreSQLContainer<?> POSTGRES = new PostgreSQLContainer<>("postgres:16-alpine");
       static final KafkaContainer KAFKA = new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:7.6.0"));

       static {
           POSTGRES.start();
           KAFKA.start();
       }
   }
   ```
2. All integration test classes extend `AbstractIntegrationTest`. Containers spin up **exactly once for the entire test suite run**, slashing CI build times by over 80%. Database cleanup between tests is managed via `@Sql` truncate scripts or DatabaseRider.

### 3. How do you verify backward compatibility of Apache Kafka message schemas in automated tests?
**Answer:**
Using **Confluent Schema Registry Testcontainers** coupled with the Confluent Maven/Gradle plugin:
1. The CI pipeline invokes `schema-registry:test-compatibility`.
2. The plugin registers the proposed Avro or Protobuf schema change against the Schema Registry and validates it according to configured compatibility rules (**`BACKWARD`**, **`FULL`**).
3. The build fails immediately if an engineer renames an existing field, deletes a required field without a default value, or alters a data type incompatibly.

### 4. Why should you inject a `java.time.Clock` bean instead of using `Thread.sleep()` when testing TTL and expiration logic?
**Answer:**
Using `Thread.sleep(5000)` to verify token expiration or cache TTL slows down test execution and makes builds non-deterministic.
*The Architectural Fix:* Inject Java’s `java.time.Clock` into domain services as a Spring bean:
In production, the application uses `Clock.systemUTC()`. In unit and integration tests, inject a `TestClock` (or `Clock.offset()`):
```java
// Advance application time by 1 hour instantly within the same thread:
TestClock.forward(Duration.ofHours(1));
assertTrue(sessionService.isExpired(sessionId));
```
This enables instantaneous, deterministic testing of time-based business rules with zero real-time waiting.

## 🎯 Interview Cheat Sheet

### Must Know:
- **Test Pyramid:** 50% Unit Tests (fast), 30% Integration Tests (Testcontainers), 15% Contract Tests (Pact), 5% E2E Smoke Tests.
- **Testcontainers:** The enterprise standard for testing real PostgreSQL, Kafka, and Redis instances inside Docker.
- **Spring Boot 3.1+:** Use `@ServiceConnection` for zero-boilerplate Testcontainer property injection.
- **Singleton Containers Pattern:** Start static containers once in an abstract base class to avoid restarting Docker per test.
- **Consumer-Driven Contract Testing:** **Pact** verifies API schema compatibility between Consumer and Provider in CI before deployment.
- **WireMock:** Simulates third-party external HTTP REST APIs and failure modes (timeouts, 500 errors).
- **Awaitility:** Use instead of `Thread.sleep()` to eliminate flaky tests in asynchronous Kafka event pipelines.

### Common Follow-up Questions:
- *"What is the difference between `@MockBean` and WireMock?"* → `@MockBean` replaces a Java Spring bean inside the JVM using Mockito reflection; WireMock launches a local mock HTTP server that tests the entire networking stack (HTTP status codes, headers, JSON serialization, socket timeouts).
- *"What is the Pact `can-i-deploy` tool?"* → A CLI tool used in CI/CD that queries the Pact Broker to verify that all consumer-provider contracts are compatible before promoting a microservice artifact to production.

### Red Flags (DO NOT Say):
- ❌ *"We use in-memory H2 database for all our integration tests."* (H2 dialect differences mask production SQL bugs).
- ❌ *"We test microservices by running 500 end-to-end Selenium tests on a shared staging environment."* (The classic Ice Cream Cone anti-pattern that leads to massive release bottlenecks).
- ❌ *"We put `Thread.sleep(5000)` in our tests to wait for Kafka messages to arrive."* (Causes flaky tests and inflates CI build duration).
