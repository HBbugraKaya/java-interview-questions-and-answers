# How Does Consumer Balancing Work in a Group

---

## 🟢 Junior Level

### 30-Second Summary
**Consumer Balancing (Partition Assignment)** is Apache Kafka's automated distributed mechanism that dynamically distributes topic partitions among active consumer instances within a Consumer Group.

**Core Objectives:**
1. **Zero Manual Configuration:** Developers do not hardcode which server reads which partition; the cluster manages partition assignment dynamically.
2. **Elastic Fault Tolerance:** When consumer instances fail or scale up, Kafka initiates a **rebalance** to redistribute partitions across surviving live workers.
3. **Strict Partition Invariant:** Within a single Consumer Group, **one partition is assigned to at most one consumer** at any moment in time. However, a single consumer can read from multiple partitions concurrently.

---

### Real-World Analogy
Think of partition balancing as **air traffic controllers managing airport runways**:
- An international airport has 6 active runways (6 topic partitions).
- 3 air traffic controllers report for duty (3 consumers in a group).
- The shift supervisor assigns 2 runways to each controller: Controller A manages Runways 0 and 1, Controller B manages 2 and 3, and Controller C manages 4 and 5.
- If Controller C suddenly faints (service pod crash), the supervisor immediately triggers emergency redistribution, transferring Runways 4 and 5 to Controllers A and B. No runway is left unmonitored, and two controllers never issue conflicting landing commands on the same runway.

---

### Basic Architecture and Java Configuration
```
Topic (6 Partitions):   [ P0 ]  [ P1 ]    [ P2 ]  [ P3 ]    [ P4 ]  [ P5 ]
                           │       │         │       │         │       │
                           └───┬───┘         └───┬───┘         └───┬───┘
                               ▼                 ▼                 ▼
                          [Consumer A]      [Consumer B]      [Consumer C]
```

In Java, consumers simply provide a common `group.id` and subscribe to topics:
```java
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "orders-processing-group");
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("orders")); // Kafka coordinates partition assignment automatically
```

## 🟡 Middle Level

### 4 Primary Partition Assignment Strategies
The assignment algorithm is selected via `partition.assignment.strategy`:

| Strategy | Algorithm Mechanics | Advantages | Disadvantages |
| :--- | :--- | :--- | :--- |
| **`RangeAssignor`** *(historic default)* | Evaluates each topic independently, assigning contiguous ranges of numeric partitions. | Simple logic; aligns co-partitioned topics for local stream joins. | **Severe partition skew** when subscribing to multiple topics! |
| **`RoundRobinAssignor`** | Interleaves all partitions of all subscribed topics uniformly across consumers in a circle. | Perfectly uniform partition distribution. | Scrambles and shuffles all partition assignments during any rebalance. |
| **`StickyAssignor`** | Balances partition counts while preserving existing assignments to minimize partition movement. | Retains cached state and keeps partition churn low. | Bound to the legacy Eager protocol (Stop-the-World group pause). |
| **`CooperativeStickyAssignor`** *(modern standard)* | Incremental cooperative rebalancing (KIP-429); reassigns only migrating partitions without pausing others. | 🚀 **Near-zero downtime**, eliminates global Stop-the-World pauses. | Requires Kafka client 2.3+. |

---

### The Multi-Topic RangeAssignor Imbalance Trap
Consider a microservice subscribed to 10 topics, where each topic has 3 partitions (`P0`, `P1`, `P2`). The group consists of 2 consumer instances (`C1` and `C2`):
- `RangeAssignor` calculates assignments independently per topic: $3 \text{ partitions} \div 2 \text{ consumers} = 1.5$. It rounds up for the first consumer: `C1` receives `P0` and `P1`, while `C2` receives `P2`.
- Because this exact assignment is computed independently for **every one of the 10 topics**:
  - **Consumer `C1` is assigned 20 partitions!**
  - **Consumer `C2` is assigned only 10 partitions!**
- `C1` suffers double the CPU and memory load, accumulates massive consumer lag, and risks GC timeouts, while `C2` sits underutilized.
- **Production Takeaway:** Never use `RangeAssignor` for multi-topic consumer groups; standardise on `CooperativeStickyAssignor`.

---

### Lifecycle Management via `ConsumerRebalanceListener`
When a rebalance occurs, consumers must flush in-flight operations and commit offsets before losing partition ownership:

```java
consumer.subscribe(List.of("orders"), new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        // Invoked BEFORE the broker revokes partitions from this consumer.
        // Synchronously commit offsets to prevent duplicate processing by the next owner!
        consumer.commitSync();
    }

    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        // Invoked AFTER new partitions are assigned.
        // Initialize local caches, seek specific offsets, or refresh database connections.
    }

    @Override
    public void onPartitionsLost(Collection<TopicPartition> partitions) {
        // Invoked if partitions were already seized by the coordinator (e.g. heartbeat timeout).
        // DO NOT commit offsets here; state was already reassigned!
    }
});
```

## 🔴 Senior Level

### Anatomy of the Classic Rebalance Protocol (JoinGroup / SyncGroup)
A common interview misconception is that the Kafka broker computes partition assignments. In the classic protocol, **one of the client consumers (the Group Leader) executes the assignment algorithm**:

```
[ Consumer A ]               [ Group Coordinator (Broker) ]               [ Consumer B ]
      │                                    │                                    │
      │ 1. JoinGroup Request               │                                    │
      ├───────────────────────────────────►│ 1. JoinGroup Request               │
      │                                    │◄───────────────────────────────────┤
      │                                    │                                    │
      │ (Broker elects Consumer A Leader)  │                                    │
      │                                    │                                    │
      │ 2. JoinGroup Response              │ 2. JoinGroup Response              │
      │ (allMembers + IS_LEADER=true)      │ (memberId + IS_LEADER=false)       │
      │◄───────────────────────────────────┼───────────────────────────────────►│
      │                                    │                                    │
      │ [ Leader A runs                    │                                    │
      │   PartitionAssignor.assign() ]     │                                    │
      │                                    │                                    │
      │ 3. SyncGroup Request               │ 3. SyncGroup Request               │
      │ (sends full assignment plan)       │ (empty wait request)               │
      │───────────────────────────────────►│◄───────────────────────────────────┤
      │                                    │                                    │
      │ 4. SyncGroup Response              │ 4. SyncGroup Response              │
      │ (assigned: P0, P1, P2)             │ (assigned: P3, P4, P5)             │
      │◄───────────────────────────────────┼───────────────────────────────────►│
```

### KIP-848: Next Generation Consumer Protocol (Kafka 3.7+ / 4.0)
The legacy client-side protocol suffered from high join latency and vulnerability to slow group leaders. **KIP-848** fundamentally redesigns consumer rebalancing:
1. **Server-Side Assignment:** The partition assignment algorithm moves completely to the **Group Coordinator (Broker)**.
2. **Elimination of JoinGroup/SyncGroup:** Rebalancing is driven continuously via lightweight `ConsumerGroupHeartbeat` RPCs.
3. **True Incremental Handoff:** The broker instructs individual members to release or claim specific partitions directly inside periodic heartbeat responses without freezing the consumer group.

---

### The Kubernetes Autoscaling Death Loop (HPA Anti-Pattern)
A dangerous failure mode in cloud-native Kafka architectures:
1. SREs configure Kubernetes **Horizontal Pod Autoscaler (HPA)** based on pod CPU utilization (`targetCPUUtilizationPercentage: 70%`).
2. An upstream traffic surge arrives, pushing consumer pod CPU usage to 85%.
3. HPA detects threshold breach and spawns 3 new pods.
4. The new pods join the Consumer Group, triggering a **rebalance**.
5. During rebalance, consumers pause, commit offsets, establish socket pools, and re-fetch records. GC pauses and network connection floods spike pod CPU to 100%.
6. HPA interprets this secondary spike as higher workload demand and **schedules another 5 pods**!
7. The system enters an infinite cascading rebalance storm: consumers never finish processing, and consumer lag explodes into millions of records.
- **Architectural Solution:** Never autoscale Kafka consumer pods on CPU! Autoscale strictly on **Consumer Lag** (using KEDA or Prometheus Adapter) and enforce a cooldown period (minimum 5–10 minutes) with `CooperativeStickyAssignor`.

## 4 Tricky Questions

### 1. Why does `RangeAssignor` cause extreme partition skew on multi-topic subscriptions, and why was it kept as the default for so long?
**Answer:**
- `RangeAssignor` sorts partitions numerically for each topic and divides them by consumer count. If 10 topics each have 3 partitions and there are 2 consumers, the division yields a remainder of 1 for every topic. `C1` receives 2 partitions and `C2` receives 1 partition across all 10 topics, culminating in 20 partitions on `C1` vs 10 on `C2`.
- It remained the historic default for backward compatibility with **Co-partitioning**: in early streaming designs, if Topic A and Topic B shared identical partition keys and counts, `RangeAssignor` guaranteed that `TopicA-Partition0` and `TopicB-Partition0` landed on the same JVM instance, allowing in-memory joins without cross-network data shuffling.

---

### 2. Who physically executes the `PartitionAssignor.assign()` code in Kafka—the broker or the client?
**Answer:**
- In the classic Kafka protocol (prior to KIP-848), the partition assignment logic is executed entirely on **one of the client consumer instances designated as the Group Leader**.
- The broker (Group Coordinator) merely collects member metadata during `JoinGroup` and delegates assignment calculation to the Leader. The Leader executes the Java bytecode of `PartitionAssignor`, produces the partition mapping, and submits it back to the broker via `SyncGroup`.
- Starting with KIP-848 (Kafka 3.7+ preview, default in Kafka 4.0), execution shifts to **Server-Side Assignment** on the broker itself.

---

### 3. What happens if an unhandled `RuntimeException` is thrown inside `ConsumerRebalanceListener.onPartitionsRevoked()`?
**Answer:**
- If an unhandled exception escapes `onPartitionsRevoked()` (e.g., database flush failure or network timeout), the consumer aborts its graceful rebalance cleanup.
- Uncommitted offsets remain unpersisted in `__consumer_offsets`.
- The consumer marks its internal state as corrupted, aborts the `poll()` loop, and terminates its session by throwing a fatal `KafkaException`.
- The coordinator evicts the failed consumer after `session.timeout.ms`. When the coordinator reassigns those partitions to another member, the new owner resumes from the last successfully committed offset, causing **duplicate processing** of all uncommitted records.

---

### 4. How does `StickyAssignor` differ from `CooperativeStickyAssignor` when a new consumer instance joins an active group?
**Answer:**
- **`StickyAssignor`** operates on the **Eager protocol**: when a new instance joins, the broker forces **all existing consumers to immediately surrender 100% of their partitions**. The entire group suffers a Stop-the-World pause while a new plan is formed, even though `StickyAssignor` ends up reassigning most original partitions back to their previous owners.
- **`CooperativeStickyAssignor`** operates on the **Cooperative protocol (KIP-429)**: existing consumers **continue reading their unaffected partitions without stopping**. Only the specific 1–2 partitions destined for the new member are revoked in an incremental, non-blocking phase, completely eliminating group-wide processing pauses.

## 🎯 Interview Cheat Sheet

### Core Concepts at a Glance
- **Core Function:** Automatic partition distribution across active consumers under a unified `group.id`.
- **Partition Rule:** Exactly 1 consumer per partition within a group; excess consumers remain idle.
- **Production Standard:** Always configure `CooperativeStickyAssignor` to avoid Stop-the-World pauses.
- **Range Skew:** Multi-topic subscriptions using `RangeAssignor` severely overload early consumer instances.
- **Execution Location:** In classic Kafka, the client Group Leader runs `assign()`, not the broker.
- **State Preservation:** Implement `ConsumerRebalanceListener` to commit offsets in `onPartitionsRevoked()`.
- **K8s Autoscaling:** Scale consumer pods based on Consumer Lag metrics via KEDA, never on CPU utilization.

---

### Strategy Comparison Matrix

| Strategy | Protocol | Distribution Uniformity | Partition Churn on Rebalance |
| :--- | :--- | :--- | :--- |
| **`RangeAssignor`** | Eager (Stop-the-World) | ❌ Severely skewed on multi-topic | Medium |
| **`RoundRobinAssignor`** | Eager (Stop-the-World) | ✅ Uniform across all topics | ❌ High (reshuffles everything) |
| **`StickyAssignor`** | Eager (Stop-the-World) | ✅ Uniform | ✅ Low (preserves assignments) |
| **`CooperativeStickyAssignor`** | **Cooperative (Incremental)** | ✅ Uniform | 🚀 Lowest (reassigns migrating only) |

---

### Red Flags to Avoid
- ❌ *"The Kafka broker runs the Java code to determine partition distribution in standard Kafka."* (In classic Kafka, the client Group Leader computes the assignment).
- ❌ *"RangeAssignor divides partitions evenly across consumers in all scenarios."* (It causes severe multi-topic skew).
- ❌ *"Every rebalance freezes message processing across the entire consumer group for 30 seconds."* (With `CooperativeStickyAssignor`, unaffected partitions process uninterrupted).
- ❌ *"Autoscaling consumer pods on CPU utilization in Kubernetes is standard practice."* (Triggers cascading rebalance storms; use Consumer Lag instead).
