# What is the difference between checked and unchecked exceptions

---

## 🟢 Junior Level

In the Java platform, all errors and exceptional conditions are represented as first-class objects deriving from the root class **`java.lang.Throwable`**. Architecturally, they are bifurcated into two foundational categories: **Checked** and **Unchecked**.

```
                         java.lang.Throwable
                                  │
                 ┌────────────────┴────────────────┐
                 ▼                                 ▼
         java.lang.Error                 java.lang.Exception
          (Unchecked)                     (Checked by default)
                                                   │
                                                   ▼
                                        java.lang.RuntimeException
                                               (Unchecked)
```

### Core Comparison Matrix

| Criterion | Checked Exceptions | Unchecked Exceptions |
| :--- | :--- | :--- |
| **Base Class** | Subclasses of `java.lang.Exception` (excluding `RuntimeException`). | Subclasses of `java.lang.RuntimeException` and `java.lang.Error`. |
| **Compiler Enforcement** | **Mandatory**. The `javac` compiler refuses to compile if unhandled. | **Optional**. The compiler does not verify or demand handling. |
| **Handling Mechanism** | Must be enclosed in a `try-catch` block or declared in signature: `throws IOException`. | Optional `try-catch`. No method signature declaration required. |
| **Architectural Intent** | Recoverable, foreseeable external infrastructure failures (disk, network, DB). | Programming defects (bugs), API contract violations, or unrecoverable states. |
| **Standard Examples** | `IOException`, `SQLException`, `ClassNotFoundException`, `InterruptedException`. | `NullPointerException`, `IllegalArgumentException`, `IndexOutOfBoundsException`, `IllegalStateException`. |

### Code Example

```java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class ExceptionBasics {

    // 1. Checked exception: Method MUST declare throws or handle inside try-catch
    public void readConfigFile(Path path) throws IOException {
        byte[] bytes = Files.readAllBytes(path);
    }

    // 2. Unchecked exception: Compiler does not require throws or try-catch
    public int calculateRatio(int numerator, int denominator) {
        if (denominator == 0) {
            throw new IllegalArgumentException("Denominator cannot be zero"); // RuntimeException
        }
        return numerator / denominator;
    }
}
```

## 🟡 Middle Level

### The Runtime Illusion: Compiler (`javac`) vs JVM Bytecode

One of the most crucial architectural realities of the Java platform is: **The JVM runtime at the bytecode level has zero concept of checked exceptions!**

- The distinction between checked and unchecked exceptions exists **strictly at compile time** inside the `javac` compiler.
- In the JVM specification (JVMS §6.5), the **`athrow`** opcode takes whatever reference is on top of the operand stack (which must be an instance of `java.lang.Throwable`) and unwinds the call stack identically regardless of its class hierarchy.
- In the class file bytecode, the method's `Exception_table` maps bytecode offset ranges (`from`, `to`, `target`, `type`) without distinguishing whether `type` is checked or unchecked.
- The `Exceptions` attribute in the method signature metadata is used solely for static verification during compilation and class loading.

### Why Modern Software Engineering Abandoned Checked Exceptions

Modern enterprise languages designed after Java (such as C#, Kotlin, Scala, Go, Rust, and Swift) deliberately rejected checked exceptions. Even within the Java ecosystem, nearly all leading frameworks (Spring, Hibernate, Jackson, Quarkus) migrated entirely to `RuntimeException`.

**Key Architectural Flaws of Checked Exceptions:**
1. **Signature Pollution (Interface Fragility):**  
   If a low-level DAO throws `SQLException`, that checked exception leaks into the service interface, domain models, and controllers. Replacing a relational database with NoSQL breaks every intermediate signature across the entire call stack.
2. **Incompatibility with Functional Programming & Stream API:**  
   Standard Java functional interfaces (`Function<T, R>`, `Predicate<T>`, `Consumer<T>`, `Supplier<T>`) do not declare `throws Exception`. Calling a checked method inside a Stream pipeline causes immediate compilation errors:
   ```java
   // COMPILATION ERROR: Unhandled exception: java.io.IOException
   List<String> lines = paths.stream()
           .map(path -> Files.readString(path))
           .toList();
   ```
3. **The Catch-and-Swallow Anti-Pattern:**  
   Developers forced to catch checked exceptions that they cannot reasonably recover from often write empty catch blocks (`catch (Exception e) {}`), hiding critical failures and corrupting system state.

### The Exception Translation Pattern

Production enterprise architectures intercept low-level checked infrastructure exceptions at module boundaries and wrap them into semantic, unchecked domain exceptions:

```java
public class OrderRepositoryImpl implements OrderRepository {

    @Override
    public Order findById(Long id) {
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement("SELECT * FROM orders WHERE id = ?")) {
            ps.setLong(1, id);
            ResultSet rs = ps.executeQuery();
            if (!rs.next()) {
                throw new OrderNotFoundException("Order not found with id: " + id);
            }
            return mapOrder(rs);
        } catch (SQLException ex) {
            // Translate technical checked SQLException into a semantic unchecked domain exception
            throw new RepositoryAccessException("Database access error for order: " + id, ex);
        }
    }
}
```
*In Spring Framework, `PersistenceExceptionTranslationPostProcessor` performs this translation automatically, transforming all vendor-specific JDBC and JPA exceptions into Spring's unchecked `org.springframework.dao.DataAccessException` hierarchy.*

## 🔴 Senior Level

### Sneaky Throws: Bypassing the Compiler via Generic Type Erasure

Because the JVM does not verify checked exception signatures at runtime, generic type erasure allows throwing any checked exception without declaring `throws` or wrapping it:

```java
public class SneakyThrowUtil {

    // Generic parameter E is erased to Throwable in bytecode
    @SuppressWarnings("unchecked")
    private static <E extends Throwable> void sneakyThrowInternal(Throwable ex) throws E {
        throw (E) ex;
    }

    public static void sneakyThrow(Throwable ex) {
        SneakyThrowUtil.<RuntimeException>sneakyThrowInternal(ex);
    }
}
```

Usage inside Stream API pipelines:
```java
List<String> list = paths.stream()
        .map(path -> {
            try {
                return Files.readString(path);
            } catch (IOException e) {
                SneakyThrowUtil.sneakyThrow(e); // Throws checked IOException without method throws!
                return null;
            }
        })
        .toList();
```
*Project Lombok's `@SneakyThrows` annotation generates this exact generic casting trick directly into the generated class bytecode.*

### High-Throughput Performance: The Cost of `fillInStackTrace()`

In high-throughput microservices and low-latency systems (e.g., handling 100k+ RPS), throwing exceptions as flow control severely degrades CPU performance.

The primary bottleneck in `new MyException()` is not object allocation, but the native call to **`Throwable.fillInStackTrace()`**:
- The JVM suspends execution, captures a snapshot of the current thread's call frames, and walks back through the stack to resolve class names, method names, and line numbers from JVM metadata.
- This creates massive CPU cache churn and GC allocation pressure under sustained loads.

#### Stackless Exceptions (Highload Optimization)
When an exception represents an expected domain condition (such as validation failure, optimistic lock collision, or circuit-breaker trip) where a stack trace is unnecessary for debugging, create a stackless exception:

```java
package com.example.exception;

public class BusinessValidationException extends RuntimeException {

    public BusinessValidationException(String message) {
        // Java 7+ protected constructor:
        // super(message, cause, enableSuppression = false, writableStackTrace = false)
        super(message, null, false, false);
    }

    // Alternative override for legacy libraries:
    @Override
    public synchronized Throwable fillInStackTrace() {
        return this; // Bypasses expensive JVM stack walking! 30-50x faster instantiation
    }
}
```

## 4 Tricky Questions

### 1. Does the JVM runtime distinguish between checked and unchecked exceptions during execution?

**Answer:**  
No. At the bytecode and JVM runtime levels, there is no distinction between checked and unchecked exceptions. Both are instantiated and thrown using the identical bytecode instruction **`athrow`**, which operates on any instance of `java.lang.Throwable`. The checked vs. unchecked distinction is purely a static check enforced by the Java compiler (`javac`).

### 2. How does Lombok's `@SneakyThrows` enable throwing a checked exception without a `throws` clause?

**Answer:**  
It exploits Java's **generic type erasure**. A generic helper method casts the `Throwable` instance to a generic type parameter `<E extends Throwable>`, where the compiler infers `E` as `RuntimeException`. However, during compilation, type erasure strips `E` down to `Throwable` in the bytecode. The JVM executes the resulting `athrow` instruction without complaint because it does not enforce compile-time checked exception rules.

### 3. Why is creating an exception hundreds of times slower than creating a standard Java object, and how can it be optimized?

**Answer:**  
The constructor of `Throwable` invokes the native method `fillInStackTrace()`. This forces the JVM to traverse the execution stack frames of the current thread to record class names, method names, source files, and line numbers.  
In high-throughput environments, this can be optimized by invoking the 4-argument `Throwable` constructor with `writableStackTrace = false` or by overriding `fillInStackTrace()` to return `this` without traversing the stack, providing a 30x–50x performance improvement.

### 4. What happens when a checked exception occurs inside a Java Stream API lambda, and what are the best architectural solutions?

**Answer:**  
The code fails to compile because standard functional interface methods (such as `Function.apply()` or `Consumer.accept()`) do not declare `throws Exception`.  
Architectural solutions:
1. **Try-Catch Wrapping:** Catch the checked exception inside the lambda and wrap it into an unchecked domain exception (`RuntimeException`).
2. **Library Support (Vavr):** Use functional control abstractions like `Try.of(...)` or `Either<L, R>`.
3. **Sneaky Throws:** Use Lombok's `@SneakyThrows` or custom type erasure utilities if bubbling the checked exception untouched is required.

## 🎯 Interview Cheat Sheet

### 30-Second Summary
> - **Checked Exceptions** inherit from `java.lang.Exception` (excluding `RuntimeException`). The `javac` compiler enforces handling via `try-catch` or `throws`. They represent recoverable external failures (`IOException`, `SQLException`).
> - **Unchecked Exceptions** inherit from `java.lang.RuntimeException` (or `Error`). Handling is optional. They denote programming bugs, contractual violations (`NullPointerException`, `IllegalArgumentException`), or domain failures.
> - **JVM Bytecode Invariant:** The JVM runtime does not distinguish checked from unchecked exceptions; all exceptions are processed identically via the `athrow` opcode.
> - **Enterprise Standard:** Modern Java architectures catch low-level checked exceptions at module boundaries and wrap them into unchecked domain exceptions (Exception Translation).

### Red Flags (What to Avoid)
- ❌ *"Unchecked exceptions are fatal JVM errors that cannot be caught."* (`Error` represents fatal JVM conditions; `RuntimeException` is unchecked and can be caught and handled).
- ❌ *"The JVM verifies checked exception declarations at runtime when executing classes."* (Only the `javac` compiler checks them; the JVM treats all `Throwable` objects identically).
- ❌ *"All business errors should be checked exceptions to force developers to handle them."* (This is an anti-pattern that leads to signature pollution and empty catch blocks).
- ❌ *"Throwable and Exception are exact synonyms."* (`Throwable` is the superclass of both `Exception` and `Error`).
