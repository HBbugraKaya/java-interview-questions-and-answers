# Что такое bounded type parameters

---

## 🟢 Junior Level

**Bounded Type Parameters (ограниченные параметры типов)** — это механизм дженериков, позволяющий **ограничить диапазон типов**, которые можно передавать в качестве аргументов дженерика.

Без ограничений переменная типа `<T>` может быть заменена абсолютно любым ссылочным типом. При наложении ограничения вы указываете, что тип обязан быть наследником определенного класса или реализовывать определенный интерфейс.

### Синтаксис

Для ограничения сверху всегда используется ключевое слово **`extends`** (даже если границей выступает интерфейс!):

```java
// T обязан быть подтипом Number (Integer, Double, BigDecimal и т.д.):
public class NumberBox<T extends Number> {
    private T value;

    public void set(T value) { this.value = value; }

    public double getAsDouble() {
        // Благодаря bound компилятор разрешает вызывать методы Number:
        return value.doubleValue();
    }
}

// Использование:
NumberBox<Integer> intBox = new NumberBox<>(); // ✅ Успешно: Integer extends Number
NumberBox<Double> dblBox = new NumberBox<>();  // ✅ Успешно: Double extends Number

// ❌ Ошибка компиляции: Type parameter 'java.lang.String' is not within its bound
// NumberBox<String> strBox = new NumberBox<>(); 
```

## 🟡 Middle Level

### 1. Зачем нужны ограничения: доступ к методам

В неограниченном дженерике `<T>` компилятор знает только то, что $T$ является `Object`. Вы можете вызывать у переменной типа $T$ только базовые методы: `equals()`, `hashCode()`, `toString()`.

Ограничение типа открывает доступ ко всем публичным методам границы (Bound):

```java
// Без ограничения: вызов compareTo() невозможен!
// public static <T> int compare(T a, T b) { return a.compareTo(b); } // ❌ Ошибка!

// С ограничением: компилятор гарантирует наличие compareTo()
public static <T extends Comparable<T>> int compare(T a, T b) {
    return a.compareTo(b); // ✅ Безопасный вызов!
}
```

### 2. Множественные ограничения (Multiple Bounds)

Один параметр типа может быть ограничен несколькими типами через символ **`&`** (логическое пересечение типов — Intersection Type):

```java
public class Processor<T extends Number & Comparable<T> & Serializable> {
    // T обязан:
    // 1. Быть подклассом Number
    // 2. Реализовывать Comparable<T>
    // 3. Реализовывать Serializable
}
```

#### Жесткое правило порядка (JLS §4.4):
Если среди ограничений присутствует **класс**, он **в обязательном порядке должен стоять на первом месте**:
```java
// ✅ Верно: класс идет первым, интерфейсы следом
public class Valid<T extends Number & Serializable> {}

// ❌ Ошибка компиляции: Interface cannot precede a class in bounds
// public class Invalid<T extends Serializable & Number> {}
```

## 🔴 Senior Level

### Правила стирания при множественных ограничениях (First Bound Rule)

Спецификация Java (JLS §4.6) предписывает: при стирании типов переменная $T$ стирается **строго до своей первой границы (`First Bound`)**:

```java
public class Worker<T extends CharSequence & Serializable> {
    private T data;
    public T getData() { return data; }
}
```

После компиляции и стирания типов в байткод:
- Поле `data` превращается в **`CharSequence`** (первая граница).
- Во всех местах, где объект `data` используется в контексте второго интерфейса (`Serializable`), компилятор автоматически генерирует проверочную инструкцию **`checkcast`**.

Именно поэтому класс всегда обязан быть первой границей: в байткоде JVM поле экземпляра может иметь только один класс-предок (одиночное наследование классов в Java).

### Запрет `super` для Type Parameters

> [!CAUTION]
> **Частая ловушка на собеседованиях:**
> Можно ли написать `class Box<T super Integer>`?
> **НЕТ! Это синтаксическая ошибка компиляции.**

Ключевое слово **`super`** (нижняя граница) применимо **исключительно к подстановочным знакам (Wildcards)**:
```java
List<? super Integer> list; // ✅ Bounded Wildcard разрешен
// class Box<T super Integer> {} // ❌ Ошибка компиляции: Type parameter cannot have lower bound
```
*Почему?* Параметр типа `<T>` вводит новую именованную переменную типа, используемую для создания полей и методов. Нижняя граница `<T super Integer>` означала бы, что $T$ может быть `Integer`, `Number` или `Object`. Компилятор не мог бы гарантировать, какие методы доступны у такого объекта, а стирание типов привело бы к невозможности выбора типа в байткоде.

### Рекурсивные ограничения (Recursive Type Bounds)

Сложный паттерн, где параметр типа ссылается на самого себя:
```java
// Классический пример из JDK: java.lang.Enum
public abstract class Enum<E extends Enum<E>> implements Comparable<E> { ... }
```

В обобщенных коллекциях лучшей практикой является использование **Relaxed Recursive Bound** (рекомендация Джошуа Блоха):
```java
// Строгое ограничение (ломает наследование):
public static <T extends Comparable<T>> T max(Collection<T> coll) { ... }

// Идиоматичное гибкое ограничение:
public static <T extends Comparable<? super T>> T max(Collection<T> coll) { ... }
```

## 4 Tricky Questions

### 1. Можно ли объявить нижнюю границу (lower bound) для type parameter, например `<T super Number>`?
**Ответ:** 
**Категорически нет.** 

Спецификация языка Java (JLS §4.4) не допускает использование ключевого слова `super` в декларации параметров типов (`type parameters`). Конструкция `<T super Number>` вызовет синтаксическую ошибку компиляции. 

Ключевое слово `super` зарезервировано исключительно для подстановочных знаков (**Bounded Wildcards**): `<? super Number>`. Wildcard используется как анонимный тип аргумента метода при применении принципа PECS (Consumer Super), но создать класс или метод с объявлением типа `<T super ...>` невозможно.

### 2. Почему в объявлении `<T extends ClassA & InterfaceB>` класс обязательно должен стоять первым, и что будет, если поменять их местами?
**Ответ:** 
Если поменять их местами (`<T extends InterfaceB & ClassA>`), код не скомпилируется с ошибкой: `«Interface expected here»` или `«The class must be the first bound»`. 

Это обусловлено двумя факторами:
1. **Спецификация стирания типов (JLS §4.6)**: компилятор всегда стирает тип $T$ до его первой границы (First Bound).
2. **Модель объектной памяти JVM**: в байткоде поле класса должно иметь конкретный тип дескриптора. Поскольку в Java действует одиночное наследование классов, первым типом обязан быть класс, чтобы стать базовым дескриптором в байткоде.

### 3. В чем фундаментальная разница между Bounded Type Parameter (`<T extends Number> void method(T val)`) и Bounded Wildcard (`void method(List<? extends Number> list)`)?
**Ответ:** 
- **Bounded Type Parameter (`<T extends Number>`)**: объявляет именованную переменную типа $T$. Она может использоваться многократно: для связи типов между несколькими аргументами (`void merge(T a, T b)`), для типизации возвращаемого значения (`T calculate()`), а также для инстанциации локальных переменных внутри метода.
- **Bounded Wildcard (`<? extends Number>`)**: представляет собой анонимный, неизвестный тип. Он служит только для обеспечения безопасной ковариантности параметров коллекций (чтение данных). Внутри метода нельзя объявить переменную типа `?`, и нельзя связать два аргумента гарантией, что они принадлежат к одному и тому же конкретному подтипу.

### 4. Почему при объявлении метода поиска максимума правильнее писать `<T extends Comparable<? super T>>`, а не `<T extends Comparable<T>>`?
**Ответ:** 
Рассмотрим иерархию: базовый класс `ScheduledTask implements Comparable<ScheduledTask>`, и его наследник `DelayedTask extends ScheduledTask`. 

Класс `DelayedTask` не реализует `Comparable<DelayedTask>`, он унаследовал интерфейс `Comparable<ScheduledTask>`. Если метод поиска максимума объявлен строго как `<T extends Comparable<T>>`, компилятор откажется принимать `List<DelayedTask>`, потому что для `DelayedTask` условие `T implements Comparable<T>` ложно (он реализует `Comparable` для супертипа). 

Конструкция `<T extends Comparable<? super T>>` решает проблему, разрешая сравнивать объекты потомка компаратором любого его суперкласса.

## 🎯 Шпаргалка для интервью

### Главное о Bounded Type Parameters

- **Синтаксис**: `<T extends UpperBound>`. Ключевое слово всегда `extends` (и для классов, и для интерфейсов).
- **Смысл**: Ограничивает тип сверху и открывает доступ к методам границы.
- **Multiple Bounds**: `<T extends ClassA & InterfaceB & InterfaceC>`. Класс обязан быть **первым**!
- **Стирание типов**: $T$ стирается до своей **первой границы**.
- **Запрет `super`**: `<T super Type>` запрещен синтаксически. `super` разрешен только в wildcards: `<? super Type>`.
- **PECS в компараторах**: Всегда используйте `<T extends Comparable<? super T>>` для поддержки полиморфных иерархий.
