# Когда использовать parallel streams

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
Использовать **`parallelStream()`** целесообразно **только** при одновременном соблюдении трех обязательных условий:

1. **Большой объем данных:** в источнике содержатся десятки или сотни тысяч элементов.
2. **Тяжелые вычисления процессора (CPU-Bound):** математика, криптографическое хеширование, парсинг сложных форматов, обработка графики/аудио.
3. **Полная независимость элементов:** функции внутри стрима чистые (stateless), не имеют побочных эффектов (side-effects) и не мутируют общее состояние.

Если хотя бы одно условие не выполняется — параллельные стримы применять не следует. Для задач ввода-вывода (I/O: HTTP-запросы, запросы к БД, чтение файлов) использовать `parallelStream()` категорически нельзя, так как это парализует общий пул `ForkJoinPool.commonPool()` всей JVM.

---

### Базовый пример на Java 21

```java
import java.math.BigInteger;
import java.util.List;
import java.util.stream.LongStream;

public class WhenToUseParallelDemo {

    public static void main(String[] args) {
        // ✅ ХОРОШО: CPU-нагрузка, массив с быстрым делением, чистая функция
        List<BigInteger> heavyPrimes = LongStream.rangeClosed(1_000_000, 1_100_000)
            .parallel()
            .mapToObj(BigInteger::valueOf)
            .filter(n -> n.isProbablePrime(50))
            .toList();

        System.out.println("Найдено простых чисел: " + heavyPrimes.size());

        // ❌ ПЛОХО: Маленький список и примитивная операция
        List<String> words = List.of("apple", "banana", "cherry");
        List<String> upper = words.parallelStream() // Оверхед на fork/join в 10 раз дольше самой работы!
            .map(String::toUpperCase)
            .toList();
    }
}
```

## 🟡 Middle Level

### Оценка целесообразности: модель $N \times Q$

Согласно эмпирической модели Брайана Гетца, параллелизм приносит ускорение, когда:
$$N \times Q > 10\,000$$
где:
- $N$ — число элементов в источнике;
- $Q$ — количество тактов процессора, затрачиваемое на обработку одного элемента.

Если операция над элементом дешевая ($Q$ мало: сложение чисел, чтение поля объекта), $N$ должно быть не менее сотен тысяч элементов. Если операция тяжелая ($Q$ велико: вычисление RSA, парсинг JSON), параллелизм может быть эффективен даже при $N = 1\,000$.

---

### Анализ структуры источника и операций

#### 1. Структура источника данных:
- **Отлично делятся ($O(1)$):** `int[]`, `long[]`, `ArrayList`, `IntStream.rangeClosed()`. Они знают точный размер (`SIZED`), расположены компактно в памяти и мгновенно делятся по индексам ровно пополам.
- **Средне делятся ($O(1)$ амортизировано):** `HashSet`, `TreeSet`. Размер известен, но деление по бакетам требует дополнительных накладных расходов.
- **Ужасно делятся ($O(N)$):** `LinkedList`, `Stream.iterate()`. Для разделения связного списка пополам нужно обойти $N/2$ ссылок. Накладные расходы на разделение делают параллельный стрим медленнее последовательного.

#### 2. Влияние промежуточных операций:
- **Stateless-операции (`filter`, `map`, `flatMap`):** отлично масштабируются, потоки работают изолированно.
- **Stateful-операции (`sorted`, `distinct`, `limit`, `skip`):** создают глобальные барьеры синхронизации. Например, операция `sorted()` в параллельном стриме вынуждена собрать все элементы из всех потоков в один огромный буфер, отсортировать его и только потом передать дальше.

## 🔴 Senior Level

### Архитектурный выбор в современных сервисах

В серверных приложениях (Spring Boot, Quarkus) большая часть нагрузки уже является конкурентной: веб-сервер обрабатывает тысячи входящих HTTP-запросов одновременно в разных потоках.

```
Incoming Web Requests (Tomcat Worker Threads)
Request 1  ───> Thread 1 ──┐
Request 2  ───> Thread 2 ──┼──> Запуск parallelStream() в каждом запросе
Request 3  ───> Thread 3 ──┘           │
                                       ▼
                       ForkJoinPool.commonPool() (Количество ядер - 1)
                       [Worker 1] [Worker 2] [Worker 3] (Захлебываются)
                       ───> Thread Starvation, лавинообразный рост латентности!
```

1. **Серверный параллелизм:** Если сервис уже загружен сотнями параллельных клиентских запросов, включение `parallelStream()` внутри обработки одного запроса приведет к исчерпанию потоков пула, конкуренции за кэши CPU (Cache Thrashing) и деградации общей пропускной способности.
2. **Пакетная обработка (Batch / ETL):** Напротив, в ночных фоновых джобах (Spring Batch, CLI-утилитах), где один процесс монопольно утилизирует все ядра сервера, `parallelStream()` является великолепным и простым решением для ускорения вычислений.

---

### `parallelStream()` vs Virtual Threads (Java 21) vs `CompletableFuture`

| Профиль задачи | Лучший инструмент | Почему НЕ `parallelStream()` |
|---|---|---|
| **CPU-Bound над большими данными** (математика, хэши) | 🟢 **`parallelStream()`** | Идеально загружает доступные физические ядра без накладных расходов на контекст |
| **I/O-Bound задачи** (HTTP-вызовы, SQL, очереди) | 🟢 **Virtual Threads (Java 21+)** | `parallelStream` блокирует платформенные потоки `commonPool` |
| **Асинхронные графы зависимостей** | 🟢 **`CompletableFuture`** | Поддерживает неблокирующие цепочки `thenCompose`, таймауты и обработку ошибок |

---

### Влияние аппаратной архитектуры: False Sharing и кэш-линии

При параллельной обработке коллекций ссылочных объектов (`List<Object>`):
1. **Cache Misses:** Ссылочные объекты разбросаны по всей куче (heap fragmentation). Каждый поток при обращении к объекту промахивается мимо L1/L2 кэша процессора и обращается к медленной оперативной памяти (DRAM).
2. **False Sharing:** Если разные потоки пишут результаты в соседние элементы одного массива или структуры данных, расположенные в пределах одной 64-байтной строки кэша (Cache Line), ядра процессора вынуждены непрерывно инвалидировать кэши друг друга по протоколу когерентности (MESI), снижая скорость вычислений в десятки раз.

> **Senior Insight:** Для достижения максимальной производительности в CPU-Bound задачах параллельные стримы должны использовать примитивные массивы (`long[]`, `int[]`) или примитивные стримы (`LongStream`, `IntStream`), обеспечивающие последовательную упаковку данных в памяти (Memory Locality).

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> «Использовать `parallelStream` следует только для CPU-интенсивных вычислений над большими объемами данных при условии выполнения правила $N \times Q > 10\,000$ и использования эффективных структур данных (`ArrayList`, массивы, числовые диапазоны). Категорически запрещено использовать `parallelStream` для I/O-операций или внутри нагруженных веб-серверов, так как он использует общий `ForkJoinPool.commonPool()` и создает конкуренцию за ресурсы между клиентскими запросами. Для I/O в современной Java 21 стандартом являются Virtual Threads.»

### Чек-лист: включать ли `parallelStream`?

| Вопрос проверки | Ответ ДА | Ответ НЕТ |
|---|---|---|
| Операция выполняет чтение БД, сети или файла? | 🔴 **СТОП!** Только `Virtual Threads` / CF | 🟢 Продолжаем проверку |
| Объем данных $N \times Q > 10\,000$? | 🟢 Продолжаем проверку | 🔴 **СТОП!** Обычный `stream()` быстрее |
| Источник — `ArrayList` или массив? | 🟢 Продолжаем проверку | 🟡 Осторожно: `LinkedList` замедлит код |
| В конвейере есть `sorted()` или `distinct()`? | 🟡 Осторожно: барьер синхронизации | 🟢 Отлично (stateless операции) |
| Сервер уже нагружен тысячами HTTP-запросов? | 🔴 **СТОП!** Пул потоков будет истощен | 🟢 Включаем `parallelStream()` |

### Топ-4 каверзных вопроса на интервью

#### 1. Почему добавление `.parallel()` к обработке входящего запроса в Spring Boot контроллере часто замедляет сервер?
- Веб-сервер (Tomcat) уже параллелит нагрузку, выделяя поток на каждый HTTP-запрос. Если каждый запрос начнет захватывать потоки из общего `ForkJoinPool.commonPool()`, возникнет острая конкуренция за процессорные ядра, постоянные переключения контекста и задержки в очереди пула. В итоге латентность всех запросов возрастает, а пропускная способность сервиса падает.

#### 2. Как аппаратные кэши CPU (L1/L2/L3) влияют на выбор между `parallelStream()` и обычным циклом?
- Последовательный цикл обходит данные строго по порядку, что позволяет аппаратному блоку упреждающей выборки процессора (Hardware Prefetcher) заранее подгружать данные в L1/L2 кэши.
- Параллельный стрим делит память на чанки между ядрами. Если элементы — это ссылочные объекты в куче, каждое ядро читает случайные адреса памяти, вызывая постоянные Cache Misses. В таких случаях простой последовательный цикл по примитивному массиву может оказаться быстрее параллельного стрима по списку объектов.

#### 3. В каких случаях операция `parallelStream().sorted()` может исчерпать память (OOM)?
- `sorted()` является операцией с состоянием (stateful) и требует накопления всех элементов стрима перед их упорядочиванием. В параллельном стриме данные накапливаются в многопоточные буферы, после чего выполняется параллельная сортировка слиянием (Parallel Merge Sort), требующая дополнительной памяти под вспомогательные массивы. При обработке огромных коллекций это удваивает потребление heap и может привести к `OutOfMemoryError`.

#### 4. Когда при $N = 10\,000$ параллельный стрим по `ArrayList<Integer>` проигрывает последовательному циклу по `int[]`?
- Почти всегда. В `ArrayList<Integer>` каждый элемент — это объект-обертка (24 байта в куче с указателем). Затраты на разыменование ссылок, промахи кэша и автораспаковку (unboxing) многократно превышают выгоду от параллелизма, а накладные расходы на координацию потоков `ForkJoinPool` делают параллельный код в 2–5 раз медленнее, чем векторизованный последовательный цикл по непрерывному массиву примитивов `int[]`.

---

### Типичные ошибки и Red Flags
- 🚩 Использование `parallelStream()` для выполнения сетевых или дисковых вызовов (HTTP клиент, JDBC).
- 🚩 Включение `.parallel()` «на всякий случай» без профилирования и проверки через JMH-бенчмарки.
- 🚩 Параллельная обработка `LinkedList` или бесконечных генераторов `Stream.iterate()`.
- 🚩 Использование операций с зависимостью от порядка (`findFirst()`, `limit()`) в параллельном стриме без острой необходимости (вместо них следует использовать `findAny()`).
