# Что такое паттерны проектирования?

---

## 🟢 Junior Level

**Паттерн (шаблон) проектирования** — это проверенное временем, повторяемое и задокументированное архитектурное решение типовой задачи в объектно-ориентированном программировании.

Паттерн — это **не готовая библиотека** и **не готовый кусок кода**, который можно скопировать через `Ctrl+C / Ctrl+V`. Это архитектурная концепция, стратегия и чертёж, описывающий, как выстроить взаимосвязи между классами и интерфейсами для достижения гибкости и сопровождаемости.

```mermaid
graph LR
    A["Типовая проблема проектирования"] --> B["Паттерн (Архитектурный чертёж)"]
    B --> C["Адаптация под контекст задачи"]
    C --> D["Гибкий, расширяемый код"]
```

### Наглядная бытовая аналогия

Представьте строительство загородного дома:
Вам не нужно заново изобретать, как устроить ленточный фундамент, двускатную крышу или систему отопления. Существуют стандартные инженерные проекты и регламенты (паттерны). Вы берёте типовой проект фундамента и адаптируете его под размеры и тип грунта вашего конкретного участка.

### Зачем нужны паттерны:
1. **Экономия времени:** Вы используете готовое, отлаженное сообществом решение, экономя часы на проектировании структуры.
2. **Единый словарь команды (Ubiquitous Language):** Вместо объяснения на полчаса «давайте сделаем класс с приватным конструктором и статической точкой доступа» разработчик говорит: «Используем Singleton» или «Обернём в Decorator».
3. **Предотвращение архитектурных ошибок:** Паттерны построены на базовых принципах объектно-ориентированного дизайна (SOLID).

### Простейший пример (Паттерн Singleton)

```java
// Классический Singleton: гарантирует наличие ровно одного экземпляра класса
public class DatabaseConnectionPool {

    // Статическое поле, хранящее единственный экземпляр
    private static final DatabaseConnectionPool INSTANCE = new DatabaseConnectionPool();

    // Приватный конструктор запрещает создание объекта через 'new' снаружи
    private DatabaseConnectionPool() {
        System.out.println("Инициализация пула соединений...");
    }

    // Глобальная статическая точка доступа
    public static DatabaseConnectionPool getInstance() {
        return INSTANCE;
    }
}
```

## 🟡 Middle Level

### Иерархия уровней абстракции в разработке

В профессиональной разработке важно отличать паттерны проектирования от смежных понятий:

| Уровень абстракции | Описание | Примеры в экосистеме Java |
|---|---|---|
| **Идиомы языка (Idioms)** | Специфичные для конкретного языка синтаксические конструкции | `try-with-resources`, `Optional`, Records, Pattern Matching |
| **GoF-паттерны** | Паттерны проектирования классов и их взаимодействия (Gang of Four) | `Strategy`, `Decorator`, `Observer`, `Factory Method` |
| **Enterprise-паттерны** | Архитектура взаимодействия с базами данных и слоями бизнес-логики | `Repository`, `Unit of Work`, `Data Mapper`, `DTO` |
| **Cloud / Distributed** | Паттерны распределённых систем и микросервисов | `Circuit Breaker`, `Saga`, `CQRS`, `Outbox`, `Sidecar` |

> [!NOTE]
> **GoF (Gang of Four — «Банда четырёх»):** Эрих Гамма, Ричард Хелм, Ральф Джонсон и Джон Влиссидес — авторы фундаментальной книги *«Design Patterns: Elements of Reusable Object-Oriented Software»* (1994), описавшие 23 классических паттерна.

### 3 классические категории паттернов GoF

1. **Порождающие (Creational):** Управляют процессами создания объектов, изолируя клиентский код от деталей инстанцирования (`Singleton`, `Factory Method`, `Abstract Factory`, `Builder`, `Prototype`).
2. **Структурные (Structural):** Определяют способы компоновки классов и объектов в более крупные и гибкие структуры (`Adapter`, `Decorator`, `Proxy`, `Facade`, `Composite`, `Bridge`, `Flyweight`).
3. **Поведенческие (Behavioral):** Организуют эффективное и гибкое распределение обязанностей и алгоритмов между взаимодействующими объектами (`Strategy`, `Observer`, `Command`, `Template Method`, `Iterator`, `State`, `Chain of Responsibility`, `Visitor`, `Mediator`, `Memento`).

### Паттерны GoF внутри стандартной библиотеки Java (JDK)

Паттерны окружают Java-разработчика повседневно прямо в `java.base`:

```java
// 1. Decorator: каскадное оборачивание потоков ввода-вывода
InputStream is = new BufferedInputStream(new FileInputStream("data.bin"));

// 2. Factory Method: статические фабричные методы коллекций
List<String> list = List.of("A", "B", "C");

// 3. Strategy: передача алгоритма сравнения
Collections.sort(users, Comparator.comparing(User::getAge));

// 4. Adapter: адаптация массива к интерфейсу List
List<String> adaptedList = Arrays.asList("Alpha", "Beta");

// 5. Prototype: метод clone() и интерфейс Cloneable
```

### Эволюция паттернов в Modern Java (Java 8–21+)

С появлением лямбда-выражений, `Stream API`, `Records` и сопоставления с образцом (`Pattern Matching`) многие тяжеловесные паттерны GoF превратились в компактные языковые конструкции:

#### 1. Паттерн Strategy через Функциональные Интерфейсы
```java
// ❌ До Java 8: создание интерфейса и десятка классов-реализаций
// public interface DiscountStrategy { BigDecimal apply(BigDecimal price); }
// public class BlackFridayDiscount implements DiscountStrategy { ... }

// ✅ Modern Java: использование встроенного Function / UnaryOperator
public BigDecimal calculatePrice(BigDecimal originalPrice, UnaryOperator<BigDecimal> discountStrategy) {
    return discountStrategy.apply(originalPrice);
}

// Вызов в одну строчку через лямбду или Method Reference:
BigDecimal finalPrice = calculatePrice(price, p -> p.multiply(BigDecimal.valueOf(0.8)));
```

#### 2. Замена Visitor через Sealed Interfaces + Pattern Matching (Java 17–21)
Классический паттерн `Visitor` требовал двухсторонней диспетчеризации (`accept()` / `visit()`) для обхода гетерогенных иерархий. В Modern Java это решается через `sealed interface` и `switch`:

```java
public sealed interface OrderEvent permits OrderCreated, OrderPaid, OrderCancelled {}
public record OrderCreated(Long orderId) implements OrderEvent {}
public record OrderPaid(Long orderId, BigDecimal amount) implements OrderEvent {}
public record OrderCancelled(Long orderId, String reason) implements OrderEvent {}

// Обработка без громоздкого Visitor:
public void handle(OrderEvent event) {
    switch (event) {
        case OrderCreated c   -> System.out.println("Создан: " + c.orderId());
        case OrderPaid p      -> System.out.println("Оплачен: " + p.amount());
        case OrderCancelled r -> System.out.println("Отменён: " + r.reason());
    }
}
```

## 🔴 Senior Level

### Паттерны как инструмент следования принципам SOLID

Паттерны проектирования не возникают сами по себе — они являются практическим воплощением фундаментальных принципов проектирования:

- **Open/Closed Principle (OCP):** Паттерны `Strategy`, `Decorator` и `Observer` позволяют расширять функционал системы новыми классами без модификации существующего проверенного кода.
- **Dependency Inversion Principle (DIP):** `Factory Method`, `Abstract Factory` и `Dependency Injection` заставляют высокоуровневые модули зависеть от интерфейсов, а не от конкретных классов реализации.
- **Single Responsibility Principle (SRP):** Паттерн `Proxy` отделяет нефункциональные требования (логирование, транзакции, кэширование) от чистой бизнес-логики.

### Влияние полиморфизма паттернов на JIT-компилятор (HotSpot JVM)

При проектировании критичных к задержкам участков кода (**Hot-Path / Highload**) Senior-инженер обязан учитывать, как паттерны влияют на JIT-оптимизации JVM:

1. **Monomorphic Call Site (1 реализация):**
   Если интерфейс паттерна `Strategy` в рантайме всегда представлен только одним конкретным классом, JIT-компилятор C2 выполняет **агрессивный инлайнинг (Method Inlining)**. Накладные расходы абстракции равны абсолютному **нулю** (код функции встраивается прямо в место вызова).
2. **Bimorphic Call Site (2 реализации):**
   JIT генерирует быстрый условный переход `if (type == A) ... else if (type == B) ...`.
3. **Megamorphic Call Site (> 2 реализаций):**
   Инлайнинг невозможен. JVM вынуждена при каждом вызове осуществлять поиск адреса метода в таблице виртуальных методов (**vtable lookup**), что разрушает конвейер процессора и вызывает сброс инструкций кэша.

```
Оптимизация для Hot-Path:
Если вариантов стратегии ограниченное количество (3-5 штук), замена полиморфных классов 
на enum с switch-выражением позволяет JIT генерировать компактную таблицу переходов (tableswitch)
на уровне машинного кода, обгоняя интерфейсный вызов.
```

### Паттерны в IoC-контейнерах (Spring Framework)

В корпоративных приложениях управление паттернами практически полностью делегировано фреймворку:
- **Singleton & Prototype:** Жизненный цикл бинов по умолчанию управляется контейнером Spring IoC (`@Scope("singleton")` / `@Scope("prototype")`). Ручная реализация классического Singleton в коде считается антипаттерном, так как препятствует Unit-тестированию.
- **Dynamic Proxy:** Все аннотации `@Transactional`, `@Cacheable`, `@Async` и `@Retryable` под капотом построены на паттерне `Proxy` (реализуемом через JDK Dynamic Proxy или ByteBuddy/CGLIB).

### Опасности злоупотребления: Golden Hammer и Overengineering

```
                    ┌────────────────────────────┐
                    │      Простая задача        │
                    └─────────────┬──────────────┘
                                  │
                  ┌───────────────┴───────────────┐
                  ▼                               ▼
       Прагматичный инженер             Инженер-overengineer
       ┌────────────────────────┐       ┌─────────────────────────┐
       │ Простая функция        │       │ AbstractFactory         │
       │ + if-else              │       │ StrategyRegistry        │
       │ 15 строк кода          │       │ ValidationProxy         │
       │ Читается за 30 секунд  │       │ 12 интерфейсов и классов│
       │                        │       │ Неделя на багфиксинг    │
       └────────────────────────┘       └─────────────────────────┘
```

1. **Антипаттерн «Золотой молоток» (Golden Hammer):** Разработчик, только что прочитавший книгу GoF, пытается встроить любимый паттерн в каждую строчку кода, усложняя простейший CRUD.
2. **Увеличение уровней косвенности (Indirection Layers):** Чрезмерное дробление на фабрики и адаптеры делает Stack Trace глубиной в 60 вызовов, затрудняя отладку и понимание логики.
3. **Принцип YAGNI (You Aren't Gonna Need It):** Введение паттернов «на будущее» до того, как система реально столкнулась с вариативностью требований, считается архитектурной ошибкой.

## 🎯 Шпаргалка для интервью

### Обязательно знать (Первые 30 секунд ответа)
- **Определение:** Паттерн проектирования — это проверенное типовое архитектурное решение частой задачи в ООП, описывающее отношения между классами и интерфейсами.
- **3 группы GoF (23 паттерна):**
  1. *Порождающие (Creational):* создание объектов (`Builder`, `Factory Method`, `Singleton`).
  2. *Структурные (Structural):* композиция и адаптация (`Adapter`, `Decorator`, `Proxy`).
  3. *Поведенческие (Behavioral):* алгоритмы и взаимодействие (`Strategy`, `Observer`, `Command`).
- **Modern Java:** В версиях 8–21 многие паттерны заменены лямбдами (`Strategy`), Records и Sealed Interfaces (`Visitor`), а создание объектов отдано Spring IoC.
- **Принцип прагматизма:** Лучшая архитектура — простейшая из возможных. Не используйте паттерны там, где достаточно обычного условия `if-else`.

### Частые уточняющие вопросы на засыпку

1. **«В чём разница между архитектурным паттерном и паттерном проектирования?»**
   *Ответ:* Архитектурный паттерн (Microservices, Event-Driven, Hexagonal, CQRS) определяет глобальную структуру всей системы или распределённых сервисов. Паттерн проектирования (GoF: Strategy, Factory) решает локальные задачи взаимодействия классов внутри одного процесса.

2. **«Почему классический синглтон из книги GoF часто считают антипаттерном в Java?»**
   *Ответ:* Классический Singleton со статическим методом скрывает зависимости класса (нарушает DIP), жёстко связывает код, крайне затрудняет Unit-тестирование (невозможно подменить моком без PowerMock) и нарушает многопоточную безопасность без аккуратной синхронизации. В современном коде жизненным циклом одиночки должен управлять DI-контейнер (Spring).

3. **«Как лямбда-выражения в Java 8 упростили паттерн Strategy?»**
   *Ответ:* Раньше требовалось создавать интерфейс стратегии и отдельный класс для каждой реализации. В Java 8 любая стратегия — это объект стандартного функционального интерфейса (`Function`, `Consumer`, `Predicate`, `Supplier`), передаваемый в виде лаконичной лямбды без создания файлов классов.

4. **«Что такое мегаморфный вызов (Megamorphic Call) и как паттерны влияют на JIT?»**
   *Ответ:* Если интерфейс паттерна имеет более двух активных реализаций в месте вызова, JIT-компилятор C2 не может выполнить инлайнинг метода и вынужден делать дорогой поиск адреса в таблице виртуальных методов (vtable), что снижает пропускную способность на Hot-Path вызовах.

### Красные флаги (НЕ говорить на интервью)
- ❌ *«Я всегда проектирую систему на основе паттернов ещё до написания первой строчки кода»* — верный признак склонности к преждевременному оверинжинирингу. Паттерны вводятся в процессе рефакторинга по мере усложнения бизнес-логики.
- ❌ *«Паттерн — это готовый кусок кода или библиотека, которую можно подключить»* — паттерн является архитектурным чертежом и концепцией, а не кодом.
- ❌ *«Использование паттернов всегда ускоряет работу программы»* — паттерны добавляют уровни косвенности и полиморфные вызовы, что может приводить к небольшим накладным расходам по CPU и памяти.
