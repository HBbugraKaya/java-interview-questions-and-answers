# Можно ли использовать Record как ключ в HashMap

---

## 🟢 Junior Level

**Да, Record — один из лучших и наиболее рекомендуемых типов для ключей в `HashMap` и `HashSet`.**

### Почему Record идеален в роли ключа

Для корректной работы ключа в `HashMap` требуются два условия:
1. **Неизменяемость (Immutability)**: состояние ключа не должно меняться после помещения в карту.
2. **Согласованность `equals()` и `hashCode()`**: одинаковые по значению ключи обязаны возвращать одинаковый хеш-код и быть равны по `.equals()`.

`Record` удовлетворяет обоим требованиям «из коробки»:
- Все поля неявно являются `private final`.
- Методы `equals()` и `hashCode()` компилятор генерирует автоматически по всем компонентам.

```java
// Идеальный составной ключ для кэша или таблицы:
public record CacheKey(String tenantId, Long userId) {}

Map<CacheKey, UserProfile> cache = new HashMap<>();

CacheKey key1 = new CacheKey("tenant-A", 42L);
cache.put(key1, new UserProfile("Alice"));

// Поиск по новому объекту с идентичными значениями:
CacheKey key2 = new CacheKey("tenant-A", 42L);
UserProfile profile = cache.get(key2); // ✅ Успешно находит Alice!
```

## 🟡 Middle Level

### 1. Критическая ловушка: Мутабельные компоненты в ключе

Если компонент `Record` ссылается на изменяемый объект (например, `ArrayList` или `Date`), иммутабельность нарушается, что ведет к **катастрофическому сбою `HashMap`**:

```java
public record BrokenKey(String tenant, List<String> tags) {}

List<String> tags = new ArrayList<>(List.of("vip"));
BrokenKey key = new BrokenKey("org1", tags);

Map<BrokenKey, String> map = new HashMap<>();
map.put(key, "VIP Account");

// 💣 Опасная мутация: меняем список после добавления в HashMap!
tags.add("blocked");

// Хеш-код ключа изменился!
// map.get(key) вернет null, а значение останется в памяти навсегда (Memory Leak)!
System.out.println(map.get(key)); // null
```

#### Решение: Глубокая иммутабельность в компактном конструкторе

```java
public record SafeKey(String tenant, List<String> tags) {
    public SafeKey {
        // List.copyOf создает по-настоящему неизменяемую коллекцию
        tags = List.copyOf(tags);
    }
}
```

### 2. Массивы как компоненты ключа

> [!WARNING]
> Если компонент `Record` — массив (`byte[]`, `int[]`), автогенерированный `equals()` будет сравнивать **ссылки**, а `hashCode()` вернет адрес в памяти! Поиск в `HashMap` по новому экземпляру всегда будет возвращать `null`.

**Решение**: Переопределите `equals` и `hashCode` через методы класса `Arrays`:

```java
public record CompositeHashKey(String prefix, byte[] hash) {
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof CompositeHashKey other)) return false;
        return Objects.equals(prefix, other.prefix) && Arrays.equals(hash, other.hash);
    }

    @Override
    public int hashCode() {
        return 31 * Objects.hashCode(prefix) + Arrays.hashCode(hash);
    }
}
```

## 🔴 Senior Level

### Проблема Garbage Collector (GC Pressure) при поиске в Highload

Хотя составные ключи на Records пишутся лаконично, в высоконагруженных системах (Highload / Low Latency) возникает проблема давления на сборщик мусора:

```java
public UserProfile getProfile(String tenant, Long userId) {
    // При КАЖДОМ вызове get() в куче создается временный объект CacheKey:
    return cache.get(new CacheKey(tenant, userId));
}
```

#### Почему Escape Analysis не спасает:
1. Метод `map.get(key)` передает ссылку на объект внутрь метода `HashMap.getNode(hash, key)`.
2. В сложных реализациях коллекций C2-компилятор часто не может доказать, что объект не утекает за пределы локального фрейма (No Escape).
3. В результате на миллионы запросов в секунду создаются миллионы мелких объектов в `Eden Space`, провоцируя частые Minor GC.

**Решения в production:**
- Использование специализированных структур без аллокаций (FastUtil, Agrona primitive maps, Eclipse Collections).
- Перспектива **Project Valhalla**: превращение `Record` в Value Object (Identity-free) устранит выделение памяти в куче, так как объект будет скаляризован или передан по значению без заголовка.

### Миф о кэшировании `hashCode` внутри Record

Часто на собеседованиях кандидаты предлагают: *«Если расчет хеш-кода для большого Record дорог, давайте закэшируем его в приватном поле, как в String»*:

```java
// ❌ ТАК НАПИСАТЬ НЕЛЬЗЯ! НЕ СКОМПИЛИРУЕТСЯ!
public record HeavyKey(String a, String b, String c) {
    // private int hash; // ❌ Ошибка компиляции: non-static field not allowed in record
}
```
Спецификация языка Java **категорически запрещает** объявление нестатических полей внутри тела `record`. Если вам действительно необходимо кэшировать хеш-код, вы **обязаны использовать обычный класс**, а не `Record`.

## 4 Tricky Questions

### 1. Почему Record считается идеальным составным ключом для HashMap, и какую частую ошибку с кэшированием хеш-кода допускают на собеседованиях?
**Ответ:** 
Record решает главную проблему составных ключей в Java: избавляет от необходимости писать громоздкие классы с ручным `equals`/`hashCode` или соединять строки через разделители (`tenant + ":" + id`), что медленно и небезопасно. 

Типичная ошибка кандидатов: предложение объявить поле-кэш `private int hash;` для оптимизации повторных вызовов `hashCode()`. В `Record` **запрещены любые нестатические поля экземпляра**, поэтому кэшировать хеш внутри самого объекта физически невозможно. Для кэширования хеша придется использовать классический `final class`.

### 2. Что произойдет, если вставить в `HashMap` объект `record Key(String prefix, byte[] salt)` и попытаться получить значение по новому рекорду с теми же строкой и байтами?
**Ответ:** 
Вызов `map.get(new Key(prefix, saltCopy))` **вернет `null`**! 

Автогенерированный компилятором `equals()` вызывает `Objects.equals()`, который для массивов проверяет равенство ссылок (`==`). У двух разных экземпляров `Key` массивы `salt` будут лежать по разным адресам в куче. Их `equals()` вернет `false`, а автосгенерированный `hashCode()` выдаст разные значения. Для использования записи с массивами в качестве ключа необходимо явно переопределить `equals()` и `hashCode()` с помощью `Arrays.equals()` и `Arrays.hashCode()`.

### 3. Что произойдет, если компонент Record является мутабельным объектом (например, `ArrayList`), и его содержимое изменится после добавления в `HashMap`?
**Ответ:** 
Произойдет классический эффект **«потери ключа» (Lost Key)**:
1. При добавлении `map.put(key, value)` элемент размещается в корзине (bucket), вычисленной по исходному `hashCode()`.
2. После мутации списка внутри рекорда значение `key.hashCode()` изменяется.
3. При попытке найти объект через `map.get(key)` хэш-мапа вычисляет новый индекс корзины и ищет элемент там, где его нет. Метод вернет `null`.
4. Старая запись навсегда останется заблокированной в исходной корзине, приводя к скрытой утечке памяти. Для предотвращения этого в компактном конструкторе всегда следует вызывать `List.copyOf()`.

### 4. Создает ли использование конструкции `cache.get(new MyRecordKey(a, b))` нагрузку на Garbage Collector в highload-системах?
**Ответ:** 
**Да, создает ощутимое давление на память (GC Pressure).** 

При каждом поиске в карте создается новый экземпляр `MyRecordKey`. Хотя объект живет недолго, JVM Escape Analysis не всегда способен скаляризовать его (разложить на стеке), так как ссылка на ключ передается в глубокую цепочку вызовов `HashMap.getNode()`. При темпе в сотни тысяч запросов в секунду это вызывает стремительное засорение области `Young Generation (Eden)` и частые паузы на сборку мусора. 

В высокопроизводительных сервисах до прихода Project Valhalla такие составные ключи заменяют пулингом, плоскими примитивными мапами (LongLongMap) или составными примитивными битовыми ключами.

## 🎯 Шпаргалка для интервью

### Главное о Record как ключе в HashMap

- **Плюсы**: Поля неизменяемы (`final`), `equals` и `hashCode` сгенерированы автоматически и строго согласованы.
- **Главная угроза**: Мутабельные коллекции и массивы. Всегда применяйте `List.copyOf()` / `Set.copyOf()` в компактном конструкторе.
- **Массивы**: Автогенерация не работает! Обязательно переопределять `equals` и `hashCode` через `Arrays.equals` / `Arrays.hashCode`.
- **Кэширование хеша**: Невозможно добавить поле `hash` в `Record`. Для кэширования хеша используйте обычный класс.
- **Highload**: Постоянный `new Key(...)` в цикле создает нагрузку на GC (ждет Project Valhalla для скаляризации).
