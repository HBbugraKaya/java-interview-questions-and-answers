# Какие инструменты помогают анализировать память

---

## 🟢 Junior Level

Для анализа памяти в Java существует широкий спектр инструментов: от стандартных консольных утилит JDK до мощных графических анализаторов дампов и профилировщиков реального времени.

### Основные категории инструментов

| Инструмент | Тип | Назначение | Когда применяется |
| :--- | :--- | :--- | :--- |
| **Eclipse MAT** | GUI (Десктоп) | Глубокий оффлайн-анализ дампов памяти (HPROF) | После `OutOfMemoryError` или для поиска утечек памяти. |
| **VisualVM** | GUI (Десктоп) | Мониторинг в реальном времени, легковесное профилирование | Локальная разработка и тестовые стенды. |
| **`jcmd`** | CLI (Консоль JDK) | Универсальный интерфейс управления и диагностики JVM | Production-серверы (минимальное влияние). |
| **JFR / JMC** | Профайлер (JDK) | Сверхлегковесная телеметрия событий JVM (< 1% оверхеда) | Непрерывный мониторинг и трассировка под боевой нагрузкой. |
| **JProfiler / YourKit** | GUI (Коммерческий) | Интерактивное профилирование аллокаций и потоков | Глубокая оптимизация кода на этапе разработки. |

### Базовый сценарий: Eclipse MAT
**Eclipse Memory Analyzer (MAT)** — ведущий бесплатный инструмент с открытым исходным кодом для анализа файлов дампов кучи (`.hprof`):
- Вычисляет **Retained Heap** (сколько памяти реально освободится при удалении объекта);
- Строит **Dominator Tree** (дерево доминаторов владения памятью);
- Предоставляет автоматический отчет **Leak Suspects Report**, самостоятельно определяющий подозрительные компоненты с вероятностью утечки.

## 🟡 Middle Level

### 1. Универсальная консольная утилита `jcmd`

Начиная с Java 7/8, утилита `jcmd` является официальным рекомендуемым стандартом командной строки HotSpot, заменившим устаревшие и нестабильные инструменты (`jmap`, `jinfo`).

```bash
# Получить список доступных Java-процессов
jcmd -l

# 1. Быстрая гистограмма классов (пауза доли секунды)
# Показывает топ классов по числу объектов и объёму памяти
jcmd <pid> GC.class_histogram

# 2. Снятие полного дампа кучи в файл
jcmd <pid> GC.heap_dump /dumps/heap_analysis.hprof

# 3. Сводка потребления Native Memory (требует -XX:NativeMemoryTracking)
jcmd <pid> VM.native_memory summary

# 4. Анализ метаданных классов в Metaspace
jcmd <pid> VM.metaspace show-loaders
```

> [!TIP]
> **Почему `GC.class_histogram` безопаснее `GC.heap_dump`?**
> Гистограмма классов обходит заголовки объектов в памяти и агрегирует счетчики за очень короткую паузу (обычно < 1 сек), не выполняя сериализацию графа ссылок на диск. Это идеальный первый шаг экспресс-диагностики прямо на боевом сервере.

### 2. Java Flight Recorder (JFR) и JDK Mission Control (JMC)

**JFR** встроен непосредственно в ядро HotSpot JVM. Он собирает детальные метрики виртуальной машины с аппаратной поддержкой и накладными расходами процессора менее 1%:
- **Событие `jdk.OldObjectSample`:** алгоритмическая выборка долгоживущих объектов старшего поколения, позволяющая отслеживать путь до GC Roots и стек-трейс аллокации в боевом проде без остановки JVM;
- **Allocation Profiling:** фиксация темпа аллокаций внутри TLAB (*Thread Local Allocation Buffer*) и вне TLAB (выделение крупных объектов напрямую в кучу).

```bash
# Запуск записи JFR длительностью 15 минут в production:
jcmd <pid> JFR.start name=Profile memory=100m duration=15m filename=recording.jfr settings=profile
```

Полученный `.jfr` файл открывается в **JDK Mission Control (JMC)**, где на графиках отображаются утечки памяти, фазы сборки мусора и время пауз.

### 3. Сравнение подходов к профилированию

```
+-------------------------------------------------------------------------+
|                  Методы анализа памяти приложения                       |
+-------------------------------------------------------------------------+
| 1. Live Sampling / Instrumentation (JProfiler, YourKit, VisualVM)       |
|    - Перехват каждой аллокации (Bytecode instrumentation / BCI)         |
|    - Замедляет работу приложения в 2-10 раз (неприменимо в Production)  |
+-------------------------------------------------------------------------+
| 2. Event-based / Asynchronous Sampling (JFR, Async-profiler)            |
|    - Статистическая выборка аллокаций через perf_events / safepoints    |
|    - Накладные расходы < 1-2% (безопасно для Production)                |
+-------------------------------------------------------------------------+
| 3. Post-Mortem Snapshot (Eclipse MAT)                                   |
|    - Статический снимок (Dump) замороженного состояния кучи             |
|    - Требует STW-паузы при создании, но даёт 100% точность графа ссылок |
+-------------------------------------------------------------------------+
```

## 🔴 Senior Level

### 1. Анализ внекучевой памяти: Native Memory Tracking (NMT)

Если метрики Java Heap стабильны, но физическое потребление процесса (RSS в Linux) растет и грозит OOM Killer, проблема кроется в **Native Memory** (Off-Heap).

Для включения NMT JVM запускается с флагом:
```bash
-XX:NativeMemoryTracking=summary  # или =detail для точных адресов аллокаций
```

#### Методология поиска нативных утечек через NMT Baseline & Diff:
```bash
# Шаг 1: Фиксируем базовую точку после старта и прогрева сервиса
jcmd <pid> VM.native_memory baseline

# Шаг 2: Выполняем нагрузку или ожидаем деградации памяти

# Шаг 3: Получаем дельту (что именно выросло в нативной памяти)
jcmd <pid> VM.native_memory detail.diff
```

Пример вывода дельты:
```
Total: reserved=5840MB +120MB, committed=3410MB +85MB
-                 Java Heap (reserved=4096MB, committed=2048MB)
-                    Class (reserved=1085MB +5MB, committed=65MB +3MB)
-                   Thread (reserved=120MB +45MB, committed=120MB +45MB)  <-- Утечка: +45 новых потоков!
-            Internal (NIO) (reserved=250MB +60MB, committed=250MB +60MB) <-- Утечка DirectByteBuffer!
```

### 2. Async-Profiler для отслеживания аллокаций памяти

**Async-profiler** — высокопроизводительный низкоуровневый профилировщик для Linux и macOS, не страдающий от проблемы *Safepoint Bias* (искажение данных из-за сбора метрик только в точках останова).

Он умеет профилировать не только процессор, но и аллокации памяти:
```bash
# Профилирование аллокаций в Java Heap (генерация FlameGraph):
./asprof -d 60 -e alloc -f alloc_flamegraph.html <pid>

# Профилирование нативных аллокаций malloc() ядра C/C++:
./asprof -d 60 -e malloc -f native_malloc.html <pid>
```
Пламенные графики (*Flame Graphs*) аллокаций мгновенно показывают методы, создающие больше всего временных объектов и нагружающие Garbage Collector.

### 3. Интерактивная диагностика через Arthas (Alibaba)

**Arthas** позволяет подключаться к работающему production-процессу без изменения конфигурации и флагов запуска:

```bash
# Запуск консоли Arthas
java -jar arthas-boot.jar

# В интерактивной консоли:
[arthas]$ dashboard         # Монитор состояния памяти (Heap, Non-Heap, GC, Threads)
[arthas]$ memory            # Детальная разбивка пулов памяти JVM
[arthas]$ vmtool --action getInstances --className com.example.OrderService --limit 5
[arthas]$ heapdump /tmp/dump.hprof --live  # Снять дамп только живых объектов
```

### 4. Опасности и риски использования инструментов

1. **`GC.heap_dump` на терабайтных кучах:** Переводит все потоки приложения в Safepoint на десятки секунд. Для высоконагруженных узлов узел необходимо предварительно отключать от балансировщика нагрузки (*traffic drain*).
2. **Флаг `-XX:NativeMemoryTracking=detail`:** Увеличивает задержки системных вызовов `malloc` и `mmap`, создавая накладные расходы 5–10% CPU. В production для постоянной работы рекомендуется использовать только уровень `summary`.
3. **`jstack -F` или `jmap -F`:** Использование принудительного флага `-F` цепляется к процессу через системный отладчик `ptrace`, что при сбое может полностью зависнуть или аварийно завершить JVM процесс.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ для собеседования
> «Инструменты анализа памяти делятся на три ключевые группы:
> 1) **CLI-инструменты JVM** (`jcmd`) для оперативной телеметрии на сервере: снятия гистограммы классов (`GC.class_histogram`), отслеживания нативной памяти (NMT) и снятия дампов;
> 2) **Оффлайн-анализаторы дампов** (Eclipse MAT), используемые для глубокого расследования причин OOME через Dominator Tree, вычисление Retained Heap и анализ путей к GC Roots;
> 3) **Низкооверхедные профайлеры** (JFR/JMC и Async-profiler), позволяющие безопасно отслеживать аллокации и утечки (`jdk.OldObjectSample`) непосредственно под нагрузкой в боевом production с накладными расходами менее 1%».

### Вопросы повышенной сложности с ответами

1. **Почему `jcmd <pid> GC.class_histogram` гораздо безопаснее запускать в production, чем `jcmd <pid> GC.heap_dump`?**
   *Ответ:* Команда `GC.class_histogram` лишь быстро сканирует заголовки объектов в памяти и агрегирует количество экземпляров и их размер по типам. Пауза Safepoint при этом обычно не превышает сотен миллисекунд. Напротив, `GC.heap_dump` выполняет полную сериализацию сложного графа объектов со всеми ссылками и примитивными полями на диск. Для кучи в десятки гигабайт запись на диск блокирует приложение на десятки секунд, что гарантированно приводит к таймаутам клиентов и сбою health-check проверок.

2. **Как найти утечку нативной памяти (Off-Heap / Direct Memory), если Heap Dump показывает, что куча почти пуста?**
   *Ответ:* В кучевом дампе нативная память не отображается. Для поиска off-heap утечек используют:
   - Флаг `-XX:NativeMemoryTracking=summary` (или `detail`) и команду `jcmd <pid> VM.native_memory detail.diff`, которая наглядно отобразит рост секций `Internal (Direct buffers)`, `Thread (стеки)`, `Class` или `GC`;
   - Профилирование системных вызовов аллокации памяти с помощью `async-profiler` с параметром `-e malloc`;
   - Анализ системных инструментов операционной системы: `pmap -x <pid>` и утилиты трассировки памяти glibc (jemalloc / jemalloc profiling).

3. **Чем инструмент `jcmd` принципиально превосходит старый `jmap`?**
   *Ответ:* `jmap` разрабатывался как отдельная сервисная утилита (`Serviceability Agent`), которая часто требовала совпадения точных версий бинарников, при сбоях могла подвесить процесс сигналом ptrace и не поддерживала динамическое управление новыми подсистемами HotSpot. `jcmd` — это единая консольная точка входа, работающая через официальный JVM Attach API. `jcmd` поддерживает десятки подсистем (управление GC, JFR, NMT, компилятором JIT, потоками), активно развивается и является рекомендованным стандартом Oracle и OpenJDK.

4. **Как механизм JFR `OldObjectSample` помогает находить утечки памяти без снятия тяжелого Heap Dump?**
   *Ответ:* JFR непрерывно поддерживает кольцевой буфер объектов-выборки (обычно 256–512 экземпляров), аллоцированных приложением. Если эти объекты переживают множество циклов сборок мусора и продвигаются в старшее поколение (Tenured), JFR фиксирует стек вызова момента их создания и динамически отслеживает цепочку ссылок до GC Roots. Инженер в JMC видит реальный путь удержания и точную строку кода, создавшую утекший объект, без необходимости замораживать приложение и сбрасывать десятки гигабайт на диск.

### Типичные ошибки и Red Flags
- ❌ **Снимать полный Heap Dump на терабайтной куче боевого сервиса в пик нагрузки.** (Red Flag: гарантированный отказ сервиса по таймаутам и падение пода по Liveness Probe).
- ❌ **Использовать тяжелое профилирование с инструментацией байткода (Live BCI profiling) в боевом production.** (Накладные расходы могут замедлить приложение в 5–10 раз).
- ❌ **Пытаться искать нативные утечки (Direct ByteBuffer / Netty / JNI) в Eclipse MAT.** (В дампе кучи видны только 64-байтные Java-обёртки `DirectByteBuffer`, но не сами гигабайты выделенной нативной памяти).
