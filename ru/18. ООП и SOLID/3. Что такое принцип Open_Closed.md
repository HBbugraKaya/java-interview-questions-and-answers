# Что такое принцип Open-Closed

---

## 🟢 Junior Level

**Принцип открытости-закрытости (Open-Closed Principle, OCP)** — это второй принцип SOLID, сформулированный следующим правилом:
> **"Программные сущности (классы, модули, функции) должны быть открыты для расширения, но закрыты для модификации."**

### Что это означает простыми словами
- **Закрыты для модификации:** стабильный, оттестированный и работающий в продакшене код не должен редактироваться каждый раз, когда бизнесу требуется новая фича. Внесение изменений в проверенный код порождает риск регрессионных ошибок в уже работающем функционале.
- **Открыты для расширения:** система спроектирована так, что новое поведение добавляется путем написания *нового* кода (новых классов или модулей), подключаемых к существующему каркасу через абстракции.

### Житейская аналогия
Смартфон с разъемом USB Type-C:
- Телефон **закрыт для модификации**: чтобы послушать музыку или скопировать файлы, вам не нужно разбирать корпус и перепаивать материнскую плату.
- Телефон **открыт для расширения**: благодаря стандартизированному интерфейсу USB вы можете подключить зарядное устройство, флешку, внешнюю клавиатуру или ЦАП-наушники.

### Пример нарушения OCP (Антипаттерн)

В коде ниже для добавления каждого нового типа нотификации приходится модифицировать метод `sendNotification`:

```java
public class NotificationService {
    public void sendNotification(String type, String message, String recipient) {
        if ("EMAIL".equalsIgnoreCase(type)) {
            // Логика отправки Email через SMTP
            System.out.println("Sending Email to " + recipient + ": " + message);
        } else if ("SMS".equalsIgnoreCase(type)) {
            // Логика отправки SMS через SMPP-шлюз
            System.out.println("Sending SMS to " + recipient + ": " + message);
        } else if ("TELEGRAM".equalsIgnoreCase(type)) {
            // Логика отправки Telegram через Bot API
            System.out.println("Sending Telegram to " + recipient + ": " + message);
        } else {
            throw new IllegalArgumentException("Unsupported channel: " + type);
        }
    }
}
```

**В чем проблема:**
1. При добавлении Push-уведомлений разработчик вынужден редактировать класс `NotificationService`.
2. Есть риск случайно повредить логику отправки Email или SMS.
3. Приходится заново тестировать весь класс и все существующие сценарии.
4. Метод разрастается в гигантский спагетти-блок (нарушение SRP и OCP).

### Соблюдение OCP через полиморфизм

Выделяем контракт (интерфейс) и создаем независимые реализации:

```java
// 1. Стабильная абстракция
public interface NotificationChannel {
    boolean supports(String channelType);
    void send(String recipient, String message);
}

// 2. Реализация для Email
public class EmailNotificationChannel implements NotificationChannel {
    @Override
    public boolean supports(String channelType) {
        return "EMAIL".equalsIgnoreCase(channelType);
    }

    @Override
    public void send(String recipient, String message) {
        System.out.println("Sending Email to " + recipient + ": " + message);
    }
}

// 3. Клиентский сервис — ЗАКРЫТ для модификации
public class NotificationService {
    private final List<NotificationChannel> channels;

    public NotificationService(List<NotificationChannel> channels) {
        this.channels = List.copyOf(channels);
    }

    public void sendNotification(String channelType, String message, String recipient) {
        NotificationChannel targetChannel = channels.stream()
                .filter(ch -> ch.supports(channelType))
                .findFirst()
                .orElseThrow(() -> new IllegalArgumentException("Unsupported channel: " + channelType));

        targetChannel.send(recipient, message);
    }
}
```

Чтобы добавить `TelegramNotificationChannel`, мы создаем **новый класс**, реализующий `NotificationChannel`. Класс `NotificationService` не изменяется ни на строчку.

## 🟡 Middle Level

### Архитектурные паттерны реализации OCP

Для соблюдения OCP в объектно-ориентированном коде применяются фундаментальные паттерны GoF:

1. **Strategy (Стратегия):** подмена семейств алгоритмов через общий интерфейс (как в примере с каналами нотификаций выше).
2. **Template Method (Шаблонный метод):** инвариантный скелет алгоритма определяется в базовом классе, а вариативные шаги переопределяются в наследниках.
3. **Decorator (Декоратор):** расширение функциональности объекта на лету (например, обертка `BufferedInputStream` вокруг `FileInputStream` в `java.io`).
4. **Observer / Event Listener (Слушатель событий):** новые модули подписываются на события системы, не затрагивая генератор событий (`ApplicationEventPublisher` в Spring).

### OCP в Spring Framework: Dependency Injection & Plugins

В экосистеме Spring Framework принцип OCP является основой архитектуры. Spring автоматически инжектирует все зарегистрированные бины заданного интерфейса в коллекцию:

```java
@Service
public class OrderProcessingService {

    // Spring собирает все бины OrderValidator, зарегистрированные в контексте
    private final List<OrderValidator> validators;
    private final Map<String, PaymentProcessor> paymentProcessors;

    public OrderProcessingService(List<OrderValidator> validators,
                                  Map<String, PaymentProcessor> paymentProcessors) {
        this.validators = validators;
        this.paymentProcessors = paymentProcessors;
    }

    public void processOrder(Order order, String paymentMethod) {
        // Выполняем все проверки (новые валидаторы подключаются без правок сервиса)
        for (OrderValidator validator : validators) {
            validator.validate(order);
        }

        PaymentProcessor processor = paymentProcessors.get(paymentMethod);
        if (processor == null) {
            throw new UnsupportedPaymentMethodException(paymentMethod);
        }
        processor.pay(order);
    }
}
```

Добавление проверки на санкционные ограничения (`SanctionsOrderValidator`) требует лишь добавления класса с аннотацией `@Component`.

### Expression Problem: OCP vs Sealed Hierarchies (Java 21+)

В современной Java (начиная с Java 17/21) появился мощный механизм **Sealed Classes / Interfaces** и **Pattern Matching for `switch`**. Это возвращает нас к фундаментальной дилемме компьютерных наук — **Проблеме Выражений (Expression Problem)**:

| Измерение расширения | Традиционный полиморфизм OCP (Strategy / Interface) | Алгебраические типы данных (Sealed Interface + Pattern Matching) |
|---|---|---|
| **Добавление нового типа (данных)** | **Легко (OCP соблюден):** создается новый класс-реализация без изменения существующих классов. | **Сложно:** добавление подтипа в `sealed`-иерархию требует обновления всех `switch`-выражений в коде. |
| **Добавление новой операции (поведения)** | **Сложно (OCP нарушается):** добавление нового метода в интерфейс требует модификации всех существующих классов-реализаций. | **Легко:** пишется новая функция со `switch`, не затрагивая сами типы данных. |

#### Пример Sealed Pattern Matching:
```java
public sealed interface OrderEvent permits OrderCreated, OrderCancelled, OrderShipped {}

public record OrderCreated(UUID orderId, BigDecimal amount) implements OrderEvent {}
public record OrderCancelled(UUID orderId, String reason) implements OrderEvent {}
public record OrderShipped(UUID orderId, String trackingNumber) implements OrderEvent {}

// Новая операция добавляется без изменения типов данных:
public class AuditLogService {
    public String describeEvent(OrderEvent event) {
        return switch (event) {
            case OrderCreated created -> "Created order: " + created.orderId();
            case OrderCancelled cancelled -> "Cancelled order: " + cancelled.orderId();
            case OrderShipped shipped -> "Shipped order: " + shipped.orderId();
            // Компилятор проверяет exhaustive coverage: ветка default не нужна!
        };
    }
}
```

**Вывод для Middle/Senior:** использование `switch` по `sealed`-типам **не является антипаттерном OCP**. Это осознанный выбор дизайна: если набор типов фиксирован предметной областью, но над ними постоянно добавляются новые операции — `sealed`-иерархия предпочтительнее классического полиморфизма.

## 🔴 Senior Level

### Историческая эволюция: Bertrand Meyer vs Robert C. Martin

1. **Формулировка Бертрана Мейера (1988, "Object-Oriented Software Construction"):**
   - Мейер формулировал OCP в терминах **наследования implementation-классов**.
   - Класс закрыт, когда он скомпилирован и положен в библиотеку.
   - Класс открыт, так как новый класс может унаследовать его и переопределить методы.
   - *Проблема подхода Мейера:* Наследование создает жесткое зацепление (tight coupling). Изменение приватных деталей предка или побочные эффекты ломают потомков (Fragile Base Class Problem).

2. **Полиморфный OCP Роберта Мартина (Uncle Bob, 1996+):**
   - Переориентация с наследования реализаций на **полиморфизм интерфейсов** и **инверсию зависимостей (DIP)**.
   - Модули зависят исключительно от стабильных абстракций. Расширение достигается через добавление новых реализаций интерфейса или композицию (декораторы, стратегии).

### Низкоуровневое влияние OCP на JVM и HotSpot JIT (C2)

Хотя OCP идеален на уровне архитектуры, на уровне виртуальной машины полиморфизм имеет конкретную цену:

1. **Monomorphic Call Site (1 реализация):**
   - JIT фиксирует ровно один целевой класс метода (`invokevirtual` / `invokeinterface`).
   - Применяется агрессивный **Inlining** (подстановка тела метода в вызывающий код).
   - После инлайнинга срабатывает **Escape Analysis** (скалярная замена объектов, размещение на стеке вместо кучи, устранение блокировок).
   - Скорость вызова: ~1 ns (прямой переход CPU).

2. **Bimorphic Call Site (2 реализации):**
   - JIT строит быструю проверку: `if (obj.klass == ImplA) ImplA.method() else ImplB.method()`.
   - Обе ветки могут быть заинлайнены компилятором C2.

3. **Megamorphic Call Site (> 2 реализаций):**
   - Inline Cache отключается, JIT деоптимизирует вызов.
   - Для `invokevirtual` используется поиск по таблице виртуальных методов (**vtable**).
   - Для `invokeinterface` используется поиск по интерфейсной таблице (**itable**) или переход через Stub (**Stub calling sequence**).
   - **Последствия:** Инлайнинг невозможен! Escape Analysis не срабатывает. Скрытый оверхед: косвенный переход по указателю функции вызывает сброс конвейера команд процессора (CPU branch target misprediction) и cache miss по L1/L2 инструкций (штраф ~15–30 тактов процессора на вызов).

> **В Highload-системах (Ultra-Low Latency, High-Frequency Trading):**
> Для критических путей (hot path) полиморфизм намеренно устраняется через `final`-классы, прямые вызовы или шаблоны code generation (на этапе компиляции), чтобы гарантировать мономорфный инлайнинг JIT.

### Архитектурные границы и blast radius (радиус поражения)

В распределенных и модульных системах OCP масштабируется с уровня классов на уровень сервисов и библиотек:

```
[UI / REST Controller] ──> (Зависит от) ──> [OrderService Interface]
                                                    ▲
                                                    │ (Реализует)
                                       [OrderServiceImpl Plugin JAR]
```

- **Стабильность API:** Интерфейс ядра объявляется в отдельном артефакте (`order-api.jar`) с минимальным количеством транзитивных зависимостей.
- **Java SPI (Service Provider Interface):** Механизм `java.util.ServiceLoader` позволяет ядру загружать реализации из classpath без единой зависимости времени компиляции на конкретные драйверы (пример: `java.sql.Driver` и реализации от PostgreSQL/MySQL).
- **Радиус поражения (Blast Radius):** Изменение в конкретном плагине/адаптере затрагивает только его собственный модуль и тесты. Время сборки (CI build time) снижается благодаря кэшированию неизменных модулей.

## 4 Tricky Questions

### 1. Что первично в OCP: наследование по Бертрану Мейеру или полиморфизм по Мартину, и почему вариант Мейера опасен?
**Ответ:**
Первична исторически формулировка Бертрана Мейера (1988), которая опиралась на наследование классов (`extends`). Однако в промышленной разработке подход Мейера признан хрупким из-за проблемы базового класса (*Fragile Base Class Problem*): изменение внутренней реализации предка способно неявно сломать инварианты наследников. Роберт Мартин переосмыслил OCP через полиморфизм абстракций (*Polymorphic OCP*), сделав во главу угла следование принципу подстановки Барбары Лисков (LSP) и предпочтение композиции перед наследованием.

### 2. Является ли оператор `switch` по `sealed interface` нарушением OCP?
**Ответ:**
С точки зрения строгой классической формулировки полиморфного OCP — да, так как добавление нового подтипа в `sealed`-иерархию требует модификации существующего `switch`. Однако с точки зрения архитектурной концепции **Expression Problem** — нет. `Sealed`-типы закрывают систему для расширения новыми типами данных, но делают ее открытой для расширения новыми операциями без изменения самих классов моделей. Это ортогональный OCP подход (функциональная декомпозиция), гарантирующий полноту покрытия (exhaustiveness check) на этапе компиляции.

### 3. Как соблюдение OCP через выделение 10 стратегий скажется на производительности JVM в Hot-Path цикле?
**Ответ:**
Вызов метода стратегии станет мегаморфным (Megamorphic call site, когда в точке вызова встречается более 2 реализаций интерфейса). JIT-компилятор HotSpot (C2) не сможет выполнить метод-инлайнинг (method inlining). В результате:
1. Вызов будет идти через поиск по `itable` (interface table) со штрафом indirect branch prediction.
2. Не сработает Escape Analysis, и любые временные объекты, создаваемые внутри стратегии, будут аллоцироваться в куче (Heap), увеличивая нагрузку на GC.
В ультра-критичных циклах hot-path применяют мономорфную диспетчеризацию, предварительную сортировку данных по типам или явную кодогенерацию.

### 4. Что делать, если новая фича требует передачи дополнительных аргументов в интерфейс, спроектированный по OCP?
**Ответ:**
Изменение сигнатуры метода в интерфейсе сломает всех существующих потребителей (нарушение закрытости). Для решения применяют:
1. **Parameter Object (Context Object):** сигнатура метода исходно принимает объект контекста (например, `ExecutionEnvironment context` или `ValidationRequest request`), поля которого можно расширять без ломки контракта.
2. **Интерфейс-наследник или маркерные интерфейсы:** введение расширенного интерфейса (например, `AdvancedNotificationChannel extends NotificationChannel`), где вызывающий код проверяет `if (channel instanceof AdvancedNotificationChannel adv)`.
3. **Default-методы в интерфейсе (Java 8+):** добавление метода с дефолтной реализацией по умолчанию, выбрасывающей `UnsupportedOperationException` или делегирующей вызов базовому методу, что сохраняет обратную совместимость для остальных реализаций.

## 🎯 Шпаргалка для интервью

**Главные тезисы (30 секунд на ответ):**
- **Суть:** Код должен расширяться добавлением новых классов, а не переписыванием старых.
- **Главные инструменты:** Интерфейсы, полиморфизм, паттерны Strategy, Template Method, Decorator, фабрики и Dependency Injection.
- **Маркер нарушения:** Разрастающиеся цепочки `if-else` / `switch` с проверками типов (`instanceof`), необходимость править старый класс при добавлении нового бизнес-сценария.
- **Sealed classes:** В Java 21+ выбор между полиморфизмом OCP и `sealed switch` определяется тем, что чаще расширяется: типы данных (выбираем полиморфизм) или операции над ними (выбираем sealed + pattern matching).

**Чего избегать (Red Flags):**
- ❌ Утверждать, что ради OCP нужно создавать интерфейс абсолютно для каждого класса с единственной реализацией (это нарушение YAGNI и спекулятивная генерализация).
- ❌ Заявлять, что OCP запрещает багфиксы или рефакторинг исходных классов (закрытость касается добавления новой бизнес-функциональности, а не исправления дефектов).
- ❌ Игнорировать накладные расходы полиморфизма (мегаморфизм JIT) в высоконагруженных сценариях.
