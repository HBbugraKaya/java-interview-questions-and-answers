# Что такое операция peek() и когда её использовать

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**`peek(Consumer<T>)`** — это промежуточная (intermediate) операция Stream API, которая применяет переданное действие к каждому проходящему элементу и **без изменений передает его дальше** вниз по конвейеру.

Официальная документация Java четко фиксирует ее единственное легитимное назначение:
> *«Этот метод существует в основном для поддержки отладки, позволяя наблюдать за элементами в процессе их прохождения через определенный этап конвейера обработки.»*

Использовать `peek()` для бизнес-логики (мутация полей, запись в БД, отправка уведомлений) **строго запрещено**, поскольку из-за ленивости Stream API, операций короткого замыкания (short-circuiting) и оптимизаций JVM вызов `peek()` может быть выполнен не для всех элементов или вообще пропущен.

---

### Пример использования для отладки на Java 21

```java
import java.util.List;

public class PeekBasicsDemo {

    public static void main(String[] args) {
        List<String> words = List.of("кот", "слон", "бегемот", "тигр");

        List<String> result = words.stream()
            .filter(w -> w.length() > 3)
            .peek(w -> System.out.println("[DEBUG After filter]: " + w))
            .map(String::toUpperCase)
            .peek(w -> System.out.println("[DEBUG After map]: " + w))
            .toList();

        System.out.println("Итог: " + result);
    }
}
```

**Вывод в консоль:**
```
[DEBUG After filter]: слон
[DEBUG After map]: СЛОН
[DEBUG After filter]: бегемот
[DEBUG After map]: БЕГЕМОТ
[DEBUG After filter]: тигр
[DEBUG After map]: ТИГР
Итог: [СЛОН, БЕГЕМОТ, ТИГР]
```

## 🟡 Middle Level

### Внутреннее устройство: `Sink.ChainedReference`

В исходном коде OpenJDK (`ReferencePipeline.java`) метод `peek()` конструирует промежуточную операцию, возвращающую обертку над приемником данных (`Sink`):

```java
// Упрощенный фрагмент реализации в OpenJDK:
@Override
public Sink<P_OUT> opWrapSink(int flags, Sink<P_OUT> sink) {
    return new Sink.ChainedReference<P_OUT, P_OUT>(sink) {
        @Override
        public void accept(P_OUT u) {
            action.accept(u);       // 1. Вызываем пользовательский Consumer
            downstream.accept(u);   // 2. Проталкиваем элемент дальше без изменений
        }
    };
}
```

---

### Сравнение: `peek()` vs `map()` vs `forEach()`

| Критерий | `peek()` | `map()` | `forEach()` |
|---|---|---|---|
| **Тип операции** | Промежуточная (Intermediate) | Промежуточная (Intermediate) | **Терминальная (Terminal)** |
| **Возвращаемое значение** | `Stream<T>` (тот же тип) | `Stream<R>` (новый тип) | `void` |
| **Назначение** | Отладка, логирование прохода | Трансформация данных | Завершение работы, вывод данных |
| **Гарантия вызова** | **Нет** (зависит от терминальной) | **Нет** (зависит от терминальной) | **Да** (пока конвейер активен) |

---

### Антипаттерн: Мутация объектов внутри `peek()`

```java
// ❌ ГРУБЫЙ АНТИПАТТЕРН: Мутация сущностей внутри отладочного метода
users.stream()
    .peek(user -> user.setStatus("PROCESSED")) // Побочный эффект!
    .toList();

// ✅ ПРАВИЛЬНО: Чистая трансформация в новый объект или вызов forEach()
List<User> processed = users.stream()
    .map(user -> user.withStatus("PROCESSED"))
    .toList();
```

Если мутировать объект внутри `peek()`, код перестает быть чистой функцией, нарушает детерминизм конвейера и приводит к скрытым дефектам при многопоточной обработке в `parallelStream()`.

## 🔴 Senior Level

### Ловушка оптимизации Stream Pruning в Java 9+ (JDK-8075056)

В Java 9+ терминальная операция `.count()` получила глубокую оптимизацию: если источник стрима обладает характеристикой **`SIZED`** (например, `ArrayList`, массив, `List.of()`) и в пайплайне **нет операций фильтрации**, рантайм берет точный размер напрямую из сплитератора, **вообще не запуская обход элементов**:

```java
import java.util.List;

public class PeekPruningDemo {

    public static void main(String[] args) {
        List<String> data = List.of("A", "B", "C");

        // ❌ ОПАСНО: Попытка выполнить бизнес-логику в peek()
        long count = data.stream()
            .peek(item -> System.out.println("Выполняю аудит: " + item))
            .count();

        System.out.println("Всего элементов: " + count);
        // В Java 9+ вывод "Выполняю аудит..." НЕ ПОЯВИТСЯ ВОВСЕ!
        // JVM вернула 3 напрямую из data.size(), а peek() был удален из конвейера.
    }
}
```

---

### Влияние операций короткого замыкания (Short-Circuiting)

Операции вроде `findFirst()`, `findAny()`, `anyMatch()`, `limit()` прерывают конвейер, как только условие удовлетворено:

```java
List<String> items = List.of("A", "B", "C", "D", "E");

// peek() сработает только для элементов "A" и "B"!
items.stream()
    .peek(x -> auditService.save(x)) // Элементы C, D, E никогда не сохранятся!
    .filter(x -> "B".equals(x))
    .findFirst();
```

---

### Производительность в Highload и альтернативы отладки

1. **Virtual Call Overhead:** Каждый `peek()` добавляет виртуальный вызов `Consumer.accept()` на каждый элемент потока, мешая C2-компилятору производить агрессивный инлайнинг и векторизацию (SIMD).
2. **Production-практика:** В промышленном коде `peek()` не должен доходить до production-репозиториев (линтеры Checkstyle/SonarQube содержат правило `S3864: "peek" should be used only for debugging`).
3. **IDE Stream Debugger:** Для визуализации конвейера в IntelliJ IDEA есть плагин **Java Stream Debugger**, позволяющий пошагово наблюдать вход и выход каждого этапа конвейера без модификации исходного кода.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> «`peek()` — промежуточная операция, предназначенная исключительно для отладки. Она принимает `Consumer`, выполняет действие над элементом и пропускает его дальше без изменений. Главное правило: никогда не использовать `peek()` для бизнес-логики. Во-первых, стримы ленивы и не выполняются без терминальной операции. Во-вторых, short-circuiting операции прерывают вызовы `peek()` на середине. В-третьих, начиная с Java 9, операция `stream.peek(...).count()` на коллекциях `SIZED` полностью отбрасывается оптимизатором JVM, и код в `peek()` вообще не вызывается.»

---

### Сводка рисков использования `peek()`

| Сценарий | Результат | Почему так происходит |
|---|---|---|
| `stream.peek(...).count()` (Java 9+) | 🔴 **Действие не выполнится** | Stream Pruning оптимизация по размеру `SIZED` |
| `stream.peek(...).findFirst()` | 🟡 **Выполнится частично** | Short-circuiting останавливает стрим при первой находке |
| `stream.peek(...);` (без терминальной) | 🔴 **Действие не выполнится** | Ленивость стримов (без терминальной нет запуска) |
| `stream.peek(u -> u.setX()).toList()` | 🔴 **Антипаттерн** | Нарушение чистоты функций, сайд-эффект в промежуточном узле |
| `stream.filter(...).peek(log).toList()` | 🟢 **Корректно** | Временная отладка на этапе разработки |

### Топ-4 каверзных вопроса на интервью

#### 1. Почему в Java 9+ вызов `stream.peek(System.out::println).count()` ничего не выводит в консоль?
- Это следствие оптимизации JDK-8075056. Если терминальная операция — `count()`, а в конвейере нет промежуточных операций, фильтрующих или генерирующих элементы (`filter`, `flatMap`), и источник стрима имеет характеристику `SIZED`, рантайм считывает размер напрямую через `spliterator.getExactSizeIfKnown()`, не запуская конвейер и отбрасывая промежуточные узлы.

#### 2. В чем разница между `peek()` и `forEach()`?
- `peek()` — промежуточная (intermediate) операция, возвращающая `Stream<T>` и предназначенная для пассивного наблюдения за потоком в процессе его трансформации.
- `forEach()` — терминальная (terminal) операция, возвращающая `void`, которая запускает конвейер и предназначена для выполнения финального действия над элементами.

#### 3. Почему статические анализаторы (SonarQube правило `S3864`) помечают вызовы `peek()` как ошибку/code smell?
- Разработчики часто по ошибке используют `peek()` вместо `map()` для мутации сущностей или пытаются выполнять в нем бизнес-действия (запись в БД, аудит). Из-за оптимизаций рантайма, ленивости и параллелизма такое поведение нестабильно, поэтому линтеры запрещают нахождение `peek()` в production-коде.

#### 4. Как ведет себя `peek()` в параллельном стриме (`parallelStream()`)?
- Вызовы `Consumer.accept()` происходят в разных рабочих потоках `ForkJoinPool` параллельно и в непредсказуемом порядке. Если внутри `peek()` выполняется несинхронизированная запись или логирование без учета многопоточности, возникнут гонки данных и конкуренция за блокировки аппендеров логгера.

---

### Типичные ошибки и Red Flags
- 🚩 Использование `peek()` для сохранения сущностей в базу данных или отправки метрик.
- 🚩 Ожидание, что `peek()` гарантированно вызовется для каждого элемента перед `count()` или `findFirst()`.
- 🚩 Оставление отладочных вызовов `peek(System.out::println)` в production-коде.
- 🚩 Изменение полей объектов внутри `peek()` вместо создания новых DTO через `map()`.
