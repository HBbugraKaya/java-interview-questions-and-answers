# Как реализовать потокобезопасный Singleton

---

## 🟢 Junior Level

Когда приложение работает в многопоточной среде, наивная реализация Singleton с ленивой инициализацией ломается из-за состояния гонки (Race Condition):

```java
// ❌ НЕПРАВИЛЬНО: Состояние гонки!
public class UnsafeSingleton {
    private static UnsafeSingleton instance;
    private UnsafeSingleton() {}

    public static UnsafeSingleton getInstance() {
        if (instance == null) {
            // Если Поток A и Поток B придут сюда одновременно,
            // оба выполнят оператор new и создадут ДВА РАЗНЫХ объекта!
            instance = new UnsafeSingleton();
        }
        return instance;
    }
}
```

Чтобы гарантировать единственный экземпляр, создание объекта должно быть **потокобезопасным (Thread-Safe)**.

---

### Самый простой и надежный способ — Enum Singleton

Начиная с Java 5, самый простой, лаконичный и безопасный способ создания потокобезопасного Singleton — использование `enum`:

```java
public enum AppSettings {
    INSTANCE;

    private String databaseUrl = "jdbc:postgresql://localhost:5432/mydb";

    public String getDatabaseUrl() {
        return databaseUrl;
    }

    public void setDatabaseUrl(String databaseUrl) {
        this.databaseUrl = databaseUrl;
    }
}

// Использование:
public class Main {
    public static void main(String[] args) {
        AppSettings settings = AppSettings.INSTANCE;
        System.out.println(settings.getDatabaseUrl());
    }
}
```

**Почему Enum безопасен «из коробки»:**
1. **Потокобезопасность:** JVM на уровне загрузчика классов гарантирует, что константа enum создается ровно один раз и полностью инициализирована до первого использования.
2. **Защита от рефлексии:** Попытка вызвать `Constructor.newInstance()` для enum выбрасывает `IllegalArgumentException`.
3. **Защита от десериализации:** Механизм сериализации Java гарантирует, что десериализация enum возвращает существующий экземпляр, а не создает новый.

## 🟡 Middle Level

В промышленной Java-разработке применяются четыре основных подхода к реализации потокобезопасного Singleton.

### 1. Eager Initialization (Ранняя инициализация)
Экземпляр создается статическим инициализатором при загрузке класса.

```java
public class EagerSingleton {
    private static final EagerSingleton INSTANCE = new EagerSingleton();

    private EagerSingleton() {}

    public static EagerSingleton getInstance() {
        return INSTANCE;
    }
}
```
- **Плюсы:** Предельная простота, 100% потокобезопасность гарантирована JVM.
- **Минусы:** Объект создается в памяти сразу при загрузке класса, даже если он тяжелый и в текущем сценарии работы приложения не понадобится.

---

### 2. Double-Checked Locking (DCL с volatile)
Ленивая инициализация, при которой синхронизация через блок `synchronized` происходит только при первом обращении.

```java
public class DclSingleton {
    // volatile критически обязателен для предотвращения переупорядочивания инструкций!
    private static volatile DclSingleton instance;

    private DclSingleton() {
        // Защита от повторного создания через Reflection API
        if (instance != null) {
            throw new IllegalStateException("Экземпляр уже создан!");
        }
    }

    public static DclSingleton getInstance() {
        DclSingleton local = instance; // Чтение volatile в локальную переменную
        if (local == null) {
            synchronized (DclSingleton.class) {
                local = instance;
                if (local == null) {
                    instance = local = new DclSingleton();
                }
            }
        }
        return local;
    }
}
```
- **Плюсы:** Ленивая инициализация, минимальные накладные расходы на синхронизацию (только один раз при первом старте).
- **Минусы:** Сложность кода, необходимость четкого понимания роли `volatile` и барьеров памяти.

---

### 3. Bill Pugh Singleton (Initialization-on-demand Holder)
Оптимальный компромисс между ленивой инициализацией, производительностью и простотой кода.

```java
public class BillPughSingleton {
    private BillPughSingleton() {}

    // Вложенный static class НЕ загружается JVM до первого вызова getInstance()
    private static class Holder {
        private static final BillPughSingleton INSTANCE = new BillPughSingleton();
    }

    public static BillPughSingleton getInstance() {
        return Holder.INSTANCE;
    }
}
```
- **Как это работает:** Внешний класс `BillPughSingleton` может загружаться и использоваться другими частями программы, но внутренний статический класс `Holder` не будет загружен в память и проинициализирован до тех пор, пока не будет вызван метод `getInstance()`.
- **Потокобезопасность:** Спецификация JVM (JLS §12.4.2) гарантирует, что инициализация статических полей класса защищена внутренней блокировкой загрузчика классов (Class Initialization Lock).

---

### 4. Комплексная защита от атак (Reflection, Serialization, Cloning)

Если класс реализует интерфейс `Serializable` или `Cloneable`, стандартные механизмы JVM могут нарушить инвариант единственности:

```java
public class HardenedSingleton implements Serializable {
    private static final long serialVersionUID = 1L;

    private HardenedSingleton() {
        if (Holder.INSTANCE != null) {
            throw new IllegalStateException("Попытка создания второго экземпляра через рефлексию!");
        }
    }

    private static class Holder {
        private static final HardenedSingleton INSTANCE = new HardenedSingleton();
    }

    public static HardenedSingleton getInstance() {
        return Holder.INSTANCE;
    }

    // Защита от сериализации: подменяет десериализованный объект на синглтон
    protected Object readResolve() {
        return getInstance();
    }

    // Защита от клонирования
    @Override
    protected Object clone() throws CloneNotSupportedException {
        throw new CloneNotSupportedException("Клонирование Singleton запрещено!");
    }
}
```

## 🔴 Senior Level

### Глубокий анализ JMM: Переупорядочивание инструкций и аппаратные архитектуры (x86 vs ARM)

В выражении `instance = new DclSingleton()` JVM и компилятор выполняют три шага:
```
1. allocate_memory(sizeof(DclSingleton)) -> выделение сырой памяти в куче
2. invokespecial DclSingleton.<init>()   -> вызов конструктора (инициализация полей)
3. instance = ref                        -> запись ссылки на память в переменную
```

**Опасность без `volatile`:**
Компилятор JIT (C2) и суперскалярный процессор (Out-of-Order Execution) в целях оптимизации имеют право переупорядочить шаги: `1 -> 3 -> 2`.

```
[Поток 1]                                 [Поток 2]
1. allocate_memory()
3. instance = addr (ссылка опубликована!)
                                          Вызывает getInstance():
                                          Проверяет: if (instance == null) -> FALSE!
                                          Возвращает полуинициализированную ссылку!
                                          Вызывает метод: obj.doSomething() -> NPE / Corrupted State!
2. invokespecial <init>() (конструктор)
```

#### Разница в аппаратных моделях памяти: x86 (TSO) vs ARM / Apple Silicon
- **Архитектура x86-64:** использует модель памяти **Total Store Order (TSO)** — строгую модель памяти. Процессор x86 аппаратно не переупорядочивает инструкции записи между собой (StoreStore reordering запрещен аппаратно). Из-за этого DCL без `volatile` мог годами «случайно работать» на серверах Intel/AMD в проде без видимых сбоев.
- **Архитектуры ARM64 (AWS Graviton, Apple M-series) и PowerPC:** используют **Weak Memory Model (Слабую модель памяти)**. В них процессоры агрессивно переупорядочивают операции чтения и записи. Запуск кода со сломанным DCL без `volatile` на ARM64 приводит к немедленным падениям и порче данных.

**Роль `volatile`:**
По спецификации JSR-133 (Java 5+) запись в `volatile`-переменную генерирует инструкцию барьера памяти (`StoreStore` перед записью и `StoreLoad` после нее на x86 это `lock addl` или `mfence`, на ARM — `dmb ish`). Это создает отношение **Happens-Before**: все операции записи, сделанные в конструкторе, гарантированно становятся видны другим потокам до того, как они прочитают ненулевую ссылку `instance`.

---

### Оптимизация через VarHandle (Java 9+)

Ключевое слово `volatile` накладывает строгие барьеры памяти (Sequential Consistency). Начиная с Java 9, для экстремально высоконагруженных систем доступен механизм `VarHandle` с семантикой Acquire/Release:

```java
import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;

public class VarHandleSingleton {
    private static final VarHandle INSTANCE_HANDLE;

    static {
        try {
            INSTANCE_HANDLE = MethodHandles.lookup()
                .findStaticVarHandle(VarHandleSingleton.class, "instance", VarHandleSingleton.class);
        } catch (ReflectiveOperationException e) {
            throw new ExceptionInInitializerError(e);
        }
    }

    private static VarHandleSingleton instance;

    private VarHandleSingleton() {}

    public static VarHandleSingleton getInstance() {
        VarHandleSingleton local = (VarHandleSingleton) INSTANCE_HANDLE.getAcquire();
        if (local == null) {
            synchronized (VarHandleSingleton.class) {
                local = (VarHandleSingleton) INSTANCE_HANDLE.getAcquire();
                if (local == null) {
                    local = new VarHandleSingleton();
                    INSTANCE_HANDLE.setRelease(local);
                }
            }
        }
        return local;
    }
}
```
- **Почему это быстрее:** `getAcquire` и `setRelease` формируют однонаправленные барьеры памяти (Acquire-Release semantics), которые дешевле полных двухсторонних барьеров `volatile` (Seq-Cst) на ARM64-архитектурах, сохраняя при этом полную гарантию видимости инициализированного объекта.

### Механика Class Initialization Lock в Bill Pugh Singleton

Спецификация языка Java (JLS §12.4.2) детально описывает процедуру инициализации класса. Инициализация вложенного класса `Holder`:
1. Синхронизируется уникальной внутренней блокировкой (Initialization Lock), ассоциированной с объектом `Class<Holder>`.
2. Поток, первый запросивший загрузку `Holder`, захватывает эту блокировку, переводит класс в состояние `initializing`, запускает статический конструктор `<clinit>` и создает объект `INSTANCE`.
3. Все остальные потоки, одновременно вызвавшие `getInstance()`, блокируются на мониторе инициализации класса до тех пор, пока состояние класса не перейдет в `initialized`.
4. После перехода в `initialized` любые последующие обращения к полю `Holder.INSTANCE` выполняются со скоростью обычного чтения статической константы **без каких-либо блокировок и накладных расходов**.

### 3–4 каверзных вопроса с ответами

1. **Почему код с DCL без `volatile` мог годами работать на серверах Intel, но сразу падает на AWS Graviton (ARM64)?**
   - *Ответ:* Архитектура x86-64 обладает строгой моделью памяти TSO (Total Store Order), где аппаратное переупорядочивание записей (StoreStore) запрещено. Архитектура ARM64 имеет слабую модель памяти (Weak Memory Ordering), где процессор активно меняет порядок записи в память ради параллелизма. Без ключевого слова `volatile` на ARM64 ссылка на объект записывается до завершения полей в конструкторе, и параллельный поток считывает некорректные данные.

2. **Зачем в методе `getInstance()` паттерна DCL объявляется локальная переменная `local = instance`?**
   - *Ответ:* Это оптимизация производительности (Local Variable Optimization). Чтение `volatile`-поля стоит дороже чтения из стека или регистра процессора, так как требует соблюдения протокола когерентности кэшей (MESI). Сохранение ссылки в локальную переменную гарантирует, что при уже созданном объекте (99.9% случаев) обращение к `volatile`-переменной происходит строго один раз.

3. **Почему Bill Pugh Singleton считается лучше, чем метод с `synchronized`?**
   - *Ответ:* `synchronized`-метод блокирует монитор класса при **каждом** вызове `getInstance()`, создавая серьезную конкуренцию потоков (lock contention) в hot-path. Bill Pugh использует блокировку загрузчика классов (JLS §12.4.2), которая отрабатывает ровно один раз при инициализации вложенного класса, после чего все вызовы происходят на скорости чтения обычной константы без синхронизации.

4. **Как рефлексия ломает Bill Pugh Singleton и как от этого защититься?**
   - *Ответ:* Через вызов `constructor.setAccessible(true)` и `newInstance()`. Для защиты в приватном конструкторе Singleton добавляется проверка: если экземпляр уже существует (или флаг инициализации равен true), выбрасывается `IllegalStateException`.

---

### Типичные ошибки и Red Flags

- 🚩 **Использование DCL без модификатора `volatile`** — классическое непонимание JMM и race condition.
- 🚩 **Синхронизация всего метода `getInstance()`** в высоконагруженных сервисах — создание искусственного bottleneck.
- 🚩 **Заявление, что `Enum` Singleton можно создать через рефлексию** — метод `Constructor.newInstance()` в JVM содержит явную проверку на `Modifier.ENUM` и выбрасывает исключение.
- 🚩 **Игнорирование сериализации** в классах, реализующих `Serializable` (отсутствие `readResolve()`), что приводит к незаметному размножению экземпляров.
