# Как предотвратить deadlock

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**Предотвращение взаимных блокировок (Deadlock Prevention)** — это архитектурный подход к проектированию многопоточных программ, при котором устраняется сама возможность возникновения Deadlock путём гарантированного нарушения хотя бы одного из четырёх условий Коффмана на этапе написания кода.

Четыре основных практических метода предотвращения Deadlock в Java:
1. **Глобальный порядок захвата (Lock Ordering):** все потоки приложения захватывают разделяемые блокировки строго в одинаковой последовательности (например, по возрастанию уникального идентификатора `id` сущности). Это разрушает условие циклического ожидания (*Circular Wait*).
2. **Захват с таймаутом (`tryLock`):** использование `ReentrantLock.tryLock(timeout, unit)` вместо непрерываемого `synchronized`. Если за отведённое время захватить следующий замок не удалось, поток освобождает все ранее захваченные ресурсы и отступает. Это разрушает условия *Hold and Wait* и *No Preemption*.
3. **Использование неблокирующих (Lock-Free) структур:** замена классических мьютексов на классы из пакетов `java.util.concurrent.atomic` и `ConcurrentHashMap`. Нет блокировок — нет взаимного исключения (*Mutual Exclusion*).
4. **Правило открытых вызовов (Open Calls):** никогда не вызывать внешние методы, обработчики событий (listeners) и медленный I/O (БД, сеть), удерживая блокировку.

---

### Базовый пример: Предотвращение через Lock Ordering в Java 21

```java
public class SafeBankTransfer {

    public record Account(long id, int balance) {}

    // Безопасный перевод: порядок захвата детерминирован по ID счетов
    public void transfer(Account from, Account to, int amount) {
        // Защита от попытки перевода самому себе
        if (from.id() == to.id()) {
            throw new IllegalArgumentException("Нельзя перевести деньги на тот же счет");
        }

        // Детерминированное упорядочивание: меньший ID всегда блокируется первым!
        Account firstLock = from.id() < to.id() ? from : to;
        Account secondLock = from.id() < to.id() ? to : from;

        synchronized (firstLock) {
            synchronized (secondLock) {
                // Критическая секция: циклический Deadlock невозможен ни при каких обстоятельствах!
                debit(from, amount);
                credit(to, amount);
            }
        }
    }

    private void debit(Account acc, int amount) {}
    private void credit(Account acc, int amount) {}
}
```

## 🟡 Middle Level

### Паттерн «Попытка захвата с отступлением» (`tryLock` + Back-off)

Если ресурсы создаются динамически и установить для них естественный порядок невозможно, применяется подход с таймаутом захвата.

> [!WARNING]
> **Опасность Livelock:** если два потока не могут захватить второй ресурс, одновременно отпускают первый и немедленно пытаются повторить попытку, они могут бесконечно блокировать друг друга на полной мощности CPU (**Livelock**). Для предотвращения Livelock обязательна случайная задержка (**Jitter / Random Back-off**).

```java
import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class SafeTryLockTransfer {

    public boolean transferWithTimeout(ReentrantLock lockA, ReentrantLock lockB, 
                                       long maxTimeout, TimeUnit unit) throws InterruptedException {
        long deadline = System.nanoTime() + unit.toNanos(maxTimeout);

        while (System.nanoTime() < deadline) {
            // Попытка захвата первого ресурса
            if (lockA.tryLock(50, TimeUnit.MILLISECONDS)) {
                try {
                    // Попытка захвата второго ресурса
                    if (lockB.tryLock(50, TimeUnit.MILLISECONDS)) {
                        try {
                            executeTransfer();
                            return true; // Успешно выполнен перевод
                        } finally {
                            lockB.unlock();
                        }
                    }
                } finally {
                    // ЕСЛИ ВТОРОЙ ЗАМОК НЕ ПОЛУЧЕН — НЕМЕДЛЕННО ОСВОБОЖДАЕМ ПЕРВЫЙ!
                    lockA.unlock();
                }
            }

            // Случайная пауза (Jitter) предотвращает синхронный вход потоков в Livelock
            int backoffMs = ThreadLocalRandom.current().nextInt(10, 40);
            Thread.sleep(backoffMs);
        }

        return false; // Таймаут исчерпан, операция отменена
    }

    private void executeTransfer() {}
}
```

### Архитектурный паттерн: Открытые вызовы (Open Calls)

Вызов чужого кода под замком — главная причина скрытых Deadlock в развитых проектах:

```java
// ОПАСНО: Вызов внешнего listener под монитором
public synchronized void updateState(State newState) {
    this.state = newState;
    for (StateListener listener : listeners) {
        // КАТАСТРОФА: внешний listener может внутри захватывать свой собственный лок,
        // а другой поток, удерживая тот лок, может вызвать метод текущего класса!
        listener.onStateChanged(newState); 
    }
}
```

#### Эталонная реализация Open Call (без удержания лока):

```java
public class SafeStateHolder {
    private final List<StateListener> listeners = new CopyOnWriteArrayList<>();
    private final Object stateLock = new Object();
    private State state;

    public void updateState(State newState) {
        // 1. Быстро обновляем внутреннее состояние под коротким замком
        synchronized (stateLock) {
            this.state = newState;
        }

        // 2. Внешние уведомления рассылаются СТРОГО ЗА ПРЕДЕЛАМИ критической секции!
        for (StateListener listener : listeners) {
            listener.onStateChanged(newState); // Открытый вызов (Open Call)
        }
    }
}
```

## 🔴 Senior Level

### Упорядочивание произвольных объектов памяти: Tie-Breaker Lock

Когда требуется упорядочить захват двух произвольных Java-объектов, у которых нет бизнес-идентификаторов (например, графические узлы графа), используют их адресные хеши `System.identityHashCode()`.

Для обработки редких коллизий хеш-кодов применяется специальный статический замок разрешения ничьей (**Tie-Breaker Lock**):

```java
public class ArbitraryLockOrdering {
    private static final Object TIE_BREAKER_LOCK = new Object();

    public void performAction(Object objA, Object objB) {
        int hashA = System.identityHashCode(objA);
        int hashB = System.identityHashCode(objB);

        if (hashA < hashB) {
            synchronized (objA) {
                synchronized (objB) {
                    process(objA, objB);
                }
            }
        } else if (hashA > hashB) {
            synchronized (objB) {
                synchronized (objA) {
                    process(objA, objB);
                }
            }
        } else {
            // КОЛЛИЗИЯ ХЕШ-КОДОВ: сериализуем редкие коллизии через общий замок
            synchronized (TIE_BREAKER_LOCK) {
                synchronized (objA) {
                    synchronized (objB) {
                        process(objA, objB);
                    }
                }
            }
        }
    }

    private void process(Object a, Object b) {}
}
```

### Deadlock в базах данных (JPA / Hibernate / SQL)

Deadlock на уровне базы данных происходит при параллельном выполнении транзакций, обновляющих одни и те же строки в разном порядке:
- Транзакция 1: `UPDATE account SET balance = ... WHERE id = 1;` затем `WHERE id = 2;`
- Транзакция 2: `UPDATE account SET balance = ... WHERE id = 2;` затем `WHERE id = 1;`

#### Предотвращение на уровне ORM/SQL:
1. **Детерминированная сортировка батча:** при массовом обновлении или блокировке строк (`SELECT ... FOR UPDATE`) список сущностей **всегда должен быть отсортирован по первичному ключу (`ORDER BY id ASC`)** перед отправкой запроса.
2. **Пессимистичные блокировки с таймаутом:** использование подсказки `PESSIMISTIC_WRITE` со свойством `jakarta.persistence.lock.timeout`:
   ```java
   @Lock(LockModeType.PESSIMISTIC_WRITE)
   @QueryHints({@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000")})
   @Query("SELECT a FROM Account a WHERE a.id IN :ids ORDER BY a.id ASC")
   List<Account> findAccountsForUpdate(@Param("ids") List<Long> ids);
   ```

### Архитектурный контроль: Static Analysis и ArchUnit

В корпоративной разработке соблюдение порядка блокировок невозможно проконтролировать только через ручной Code Review.

#### Инструменты автоматической верификации:
1. **SonarQube / SpotBugs:** правила `Locks should be acquired in a specific order` и `ThreadCheck` детектируют перекрёстные блокировки на этапе CI/CD.
2. **ArchUnit тесты:** запрет на вызов методов сторонних сервисов из-под блоков `@Synchronized` или методов, удерживающих блокировки.
3. **ThreadSanitizer (TSan):** флаг `-XX:+UseThreadSanitizer` в JVM выявляет потенциальные циклы в графе блокировок во время выполнения интеграционных тестов.

## 🎯 Шпаргалка для интервью

### 1. 30-секундный эссенс (Elevator Pitch)
Главная стратегия предотвращения Deadlock — **Lock Ordering (детерминированный порядок захвата замков)** по естественному или синтетическому ID, что математически делает невозможным циклическое ожидание (Circular Wait). Вторым стандартом является применение **`ReentrantLock.tryLock(timeout)` со случайным back-off**, разрушающим условие Hold and Wait и устраняющим риск Livelock. В архитектуре кода критически важно применять **Open Calls (открытые вызовы)** — выносить любые внешние вызовы, колбеки и I/O за пределы критических секций.

### 2. 4 каверзных вопроса с глубокими ответами

#### Вопрос 1: Что такое «Открытые вызовы» (Open Calls) в многопоточном программировании, и как они защищают от Deadlock?
**Ответ:**
Открытый вызов (Open Call) — это архитектурное правило, согласно которому вызовы сторонних методов (интерфейсов, обработчиков событий, делегатов или удалённых служб) выполняются **строго вне контекста удерживаемых синхронизаторов**.  
Если вызвать чужой метод, удерживая свой монитор, разработчик теряет контроль над графом блокировок: неизвестный код внутри чужого метода может захватить свой внутренний замок, а другой поток может попытаться сделать то же самое в обратном порядке. Вынесение вызовов за пределы критической секции изолирует блокировку от чужого кода.

#### Вопрос 2: Почему наивный retry-цикл с `tryLock()` вместо предотвращения Deadlock часто порождает Livelock, и как этого избежать?
**Ответ:**
Если два потока одновременно захватывают первый замок (`lockA.tryLock()` и `lockB.tryLock()`), ни один не может захватить второй замок. Если они оба освобождают первый замок и сразу же в следующей итерации цикла без паузы пытаются повторить захват, сценарий воспроизведётся снова. Потоки будут бесконечно захватывать и отпускать замки, потребляя 100% CPU без совершения полезного прогресса (**Livelock**).  
*Решение:* добавление экспоненциальной случайной задержки (**Random Back-off / Jitter**) перед каждой новой попыткой.

#### Вопрос 3: Как предотвратить Deadlock на уровне SQL-запросов в JPA/Hibernate при обновлении множества связанных сущностей?
**Ответ:**
На уровне реляционной БД дедлоки возникают при параллельных операциях `UPDATE` или `SELECT FOR UPDATE` над одними и теми же строками в разном порядке.  
Для предотвращения:
1. Коллекция обновляемых ID обязана быть отсортирована: `ids.sort(Long::compareTo)` перед выполнением запроса.
2. Использовать `SELECT ... FOR UPDATE` со строгим предложением `ORDER BY a.id ASC`.
3. Задавать таймаут ожидания блокировки (`lock.timeout` / `NOWAIT` / `SKIP LOCKED`), чтобы база сбрасывала зависшую транзакцию по таймауту вместо бесконечного ожидания.

#### Вопрос 4: Зачем при сортировке объектов по `System.identityHashCode()` нужен дополнительный `Tie-Breaker Lock`?
**Ответ:**
Хеш-код `identityHashCode` формируется на базе 31-битного представления и по принципу Дирихле неизбежно даёт коллизии (два разных объекта в куче получают одинаковое число). Если хеши двух конкурирующих объектов совпадут, условие `hashA < hashB` не сработает, и потоки могут захватить их в произвольном порядке, спровоцировав Deadlock. Третий статический замок `TIE_BREAKER_LOCK` сериализует редкие коллизии, гарантируя атомарность входа.

### 3. Типичные ошибки и Red Flags

❌ **"Использование одного глобального замка (`synchronized(globalLock)`) для решения проблемы Deadlock в нагруженных сервисах."**  
*Правильно:* Глобальный замок действительно предотвращает Deadlock, но превращает многопоточную систему в строго последовательную, обрушая пропускную способность до уровня одного ядра CPU.

❌ **"Удержание Java-блокировки во время выполнения медленного HTTP-запроса или транзакции БД."**  
*Правильно:* Это грубейшее нарушение правила Open Calls. Задержка внешнего сервиса приведёт к каскадному блокированию всех потоков пула приложения.

❌ **"Игнорирование сортировки ключей при пакетных операциях."**  
*Правильно:* При пакетной обработке (в Java-коллекциях или БД) несортированные списки ключей являются главной причиной трудновоспроизводимых спорадических Deadlock.
