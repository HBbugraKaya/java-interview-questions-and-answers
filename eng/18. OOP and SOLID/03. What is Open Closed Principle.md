# What is Open Closed Principle

---

## 🟢 Junior Level

The **Open/Closed Principle (OCP)** is the second principle of the **SOLID** design principles, formulated by Bertrand Meyer and popularized by Robert C. Martin ("Uncle Bob"):

> **"Software entities (classes, modules, functions) should be open for extension, but closed for modification."**

### Core Meaning
- **Closed for Modification:** Stable, tested, production-grade code should not be edited every time business requirements evolve. Modifying battle-tested source files introduces regression bugs into existing features.
- **Open for Extension:** The architecture is structured so that new functionality is added by writing **new code** (new classes or plugins) that integrate with existing logic via stable abstractions.

```
Smartphone USB-C Port Analogy:
+-------------------------------------------------------------------------+
| • Closed for Modification: To use headphones, flash storage, or an      |
|   external monitor, you do NOT open the phone chassis and solder wires. |
| • Open for Extension: The standardized USB-C interface allows any       |
|   compliant accessory to plug in and function immediately.              |
+-------------------------------------------------------------------------+
```

### Anti-Pattern: Violating OCP with Type Checking
When adding a new notification channel requires modifying existing control flow, OCP is violated:

```java
// ❌ VIOLATION: NotificationService must be edited for every new channel
public class NotificationService {
    public void sendNotification(String channelType, String message, String recipient) {
        if ("EMAIL".equalsIgnoreCase(channelType)) {
            // SMTP email dispatch logic
            System.out.println("Sending Email to " + recipient + ": " + message);
        } else if ("SMS".equalsIgnoreCase(channelType)) {
            // SMPP SMS gateway logic
            System.out.println("Sending SMS to " + recipient + ": " + message);
        } else if ("TELEGRAM".equalsIgnoreCase(channelType)) {
            // Telegram Bot API logic
            System.out.println("Sending Telegram message to " + recipient + ": " + message);
        } else {
            throw new IllegalArgumentException("Unsupported channel: " + channelType);
        }
    }
}
```

### Refactoring to Polymorphic OCP
Define an abstraction and provide dedicated, self-contained implementations:

```java
// 1. Stable Abstraction
public interface NotificationChannel {
    boolean supports(String channelType);
    void send(String recipient, String message);
}

// 2. Concrete Strategy
@Component
public class EmailNotificationChannel implements NotificationChannel {
    @Override
    public boolean supports(String channelType) {
        return "EMAIL".equalsIgnoreCase(channelType);
    }

    @Override
    public void send(String recipient, String message) {
        System.out.println("Sending Email to " + recipient + ": " + message);
    }
}

// 3. Client Service: CLOSED for modification
@Service
public class NotificationService {
    private final List<NotificationChannel> channels;

    public NotificationService(List<NotificationChannel> channels) {
        this.channels = List.copyOf(channels);
    }

    public void sendNotification(String channelType, String message, String recipient) {
        NotificationChannel channel = channels.stream()
            .filter(ch -> ch.supports(channelType))
            .findFirst()
            .orElseThrow(() -> new IllegalArgumentException("Unsupported channel: " + channelType));

        channel.send(recipient, message);
    }
}
```

To support WhatsApp or Slack, you implement a new `NotificationChannel` class. `NotificationService` remains untouched, preventing regression bugs.

## 🟡 Middle Level

### 1. Key Design Patterns Enabling OCP

| Pattern | Role in OCP | Real-World Example |
| :--- | :--- | :--- |
| **Strategy** | Encapsulates swappable algorithm families behind a uniform interface. | `PaymentStrategy` (`CreditCardPayment`, `PayPalPayment`, `CryptoPayment`). |
| **Template Method** | Fixes invariant workflow steps in an abstract class while deferring variant steps to subclasses. | `AbstractReportGenerator.generate()` calling hook `formatData()`. |
| **Decorator** | Dynamically wraps objects to add behaviors without modifying original source code. | `BufferedInputStream` wrapping `FileInputStream` in `java.io`. |
| **Observer / Pub-Sub**| Producers emit domain events without knowing what downstream consumers exist. | Spring `ApplicationEventPublisher` dispatching `OrderPlacedEvent`. |

### 2. OCP in Spring Boot: Dependency Injection & Map Lookups

In Spring Boot, OCP is natural because Spring's ApplicationContext can collect all implementations of an interface into collections or maps:

```java
@Service
public class OrderProcessingService {

    private final List<OrderValidator> validators;
    private final Map<String, PaymentProcessor> paymentProcessors;

    // Spring auto-wires all beans implementing OrderValidator and PaymentProcessor
    public OrderProcessingService(List<OrderValidator> validators,
                                  Map<String, PaymentProcessor> paymentProcessors) {
        this.validators = validators;
        this.paymentProcessors = paymentProcessors;
    }

    public void processOrder(Order order, String paymentMethod) {
        // Closed for modification: new validators execute automatically
        for (OrderValidator validator : validators) {
            validator.validate(order);
        }

        PaymentProcessor processor = paymentProcessors.get(paymentMethod);
        if (processor == null) {
            throw new UnsupportedPaymentMethodException(paymentMethod);
        }
        processor.pay(order);
    }
}
```

### 3. The Expression Problem: OCP vs. Sealed Hierarchies (Java 21+)

The **Expression Problem** is a fundamental trade-off in programming language design:

| Dimension of Extensibility | Polymorphic OCP (Interface / Strategy) | Algebraic Data Types (Sealed Interface + Switch) |
| :--- | :--- | :--- |
| **Adding New Data Types** | **Trivial (OCP Honored):** Add a new class implementing the interface without modifying existing code. | **Difficult:** Adding a new subtype requires editing all exhaustive `switch` expressions across the codebase. |
| **Adding New Operations** | **Difficult (Breaks OCP):** Adding a method to an interface requires updating every implementing class. | **Trivial (OCP Honored):** Write a new function containing an exhaustive `switch` over existing types without modifying model classes. |

```java
// Java 21 Sealed Hierarchy (Closed for new types, open for new operations)
public sealed interface OrderEvent permits OrderCreated, OrderCancelled, OrderShipped {}

public record OrderCreated(UUID orderId, BigDecimal amount) implements OrderEvent {}
public record OrderCancelled(UUID orderId, String reason) implements OrderEvent {}
public record OrderShipped(UUID orderId, String trackingNumber) implements OrderEvent {}

public class AuditService {
    // Adding new operations requires zero modifications to the OrderEvent records
    public String describe(OrderEvent event) {
        return switch (event) {
            case OrderCreated c   -> "Order created: " + c.orderId();
            case OrderCancelled c -> "Order cancelled: " + c.reason();
            case OrderShipped s   -> "Order shipped: " + s.trackingNumber();
        };
    }
}
```

## 🔴 Senior Level

### 1. Bertrand Meyer vs. Robert C. Martin: The Evolution of OCP

1. **Bertrand Meyer (1988, "Object-Oriented Software Construction"):**
   - Defined OCP primarily through **Implementation Inheritance** (`extends`).
   - A class is closed once compiled and stored in a shared library.
   - A class is open because another class can subclass it and override methods.
   - *Limitation:* Deep inheritance hierarchies introduce the **Fragile Base Class Problem**, where alterations to superclass internals break subclass invariants.

2. **Robert C. Martin (Uncle Bob, 1996+):**
   - Re-imagined OCP around **Polymorphic Abstraction** and the **Dependency Inversion Principle (DIP)**.
   - Systems depend on clean interfaces and composition rather than class inheritance. Subclasses must strictly satisfy the Liskov Substitution Principle (LSP).

### 2. Low-Level JVM Performance: Call Sites and HotSpot JIT (C2)

While polymorphic OCP creates flexible architectures, it impacts execution performance in HotSpot JIT:

```
Polymorphic Call Site Classifications:
1. Monomorphic (1 Implementation observed at runtime):
   [Call Site] ────────> [Impl A]
   HotSpot C2 Action: Direct method inlining. Escape analysis succeeds. Overhead: ~0 ns.

2. Bimorphic (2 Implementations observed):
   [Call Site] ────┬───> [Impl A]
                   └───> [Impl B]
   HotSpot C2 Action: Inlined conditional check: if (klass == A) A() else B().

3. Megamorphic (> 2 Implementations observed):
   [Call Site] ────┼───> [Impl A]
                   ├───> [Impl B]
                   └───> [Impl C, D, ...]
   HotSpot C2 Action: Inlining fails! Dynamic dispatch via vtable/itable lookup.
```

#### The Cost of Megamorphic Call Sites:
- **No Inlining:** The compiler cannot pull method bytecode into the calling loop.
- **Escape Analysis Failure:** Objects created inside the method cannot be scalar-replaced on the thread stack and must be allocated on the heap, increasing GC pressure.
- **CPU Branch Target Misprediction:** Dynamic indirect calls cause pipeline stalls and L1 instruction cache misses (~15–30 CPU cycles penalty per invocation).

> [!TIP]
> In Ultra-Low Latency systems (e.g., High-Frequency Trading or game engines), architects intentionally replace megamorphic interfaces on critical hot paths with `final` classes, enum dispatch, or compile-time code generation to guarantee JIT inlining.

### 3. Architectural Blast Radius and SPI

At enterprise architecture scale, OCP isolates the **Blast Radius** of software updates:
- **Core API Module (`order-api.jar`):** Defines immutable contracts and interfaces with zero heavy external dependencies.
- **Plugin Adapters (`order-payment-stripe.jar`):** Implement the core interfaces.
- **Java SPI (`java.util.ServiceLoader`):** Discovers implementations dynamically at runtime from the classpath without compile-time coupling.
- **CI/CD Impact:** Modifying a payment provider only triggers a build and test run for that single plugin module, drastically reducing CI pipeline times.

## 4 Tricky Questions

### 1. What was Bertrand Meyer's original view of OCP, and why is class inheritance dangerous compared to polymorphic OCP?
**Answer:**
Meyer formulated OCP using class inheritance (`extends`), where a subclass overrides superclass methods to extend functionality. 
In production systems, this approach is dangerous due to the **Fragile Base Class Problem**:
- Subclasses depend on internal implementation details and execution order of the base class.
- Modifying a `protected` method or internal caching behavior in the base class can silently break subclass invariants.
Robert Martin's polymorphic OCP relies on **Interface Abstraction** and **Composition**, which decouples callers from implementation state and isolates side effects.

### 2. Does pattern matching with a `switch` over a `sealed interface` violate OCP?
**Answer:**
Under Robert Martin's classic polymorphic definition, yes: adding a new type to a `sealed interface` forces modifying existing `switch` statements across the system.

However, from the perspective of the **Expression Problem**, sealed hierarchies provide orthogonal OCP compliance:
- **Classic Polymorphism:** Open for new types, closed for new operations.
- **Sealed Types (Functional approach):** Open for new operations, closed for new types.
When the domain variants are mathematically finite (e.g., HTTP status categories, chess pieces, domain events), a sealed hierarchy is superior because the Java compiler enforces **exhaustive coverage** without requiring fallback `default` branches.

### 3. How does introducing 10 strategy implementations impact JVM performance in a hot-path loop?
**Answer:**
It degrades the call site from monomorphic/bimorphic to **megamorphic**:
1. The JIT compiler (C2) cannot inline the target method body.
2. Method invocation relies on dynamic `itable` (interface table) lookups, causing CPU branch prediction penalties.
3. Escape analysis fails, meaning any temporary objects instantiated inside the strategy cannot be allocated on the thread stack and must go to the garbage-collected heap.

In extreme low-latency scenarios, developers avoid megamorphic strategy dispatch on hot paths by sorting data by type before processing or using direct method calls on `final` classes.

### 4. How do you extend an OCP-compliant interface if a new feature requires passing additional parameters without breaking existing implementations?
**Answer:**
Changing an interface method signature breaks all existing implementations, violating the "closed for modification" rule. Standard solutions include:
1. **Parameter / Context Object:** Design the interface from the start to accept a request or context object (e.g., `ValidationContext context`). New attributes can be added to the context without modifying method signatures.
2. **Sub-Interfaces:** Define a new interface extending the old one (`AdvancedChannel extends NotificationChannel`). Calling code uses pattern matching: `if (channel instanceof AdvancedChannel adv) adv.sendWithMetadata(...)`.
3. **Default Methods (Java 8+):** Add a `default` method to the interface with a no-op or fallback implementation, maintaining binary and source compatibility for existing classes.

## 🎯 Interview Cheat Sheet

### Core Concepts:
- **OCP Definition:** Software entities should be open for extension, but closed for modification.
- **Primary Mechanism:** Interfaces, Polymorphism, Dependency Injection, and Strategy / Decorator patterns.
- **Code Smell:** Cascading `if-else` or `switch` blocks checking type strings or `instanceof`.
- **Spring Integration:** Injecting `List<Interface>` or `Map<String, Interface>` to auto-discover extension points.
- **Modern Java:** Use Sealed Hierarchies when data types are fixed and new operations are frequent; use Polymorphic Interfaces when types are open-ended.
- **JVM Consideration:** Beware of megamorphic call sites on ultra-critical hot paths.

### Red Flags to Avoid:
- ❌ *"OCP means we should create an interface for every single class in the application."* (Violates YAGNI; abstract only along anticipated vectors of change).
- ❌ *"OCP forbids editing a file even if there is a known bug or security vulnerability."* (OCP applies to adding new features, not bug fixes or refactoring).
- ❌ *"Inheritance is the best way to satisfy OCP."* (Inheritance creates tight coupling; prefer composition and interfaces).
