# Что такое orphan removal

Механизм удаления «сирот» (**`orphanRemoval = true`**) в JPA и Hibernate — это декларативное правило управления жизненным циклом зависимых сущностей в отношениях композиции (**`@OneToMany`** и **`@OneToOne`**). Когда дочерний объект удаляется из родительской коллекции или ссылка на него обнуляется (`null`), Hibernate автоматически переводит такую сущность в состояние `Removed` и генерирует команду SQL `DELETE` при синхронизации с базой данных.

---

## 🟢 Junior Level

### Что такое «сирота» (Orphan) и зачем нужен `orphanRemoval`

В реляционных базах данных разрыв связи между родителем и ребенком (например, удаление элемента из списка в Java) по умолчанию лишь устанавливает внешний ключ `parent_id` в значение `NULL`:

```sql
-- Без orphanRemoval: запись остается в БД "осиротевшей" (Orphan)
UPDATE order_items SET order_id = NULL WHERE id = 5;
```

Если колонка `order_id` имеет ограничение `NOT NULL`, такое обновление завершится ошибкой целостности. Если ограничение нет — таблица засоряется брошенными строками, не принадлежащими ни одному заказу.

Параметр **`orphanRemoval = true`** приказывает Hibernate не обнулять внешний ключ, а **физически удалять строку из БД**:

```java
@Entity
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Включаем автоматическое удаление осиротевших записей:
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();
}
```

```java
Order order = entityManager.find(Order.class, 1L);

// Просто удаляем элемент из коллекции в памяти:
order.getItems().remove(0);

// При коммите транзакции Hibernate автоматически выполнит:
// DELETE FROM order_items WHERE id = ?;
```

### Сравнение: `CascadeType.REMOVE` vs `orphanRemoval = true`

Главное концептуальное различие, которое проверяют на собеседованиях:

| Сценарий | `CascadeType.REMOVE` | `orphanRemoval = true` |
| :--- | :--- | :--- |
| **Удаление родителя:** `entityManager.remove(order)` | ✅ Дочерние записи удаляются из БД | ✅ Дочерние записи удаляются из БД |
| **Удаление из коллекции:** `order.getItems().remove(item)` | ❌ Запись в БД **остается** (внешний ключ становится `NULL`) | ✅ Запись в БД **физически удаляется (`DELETE`)** |
| **Очистка коллекции:** `order.getItems().clear()` | ❌ Ни одна строка из БД не удалится | ✅ **Все** дочерние записи удалятся из БД |

## 🟡 Middle Level

### Поддерживаемые типы связей

Спецификация JPA разрешает использование `orphanRemoval = true` **только для отношений с монопольным владением**:

1. **`@OneToMany`**: Коллекции дочерних сущностей (заказ -> позиции, пользователь -> адреса).
2. **`@OneToOne`**: Одиночные зависимые сущности (пользователь -> профиль, заказ -> детали доставки).
   ```java
   @OneToOne(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
   private UserProfile profile;

   // Удаление профиля из БД:
   user.setProfile(null); // При flush сгенерирует DELETE FROM user_profiles
   ```
3. **Запрещено для `@ManyToOne` и `@ManyToMany`:** В этих отношениях сущности являются разделяемыми (Shared Entities), и удаление ссылки не означает уничтожение самого объекта.

### Ловушка переприсвоения коллекции: `was no longer referenced`

Одна из самых частых и неприятных ошибок новичков:

```java
Order order = entityManager.find(Order.class, 1L);

// ❌ ГРУБАЯ ОШИБКА: Замена экземпляра коллекции!
order.setItems(new ArrayList<>(newItems));
entityManager.flush();
```

**Результат выполнения:**
Hibernate выбросит фатальное исключение:
`org.hibernate.HibernateException: A collection with cascade="all-delete-orphan" was no longer referenced by the owning entity instance`.

#### Почему это происходит:
Hibernate оборачивает исходную коллекцию в свой собственный прокси-класс **`PersistentBag`** / **`PersistentSet`**, привязанный к сессии. Если перетереть ссылку новой коллекцией (`new ArrayList`), Hibernate теряет возможность отслеживать разницу между старыми и новыми элементами по снимку `CollectionEntry`.

**Как делать правильно:**
```java
// ✅ ПРАВИЛЬНО: Модифицировать существующую коллекцию по месту
order.getItems().clear();     // Помечает старые элементы на удаление
order.getItems().addAll(newItems); // Добавляет новые элементы
```

## 🔴 Senior Level

### Место `OrphanRemovalAction` в очереди действий Hibernate (`ActionQueue`)

Внутри ядра Hibernate (`SessionImpl`) удаление сирот обрабатывается особым образом:

```
                    ПОРЯДОК ВЫПОЛНЕНИЯ В ACTIONQUEUE
                    
  1. OrphanRemovalAction      <── СРАБАТЫВАЕТ ПЕРВЫМ!
  2. EntityInsertAction
  3. EntityUpdateAction
  4. CollectionRemoveAction
  5. CollectionUpdateAction
  6. EntityDeleteAction       <── Обычный remove() срабатывает в конце!
```

#### Архитектурное преимущество:
Обычный `CascadeType.REMOVE` ставит операцию `EntityDeleteAction` в самый конец очереди (после всех `INSERT`). Из-за этого замена элемента с уникальным ограничением (`UNIQUE`) падала с ошибкой дублирования ключа.

Поскольку **`OrphanRemovalAction` выполняется на первом месте**:
1. Сначала удаляется старый элемент: `DELETE FROM items WHERE code = 'ITEM_1';`
2. Затем вставляется новый элемент: `INSERT INTO items (code) VALUES ('ITEM_1');`
3. Уникальное ограничение не нарушается!

### Синхронизация двунаправленных связей (Helper Methods)

В двунаправленной связи `@OneToMany(mappedBy = "order")` владельцем внешнего ключа является дочерняя сущность `OrderItem` (колонка `order_id`).

Если при удалении сироты из списка родителя не обнулить ссылку на стороне дочерней сущности:
```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    // Обязательный defensive-метод бизнес-логики:
    public void removeItem(OrderItem item) {
        this.items.remove(item);
        item.setOrder(null); // КРИТИЧНО для согласованности в памяти!
    }
}
```
Если забыть про `item.setOrder(null)`, то пока сущность `item` удерживается в памяти текущего потока, она сохраняет битую ссылку на родителя, что может привести к непредсказуемым ошибкам при повторном обращении к ней в рамках транзакции.

## 4 Tricky Questions

### 1. Что произойдет, если в коллекции с `orphanRemoval = true` удалить элемент `order.getItems().remove(item)`, а затем в этом же методе вызвать `entityManager.persist(item)`?

**Ответ:**
1. При вызове `order.getItems().remove(item)` объект помечается как сирота для планирования `OrphanRemovalAction`.
2. Однако явный вызов `entityManager.persist(item)` сообщает контексту постоянства, что этот Java-объект должен оставаться в статусе `Status.MANAGED`.
3. Hibernate обнаруживает конфликт намерений: сущность одновременно помечена как удаляемая сирота и как управляемая для вставки/сохранения.
4. В зависимости от диалекта и версии Hibernate это приведет либо к отмене удаления и повторному сохранению, либо к выбросу `ObjectDeletedException: deleted object would be re-saved by cascade`.
5. **Правило:** Никогда не вызывать `persist()` на объектах, исключенных из коллекций с `orphanRemoval`.

### 2. Будет ли работать `orphanRemoval = true` для однонаправленной связи `@OneToMany` (без `mappedBy`, с `@JoinColumn`)?

**Ответ:**
1. **Да, будет!**
2. В однонаправленной связи `@OneToMany @JoinColumn(name = "order_id")` родительская сущность полностью управляет внешним ключом.
3. При удалении элемента из коллекции `order.getItems().remove(0)` Hibernate во время фазы `flush()` сгенерирует команду `DELETE FROM order_items WHERE id = ?`.
4. Однако однонаправленные `@OneToMany` порождают неэффективный SQL (лишние `UPDATE` внешнего ключа перед `INSERT`), поэтому двунаправленная связь с `mappedBy` остается лучшей практикой.

### 3. Чем отличается поведение `orphanRemoval = true` при удалении родителя от аннотации Hibernate `@OnDelete(action = OnDeleteAction.CASCADE)`?

**Ответ:**
1. При `orphanRemoval = true` Hibernate загружает все дочерние сущности в память JVM (L1 кэш), исполняет их жизненные колбэки (`@PreRemove`) и генерирует $N$ отдельных запросов `DELETE FROM child WHERE id = ?`.
2. При `@OnDelete(action = OnDeleteAction.CASCADE)` Hibernate делегирует удаление внешнему ключу СУБД. В базу уходит всего один запрос `DELETE FROM parent WHERE id = ?`, а движок базы данных мгновенно стирает детей на диске без их вычитки в память Java.

### 4. Допустим, мы вызвали `order.getItems().clear()`, но транзакция завершилась с ошибкой и откатилась (`ROLLBACK`). Восстановится ли коллекция в Java-объекте?

**Ответ:**
1. В базе данных все останется в исходном состоянии: откат транзакции отменит любые отправленные команды SQL `DELETE`.
2. Однако в оперативной памяти Java-объект `order` **останется с пустой коллекцией** (`order.getItems().isEmpty() == true`), так как откат транзакции в СУБД не откатывает мутации полей Java-объектов в куче JVM.
3. Чтобы вернуть актуальное состояние в память, необходимо заново запросить объект из БД в новой сессии или вызвать `entityManager.refresh(order)`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «Параметр `orphanRemoval = true` в JPA активирует автоматическое удаление дочерних сущностей из базы данных при их удалении из коллекции родителя (`order.getItems().remove(item)`) или при обнулении ссылки `@OneToOne`. В отличие от `CascadeType.REMOVE`, который удаляет детей только при удалении самого родителя, `orphanRemoval` защищает базу от накопления брошенных записей без внешнего ключа. Внутри ядра Hibernate `OrphanRemovalAction` исполняется в самом начале очереди действий `ActionQueue`, что предотвращает коллизии уникальных ограничений. Критический нюанс: нельзя перетирать коллекцию новым экземпляром (`setItems(new ArrayList)`), ее можно только модифицировать через `clear()` и `addAll()`, иначе Hibernate выбросит исключение».

### Ключевые метрики для Production-мониторинга
- **Количество непредвиденных SQL DELETE**: внезапный всплеск удалений может свидетельствовать о случайном вызове `clear()` на коллекции с `orphanRemoval`.
- **Foreign Key Constraint Violations**: ошибки внешних ключей при разрыве связей без включенного `orphanRemoval`.

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«orphanRemoval и CascadeType.REMOVE — это абсолютно одно и то же»* — Грубая ошибка. REMOVE срабатывает только при удалении родителя; orphanRemoval — при удалении из коллекции.
- ❌ *«Я могу повесить orphanRemoval = true на связь @ManyToOne»* — Запрещено JPA, имеет смысл только для композиций с монопольным владением (`@OneToMany`, `@OneToOne`).
- ❌ *«Чтобы обновить коллекцию, я просто вызываю entity.setItems(newItems)»* — Приведет к `HibernateException: A collection was no longer referenced`.
- ❌ *«orphanRemoval удаляет запись из базы прямо в момент вызова list.remove()»* — Нет, удаление происходит во время фазы `flush()`.
