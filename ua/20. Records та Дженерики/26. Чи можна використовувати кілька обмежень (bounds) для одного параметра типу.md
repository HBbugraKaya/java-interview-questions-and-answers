# Чи можна використовувати кілька обмежень (bounds) для одного параметра типу

---

## 🟢 Junior Level

**Так, можна.** В Java параметр типу дженерика може мати кілька обмежень (**multiple bounds**), які перераховуються через символ амперсанда **`&`**:

```java
// T зобов'язаний одночасно бути підкласом Number ТА реалізовувати інтерфейс Comparable<T>
public class SortedNumberBox<T extends Number & Comparable<T>> {
    private final T value;

    public SortedNumberBox(T value) {
        this.value = value;
    }

    public boolean isGreaterThan(T other) {
        // Доступні методи обох типів: Number (doubleValue) та Comparable (compareTo)
        return value.compareTo(other) > 0;
    }
}
```

### Головні синтаксичні правила
1. **Тільки один клас:** В Java заборонено множинне наслідування класів, тому в списку обмежень може бути присутнім **максимум один клас**.
2. **Клас завжди йде першим:** Якщо серед обмежень є клас, він зобов'язаний стояти на першому місці, а за ним можуть слідувати один або кілька інтерфейсів.
   ```java
   // ✅ Коректно: клас на першому місці, потім інтерфейс
   <T extends Number & Runnable>

   // ❌ Помилка компіляції: interface expected here
   // <T extends Runnable & Number>
   ```

## 🟡 Middle Level

### Механізм стирання типів при множинних межах (Erasure to First Bound)

Відповідно до специфікації Java Language Specification (JLS §4.6), типом стирання змінної типу з множинними межами завжди стає її **перша ліва межа (leftmost bound)**:

```java
public class Processor<T extends Number & Serializable> {
    public void execute(T item) {
        double d = item.doubleValue(); // Виклик методу першого типу
        serialize(item);              // Передача у другий інтерфейс
    }

    private void serialize(Serializable s) { /* ... */ }
}
```

Що компілятор генерує в байткоді:
1. Тип змінної `item` стирається до `java.lang.Number`:
   ```bytecode
   public void execute(java.lang.Number item);
   ```
2. Виклики методів першого обмеження (`Number.doubleValue()`) виконуються безпосередньо через `invokevirtual`.
3. При зверненні до методів наступних обмежень (`Serializable`) компілятор автоматично вставляє інструкцію приведення типу **`checkcast`**:
   ```bytecode
   aload_1
   checkcast     #4 // class java/io/Serializable
   invokevirtual #5 // Method serialize:(Ljava/io/Serializable;)V
   ```

> [!TIP]
> З міркувань мікрооптимізації та чистоти байткоду на перше місце серед інтерфейсів рекомендується ставити той, до чиїх методів звернення відбуваються найчастіше — це мінімізує кількість згенерованих інструкцій `checkcast`.

## 🔴 Senior Level

### Intersection Types у виразах приведення типів (Casts)

Починаючи з Java 8, множинні обмеження типу вийшли за межі оголошень класів і методів та стали частиною **Intersection Types** у виразах явного приведення типів (JLS §15.16):

```java
// Приведення лямбди одночасно до інтерфейсу Runnable та Serializable
Runnable task = (Runnable & Serializable) () -> System.out.println("Distributed task");
```

#### Навіщо це потрібно на практиці:
У розподілених обчислювальних системах (таких як **Apache Spark**, **Apache Flink**, **Hazelcast**) функції та лямбди передаються мережею на робочі вузли кластера (Workers). Лямбда за замовчуванням не реалізує інтерфейс `java.io.Serializable`. Використання intersection cast дозволяє змусити компілятор згенерувати лямбда-клас, який реалізує обидва інтерфейси, без необхідності оголошувати проміжний інтерфейс `interface SerializableRunnable extends Runnable, Serializable`.

### Конфлікти сигнатур при множинних межах

Якщо кілька інтерфейсів оголошують методи з однаковою сигнатурою, набувають чинності суворі правила компіляції:

#### 1. Несумісні типи значень, що повертаються
```java
interface ReaderA { String read(); }
interface ReaderB { Integer read(); }

// ❌ Помилка компіляції: methods have unrelated return types
// class Service<T extends ReaderA & ReaderB> { }
```
Не існує типу, здатного одночасно повернути `String` та `Integer` з методу з однаковим ім'ям та аргументами.

#### 2. Конфлікт Default-методів
Якщо два інтерфейси оголошують дефолтні методи з однаковою сигнатурою:
```java
interface Alpha { default void run() { System.out.println("A"); } }
interface Beta  { default void run() { System.out.println("B"); } }

// ❌ Помилка компіляції: types Alpha and Beta are incompatible;
// both define run() with identical signature
// class Worker<T extends Alpha & Beta> { }
```
Конфлікт множинного наслідування інтерфейсів припиняється компілятором на етапі оголошення параметра типу.

## 4 Tricky Questions

### 1. Чи можна використовувати множинні обмеження в підстановочних знаках (Wildcards), наприклад `List<? extends Number & Comparable>`?
**Відповідь:**  
**Ні, синтаксис Wildcards не підтримує множинні обмеження** (JLS §4.5.1). Запис `<? extends A & B>` викличе помилку компіляції.  
Якщо методу необхідно прийняти колекцію елементів, що задовольняють кілька меж одночасно, слід оголосити generic-метод з іменованим параметром типу:
```java
// ❌ Помилка компіляції:
// public void process(List<? extends Number & Comparable<?>> list)

// ✅ Правильне рішення:
public <T extends Number & Comparable<?>> void process(List<T> list) { /* ... */ }
```

### 2. Чи має значення порядок інтерфейсів, якщо клас в обмеженнях відсутній (`<T extends A & B>` vs `<T extends B & A>`)?
**Відповідь:**  
Так, має вирішальне значення для скомпільованого байткоду!  
Стирання типу (Type Erasure) завжди відбувається до **першої** межі в списку:
- Для `<T extends Comparable<?> & CharSequence>` стертим типом у дескрипторах методів буде `Comparable`.
- Для `<T extends CharSequence & Comparable<?>>` стертим типом буде `CharSequence`.  
Це впливає на бінарну сумісність публічного API бібліотеки і на те, до якого типу JVM вставляє інструкції `checkcast`.

### 3. Чи можна оголосити локальну змінну типу Intersection Type?
**Відповідь:**  
До Java 10 оголосити змінну перетину типів безпосередньо було неможливо (синтаксис `(Runnable & Serializable) x` неприпустимий для типів змінних).  
Однак починаючи з Java 10 із введенням виведення типів через **`var`**, компілятор може вивести тип перетину для змінної:
```java
var task = (Runnable & Serializable) () -> {};
// Тип змінної task виводиться компілятором як невиразний у синтаксисі тип перетину:
// Runnable & Serializable
task.run(); // ✅ Доступно з Runnable
boolean isSerializable = task instanceof Serializable; // ✅ true
```

### 4. Як отримати всі межі типу через Reflection API в runtime?
**Відповідь:**  
За допомогою методу `TypeVariable.getBounds()`:
```java
TypeVariable<?>[] typeParameters = SortedNumberBox.class.getTypeParameters();
Type[] bounds = typeParameters[0].getBounds();
for (Type bound : bounds) {
    System.out.println(bound.getTypeName());
}
// Виведе:
// java.lang.Number
// java.lang.Comparable<T>
```
Інформація про межі зберігається в сигнатурі класу (атрибут `Signature`) і доступна для рефлексивного аналізу.

## 🎯 Шпаргалка для інтерв'ю

- **Синтаксис:** Перераховуються через амперсанд: `<T extends Class & Interface1 & Interface2>`.
- **Правило першого елемента:** Клас може бути тільки один і зобов'язаний стояти **суворо на першому місці**. Усі інші межі — тільки інтерфейси.
- **Стирання типів (Type Erasure):** Відбувається до **першої лівої межі**. Для виклику методів наступних інтерфейсів `javac` генерує інструкції `checkcast`.
- **Wildcard пастка:** Для підстановочних знаків множинні обмеження заборонені (`<? extends A & B>` не компілюється); замість цього оголошують метод `<T extends A & B> void foo(List<T> list)`.
- **Intersection Types у лямбдах:** `(Runnable & Serializable) () -> ...` — застосовується в розподілених системах (Apache Spark/Flink) для серіалізації лямбд мережею.
- **Змінна `var`:** Дозволяє захоплювати перетини типів у локальних змінних (`var x = (A & B) obj`).
