# Как избежать race condition

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
Для предотвращения **Race Condition (состояния гонки)** в Java применяются четыре фундаментальные архитектурные стратегии:

1. **Взаимное исключение (Mutual Exclusion):** защита критических секций с помощью блокировок (`synchronized`, `ReentrantLock`), гарантирующих, что составные операции выполняются только одним потоком одновременно.
2. **Атомарные неблокирующие операции (Lock-Free):** использование классов пакета `java.util.concurrent.atomic` (`AtomicInteger`, `AtomicReference`, `LongAdder`), которые опираются на аппаратные инструкции процессора CAS (`Compare-And-Swap`).
3. **Неизменяемость (Immutability):** проектирование неизменяемых объектов данных (в Java 21 идеально подходят `record` с `final`-полями). Если состояние объекта невозможно изменить после создания, состояние гонки невозможно по определению.
4. **Изоляция потоков (Thread Confinement):** устранение разделения данных между потоками через локальные переменные стека или `ThreadLocal` (каждый поток оперирует собственной изолированной копией).

---

### Сравнительная таблица стратегий

| Стратегия | Инструменты в Java 21 | Плюсы | Минусы |
|---|---|---|---|
| **Пессимистичная блокировка** | `synchronized`, `ReentrantLock` | Защищает любые сложные составные транзакции | Накладные расходы на context switch, риск Deadlock |
| **Оптимистичный Lock-Free** | `AtomicInteger`, `LongAdder` | Максимальная скорость (~5–10 ns), нет Deadlock | Применимо только к отдельным полям/переменным |
| **Неизменяемость** | `record`, `Collections.unmodifiable*` | Абсолютная потокобезопасность «из коробки» | Нагрузка на GC из-за создания новых копий при записи |
| **Изоляция потоков** | Стек метода, `ThreadLocal`, `ScopedValue` | Нулевая конкуренция за память, 100% изоляция | Риск утечек памяти в пулах потоков (`ThreadLocal`) |

---

### Примеры на Java 21

```java
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.ConcurrentHashMap;

public class RaceConditionPreventionDemo {

    // 1. Устранение гонки через Atomic-класс (Lock-free инкремент)
    public static class SafeCounter {
        private final AtomicInteger count = new AtomicInteger(0);
        public void increment() { count.incrementAndGet(); }
        public int get() { return count.get(); }
    }

    // 2. Устранение гонки через Immutability (Java 21 Record)
    public record UserProfile(long id, String name, String email) {
        // Защитный конструктор (Compact Constructor)
        public UserProfile {
            if (name == null) throw new IllegalArgumentException();
        }
    }

    // 3. Устранение гонки Check-Then-Act через ConcurrentHashMap
    public static class CacheService {
        private final ConcurrentHashMap<String, String> cache = new ConcurrentHashMap<>();

        public String getOrCompute(String key) {
            // Атомарная проверка и вставка: функция вызовется ровно один раз!
            return cache.computeIfAbsent(key, k -> "ComputedValueFor_" + k);
        }
    }
}
```

## 🟡 Middle Level

### Безопасная публикация объектов (Safe Publication)

Одной из самых коварных разновидностей Race Condition является **гонка публикации (Publication Race)**, когда другой поток видит ссылку на созданный объект, но его поля ещё не успели инициализироваться (чтение частично сконструированного объекта).

#### 4 способа гарантированно безопасной публикации по спецификации JMM:
1. **Инициализация в `final`-полях:** спецификация JLS (§17.5) гарантирует «заморозку» (`freeze action`) значений всех `final`-полей объекта при выходе из конструктора, если ссылка `this` не утекла во время конструирования.
2. **Инициализация в статическом инициализаторе класса:** гарантия ClassLoader JVM (потокобезопасная ленивая инициализация через `Holder Pattern` / `Bill Pugh Singleton`).
3. **Запись ссылки в `volatile`-поле:** выставляет барьер памяти `StoreStore`, гарантируя завершение инициализации всех полей объекта до публикации ссылки.
4. **Публикация через монитор `synchronized` или `ReentrantLock`:** гарантирует отношение Happens-Before между выходом из блокировки в одном потоке и входом в другом.

```java
// Идиома потокобезопасной ленивой инициализации без синхронизации (Initialization-on-demand holder):
public class GlobalServiceRegistry {
    private GlobalServiceRegistry() {}

    private static class Holder {
        // ClassLoader гарантирует неделимую и потокобезопасную инициализацию!
        private static final GlobalServiceRegistry INSTANCE = new GlobalServiceRegistry();
    }

    public static GlobalServiceRegistry getInstance() {
        return Holder.INSTANCE;
    }
}
```

### Атомарные композитные методы коллекций

Типичная ошибка Junior/Middle — использование раздельных методов у потокобезопасной коллекции:

```java
// ГОНКА: два потока могут одновременно пройти проверку containsKey!
if (!map.containsKey(key)) {
    map.put(key, value);
}

// РЕШЕНИЕ 1: Атомарная вставка при отсутствии
map.putIfAbsent(key, value);

// РЕШЕНИЕ 2: Атомарное ленивое вычисление (идеально для тяжелых объектов)
map.computeIfAbsent(key, k -> createHeavyResource(k));

// РЕШЕНИЕ 3: Атомарное слияние (счётчик слов / агрегация)
map.merge(word, 1, Integer::sum);
```

---

### Изоляция потоков (Thread Confinement)

Если данные доступны строго одному потоку, синхронизация не требуется вовсе:
1. **Stack Confinement (Изоляция на стеке):** переменные, созданные внутри метода, хранятся в стековом фрейме конкретного потока и физически недоступны другим потокам.
2. **ThreadLocal Confinement:** хранение состояния в `ThreadLocal`. Обязательно требует вызова `remove()` в блоке `finally` при работе с пулами потоков.

## 🔴 Senior Level

### Аппаратный уровень: Архитектура ARM против x86

Многие состояния гонки, остающиеся незамеченными на ноутбуках с Intel x86, мгновенно взрываются при деплое в облако на серверы с процессорами **ARM64 (AWS Graviton, Apple Silicon, Ampere)**.

#### Причина в модели памяти процессоров:
- **x86 (TSO — Total Store Order):** аппаратно строгая модель памяти. Процессор x86 аппаратно запрещает почти все виды переупорядочивания инструкций (запрещены `StoreStore`, `LoadLoad`, `LoadStore`), допуская только `StoreLoad`. Многие некорректные программы без синхронизации случайно работают на x86 стабильно!
- **ARM64 / Apple Silicon (Weak Memory Order):** слабоупорядоченная модель памяти. Процессор агрессивно переупорядочивает любые независимые чтения и записи памяти для максимального параллелизма микроопераций. Несинхронизированный код на ARM мгновенно читает устаревшие значения и повреждённые ссылки.

---

### Java 21 Scoped Values (JEP 446 / JEP 429)

В Java 21 представлена замена устаревшему механизму `ThreadLocal` — **`ScopedValue`**, разработанная специально для работы с миллионами виртуальных потоков (Virtual Threads):

```java
public class SecurityContextHolder {
    // Неизменяемое значение, привязанное к скоупу выполнения
    public static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

    public void processRequest(User user) {
        // Контекст безопасно и эффективно пробрасывается в вызовы:
        ScopedValue.where(CURRENT_USER, user).run(() -> {
            doStep1();
            doStep2();
        }); // Автоматически очищается при выходе из скоупа!
    }

    private void doStep1() {
        User user = CURRENT_USER.get();
    }
}
```

#### Преимущества перед `ThreadLocal`:
1. **Иммутабельность:** значение `ScopedValue` невозможно мутировать изнутри задачи, исключая гонки изменений.
2. **Ограниченное время жизни:** привязано к лексическому блоку исполнения; исключает утечки памяти (Memory Leaks) в переиспользуемых пулах потоков без необходимости вызова `remove()`.
3. **Оптимизация под Virtual Threads:** занимает минимум памяти и легко наследуется миллионами дочерних виртуальных потоков в Structured Concurrency.

---

### Архитектурные парадигмы без изменяемого разделяемого состояния

Senior-разработчики стремятся избегать Race Condition на уровне системного дизайна:
1. **Actor Model (Акторная модель):** сущности не делят общее состояние в памяти, а обмениваются асинхронными неизменяемыми сообщениями через почтовые ящики (Mailbox).
2. **Event Sourcing & CQRS:** состояние системы восстанавливается из цепочки неизменяемых событий (Events), исключая параллельные перезаписи одной сущности в оперативной памяти.
3. **Copy-On-Write (Копирование при записи):** структуры `CopyOnWriteArrayList` оптимизированы под сценарий: 99% быстрых чтений без блокировок, 1% записей с созданием новой копии базового массива.

## 🎯 Шпаргалка для интервью

### 1. 30-секундный эссенс (Elevator Pitch)
Избежать Race Condition можно через: взаимное исключение (`synchronized`/`ReentrantLock`), неблокирующие CAS-структуры (`Atomic*`, `LongAdder`), архитектурную неизменяемость (`record` с `final`-полями) и изоляцию данных на стеке потока или в `ThreadLocal`/`ScopedValue`. При использовании `ConcurrentHashMap` критично применять атомарные методы (`computeIfAbsent`, `merge`) вместо парных вызовов `containsKey()` + `put()`. На процессорах ARM64 со слабой моделью памяти (AWS Graviton) ошибки синхронизации проявляются значительно агрессивнее, чем на x86.

### 2. 4 каверзных вопроса с глубокими ответами

#### Вопрос 1: Почему ключевое слово `final` гарантирует потокобезопасную публикацию объекта без блокировок, и при каком условии эта гарантия нарушается?
**Ответ:**
Спецификация модели памяти Java (JSR-133 / JLS §17.5) вводит правило **«Final Field Freeze»**: к моменту завершения конструктора объекта JVM вставляет процессорный барьер памяти `StoreStore`, который сбрасывает значения всех `final`-полей из регистров и буферов записи в память до того, как ссылка на новый объект станет доступна другим потокам. Читающие потоки гарантированно увидят актуальные значения `final`-полей даже при чтении ссылки через несинхронизированное обращение.  
*Условие нарушения:* если ссылка `this` «утекает» из конструктора до его завершения (например, передача `this` в слушатель событий, статический список или запуск потока прямо из конструктора). В этом случае гарантия JMM полностью аннулируется.

#### Вопрос 2: В чём архитектурное преимущество `ConcurrentHashMap.computeIfAbsent()` перед традиционной связкой `get()` + `synchronized` + `put()`?
**Ответ:**
1. **Атомарность без глобальной блокировки:** `computeIfAbsent()` блокирует только конкретную корзину (bucket / узел хеш-таблицы) через тонкий замок на уровне первой ноды, не блокируя остальные корзины мапы.
2. **Гарантия однократного вычисления (Single Execution):** переданная лямбда-функция вычисления ресурса гарантированно выполнится **ровно один раз** для заданного ключа, предотвращая дублирование тяжелых инициализаций (например, соединений с БД).
3. **Устранение гонки Check-Then-Act:** проверка наличия ключа и вставка нового узла объединены в единую неделимую операцию под контролем внутреннего механизма коллекции.

#### Вопрос 3: Почему ошибки Race Condition значительно чаще проявляются на процессорах архитектуры ARM (Apple Silicon, AWS Graviton), чем на Intel x86?
**Ответ:**
Процессоры архитектуры x86 реализуют модель памяти **TSO (Total Store Order)**, которая аппаратно гарантирует сохранение порядка практически всех чтений и записей (за исключением `StoreLoad`). На x86 компилятор JIT опускает многие барьеры памяти, так как железо само упорядочивает инструкции.  
Процессоры ARM64 используют модель со **слабым порядком памяти (Weak Ordering)**. Ядро процессора активно переставляет местами независимые инструкции чтения и записи для максимальной утилизации вычислительных конвейеров. Если в Java-коде пропущена синхронизация или `volatile`, процессор ARM немедленно произведет переупорядочивание, вызвав чтение устаревших данных.

#### Вопрос 4: Как механизм `ScopedValue` в Java 21 решает проблемы производительности и утечек памяти традиционного `ThreadLocal`?
**Ответ:**
1. **Защита от утечек:** `ThreadLocal` живёт в карте потока `threadLocals` до явного вызова `remove()`. В пулах потоков забытый `remove()` приводит к утечкам памяти в Metaspace и загрязнению контекста между задачами. `ScopedValue` привязан к лексическому блоку выполнения (`where().run(...)`) и очищается средой исполнения автоматически при выходе из скоупа.
2. **Неизменяемость:** значение `ScopedValue` нельзя перезаписать после привязки к скоупу, что гарантирует безопасность передачи контекста.
3. **Масштабируемость:** `ScopedValue` оптимизирован для миллионов виртуальных потоков (Project Loom): дочерние потоки могут разделять контекст родителя по ссылке без дублирования хеш-таблиц.

### 3. Типичные ошибки и Red Flags

❌ **"Использование `Collections.synchronizedList()` делает любой обход по списку потокобезопасным."**  
*Правильно:* Синхронизированы только отдельные методы (`add`, `get`). Итерация через цикл `for (Item x : list)` поверх `synchronizedList` **обязана** быть явно обёрнута в `synchronized(list)`, иначе параллельная модификация списка выбросит `ConcurrentModificationException`.

❌ **"Утечка `this` в конструкторе при наличии `final`-полей."**  
*Правильно:* Передача `this` во внешние структуры до завершения конструктора лишает объект гарантий потокобезопасной публикации JMM.

❌ **"Использование `CopyOnWriteArrayList` в коллекциях с высокой частотой записи."**  
*Правильно:* Каждая операция добавления или удаления копирует весь базовый массив в куче (`Arrays.copyOf`), что создаёт чудовищную нагрузку на сборщик мусора при частых мутациях.
