# Что такое GC roots

---

## 🟢 Junior Level

**GC Roots (корни сборщика мусора)** — это специальные базовые объекты в памяти Java, которые считаются априори живыми и служат отправной точкой для алгоритма обхода графа достижимости (**Reachability Analysis**).

### Простая аналогия
Представьте генеалогическое дерево. Корни дерева — это GC Roots. Сборщик мусора начинает движение от корней и по ссылкам спускается к ветвям и листьям (обычным объектам в куче). Любой объект, до которого можно проследить непрерывную цепочку ссылок хотя бы от одного корня, признаётся **живым**. Если объект изолирован от всех корней (даже если он входит в группу циклических ссылок), он считается мусором и подлежит утилизации.

```
[GC Root: Локальная переменная стека]
        │
        ▼
   [Объект A] ──► [Объект B] ──► [Объект C]   <-- ВСЕ ЖИВЫ (достижимы)

   [Объект D] ◄───► [Объект E]                <-- МУСОР (не достижимы от GC Root,
                                                   хотя ссылаются друг на друга)
```

### Основные категории GC Roots:
1. **Локальные переменные и параметры методов** в стеках активных потоков;
2. **Статические поля классов**, загруженных в JVM;
3. **Активные объекты потоков** (`Thread`);
4. **JNI-ссылки** (глобальные и локальные ссылки в нативном C/C++ коде);
5. **Объекты-мониторы**, удерживаемые в блоках `synchronized`.

## 🟡 Middle Level

### 1. Исчерпывающая классификация GC Roots в HotSpot

Внутренняя архитектура HotSpot классифицирует корни на несколько строгих категорий:

| Категория GC Root | Описание | Место хранения |
| :--- | :--- | :--- |
| **`Stack Local`** | Локальные переменные и операнды методов, исполняемых в текущих стековых фреймах. | Thread Stack |
| **`Static Field`** | Ссылки, хранящиеся в статических полях загруженных классов (в зеркалах `java.lang.Class`). | Java Heap |
| **`Active Thread`** | Сами объекты живых потоков (`java.lang.Thread`), зарегистрированные в планировщике JVM. | Heap / Thread Table |
| **`JNI Global`** | Глобальные ссылки, созданные нативным кодом через `(*env)->NewGlobalRef`. | JNI Global Table |
| **`JNI Local`** | Аргументы и локальные переменные нативных C-функций (`NewLocalRef`). | C-Stack фрейма JNI |
| **`Monitor Used`** | Объекты, на которых в данный момент захвачен монитор синхронизации (`synchronized`). | ObjectMonitor list |
| **`JVM Internal`** | Системные объекты JVM: базовые загрузчики классов (Bootstrap/Platform ClassLoader), таблица интернированных строк (`StringTable`), исключения OutOfMemoryError. | JVM Native Runtime |

```
+-------------------------------------------------------------------------+
|                              МНОЖЕСТВО GC ROOTS                         |
+-------------------------------------------------------------------------+
|  [Стеки потоков]        [Классы и статика]      [Нативные JNI-ссылки]   |
|  - Frame 1: userRef     - AppConfig.INSTANCE   - NewGlobalRef(callback)|
|  - Frame 2: buffer      - DatabasePool.cache   - JNI local references  |
|                                                                         |
|  [Системные сущности]   [Блокировки]                                   |
|  - Thread instances     - Synchronized objects (ObjectMonitor)         |
|  - System ClassLoaders  - JVM interned string pool                     |
+-------------------------------------------------------------------------+
```

### 2. Точный сбор мусора (Exact GC) и OopMaps

Стековый фрейм потока в операционной системе представляет собой массив 64-битных ячеек памяти. В ячейке может лежать как примитивное число `long` со значением `0x7fa281c00`, так и реальный указатель на объект по адресу `0x7fa281c00`.

Как JVM понимает, что перед ней: число или ссылка на объект?
- В ранних виртуальных машинах использовался **Conservative GC** (консервативный сборщик), который считал любое значение, похожее на валидный адрес в куче, потенциальным объектом. Это приводило к ложным удержаниям памяти.
- HotSpot является **Exact (Precise) GC** (точным сборщиком мусора). JIT-компилятор во время компиляции байткода генерирует специальные карты указателей — **OopMaps** (*Ordinary Object Pointer Maps*).
- Для каждой инструкции точки останова (**Safepoint**) в OopMap жестко зафиксировано: какие именно регистры процессора и какие смещения на стеке содержат ссылки на объекты, а какие — примитивные типы.
- Благодаря OopMaps фаза сканирования корней (**Root Scanning**) занимает доли миллисекунды, так как сборщик мусора обходит только гарантированные ссылки.

## 🔴 Senior Level

### 1. Масштабируемость Root Scanning и Handshakes

Фаза поиска и обхода корней традиционно являлась частью Stop-The-World паузы. Если в приложении запущены десятки тысяч потоков (например, до перехода на виртуальные потоки) или загружены миллионы статических ссылок, время сканирования стеков (**Root Scanning Time**) может вырасти до десятков миллисекунд:

$$\text{Время паузы STW} \ge \text{Время остановки потоков (TTSP)} + \text{Root Scanning Time}$$

#### Современная оптимизация: Thread-Local Handshakes (JEP 312, Java 10+)
Вместо остановки всех потоков одновременно ради сканирования стеков:
- JVM выполняет персональные «рукопожатия» (*Handshakes*) с каждым отдельным потоком;
- В ZGC и Shenandoah сканирование стека потока выполняется в момент, когда сам поток достигает точки паузы, не останавливая глобально всю систему.

### 2. Утечки памяти через JNI Global References

Одной из самых опасных и трудноуловимых утечек в корпоративных приложениях является утечка через JNI:

```c
// Нативный код C/C++ через JNI:
JNIEXPORT void JNICALL Java_com_example_NativeBridge_registerListener(JNIEnv *env, jobject caller, jobject listener) {
    // Создание глобального GC Root!
    jobject globalListener = (*env)->NewGlobalRef(env, listener);
    // Если разработчик забыл вызвать (*env)->DeleteGlobalRef(env, globalListener),
    // объект listener навсегда становится бессмертным GC Root.
}
```

- В Eclipse MAT такие объекты идентифицируются в дереве корней как **`JNI Global`**.
- Опасность заключается в том, что утечка инициируется на уровне C/C++, где отсутствуют средства автоматического управления памятью, а Java-код не имеет возможности сбросить эту ссылку.

### 3. Где хранятся статические поля: миф о Metaspace

> [!IMPORTANT]
> **Частое заблуждение на собеседованиях:** «Статические переменные хранятся в Metaspace».
> **Реальность HotSpot:** Начиная с Java 7 (и окончательно закреплено в Java 8 с удалением PermGen), все статические переменные классов хранятся в **Java Heap** внутри зеркального объекта `java.lang.Class`. В Metaspace хранятся только нативные метаданные структуры `Klass` (таблицы методов, аннотации, байткод). Сам объект `Class` лежит в куче, и его поля являются полноценными корнями GC Roots.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ для собеседования
> «GC Roots — это базовое множество объектов, гарантированно считающихся живыми, от которых сборщик мусора начинает трассировку графа достижимости объектов в куче. В число GC Roots входят: локальные переменные и операнды на стеках активных потоков, статические поля загруженных классов, сами объекты живых потоков, глобальные и локальные ссылки JNI, а также объекты, на которых захвачены блокировки `synchronized`. HotSpot является точным сборщиком мусора и с помощью сгенерированных компилятором карт указателей (OopMaps) мгновенно отличает на стеке ссылки на объекты от примитивных чисел».

### Вопросы повышенной сложности с ответами

1. **Где физически располагаются статические переменные классов и почему они являются GC Roots?**
   *Ответ:* В современных версиях Java (начиная с Java 7/8) статические переменные физически располагаются в обычной куче (Java Heap) внутри объекта-зеркала `java.lang.Class`. Пока загрузчик классов (`ClassLoader`), загрузивший этот класс, остаётся живым, сам объект `Class` достижим, а его статические поля выступают в качестве активных GC Roots, удерживая весь граф дочерних объектов.

2. **Как HotSpot JVM определяет, является ли 64-битное значение на стеке ссылкой или примитивным типом `long`?**
   *Ответ:* HotSpot является точным сборщиком мусора (*Exact GC*). Во время JIT-компиляции для каждой безопасной точки останова (*Safepoint*) генерируются структуры **OopMaps** (*Ordinary Object Pointer Maps*). В OopMap для каждого машинного адреса указано, какие регистры процессора и какие ячейки стека в данный момент содержат ссылки на объекты. При остановке потока GC обращается к OopMap и читает только валидные ссылки, не тратя время на догадки и сканирование примитивов.

3. **Будет ли удален объект, на котором висит блок `synchronized`, если все ссылки на него в Java-коде занулили?**
   *Ответ:* Нет, объект не будет удален до тех пор, пока поток не покинет блок `synchronized`. Объект, чей внутренний монитор (`ObjectMonitor`) в данный момент удерживается или ожидается живым потоком, автоматически регистрируется в списке мониторов виртуальной машины и признаётся системным корнем **Monitor Used GC Root**.

4. **Что происходит с фазой Root Scanning при увеличении числа потоков с 200 до 10 000?**
   *Ответ:* Фаза сканирования корней линейно масштабируется от количества активных потоков, так как сборщику мусора необходимо обойти стек каждого потока. Большое число потоков увеличивает длительность паузы Stop-the-World. Для решения этой проблемы в современной Java внедрены механизм Thread-Local Handshakes и легковесные виртуальные потоки (Virtual Threads / Project Loom), чьи стеки хранятся в куче как обычные объекты и не требуют сканирования отдельных стеков ядра ОС.

### Типичные ошибки и Red Flags
- ❌ **Утверждать, что GC Roots — это исключительно статические переменные.** (Red Flag: игнорирование стеков потоков, мониторов и нативных ссылок JNI).
- ❌ **Считать, что сборщик мусора сканирует всю память вслепую в поисках любых адресов.** (Заблуждение: незнание концепции Exact GC и OopMaps).
- ❌ **Утверждать, что статические переменные лежат в Metaspace.** (В Metaspace хранятся метаданные C++ `Klass`, а статические поля лежат в объекте `java.lang.Class` в Java Heap).
