# У чому переваги Decorator перед успадкуванням

---

## 🟢 Junior Level

**Decorator (Декоратор / Обгортка / Wrapper)** — це структурний патерн проєктування, призначений для динамічного додавання об'єкту нових обов'язків та функціональності без зміни його вихідного коду і без використання наслідування.

---

### Головна проблема наслідування: Комбінаторний вибух класів

Уявімо систему розрахунку вартості кави з опціональними додатками (молоко, цукор, сироп). Якщо використовувати звичайне наслідування, для кожної можливої комбінації доведеться створювати окремий підклас:

```
Ієрархія при наслідуванні:
                  Coffee
         ┌───────────┼───────────┐
     MilkCoffee  SugarCoffee  SyrupCoffee
         ┌───────────┴───────────┐
  MilkSugarCoffee         MilkSyrupCoffee
         │
  MilkSugarSyrupCoffee (для n додатків потрібно створити 2^n класів!)
```

При 10 різних додатках вам знадобиться створити $2^{10} = 1024$ класи, що перетворює архітектуру на некерований кошмар підтримки.

---

### Рішення через Decorator

Замість наслідування застосовується **композиція**: декоратор реалізує той самий інтерфейс, що й об'єкт, який декорується, та зберігає посилання на нього:

```java
// Спільний інтерфейс
public interface Beverage {
    String getDescription();
    double getCost();
}

// Базовий компонент
public class Espresso implements Beverage {
    public String getDescription() { return "Еспресо"; }
    public double getCost() { return 60.0; }
}

// Базовий абстрактний декоратор
public abstract class BeverageDecorator implements Beverage {
    protected final Beverage wrapped;

    public BeverageDecorator(Beverage wrapped) {
        this.wrapped = wrapped;
    }
}

// Конкретні декоратори
public class MilkDecorator extends BeverageDecorator {
    public MilkDecorator(Beverage wrapped) { super(wrapped); }

    public String getDescription() { return wrapped.getDescription() + ", Молоко"; }
    public double getCost() { return wrapped.getCost() + 20.0; }
}

public class SugarDecorator extends BeverageDecorator {
    public SugarDecorator(Beverage wrapped) { super(wrapped); }

    public String getDescription() { return wrapped.getDescription() + ", Цукор"; }
    public double getCost() { return wrapped.getCost() + 5.0; }
}

// Використання: будь-яка комбінація в runtime без створення нових класів!
public class Main {
    public static void main(String[] args) {
        Beverage order = new SugarDecorator(new MilkDecorator(new Espresso()));
        System.out.println(order.getDescription() + " = " + order.getCost() + " грн.");
        // Вивід: Еспресо, Молоко, Цукор = 85.0 грн.
    }
}
```

## 🟡 Middle Level

### Порівняльний аналіз: Наслідування проти Декоратора

| Критерій | Наслідування (Inheritance) | Декоратор (Decorator) |
|---|---|---|
| **Зв'язування (Binding)** | **Статичне (Compile-time):** поведінка жорстко зафіксована на етапі компіляції. | **Динамічне (Runtime):** поведінка гнучко конструюється під час роботи програми. |
| **Кількість класів** | Зростає експоненціально ($2^n$ для $n$ опцій). | Зростає лінійно ($n$ класів декораторів). |
| **Принцип єдиної відповідальності (SRP)** | Клас-нащадок перевантажений різнорідними обов'язками. | Кожен окремий обов'язок ізольований у власному класі-декораторі. |
| **Гнучкість комбінацій** | Неможливо змінити поведінку вже створеного об'єкта. | Можна огортати об'єкт новими шарами на льоту в будь-якому порядку. |

### Класичний приклад із Java SE: Пакет `java.io`

Уся підсистема вводу-виводу стандартної бібліотеки Java побудована на патерні Decorator:

```java
import java.io.BufferedInputStream;
import java.io.FileInputStream;
import java.io.InputStream;
import java.util.zip.GZIPInputStream;

InputStream stream = new BufferedInputStream(
                         new GZIPInputStream(
                             new FileInputStream("data.txt.gz")
                         )
                     );
```
- `FileInputStream` — базовий компонент (читає сирі байти безпосередньо з файлу).
- `GZIPInputStream` — декоратор (на льоту розпаковує стиснений потік байтів).
- `BufferedInputStream` — декоратор (додає буфер в оперативній пам'яті для прискорення читання).
Клієнтський код взаємодіє з усім ланцюжком через єдиний базовий інтерфейс `InputStream`.

### Розмежування структурних патернів: Decorator vs Proxy vs Adapter

| Патерн | Мета використання | Інтерфейс |
|---|---|---|
| **Decorator** | **Розширення функціональності:** додавання нової поведінки та обов'язків об'єкту. | Зберігає **той самий** інтерфейс. |
| **Proxy** | **Контроль доступу:** лінива ініціалізація, кешування, перевірка прав, логування. | Зберігає **той самий** інтерфейс. |
| **Adapter** | **Узгодження контрактів:** перетворення інтерфейсу одного класу в інтерфейс іншого. | **Змінює** інтерфейс на несумісний цільовий. |

## 🔴 Senior Level

### Принцип Composition over Inheritance та крихкість базового класу (Fragile Base Class)

Джошуа Блох у праці *Effective Java* (Item 18: «Надавайте перевагу композиції перед наслідуванням») виділяє фундаментальні ризики наслідування:
1. **Порушення інкапсуляції:** Клас-нащадок жорстко залежить від внутрішніх деталей реалізації методів базового класу. Якщо в новій версії бібліотеки зміниться логіка виклику внутрішніх методів (self-use), функціональність спадкоємця може непомітно зламатися.
2. **Проблема Decorator-обгорток (The "SELF" Problem):**
   Огорнутий базовий об'єкт нічого не знає про зовнішній декоратор. Якщо метод усередині цільового об'єкта викликає власний метод через `this.method()`, виклик піде в базову реалізацію, а **не через декоратор** (self-invocation bypass).
3. **Втрата ідентичності об'єкта (Object Identity):**
   Під час використання декораторів посилання на оригінальний об'єкт `original` і посилання на декоратор `decorator` — це різні об'єкти в купі (`original != decorator`). Методи `equals()`, `hashCode()` та порівняння через `==` можуть давати несподівані результати.

### Декоратори у веб-архітектурі та Spring Framework

У корпоративних системах патерн Decorator застосовується повсюдно:

#### 1. Сервлетні фільтри: `HttpServletRequestWrapper`
Якщо у фільтрі потрібно перехопити вхідний JSON, дешифрувати його або записати в журнал аудиту, створюється декоратор запиту:
```java
import jakarta.servlet.ServletInputStream;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletRequestWrapper;
import java.io.IOException;

public class DecryptingRequestWrapper extends HttpServletRequestWrapper {
    public DecryptingRequestWrapper(HttpServletRequest request) {
        super(request);
    }

    @Override
    public ServletInputStream getInputStream() throws IOException {
        // Повертаємо декорований потік із розшифруванням даних на льоту
        return new DecryptingServletInputStream(super.getInputStream());
    }
}
```

#### 2. Spring AOP як декларативний мета-декоратор
Анотації `@Transactional`, `@Cacheable`, `@Retryable` під капотом конструюють динамічні проксі / декоратори навколо бінів за допомогою CGLIB або JDK Dynamic Proxy, інкапсулюючи наскрізну функціональність (cross-cutting concerns).

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь (Elevator Pitch)
> «Головна перевага **Decorator** перед наслідуванням полягає в дотриманні принципу **Composition over Inheritance** та запобіганні комбінаторному вибуху класів ($2^n$ класів при наслідуванні проти $n$ класів декораторів). Декоратор дозволяє додавати обов'язки об'єкту **динамічно в runtime**, комбінуючи поведінку в будь-якому порядку без модифікації наявного коду (суворе дотримання принципу **Open/Closed**). У Java класичним прикладом є пакет `java.io` (`BufferedInputStream` поверх `FileInputStream`), а в Spring — обгортки сервлетних запитів (`HttpServletRequestWrapper`) та інфраструктура AOP».

---

### 3–4 каверзних запитання з відповідями

1. **Чим патерн Decorator відрізняється від Proxy, якщо обидва реалізують один і той самий інтерфейс і зберігають посилання на цільовий об'єкт?**
   - *Відповідь:* Різниця полягає в семантичному призначенні. **Decorator** застосовується для динамічного додавання нової функціональності та розширення поведінки (клієнт зазвичай сам складає ланцюжок обгорток). **Proxy** призначений для контролю доступу до об'єкта (ліниве завантаження, перевірка прав, кешування, віддалений виклик RPC) і, як правило, сам керує життєвим циклом цільового об'єкта, приховуючи його від клієнта.

2. **Що таке проблема «SELF» (The SELF Problem) під час використання декораторів?**
   - *Відповідь:* Декорований об'єкт не має зворотного посилання на зовнішній декоратор. Якщо метод усередині цільового об'єкта викликає інший власний метод через ключове слово `this`, виконання піде в обхід декоратора безпосередньо в базовий клас. Це може призвести до пропуску доданої декоратором логіки (наприклад, транзакційності чи логування).

3. **Чому підсистему `java.io` часто критикують, незважаючи на канонічне використання патерна Decorator?**
   - *Відповідь:* Для виконання найпростішої операції (наприклад, прочитати стиснутий текстовий рядок із файлу з буферизацією) розробник змушений створювати громіздкі ланцюжки інстанціювання з 3–4 класів (`new BufferedReader(new InputStreamReader(new GZIPInputStream(...)))`), що погіршує читабельність коду та викликає зайві алокації короткоживучих об'єктів у купі.

4. **Як Decorator вирішує проблему крихкого базового класу (Fragile Base Class)?**
   - *Відповідь:* Клас-нащадок жорстко залежить від внутрішньої реалізації методів базового класу і може зламатися при зміні його приватного коду. Декоратор залежить виключно від публічного контракту **інтерфейсу**, делегуючи виклики цільовому об'єкту як чорній скриньці, що робить архітектуру слабозв'язаною та стійкою до змін.

---

### Типові помилки та Red Flags

- 🚩 **Використання наслідування для додавання необов'язкових опцій** (створення класів-мутантів на кшталт `FastEncryptedCompressingFileStream`).
- 🚩 **Плутанина між Decorator та Adapter** (декоратор ніколи не змінює інтерфейс об'єкта, на відміну від адаптера).
- 🚩 **Використання порівняння за посиланням `==`** між декорованим об'єктом і оригіналом (ламає логіку в сетах, мапах та кешах).
- 🚩 **Ігнорування Spring AOP** при спробах вручну писати декоратори для аудиту, логування або керування транзакціями в Spring-додатках.
