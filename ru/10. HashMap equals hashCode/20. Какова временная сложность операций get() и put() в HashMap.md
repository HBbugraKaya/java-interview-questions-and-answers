# Какова временная сложность операций get() и put() в HashMap

---

## 🟢 Junior Level

В `HashMap` основные операции взаимодействия с элементами (`get`, `put`, `remove`, `containsKey`) в среднем выполняются за **константное время $O(1)$**, то есть практически мгновенно независимо от общего количества записей в таблице.

### Почему это работает так быстро:

1. **Мгновенное вычисление адреса:** Хеш-код ключа указывает точный номер бакета (индекс массива) за 1–2 такта процессора.
2. **Прямой доступ к памяти:** Доступ к ячейке массива по индексу `table[index]` происходит мгновенно ($O(1)$).
3. **Минимум сравнений:** При хорошем распределении хеш-кодов в бакете находится всего 1 узел. Значение возвращается сразу после быстрой проверки.

```java
import java.util.HashMap;
import java.util.Map;

public class ComplexityDemo {
    public static void main(String[] args) {
        Map<String, String> map = new HashMap<>();

        // Вставка: O(1) в среднем
        map.put("user_101", "Slava");

        // Поиск: O(1) в среднем
        String name = map.get("user_101");

        // Удаление: O(1) в среднем
        map.remove("user_101");
    }
}
```

> **Аналогия:** Представьте гардероб с пронумерованными номерками от 1 до 1 000 000. Чтобы забрать куртку, гардеробщик не осматривает все миллион вешалок по очереди ($O(N)$) — он сразу подходит к вешалке с номером вашего номерка ($O(1)$).

## 🟡 Middle Level

### Сводная таблица временной сложности

| Операция | Лучший случай | Средний случай | Худший случай (Java 7) | Худший случай (Java 8+) |
| :--- | :--- | :--- | :--- | :--- |
| **`get()`** | $O(1)$ | $O(1)$ | $O(N)$ (связный список) | $O(\log N)$ (RB-Tree)* |
| **`put()`** | $O(1)$ | $O(1)$ амортизированное | $O(N)$ | $O(\log N)$ (RB-Tree)* |
| **`remove()`** | $O(1)$ | $O(1)$ | $O(N)$ | $O(\log N)$ (RB-Tree)* |
| **`containsKey()`** | $O(1)$ | $O(1)$ | $O(N)$ | $O(\log N)$ (RB-Tree)* |
| **Итерация (`keySet`/`entrySet`)** | $O(C + N)$ | $O(C + N)$ | $O(C + N)$ | $O(C + N)$ |

*\*Примечание: Худший случай в Java 8+ равен $O(\log N)$ только при условии, что ключи реализуют `Comparable`. Если ключи не сравнимы, поиск по дереву при одинаковых хешах может деградировать до $O(N)$.*

### Амортизированная стоимость `put()`

Операция `put()` имеет амортизированную сложность $O(1)$, несмотря на то, что периодически срабатывает процедура ресайза (`resize()`), требующая создания нового массива и переноса всех элементов ($O(N)$).

#### Метод агрегатного анализа:
Ёмкость массива растет как геометрическая прогрессия: $16 \to 32 \to 64 \to \dots \to N$.
При добавлении $N$ элементов суммарное количество операций перемещения при всех ресайзах составляет:
$$1 + 2 + 4 + 8 + \dots + \frac{N}{2} = N - 1 \text{ операций}$$
Суммарные затраты на $N$ вставок:
$$\text{Cost} = N \text{ (базовые вставки)} + (N - 1) \text{ (копирования при ресайзах)} < 2N$$
Делим общую стоимость на количество операций:
$$\text{Amortized Cost} = \frac{2N}{N} = O(1)$$

### Временная сложность итерации: $O(\text{capacity} + \text{size})$

Время полного обхода коллекции (`for (Map.Entry<K, V> entry : map.entrySet())`) зависит **не только от числа элементов $N$, но и от размера массива бакетов $C$**.
Итератор обязан последовательно просканировать все ячейки массива `table` от $0$ до `capacity - 1`. Если создать `new HashMap<>(1_000_000)` и положить туда всего 2 элемента, итерация будет медленной ($O(1\,000_000)$), так как итератор будет проверять миллион пустых ячеек `null`.

## 🔴 Senior Level

### Потактовый разбор операции `get(key)` на уровне процессора

Реальная задержка (latency) операции `get()` складывается из следующих микроархитектурных этапов:

```java
final Node<K,V> getNode(int hash, Object key) {
    Node<K,V>[] tab; Node<K,V> first, e; int n; K k;
    if ((tab = table) != null && (n = tab.length) > 0 &&
        (first = tab[(n - 1) & hash]) != null) { // 1 & 2
        if (first.hash == hash && // 3
            ((k = first.key) == key || (key != null && key.equals(k)))) // 4 & 5
            return first;
        // ... обход цепочки / дерева ...
    }
    return null;
}
```

1. **Хеширование ключа (`hash(key)`):** `(h = key.hashCode()) ^ (h >>> 16)` — 2-3 такта CPU (побитовый сдвиг и XOR выполняются в регистрах за доли наносекунды).
2. **Расчет индекса:** `(n - 1) & hash` — 1 такт CPU.
3. **Чтение из массива (`tab[index]`):**
   - **L1/L2 Cache Hit:** 1–4 нс (если массив находится в процессорном кэше).
   - **RAM Cache Miss:** 60–100 нс (если таблица огромная и разбросана по памяти).
4. **Сравнение 32-битного хеша:** `first.hash == hash` — 1 такт CPU. Быстро отсекает ложные совпадения бакетов без обращения к полям объекта.
5. **Сравнение по ссылке (`first.key == key`):** 1 такт. Если ссылка совпала (например, один литерал строки), метод `equals()` не вызывается.
6. **Вызов `key.equals(k)`:** Зависит от реализации. Для простых классов — 2–5 нс. Для длинных `String` — зависит от длины строки $L$ ($O(L)$), оптимизируется SIMD-векторизацией (`ArraysSupport.mismatch`).

### Влияние CPU Cache Locality на асимптотику

Теоретическое равенство $O(\log N)$ для красно-чёрного дерева на практике может работать значительно медленнее, чем теоретическое $O(1)$:
- Узлы `TreeNode` создаются в разное время и хаотично раскиданы по адресной памяти кучи (Heap).
- При переходе по указателям `node.left` и `node.right` каждое разыменование ссылки с высокой вероятностью приводит к аппаратному промаху кэша (Cache Miss).
- Поиск в идеально сбалансированном дереве из 15 элементов ($4$ перехода по ссылкам) может занять до $4 \times 80 = 320$ нс, в то время как поиск в компактном непрерывном массиве из тех же 15 элементов с линейным сканированием ($O(N)$) благодаря аппаратному prefetcher процессора укладывается в 10–15 нс.

## 4 Tricky Questions

### 1. Может ли сложность `get()` в `HashMap` на Java 8+ стать $O(N)$, несмотря на использование красно-чёрных деревьев?

**Ответ:**
**Да, может.**
Красно-чёрное дерево обеспечивает гарантированное время $O(\log N)$ только в том случае, если узлы можно упорядочить в бинарном дереве поиска (BST).
`HashMap` упорядочивает узлы с одинаковым `hash` с помощью интерфейса `Comparable<K>`.
Если ключи:
1. Имеют одинаковый `hashCode()` (например, разработчик жестко захардкодил `return 42;`).
2. **НЕ реализуют** интерфейс `Comparable<K>` (или метод `compareTo` возвращает 0 для неравных ключей).

В этом случае при поиске внутри `TreeNode.find(int h, Object k, Class<?> kc)` алгоритм не знает, в какую ветвь идти (влево или вправо). Ему приходится **рекурсивно сканировать обе ветви** поддерева. Полный обход всех узлов дерева возвращает сложность к худшему случаю **$O(N)$**.

---

### 2. Почему операция `put()` считается $O(1)$, если в худшем случае при ресайзе она занимает $O(N)$?

**Ответ:**
В алгоритмическом анализе разделяют понятия **худшего времени одной операции (Worst-case single operation)** и **амортизированного времени последовательности операций (Amortized time)**.
Для `put()` худшее время отдельного вызова действительно равно $O(N)$ (в момент ресайза). Однако благодаря удвоению емкости ($2 \times$) ресайзы происходят экспоненциально реже по мере роста коллекции. Серия из $N$ операций `put()` суммарно требует не более $3N$ элементарных шагов. Поэтому средняя стоимость одной вставки в длинной последовательности строго ограничена константой: $\frac{3N}{N} = 3 = O(1)$.

---

### 3. Какова временная сложность вызова `map.size()` и `map.isEmpty()`?

**Ответ:**
Строго **$O(1)$**.
В `HashMap` текущее количество элементов хранится в явном примитивном поле `transient int size;`.
Метод `size()` просто возвращает значение этого поля за 1 такт CPU:
```java
public int size() {
    return size;
}
```
Метод `isEmpty()` просто проверяет `return size == 0;`. Никакого сканирования бакетов или подсчета узлов не происходит (в отличие, например, от `ConcurrentLinkedQueue.size()`, где до Java 8 требовался обход списка).

---

### 4. Почему итерация по `HashMap` может быть значительно медленнее, чем итерация по `ArrayList` с тем же числом элементов?

**Ответ:**
Сложность итерации по `ArrayList` составляет $O(N)$, а элементы расположены в непрерывном блоке оперативной памяти, что идеально утилизирует CPU L1/L2 кэш-линии (64 байта за такт).

Сложность итерации по `HashMap` составляет **$O(\text{capacity} + N)$**:
1. **Пропуск пустых ячеек:** Итератор обязан пройти по всему массиву ссылок `table.length`. Если таблица заполнена разреженно (например, 1 000 элементов в таблице на 65 536 ячеек), итератор совершит 64 536 проверок на `null`.
2. **Рассеянность по памяти:** Каждый узел `Node` является отдельным объектом в куче. Переход по ссылкам `e.next` приводит к постоянным промахам процессорного кэша (Pointer Chasing).

## 🎯 Шпаргалка для интервью

* **Базовая сложность:** `get`, `put`, `remove`, `containsKey` выполняются за $O(1)$ в среднем.
* **Худший случай:**
  - Java 7: $O(N)$ (длинный связный список).
  - Java 8+: $O(\log N)$ (красно-чёрное дерево `TreeNode`), но может деградировать до $O(N)$, если ключи не реализуют `Comparable`.
* **Амортизация `put()`:** Единичная вставка может занять $O(N)$ из-за `resize()`, но среднее время последовательности из $N$ вставок всегда $O(1)$ благодаря геометрическому росту $2 \times$.
* **Итерация:** Сложность $O(C + N)$, где $C$ — текущий `capacity`, $N$ — число элементов `size`. Разреженные таблицы обходятся медленно.
* **Факторы задержки:** Cache Locality (L1 hit $\approx 1$ нс против RAM miss $\approx 80$ нс), сложность метода `equals()` и тяжесть расчета `hashCode()`.
