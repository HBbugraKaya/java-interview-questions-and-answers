# Что такое Service Discovery и зачем он нужен

---

## 🟢 Junior Level

**Service Discovery (Обнаружение сервисов)** — это автоматический механизм, с помощью которого микросервисы в распределённой системе находят сетевые координаты (IP-адрес и порт) друг друга без ручной настройки и жестко зашитых конфигураций (hardcoded IPs).

```
Динамическая облачная среда:
[Поднялся новый инстанс] ──► Регистрация: "Я payment-service на 10.244.2.15:8080"
                                                │
                                                ▼
                                    ┌───────────────────────┐
                                    │   Service Registry    │
                                    │  (Реестр сервисов)    │
                                    │ order:   10.244.1.5   │
                                    │ payment: 10.244.2.15  │
                                    │ payment: 10.244.3.40  │
                                    └───────────────────────┘
                                                ▲
[Order Service] ── Запрос: "Где payment?" ─────┘
                ◄── Ответ: [10.244.2.15, 10.244.3.40]
[Order Service] ── Прямой вызов ──► [Payment Service (10.244.2.15)]
```

### Зачем это нужно?
В современной облачной и контейнерной инфраструктуре (Kubernetes, AWS ECS, Docker Swarm):
1. **Эфемерные IP-адреса:** Контейнеры (поды) регулярно перезапускаются, перемещаются между физическими нодами и при каждом рестарте получают **новый динамический IP-адрес**.
2. **Динамическое масштабирование (Auto-scaling):** При росте нагрузки по сигналу метрик создаются десятки новых копий сервиса, а при спаде — уничтожаются.
3. **Обнаружение сбоев:** Если инстанс завис или упал, он должен быть немедленно исключён из маршрутизации, чтобы на него не отправлялся пользовательский трафик.

## 🟡 Middle Level

### 1. Архитектурные компоненты Service Discovery

1. **Service Registry (Реестр сервисов):** Высокодоступная база данных сетевых адресов активных экземпляров микросервисов (например, HashiCorp Consul, Netflix Eureka, etcd, Apache ZooKeeper).
2. **Service Registration (Регистрация):**
   - *Self-Registration:* Сервис при старте сам отправляет HTTP/gRPC запрос в реестр («я жив по адресу $X$»).
   - *Third-Party Registration:* Внешний агент (например, Kubernetes Kubelet или Registrator) отслеживает статус контейнеров и сам обновляет реестр.
3. **Health Checking & Heartbeating (Пульс и проверка здоровья):**
   Каждый инстанс периодически шлёт сердечные сокращения (*Heartbeat*) каждые 5–30 секунд. Если пульс не пришел в течение таймаута аренды (*Lease TTL*), реестр автоматически удаляет инстанс.

### 2. Реализация в Spring Cloud (Netflix Eureka / Consul)

```java
// Сервис-потребитель (Order Service)
@Service
@RequiredArgsConstructor
public class PaymentOrderGateway {

    private final DiscoveryClient discoveryClient;
    private final RestClient restClient;

    public void chargeCustomer(String orderId, BigDecimal amount) {
        // Получаем список всех живых инстансов из локально кэшированного реестра
        List<ServiceInstance> instances = discoveryClient.getInstances("payment-service");
        
        if (instances.isEmpty()) {
            throw new IllegalStateException("Нет доступных инстансов payment-service!");
        }

        // Выбираем инстанс (в реальности это делает LoadBalancer автоматически)
        ServiceInstance target = instances.get(0);
        String url = String.format("http://%s:%d/api/v1/charge", target.getHost(), target.getPort());

        restClient.post()
            .uri(url)
            .body(new ChargeRequest(orderId, amount))
            .retrieve()
            .toBodilessEntity();
    }
}
```

С использованием высокоуровневой декларативной абстракции `@LoadBalanced`:
```java
@Configuration
public class WebClientConfig {
    @Bean
    @LoadBalanced // Spring Cloud автоматически резолвит имя "payment-service" через Discovery
    public RestClient.Builder restClientBuilder() {
        return RestClient.builder();
    }
}
// Вызов: restClient.get().uri("http://payment-service/api/v1/status").retrieve()...
```

## 🔴 Senior Level

### 1. CAP-теорема в Service Registry: AP (Eureka) vs CP (Consul / ZooKeeper / etcd)

При проектировании Service Registry инженеры сталкиваются с фундаментальным выбором по теореме CAP во время сетевого разделения (Network Partition):

```
       [Consul / etcd / K8s API]               [Netflix Eureka]
                (CP)                                 (AP)
  ┌───────────────────────────────┐   ┌───────────────────────────────┐
  │ Консистентность превыше всего │   │ Доступность превыше всего     │
  │ Используют консенсус Raft.    │   │ Одноранговая репликация (P2P).│
  │ При разрыве кворума запись    │   │ Всегда отвечает на чтение,    │
  │ блокируется. Адреса всегда    │   │ допускает устаревшие данные   │
  │ строго актуальны.             │   │ (Stale Data) и ошибки.        │
  └───────────────────────────────┘   └───────────────────────────────┘
```

#### Режим самосохранения в Eureka (Self-Preservation Mode):
Если в Eureka за 15 минут более 15% сердечных сокращений перестают доходить, Eureka предполагает, что произошла сетевая авария между дата-центрами, а не одновременная смерть всех сервисов. 
Она **замораживает удаление записей по тайм-ауту**. Лучше попытаться отправить запрос на возможно живой сервис, чем мгновенно «похоронить» всю систему из-за сетевого сбоя.

### 2. Эволюция: от Application-Level к Infrastructure-Level (Kubernetes & Service Mesh)

В современных enterprise-системах наблюдается явный отказ от самодельных прикладных реестров (Eureka) в пользу нативных инфраструктурных решений:

```
Эволюция Service Discovery:
1. Прикладной (Spring Cloud Eureka/Ribbon):
   [Java App + Eureka Client] ──HTTP──► [Eureka Server]
   (Минусы: привязка к языку Java, тяжелые клиенты, дублирование ресурсов)

2. Инфраструктурный (Kubernetes CoreDNS + kube-proxy):
   [App (любой язык)] ──DNS──► [CoreDNS] ──► [ClusterIP (iptables/IPVS)] ──► [Pod]
   (Плюсы: прозрачно для любого языка, нативно поддерживается платформой)

3. Service Mesh (Istio / Envoy):
   [App] ──localhost──► [Envoy Sidecar] ──mTLS/xDS──► [Envoy Sidecar] ──► [App B]
   (Плюсы: xDS dynamic routing, Canary, Circuit Breaking, Zero-Trust mTLS)
```

В Kubernetes каждый `Service` получает стабильное DNS-имя (`payment-service.default.svc.cluster.local`), а `kube-proxy` на уровне ядра Linux (через `IPVS` или `eBPF`) транслирует виртуальный ClusterIP в реальные IP-адреса подов.

## 4 Tricky Questions

### 1. Что произойдет, если центральный кластер Service Registry (например, Consul) полностью ляжет?
**Ответ:**
Грамотно спроектированные клиенты (Spring Cloud Discovery, Envoy) реализуют **Client-Side Caching**:
1. Клиент периодически вычитывает реестр и кэширует список актуальных IP-адресов в локальной памяти.
2. При падении Service Registry микросервисы продолжают успешно вызывать друг друга, используя кэшированные адреса.
3. Система переходит в деградированный режим: старые сервисы работают стабильно, но новые поднявшиеся инстансы не будут обнаружены, а умершие поды будут отсекаться клиентским Circuit Breaker / Retry при попытке соединения.

### 2. Почему в инфраструктуре Kubernetes использование Netflix Eureka считается антипаттерном?
**Ответ:**
1. **Дублирование функционала:** Kubernetes уже содержит встроенный Service Discovery промышленного уровня на базе CoreDNS, Endpoints и kube-proxy.
2. **Языковой барьер (Polyglot restrictions):** Eureka ориентирована на JVM. Если в компании появляется сервис на Go, Python или Node.js, интеграция с Eureka требует сторонних костылей, тогда как DNS в Kubernetes одинаково работает для любого языка программирования.
3. **Рассинхронизация жизненного цикла:** Eureka полагается на Heartbeat (TTL 30–90 сек), а Kubernetes моментально обновляет Endpoints по сигналам контроллера подов. При использовании Eureka запросы будут идти на уже убитые поды ещё десятки секунд.

### 3. Как решается проблема «холодного старта» (Warm-up problem), когда сервис зарегистрировался в Registry, но JVM ещё не прогрета JIT-компилятором?
**Ответ:**
Если на только что зарегистрированный инстанс сразу направить 100% рабочего трафика, холодный JVM-процесс захлебнется и начнет отдавать тайм-ауты.
*Решения:*
- **Kubernetes Readiness Probe с начальной задержкой (`initialDelaySeconds`)**: под не включается в Endpoints до успешного прогрева.
- **Canary / Slow-Start балансировка (в Envoy / Ribbon)**: новый инстанс получает линейно нарастающий процент трафика (например, от 1% до 100% в течение 2 минут), давая JIT-компилятору скомпилировать байткод в нативный код.

### 4. Что такое «Stale Registry Entry» и почему один только Health Check на стороне Registry не гарантирует отсутствие ошибок соединения?
**Ответ:**
Stale Entry (устаревшая запись) — это ситуация, когда инстанс аварийно завершился (OOMKilled, отключение питания сервера), но запись в реестре остается активной до истечения срока аренды (Heartbeat TTL, обычно 30–90 секунд). В этот интервал клиенты получают мертвый IP.
Никакой Health Check не способен мгновенно распространить информацию по распределённой сети с нулевой задержкой. 
*Защита:* Service Discovery **никогда не используется изолированно**. На клиенте обязана быть связка с **Retry** (повторить запрос на другой инстанс из списка) и **Circuit Breaker**.

## 🎯 Шпаргалка для интервью

### Главное:
- **Service Discovery** решает проблему динамических IP-адресов микросервисов в облачной среде при рестартах и автомасштабировании.
- Состоит из трёх частей: **Service Registry** (база адресов), **Registration** (постановка на учет), **Discovery** (поиск живых адресов).
- В Java-мире исторически использовались **Eureka / Consul / ZooKeeper**, в современном продакшене стандарт — **Kubernetes DNS + Service Mesh (Istio / Envoy)**.
- По CAP-теореме: Eureka — **AP** (при аварии включает *Self-Preservation*, жертвуя актуальностью ради доступности); Consul/etcd — **CP** (строгий консенсус Raft).
- Клиент обязан кэшировать адреса локально (**Client-side cache**), чтобы пережить отказ самого реестра.

### Красные флаги (Чего говорить НЕЛЬЗЯ):
- ❌ *«В микросервисах адреса других сервисов прописываются в `application.yml` через IP-адреса»* (В контейнерах IP эфемерны, хардкод исключен).
- ❌ *«При падении Eureka вся система моментально останавливается»* (Клиенты кэшируют список инстансов и продолжают работать на кэше).
- ❌ *«В Kubernetes обязательно нужно разворачивать Eureka Server»* (В K8s есть нативный CoreDNS + Endpoints, Eureka там избыточна и вредна).
