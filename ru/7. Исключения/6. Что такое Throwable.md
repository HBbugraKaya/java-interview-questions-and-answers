# Что такое Throwable

---

## 🟢 Junior Level

**`java.lang.Throwable`** — это суперкласс всех исключений и ошибок в языке Java. Только экземпляры этого класса (или его наследников) могут быть переданы в инструкцию **`throw`**, объявлены в секции **`throws`** метода или перехвачены блоком **`catch`**.

Наследуется напрямую от `java.lang.Object` и реализует интерфейс `java.io.Serializable`.

### Иерархия потомков

```
                           java.lang.Throwable
                                  │
                 ┌────────────────┴────────────────┐
                 ▼                                 ▼
         java.lang.Error                 java.lang.Exception
     (Фатальные аварии JVM)            (Прикладные исключения)
                 │                                 │
     ┌───────────┴───────────┐         ┌───────────┴───────────┐
     ▼                       ▼         ▼                       ▼
OutOfMemoryError   StackOverflowError Checked Exceptions  RuntimeException
                                      (IOException и др.) (NPE, IllegalArgument)
```

### Ключевые методы класса Throwable

| Метод | Назначение |
| :--- | :--- |
| **`getMessage()`** | Возвращает строковое описание ошибки, переданное в конструктор. |
| **`getCause()`** | Возвращает причину сбоя (исходное исключение) или `null`, если причины нет. |
| **`initCause(Throwable)`** | Устанавливает первопричину (если она не была задана в конструкторе). Можно вызвать только один раз. |
| **`getStackTrace()`** | Возвращает массив элементов стека `StackTraceElement[]` для программного анализа. |
| **`addSuppressed(Throwable)`** | Добавляет подавленное исключение (используется в `try-with-resources`). |
| **`getSuppressed()`** | Возвращает массив всех подавленных исключений `Throwable[]`. |
| **`printStackTrace()`** | Выводит текстовый стек-трейс в стандартный поток ошибок `System.err` *(в продакшене не используется!)*. |

## 🟡 Middle Level

### Почему Throwable — это абстрактный по замыслу класс, а не интерфейс?

На собеседованиях часто спрашивают: *«Почему авторы Java спроектировали Throwable как класс, а не как интерфейс Throwableable?»*

**Архитектурные причины:**
1. **Необходимость хранения состояния:** Для формирования ошибки требуется инкапсулировать состояние: сообщение `detailMessage`, ссылку на причину `cause`, список `suppressedExceptions` и нативный указатель `backtrace`. Интерфейсы в Java не могут иметь полей экземпляра.
2. **Специфика взаимодействия с JVM:** Виртуальная машина JVM при создании объекта исключения обязана вызвать нативный код заполнения стека вызовов (`fillInStackTrace()`). Интерфейс не может гарантировать наличие необходимой структуры памяти и нативных хуков внутри C++ ядра JVM (HotSpot).
3. **Безопасность и типобезопасность:** Если бы `Throwable` был интерфейсом, разработчик мог бы объявить `class MyService implements Throwable` и передать рабочий бин сервиса в инструкцию `throw`, что привело бы к абсурду.

### Опасность перехвата `catch (Throwable t)`

Перехват `catch (Throwable t)` в прикладных методах считается антипаттерном, потому что он ловит не только ошибки приложения, но и **`java.lang.Error`**:
- Если в JVM заканчивается оперативная память (`OutOfMemoryError`), перехват `Throwable` не позволит процессу упасть.
- Поток продолжит выполнение в условиях поврежденной кучи (Heap Corruption), удерживая разделяемые блокировки и зависая.
- **Единственное место, где допустим `catch (Throwable t)`** — это внешний цикл потока-демона верхнего уровня или обработчик входящих сообщений (например, Kafka Consumer Loop), где необходимо залогировать критический сбой перед вызовом `System.exit(1)`.

### Почему метод `printStackTrace()` запрещен в продакшене?

1. **Блокировка потоков (Thread Contention):** `System.err` внутри использует синхронизацию (`PrintStream.println()` синхронизирован по монитору). При одновременном всплеске ошибок несколько потоков будут блокировать друг друга на выводе в консоль.
2. **Разрушение структуры логов в Kubernetes:** В современных облачных средах логи собираются агентами (Fluentd, Promtail, Vector) в формате JSON. Вызов `printStackTrace()` выплевывает десятки отдельных строк в `stderr`, разбивая одну ошибку на множество разрозненных записей в Kibana / Grafana Loki.
3. **Отсутствие метаданных:** `printStackTrace()` не выводит контекст логирования (MDC): `traceId`, `spanId`, `userId`.

*Вместо этого всегда используют логгер:*
```java
log.error("Failed to process transaction for account {}", accountId, exception);
```

## 🔴 Senior Level

### Асинхронное «сшивание» стек-трейсов (Stack Trace Stitching)

В современных реактивных и асинхронных фреймворках (Project Reactor, CompletableFuture, Virtual Threads) задача переключается между разными потоками пула. Когда происходит ошибка, стандартный стек-трейс `Throwable` содержит только 2–3 фрейма рабочего потока `ForkJoinPool.worker`, полностью скрывая контекст того, где запрос начинался.

Для решения этой проблемы архитекторы используют методы **`setStackTrace()`** и **`initCause()`** для объединения контекстов:

```java
package com.example.async;

import java.util.Arrays;
import java.util.concurrent.CompletableFuture;

public class AsyncStackStitcher {

    public static <T> CompletableFuture<T> withCallerStack(CompletableFuture<T> future) {
        // Захватываем стек потока, создавшего асинхронную задачу
        StackTraceElement[] callerStack = Thread.currentThread().getStackTrace();

        return future.exceptionally(ex -> {
            // Сшиваем асинхронный стек с оригинальным вызывающим стеком
            StackTraceElement[] asyncStack = ex.getStackTrace();
            StackTraceElement[] combined = new StackTraceElement[asyncStack.length + callerStack.length];

            System.arraycopy(asyncStack, 0, combined, 0, asyncStack.length);
            System.arraycopy(callerStack, 0, combined, asyncStack.length, callerStack.length);

            ex.setStackTrace(combined);
            throw new CompletionException("Asynchronous execution failed", ex);
        });
    }
}
```

### Защита от циклических зависимостей в Cause и Suppressed

Класс `Throwable` содержит встроенную защиту от бесконечных циклов:
1. Если попытаться сделать `t1.initCause(t2)` и `t2.initCause(t1)`, метод `initCause()` выбросит:
   `IllegalArgumentException: Self-causation not permitted`.
2. Если вызвать `t1.addSuppressed(t1)`, метод выбросит:
   `IllegalArgumentException: Self-suppression not permitted`.

При программном обходе цепочки причин (`getCause()`) Senior-разработчик обязан использовать детекцию циклов (например, с помощью `Set<Throwable> visited = Collections.newSetFromMap(new IdentityHashMap<>())`), чтобы защититься от зависания при рекурсивном разборе.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> **`Throwable`** — это базовый класс всей системы обработки исключений в Java. Только его прямые или косвенные потомки могут использоваться с операторами `throw`, `throws` и `catch`. 
> 
> Разделяется на:
> - **`Error`** — системные неустранимые сбои JVM (`OutOfMemoryError`), перехватывать которые запрещено.
> - **`Exception`** — прикладные ошибки (включая непроверяемые `RuntimeException`).
> 
> Хранит сообщение, причину (`cause`), подавленные исключения (`suppressed`) и нативный указатель на стек `backtrace`. Вызов `printStackTrace()` в реальных приложениях запрещен из-за синхронизации на `System.err` и разбивки JSON-логов в контейнерах; логировать исключения следует строго через SLF4J / Logback с передачей объекта ошибки последним аргументом.

### 4 каверзных вопроса с ответами

1. **Почему класс Throwable спроектирован как класс, а не как интерфейс?**
   *Ответ:* `Throwable` должен нести в себе изменяемое состояние (`cause`, `suppressedExceptions`, `detailMessage`) и нативную структуру данных `backtrace`, заполняемую ядром JVM при обходе стека вызовов потока. Интерфейсы не могут содержать полей экземпляра и не могут гарантировать нативную интеграцию с HotSpot JVM.

2. **Чем грозит вызов `e.printStackTrace()` в высоконагруженном многопоточном сервисе?**
   *Ответ:* Поток `System.err` синхронизирован на уровне `PrintStream`. При одновременном выбросе исключений в десятках потоков возникнет сильная конкуренция за блокировку (Thread Contention) консольного вывода, приводящая к просадке пропускной способности приложения.

3. **Что делает метод `Throwable.addSuppressed(Throwable exception)` и в каком сценарии он используется?**
   *Ответ:* Метод прикрепляет вторичное (подавленное) исключение к первичному. Он автоматически используется компилятором в конструкции `try-with-resources`: если при выполнении блока `try` возникла ошибка, а затем метод `AutoCloseable.close()` также выбросил ошибку, закрывающее исключение добавляется в список подавленных, чтобы не затереть исходную причину сбоя.

4. **Как программно защититься от зацикливания при обходе цепочки `t.getCause()`?**
   *Ответ:* Хотя метод `initCause()` валидирует прямые циклы, при сложной десериализации или кастомных переопределениях `getCause()` возможны циклические ссылки. Для безопасного поиска корневой причины (Root Cause) запоминают посещенные объекты в `IdentityHashMap` (проверка по ссылочной идентичности `==`).

### Красные флаги (чего категорически нельзя говорить)
- ❌ *«Throwable — это интерфейс, который можно реализовать в любом классе»* (это класс, наследующийся от Object).
- ❌ *«printStackTrace() — это лучший способ логирования ошибок в продакшене»* (грубейшая ошибка; нужно использовать логгер SLF4J).
- ❌ *«Перехват catch (Throwable t) в сервисе гарантирует отсутствие падений приложения»* (наоборот, приводит к зомби-процессам при `OutOfMemoryError`).
- ❌ *«Исключение можно выбросить без создания Throwable»* (оператор `throw` строго требует экземпляр класса `Throwable`).
