# How can a memory leak occur in Java

---

## 🟢 Junior Level

A **Memory Leak** in Java occurs whenever an object is **no longer required by application business logic**, but an active **strong reference path from a GC Root** remains intact, preventing the Garbage Collector from freeing its memory.

---

### Real-World Analogy
Think of a **library catalog system**:
- A patron borrows a book and returns it to the physical returns bin.
- However, the librarian forgets to scan the return barcode in the computer database.
- The system still lists the patron as actively holding the book. The book cannot be re-shelved, checked out by others, or archived, and the patron's account remains permanently flagged as active.
- Over time, the library's shelves empty out while phantom checkout records consume all system database storage.

---

### The Top 3 Common Leak Scenarios

1. **Unbounded Static Collections:**
   ```java
   // ❌ LEAK: Static collections are permanent GC Roots; this list grows indefinitely!
   public class EventTracker {
       private static final List<OrderEvent> EVENT_HISTORY = new ArrayList<>();

       public static void track(OrderEvent event) {
           EVENT_HISTORY.add(event); // Never pruned, evicted, or sized!
       }
   }
   ```

2. **Unclosed I/O Streams and Native Descriptors:**
   ```java
   // ❌ LEAK: Unclosed streams pin native OS file descriptors and intermediate byte buffers
   public void readFile(String path) throws IOException {
       InputStream in = new FileInputStream(path);
       in.read();
       // If an exception occurs, 'in.close()' is never called!
   }
   ```
   *Fix:* Always use `try-with-resources`.

3. **Lapsed Event Listeners (Unregistered Callbacks):**
   ```java
   // ❌ LEAK: Registering a short-lived listener with a long-lived publisher
   public class PaymentProcessor {
       public void init() {
           // GlobalEventPublisher is a singleton (GC Root)
           // It retains a strong reference to this PaymentProcessor forever!
           GlobalEventPublisher.getInstance().subscribe(this::onPaymentReceived);
       }
   }
   ```

## 🟡 Middle Level

### 1. Mutable Keys in `HashMap` and `HashSet`

A classic, subtle memory leak occurs when mutable objects are used as keys in hash-based collections:

```java
public class MutableKeyLeak {
    public static void main(String[] args) {
        Set<User> activeUsers = new HashSet<>();
        User user = new User("Alice", 25);
        activeUsers.add(user); // Computed bucket index based on initial hashCode()

        // 💥 MUTATION: Modifying a field participating in hashCode()!
        user.setAge(26); // hashCode() changes!

        // Attempting to remove the user:
        boolean removed = activeUsers.remove(user); 
        // -> FALSE! HashSet searches the NEW bucket, but the object resides in the OLD bucket!

        System.out.println("Set size: " + activeUsers.size()); // Prints: 1 (Zombie entry!)
    }
}
```
*Result:* The `User` object is trapped permanently in the `HashSet`. It can never be removed via standard API calls, and repeated insertions cause the set to grow indefinitely.

### 2. Non-Static Inner Classes vs. Lambdas

Every non-static inner class (including anonymous classes) contains an invisible, synthetic pointer to its outer enclosing instance (`Outer.this` or `this$0` in bytecode):

```java
public class HeavyReportService {
    private final byte[] reportPayload = new byte[100 * 1024 * 1024]; // 100 MB

    public Runnable createWorkerTask() {
        // ❌ Anonymous class implicitly retains 'HeavyReportService.this'!
        return new Runnable() {
            @Override
            public void run() {
                System.out.println("Running background task...");
            }
        };
    }
}

// In another thread:
Runnable task = reportService.createWorkerTask();
longLivedExecutor.submit(task);
reportService = null; 
// 💥 100 MB payload CANNOT be garbage collected because 'task' retains the enclosing instance!
```

#### ✅ The Lambda Advantage:
Unlike anonymous classes, a **Lambda Expression** captures `this` **only if it explicitly accesses instance fields or methods of the enclosing class**. If the lambda references only its own parameters or local variables, the compiler does not bind `this`, preventing accidental memory retention:

```java
// ✅ SAFE: This lambda does not capture 'this'; no outer reference exists!
public Runnable createSafeWorkerTask() {
    return () -> System.out.println("Running pure task...");
}
```

---

### 3. Unbounded In-Memory Caching

Using a naive `ConcurrentHashMap` as an in-memory cache inevitably leads to an `OutOfMemoryError`:

```java
// ❌ WRONG: Primitive unbounded cache
private static final Map<String, UserProfile> CACHE = new ConcurrentHashMap<>();

// ✅ PRODUCTION STANDARD: Bounded, self-evicting cache using Caffeine
private static final Cache<String, UserProfile> CACHE = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(30))
    .recordStats()
    .build();
```

## 🔴 Senior Level

### 4. Metaspace & ClassLoader Leaks (Hot-Redeployment Leaks)

In enterprise application servers (Tomcat, Jetty, WildFly) and OSGi runtimes, deploying an updated web application creates a new `WebAppClassLoader`. The previous class loader must be collected along with all loaded classes:

```
Bootstrap ClassLoader
        │
Application / System ClassLoader
        │
WebAppClassLoader_v1 (Expected to be garbage collected!)  <── Pinned by leak!
        │
    Loaded Classes (UserController.class, OrderService.class)
        │
   Static Fields & Singletons
```

#### Why ClassLoaders Fail to Unload:
1. **Un-deregistered JDBC Drivers:** When a web app registers a database driver, `java.sql.DriverManager` (loaded by the Bootstrap ClassLoader) holds a strong reference to the driver. The driver references the `WebAppClassLoader`, pinning all loaded classes in **Metaspace**.
2. **Abandoned `ThreadLocal` in Shared Pools:** If a pooled Tomcat thread retains a `ThreadLocal<TenantContext>`, and `TenantContext` was loaded by `WebAppClassLoader`, the thread pins the entire class loader tree.
3. **Orphaned Background Threads:** Background daemon threads (e.g., `java.util.Timer`, custom `Thread`) that are not stopped on context shutdown remain active GC Roots, pinning their context class loaders.

### 5. Off-Heap Direct Memory Leaks: `DirectByteBuffer` & Native Deflaters

Applications that allocate native off-heap memory bypass standard `-Xmx` heap limits:

```java
// Allocates 1 GB of native OS memory outside the JVM Heap:
ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024 * 1024);
```

#### The "Empty Heap" Native OOM Hazard:
- On the Java Heap, a `DirectByteBuffer` is a tiny wrapper object occupying only **64 bytes** (containing a native memory address pointer).
- Reclamation of the 1 GB native memory buffer is mediated by a `PhantomReference` and a `Cleaner` that executes when the 64-byte wrapper is garbage collected.
- **The Failure Scenario:** If the Java Heap has very low churn (the application allocates few heap objects), **the Garbage Collector rarely triggers**. Native memory continues to expand, consuming all available system RAM until the **Linux OOM Killer violently terminates the JVM process (Exit Code 137)**—even though the Java Heap is 95% empty!
- *Defense:* Set `-XX:MaxDirectMemorySize=2g` and use pooled buffer management (e.g., Netty's `PooledByteBufAllocator`).

#### The `java.util.zip.Deflater` Native Leak:
When compressing data with `Deflater` or `GZIPOutputStream`, native C memory is allocated in the `zlib` library. If code fails to explicitly call `deflater.end()`, native memory leaks outside JVM visibility until process restart.

## 4 Tricky Questions

### 1. Why does mutating an object's fields after putting it into a `HashSet` or `HashMap` cause a silent memory leak?
**Answer:** Hash-based collections distribute entries across buckets calculated using the key object's `hashCode()`. When you mutate a field that participates in the hash code calculation, the object's `hashCode()` changes, but its physical location inside the hash table remains in the original bucket. When code later attempts to remove the object using `map.remove(key)` or `set.remove(element)`, the collection calculates the hash code of the mutated object and searches the *new* corresponding bucket. Finding nothing there, the method returns `false`, leaving the original entry permanently stranded in the old bucket with no way to evict it.

---

### 2. What is the fundamental difference between an anonymous inner class and a lambda expression regarding memory leak risks?
**Answer:** An anonymous inner class declared inside an instance method always compiles with a hidden synthetic field (named `this$0`) that holds a strong reference to the enclosing outer class instance, regardless of whether the anonymous class ever references any outer fields or methods. In contrast, a lambda expression compiled via `invokedynamic` is strictly non-capturing by default: it captures a reference to the enclosing instance *only* if the lambda body explicitly accesses instance fields or methods of the outer class. A non-capturing lambda can be submitted to long-running thread pools with zero risk of inadvertently pinning the outer class.

---

### 3. How can `DirectByteBuffer` allocations trigger a Linux kernel OOM Killer crash even when the JVM Heap is 90% free?
**Answer:** `DirectByteBuffer` allocates native memory outside the JVM Heap via native OS calls (`malloc`). On the Java Heap, the buffer is represented solely by a lightweight Java wrapper object occupying roughly 64 bytes. The deallocation of the native buffer is triggered via a `Cleaner` (based on `PhantomReference`) that executes only when the Java wrapper object is garbage collected. If the application performs heavy I/O without generating high Java heap allocation traffic, the JVM Heap never reaches its GC threshold. Consequently, the Garbage Collector never runs, the wrappers are never collected, and the underlying native memory grows unchecked until the host operating system kernel exhausts physical RAM and issues a `SIGKILL` (Exit Code 137).

---

### 4. How does an un-deregistered JDBC driver in `DriverManager` cause a Metaspace `OutOfMemoryError` during web application redeployment?
**Answer:** The `java.sql.DriverManager` class is loaded by the JVM's Bootstrap ClassLoader, making it a permanent GC Root that survives the entire lifetime of the JVM process. When a web application starts, it registers its JDBC driver with `DriverManager`. If the application undeploys or reloads without explicitly calling `DriverManager.deregisterDriver()`, `DriverManager` retains a strong reference to the driver class. Because a loaded class retains a strong reference to the `ClassLoader` that loaded it (`WebAppClassLoader`), and that class loader retains references to all classes it ever loaded, the entire class graph of the undeployed application remains pinned in **Metaspace**. Repeated deployments accumulate orphaned class loaders until `OutOfMemoryError: Metaspace` occurs.

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
> "A **Java Memory Leak** happens when obsolete objects are unintentionally kept reachable from **GC Roots**. In enterprise applications, leaks primarily stem from: **unbounded static collections** or caches without eviction policies (solved via Caffeine); **`ThreadLocal` instances in thread pools** where `.remove()` is omitted in `finally` blocks; **non-static inner classes** that capture `Outer.this`; **ClassLoader leaks in Metaspace** caused by un-deregistered JDBC drivers or unstopped background threads during hot reloads; and **Off-Heap native memory** where `DirectByteBuffer` native buffers are not promptly freed because heap churn is too low to trigger GC."

---

### Key Architectural Takeaways
- **Static Scope Danger:** Static fields are roots that live forever; never use raw static collections as caches.
- **Mutable Hash Keys:** Mutating fields participating in `hashCode()` strands objects permanently in hash tables.
- **Inner Classes vs Lambdas:** Non-static inner classes always capture `this$0`; lambdas capture `this` only when accessing outer instance state.
- **`ThreadLocal` Rule:** Always invoke `threadLocal.remove()` in a `finally` block to protect pooled worker threads.
- **Metaspace Retention:** Always unregister JDBC drivers, shut down thread pools, and deregister MBeans during web app shutdown.
- **Off-Heap Caution:** `DirectByteBuffer` and `Deflater` consume native OS RAM; configure `-XX:MaxDirectMemorySize` and explicitly close native resources.

---

### Red Flags & Anti-Patterns
- 🚩 **Using `ConcurrentHashMap` as a production cache without eviction:** Inevitably triggers an `OutOfMemoryError`.
- 🚩 **Omitting `.remove()` on `ThreadLocal` in servlet filters or interceptors:** Causes memory leaks and cross-tenant data corruption.
- 🚩 **Mutating objects after inserting them into `HashSet` or `HashMap`:** Destroys hash bucket lookup invariants.
- 🚩 **Passing non-static inner `Runnable` instances to long-lived thread pools:** Silently pins large outer services in memory.
- 🚩 **Ignoring native resource cleanup (`deflater.end()`, `DirectByteBuffer`):** Risks abrupt container termination via Linux OOM Killer.
