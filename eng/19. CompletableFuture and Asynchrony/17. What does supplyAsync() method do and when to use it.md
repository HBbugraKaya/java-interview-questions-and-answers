# What does supplyAsync() method do and when to use it

---

## 🟢 Junior Level

The `CompletableFuture.supplyAsync()` method is the primary static factory method for initiating asynchronous computations that produce a result. It accepts a `Supplier<T>` functional interface and schedules the execution of the computation on a background worker thread.

### Basic Code Example

```java
// Launch an asynchronous background task:
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    // Code executes in a background worker thread
    return "Data from external service";
});

// Non-blocking consumption of the computed result:
future.thenAccept(result -> System.out.println("Received: " + result));
```

### `supplyAsync()` vs `runAsync()`

| Method | Accepted Interface | Return Value | Primary Use Case |
| :--- | :--- | :--- | :--- |
| **`supplyAsync`** | `Supplier<T>` (`() -> T`) | `CompletableFuture<T>` | Data retrieval, mathematical computation, I/O reads |
| **`runAsync`** | `Runnable` (`() -> void`) | `CompletableFuture<Void>` | Notifications, cache eviction, fire-and-forget logging |

```java
// supplyAsync — Computes and returns value T
CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> fetchUser(42));

// runAsync — Performs side effect without returning a value
CompletableFuture<Void> auditFuture = CompletableFuture.runAsync(() -> sendAuditLog("User 42 logged in"));
```

## 🟡 Middle Level

### Method Overloads and Thread Pool Isolation

The method provides two overloads:
1. `supplyAsync(Supplier<U> supplier)`: Submits the task to the default JVM-wide `ForkJoinPool.commonPool()`.
2. `supplyAsync(Supplier<U> supplier, Executor executor)`: Submits the task to an explicitly provided custom `Executor`.

```java
// For blocking I/O, ALWAYS supply a dedicated thread pool:
ExecutorService ioExecutor = Executors.newFixedThreadPool(16);

CompletableFuture<List<Product>> productsFuture = CompletableFuture.supplyAsync(
    () -> catalogClient.getProducts(), 
    ioExecutor
);
```

### The Checked Exceptions Constraint

The `Supplier<T>` functional interface defines `T get()`, which **does not declare checked exceptions** (`throws Exception`).
If a method throws checked exceptions (such as `IOException` or `SQLException`), the code will not compile without explicit handling:

```java
// COMPILATION ERROR: Unhandled IOException
CompletableFuture.supplyAsync(() -> Files.readString(Path.of("config.json")));

// Solution 1: Explicit try-catch wrapping in unchecked exception
CompletableFuture.supplyAsync(() -> {
    try {
        return Files.readString(Path.of("config.json"));
    } catch (IOException e) {
        throw new UncheckedIOException(e); // Propagates as CompletionException
    }
});

// Solution 2: Functional wrapper / Lombok @SneakyThrows
CompletableFuture.supplyAsync(rethrow(() -> Files.readString(Path.of("config.json"))));
```

## 🔴 Senior Level

### Internal Architecture: The `AsyncSupply` Task

Under the hood, invoking `CompletableFuture.supplyAsync(supplier, executor)` executes the following internal flow:

```java
public static <U> CompletableFuture<U> supplyAsync(Supplier<U> supplier, Executor executor) {
    return asyncSupplyStage(screenExecutor(executor), supplier);
}

static <U> CompletableFuture<U> asyncSupplyStage(Executor e, Supplier<U> f) {
    if (f == null) throw new NullPointerException();
    CompletableFuture<U> d = new CompletableFuture<U>();
    e.execute(new AsyncSupply<U>(d, f)); // Enqueues custom internal task
    return d;
}
```

The `AsyncSupply` class extends `ForkJoinTask<Void>` and implements `Runnable` and `AsynchronousCompletionTask`:

```java
static final class AsyncSupply<T> extends ForkJoinTask<Void> implements Runnable, AsynchronousCompletionTask {
    CompletableFuture<T> dep; 
    Supplier<? extends T> fn;

    AsyncSupply(CompletableFuture<T> dep, Supplier<? extends T> fn) {
        this.dep = dep; this.fn = fn;
    }

    public void run() {
        CompletableFuture<T> d; Supplier<? extends T> f;
        if ((d = dep) != null && (f = fn) != null) {
            dep = null; fn = null; // Clears references immediately to assist GC!
            if (d.result == null) {
                try {
                    d.completeValue(f.get()); // CAS transition to result
                } catch (Throwable ex) {
                    d.completeThrowable(ex);  // Stores AltResult(ex)
                }
            }
            d.postComplete(); // Wakes and fires dependent Treiber stack stages
        }
    }
}
```

**Key Architectural Insights:**
1. References to `dep` and `fn` are nulled out immediately before executing `f.get()`, preventing garbage collection retention if the lambda captured a large outer scope.
2. Any `Throwable` (including JVM `Error` and `RuntimeException`) is caught and safely stored in the `result` field as an `AltResult`, failing the future gracefully without killing the worker thread.

## 4 Tricky Questions

### 1. What happens if `supplier.get()` inside `supplyAsync()` returns `null`? Is it considered a failure?

**Answer:**
**No, it is not considered an error.**
The future completes successfully. Internally, `CompletableFuture` represents `null` using the sentinel `NIL` (an instance of `AltResult` with a null `Throwable`). When `future.join()` is called or when the value is passed to downstream consumers like `.thenAccept(val -> ...)`, `NIL` is transparently unwrapped back to `null`.

### 2. What is the difference between `executorService.submit(callable)` and `CompletableFuture.supplyAsync(supplier, executorService)`?

**Answer:**
- `executorService.submit(Callable<T>)` returns a legacy `Future<T>` (Java 5). It lacks non-blocking composition, chaining, and error handling, forcing callers to block via `get()`. However, `Callable` can declare checked exceptions (`throws Exception`).
- `CompletableFuture.supplyAsync(Supplier<T>, executor)` returns a composable `CompletableFuture<T>` supporting 40+ reactive continuation methods (`CompletionStage`). However, `Supplier` does not allow checked exceptions without runtime wrapping.

### 3. If a task submitted to `supplyAsync()` hangs, and `future.cancel(true)` is invoked, does the thread executing the task get interrupted?

**Answer:**
**No, the task continues executing to completion.**
Unlike `FutureTask`, in `CompletableFuture.cancel(boolean mayInterruptIfRunning)`, the `mayInterruptIfRunning` flag is **completely ignored**. Calling `cancel()` atomically transitions the `CompletableFuture` instance into an exceptionally completed state with `CancellationException`. However, **no `Thread.interrupt()` call is dispatched** to the underlying worker thread. To support true cooperative cancellation, task logic must poll an external cancellation flag.

### 4. What happens if you pass `null` as the supplier: `CompletableFuture.supplyAsync(null)`?

**Answer:**
The method throws a **`NullPointerException` immediately in the calling thread** before any task is submitted to an executor.
`CompletableFuture` validates its input arguments upfront via `if (f == null) throw new NullPointerException();`, preventing invalid, empty tasks from entering the execution pipeline.

## 🎯 Interview Cheat Sheet

### Summary in 60 Seconds
- `supplyAsync(Supplier<T>)`: Asynchronously launches a computation returning value $T$.
- `runAsync(Runnable)`: Asynchronously launches a computation returning `Void`.
- Defaults to `ForkJoinPool.commonPool()`; always pass an explicit `Executor` for I/O operations.
- `Supplier` does not declare checked exceptions; wrap them in `RuntimeException` or `UncheckedIOException`.
- Returning `null` from the supplier is valid and completes the future successfully.
- `future.cancel(true)` marks the future cancelled, but does **not** interrupt the executing worker thread.

### Common Interview Mistakes
- Confusing `supplyAsync` (returns `CompletableFuture<T>`) with `runAsync` (returns `CompletableFuture<Void>`).
- Assuming `cancel(true)` interrupts the worker thread running `supplyAsync`.
- Wrapping blocking I/O in `supplyAsync` without providing an isolated custom thread pool.
