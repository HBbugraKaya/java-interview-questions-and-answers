# Что хранится в Stack

---

## 🟢 Junior Level

**Stack (Стек вызовов)** — это область оперативной памяти, выделяемая виртуальной машиной Java индивидуально для каждого работающего потока (**Thread-Local Memory**). Стек организован по принципу **LIFO (Last-In, First-Out)**: данные последнего вызванного метода помещаются наверх стека и первыми удаляются при его завершении.

Стек полностью изолирован между потоками: ни один поток не может получить прямой доступ к стеку другого потока, что обеспечивает абсолютную потокобезопасность локальных переменных.

---

### Что хранится в Stack:
1. **Примитивные локальные переменные:** значения типов `int`, `long`, `boolean`, `double`, `float`, `char`, `byte`, `short`, объявленные внутри методов.
2. **Ссылки на объекты (Reference Variables):** 4-байтные (при Compressed OOPs) или 8-байтные адреса, указывающие на реальные объекты, которые размещены в куче (Heap).
3. **Стековые фреймы (Stack Frames):** служебные блоки контекста выполнения каждого активного в данный момент метода.

---

### Бытовая аналогия
- **Стопка подносов в столовой:** Вызов метода — это новый поднос, положенный поверх стопки. На него ставят тарелки (локальные переменные). Когда блюдо съедено (метод вернул результат), верхний поднос снимается. Память освобождается мгновенно — сборщик мусора (GC) для стека не требуется, так как аппаратный указатель вершины стека (Stack Pointer) просто сдвигается процессором.

---

### Наглядный пример

```java
public class StackDemo {
    public void firstMethod() {
        int x = 10;                // Примитив в Stack (фрейм firstMethod)
        secondMethod(x);           // Добавление нового фрейма поверх
    }                              // Фрейм firstMethod уничтожается

    private void secondMethod(int param) {
        boolean flag = true;       // Примитив в Stack (фрейм secondMethod)
        User user = new User();    // Ссылка user в Stack -> объект в Heap
    }                              // Фрейм secondMethod уничтожается
}
```

**Ошибки переполнения стека:**
- **`java.lang.StackOverflowError`:** возникает при исчерпании размера стека потока (чаще всего из-за бесконечной рекурсии или чрезмерно глубокой вложенности вызовов).
- Размер стека настраивается флагом `-Xss` (по умолчанию **1024 КБ** на 64-битных ОС).

## 🟡 Middle Level

### Анатомия стекового фрейма (Stack Frame)

При каждом вызове метода виртуальная машина выделяет на вершине стека потока новый фрейм. Точный размер каждого компонента фрейма рассчитывается компилятором `javac` заранее и фиксируется в заголовке метода в скомпилированном `.class` файле.

```
┌────────────────────────────────────────────────────────┐
│                      STACK FRAME                       │
├────────────────────────────────────────────────────────┤
│ 1. Local Variable Table (LVT)                          │
│    - Массив 32-битных слотов                           │
│    - Слот 0: 'this' (для нестатических методов)        │
│    - Входные параметры метода                          │
│    - Локальные переменные                              │
├────────────────────────────────────────────────────────┤
│ 2. Operand Stack (Стек операндов)                      │
│    - Рабочая область для вычислений байткод-инструкций │
│    - Выполнение push/pop, сложения, сравнения          │
├────────────────────────────────────────────────────────┤
│ 3. Frame Data (Служебные данные)                       │
│    - Dynamic Linking (ссылка на Constant Pool класса)  │
│    - Normal Method Completion (адрес возврата в caller)│
│    - Exception Table (диспетчеризация catch-блоков)    │
└────────────────────────────────────────────────────────┘
```

#### Особенности Local Variable Table (Таблица локальных переменных):
- Состоит из 32-битных слотов.
- Типы `int`, `float`, `reference`, `boolean`, `byte`, `char`, `short` занимают **1 слот**.
- 64-битные типы `long` и `double` занимают **2 последовательных слота**.
- **Переиспользование слотов (Slot Sharing):** Если переменные объявлены в непересекающихся блоках видимости внутри метода, JVM назначает им один и тот же индекс слота, экономя память фрейма:
  ```java
  public void slotReuse() {
      {
          int a = 1; // Занимает слот 1
      }
      int b = 2;     // Занимает тот же слот 1!
  }
  ```

### Анализ стека: StackWalker API (Java 9+)

До Java 9 анализ стека вызовов производился через `new Throwable().getStackTrace()` или `Thread.currentThread().getStackTrace()`. Это приводило к серьезным просадкам производительности, так как JVM принудительно материализовала весь нативный стек целиком.

Начиная с Java 9, используется производительный **`StackWalker`**:
- Работает **лениво (lazy evaluation)**: фреймы читаются потоково только до нужной глубины.
- Позволяет фильтровать служебные фреймы (reflection, lambda, proxy).

```java
public class StackInspection {
    public void logCaller() {
        StackWalker walker = StackWalker.getInstance(StackWalker.Option.RETAIN_CLASS_REFERENCE);
        String callerClass = walker.walk(frames -> frames
            .skip(1) // Пропустить текущий метод
            .findFirst()
            .map(StackWalker.StackFrame::getClassName)
            .orElse("Unknown"));
        System.out.println("Вызов совершен из: " + callerClass);
    }
}
```

## 🔴 Senior Level

### Трассировка выполнения на уровне байткода

Рассмотрим, как Local Variable Table (LVT) и Operand Stack взаимодействуют на уровне инструкций JVM:

```java
public int calculate(int a, int b) {
    int c = a + b;
    return c;
}
```

Байткод метода (вывод `javap -c -v`):
```bytecode
public int calculate(int, int);
  descriptor: (II)I
  flags: (0x0001) ACC_PUBLIC
  Code:
    stack=2, locals=4, args_size=3
       0: iload_1         // Поместить int из LVT[1] (параметр a) на Operand Stack
       1: iload_2         // Поместить int из LVT[2] (параметр b) на Operand Stack
       2: iadd            // Снять два числа со стека, сложить, положить сумму обратно
       3: istore_3        // Снять сумму со стека и сохранить в LVT[3] (переменная c)
       4: iload_3         // Поместить LVT[3] на стек для возврата
       5: ireturn         // Вернуть верхнее значение Operand Stack вызывающему методу
```
*Обратите внимание:* `locals=4` (слот 0 — `this`, слот 1 — `a`, слот 2 — `b`, слот 3 — `c`), `stack=2` (максимальная глубина стека операндов равна 2).

### Виртуальные потоки (Virtual Threads, Java 21+) и память стека

В классической модели платформенных потоков (Platform Threads) каждый поток жестко связан с потоком операционной системы (`pthread`) с фиксированным размером стека `-Xss1m`. При 5000 потоков только на стеки резервируется ~5 ГБ виртуальной памяти.

**Виртуальные потоки (Project Loom):**
1. Стек виртуального потока хранится не в нативной памяти ОС, а в **Heap** в виде цепочки объектов `Continuation`.
2. Начальный размер стека составляет всего несколько сотен байт и растет/уменьшается динамически.
3. При блокирующей операции (сокет, блокировка) виртуальный поток отмонтируется (**unmount**) от несущего потока (Carrier Thread). Содержимое стека сохраняется в куче, а Carrier Thread немедленно берет в работу другой виртуальный поток.
4. Это позволяет легко удерживать в памяти миллионы конкурентных потоков одновременно.

#### Проблема закрепления (Thread Pinning Gotcha):
Если виртуальный поток выполняет блокирующую операцию внутри блока **`synchronized`** или нативного вызова через **JNI**, поток не может отмонтироваться («закрепляется» / pinned к Carrier Thread). Это блокирует системный поток ОС и нивелирует преимущества виртуальных потоков. Решение: замена `synchronized` на `ReentrantLock`.

---

### Почему в Java нет Tail Call Optimization (TCO)?

В функциональных языках (Scala, Clojure, Haskell) компилятор заменяет хвостовую рекурсию плоским циклом, переиспользуя один и тот же стек-фрейм (TCO). В HotSpot JVM прямая поддержка TCO отсутствует по двум фундаментальным архитектурным причинам:
1. **Security & Permissions Check:** Механизм безопасности Java (`AccessController.doPrivileged()` и `SecurityManager`) выполняет аудит прав доступа посредством анализа всей цепочки стек-фреймов вызывающих методов (Stack Inspection). Схлопывание фреймов сломало бы модель безопасности платформы.
2. **StackTrace Fidelity:** Для точной отладки и формирования информативных `StackTrace` в логах JVM обязана сохранять полную историю переходов между методами.

> 💡 **Компенсация через JIT Inlining:** Вместо TCO компилятор C2 выполняет агрессивный **Method Inlining**: небольшие методы встраиваются прямо в тело вызывающего метода, что полностью устраняет накладные расходы на создание стек-фреймов.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «**Stack** — это приватная область памяти каждого потока с мгновенным LIFO-доступом, где хранятся стековые фреймы исполняемых методов. Внутри каждого фрейма находятся: **Local Variable Table** (локальные примитивы и ссылки на объекты кучи), **Operand Stack** (рабочая зона байткод-инструкций) и **Frame Data** (динамическое связывание и адреса возврата). Стек очищается аппаратно по указателю, поэтому GC его не затрагивает. В Java 21+ виртуальные потоки кардинально изменили работу со стеком: их фреймы хранятся в **Heap** как чанки `Continuation`, динамически сжимаясь до сотен байт, что позволяет создавать миллионы потоков вместо тысяч».

### 3–4 каверзных вопроса с ответами

1. **Что конкретно хранится внутри стекового фрейма?**
   - *Ответ:* Стек-фрейм состоит из трех основных блоков:
     1. *Local Variable Table (LVT)* — индексированный массив слотов для хранения входных параметров, ссылки `this` и локальных переменных.
     2. *Operand Stack* — стек операндов, куда инструкции байткода загружают значения для вычислений и куда помещают результаты.
     3. *Frame Data* — метаданные вызова: ссылка на Runtime Constant Pool текущего класса для динамического связывания, адрес возврата в вызывающий метод и ссылка на таблицу обработки исключений.

2. **Почему типы `long` и `double` занимают два слота в Local Variable Table?**
   - *Ответ:* Архитектура JVM изначально проектировалась с ориентацией на 32-битный размер слота локальных переменных. Для размещения 64-битных типов данных (`long` и `double`) в спецификации JVM закреплено выделение двух последовательных слотов (индексация последующей переменной сдвигается на 2).

3. **Почему в Java JVM отсутствует оптимизация хвостовой рекурсии (Tail Call Optimization)?**
   - *Ответ:* TCO отсутствует намеренно ради сохранения полной картины стека вызовов:
     - Для работы проверок безопасности, зависящих от анализа всех классов в стеке вызовов (Stack Inspection).
     - Для сохранения точной информации в `Throwable.printStackTrace()` при расследовании инцидентов.
     Частично вызовы компенсируются JIT-компилятором с помощью инлайнинга методов (Method Inlining).

4. **Что такое Thread Pinning (закрепление) виртуального потока в Java 21?**
   - *Ответ:* Это ситуация, когда виртуальный поток уходит в блокирующее ожидание (например, сетевой I/O), но не может отмонтироваться от системного несущего потока (Carrier Thread) и сериализовать свой стек в кучу. Это происходит, если блокировка происходит внутри блока/метода `synchronized` или нативного JNI-вызова. В результате несущий поток простаивает, блокируя планировщик `ForkJoinPool`. Для устранения этой проблемы в Java 21+ синхронизацию заменяют на `java.util.concurrent.locks.ReentrantLock`.

### Типичные ошибки и Red Flags

- 🚩 **Утверждение: «Объекты хранятся в Stack»** (в стеке живут исключительно примитивы и ссылки-указатели, сами объекты — в Heap).
- 🚩 **Заблуждение: «Stack общий для всех потоков»** (стек строго изолирован и привязан к конкретному потоку).
- 🚩 **Утверждение: «Java поддерживает TCO (хвостовую рекурсию)»** (демонстрирует непонимание ограничений JVM).
- 🚩 **Попытка лечить `StackOverflowError` только увеличением флага `-Xss`** без поиска бесконечной или неконтролируемой рекурсии в алгоритмах.
