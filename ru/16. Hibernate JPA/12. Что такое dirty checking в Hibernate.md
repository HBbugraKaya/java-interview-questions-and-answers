# Что такое dirty checking в Hibernate

Dirty Checking (Автоматическое отслеживание «грязных» изменений) — это встроенный механизм Hibernate и спецификации JPA, который автоматически фиксирует любые мутации полей управляемых сущностей (**`Managed`**) в течение транзакции и синхронизирует их с базой данных в момент сброса контекста (**`flush`**). Благодаря этому механизму разработчику не требуется вручную формировать запросы `UPDATE` или вызывать методы `save()` / `update()` у репозитория.

---

## 🟢 Junior Level

### Как работает Dirty Checking

Когда сущность загружается из базы данных с помощью `entityManager.find()` или JPQL-запроса, она переходит в состояние `Managed`. Hibernate не просто отдает Java-объект приложению, а сохраняет в памяти точную копию его исходного состояния — **снимок (Snapshot)**.

В конце транзакции (или перед выполнением нового запроса) Hibernate сравнивает текущие значения полей объекта со снимком. Если обнаружены различия, автоматически генерируется и выполняется SQL-запрос `UPDATE`.

```java
@Transactional
public void updateUserEmail(Long userId, String newEmail) {
    // 1. Загрузка сущности: Hibernate сохраняет snapshot состояния полей
    User user = entityManager.find(User.class, userId);

    // 2. Обычная мутация через сеттер
    user.setEmail(newEmail);

    // 3. НИКАКИХ entityManager.merge(user) или repository.save(user)!
    // При выходе из метода Spring зафиксирует транзакцию,
    // Hibernate выполнит dirty checking и сам отправит SQL UPDATE в БД:
    // UPDATE users SET email = ?, name = ?, age = ? WHERE id = ?
}
```

```
                   ЖИЗНЕННЫЙ ЦИКЛ DIRTY CHECKING
                   
   [ SELECT из БД ] ──> Загрузка User (name="Иван", email="a@ya.ru")
          │
          ├──> 1. Создание Java-объекта в Heap: User@0x1
          │
          └──> 2. Создание снимка (Snapshot): ["Иван", "a@ya.ru"] в L1 Cache
          
   [ Бизнес-логика ] ──> user.setEmail("new@ya.ru")
          
   [ Фаза FLUSH ]
          │
          ├──> Сравнение: User@0x1 ("new@ya.ru") != Snapshot ("a@ya.ru")
          │
          └──> Генерация SQL: UPDATE users SET email = 'new@ya.ru' WHERE id = 1;
```

### Основные правила Dirty Checking

1. **Работает только для состояния `Managed`:** Изменения в объектах со статусом `Transient` или `Detached` Hibernate не отслеживает.
2. **Отложенное выполнение (Write-Behind):** Сеттер `user.setName(...)` не отправляет SQL мгновенно. Все изменения накапливаются в памяти до фазы `flush()`.
3. **Холостой ход:** Если вернуть полю первоначальное значение до момента коммита (`user.setName("Old"); user.setName("Old");`), Dirty Checking поймет, что состояние совпадает со снимком, и SQL `UPDATE` сгенерирован не будет.

## 🟡 Middle Level

### Когда именно запускается проверка Dirty Checking

Dirty Checking активируется во время процедуры **`flush`** контекста постоянства. Моменты срабатывания зависят от режима `FlushModeType`:

1. **При коммите транзакции:** Завершение метода с `@Transactional` инициирует `flush()` и отправку всех накопленных `UPDATE` перед фиксацией транзакции в СУБД.
2. **Перед выполнением JPQL / Criteria / Native запросов (при `FlushModeType.AUTO`):**
   Если приложение изменило сущность `User`, а затем выполняет запрос к таблице пользователей:
   ```java
   user.setStatus("BLOCKED");
   // Чтобы запрос вернул актуальные данные, Hibernate СНАЧАЛА делает flush dirty checking:
   List<User> blockedUsers = entityManager.createQuery("FROM User WHERE status = 'BLOCKED'", User.class).getResultList();
   ```
3. **При явном вызове `entityManager.flush()`:** Принудительный сброс контекста разработчиком.

### Проблема обновления всех колонок по умолчанию и `@DynamicUpdate`

По умолчанию Hibernate генерирует **один и тот же статический SQL `UPDATE`** для сущности, перечисляя в нем абсолютно все колонки таблицы, даже если изменилось всего одно поле:

```sql
-- Изменился только email, но обновляются все поля:
UPDATE users SET name = ?, email = ?, created_at = ?, role = ? WHERE id = ?;
```

Чтобы генерировать SQL строго по измененным полям, применяется аннотация `@DynamicUpdate`:
```java
@Entity
@Table(name = "users")
@org.hibernate.annotations.DynamicUpdate
public class User {
    // ...
}
```

```sql
-- При @DynamicUpdate сгенерируется точечный SQL:
UPDATE users SET email = ? WHERE id = ?;
```

#### Почему `@DynamicUpdate` НЕ включен по умолчанию:
- СУБД кэширует планы выполнения для параметризованных запросов (Prepared Statement Execution Plans).
- Без `@DynamicUpdate` SQL-запрос `UPDATE` всегда идентичен, база данных переиспользует скомпилированный план из кэша.
- С `@DynamicUpdate` для каждого набора измененных колонок генерируется уникальный SQL, что приводит к компиляции нового плана на каждый чих, загрязнению кэша запросов СУБД и дополнительным накладным расходам CPU Hibernate на динамическую сборку строки запроса.
- **Правило:** Применяйте `@DynamicUpdate` только для очень широких таблиц (30+ колонок), таблиц с `BLOB`/`TEXT` полями или при высоком риске конкурентной перезаписи несвязанных колонок.

### Отключение отслеживания (Read-Only сущности)

Сравнение со снимком требует времени CPU $O(N \times M)$ ($N$ — количество сущностей, $M$ — количество полей) и расходует дополнительную память JVM на хранение снимков.

Для запросов на чтение снимки можно отключить:
```java
// Через Spring Data JPA / Query Hint
@QueryHints(@QueryHint(name = org.hibernate.jpa.HibernateHints.HINT_READ_ONLY, value = "true"))
@Query("SELECT u FROM User u WHERE u.country = :country")
List<User> findUsersReadOnly(@Param("country") String country);
```
Для таких сущностей снимок `loadedState` не сохраняется, и фаза dirty checking пропускает их за $O(0)$, снижая время коммита транзакции.

## 🔴 Senior Level

### Внутренности Dirty Checking: Snapshot-based vs Bytecode Enhancement

Существует два фундаментальных механизма реализации Dirty Checking в Hibernate:

```
┌────────────────────────────────────────────────────────────────────────┐
│                   МЕХАНИЗМЫ ДЕТЕКЦИИ ИЗМЕНЕНИЙ                         │
├────────────────────────────────────┬───────────────────────────────────┤
│ 1. Снимок по умолчанию (Snapshot)  │ 2. Bytecode Enhancement Tracking  │
├────────────────────────────────────┼───────────────────────────────────┤
│ • SessionImpl хранит Object[]      │ • Плагин компилятора модифицирует │
│ • При flush(): цикл по всем полям  │   байт-код сущности               │
│ • Сравнение через equals / ==      │ • Сущность реализует SelfDirty    │
│ • Расход памяти: 2x (сущность +    │ • Сеттер сам взводит dirty-флаг   │
│   снапшот каждого поля)            │ • Нулевой оверхед памяти на снимок│
│ • Сложность при flush: O(N * M)    │ • Сложность при flush: O(K)       │
│                                    │   где K — только измененные       │
└────────────────────────────────────┴───────────────────────────────────┘
```

#### Механизм 1: Снимок по умолчанию (Snapshot-based)
В `StatefulPersistenceContext` хранится `EntityEntry`, содержащий массив `Object[] loadedState`. При вызове `flush()` класс `DefaultFlushEntityEventListener` вызывает метод `Type.isDirty(old, current)`.
- Для примитивов и неизменяемых типов (`String`, `Long`) выполняется обычное равенство значений.
- Для коллекций (`List`, `Set`) используется обертка `PersistentCollection` (`PersistentBag`, `PersistentSet`), которая хранит внутри себя снимок ключей и элементов на момент загрузки.

#### Механизм 2: Bytecode Enhancement (Продвинутый трекинг)
С помощью плагина Maven/Gradle байт-код классов модифицируется на этапе сборки:
```xml
<plugin>
    <groupId>org.hibernate.orm.tooling</groupId>
    <artifactId>hibernate-enhance-maven-plugin</artifactId>
    <executions>
        <execution>
            <configuration>
                <enableDirtyTracking>true</enableDirtyTracking>
            </configuration>
            <goals>
                <goal>enhance</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```
Класс сущности прозрачно начинает реализовывать интерфейс `org.hibernate.engine.spi.SelfDirtyTracker`. При вызове любого сеттера байт-код автоматически добавляет имя измененного поля во внутреннюю структуру `tracker`. Во время `flush()` Hibernate не выполняет никаких сравнений: он мгновенно берет список измененных полей из самого объекта, сокращая время сброса в десятки раз.

### Тонкости Dirty Checking для пользовательских типов и `@Embedded`

Если сущность содержит составной объект (`@Embedded`):
```java
@Embedded
private Address address;
```
1. Если изменить поле адреса: `user.getAddress().setCity("Москва")`.
2. Hibernate при стандартном snapshot-анализе сравнивает поля вложенного компонента рекурсивно.
3. **Ловушка изменяемых пользовательских типов (`@Type`):** Если вы используете собственный класс и кастомный `UserType`, метод `equals(Object x, Object y)` и `deepCopy(Object value)` должны быть реализованы идеально строго. Если `deepCopy()` возвращает ту же самую ссылку вместо глубокого клона, `loadedState` будет ссылаться на тот же объект, что и текущее поле, Dirty Checking посчитает `old == current` и **никогда не сохранит изменения в БД**!

## 4 Tricky Questions

### 1. Почему Hibernate по умолчанию обновляет ВСЕ колонки таблицы в SQL UPDATE, и в каких случаях включение `@DynamicUpdate` может УХУДШИТЬ производительность высоконагруженной СУБД?

**Ответ:**
1. Статический запрос со всеми полями компилируется СУБД (PostgreSQL, Oracle, MySQL) ровно один раз. План выполнения помещается в Prepared Statement Cache как на стороне драйвера JDBC, так и в `shared_buffers` СУБД.
2. При включении `@DynamicUpdate` для таблицы из 20 колонок существует теоретически $2^{20} - 1$ различных вариантов SQL `UPDATE`.
3. Каждый уникальный вариант запроса требует от СУБД повторного парсинга, оптимизации и генерации нового плана выполнения (Hard Parse), что перегружает CPU базы данных и вымывает полезные запросы из кэша планов.
4. Кроме того, сам Hibernate тратит дополнительное процессорное время на динамическую склейку SQL-строки при каждом `flush()`.

### 2. Что произойдет, если в транзакционном методе изменить сущность `user.setName("Петр")`, а затем в этом же методе будет выброшено непроверяемое исключение (`RuntimeException`)? Сохранится ли имя в БД?

**Ответ:**
1. Нет, изменение в базе данных **не зафиксируется**.
2. По умолчанию в Spring `@Transactional` перехватывает `RuntimeException` и выполняет команду `ROLLBACK` транзакции базы данных.
3. Даже если до момента выброса исключения был выполнен явный промежуточный `entityManager.flush()` и SQL `UPDATE` физически ушел в сетевой сокет СУБД, откат транзакции (`ROLLBACK`) вернет состояние строки в БД к исходному.

### 3. Мы загрузили сущность, изменили ее поле `user.setStatus("ACTIVE")`, а затем вызвали `entityManager.detach(user)`. Сгенерирует ли Hibernate SQL UPDATE при коммите транзакции?

**Ответ:**
1. Нет, SQL `UPDATE` **не будет сгенерирован**.
2. Метод `detach(user)` удаляет экземпляр сущности из структур `entitiesByKey` и `entityEntries` контекста `StatefulPersistenceContext`.
3. В момент вызова `flush()` перед коммитом транзакции Hibernate сканирует только сущности, оставшиеся в статусе `Status.MANAGED`. Поскольку отсоединенного объекта в реестре больше нет, его снимок игнорируется, а накопленные изменения в памяти теряются.

### 4. Почему вызов метода `user.setName(user.getName())` (присвоение того же самого значения) не генерирует SQL UPDATE, но все равно имеет накладные расходы?

**Ответ:**
1. Dirty Checking выполняет сравнение через `Objects.equals(loadedState[i], currentState[i])`. Так как значения эквивалентны, Hibernate корректно определяет отсутствие изменений и не планирует операцию в `ActionQueue`.
2. Однако накладные расходы заключаются в самом цикле обхода: для каждой сущности в контексте извлекаются массивы полей через reflection/аксессоры. Если в сессии загружено 20 000 сущностей по 15 полей, движок все равно выполнит 300 000 проверок равенства во время фазы сброса контекста.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «Dirty Checking — это встроенный механизм Hibernate, отслеживающий изменения полей управляемых сущностей (`Managed`) и автоматически синхронизирующий их с БД через SQL `UPDATE` во время фазы `flush`. По умолчанию Hibernate сохраняет снимок (`loadedState`) при чтении объекта и сравнивает его с текущим состоянием перед коммитом транзакции. Ручной вызов `save()` или `merge()` для управляемых объектов избыточен. По умолчанию обновляются все колонки для эффективного переиспользования планов Prepared Statement в СУБД, но через `@DynamicUpdate` можно включить выборочный UPDATE. Для оптимизации тяжелых выборок следует использовать read-only запросы или плагин Bytecode Enhancement».

### Ключевые метрики для Production-мониторинга
- **Flush Duration (`session.getStatistics().getFlushCount()` / `getTransactionCount()`)**: среднее время, затрачиваемое на детекцию изменений. Рост выше 50 мс говорит о раздутом `PersistenceContext`.
- **Prepared Statement Cache Hit Ratio в пуле соединений (HikariCP / БД)**: резкое падение указывает на злоупотребление `@DynamicUpdate`.

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«После изменения поля сущности обязательно нужно вызвать repository.save(entity) или entityManager.merge(entity)»* — Это фундаментальное непонимание жизненного цикла JPA. Для Managed-сущностей dirty checking сделает всё сам.
- ❌ *«Dirty checking работает для любых Java-объектов в приложении»* — Работает строго для сущностей в состоянии `Managed` внутри открытой сессии.
- ❌ *«Я всегда ставлю @DynamicUpdate на все классы для экономии трафика»* — Приводит к деградации кэша планов запросов в СУБД.
- ❌ *«Каждый сеттер сущности сразу же отправляет запрос UPDATE в базу данных»* — Hibernate использует write-behind и накапливает изменения до момента `flush()`.
