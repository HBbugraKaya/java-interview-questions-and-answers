# Какие требования к ресурсам в try-with-resources

---

## 🟢 Junior Level

Для того чтобы объект мог быть использован в конструкции `try-with-resources`, к нему предъявляется **одно строгое синтаксическое требование на уровне компилятора Java**:

> **Тип ресурса обязан реализовывать интерфейс `java.lang.AutoCloseable`** (или его дочерний интерфейс `java.io.Closeable`).

Если класс не реализует `AutoCloseable`, компилятор `javac` завершит сборку с ошибкой:
`The resource type ... does not implement java.lang.AutoCloseable`.

### Базовый пример

```java
// Собственный ресурс, пригодный для использования в TWR
public class DatabaseSession implements AutoCloseable {

    public void executeQuery(String sql) {
        System.out.println("Executing: " + sql);
    }

    @Override
    public void close() {
        System.out.println("Session closed successfully");
    }
}
```

Использование в блоке:
```java
try (DatabaseSession session = new DatabaseSession()) {
    session.executeQuery("SELECT * FROM users");
} // Здесь компилятор автоматически вызовет session.close()
```

## 🟡 Middle Level

### 4 инженерных требования к методу close()

Хотя компилятор проверяет только наличие интерфейса `AutoCloseable`, к качественной реализации метода `close()` предъявляются критические требования надежности:

#### 1. Идемпотентность (Idempotency)
Повторный вызов метода `close()` **не должен приводить к ошибке или повторному освобождению памяти**:
- Первый вызов освобождает ресурс.
- Все последующие вызовы тихо игнорируются (no-op).
- Для многопоточных ресурсов флаг закрытия защищают через `AtomicBoolean`:
  ```java
  private final AtomicBoolean closed = new AtomicBoolean(false);

  @Override
  public void close() {
      if (closed.compareAndSet(false, true)) {
          // Реальное освобождение сокета или файла
      }
  }
  ```

#### 2. Сужение сигнатуры throws (Exception Narrowing)
Интерфейс `AutoCloseable` объявляет метод:
`void close() throws Exception;`

Реализация в прикладном классе **настоятельно рекомендует сузить тип выбрасываемого исключения** (или убрать `throws` вовсе, если метод завершается безотказно):
```java
// ✅ ХОРОШО: метод объявляет конкретный IOException или не бросает ничего
public class MemoryBuffer implements AutoCloseable {
    @Override
    public void close() { 
        // Не бросает checked-исключений, клиенту не нужен try-catch вокруг TWR!
    }
}
```
*Если оставить `throws Exception`, вызывающему коду придется писать `catch (Exception e)`, перехватывая лишние ошибки.*

#### 3. Быстродействие и отсутствие блокировок
Метод `close()` не должен выполнять тяжелые сетевые вызовы, долгие транзакции или блокироваться без таймаутов, так как он выполняется в критической фазе очистки потока.

#### 4. Не выбрасывать исключения при очистке в catch
Если в теле `try` произошел сбой, метод `close()` обязан попытаться корректно освободить нативные ресурсы, даже если внутреннее состояние объекта частично повреждено.

## 🔴 Senior Level

### Требования Java 9+: переменные должны быть Effectively Final

Начиная с Java 9, в круглых скобках TWR разрешено указывать ссылки на уже объявленные переменные:
```java
final Resource r1 = new Resource();
Resource r2 = new Resource(); // effectively final

try (r1; r2) {
    // работа с ресурсами
}
```

**Критическое правило:** переменные обязаны быть `final` или `effectively final` (значение ссылки не переприсваивается после инициализации).
*Под капотом JVM:* Компилятор генерирует скрытую локальную синтетическую переменную внутри байткода метода (`final Resource $r1 = r1;`). Это защищает от ситуации, когда другой поток мог бы подменить ссылку на объект в процессе выполнения блока `try`.

### Проблема «Частично сконструированного ресурса» (Constructor Failure)

Если конструктор ресурса открывает нативный дескриптор файла в ОС, а затем падает с ошибкой до завершения инициализации:
```java
public class BrokenResource implements AutoCloseable {
    private final FileDescriptor fd;

    public BrokenResource(String path) {
        this.fd = openNativeFile(path); // 1. Нативный ресурс захвачен!
        throw new RuntimeException("Crash"); // 2. Сбой конструктора!
    }

    @Override
    public void close() {
        closeNativeFile(fd);
    }
}
```
**Последствия:** Поскольку конструктор завершился аварийно, ссылка на объект не была возвращена, переменная в `try (...)` не была инициализирована, и **TWR никогда не вызовет метод `close()`**! Нативный дескриптор навсегда утечет в операционную систему.

**Senior-решение: Идиома 2-фазной инициализации или фабричного метода:**
```java
public static SafeResource open(String path) {
    FileDescriptor fd = openNativeFile(path);
    try {
        return new SafeResource(fd);
    } catch (Throwable t) {
        closeNativeFile(fd); // Гарантированная очистка при падении конструктора
        throw t;
    }
}
```

### Пулы соединений (HikariCP / Commons DBCP)

В высоконагруженных enterprise-системах открытие физического TCP-соединения к PostgreSQL занимает 20–50 мс. 
Поэтому классы соединений `java.sql.Connection`, выдаваемые HikariCP, являются **прокси-обертками (`ProxyConnection`)**:
- Они реализуют `AutoCloseable`.
- При вызове TWR метода `connection.close()` физический сокет **не закрывается**; прокси-объект просто возвращает соединение обратно в пул свободных коннектов HikariCP за доли микросекунды.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> - **Синтаксическое требование компилятора:** Тип ресурса обязан реализовывать интерфейс **`java.lang.AutoCloseable`** (или `java.io.Closeable`).
> - **Требования к методу `close()`:**
>   1. **Идемпотентность:** Повторные вызовы `close()` не должны приводить к исключениям.
>   2. **Сужение сигнатуры `throws`:** Не объявлять `throws Exception`, а указывать конкретные типы (например, `IOException`) либо вовсе убирать checked-исключения, если закрытие безотказно.
>   3. **Неблокирующее выполнение:** Не допускать вечных блокировок в `close()`.
> - **Java 9+ требование:** Внешние переменные, передаваемые в TWR, обязаны быть `final` или `effectively final`.
> - Для ресурсов из пулов (HikariCP) вызов `close()` в TWR возвращает ресурс в пул, а не уничтожает его.

### 4 каверзных вопроса с ответами

1. **Что произойдет, если класс ресурса имеет публичный метод `void close()`, но не реализует интерфейс `AutoCloseable`?**
   *Ответ:* Код не скомпилируется. Java является строго типизированным языком, и конструкция `try-with-resources` проверяет реализацию интерфейса `java.lang.AutoCloseable` на этапе статического анализа типов `javac`, а не через рефлексию.

2. **Почему в реализации метода `close()` настоятельно рекомендуется убирать или сужать секцию `throws Exception`?**
   *Ответ:* В интерфейсе `AutoCloseable` метод объявлен как `void close() throws Exception`. Если разработчик оставит `throws Exception`, то вызывающий код вокруг TWR будет обязан перехватывать или пробрасывать самый общий `Exception`, что ломает чистоту обработки ошибок. Если метод `close()` не бросает исключений, разработчику вокруг TWR не придется писать пустые блоки `catch`.

3. **Обязан ли метод close() в AutoCloseable быть идемпотентным по официальной спецификации Javadoc?**
   *Ответ:* В спецификации интерфейса `AutoCloseable` сказано, что метод *рекомендуется* делать идемпотентным, но строгое требование отсутствует. Однако в дочернем интерфейсе `java.io.Closeable` идемпотентность является **строго обязательной спецификацией** (повторный `close()` обязан быть no-op). На практике все качественные реализации `AutoCloseable` делают идемпотентными.

4. **Что произойдет, если передать в TWR переменную, которая затем изменяется в коде?**
   *Ответ:* Код не скомпилируется с ошибкой `local variables referenced from a try-with-resources statement must be final or effectively final`. Переменная должна быть неизменяемой, чтобы исключить конкурентную подмену ресурса.

### Красные флаги (чего категорически нельзя говорить)
- ❌ *«Для try-with-resources подходит любой класс, у которого есть метод close()»* (класс обязан явно имплементировать интерфейс `AutoCloseable`).
- ❌ *«Метод close() обязан каждый раз выбрасывать исключение, если ресурс уже закрыт»* (метод `close()` обязан быть идемпотентным).
- ❌ *«В Java 9 в try-with-resources можно передавать изменяемые переменные»* (переменные обязаны быть strictly final или effectively final).
- ❌ *«try-with-resources всегда физически закрывает сетевой сокет базы данных»* (в пулах соединений HikariCP метод `close()` возвращает коннект в пул).
