# What is Saga Pattern and When to Use It

The **Saga Pattern** is an architectural design pattern for managing **distributed business transactions** across microservices with decentralized, isolated databases (**Database per Service**). Because traditional distributed transactions based on Two-Phase Commit (2PC / XA) hold database locks and scale poorly across distributed cloud environments, Saga replaces them with a sequence of decoupled local transactions, ensuring **Eventual Consistency** through forward actions and **Compensating Transactions**.

---

## 🟢 Junior Level

### Why Classical ACID Fails in Microservices

In a monolithic architecture, all entity tables reside in a single database. When creating an order, Spring executes a single ACID transaction:

```java
// Monolith: Single local ACID transaction in one database
@Transactional
public void createOrder(OrderRequest request) {
    orderRepository.save(order);       // Step 1
    paymentService.charge(payment);    // Step 2
    inventoryService.reserve(items);   // Step 3
    // Failure at step 3? The database executes an immediate physical ROLLBACK!
}
```

In a microservices architecture, each service operates its **own private database** (`OrderDB`, `PaymentDB`, `InventoryDB`). There is no global transaction coordinator across heterogeneous storage engines, and a standard SQL `ROLLBACK` cannot undo changes committed across network boundaries.

```
                    DISTRIBUTED TRANSACTION PROBLEM
                    
  [ Order Service ]     ──►  [ Payment Service ]   ──►  [ Inventory Service ]
          │                          │                           │
          ▼                          ▼                           ▼
    [ Order DB ]              [ Payment DB ]              [ Inventory DB ]
  (Order Created)             (Funds Debited)             (Out of Stock! ERROR!)
        │                          │                           │
        └──────────────────────────┴───────────────────────────┘
         HOW DO WE CANCEL A COMMITTED PAYMENT IN A REMOTE DATABASE?!
```

---

### How Saga Solves the Problem

A Saga breaks a single distributed transaction into a sequence of **local ACID transactions**:
1. Each microservice executes a local transaction in its own database and emits an event/message.
2. The subsequent service listens for this event and triggers its own local transaction.
3. If a business error occurs at any step (e.g., insufficient stock), the Saga triggers a chain of **Compensating Transactions** in reverse order, semantically neutralizing previously committed changes (issuing refunds, cancelling orders).

```
                            SUCCESSFUL SAGA EXECUTION:
    [Create Order] ──► [Charge Payment] ──► [Reserve Inventory] ──► [Order Completed]

                           COMPENSATION UPON FAILURE:
    [Create Order] ──► [Charge Payment] ──► [Out of Stock! FAILURE!]
          │                    │                     │
          ▼                    ▼                     ▼
    [Cancel Order] <── [Refund Payment] <────────────┘
    (Compensation 2)   (Compensation 1)
```

## 🟡 Middle Level

### Two Saga Implementation Approaches: Choreography vs. Orchestration

| Criterion | Choreography | Orchestration |
| :--- | :--- | :--- |
| **Coordination** | Decentralized (Event-driven via Kafka/RabbitMQ) | Centralized (Explicit state machine / coordinator) |
| **Coupling** | Loose (Services only observe topic events) | Services execute commands dispatched by orchestrator |
| **Cognitive Load** | High for > 4 services (Logic scattered across services) | Low (Entire workflow is visible in coordinator code) |
| **Cyclic Dependencies** | High risk of cyclic event loops | Prevented by design |
| **Single Point of Failure (SPOF)** | None | Orchestrator must be architected for high availability |
| **Best For** | Simple workflows (2–4 participating services) | Complex business processes (5+ participating services) |

#### 1. Choreography:
Services react to domain events published by peers without a centralized orchestrator:
- `OrderService` saves an order with status `PENDING` and publishes `OrderCreatedEvent`.
- `PaymentService` consumes `OrderCreatedEvent`, charges the customer, and publishes `PaymentCompletedEvent`.
- `InventoryService` consumes `PaymentCompletedEvent`, detects zero stock, and publishes `InventoryFailedEvent`.
- `PaymentService` consumes `InventoryFailedEvent` and executes a refund (`PaymentRefundedEvent`).
- `OrderService` consumes `PaymentRefundedEvent` and updates order status to `CANCELLED`.

#### 2. Orchestration:
A dedicated component (Saga Orchestrator / Workflow Engine) dispatches explicit commands to participants:

```java
// Orchestrator coordinates the state machine
public class OrderSagaOrchestrator {

    public void execute(CreateOrderCommand cmd) {
        orderService.createPendingOrder(cmd.orderId());
        
        PaymentResult payment = paymentService.authorize(cmd.orderId(), cmd.amount());
        if (!payment.isSuccess()) {
            orderService.cancelOrder(cmd.orderId());
            return;
        }

        InventoryResult inventory = inventoryService.reserve(cmd.orderId(), cmd.items());
        if (!inventory.isSuccess()) {
            // Trigger compensating transactions in reverse order:
            paymentService.refund(cmd.orderId(), cmd.amount());
            orderService.cancelOrder(cmd.orderId());
            return;
        }

        orderService.approveOrder(cmd.orderId());
    }
}
```

## 🔴 Senior Level

### Concurrency Anomalies Due to Lack of Isolation (ACD vs. ACID)

Classical distributed transactions provide full ACID guarantees. **Saga guarantees only ACD (Atomicity, Consistency, Durability), but provides NO Isolation (Isolation = None)!**

Because each step commits immediately to its local database, intermediate states **are immediately visible to concurrent transactions**. This introduces classic concurrency anomalies at the business level:

1. **Dirty Reads:**
   - Saga 1 debits $500 from a customer's bank account.
   - Concurrent Saga 2 reads the reduced balance and rejects a credit application.
   - Saga 1 subsequently fails during inventory reservation and refunds the $500. Saga 2 made an irreversible business decision based on dirty intermediate state!
2. **Lost Updates:**
   - Saga A decrements warehouse stock from 10 to 8.
   - Saga B reads 8 and decrements to 5.
   - Saga A fails and applies a compensation (+2), writing 7 instead of the true value of 8.

#### Saga Isolation Countermeasures:
- **Semantic Lock:** Entities flag records with an intermediate pending status (e.g., `order.status = PENDING_APPROVAL`, `account.frozen_amount = 500`). Concurrent operations check this flag and back off until the lock clears.
- **Commutative Updates:** Design operations so that execution order does not affect the final result (`account.debit(50)` and `account.credit(50)` are commutative).
- **Pessimistic Ordering:** Order saga steps such that high-risk or irreversible operations (e.g., charging credit cards, dispatching physical goods) execute at the very end.

---

### The Persistent Saga Log and Transactional Outbox Pattern

A production orchestrator must never store workflow state purely in JVM heap memory. If the host container or pod terminates mid-saga, in-flight state is lost, leaving funds deducted and orders abandoned.

#### Enterprise Implementation Pattern:
1. **Saga Execution Coordinator (SEC)** writes each step transition to a relational `SagaLog` table (`saga_id`, `current_step`, `payload`, `status`).
2. Commands dispatched to remote microservices utilize the **Transactional Outbox Pattern**, ensuring local database writes and message broker dispatch occur atomically.
3. Upon restart, the orchestrator scans `SagaLog` for incomplete sagas, resuming forward execution or executing compensations past timeout limits.
4. In enterprise production, custom orchestrator frameworks are commonly superseded by dedicated workflow engines: **Temporal.io**, **Camunda (BPMN)**, **Cadence**, or **AWS Step Functions**.

## 4 Tricky Questions

### 1. Which property of ACID does Saga violate, and why is a Compensating Transaction fundamentally different from an SQL ROLLBACK?

**Answer:**
1. Saga violates **`I` (Isolation)**. Each local transaction commits immediately within its own database, making intermediate uncommitted states visible to all other transactions in the system.
2. An SQL `ROLLBACK` physically reverts database pages using undo logs, erasing the transaction as if it never occurred.
3. A Compensating Transaction is a **new forward transaction (Compensating Forward Action)**. It does not erase database history; instead, it executes a semantically opposing business operation (e.g., issuing a `REFUND` ledger entry), preserving an auditable trail of events.

---

### 2. What happens if a Compensating Transaction itself fails (e.g., payment gateway returns HTTP 500)? Can the Saga terminate?

**Answer:**
1. **No, the Saga cannot stop.** Halting compensation leaves the system in an inconsistent state (e.g., customer funds debited while their order is canceled).
2. Compensating transactions **must be designed to be strictly idempotent and highly available**.
3. The orchestrator must retry failed compensations using **Exponential Backoff** until they succeed.
4. If retries are exhausted or an unrecoverable failure occurs (e.g., bank account frozen), the event is routed to a **Dead Letter Queue (DLQ)**, triggering urgent operational alerts for human-in-the-loop manual resolution.

---

### 3. How do you resolve out-of-order messaging races (e.g., compensation message arrives BEFORE the forward action) in an asynchronous Saga?

**Answer:**
1. In distributed networks, a cancellation message (`CancelPayment`) can overtake a delayed forward message (`ProcessPayment`) due to message broker rebalancing or network latency.
2. If the cancellation executes first, a subsequent delayed payment processing command would charge the customer without a following refund.
3. **Solution — Entity State Machine:**
   - When the payment service receives `CancelPayment` for an unknown `paymentId`, it inserts a placeholder record with status `CANCELLED_BEFORE_ARRIVAL`.
   - When the delayed `ProcessPayment` command eventually arrives, the service inspects the record, sees `CANCELLED_BEFORE_ARRIVAL`, and **discards the charge command immediately**.

---

### 4. What are the fundamental differences between Two-Phase Commit (2PC) and Saga, and why is 2PC avoided in modern microservices?

**Answer:**
1. **Resource Locking:** 2PC physically locks database rows during its *Prepare* phase across all participants until the *Commit* decision is broadcast. In distributed systems, this leads to cascading latency bottlenecks and deadlocks.
2. **Single Point of Failure:** If the 2PC transaction coordinator fails during the commit phase, participant databases remain locked indefinitely.
3. **Heterogeneity Limits:** 2PC requires XA standard support across all participants. Modern message brokers (Kafka, RabbitMQ) and NoSQL databases (MongoDB, DynamoDB) do not support XA.
4. Saga uses non-blocking, decoupled local transactions, making it scalable and resilient in cloud-native microservice architectures.

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
> "The Saga pattern manages distributed transactions across microservices with isolated databases by replacing blocking Two-Phase Commit (2PC) with a sequence of local ACID transactions. When a step fails, compensating transactions execute in reverse order to achieve eventual consistency. Sagas are implemented via Choreography (event-driven pub/sub for simple 2–4 service flows) or Orchestration (centralized workflow coordinator or Temporal/Camunda for complex flows). Sagas guarantee Atomicity, Consistency, and Durability, but lack Isolation (ACD instead of ACID), requiring semantic locks to prevent dirty reads and mandatory idempotency on all compensating actions."

---

### Key Production Metrics & Indicators
- **Saga Completion vs. Compensation Rate**: Ratio of successful sagas to compensated rollbacks; a compensation rate > 5% indicates supplier inventory or payment gateway failure.
- **Saga End-to-End Latency**: Time elapsed from saga initiation to final completion or rollback.
- **Dead Letter Queue (DLQ) & Failed Compensation Count**: Critical alert metric tracking unresolved compensations requiring manual engineering intervention.

---

### Red Flags (What NOT to Say)
- ❌ *"Sagas provide complete ACID isolation across microservices."* — Sagas lack Isolation (`I`); intermediate state is visible immediately to concurrent users.
- ❌ *"A compensating transaction performs a database ROLLBACK."* — Compensations execute *new forward operations* (e.g., issuing refunds).
- ❌ *"Choreography is the best choice for enterprise sagas spanning 15 services."* — Leads to untraceable spaghetti event loops; orchestrators are required for complex workflows.
- ❌ *"If a compensation fails, we just log the error and complete the request."* — Compensations must retry endlessly or route to a DLQ for manual remediation.
