# Чому змінилася реалізація substring() в Java 7

---

## 🟢 Junior Level

Інженери Oracle та спільнота OpenJDK змінили внутрішню реалізацію методу `substring()` в оновленні **Java 7 Update 6 (JDK-7068364)** з двох ключових архітектурних причин:
1. **Усунення прихованих витоків пам'яті (Memory Retention Leaks):** У старій реалізації підрядок не копіював символи, а розділяв спільний внутрішній масив `char[]` із вихідним рядком. Через це крихітний підрядок із 5 символів утримував у купі весь величезний батьківський масив (наприклад, файл на 100 МБ), не дозволяючи збирачу сміття звільнити пам'ять.
2. **Глобальне зменшення розміру об'єкта `String` у купі:** З класу `String` видалили два поля (`int offset` та `int count`). Сам об'єкт `String` став легшим на 8 байтів (економія 25% заголовка), що зменшило загальне споживання пам'яті купи в усій екосистемі Java.

### Суть у 30 секундах
- **До Java 7u6:** `substring()` працював за $O(1)$ без копіювання, але провокував часті аварійні збої `OutOfMemoryError` через утримання гігабайтних масивів у пам'яті.
- **Після Java 7u6:** `substring()` працює за $O(N)$, створюючи незалежну копію потрібного фрагмента. Розробники свідомо пожертвували $O(1)$ заради гарантованої безпеки за пам'яттю та чистоти архітектури.

```java
// Ілюстрація проблеми витоку пам'яті в Java 6:
String loadLogLine() {
    String hugePayload = readHttpBody(); // 10 Мегабайтів
    return hugePayload.substring(0, 5);  // У Java 6: утримує всі 10 МБ!
}

// У Java 7+:
// Повернений підрядок виділяє масив рівно на 5 символів.
// 10-мегабайтний масив hugePayload безпечно знищується збирачем сміття.
```

## 🟡 Middle Level

### Технічні деталі зміни: JDK-7068364
До версії 7u6 клас `java.lang.String` зберігав 4 поля:
```java
// Java 1.0 - 7u5:
private final char[] value;
private final int offset; // 4 байти
private final int count;  // 4 байти
private int hash;
```
Метод `substring()` створював новий об'єкт `String`, у який передавав посилання на **той самий екземпляр масиву `value`**, але зі зсунутим `offset` та новим значенням `count`.

**Починаючи з Java 7u6:**
- Поля `offset` та `count` були повністю видалені.
- Поле `value.length` стало єдиним джерелом інформації про довжину рядка.
- Метод `substring()` став використовувати `Arrays.copyOfRange()`, копіюючи байти у свіжий масив точної довжини.

```
До Java 7u6 (Shared Array):
String A (10 MB) ──value──► [ A, B, C, D, E, . . . 10 000 000 chars . . . ]
                                  ▲
String B (offset=1, count=3) ─────┘  (Обидва об'єкти утримують один масив!)

Після Java 7u6 (Isolated Copy):
String A (10 MB) ──value──► [ A, B, C, D, E, . . . 10 000 000 chars . . . ] ──► GC видаляє при huge = null
String B (3 chars)──value──► [ B, C, D ] (Окремий масив на 3 символи)
```

### Порівняння архітектурних компромісів (Trade-offs)
| Характеристика | До Java 7u6 (Shared array) | Java 7u6 – Java 21+ (Copying) |
| :--- | :--- | :--- |
| **Складність за часом** | $O(1)$ (миттєво) | $O(N)$ (копіювання підмасиву) |
| **Складність за пам'яттю операції** | $O(1)$ (новий заголовок `String`) | $O(N)$ (алокація нового масиву) |
| **Розмір кожного об'єкта `String`** | 32 байти (при Compressed OOPs) | 24 байти (при Compressed OOPs) |
| **Ризик витоку пам'яті** | ⚠️ Критичний (Memory Pinning) | ❌ Відсутній (повна ізоляція) |
| **Поведінка GC** | Фрагментація Old Gen, утримання сміття | Рівномірне очищення Young/Old Gen |
| **Потреба в `new String(...)`** | Обов'язково для розриву зв'язку | ❌ Антипатерн (зайва алокація) |

## 🔴 Senior Level

### Економічне обґрунтування: чому $O(N)$ вигідніше за $O(1)$
При ухваленні рішення інженери HotSpot проаналізували реальні дампи пам'яті сотень великих корпоративних застосунків:
1. **Статистика довжин рядків:** Понад 95% рядків у типових застосунках мають довжину **менше ніж 64 символи**.
2. **Швидкість кешу L1/L2 процесора:** На сучасних процесорах копіювання 30–60 байтів через нативний виклик `System.arraycopy` (або векторний intrinsic компілятора C2) займає **від 2 до 5 наносекунд** і відбувається повністю всередині надшвидкого кешу L1D процесора. Різниця між 1 нс і 4 нс для бізнес-логіки є нехтовно малою.
3. **Економія пам'яті в усій JVM:** У корпоративному секторі рядки займають від 20% до 40% усього розміру Java Heap. Видалення полів `offset` та `count` зробило кожен інстанс `String` меншим на 8 байтів. Для застосунку з 50 мільйонами рядкових об'єктів це забезпечує **чисту економію 400 МБ купи**, що багаторазово перекриває часові витрати на копіювання.

### Вплив на роботу Garbage Collector та Old Gen Fragmentation
У старій реалізації `substring()` виникав небезпечний феномен **утримання посилань між поколіннями (Generational Pinning)**:
- Вихідний масив на 50 МБ виділявся в Eden і швидко ставав кандидатом на збирання.
- Якщо з нього вилучався підрядок, який зберігався в довгоживучому кеші, він підвищувався до **Old Generation**.
- Перейшовши в Old Gen, маленький підрядок утримував увесь 50-мегабайтний масив у пам'яті, перешкоджаючи його очищенню під час Young GC.
- У результаті відбувалося швидке вичерпання Old Generation, фрагментація купи та провокувалися важкі паузи **Full GC Stop-the-World**.

### Спрощення JIT-оптимізацій та Scalar Replacement
Видалення двох цілочисельних полів спростило внутрішнє представлення `String` для компілятора C2:
- Менше полів для аналізу під час виконання **Escape Analysis (EA)**.
- Спрощення **Scalar Replacement (скалярної декомпозиції)**: компілятору C2 значно легше «розібрати» об'єкт `String` на регістри процесора, якщо об'єкт не витікає за межі методу.
- Усунення непрямих обчислень `value[offset + i]` при кожному зверненні до `charAt()`. Тепер звернення відбувається напряму: `value[i]`, що дозволило C2 генерувати простіший машинний код перевірки меж масиву (Loop Bound Check Elimination).

## 4 Tricky Questions

### 1. Чому розробники OpenJDK погодилися погіршити теоретичну складність алгоритму з $O(1)$ до $O(N)$?
**Відповідь:**
Тому що в програмній інженерії теоретична асимптотика $O(1)$ не завжди означає оптимальне системне рішення.
Реальність полягає в наступному:
1. Витрати на копіювання невеликих підрядків (а переважна більшість рядків у продакшені коротша за 100 символів) вимірюються частками наносекунди завдяки векторизації та кешам CPU.
2. Ціна $O(1)$ у старій моделі була непомірно високою: приховані витоки десятків гігабайтів пам'яті в продакшені, часті OutOfMemoryError, фрагментація купи та постійний оверхед у 8 зайвих байтів на кожен рядковий об'єкт у пам'яті всієї планети. Безпека та передбачуваність споживання пам'яті виявилися важливішими за теоретичне $O(1)$.

### 2. Як зміна `substring()` в Java 7u6 вплинула на безпеку багатопотокового коду та модель пам'яті Java Memory Model (JMM)?
**Відповідь:**
Вона підвищила надійність та стійкість до помилок:
- У старій схемі масив `char[] value` міг розділятися десятками незалежних об'єктів `String`. Якби масив `value` якимось чином був модифікований (наприклад, через reflection або нативний JNI-код бібліотеки), пошкодження даних зачепило б не один рядок, а всі пов'язані підрядки в усіх потоках застосунку.
- Нова модель гарантує сувору ізоляцію: кожен об'єкт `String` володіє власним унікальним масивом байтів, що виключає ефект ненавмисного взаємного впливу (cross-talk) між об'єктами.

### 3. Чому в Java 6 існував приватний конструктор `String(int offset, int count, char[] value)` і чому його прибрали?
**Відповідь:**
Цей package-private конструктор було створено спеціально для методу `substring()`, щоб створювати підрядок без копіювання масиву. Він просто присвоював переданий масив полю `this.value` і задавав зміщення.
У Java 7u6 цей конструктор було повністю видалено через непотрібність, оскільки поля `offset` та `count` перестали існувати. Тепер усі конструктори підрядків викликають захисні методи копіювання (`Arrays.copyOfRange`), що гарантують створення нового масиву.

### 4. Якщо нашому сервісу критично необхідний $O(1)$ substring без копіювання масивів (наприклад, парсер мережевих пакетів 100 Gbps), як це правильно реалізувати в сучасній Java?
**Відповідь:**
Для цього використовуються спеціалізовані структури представлення зрізів (**String Views / Buffer Slices**):
1. **`java.nio.CharBuffer`:** Метод `CharBuffer.wrap(str).subSequence(start, end)` працює за $O(1)$ без копіювання символів, маніпулюючи індексами позиції та ліміту буфера.
2. **Власні класи `StringView`:** Клас-обгортка, що реалізує інтерфейс `CharSequence`, зберігає посилання на вихідний `String` (або `byte[]`) та два цілочисельних зміщення.
3. **Netty `ByteBuf.slice()`:** У мережевому стеку Netty всі фрагменти пакетів створюються як слайси єдиного прямого буфера (Direct Buffer) без алокацій у Java Heap.

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь
> «Реалізацію `substring()` змінили в Java 7u6 (JDK-7068364) через приховані витоки пам'яті: стара версія розділяла спільний масив символів із батьком, утримуючи гігабайтні масиви заради 5-символьного підрядка. Перехід на копіювання даних за $O(N)$ усунув витоки пам'яті та дозволив видалити поля `offset` і `count`, зменшивши розмір кожного об'єкта `String` у купі на 8 байтів. Для 95% коротких рядків копіювання займає лічені наносекунди, а пам'ять звільняється збирачем сміття передбачувано та швидко».

### Ключові тези для Senior-інтерв'ю
1. **Причина №1 (Memory Leaks):** Усунення утримання батьківських масивів `char[]` у купі (Generational Pinning).
2. **Причина №2 (Heap Footprint):** Видалення полів `offset` та `count` зменшило об'єкт `String` із 32 до 24 байтів (мінус 25% накладних витрат пам'яті на кожен рядок).
3. **Причина №3 (JIT & GC):** Спрощення C2 Escape Analysis, виключення непрямих звернень до масивів, зниження фрагментації Old Gen.
4. **Статистика:** Копіювання коротких рядків у кеші L1D займає 2–5 нс, що робить перехід з $O(1)$ на $O(N)$ абсолютно виправданим.
5. **Антипатерн:** Виклик `new String(str.substring(...))` більше не потрібен і є грубою помилкою (подвійна алокація).

### Червоні прапорці (Чого говорити категорично не можна)
- ❌ Стверджувати: «Розробники припустилися помилки, погіршивши продуктивність із $O(1)$ до $O(N)$».
- ❌ Заявляти: «`substring()` досі не копіює масив символів».
- ❌ Вважати, що витік пам'яті в `substring()` усе ще актуальний у Java 17/21.
- ❌ Радити використовувати `new String(...)` навколо `substring()` у сучасному коді.
