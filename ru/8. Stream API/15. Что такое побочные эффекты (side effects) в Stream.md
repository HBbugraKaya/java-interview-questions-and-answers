# Что такое побочные эффекты (side effects) в Stream

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**Побочный эффект (Side Effect)** — это любое действие функции внутри стрима, которое помимо вычисления возвращаемого значения изменяет внешнее состояние программы или взаимодействует с внешним окружением.

Примеры побочных эффектов:
- Запись элементов во внешнюю коллекцию (`list.add()`).
- Мутация состояния обрабатываемых объектов (`entity.setStatus(...)`).
- Вывод в консоль (`System.out.println`) или запись в лог (`log.info`).
- Сетевые вызовы (HTTP, gRPC) или запросы к базе данных.

Стримы спроектированы в парадигме функционального программирования для работы с **чистыми функциями (Pure Functions)**. Побочные эффекты нарушают детерминизм, разрушают параллелизм и могут приводить к трудноуловимым ошибкам многопоточности.

---

### Примеры: Чистый стрим против побочных эффектов на Java 21

```java
import java.util.ArrayList;
import java.util.List;

public class SideEffectsBasicsDemo {

    public static void main(String[] args) {
        List<String> names = List.of("иван", "анна", "сергей");

        // ❌ ПЛОХО: Использование стрима ради побочного эффекта (мутация внешнего списка)
        List<String> badList = new ArrayList<>();
        names.stream()
            .map(String::toUpperCase)
            .forEach(badList::add); // Побочный эффект!

        // ✅ ХОРОШО: Чистый функциональный пайплайн без побочных эффектов
        List<String> goodList = names.stream()
            .map(String::toUpperCase)
            .toList();

        System.out.println("Результат: " + goodList);
    }
}
```

## 🟡 Middle Level

### 3 столпа функциональной чистоты Stream API

Спецификация `java.util.stream` предъявляет к лямбда-выражениям три фундаментальных требования:

1. **Non-interference (Невмешательство):** функции конвейера **не должны модифицировать источник данных** стрима во время его выполнения (иначе выбрасывается `ConcurrentModificationException`).
2. **Statelessness (Отсутствие состояния):** поведение функции над элементом не должно зависеть от состояния, накопленного при обработке предыдущих элементов потока.
3. **Side-effect-freedom (Отсутствие побочных эффектов):** функции не должны мутировать разделяемые ресурсы без явной потокобезопасной синхронизации.

```
Pure Pipeline:
[ Source ] ──► filter(pure) ──► map(pure) ──► collect(accumulator) ──► [ Result ]
                                                       ▲
                                            Мутация изолирована
                                            внутри коллектора!
```

---

### Почему побочные эффекты ломают `parallelStream()`

В параллельном стриме данные разбиваются на чанки и обрабатываются несколькими ядрами CPU одновременно:
- **Гонки данных (Race Conditions):** одновременный вызов `list.add()` или `map.put()` разрушает внутренние структуры данных коллекций.
- **Недетерминированный порядок:** если побочный эффект записывает данные во внешний лог или отправляет сообщения в очередь (Kafka/RabbitMQ), последовательность сообщений будет полностью хаотичной.
- **Проблемы видимости (Visibility):** изменения переменной на одном ядре CPU могут быть не видны другому ядру без барьеров памяти (`volatile`, `synchronized`).

## 🔴 Senior Level

### Пропуск побочных эффектов при оптимизациях JVM (Stream Fusion & Pruning)

Начиная с Java 9, реализация Stream API активно применяет оптимизации на основе метаданных сплитератора (`SIZED`, `SUBSIZED`).

Если стрим знает свой точный размер, а терминальная операция не требует вычисления промежуточных значений (например, `.count()`), рантайм **выбрасывает промежуточные операции без их выполнения**:

```java
import java.util.List;

public class StreamPruningTrapDemo {

    public static void main(String[] args) {
        List<String> items = List.of("A", "B", "C");

        // ❌ ОПАСНО: Побочный эффект внутри peek()
        long count = items.stream()
            .peek(item -> System.out.println("Обработан: " + item))
            .count();

        System.out.println("Всего: " + count);
        // В Java 9+ вывод "Обработан: ..." НЕ ПОЯВИТСЯ ВОВСЕ!
        // Метод count() взял items.size() напрямую из сплитератора,
        // а промежуточный peek() был полностью выброшен рантаймом.
    }
}
```

> **Senior Insight:** Полагаться на выполнение побочных эффектов внутри промежуточных операций (`map`, `filter`, `peek`) категорически запрещено спецификацией. Рантайм не дает никаких гарантий, что они будут вызваны для каждого элемента.

---

### Bottleneck синхронизации: Логирование в Highload (`peek(log::info)`)

Распространенная ошибка при отладке — добавление логирования в стрим:

```java
items.parallelStream()
    .peek(item -> log.info("Processing: {}", item.getId()))
    .map(this::heavyCpuCalculation)
    .toList();
```

**Аппаратный коллапс:**
- Аппендеры большинства логгеров (Logback, Log4j2) используют блокировки (`synchronized` или `ReentrantLock`) для гарантии целостности строк в файле или консоли.
- 16 потоков `ForkJoinPool` выстраиваются в одну очередь за монитором аппендера.
- Вместо параллельного вычисления на 16 ядрах потоки непрерывно переключают контекст (Context Switches), и производительность сервиса падает в 20–50 раз.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> «Побочный эффект в Stream — это любое действие внутри лямбды, изменяющее состояние за пределами локального контекста функции (мутация списков, запись в базу, логирование). Стримы спроектированы для чистых функций. В параллельных стримах побочные эффекты приводят к гонкам данных и хаосу в порядке выполнения. Более того, начиная с Java 9, рантайм стрима имеет право полностью пропускать промежуточные операции с побочными эффектами (например, `peek()`) при оптимизации вызовов вроде `.count()`. Единственное легитимное место для осознанного сайд-эффекта — терминальная операция `forEach()`.»

---

### Матрица допустимости побочных эффектов

| Место в пайплайне | Допустимость побочных эффектов | Последствия |
|---|---|---|
| `filter()`, `map()`, `flatMap()` | 🔴 **Категорически запрещено** | Недетерминизм, поломка параллелизма, гонки данных |
| `peek()` | 🟡 **Только временная отладка** | В Java 9+ может быть пропущен оптимизатором (`count()`) |
| `forEach()` | 🟢 **Разрешено** | Терминальная операция; порядок в parallel не гарантирован |
| `forEachOrdered()` | 🟢 **Разрешено** | Терминальная операция; сохраняет исходный порядок элементов |
| `collect()` | 🟢 **Идеально** | Мутация изолирована внутри специализированного аккумулятора |

### Топ-4 каверзных вопроса на интервью

#### 1. Почему вызов `.peek()` с побочным эффектом (например, записью в БД) может не выполниться в Java 9+?
- Начиная с Java 9, если терминальная операция не нуждается в элементах для вычисления результата (например, `stream.count()`), а источник стрима обладает характеристикой `SIZED`, рантайм берет размер напрямую из `spliterator.getExactSizeIfKnown()`. Промежуточные stateless-операции (`map`, `filter`, `peek`) оптимизатор попросту отсекает (Stream Pruning), и код внутри `peek()` не вызывается вовсе.

#### 2. В чем разница между «Non-interference» и «Side-effect-freedom» в спецификации Stream API?
- *Non-interference* требует, чтобы стрим не модифицировал **свой собственный источник данных** (коллекцию, из которой создан стрим) во время обхода. Нарушение приводит к `ConcurrentModificationException`.
- *Side-effect-freedom* требует, чтобы операции не меняли **никакое внешнее разделяемое состояние вообще** (внешние списки, синглтоны, базы данных).

#### 3. Почему логирование через `peek(log::info)` внутри `parallelStream()` уничтожает масштабируемость?
- Библиотеки логирования синхронизируют запись в выходной поток/файл через локи. Все потоки `ForkJoinPool` блокируются на одном общем мониторе аппендера, превращая параллельную обработку в последовательную с огромными накладными расходами на переключение контекста процессора.

#### 4. В каких редких случаях сайд-эффект в Stream API считается правильным проектным решением?
- Только в качестве финального шага пайплайна в терминальной операции `forEach()` / `forEachOrdered()`, когда целью всего стрима является выполнение внешнего действия (например, отправка готовых DTO в очередь сообщений или печать отчета). При этом для сборки структур данных все равно следует предпочитать `collect()`.

---

### Типичные ошибки и Red Flags
- 🚩 Запись элементов в коллекцию через `map(x -> { list.add(x); return x; })`.
- 🚩 Надежда на то, что `peek()` обязательно выполнится для всех элементов перед `count()`.
- 🚩 Использование побочных эффектов с зависимостью от порядка выполнения в `parallelStream()`.
- 🚩 Модификация исходной коллекции во время стрима (`items.stream().forEach(items::remove)`).
