# Когда объект становится кандидатом на удаление GC

---

## 🟢 Junior Level

Объект в куче (Heap) становится **кандидатом на удаление сборщиком мусора (Eligible for Garbage Collection)** в тот самый момент, когда он становится **недостижимым (Unreachable)** ни из одного корневого источника ссылок (**GC Root**).

---

### Что такое GC Roots?
**GC Roots (Корни сборки мусора)** — это специальные внешние точки входа в граф объектов, которые априори считаются живыми:
1. **Локальные переменные и параметры** в стековых фреймах всех активных потоков (Stack Locals).
2. **Статические переменные** загруженных классов (Class Statics в Heap).
3. **Сами исполняемые объекты потоков** (`Thread`, пока поток не завершил работу).
4. **JNI-ссылки** (локальные и глобальные ссылки в нативном коде C/C++).

Если от корней GC Roots по цепочкам полей и ссылок до объекта **невозможно построить путь**, объект считается мусором, даже если он всё еще физически находится в оперативной памяти.

---

### Бытовая аналогия
- **Воздушный шар на привязи:** Земля — это GC Roots, канаты — это ссылки, а шар — объект в Heap. Пока к шару привязан хотя бы один канат, идущий к земле, шар удерживается. Как только последний канат перерезан (или отвязан от земли), шар улетает и утилизируется.

---

### 4 классических способа потери достижимости в коде:

```java
public class ReachabilityDemo {
    private static Object staticRef = new Object(); // Жив, пока загружен класс

    public void scenarios() {
        // 1. Явное зануление ссылки
        Object obj1 = new Object();
        obj1 = null; // Объект потерял единственный корень -> КАНДИДАТ НА GC

        // 2. Переприсвоение ссылки на другой объект
        Object obj2 = new Object(); // Объект А
        obj2 = new Object();        // Объект А потерян, obj2 указывает на Объект Б -> А кандидат на GC

        // 3. Выход за область видимости метода
        createTemporaryObject(); // Локальная ссылка умирает вместе со стековым фреймом

        // 4. Изолированный остров (Island of Isolation)
        Node first = new Node();
        Node second = new Node();
        first.neighbor = second;
        second.neighbor = first;

        first = null;
        second = null; // first и second ссылаются друг на друга, но недостижимы из корней -> ОБА кандидаты на GC!
    }

    private void createTemporaryObject() {
        User temp = new User("Alice");
    } // temp уничтожается в Stack -> объект new User() становится кандидатом на GC
}
```

## 🟡 Middle Level

### Трассировка графа (Reachability Analysis) vs Подсчет ссылок

В отличие от таких сред, как Python, PHP или COM, виртуальная машина Java **не использует алгоритм Reference Counting (Подсчет ссылок)**:
- **Слабость Reference Counting:** Не умеет разрешать циклические зависимости. Если объект А держит ссылку на Б, а Б держит ссылку на А, их счетчики ссылок равны 1. При обрыве внешних связей счетчик не падает в 0, порождая неустранимую утечку памяти (**Island of Isolation**).
- **Сила Reachability Analysis в Java:** Алгоритм совершает поиск в ширину/глубину (BFS/DFS), отталкиваясь строго от множества GC Roots. Поскольку до циклического острова $A \leftrightarrow B$ нельзя добраться ни от одного живого стека или статического поля, вся циклическая группа утилизируется целиком за один проход сборщика.

---

### Сила достижимости и типы ссылок (`java.lang.ref`)

Степень достижимости объекта зависит от типа ссылки, через которую к нему обращаются:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ТИПЫ ССЫЛОК В JAVA                              │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Strong Reference (Сильная ссылка)                                   │
│    - Обычный синтаксис: Object obj = new Object();                     │
│    - Объект никогда не удаляется, пока доступен по сильной ссылке.     │
├────────────────────────────────────────────────────────────────────────┤
│ 2. Soft Reference (Мягкая ссылка)                                      │
│    - SoftReference<Data> soft = new SoftReference<>(data);             │
│    - Удаляется сборщиком только перед OutOfMemoryError при дефиците.   │
├────────────────────────────────────────────────────────────────────────┤
│ 3. Weak Reference (Слабая ссылка)                                      │
│    - WeakReference<Meta> weak = new WeakReference<>(meta);             │
│    - Удаляется при первой же сборке мусора (основа WeakHashMap).       │
├────────────────────────────────────────────────────────────────────────┤
│ 4. Phantom Reference (Фантомная ссылка)                                │
│    - PhantomReference<Res> ph = new PhantomReference<>(res, queue);   │
│    - get() ВСЕГДА возвращает null; служит для пост-мортем очистки.     │
└────────────────────────────────────────────────────────────────────────┘
```

### Проблема «Воскрешения» объектов и крах `finalize()`

До Java 9 метод `protected void finalize()` позволял объекту выполнить код перед уничтожением. Это порождало критическую архитектурную уязвимость — **воскрешение объекта (Object Resurrection)**:

```java
// ❌ АНТИПАТТЕРН: Воскрешение объекта
public class Zombie {
    public static Zombie ZOMBIE_LAIR;

    @Override
    protected void finalize() {
        // Присвоение this глобальной статической ссылке возвращает объект в GC Roots!
        ZOMBIE_LAIR = this; 
    }
}
```

JVM гарантировала, что `finalize()` вызывается не более одного раза за жизнь объекта. Это приводило к зависанию очередей финализации, утечкам памяти и блокировкам.
- **Статус:** `finalize()` объявлен `@Deprecated` в Java 9 и **терминально устаревшим (Terminally Deprecated for Removal)** в Java 18 (JEP 421).
- **Современная замена:** Использование интерфейса `AutoCloseable` с `try-with-resources` и утилиты **`java.lang.ref.Cleaner`** (где очищающая лямбда строго изолирована и не захватывает ссылку `this`).

## 🔴 Senior Level

### JIT-анализ живучести и ранний сбор мусора (Early Reclamation)

Распространенное заблуждение: «Объект живет до тех пор, пока не завершится блок кода или метод, в котором он объявлен».

На практике JIT-компилятор (C2) строит граф потока данных в SSA-форме (Static Single Assignment) и выполняет **Liveness Analysis (Анализ живучести)**:
- Если ссылка на объект больше **никогда не читается** в коде метода, JIT-компилятор формирует карту объектов (**OopMap**), в которой соответствующий регистр или стековый слот помечается как «мертвый» (**Dead Slot**).
- Объект может быть признан кандидатом на сборку мусора и физически уничтожен **в середине исполнения метода**, даже если метод продолжает работать еще несколько минут!

```java
public void executeHeavyTask() {
    ExternalResource resource = new ExternalResource();
    long handle = resource.getNativeHandle();

    // ⚠️ ОПАСНОСТЬ: 'resource' больше нигде не упоминается!
    // JIT помечает ссылку как неживую. GC может собрать 'resource' прямо СЕЙЧАС,
    // закрыв нативный дескриптор, пока долгий нативный вызов еще работает в фоне!
    doLongNativeCall(handle);

    // ✅ ЗАЩИТА: Гарантирует сохранение достижимости до этой точки
    Reference.reachabilityFence(resource);
}
```

Статический метод **`Reference.reachabilityFence(Object ref)`** (доступен с Java 9) создает барьер оптимизации компилятора, запрещая объявлять ссылку мертвой до прохождения данной инструкции.

---

### Архитектура Reference Processing и Reference Handler Thread

Когда GC обнаруживает, что на объект больше нет сильных ссылок, но есть `Soft`, `Weak` или `Phantom`:
1. GC переводит объект в специальное внутреннее состояние и связывает его в список **Pending References**.
2. В JVM работает специальный поток наивысшего приоритета — **`Reference Handler`**.
3. Этот поток извлекает ссылки из очереди `Pending` и помещает их в ассоциированную пользовательскую очередь **`ReferenceQueue`**.
4. Потребитель (например, фоновый поток очистки соединений в пуле) забирает фантомную ссылку из `ReferenceQueue` и безопасно освобождает связанные нативные ресурсы (память вне кучи `DirectByteBuffer` через `Cleaner`).

---

### Ловушка `SoftReference` на больших Heap (> 32 ГБ)

Время удержания объектов по мягким ссылкам вычисляется JVM по формуле:
$$\text{Survival Time (мс)} = \text{Free Heap (МБ)} \times \text{SoftRefLRUPolicyMSPerMB}$$
По умолчанию `-XX:SoftRefLRUPolicyMSPerMB=1000` (1 секунда на каждый мегабайт свободной памяти).

> ⚠️ **Highload Trap:** Если на сервере выделено `-Xmx64g` и 40 ГБ кучи свободно, мягкая ссылка будет удерживаться в памяти:
> $$40\,000 \text{ МБ} \times 1\,000 \text{ мс} = 40\,000\,000 \text{ мс} \approx 11 \text{ часов!}$$
> Использование `SoftReference` в качестве кэша на больших серверах гарантирует деградацию производительности: кэш не сбрасывается часами, куча забивается устаревшими данными, а GC начинает испытывать колоссальное давление при сканировании огромного графа ссылок. В production для кэшей следует использовать специализированные библиотеки (Caffeine) с явными политиками вытеснения по размеру и времени (W-TinyLFU).

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «Объект становится кандидатом на сборку мусора в момент, когда он становится **недостижимым (Unreachable)** от корней **GC Roots** (активные стеки потоков, статические поля, JNI-ссылки). Java использует алгоритм **Tracing**, благодаря чему легко изолирует и вычищает перекрестные циклические ссылки (Island of Isolation). Важно понимать, что благодаря анализу живучести JIT-компилятора объект может стать кандидатом на сборку **еще до завершения метода**, если ссылка на него больше не читается (для защиты применяется `Reference.reachabilityFence`). Для управления временем жизни используются типы ссылок: `Soft` (очистка при нехватке памяти), `Weak` (очистка при первой сборке) и `Phantom` (пост-мортем очистка нативных ресурсов через `Cleaner`)».

### 3–4 каверзных вопроса с ответами

1. **Может ли объект быть собран GC, пока метод, в котором он создан, еще продолжает выполняться?**
   - *Ответ:* Да. Если JIT-компилятор в ходе анализа потока управления определяет, что ссылка на объект больше ни разу не читается до конца метода, он исключает её из карты указателей (OopMap). Если на объект нет других ссылок, GC имеет полное право собрать его прямо в процессе работы метода. Для предотвращения преждевременной сборки (например, при удержании нативных дескрипторов в JNI) в конце метода вызывают `Reference.reachabilityFence(obj)`.

2. **Что такое «Остров изоляции» (Island of Isolation) и почему он не опасен для Java?**
   - *Ответ:* Остров изоляции — это группа из нескольких объектов, которые ссылаются друг на друга (например, кольцевой двусвязный список), но ни один из них не имеет входящей ссылки от корней GC Roots. В системах с подсчетом ссылок (Reference Counting) это привело бы к утечке памяти. В Java алгоритм трассировки начинает обход строго от GC Roots: так как в изолированную группу нельзя зайти из корня, сборщик мусора помечает всю группу как недостижимую и уничтожает все объекты за один цикл.

3. **Почему `PhantomReference.get()` всегда возвращает `null`?**
   - *Ответ:* Метод `get()` у `PhantomReference` намеренно всегда возвращает `null`, чтобы разработчик не мог получить сильную ссылку на объект, который уже признан финализированным и фактически мертв. Это исключает возможность «воскрешения» объекта, защищая инварианты памяти JVM.

4. **Почему `SoftReference` опасны для реализации кэшей на серверах с большой оперативной памятью?**
   - *Ответ:* По умолчанию JVM очищает `SoftReference` по формуле «1 секунда жизни на каждый мегабайт свободной кучи» (`SoftRefLRUPolicyMSPerMB=1000`). Если на сервере свободно 30 ГБ памяти, мягкие ссылки будут удерживать объекты более 8 часов, даже если они давно потеряли актуальность. Это препятствует освобождению памяти, раздувает граф объектов и увеличивает время пауз на фазе разметки GC.

---

### Типичные ошибки и Red Flags

- 🚩 **Утверждение: «Объект удаляется сразу, как только мы написали `obj = null`»** (зануление лишь делает объект кандидатом; фактическое удаление произойдет не детерминированно при очередном цикле GC).
- 🚩 **Использование `finalize()` в новом коде** (метод устарел, не дает гарантий времени исполнения и ломает throughput сборщика мусора).
- 🚩 **Заблуждение: «Объект гарантированно живет до закрывающей фигурной скобки метода `}`»** (JIT-оптимизация может сделать объект кандидатом на удаление значительно раньше).
- 🚩 **Использование `SoftReference` как единственной стратегии ограничения кэша в highload-сервисах.**
