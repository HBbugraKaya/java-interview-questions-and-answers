# Можно ли повторно использовать Stream

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**Нет, повторно использовать Stream категорически нельзя.** В Java объект `Stream` представляет собой **одноразовый вычислительный конвейер**.

Как только на стриме вызвана любая **терминальная операция** (например, `collect()`, `forEach()`, `count()`, `reduce()`), стрим считается полностью исчерпанным (consumed) и закрывается. Любая попытка вызвать терминальную операцию повторно на том же объекте стрима немедленно выбросит исключение:
`IllegalStateException: stream has already been operated upon or closed`.

Чтобы обработать те же данные заново, необходимо создать **новый экземпляр стрима** из исходной коллекции или источника.

---

### Пример поведения на Java 21

```java
import java.util.List;
import java.util.stream.Stream;

public class ReusingStreamDemo {

    public static void main(String[] args) {
        List<String> cities = List.of("Москва", "Казань", "Новосибирск");

        Stream<String> cityStream = cities.stream();

        // 1-й запуск терминальной операции — выполнится штатно
        cityStream.forEach(System.out::println);

        // 2-й запуск терминальной операции на ТОМ ЖЕ объекте:
        try {
            long count = cityStream.count(); // ❌ Бросит IllegalStateException
        } catch (IllegalStateException e) {
            System.err.println("Ошибка: " + e.getMessage());
            // stream has already been operated upon or closed
        }

        // ✅ ПРАВИЛЬНО: создавать новый стрим для каждого прохода
        long validCount = cities.stream().count();
        System.out.println("Количество городов: " + validCount);
    }
}
```

## 🟡 Middle Level

### Внутреннее устройство: флаг `linkedOrConsumed` в `AbstractPipeline`

В исходном коде OpenJDK (`java.util.stream.AbstractPipeline`) каждый узел конвейера стрима хранит внутреннее состояние готовности:

```java
// Упрощенный фрагмент реализации в AbstractPipeline.java:
private boolean linkedOrConsumed;

final <R> R evaluate(TerminalOp<E_OUT, R> terminalOp) {
    if (linkedOrConsumed) {
        throw new IllegalStateException("stream has already been operated upon or closed");
    }
    linkedOrConsumed = true; // Стрим необратимо помечается как сожженный

    return isParallel()
           ? terminalOp.evaluateParallel(this, sourceSpliterator(terminalOp.getOpFlags()))
           : terminalOp.evaluateSequential(this, sourceSpliterator(terminalOp.getOpFlags()));
}
```

---

### Почему архитектор Java (Brian Goetz) сделал стримы одноразовыми

1. **Потоки из небуферизуемых внешних источников:** Источником стрима может быть сокет (`SocketChannel`), генератор случайных чисел или бесконечный лог, которые физически невозможно «перемотать назад» без копирования.
2. **Нулевой расход памяти (Low Memory Footprint):** Если бы стрим позволял повторные проходы, рантайм был бы обязан кэшировать в оперативной памяти (heap) все когда-либо сгенерированные и трансформированные элементы. Это превратило бы легкий конвейер в тяжелую коллекцию и привело бы к `OutOfMemoryError` на больших объемах.
3. **Безопасность параллелизма (`parallelStream`):** Одноразовость защищает от состояния гонки и повторного входа рабочих потоков `ForkJoinPool` в уже завершившийся конвейер.

### Паттерн `Supplier<Stream<T>>` для повторного создания

Если алгоритм требует многократной генерации стрима с одинаковыми фильтрами и преобразованиями, используется функциональный интерфейс `Supplier`:

```java
import java.util.List;
import java.util.function.Supplier;
import java.util.stream.Stream;

public class StreamSupplierPatternDemo {

    public static void main(String[] args) {
        List<String> data = List.of("apple", "banana", "avocado", "apricot");

        // Фабрика стримов: вычисляет конвейер каждый раз заново
        Supplier<Stream<String>> streamSupplier = () -> data.stream()
            .filter(s -> s.startsWith("a"));

        // Первый проход
        streamSupplier.get().forEach(System.out::println);

        // Второй проход — новый объект Stream, ошибки нет!
        long count = streamSupplier.get().count();
        System.out.println("Начинаются на 'a': " + count);
    }
}
```

## 🔴 Senior Level

### Архитектурный антипаттерн: `Stream<T>` в аргументах публичного метода

В дизайне библиотек и интерфейсов прием `Stream<T>` в качестве входного параметра публичного метода считается грубой проектной ошибкой:

```java
// ❌ АНТИПАТТЕРН: Прием Stream в публичном API
public void processOrders(Stream<Order> orderStream) {
    long total = orderStream.count(); // Стрим исчерпан!
    // orderStream.forEach(this::save); // УПАДЕТ В РАНТАЙМЕ!
}

// ✅ ПРАВИЛЬНЫЙ ДИЗАЙН:
// 1. Для коллекций в памяти:
public void processOrders(Collection<Order> orders) { /* ... */ }

// 2. Для ленивых/тяжелых генераций:
public void processOrders(Supplier<Stream<Order>> orderStreamSupplier) { /* ... */ }
```

### Утечки ресурсов (Resource Leaks) в стримах с `AutoCloseable`

Стримы, работающие с дескрипторами ввода-вывода операционной системы (`Files.lines()`, `Files.list()`, `Files.walk()`), открывают реальные файловые дескрипторы ОС и реализуют интерфейс `AutoCloseable`.

При работе с ними обязательна конструкция **`try-with-resources`**:

```java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.stream.Stream;

public class StreamResourceLeakDemo {

    public static void readSafely(Path path) throws IOException {
        // Обязательное закрытие дескриптора ОС через try-with-resources:
        try (Stream<String> lines = Files.lines(path)) {
            lines.filter(line -> line.contains("ERROR"))
                 .forEach(System.out::println);
        } // lines.close() гарантированно вызывается при выходе
    }
}
```
Если такой стрим не закрыть, файловый дескриптор в ОС останется заблокированным вплоть до срабатывания финалайзера/клинера GC, что в высоконагруженных системах приводит к `IOException: Too many open files`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> «Стримы в Java строго одноразовые. При вызове терминальной операции внутренний флаг `linkedOrConsumed` в `AbstractPipeline` переключается в `true`, и любая повторная попытка запуска бросает `IllegalStateException`. Стрим — это не хранилище данных, а процесс их обработки; повторное использование потребовало бы кэширования всех элементов в куче, что убило бы главное преимущество Stream API — минимальный расход памяти. Для повторного обхода нужно создавать новый стрим или использовать паттерн `Supplier<Stream<T>>`. Стримы, читающие файлы (`Files.lines()`), требуют закрытия через `try-with-resources`.»

---

### Сравнение `Stream<T>` и `Iterable<T>`

| Характеристика | `Iterable<T>` (Коллекции) | `Stream<T>` (Конвейер) |
|---|---|---|
| **Количество проходов** | **Неограниченно** (каждый `.iterator()` новый) | **Строго один раз** |
| **Хранение данных** | Хранит элементы в памяти структуры | Не хранит данные (только вычисления) |
| **Вычисления** | Немедленные (Eager) | Ленивые (Lazy) |
| **Поддержка параллелизма** | Вручную через потоки | Встроена через `parallel()` |
| **Управление ресурсами** | Память в куче | Может держать дескрипторы ОС (`AutoCloseable`) |

### Топ-4 каверзных вопроса на интервью

#### 1. Что происходит под капотом при повторной попытке вызвать терминальную операцию на объекте Stream?
- Метод `evaluate()` в `AbstractPipeline` проверяет логическое поле `linkedOrConsumed`. Если оно уже равно `true`, выбрасывается `IllegalStateException("stream has already been operated upon or closed")`. Повторное выполнение конвейера физически блокируется рантаймом.

#### 2. Почему в Java Stream API принципиально не предусмотрели метод `reset()` для сброса стрима в начало?
- Потому что источником стрима может быть не только массив или список в памяти, но и однонаправленный сетевой сокет, генератор случайных чисел или поток ввода (`InputStream`), который невозможно перемотать назад. Кроме того, поддержка перемотки потребовала бы полного буферизирования всего потока в памяти, что сломало бы потоковую модель вычислений.

#### 3. В чем опасность использования паттерна `Supplier<Stream<T>>` при работе с внешними ресурсами?
- Если лямбда `Supplier` вызывает `Files.lines(path)` или запрос к БД через Hibernate Stream, каждый вызов `supplier.get()` будет открывать **новый файловый дескриптор или соединение с БД**. Если эти стримы не закрывать явно через `try-with-resources`, возникнет утечка ресурсов (Connection Leak / File Descriptor Leak).

#### 4. Почему `Stream` не наследует интерфейс `Iterable`, хотя имеет метод `iterator()`?
- `Iterable` подразумевает возможность многократного создания итераторов (`new iterator()`) для многократного прохода по данным (например, в цикле `for-each`). `Stream` одноразовый: его метод `stream.iterator()` можно вызвать только один раз, после чего стрим помечается как исчерпанный. Наследование `Iterable` нарушило бы принцип подстановки Барбары Лисков (LSP).

### Типичные ошибки и Red Flags
- 🚩 Попытка сохранить стрим в поле класса для повторного использования в разных методах.
- 🚩 Прием `Stream<T>` в аргументах публичных сервисных методов.
- 🚩 Незакрытие стримов ввода-вывода (`Files.lines()`, `Files.walk()`) через `try-with-resources`.
- 🚩 Попытка клонирования стрима или поиск несуществующего метода `reset()`.
