# В чём особенности bidirectional relationships

Двунаправленная связь (Bidirectional Relationship) в JPA и Hibernate — это отношение между двумя сущностями, при котором навигация по объектному графу возможна в обоих направлениях: от родителя к детям (`user.getOrders()`) и от ребенка к родителю (`order.getUser()`). Несмотря на кажущееся удобство, двунаправленные связи содержат скрытые ловушки: рассинхронизацию памяти JVM и базы данных, поломку контрактов `equals()` / `hashCode()` в коллекциях `Set` и фатальные `StackOverflowError` при сериализации и логировании.

---

## 🟢 Junior Level

### Как устроена двунаправленная связь

В реляционной базе данных связи всегда однонаправлены: внешний ключ физически хранится **только в одной таблице** (на стороне «многие»).

В Java-коде сущности двунаправленной связи делятся на две роли:
1. **Владелец связи (Owning Side):** Содержит аннотацию `@ManyToOne` и `@JoinColumn`. Только эта сторона определяет, какое значение будет физически записано в колонку внешнего ключа в БД.
2. **Обратная сторона (Inverse Side):** Содержит аннотацию `@OneToMany(mappedBy = "...")`. Она лишь указывает имя поля владельца связи и **полностью игнорируется Hibernate при вычислении изменений внешнего ключа**.

```java
// 1. Owning Side (Владелец FK):
@Entity
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")
    private User user; // Изменение этого поля меняет FK в базе!
}

// 2. Inverse Side (Обратная сторона):
@Entity
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // mappedBy = "user" указывает на поле 'user' в классе Order
    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();
}
```

```
       БАЗА ДАННЫХ (1 колонка FK)           ПАМЯТЬ JVM (2 независимые ссылки)
       
       таблица orders                        User@0x1
       ┌────┬─────────┬─────────┐            ├── orders: [ Order@0x2 ] ──┐
       │ id │ details │ user_id │                                        │
       ├────┼─────────┼─────────┤                                        ▼
       │ 10 │ "Item"  │    1    │            Order@0x2                   │
       └────┴─────────┴─────────┘            └── user: User@0x1 <────────┘
       (FK только в таблице orders!)         (Две независимые ссылки в Heap!)
```

## 🟡 Middle Level

### Обязанность синхронизации ссылок в оперативной памяти

JPA и Hibernate **не занимаются синхронизацией ссылок в памяти Java автоматически**. Если изменить одну сторону, вторая останется нетронутой:

```java
// ❌ СИТУАЦИЯ РАССИНХРОНИЗАЦИИ:
User user = new User();
Order order = new Order();

// Вариант 1: изменили только Inverse сторону
user.getOrders().add(order);
// order.getUser() == null! В базу запишется NULL!

// Вариант 2: изменили только Owner сторону
order.setUser(user);
// user.getOrders() по-прежнему ПУСТ! 
// До закрытия сессии коллекция в памяти не увидит новый заказ!
```

#### Решение: Защитные вспомогательные методы (Defensive Helper Methods)
Обе стороны связи должны синхронизироваться атомарно внутри сущности:

```java
@Entity
public class User {
    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();

    public void addOrder(Order order) {
        this.orders.add(order);
        order.setUser(this); // Синхронизируем владельца FK!
    }

    public void removeOrder(Order order) {
        this.orders.remove(order);
        order.setUser(null); // Разрываем связь владельца!
    }
}
```

### Ловушка `toString()` и Lombok: бесконечная рекурсия

Использование аннотации `@Data` или `@ToString` от Lombok на обеих сторонах двунаправленной связи приводит к аварийной остановке JVM:
- `user.toString()` вызывает `orders.toString()`.
- Каждый `order.toString()` вызывает `user.toString()`.
- Стек вызовов переполняется: **`java.lang.StackOverflowError`**.

**Решение:** Всегда исключать обратную сторону связи из генерации строкового представления:
```java
@Entity
@ToString(exclude = "orders") // Исключаем коллекцию из toString!
public class User { ... }

@Entity
@ToString(exclude = "user")   // Или исключаем родителя на стороне ребенка
public class Order { ... }
```

## 🔴 Senior Level

### Проблема `equals()` и `hashCode()` в коллекциях `Set`

Если для хранения связей используется `Set<Order>` вместо `List<Order>`, разработчик обязан переопределить `equals` и `hashCode`. Но использование генерируемого первичного ключа (`@Id`) приводит к поломке структуры хэш-таблицы:

```java
// ❌ ГРУБЕЙШАЯ ОШИБКА: equals/hashCode по генерируемому ID
@Entity
public class Order {
    @Id
    @GeneratedValue
    private Long id;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Order)) return false;
        return id != null && id.equals(((Order) o).id);
    }

    @Override
    public int hashCode() {
        return getClass().hashCode(); // или id != null ? id.hashCode() : 0;
    }
}
```

#### Анатомия катастрофы в `HashSet`:
1. Создаем новый объект `Order` в состоянии `Transient` (`order.getId() == null`).
2. Добавляем его в коллекцию `user.getOrders().add(order)`:
   - `order.hashCode()` вычисляется для `id == null` (например, возвращает `0`).
   - Объект помещается в корзину `bucket[0]` структуры `HashSet`.
3. Сохраняем пользователя: `entityManager.persist(user)`.
4. СУБД генерирует первичный ключ: поле `id` меняется с `null` на `42`.
5. Теперь вызываем `user.getOrders().contains(order)`:
   - `HashSet` вычисляет новый хэш-код для `id == 42` и ищет в корзине `bucket[42]`.
   - Корзина `bucket[42]` пуста! Метод `contains()` возвращает **`false`**!
   - Объект «потерялся» внутри `HashSet`, его невозможно удалить или найти.

#### Канонические решения проблемы `equals`/`hashCode`:
- **Вариант 1 (Идеальный):** Использовать естественный бизнес-ключ (**Natural ID** / Business Key), неизменяемый на протяжении всей жизни объекта (например, `UUID`, номер паспорта, артикул `SKU`, `email`).
- **Вариант 2 (Рекомендация Влада Михалчи):** Фиксированный хэш-код класса в сочетании с проверкой ID:
  ```java
  @Override
  public boolean equals(Object o) {
      if (this == o) return true;
      if (!(o instanceof Order)) return false;
      Order other = (Order) o;
      return id != null && id.equals(other.getId());
  }

  @Override
  public int hashCode() {
      // Константный hashCode гарантирует, что объект никогда не сменит корзину в HashSet!
      return getClass().hashCode(); 
  }
  ```

## 4 Tricky Questions

### 1. Если в транзакции изменить ТОЛЬКО inverse-сторону: `user.getOrders().add(order)`, а поле `order.setUser(user)` оставить `null`, отправит ли Hibernate SQL UPDATE при коммите?

**Ответ:**
1. **Нет, SQL UPDATE сгенерирован не будет!**
2. Механизм Dirty Checking в Hibernate отслеживает изменения исключительно на стороне **владельца связи (Owning Side)** — то есть в объекте с `@ManyToOne`.
3. Поле `mappedBy` на стороне `@OneToMany` сообщает движку: *«Эта коллекция чисто зеркальная, не проверяй ее для построения SQL»*.
4. В базе данных колонка `user_id` останется равной `NULL` (или старым значением), несмотря на то, что в памяти список `user.getOrders()` содержит заказ.

### 2. Что произойдет, если в двунаправленной связи сущности `Order` и `Item` обе используют каскад `CascadeType.ALL` друг на друга?

**Ответ:**
1. Возникает взаимный циклический каскад.
2. При вызове `entityManager.persist(order)` Hibernate обходит дерево: `order` -> `item` -> `order` -> `item`.
3. Благодаря внутренней карте `StatefulPersistenceContext.entitiesByKey` Hibernate распознает уже посещенные объекты и не уходит в бесконечную рекурсию JVM.
4. Однако на фазе сброса (`flush`) возникает конфликт порядка вставки в `ActionQueue`: чтобы вставить заказ, нужен ID позиции, а чтобы вставить позицию, нужен ID заказа. Это приведет либо к лишним штрафным `UPDATE`, либо к исключению `TransientPropertyValueException`.

### 3. Если мы загрузили `Order` через `find()`, и обратились к `order.getUser()`, создастся ли новый Java-экземпляр `User`?

**Ответ:**
1. Если сущность `User` с этим первичным ключом уже была загружена в текущую сессию (`PersistenceContext`), Hibernate вернет **ровно тот же самый экземпляр из кэша первого уровня L1** (`assert order.getUser() == existingUser;`).
2. Если `User` еще не был загружен, а связь настроена как `FetchType.LAZY`, Hibernate создаст динамический **ByteBuddy-прокси** целевого класса.
3. В обоих случаях дублирования реальных управляемых объектов в рамках одной сессии не происходит благодаря гарантии идентичности (Identity Guarantee).

### 4. Почему при двунаправленной связи `@OneToOne` ленивая загрузка (`FetchType.LAZY`) не работает на стороне `mappedBy` без байт-код инструментирования?

**Ответ:**
1. На стороне владельца (`@OneToOne @JoinColumn`) колонка `fk_id` находится прямо в таблице. Если значение в колонке `NULL`, Hibernate записывает `null`, если значение есть — создает ленивый прокси.
2. На обратной стороне (`@OneToOne(mappedBy = "...")`) колонка внешнего ключа отсутствует. Чтобы узнать, существует ли вообще связанная строка в зависимой таблице (должно ли поле быть `null` или ссылкой на прокси), Hibernate **вынужден выполнить немедленный SQL `SELECT`** в связанную таблицу!
3. В итоге `FetchType.LAZY` на обратной стороне `@OneToOne` молча вырождается в `FetchType.EAGER`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «Двунаправленная связь в JPA объединяет сторону владельца внешнего ключа (`@ManyToOne`) и обратную сторону (`@OneToMany(mappedBy = "...")`). База данных хранит только один FK, но в оперативной памяти ссылки независимы. Главная обязанность разработчика — поддерживать консистентность ссылок в памяти через хелпер-методы (`addOrder`/`removeOrder`), так как Hibernate отслеживает изменения только со стороны `@ManyToOne`. Главные риски двунаправленных связей: переполнение стека (`StackOverflowError`) в `toString()`/сериализации (лечится через `@ToString.Exclude` и DTO) и поломка контракта `HashSet` при генерации `equals()`/`hashCode()` по временным первичным ключам».

### Ключевые метрики для Production-мониторинга
- **Null Foreign Key Inserts Rate**: ошибки вставки строк с `null` внешним ключом из-за отсутствия синхронизации обратной стороны.
- **StackOverflowError Count**: критический индикатор забытого рекурсивного маппинга в логировании или JSON-сериализаторах.

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«Hibernate сам синхронизирует ссылки в памяти: если я вызвал order.setUser(u), он добавит заказ в u.getOrders()»* — Ложь. Hibernate не мутирует Java-коллекции в памяти.
- ❌ *«mappedBy можно указывать на стороне @ManyToOne»* — mappedBy бывает только на обратной стороне (Inverse Side).
- ❌ *«Я реализую equals() и hashCode() просто по полю id сущности»* — Это сломает `HashSet` при переходе из Transient в Managed.
- ❌ *«Использую аннотацию @Data от Lombok на обеих сторонах связи»* — Приведет к гарантированному `StackOverflowError` в `toString()` и `hashCode()`.
