# В чём разница между map() и flatMap()

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
Ключевое отличие заключается в **структуре возвращаемого значения функции-маппера** и результирующей размерности потока:

- **`map(Function<T, R>)`** — реализует преобразование **«один к одному»** ($1 \to 1$). Функция принимает элемент типа `T` и возвращает один объект типа `R`. Если функция возвращает коллекцию или список, результирующий поток будет вложенным (`Stream<List<R>>`).
- **`flatMap(Function<T, Stream<R>>)`** — реализует преобразование **«один ко многим»** (или «один к нулю») ($1 \to N$). Функция принимает элемент типа `T` и возвращает целый подпоток `Stream<R>`, после чего `flatMap` объединяет («сплющивает») все вложенные элементы подпотоков в один плоский `Stream<R>`.

---

### Сравнительный пример на Java 21

```java
import java.util.List;

public class MapVsFlatMapDemo {

    public record Developer(String name, List<String> languages) {}

    public static void main(String[] args) {
        List<Developer> team = List.of(
            new Developer("Алексей", List.of("Java", "Kotlin")),
            new Developer("Мария", List.of("Go", "Python", "Java"))
        );

        // 1. Использование map(): получаем стрим списков Stream<List<String>>
        List<List<String>> listOfLists = team.stream()
            .map(Developer::languages)
            .toList();
        System.out.println("map(): " + listOfLists);
        // [[Java, Kotlin], [Go, Python, Java]]

        // 2. Использование flatMap(): получаем плоский стрим строк Stream<String>
        List<String> flatLanguages = team.stream()
            .flatMap(dev -> dev.languages().stream())
            .distinct()
            .toList();
        System.out.println("flatMap(): " + flatLanguages);
        // [Java, Kotlin, Go, Python]
    }
}
```

## 🟡 Middle Level

### Сравнительный анализ характеристик

| Критерий | `map()` | `flatMap()` |
|---|---|---|
| **Сигнатура аргумента** | `Function<? super T, ? extends R>` | `Function<? super T, ? extends Stream<? extends R>>` |
| **Результирующий тип** | `Stream<R>` | `Stream<R>` |
| **Кардинальность элементов** | Всегда строго сохраняется ($N_{out} = N_{in}$) | Может меняться ($N_{out} \ge 0$, зависит от подпотоков) |
| **Возврат `null` из лямбды** | Допустим: значение `null` передается дальше по конвейеру | **Недопустим:** немедленно бросает `NullPointerException` |
| **Схлопывание вложенности** | Нет (сохраняет вложенные коллекции) | Да (разворачивает вложенные стримы в один уровень) |
| **Флаг `SIZED` потока** | **Сохраняется** (размер стрима известен заранее) | **Теряется** (размер сбрасывается в неизвестный) |

### Разница в поведении с `Optional`

Оба метода есть и в классе `java.util.Optional`:

```java
import java.util.Optional;

public class OptionalMapVsFlatMapDemo {

    public record Address(String city) {}
    public record User(String name, Optional<Address> address) {}

    public static void main(String[] args) {
        Optional<User> user = Optional.of(new User("Иван", Optional.of(new Address("Москва"))));

        // 1. Использование map(): приводит к вложенности Optional<Optional<Address>>
        Optional<Optional<Address>> nested = user.map(User::address);

        // 2. Использование flatMap(): "разворачивает" вложенный контейнер до Optional<Address>
        Optional<Address> flat = user.flatMap(User::address);

        // Извлечение города цепочкой безопасных вызовов
        String city = user
            .flatMap(User::address)
            .map(Address::city)
            .orElse("Не указан");

        System.out.println("Город: " + city); // Москва
    }
}
```

## 🔴 Senior Level

### Архитектурные различия: Функтор против Монады

В концепциях функционального программирования и теории категорий:
- **`map`** представляет операцию функтора (`fmap`): применяет чистую функцию $A \to B$ над значением внутри контекста $F[A]$, сохраняя сам контекст $F[B]$.
- **`flatMap`** представляет операцию монадического связывания (`bind` или оператор `>>=` в Haskell): берет значение из монадического контекста $M[A]$ и применяет функцию $A \to M[B]$. Затем происходит уплощение монады (операция `join`: $M[M[B]] \to M[B]$).

```
Functor (map):
[ T ] ───────── map(T -> R) ─────────> [ R ]

Monad (flatMap):
[ T ] ─ flatMap(T -> Stream<R>) ─> [[ R1, R2 ], [ R3 ]] ─ join ─> [ R1, R2, R3 ]
```

---

### Внутреннее устройство и влияние на флаги оптимизации (Stream Flags)

Каждая промежуточная операция в `AbstractPipeline` либо сохраняет, либо модифицирует битовую маску характеристик стрима:

1. **Поведение `map()`:**
   - Сохраняет флаг `StreamOpFlag.IS_SIZED` (если исходный источник знал свой точный размер, downstream-операции, такие как `toArray()` или `toList()`, могут сразу аллоцировать массив точного размера без динамического расширения).
   - Сбрасывает флаги `SORTED` и `DISTINCT`, так как трансформация значений может нарушить порядок сортировки и породить одинаковые элементы.

2. **Поведение `flatMap()`:**
   - **Всегда сбрасывает флаги `SIZED` и `SUBSIZED`**. Стрим больше не знает, сколько элементов в нем содержится.
   - Терминальные операции вынуждены использовать динамические расширяемые буферы (`SpinedBuffer`), выделяющие чанки памяти в куче ($2^k$).

---

### Производительность, GC Overhead и сравнение с `mapMulti`

Создание временных объектов в `flatMap`:
- На каждый входной элемент создается экземпляр `Stream`, узел конвейера и внутренний итератор/сплитератор.
- Хотя современные JIT-компиляторы (C2 / Graal) активно применяют Escape Analysis и скалярное замещение (Scalar Replacement), объекты `Stream` содержат виртуальные вызовы и замыкания, из-за чего часто «убегают» (escape) в Young Generation.
- В критически нагруженных путях исполнения (десятки миллионов элементов в секунду) `flatMap` приводит к заметным паузам GC.

В Java 16 добавлен метод `Stream.mapMulti()`, который решает данную проблему за счет прямого императивного проталкивания значений в downstream-потребитель:

```java
// flatMap: аллоцирует тысячи Stream-объектов
stream.flatMap(e -> e.getItems().stream()).toList();

// mapMulti (Java 16+): нулевые аллокации промежуточных стримов
stream.<Item>mapMulti((e, consumer) -> {
    for (Item item : e.getItems()) {
        consumer.accept(item);
    }
}).toList();
```

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> «`map` выполняет преобразование элементов «один к одному», сохраняя исходное количество элементов и флаг `SIZED`. `flatMap` выполняет преобразование «один ко многим», принимая функцию, возвращающую стрим, и схлопывая подпотоки в единый плоский поток. В `Optional` метод `flatMap` устраняет вложенность `Optional<Optional<T>>`. В критичных по аллокациям сценариях Java 16+ рекомендуется заменять `flatMap` на `mapMulti`, так как `flatMap` аллоцирует отдельный объект `Stream` на каждый элемент и сбрасывает оптимизационные флаги размера.»

---

### Сводная матрица различий

| Параметр | `map()` | `flatMap()` |
|---|---|---|
| **Семантика** | Трансформация значения ($1 \to 1$) | Трансформация с уплощением ($1 \to N$) |
| **Применение** | Геттеры, конвертация в DTO, расчет формул | Распаковка списков, графов, разбор токенов строк |
| **Optional поведение** | Оставляет вложенность `Optional<T>` | Схлопывает до одного `Optional<T>` |
| **Реакция на `null`** | Передает `null` вниз по конвейеру | Выбрасывает `NullPointerException` |
| **Флаг `SIZED`** | Сохраняется | Теряется (размер неизвестен) |
| **Альтернатива (Java 16+)** | — | `Stream.mapMulti()` |

### Топ-4 каверзных вопроса на интервью

#### 1. В каких ситуациях `map()` сохраняет оптимизационные характеристики потока, а `flatMap()` всегда их сбрасывает?
- `map()` сохраняет флаг `SIZED` (размер потока не меняется), что позволяет терминальным операциям (`toArray`, `toList`) выделить массив точного размера без реаллокаций.
- `flatMap()` всегда сбрасывает флаг `SIZED` в `0`, так как функция может вернуть поток любого размера. Это переключает рантайм на буферы переменного размера (`SpinedBuffer`) и ухудшает балансировку задач в параллельных потоках `ForkJoinPool`.

#### 2. Что произойдёт, если функция внутри `map()` вернет `null`, и что — если внутри `flatMap()`?
- В `map()`: значение `null` станет обычным элементом стрима и пойдет дальше по конвейеру. Если следующая операция не ожидает `null` (например, вызов метода), упадет она, но сам `map()` отработает штатно.
- В `flatMap()`: возврат `null` вместо объекта `Stream` приведет к немедленному выбрасыванию `NullPointerException` прямо в рантайме метода `flatMap`. Для пропуска элемента нужно возвращать `Stream.empty()`.

#### 3. Как концепция монады соотносится с `Optional.map()` и `Optional.flatMap()`?
- `Optional` является монадой. Метод `map()` применяет обычную функцию к упакованному значению и заново упаковывает результат в `Optional` (поведение функтора). Если функция сама возвращает `Optional`, получаем `Optional<Optional<T>>`.
- Метод `flatMap()` принимает функцию, возвращающую монаду (`T -> Optional<R>`), и применяет монадическое связывание (`bind`), не создавая двойной контейнер.

#### 4. Почему `flatMap` в parallelStream может работать медленнее, чем обычный последовательный цикл `for`?
- Во-первых, сброс флага `SIZED` ломает эффективное деление `Spliterator.trySplit()` на равные части.
- Во-вторых, аллокация промежуточных стримов для каждого элемента перегружает сборщик мусора.
- В-третьих, объединение разрозненных результирующих структур из параллельных веток требует создания промежуточных узлов дерева и блокировок/слияний, сводя на нет выигрыш от многопоточности при мелких задачах.

### Типичные ошибки и Red Flags
- 🚩 Использование `flatMap`, когда маппер возвращает единичное значение: `stream.flatMap(x -> Stream.of(x.getName()))` вместо `stream.map(User::getName)`. Это создает бессмысленную нагрузку на память.
- 🚩 Возврат `null` из лямбды `flatMap` вместо `Stream.empty()`, вызывающий внезапный NPE в продакшене.
- 🚩 Получение `Stream<List<T>>` и попытка запустить на нем терминальную операцию вместо уплощения структуры через `flatMap`.
- 🚩 Использование вложенных `Optional<Optional<T>>` в API из-за ошибочного вызова `map` вместо `flatMap`.
