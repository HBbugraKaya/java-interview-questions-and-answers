# What Fetch Strategies Exist in Hibernate

---

## 🟢 Junior Level

### The Fundamental Distinction: "When" vs. "How"

In the JPA and Hibernate ecosystem, data fetching strategies operate across two distinct architectural dimensions:

1. **JPA `FetchType` (Answers "WHEN to load?"):**
   - Standard JPA annotation parameter (`@OneToMany`, `@ManyToOne`, etc.).
   - `LAZY`: Deferred loading; data is retrieved upon the first explicit method access.
   - `EAGER`: Immediate loading; data is retrieved upfront alongside the parent entity.
2. **Hibernate `FetchMode` (Answers "HOW to load via SQL?"):**
   - Hibernate-specific annotation `@Fetch(FetchMode.xxx)`.
   - Defines the exact physical SQL structure used to query the database: via secondary `SELECT` statements, SQL table joins (`JOIN`), or nested subqueries (`SUBSELECT`).

```
JPA FetchType (WHEN):
LAZY  ──> Deferred loading upon field or getter access.
EAGER ──> Immediate loading at parent query time.

Hibernate FetchMode (HOW):
SELECT    ──> Secondary parameterized query: WHERE parent_id = ?
JOIN      ──> Single query using SQL: LEFT OUTER JOIN
SUBSELECT ──> Single batched subquery: WHERE parent_id IN (SELECT id FROM ...)
```

### Basic Hibernate Mapping Example

```java
@Entity
public class Order {
    @Id
    private Long id;

    // 1. SELECT (Default behavior for LAZY):
    // Fires an individual SQL SELECT for each order when itemsSelect is accessed
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    @Fetch(FetchMode.SELECT)
    private List<OrderItem> itemsSelect;

    // 2. JOIN:
    // Employs a SQL LEFT OUTER JOIN when loaded via entityManager.find()
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    @Fetch(FetchMode.JOIN)
    private List<OrderItem> itemsJoin;

    // 3. SUBSELECT:
    // Loads collections for all queried orders using a single subquery
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    @Fetch(FetchMode.SUBSELECT)
    private List<OrderItem> itemsSubselect;
}
```

## 🟡 Middle Level

### Detailed Analysis of `FetchMode` Strategies

#### 1. `FetchMode.SELECT`
- **Mechanism:** When accessing an uninitialized proxy or collection, Hibernate executes a separate parameterized query:
  ```sql
  SELECT * FROM order_items WHERE order_id = ?;
  ```
- **Advantages:** Minimal upfront query complexity; straightforward caching in L1 and L2 caches.
- **Disadvantages:** The primary driver of the N+1 query problem when parents are queried as a collection.

#### 2. `FetchMode.JOIN`
- **Mechanism:** Hibernate joins the parent and child tables in a single query using `LEFT OUTER JOIN` during entity lookups:
  ```sql
  SELECT o.*, i.* FROM orders o 
  LEFT OUTER JOIN order_items i ON o.id = i.order_id 
  WHERE o.id = ?;
  ```
- **The Critical Trap:** Specifying `@Fetch(FetchMode.JOIN)` **completely overrides and suppresses `FetchType.LAZY`**! Even if you explicitly declare `fetch = FetchType.LAZY`, Hibernate immediately fetches the association eagerly.
- **Limitation:** Only applies to direct primary key lookups via `entityManager.find()`. It is **completely ignored by JPQL queries**!

#### 3. `FetchMode.SUBSELECT`
- **Mechanism:** Exclusively applicable to collection mappings (`*ToMany`). Hibernate remembers the original query used to load the parent list and executes **exactly one additional subquery** for all child collections:
  ```sql
  -- Initial parent query:
  SELECT * FROM orders WHERE status = 'COMPLETED';
  
  -- Secondary subquery fetching all items across all completed orders:
  SELECT * FROM order_items 
  WHERE order_id IN (SELECT id FROM orders WHERE status = 'COMPLETED');
  ```
- **Advantages:** Eliminates N+1 queries in 2 round-trips without generating a Cartesian product.
- **Disadvantages:** If the initial parent query involved expensive joins or CPU-heavy calculations, re-executing that query inside the subquery can stress the database engine.

## 🔴 Senior Level

### Why `@Fetch(FetchMode.JOIN)` is Ignored in JPQL Queries

A frequent interview trap for senior developers:

```java
@Entity
public class Order {
    @ManyToOne(fetch = FetchType.LAZY)
    @Fetch(FetchMode.JOIN)
    private User user;
}

// Repository query execution:
List<Order> orders = entityManager.createQuery("SELECT o FROM Order o", Order.class)
        .getResultList();
```

**The Runtime Reality:**
Developers expect Hibernate to execute an outer join with `users`.
Instead, **Hibernate executes 1 initial query followed by $N$ secondary queries**!

#### Core Architectural Rationale:
1. The JPA specification mandates that JPQL queries execute strictly according to the abstract syntax tree defined in the query text. If the query specifies `SELECT o FROM Order o`, Hibernate must return only data from the `orders` table.
2. Entity mapping annotations (`@Fetch`) constitute **static mapping metadata** used during `entityManager.find()` or lazy proxy resolution.
3. The JPQL query parser takes absolute precedence over static mapping metadata. It completely ignores `@Fetch(FetchMode.JOIN)`!
4. To force an SQL join in JPQL, developers must explicitly declare dynamic query fetching:
   `SELECT o FROM Order o JOIN FETCH o.user`.

### Static vs. Dynamic Fetching Architecture

Senior systems architects distinguish between **static strategies** (baked into entity classes) and **dynamic strategies** (selected at query time based on business operations):

```
                                  FETCHING STRATEGIES
                                           │
                 ┌─────────────────────────┴─────────────────────────┐
                 ▼                                                   ▼
      STATIC (Entity-Level)                               DYNAMIC (Query-Level)
(Hardcoded in class annotations;                   (Configured per specific business use case;
 inflexible and cannot be tuned per query)          maximum performance and zero waste)
      │                                                   │
      ├── FetchType (LAZY / EAGER)                        ├── JPQL JOIN FETCH
      ├── @Fetch (SELECT / JOIN / SUBSELECT)              ├── JPA EntityGraph (fetchgraph/loadgraph)
      └── @BatchSize (IN-clause batching)                 └── DTO Projections (SELECT new Dto(...))
```

### Comparative Analysis of Dynamic Fetching Mechanisms

| Mechanism | Configuration Scope | SQL Queries | Pagination Safe? | Cartesian Product Risk |
| :--- | :--- | :--- | :--- | :--- |
| **`JOIN FETCH`** | JPQL / HQL / Criteria | Exactly 1 | ❌ Dangerous (`HHH000104`, OOM) | ❌ High (Multiple collections) |
| **`@EntityGraph`** | Repository / Query Hint | Exactly 1 (LEFT JOIN) | ❌ Dangerous for collections | ❌ High (Multiple collections) |
| **`@BatchSize`** | Entity / `application.yml` | $1 + \lceil N / \text{size} \rceil$ | ✅ **Safe** (DB LIMIT/OFFSET) | ✅ **None** (Separate queries) |
| **`FetchMode.SUBSELECT`** | Collection Mapping | Exactly 2 | ⚠️ Dialect dependent | ✅ **None** (Separate queries) |

## 4 Tricky Questions

### 1. Why are `FetchType.LAZY` and `@Fetch(FetchMode.JOIN)` mutually exclusive, and how does Hibernate resolve the conflict?

**Answer:**
Hibernate resolves the conflict by **forcing immediate eager loading via `JOIN`**, overriding `FetchType.LAZY`:
1. The definition of `FetchMode.JOIN` requires the association to be joined in the initial SQL query using an outer join.
2. Because the child row is already retrieved from the database inside the JDBC `ResultSet` during the parent query, constructing an uninitialized proxy and deferring loading is redundant.
3. Consequently, placing `@Fetch(FetchMode.JOIN)` on a relationship effectively turns it into an eager relationship (`EAGER`). The only place where lazy behavior is maintained is within JPQL queries, where Hibernate ignores the annotation and falls back to a lazy secondary select.

### 2. How does `FetchMode.SUBSELECT` behave if the original query used complex WHERE predicates and parameters?

**Answer:**
1. Hibernate captures and caches the complete query execution context used to retrieve the parent entity list (including SQL text, `WHERE` clauses, `ORDER BY` conditions, and bound positional/named parameter values).
2. Upon accessing the child collection on any parent, Hibernate constructs a subquery, embedding the saved parent query inside an `IN` predicate:
   ```sql
   SELECT items.* FROM order_items items 
   WHERE items.order_id IN (
       SELECT o.id FROM orders o WHERE o.user_id = ? AND o.total_price > ?
   );
   ```
3. Hibernate re-binds the identical parameter values automatically.
4. **The SQL Dialect Pitfall:** If the original query utilized database pagination (`LIMIT` / `OFFSET`), certain relational databases (e.g., MySQL prior to 8.0) reject queries using `WHERE id IN (SELECT ... LIMIT N)`. In such configurations, Hibernate must either generate temporary tables or abort with an SQL syntax exception.

### 3. How does batch fetching via `@BatchSize` differ from `FetchMode.SUBSELECT`?

**Answer:**
- **SQL Generation Mechanism:**
  - `@BatchSize(size = 20)` inspects the `PersistenceContext` for up to 20 uninitialized entity IDs and generates an explicit literal parameter list: `WHERE order_id IN (?, ?, ... 20 parameters)`.
  - `SUBSELECT` does not pass individual IDs; it re-executes the original parent selection query as an embedded subquery: `WHERE order_id IN (SELECT id FROM ...)`.
- **Architectural Flexibility:**
  - `@BatchSize` operates universally, regardless of how parent entities entered the session (via separate queries, pagination, or manual addition).
  - `SUBSELECT` functions strictly when parent entities were loaded together in a single query execution.

### 4. What is `@LazyGroup` in Hibernate, and how does it extend fetch strategies?

**Answer:**
The `@LazyGroup` annotation works alongside **Bytecode Enhancement** (`hibernate-enhance-maven-plugin`) to provide fine-grained control over lazy basic columns (`@Basic(fetch = FetchType.LAZY)`):
1. By default, accessing any lazy basic column triggers the simultaneous loading of all lazy columns in the entity.
2. `@LazyGroup("groupName")` groups heavy columns into independent lazy clusters:
   ```java
   @Lob @Basic(fetch = FetchType.LAZY)
   @LazyGroup("photos")
   private byte[] avatar;

   @Lob @Basic(fetch = FetchType.LAZY)
   @LazyGroup("documents")
   private byte[] passportScan;
   ```
3. Calling `getAvatar()` fetches only the avatar column, leaving `passportScan` uninitialized until its getter is explicitly called, avoiding unnecessary network and memory overhead.

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
> "In Hibernate, data fetching strategies operate across two planes: **JPA `FetchType`** dictates *when* data is retrieved (`LAZY` vs `EAGER`), while **Hibernate `FetchMode`** defines *how* the SQL is structured (`SELECT`, `JOIN`, or `SUBSELECT`). In enterprise architectures, static `FetchMode` mappings are rarely used because `FetchMode.JOIN` overrides lazy loading and is ignored by JPQL. The production standard is **Dynamic Fetching**: map all entity associations statically as `FetchType.LAZY`, and dynamically apply **`JOIN FETCH`**, **`@EntityGraph`**, or global batch fetching via **`hibernate.default_batch_fetch_size`** tailored to specific transactional operations."

### Key Production Monitoring Metrics
- Database round-trips per business transaction.
- Ratio of individual `SELECT` queries to `JOIN` queries in SQL profiling tools (`p6spy`, `datasource-proxy`).
- JDBC network egress volume per API request.

### Red Flags (DO NOT Say)
- ❌ *"FetchType and FetchMode are interchangeable synonyms."* (FetchType controls timing; FetchMode controls SQL structure).
- ❌ *"Adding `@Fetch(FetchMode.JOIN)` guarantees that JPQL queries will use a SQL JOIN."* (JPQL completely ignores `@Fetch(FetchMode.JOIN)` annotations).
- ❌ *"FetchMode.SUBSELECT can be applied to `@ManyToOne` relationships."* (`SUBSELECT` is valid strictly for collection mappings).
- ❌ *"@BatchSize is a value in the FetchMode enum."* (It is an independent batch-fetching optimization mechanism).
