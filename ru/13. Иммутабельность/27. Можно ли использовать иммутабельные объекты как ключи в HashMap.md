# Можно ли использовать иммутабельные объекты как ключи в HashMap

---

## 🟢 Junior Level

### 30-секундный ответ
**Не просто можно, а строго рекомендуется!** Иммутабельные (неизменяемые) объекты являются **золотым стандартом для ключей `HashMap` и `HashSet`**.

Главные причины:
1. **Стабильность хэш-кода:** значение `hashCode()` вычисляется на основе неизменяемых полей объекта и гарантированно остаётся константным на протяжении всей жизни программы.
2. **Гарантированное нахождение в бакете:** адрес корзины (*bucket*) в массиве хэш-таблицы рассчитывается по формуле `(n - 1) & hash`. Поскольку хэш не меняется, `map.get(key)` всегда попадает именно в ту корзину, в которую объект был помещён при `put(key, value)`.
3. **Защита от потери данных:** мутабельный ключ при изменении своих полей меняет свой хэш-код, в результате чего объект безвозвратно «теряется» внутри таблицы, вызывая утечку памяти (*Memory Leak*).

---

### Лучшие ключи в Java
- **`java.lang.String`** — самый популярный и оптимизированный ключ в Java.
- **Классы-обёртки примитивов** (`Integer`, `Long`, `UUID`).
- **Классы даты и времени** (`LocalDate`, `Instant`).
- **Java Records (Java 16+)** — идеальный выбор для составных ключей (*Composite Keys*).

```java
// Классический и безопасный пример
Map<String, UserSession> sessions = new HashMap<>();
sessions.put("session_token_123", new UserSession("Alice"));

// Гарантированно вернёт сессию Алисы:
UserSession session = sessions.get("session_token_123"); 
```

## 🟡 Middle Level

### Механика поиска ключа в `HashMap`
При вызове `map.put(key, value)` и `map.get(key)` выполняются три строгих этапа:
1. **Вычисление хэша с перемешиванием (Bit Spreader):**
   ```java
   static final int hash(Object key) {
       int h;
       return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
   }
   ```
2. **Определение индекса корзины:** `index = (table.length - 1) & hash`.
3. **Поиск узла в корзине:** проверка `p.hash == hash && (p.key == key || (key != null && key.equals(p.key)))`.

Если ключ мутабелен и изменил своё состояние между вызовами `put` и `get`:
- `get(key)` вычислит **новый хэш-код** и пойдёт искать ключ в совершенно другой корзине.
- Метод вернёт `null`, хотя физически объект с этим значением остаётся в куче в исходном бакете!

---

### Кэширование хэш-кода (Lazy Hash Caching)
Иммутабельность открывает возможность мощнейшей оптимизации — **кэширования значения `hashCode()`**:
- В классе `String` хэш-код вычисляется один раз при первом обращении и запоминается в приватное поле `private int hash`.
- Все последующие миллионы вызовов `map.get("someStringKey")` берут готовый `hash` за $O(1)$ без пересчёта символов!
- Вы также можете реализовать этот паттерн в своих неизменяемых классах:
```java
public final class ImmutableOrderId {
    private final String prefix;
    private final long number;
    private int cachedHash; // Кэш

    public ImmutableOrderId(String prefix, long number) {
        this.prefix = Objects.requireNonNull(prefix);
        this.number = number;
    }

    @Override
    public int hashCode() {
        int h = cachedHash;
        if (h == 0) {
            h = Objects.hash(prefix, number);
            cachedHash = h;
        }
        return h;
    }
}
```

## 🔴 Senior Level

### Составные ключи на базе `Record` (Composite Keys)
Для поиска по нескольким параметрам (например, `tenantId` + `userId`) вместо конкатенации строк (`tenant + ":" + id`), создающей мусорные объекты, в современном Java используют **`record`**:
```java
// Идеальный составной ключ в 1 строку:
public record TenantUserKey(UUID tenantId, Long userId) implements Comparable<TenantUserKey> {
    @Override
    public int compareTo(TenantUserKey other) {
        int cmp = this.tenantId.compareTo(other.tenantId);
        return cmp != 0 ? cmp : this.userId.compareTo(other.userId);
    }
}
```
**Преимущества для Senior:**
1. Класс гарантированно `final`.
2. Компилятор автоматически генерирует математически корректные `equals()` и `hashCode()` на основе всех компонентов.
3. Реализация `Comparable` защищает от деградации при коллизиях.

---

### Разрешение коллизий и древовидные корзины (Treeification)
Если разные иммутабельные ключи выдают одинаковый хэш-код (*Hash Collision*):
1. Элементы складываются в один бакет в виде связного списка.
2. При превышении порога в 8 элементов (`TREEIFY_THRESHOLD = 8`) и размере таблицы не менее 64 (`MIN_TREEIFY_CAPACITY = 64`) бакет преобразуется из связного списка в **красно-чёрное дерево (Red-Black Tree)**.
3. Сложность поиска падает с $O(N)$ до $O(\log N)$.
4. Если ключи реализуют интерфейс `Comparable<K>`, узлы дерева балансируются и сравниваются по `compareTo()`, полностью исключая необходимость вызова медленного `System.identityHashCode()`.

---

### Многопоточный контекст: `ConcurrentHashMap`
В `ConcurrentHashMap` иммутабельность ключей критична для масштабируемости:
- Во время процесса параллельного расширения таблицы (**Concurrent Resizing**) фоновые потоки переносят бакеты в новую таблицу.
- Читающие потоки выполняют обход без блокировок (*Lock-Free Read*).
- Неизменяемость ключей гарантирует, что чтение хэша и сравнение ссылок происходят атомарно и согласованно без гонок данных.

## 4 Tricky Questions

### 1. Почему класс `String` хранит кэшированный хэш-код в обычном, не-`volatile` поле `private int hash`, и почему это на 100% безопасно в многопоточном коде?
**Ответ:**
Это знаменитая идиома **доброкачественной гонки данных (Benign Data Race)**:
1. Класс `String` строго иммутабелен, а алгоритм вычисления `hashCode()` является **чистой детерминированной функцией**: по одним и тем же неизменным байтам всегда получается строго одно и то же 32-битное число.
2. Если два потока одновременно вызовут `hashCode()` у нового экземпляра `String`, они оба могут вычислить значение параллельно и оба запишут абсолютно **одно и то же число** в поле `hash`.
3. Поскольку `int` в Java записывается атомарно (в отличие от не-volatile `long`/`double`), потоки не могут прочитать разорванное значение. 
Отсутствие модификатора `volatile` исключает накладные расходы на барьеры памяти процессора (*Memory Barriers*), обеспечивая максимальную скорость чтения.

---

### 2. Что произойдёт, если класс-ключ `record GroupKey(List<String> tags)` объявлен как `record`, но в него передан обычный `ArrayList`?
**Ответ:**
Произойдёт скрытая катастрофа:
- Хотя `record` генерирует `final`-поля, он обеспечивает только **поверхностную (Shallow) иммутабельность**.
- Внутренний `ArrayList` остаётся мутабельным.
- Если внешний код вызовет `tags.add("new_tag")`, метод `List.hashCode()` пересчитает хэш-код списка (он зависит от элементов).
- Хэш-код `GroupKey` изменится, и объект потеряется в бакетах `HashMap`.
- **Правило:** в Record для ключей коллекция обязана быть защищена через `List.copyOf(tags)` в компактном конструкторе!

---

### 3. Зачем ключам в `HashMap` реализовывать интерфейс `Comparable<K>`, если для мапы обязательны только `equals()` и `hashCode()`?
**Ответ:**
В Java 8+ при большом количестве коллизий в одном бакете связный список преобразуется в красно-чёрное дерево (`TreeNode`).
- Для балансировки и поиска в дереве узлы необходимо упорядочивать.
- Если ключ реализует `Comparable<K>`, метод `tree.putTreeVal()` сравнивает узлы через `((Comparable)k).compareTo(x)`. Это работает быстро и предсказуемо.
- Если же ключ не реализует `Comparable`, JVM вынуждена использовать сложный механизм тай-брейка (*tie-break*): сравнивать названия классов через `getClass().getName()`, а при совпадении обращаться к нативному `System.identityHashCode()`, что существенно замедляет вставку и поиск.

---

### 4. Можно ли использовать мутабельный объект в качестве ключа, если использовать `java.util.IdentityHashMap`? В чём подвох?
**Ответ:**
Да, в `IdentityHashMap` это технически возможно, но несёт принципиально иную семантику:
- `IdentityHashMap` **полностью игнорирует** методы `equals()` и `hashCode()`.
- Сравнение ключей производится по ссылочному равенству `k1 == k2`, а хэш вычисляется через `System.identityHashCode()`, который привязан к адресу объекта в куче и никогда не меняется от модификации полей.
- **Подвох:** два логически абсолютно одинаковых объекта (например, два `User(id=1)`) будут считаться **разными ключами**, так как находятся по разным адресам в памяти кучи. Это подходит для кэшей графов сериализации, но непригодно для стандартной бизнес-логики.

## 🎯 Шпаргалка для интервью

### Главное об иммутабельных ключах в HashMap
- **Можно ли использовать?** Да, это рекомендуемый отраслевой стандарт.
- **Почему:** константный `hashCode()` $\to$ ключ всегда находится в одном и том же бакете $\to$ отсутствие утечек памяти.
- **Оптимизация:** кэширование `hashCode` (как в `String`).
- **Составные ключи:** использовать **Java Record** с реализацией `Comparable`.
- **Опасность Shallow Immutability:** если внутри ключа есть мутабельная коллекция, её мутация сломает хэш!

### Мутабельный ключ vs Иммутабельный ключ
| Характеристика | Иммутабельный ключ (`String`, `Record`) | Мутабельный ключ (`User`, `ArrayList`) |
| :--- | :--- | :--- |
| **Стабильность хэша** | 🟢 Гарантирована 100% | 🔴 Изменяется при мутации |
| **Безопасность поиска** | 🟢 Всегда находит значение | 🔴 Возвращает `null` (потеря элемента) |
| **Утечка памяти** | 🟢 Исключена | 🔴 Высокий риск *Logical Memory Leak* |
| **Кэширование хэша** | 🟢 Возможно в приватном поле | ❌ Невозможно |

### Красные флаги на собеседовании (Чего говорить нельзя)
- ❌ *«Использовать ArrayList в качестве ключа HashMap — нормальная практика»* — изменение списка сделает запись недостижимой.
- ❌ *«Для правильной работы HashMap достаточно реализовать только hashCode()»* — при коллизиях мапа использует `equals()`, оба метода обязательны.
- ❌ *«Если поле ключа объявлено как `final List<String>`, ключ полностью защищён»* — элементы списка можно менять, ломая хэш.
