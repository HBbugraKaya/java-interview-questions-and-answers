# Как работают каскадные операции (Cascade)

Каскадирование (Cascading) в JPA и Hibernate — это механизм автоматического распространения операций жизненного цикла (`PERSIST`, `MERGE`, `REMOVE`, `REFRESH`, `DETACH`) от родительской сущности к связанным с ней дочерним сущностям. Каскадные операции позволяют работать с целостными агрегатами и графами объектов через единую точку входа (Aggregate Root), избавляя разработчика от ручного сохранения каждого зависимого объекта.

---

## 🟢 Junior Level

### Что такое каскадные операции и зачем они нужны

Без каскадирования сохранение сущности `Order` вместе со списком позиций `OrderItem` требовало бы ручного вызова `persist()` для каждого отдельного объекта:

```java
// БЕЗ КАСКАДИРОВАНИЯ (Громоздко и чревато ошибками):
entityManager.persist(item1);
entityManager.persist(item2);
entityManager.persist(order);
```

С включенным каскадированием достаточно вызвать метод только для родителя:

```java
@Entity
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Все операции над Order автоматически передаются на items
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
    private List<OrderItem> items = new ArrayList<>();

    public void addItem(OrderItem item) {
        items.add(item);
        item.setOrder(this); // Синхронизация обратной стороны связи
    }
}
```

```java
// С КАСКАДИРОВАНИЕМ:
Order order = new Order();
order.addItem(new OrderItem("Ноутбук"));
order.addItem(new OrderItem("Мышь"));

// Достаточно сохранить ТОЛЬКО родительскую сущность:
entityManager.persist(order); 
// Hibernate сам выполнит 3 операции INSERT: сначала order, затем оба items
```

### Основные типы каскадирования (`CascadeType`)

Спецификация JPA определяет следующие типы в перечислении `jakarta.persistence.CascadeType`:

| Тип каскада | Распространяемый метод `EntityManager` | Описание |
| :--- | :--- | :--- |
| **`CascadeType.PERSIST`** | `persist()` | При сохранении родителя новые дочерние объекты переходят в статус `Managed`. |
| **`CascadeType.MERGE`** | `merge()` | При слиянии отсоединенного родителя дочерние объекты также обновляются в сессии. |
| **`CascadeType.REMOVE`** | `remove()` | При удалении родителя все связанные дочерние строки удаляются из БД. |
| **`CascadeType.REFRESH`** | `refresh()` | Перезагрузка родителя из БД принудительно перезагружает всех детей. |
| **`CascadeType.DETACH`** | `detach()` | Отсоединение родителя от сессии отсоединяет и все связанные сущности. |
| **`CascadeType.ALL`** | Все вышеперечисленные | Объединяет в себе абсолютно все типы каскадирования. |

## 🟡 Middle Level

### JPA Cascading vs Базовый СУБД-каскад (`ON DELETE CASCADE`)

Частая путаница среди разработчиков: каскады JPA и каскады на уровне внешних ключей в базе данных — это два принципиально разных механизма:

```
┌──────────────────────────────────────┬──────────────────────────────────────┐
│       JPA Каскад (Hibernate Core)    │      DB Каскад (ON DELETE CASCADE)   │
├──────────────────────────────────────┼──────────────────────────────────────┤
│ • Выполняется в памяти JVM           │ • Выполняется движком СУБД           │
│ • Hibernate обязан загрузить детей   │ • Дети удаляются мгновенно на уровне │
│   в L1 кэш перед удалением           │   файлов базы данных без чтения в JVM│
│ • Вызываются колбэки (@PreRemove)    │ • Колбэки JPA и Hibernate НЕ знают   │
│   и Dirty Checking                   │   об удалении                        │
│ • Генерирует N отдельных SQL DELETE  │ • 1 быстрый SQL DELETE для родителя  │
└──────────────────────────────────────┴──────────────────────────────────────┘
```

Для интеграции JPA с каскадом базы данных Hibernate предоставляет аннотацию:
```java
@OneToMany(mappedBy = "order")
@org.hibernate.annotations.OnDelete(action = OnDeleteAction.CASCADE)
private List<OrderItem> items;
```
При использовании `@OnDelete` Hibernate отправляет только `DELETE FROM orders WHERE id = ?`, а дочерние строки удаляет сам движок PostgreSQL/MySQL.

### Фатальная ошибка: `CascadeType.ALL` на связи `@ManyToOne`

Самая опасная ошибка новичков — бездумное копирование `cascade = CascadeType.ALL` на сторону «многие к одному»:

```java
@Entity
public class Order {
    @Id
    private Long id;

    // ❌ КАТАСТРОФА: Каскадное удаление направлено на общего родителя!
    @ManyToOne(cascade = CascadeType.ALL)
    private User user;
}
```

**Что произойдет в проде:**
При удалении любого обычного заказа (`entityManager.remove(order)`) сработает каскад `REMOVE`, который **удалит из базы данных самого пользователя `User`**, а если у пользователя были другие заказы — база выбросит ошибку внешнего ключа либо удалит вообще все данные клиента!

*Золотое правило:* На связях `@ManyToOne` и `@ManyToMany` каскад `REMOVE` **запрещен**.

## 🔴 Senior Level

### Проблема производительности: N+1 при каскадном JPA-удалении

Представим сущность `Category`, содержащую 10 000 товаров `Product` с настройкой `cascade = CascadeType.REMOVE`:

```java
Category category = entityManager.find(Category.class, categoryId);
entityManager.remove(category);
```

#### Что происходит внутри Hibernate:
1. Спецификация JPA требует, чтобы перед удалением каждого дочернего объекта для него были выполнены колбэки жизненного цикла (`@PreRemove`, `@PostRemove`) и очищен L2 кэш.
2. Hibernate **вынужден выполнить SQL `SELECT` и загрузить все 10 000 объектов `Product` в оперативную память** (вызывая просадку памяти и нагрузку на сборщик мусора GC).
3. Затем в фазе `flush()` Hibernate выполняет **10 000 отдельных SQL-запросов `DELETE FROM products WHERE id = ?`**!
4. **Senior-решение:** Для объемных коллекций отключать `CascadeType.REMOVE` в JPA и использовать либо уровень СУБД (`ON DELETE CASCADE`), либо прямой пакетный JPQL:
   ```java
   productRepository.deleteByCategoryId(categoryId);
   categoryRepository.deleteById(categoryId);
   ```

### Циклическое каскадирование (Circular Cascades)

В двунаправленных связях «один к одному» или графах со сложными циклическими зависимостями:
```java
@Entity
public class Account {
    @OneToOne(cascade = CascadeType.ALL)
    private Profile profile;
}

@Entity
public class Profile {
    @OneToOne(cascade = CascadeType.ALL) // ❌ Опасность цикла!
    private Account account;
}
```
При вызове `entityManager.persist(account)` процессор каскадов `Cascade.cascade()` в Hibernate начинает рекурсивный обход графа объектов. Hibernate имеет внутренний механизм защиты от зацикливания на основе карты посещенных сущностей (`IdentityMap`), однако циклический каскад часто приводит к непредсказуемому порядку формирования `ActionQueue` и ошибкам `TransientPropertyValueException`.

## 4 Tricky Questions

### 1. Если у родительской сущности объявлен `cascade = CascadeType.REMOVE`, выполнит ли Hibernate каскадное удаление дочерних записей при выполнении массового запроса `entityManager.createQuery("DELETE FROM Order o WHERE o.id = 1").executeUpdate()`?

**Ответ:**
1. **Категорически нет!** 
2. Массовые запросы на удаление через HQL/JPQL (`DELETE FROM ...`) или `@Modifying` в Spring Data JPA транслируются напрямую в один SQL `DELETE` на уровне базы данных.
3. Контекст постоянства `PersistenceContext`, сущности и аннотации каскадирования JPA в этом процессе **не участвуют вообще**.
4. Дочерние записи не будут удалены через JPA. Если в самой БД на уровне внешнего ключа не настроено `ON DELETE CASCADE`, СУБД немедленно выбросит ошибку нарушения внешнего ключа: `DataIntegrityViolationException: foreign key constraint violation`.

### 2. В чем разница между `cascade = CascadeType.REMOVE` и параметром связи `orphanRemoval = true`?

**Ответ:**
1. `CascadeType.REMOVE` срабатывает **только при удалении родительской сущности**: `entityManager.remove(order)` приводит к удалению всех связанных `order.getItems()`. Но если просто удалить элемент из коллекции в памяти (`order.getItems().remove(0)`), строка в БД **не удалится**, а лишь потеряет связь (станет «сиротой»).
2. `orphanRemoval = true` отслеживает именно **удаление из коллекции**: вызов `order.getItems().remove(0)` при очередном `flush()` приведет к физическому удалению строки `OrderItem` из базы данных.
3. Кроме того, `orphanRemoval = true` автоматически включает в себя поведение `CascadeType.REMOVE` при удалении родителя.

### 3. Допустим, на коллекции объявлен `cascade = CascadeType.PERSIST`. Мы создали родителя, добавили дочерний элемент `order.getItems().add(item)`, но забыли проставить обратную ссылку `item.setOrder(order)`. Что произойдет при вызове `entityManager.persist(order)`?

**Ответ:**
1. Каскад `PERSIST` сработает: Hibernate попытается сохранить оба объекта.
2. Сначала выполнится `INSERT INTO orders ...` и сгенерируется ID заказа.
3. Затем выполнится `INSERT INTO order_items (order_id, name) VALUES (null, 'Item 1')`.
4. В колонку внешнего ключа `order_id` уйдет значение **`NULL`**, потому что связь со стороны `OrderItem` (владельца связи) не была заполнена в памяти JVM!
5. Если в таблице `order_items` колонка `order_id` объявлена как `NOT NULL`, СУБД выбросит ошибку: `null value in column "order_id" violates not-null constraint`.

### 4. Мы вызвали `entityManager.detach(order)`. Коллекция `items` была настроена с ленивой загрузкой (`LAZY`) и не была инициализирована до этого. Перейдет ли коллекция в состояние `Detached`, и можно ли будет прочитать ее размер `order.getItems().size()` после этого?

**Ответ:**
1. Метод `detach()` при каскаде `CascadeType.DETACH` отсоединяет родителя и все уже загруженные в память связанные объекты.
2. Непроинициализированная коллекция останется специальным прокси-объектом Hibernate — `PersistentBag` в неинициализированном состоянии.
3. Поскольку родительский объект `order` перешел в состояние `Detached`, его связь с активным `Session` разорвана.
4. Попытка вызвать `order.getItems().size()` за пределами открытой сессии немедленно выбросит исключение:
   `org.hibernate.LazyInitializationException: could not initialize proxy - no Session`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «Каскадные операции (`CascadeType`) в JPA автоматически переносят изменения жизненного цикла родительской сущности на связанные дочерние объекты. Для композиционных связей `@OneToMany` (например, `Order` -> `OrderItem`), где дочерний объект не имеет смысла без родителя, стандартом является связка `cascade = CascadeType.ALL, orphanRemoval = true`. На связях `@ManyToOne` и `@ManyToMany` каскад `REMOVE` строго запрещен, так как он приведет к случайному удалению разделяемых сущностей. При каскадном JPA-удалении больших коллекций возникает просадка по памяти и N+1 удалений — для таких кейсов следует использовать `@OnDelete(action = OnDeleteAction.CASCADE)` на уровне СУБД».

### Ключевые метрики для Production-мониторинга
- **Количество SQL DELETE на один запрос**: всплеск указывает на неэффективное JPA-каскадирование вместо пакетного или баз данных.
- **Объем памяти JVM во время операций удаления**: массовая материализация дочерних сущностей при каскадах создает скачки в куче (GC pauses).

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«Я всегда ставлю cascade = CascadeType.ALL на все связи @ManyToOne для удобства»* — Это гарантированно удалит общих пользователей или справочники при удалении дочерних записей.
- ❌ *«Каскадное удаление в JPA само преобразуется в ON DELETE CASCADE в базе»* — Это два разных механизма; JPA-каскад загружает сущности в память и делает N отдельных `DELETE`.
- ❌ *«Массовый запрос deleteBy... в репозитории активирует JPA-каскады»* — Пакетные HQL/SQL запросы работают напрямую в СУБД и игнорируют JPA-каскадирование.
- ❌ *«CascadeType.REMOVE удаляет запись из базы, если просто вызвать list.remove(item)»* — Это делает `orphanRemoval = true`, а не `CascadeType.REMOVE`.
