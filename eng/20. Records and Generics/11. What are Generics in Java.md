# What are Generics in Java

**Generics** (introduced in Java 5 via JSR 14) provide compile-time parametric polymorphism, allowing classes, interfaces, and methods to operate on objects of various types while providing compile-time type safety. Generics eliminate explicit casting and shift type-mismatch errors from runtime (`ClassCastException`) to compile time.

---

## 🟢 Junior Level

### The Problem Before Java 5
Prior to Java 5, collections operated exclusively on `java.lang.Object`. This architecture had two major deficiencies:
1. **Explicit Manual Casting:** Every retrieval required boilerplate casting.
2. **Lack of Type Safety at Compile Time:** Collections accepted any reference type, deferring type mismatch errors to runtime crashes.

```java
// Pre-Java 5 (Untyped Collections):
List list = new ArrayList();
list.add("Hello World");
list.add(Integer.valueOf(42)); // Compiles without error!

// Runtime Failure:
String str1 = (String) list.get(0); // Manual cast required
String str2 = (String) list.get(1); // Throws ClassCastException at runtime!
```

### The Solution: Generics (Java 5+)
Generics allow type parameters to be specified when declaring and instantiating types:

```java
// Modern Java with Generics:
List<String> list = new ArrayList<>();
list.add("Hello World");
// list.add(42); // Compilation Error: incompatible types

String str = list.get(0); // No manual cast required; completely type-safe
```

### The Three Core Pillars of Generics
1. **Compile-Time Type Safety:** The compiler verifies type compatibility before bytecode generation, catching defects during development rather than in production.
2. **Elimination of Casts:** The compiler automatically inserts safe type casts in generated bytecode, keeping application code clean and readable.
3. **Generic Algorithm Reusability:** Data structures (`List<E>`, `Map<K, V>`) and algorithms (`Collections.sort()`, `Stream<T>`) are written once and reused across arbitrary types without duplicating code.

## 🟡 Middle Level

### Type Parameter Naming Conventions
By standard Java convention, type parameters are single uppercase letters representing their semantic role:
- `T` — Type (general-purpose type parameter)
- `E` — Element (used heavily in `java.util.Collection`)
- `K`, `V` — Key and Value (used in mappings like `Map<K, V>`)
- `N` — Number (numeric types)
- `R` — Result / Return type (used in functional interfaces like `Function<T, R>`)

```java
// Generic Class
public class Box<T> {
    private T item;

    public void put(T item) { this.item = item; }
    public T get() { return item; }
}

// Generic Interface
public interface Repository<T, ID> {
    Optional<T> findById(ID id);
    T save(T entity);
}

// Generic Static Method: Type parameter declared before return type
public class CollectionUtils {
    public static <T> List<T> fromArrayToList(T[] array) {
        return Arrays.stream(array).toList();
    }
}
```

### Bounded Type Parameters
Type parameters can be constrained using the `extends` keyword (applied to classes or interfaces):

```java
public class NumericStats<T extends Number> {
    private final List<T> values;

    public NumericStats(List<T> values) {
        this.values = values;
    }

    public double average() {
        double sum = 0.0;
        for (T val : values) {
            sum += val.doubleValue(); // doubleValue() is accessible via Number bound
        }
        return sum / values.size();
    }
}
```

### Invariance of Java Generics
A fundamental rule in Java generics is **invariance**:
Even though `String` is a subtype of `Object`, `List<String>` is **not** a subtype of `List<Object>`.

```java
List<String> stringList = new ArrayList<>();
// List<Object> objectList = stringList; // Compilation error! Incompatible types.
```

**Why invariance is strictly enforced:**
If `List<String>` could be assigned to `List<Object>`, the reference `objectList` could be used to insert an `Integer`:
```java
// If allowed:
objectList.add(100); // Pollutes the string list
String s = stringList.get(0); // Would throw ClassCastException at runtime!
```
To achieve subtyping polymorphism when needed, Java provides wildcards (`? extends T` and `? super T`).

## 🔴 Senior Level

### Type Erasure vs. Reification
Languages handle generic polymorphism through two distinct architectural models:
1. **Monomorphization / Reification (e.g., C++, C#):** The runtime retains full type metadata. The compiler or JIT generates specialized bytecode/machine code for each type instantiation (`List<int>` and `List<string>` are distinct native types).
2. **Type Erasure (Java):** Generic type parameters exist exclusively at compile time. The compiler enforces type safety, strips all generic parameter information, replaces type variables with their bounds (or `Object`), and emits explicit `checkcast` instructions.

#### Why Java Chose Type Erasure
Java 5 (2004) prioritized **Migration Compatibility (Binary Backward Compatibility)**. Millions of lines of legacy enterprise Java 1.4 code relied on raw types (`java.util.List`). If Java had adopted reification, legacy bytecode and libraries would have been incompatible with generic code without complete recompilation and rewriting. Type erasure allowed new generic collections to interoperate seamlessly with pre-Java 5 libraries on the same JVM.

#### Bytecode Transformation Example:
```java
// Source code:
public class Node<T extends Number> {
    private T data;
    public T getData() { return data; }
}

// Bytecode representation (post-erasure):
public class Node {
    private Number data; // T erased to Number bound
    public Number getData() { return data; }
}
```

### Bridge Methods
When a class extends or implements a parameterized class/interface and specifies a concrete type argument, type erasure could break method overriding in the virtual method table (`vtable`). To preserve polymorphic dispatch, the compiler synthesizes a **synthetic bridge method**:

```java
public class StringNode extends Node<String> {
    public void setData(String data) { ... }

    // Synthesized by javac:
    // public void setData(Object data) {
    //     setData((String) data); // checkcast + invokevirtual
    // }
}
```

### Reified Metadata and the Super Type Token Pattern
A common misconception is that all generic information is deleted during compilation. While type parameters are erased from **executable bytecode instructions and instances**, they are preserved in the **class file constant pool under the `Signature` attribute** for:
- Class declarations (`class MyRepo implements Repository<User, Long>`)
- Field type declarations (`private List<String> items;`)
- Method signatures (`public List<User> getUsers()`)

This preservation powers the **Super Type Token pattern** (utilized by Jackson `TypeReference`, Spring `ResolvableType`, and Gson `TypeToken`):
```java
// Creating an anonymous subclass captures the generic parameter in class metadata:
TypeReference<List<User>> token = new TypeReference<List<User>>() {};

Type genericSuperclass = token.getClass().getGenericSuperclass();
ParameterizedType paramType = (ParameterizedType) genericSuperclass;
Type actualType = paramType.getActualTypeArguments()[0];

System.out.println(actualType); // java.util.List<User> (accessible at runtime via reflection)
```

## 4 Tricky Questions

### 1. Why did Java implement generics using Type Erasure rather than Reification as in C# or C++?
**Answer:** Absolute binary and migration compatibility with Java 1.4 and older codebases. At Java 5's release in 2004, breaking backward compatibility would have fragmented the Java ecosystem. Type erasure ensured that `List<String>` and `List<Integer>` share the exact same runtime `Class` object (`List.class`), allowing raw types and generic types to coexist inside the same JVM without library recompilation. The trade-offs include inability to invoke `new T()`, lack of primitive type generics (`List<int>`), and lack of reified `instanceof T` checks.

### 2. If types are erased at compile time, how do Jackson and Spring determine the exact target generic type during JSON deserialization?
**Answer:** Type erasure removes generic metadata from local variable execution frames and heap object headers, but the compiler persists generic declarations in the `.class` constant pool inside the `Signature` attribute. When using `new TypeReference<List<User>>() {}`, developers create an anonymous inner class extending `TypeReference`. Because the type parameter is part of the class inheritance declaration, it is preserved in bytecode. At runtime, Jackson inspects `getClass().getGenericSuperclass()`, casts it to `ParameterizedType`, and extracts the `User` class via `getActualTypeArguments()`.

### 3. Why are Java arrays covariant (`String[]` can be assigned to `Object[]`), whereas generic collections are strictly invariant?
**Answer:** Array covariance was introduced in Java 1.0 (1996) because Java lacked generics, and utility algorithms like `Arrays.sort(Object[])` or `System.arraycopy(...)` required a way to operate on arbitrary arrays. However, array covariance is inherently flawed: putting an `Integer` into a `String[]` disguised as `Object[]` compiles cleanly and throws an `ArrayStoreException` at runtime. When designing generics for Java 5, the language architects avoided runtime failures by enforcing strict compile-time invariance, providing wildcards (`? extends` and `? super`) for controlled variance.

### 4. What is Heap Pollution, and why does it occur without an explicit cast in client code?
**Answer:** Heap pollution occurs when a variable of a parameterized type points to an object that is not of that type (e.g., a `List<String>` holding an `Integer`). It commonly happens through raw type interoperability, unchecked type casts, or generic varargs (`T...`). The danger of heap pollution is that it produces latent bugs: the initial corrupting write succeeds without errors, but an unexpected `ClassCastException` explodes later during a harmless read operation (`String s = list.get(0);`), even though the calling code contains no explicit casting operator.

## 🎯 Interview Cheat Sheet

- **Genesis & Purpose:** Introduced in Java 5 (JSR 14) to provide compile-time type safety, eliminate boilerplate casts, and enable reusable parametric algorithms.
- **Runtime Model:** Governed by **Type Erasure**. The compiler validates types, erases generic arguments to their upper bound or `Object`, and emits `checkcast` instructions.
- **Strict Invariance:** `List<String>` is not a `List<Object>`. Use `? extends T` (covariance/reading) and `? super T` (contravariance/writing).
- **Core Restrictions Due to Erasure:**
  - Cannot instantiate generic parameters: `new T()` or `new T[10]`.
  - Cannot check generic instances: `x instanceof List<String>` is invalid (only `List<?>`).
  - No static fields with class type parameters (`static T field`).
  - Cannot use primitive types (`List<int>` must be `List<Integer>`).
- **Metadata Retention:** Type signatures on class, method, and field declarations are retained in bytecode (`Signature` attribute) and readable via reflection (Super Type Tokens).
- **Bridge Methods:** Synthetic compiler-generated methods in bytecode that ensure polymorphic virtual dispatch works when subclasses narrow generic return types or parameters.
