# What is type erasure

**Type Erasure** is the core compiler translation mechanism whereby all generic type parameters and type arguments are removed during compilation into JVM bytecode. Introduced in Java 5, type erasure ensures that the compiled `.class` files maintain binary and migration compatibility with pre-Java 5 virtual machines and libraries.

---

## 🟢 Junior Level

### How Type Erasure Works
At compile time, the Java compiler (`javac`) verifies the type safety of generic assignments and invocations. Once validation succeeds, it erases the generic type parameters and replaces them with their bounds or `Object`. The compiler then injects explicit type cast instructions (`checkcast`) where required:

```java
// Source Code written by developer:
List<String> list = new ArrayList<>();
list.add("Hello");
String s = list.get(0);

// Compiled Bytecode representation seen by the JVM:
List list = new ArrayList();
list.add("Hello");
String s = (String) list.get(0); // javac inserts checkcast automatically
```

### The Runtime Reality of Generic Types
At runtime inside the JVM, **`List<String>` and `List<Integer>` are identical**:
```java
List<String> stringList = new ArrayList<>();
List<Integer> intList = new ArrayList<>();

System.out.println(stringList.getClass() == intList.getClass()); // true! Both are java.util.ArrayList.class
```

### Why Type Erasure Was Chosen
When Sun Microsystems designed Java 5 (2004), millions of lines of legacy enterprise Java 1.4 code were in production using raw collections (`java.util.List`). If Java had adopted reification (like C# or C++), existing compiled binaries would have broken without complete source recompilation. Type erasure allowed new generic collections to interoperate seamlessly with legacy code within the same JVM process.

## 🟡 Middle Level

### The Rules of Type Erasure (JLS §4.6)
The compiler transforms generic type variables according to strict rules:

1. **Unbounded Parameters (`<T>`):**
   Erased to `java.lang.Object`:
   ```java
   public class Box<T> { private T value; }
   // Erases to:
   public class Box { private Object value; }
   ```

2. **Single Bounded Parameters (`<T extends Number>`):**
   Erased to the specified upper bound:
   ```java
   public class NumberBox<T extends Number> { private T value; }
   // Erases to:
   public class NumberBox { private Number value; }
   ```

3. **Multiple Bounded Parameters (`<T extends Comparable<T> & Serializable>`):**
   Erased to the **first bound** (`Comparable`):
   ```java
   public class OrderedBox<T extends Comparable<T> & Serializable> { private T value; }
   // Erases to:
   public class OrderedBox { private Comparable value; }
   ```
   *Note:* Where members of the second bound (`Serializable`) are accessed, the compiler emits explicit `checkcast` instructions.

### Prohibitions Imposed by Type Erasure
Because generic type arguments do not exist at runtime, the compiler strictly bans the following operations:

```java
public class Restrictions<T> {
    // 1. Cannot instantiate generic type directly:
    // T item = new T(); // Error: JVM cannot determine the constructor of erased type

    // 2. Cannot allocate generic arrays:
    // T[] items = new T[10]; // Error: Arrays are reified and require exact runtime type

    // 3. Cannot perform parameterized instanceof checks:
    // if (obj instanceof List<String>) // Error: Only unbounded 'instanceof List<?>' is valid

    // 4. Cannot declare static fields with class type parameters:
    // private static T instance; // Error: Static fields belong to the class, not the instance

    // 5. Cannot overload methods whose parameter types have the same erasure:
    // void process(List<String> list) {}
    // void process(List<Integer> list) {} // Error: Both erase to 'process(List)'
}
```

## 🔴 Senior Level

### Bytecode Architecture: Synthetic Bridge Methods
The most intricate challenge posed by type erasure is preserving virtual method overriding in the JVM method table (`vtable`).

Consider a parameterized base class and its concrete subclass:
```java
public class Node<T> {
    public void setData(T data) { ... }
}

public class StringNode extends Node<String> {
    @Override
    public void setData(String data) { ... }
}
```

#### The Polymorphism Dilemma Post-Erasure:
- In `Node.class`, the method erases to `public void setData(Object data)`.
- In `StringNode.class`, the developer declared `public void setData(String data)`.
- In JVM method resolution, `setData(Object)` and `setData(String)` have different parameter descriptors, making them **overloaded methods, not overridden methods**!
- If client code executes:
  ```java
  Node n = new StringNode();
  n.setData("Test"); // Resolves against Node.setData(Object)
  ```
  Dynamic dispatch would bypass `StringNode.setData(String)` completely.

#### The Compiler's Solution: Synthetic Bridge Methods
To fix this, `javac` automatically generates a synthetic **bridge method** marked with `ACC_BRIDGE` and `ACC_SYNTHETIC`:

```java
// Synthesized by javac in StringNode.class:
public void setData(Object data) {
    // Bridges the call by performing checkcast and invoking the concrete method
    this.setData((String) data);
}
```
This guarantees that virtual method dispatch via the parent type correctly routes to the subclass implementation.

### Where Generic Metadata is Retained: The `Signature` Attribute
While type arguments are erased from runtime execution frames and local variables, generic declarations are **permanently recorded in the `.class` file constant pool under the `Signature` attribute** (JVMS §4.7.9) for:
1. Class inheritance and interfaces (`Class.getGenericSuperclass()`, `Class.getGenericInterfaces()`)
2. Field declarations (`Field.getGenericType()`)
3. Method signatures and return types (`Method.getGenericReturnType()`, `Method.getGenericParameterTypes()`)

#### The Super Type Token Pattern
Frameworks such as Jackson (`TypeReference`), Spring (`ResolvableType`), and Gson (`TypeToken`) exploit this metadata persistence:
```java
// By creating an anonymous inner subclass, the generic type is bound to the class metadata:
TypeReference<List<UserDTO>> token = new TypeReference<List<UserDTO>>() {};

Type genericSuperclass = token.getClass().getGenericSuperclass();
ParameterizedType parameterizedType = (ParameterizedType) genericSuperclass;
Type actualType = parameterizedType.getActualTypeArguments()[0];

System.out.println(actualType); // java.util.List<UserDTO> - preserved at runtime!
```

## 4 Tricky Questions

### 1. If a type parameter has multiple bounds (`<T extends Comparable<T> & Serializable>`), to what type does the compiler erase `T`?
**Answer:** The compiler always erases $T$ to its **first bound (First Bound)** declared in the header. 
In `<T extends Comparable<T> & Serializable>`, $T$ erases to `Comparable`. All variables and parameters of type $T$ become `Comparable` in bytecode. Wherever methods or fields from subsequent bounds (`Serializable`) are accessed, the compiler synthesizes explicit `checkcast` instructions. 

This is why Java syntax mandates that if a class bound is present, it **must** appear first: `<T extends Number & Runnable>` is legal, whereas `<T extends Runnable & Number>` produces a compilation error.

### 2. Is generic type information preserved for method local variables inside bytecode?
**Answer:** **No, local variable generic types are erased completely and permanently.** 
The JVM class file specification only generates the `Signature` attribute for structural class members: class declarations, fields, and method descriptors. Inside method bodies, local variables exist strictly as raw JVM types and stack frame indices. 

For example, `List<String> list = new ArrayList<>();` becomes a local variable slot of type `java.util.List`. No reflection API, bytecode inspection, or runtime tool can retrieve the `<String>` argument of a local variable once compiled.

### 3. Can you overload two methods that differ only in generic parameters (`void sort(List<String> l)` and `void sort(List<Integer> l)`)?
**Answer:** **No, this causes a compilation error: "both methods have the same erasure".** 
After type erasure, both methods compile into the identical JVM signature: `void sort(List l)`. The Java Virtual Machine Specification (JVMS) forbids having two methods with the exact same name and parameter descriptor in the same class file. 

Workarounds include renaming the methods (`sortStrings`, `sortIntegers`) or introducing a dummy secondary parameter to differentiate the JVM signatures.

### 4. Why does the JVM allow method overloading based on return type (covariant return types), while the Java language itself prohibits it?
**Answer:** Under the Java Language Specification (JLS §8.4.2), a method signature consists solely of the method name and parameter types—the return type is excluded. Thus, developers cannot write two methods differing only by return type in source code. 

However, under the Java Virtual Machine Specification (JVMS §4.3.3), a method descriptor **includes both parameter types and return type**: `(Ljava/lang/Object;)Ljava/lang/String;` and `(Ljava/lang/Object;)Ljava/lang/Object;` are distinct entries in the method table. The Java compiler exploits this JVM feature to generate synthetic bridge methods and support covariant return types without JVM runtime changes.

## 🎯 Interview Cheat Sheet

- **Core Definition:** Type erasure is the compile-time elimination of all generic type parameters and arguments, replacing them with bounds or `Object`.
- **Target Type Mapping:**
  - Unbounded (`<T>`): Erased to `Object`.
  - Single Bound (`<T extends Number>`): Erased to `Number`.
  - Multiple Bounds (`<T extends A & B>`): Erased to first bound `A`.
- **Reason for Design:** 100% binary and source migration compatibility with pre-Java 5 applications and libraries.
- **What is Forbidden:**
  - `new T()` and `new T[10]`.
  - `instanceof List<String>` (only `instanceof List<?>`).
  - Static fields of generic type (`static T item;`).
  - Overloading methods whose signatures have identical erasures.
- **Bridge Methods:** Synthetic compiler-generated methods in bytecode that ensure polymorphic virtual method dispatch functions correctly across class hierarchies.
- **Where Types Survive:** Class definitions, field declarations, and method headers store generic signatures in the bytecode `Signature` attribute, enabling Super Type Tokens (Jackson, Spring).
