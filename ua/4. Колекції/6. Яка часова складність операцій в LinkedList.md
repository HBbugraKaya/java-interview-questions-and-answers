# Яка часова складність операцій в LinkedList

---

## 🟢 Junior Level

**`LinkedList`** у Java реалізований у вигляді класичного **двозв'язного списку**. Кожен елемент огорнутий в об'єкт `Node`, який містить посилання на корисні дані (`item`), а також посилання на попередній (`prev`) і наступний (`next`) вузли.

На відміну від масивів, елементи списку не розташовані в пам'яті послідовно, тому операції довільного доступу вимагають послідовного переходу за вказівниками.

### Зведена таблиця часової складності

| Операція | Часова складність | Пояснення |
| :--- | :--- | :--- |
| **`get(index)`** | **$O(N)$** | Прямого доступу за адресою немає; необхідний послідовний обхід за посиланнями від голови або хвоста. |
| **`set(index, e)`** | **$O(N)$** | Пошук вузла за $O(N)$ плюс перезапис поля `item` за $O(1)$. |
| **`add(e)` (у кінець)** | **$O(1)$** | Миттєво: прив'язка нового вузла до посилання `last`. |
| **`addFirst(e)`** | **$O(1)$** | Миттєво: прив'язка нового вузла до посилання `first`. |
| **`add(index, e)`** | **$O(N)$** | Пошук позиції за $O(N)$ плюс переприв'язка покажчиків за $O(1)$. |
| **`removeFirst()` / `removeLast()`** | **$O(1)$** | Видалення крайніх елементів без обходу списку. |
| **`remove(index)`** | **$O(N)$** | Пошук вузла за $O(N)$ плюс від'єднання з ланцюжка за $O(1)$. |
| **`iterator.remove()`** | **$O(1)$** | Якщо ітератор уже спозиційований на видалюваному вузлі. |
| **`contains(e)`** | **$O(N)$** | Лінійний перебір елементів від початку до кінця. |
| **`size()`** | **$O(1)$** | Розмір зберігається в окремому цілочисельному полі `int size`. |

## 🟡 Middle Level

### 1. Як влаштований пошук за індексом: Оптимізація $N/2$

Хоча операція `get(index)` має асимптотичну складність $O(N)$, розробники JDK застосували оптимізацію ділення списку навпіл:

```java
// Вихідний код java.util.LinkedList:
Node<E> node(int index) {
    // Якщо індекс у першій половині списку — йдемо від початку:
    if (index < (size >> 1)) {
        Node<E> x = first;
        for (int i = 0; i < index; i++)
            x = x.next;
        return x;
    } else { // Якщо у другій половині — йдемо від кінця:
        Node<E> x = last;
        for (int i = size - 1; i > index; i--)
            x = x.prev;
        return x;
    }
}
```
- Максимальна кількість кроків становить $N / 2$.
- Проте в теорії алгоритмів постійний множник відкидається: $O(N / 2) = O(N)$.

### 2. Катастрофічна пастка $O(N^2)$ при ітерації

Одна з найгрубіших помилок розробників — обхід `LinkedList` за індексами у класичному циклі `for-i`:

```java
// ❌ КАТАСТРОФА ПРОДУКТИВНОСТІ: Складність O(N²)!
List<String> list = new LinkedList<>();
// ... заповнюємо 100 000 елементів
for (int i = 0; i < list.size(); i++) {
    String val = list.get(i); // Кожен виклик наново обходить список від початку або кінця!
}
```

#### Математика катастрофи:
Для отримання $i$-го елемента список проходить у середньому $i/2$ кроків:
$$\sum_{i=1}^{N} \frac{i}{2} \approx \frac{N^2}{4} = O(N^2)$$
Для 100 000 елементів це вимагатиме **2.5 мільярда операцій** розіменування посилань!

```java
// ✅ ПРАВИЛЬНО: Складність O(N)
for (String val : list) { // Використовує Iterator під капотом
    // Перехід до наступного вузла займає строго O(1) через x = x.next
}
```

### 3. Навіщо `clear()` занулює всі посилання кожного вузла?

Метод `clear()` у `LinkedList` має складність **$O(N)$**, оскільки обходить весь список:

```java
public void clear() {
    for (Node<E> x = first; x != null; ) {
        Node<E> next = x.next;
        x.item = null;
        x.next = null;
        x.prev = null; // Розрив двоспрямованих зв'язків!
        x = next;
    }
    first = last = null;
    size = 0;
    modCount++;
}
```
*Чому не можна просто виконати `first = last = null; size = 0;` за $O(1)$?*
Якщо вузли `Node` встигли пережити кілька збірок сміття і потрапили у старше покоління (Tenured/Old Gen), нерозірвані перехресні посилання `next`/`prev` між ними змушують збирач сміття витрачати ресурси на трасування взаємно утримуваного графа пам'яті. Явний розрив посилань за $O(N)$ істотно полегшує та прискорює роботу GC.

## 🔴 Senior Level

### 1. Чому $O(1)$ для `LinkedList.addFirst()` на практиці повільніший за $O(N)$ для `ArrayList`

У теорії вставка на початок `LinkedList.addFirst(e)` виконується за чистий константний час $O(1)$. Проте на реальному апаратному забезпеченні:

```
1. LinkedList.addFirst():
   - Виклик оператора new Node<E>(null, e, first);
   - Виділення 24 байтів у купі (TLAB);
   - Ініціалізація заголовка об'єкта (Mark Word + Klass Word);
   - Запис полів item, next, prev;
   - Переприв'язка покажчика first.prev;
   - Створення сміття, яке згодом повинен прибрати GC.

2. ArrayList.add(0, e):
   - Виклик System.arraycopy();
   - Векторні інструкції процесора (SIMD / AVX) зсувають 64-байтні блоки пам'яті за частки такту;
   - 0 нових об'єктів у купі;
   - Жодного додаткового навантаження на Garbage Collector.
```

Бенчмарки JMH підтверджують: на колекціях розміром до **10 000 – 20 000 елементів** операція `ArrayList.add(0, e)` працює швидше або зіставно з `LinkedList.addFirst(e)`!

### 2. Промахи кешу процесора (Hardware Cache Misses)

У сучасних багатоядерних процесорах операція читання з кешу L1 займає $\approx 1$ наносекунду, тоді як звернення до фізичної оперативної пам'яті DRAM — $\approx 60–100$ наносекунд.

Під час обходу `LinkedList`:
- Кожен вузол `Node` розташований у випадковому місці купи.
- Кожна інструкція `x = x.next` з імовірністю $>90\%$ призводить до **CPU Cache Miss**.
- Конвеєр команд процесора блокується (**Pipeline Stall**) на сотні тактів в очікуванні завантаження лінії кешу з оперативної пам'яті.
- З цієї причини зв'язні списки в сучасному високоефективному коді практично не застосовуються.

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь для співбесіди
> «У `LinkedList` операції доступу за індексом (`get`, `set`), а також вставки та видалення за індексом або значенням виконуються за лінійний час $O(N)$, оскільки вимагають послідовного переходу за ланцюжком посилань від голови або хвоста списку. Винятком є операції на кінцях списку (`addFirst`, `addLast`, `removeFirst`, `removeLast`), а також видалення через спозиційований ітератор `iterator.remove()` — вони виконуються за справжній константний час $O(1)$. Критична помилка під час роботи з `LinkedList` — використання класичного циклу `for-i` з викликом `get(i)`, що призводить до катастрофічної деградації складності до $O(N^2)$».

### Питання підвищеної складності з відповідями

1. **Як оптимізовано метод `LinkedList.get(index)` під капотом і чи змінює це його асимптотику?**
   *Відповідь:* Метод перевіряє, у якій половині списку розташований шуканий індекс: `index < (size >> 1)`. Якщо індекс знаходиться в першій половині, обхід починається з голови (`first`), переходячи за посиланнями `next`. Якщо у другій половині — обхід починається з хвоста (`last`), переходячи за посиланнями `prev`. Це скорочує максимальну кількість кроків удвічі (до $N/2$), але в рамках асимптотичного аналізу константа $1/2$ відкидається, і складність залишається рівною $O(N)$.

2. **Чому обхід `LinkedList` через `for (int i = 0; i < list.size(); i++)` вважається грубою помилкою?**
   *Відповідь:* Метод `list.get(i)` не має прямого доступу до комірки пам'яті та на кожній ітерації заново розпочинає обхід списку від початку або кінця. У результаті сумарна кількість кроків виражається сумою арифметичної прогресії $\approx N^2 / 4$, що дає катастрофічну квадратичну складність $O(N^2)$. Для обходу `LinkedList` завжди необхідно використовувати `Iterator` (або цикл `for-each`), де перехід до наступного вузла займає строго $O(1)$.

3. **Чому `LinkedList.clear()` явно обходить усі вузли списку, а не просто занулює посилання `first` і `last`?**
   *Відповідь:* Метод у циклі занулює поля `item`, `next` і `prev` у кожного вузла за $O(N)$. Якби він просто занулив `first = null` і `last = null`, увесь ланцюжок вузлів залишився б зв'язаним взаємними перехресними посиланнями. Якщо ці об'єкти пережили кілька збірок і потрапили у старше покоління пам'яті (Old Gen), збирачу сміття знадобилося б значно більше ресурсів для трасування й очищення складного графа. Явний розрив зв'язків суттєво полегшує та прискорює збирання сміття.

4. **В якому єдиному випадку вставка в середину `LinkedList` дійсно займає $O(1)$?**
   *Відповідь:* Лише в тому випадку, коли вставка здійснюється через попередньо спозиційований двоспрямований ітератор: `ListIterator.add(e)`. У такому разі ітератор уже утримує пряме посилання на поточний вузол `Node`, і вставка нового вузла зводиться до переприв'язки 4 покажчиків за строго константний час $O(1)$ без необхідності пошуку позиції.

### Типові помилки та Red Flags
- ❌ **Вважати, що `LinkedList.get(index)` працює за $O(1)$.** (Груба помилка: плутанина масиву та зв'язного списку).
- ❌ **Стверджувати, що додавання за індексом `add(index, e)` займає $O(1)$.** (Забувають, що до потрібного індексу спочатку треба дійти за $O(N)$ кроків).
- ❌ **Використовувати цикл `for (int i=0; ... list.get(i))` для обходу `LinkedList`.** (Гарантоване падіння продуктивності до $O(N^2)$).
