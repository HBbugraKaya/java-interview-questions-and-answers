# Что делает аннотация @Autowired

---

## 🟢 Junior Level

**`@Autowired`** — это аннотация Spring Framework, которая указывает IoC-контейнеру автоматически найти подходящий бин в контексте и внедрить его в зависимый класс (механизм **Dependency Injection**).

### Где можно использовать `@Autowired`

1. **Над конструктором (Рекомендуется):**
   ```java
   @Service
   public class OrderService {
       private final PaymentClient paymentClient;

       @Autowired // Если конструктор в классе один, аннотацию можно не писать (начиная со Spring 4.3)
       public OrderService(PaymentClient paymentClient) {
           this.paymentClient = paymentClient;
       }
   }
   ```
2. **Над сеттером (Setter Injection):**
   ```java
   @Autowired
   public void setPaymentClient(PaymentClient paymentClient) {
       this.paymentClient = paymentClient;
   }
   ```
3. **Над полем (Field Injection, не рекомендуется):**
   ```java
   @Autowired
   private PaymentClient paymentClient;
   ```

### Необязательные зависимости (`required = false`)

По умолчанию `@Autowired` требует обязательного наличия бина (`required = true`). Если бин не найден, приложение упадет с ошибкой `NoSuchBeanDefinitionException`.

Сделать зависимость опциональной можно тремя способами:
```java
// Вариант 1: флаг required
@Autowired(required = false)
private AuditService auditService; // останется null, если бина нет

// Вариант 2: Java 8 Optional
@Autowired
private Optional<AuditService> auditService;

// Вариант 3: аннотация @Nullable
@Autowired
public void setAuditService(@Nullable AuditService auditService) { ... }
```

## 🟡 Middle Level

### Пошаговый алгоритм разрешения бинов контейнером

Когда Spring видит точку инъекции `@Autowired`, поиск бина выполняется по строгому 5-шаговому алгоритму:

```
                          [ Точка внедрения @Autowired ]
                                       │
                                       ▼
                    Шаг 1: Поиск всех кандидатов по ТИПУ (byType)
                                       │
                     ┌─────────────────┴─────────────────┐
                     ▼                                   ▼
             [ Найден ровно 1 ]                 [ Найдено несколько ]
                     │                                   │
                     │                                   ▼
                     │                 Шаг 2: Фильтрация через @Qualifier
                     │                                   │
                     │                         ┌─────────┴─────────┐
                     │                         ▼                   ▼
                     │                 [ Найден 1 ]        [ Осталось несколько ]
                     │                         │                   │
                     │                         │                   ▼
                     │                         │       Шаг 3: Проверка @Primary
                     │                         │                   │
                     │                         │         ┌─────────┴─────────┐
                     │                         │         ▼                   ▼
                     │                         │     [ Есть @Primary ]   [ Нет @Primary ]
                     │                         │         │                   │
                     │                         │         │                   ▼
                     │                         │         │       Шаг 4: Проверка @Priority
                     │                         │         │                   │
                     │                         │         │         ┌─────────┴─────────┐
                     │                         │         │         ▼                   ▼
                     │                         │         │     [ Есть @Priority ]  [ Нет @Priority ]
                     │                         │         │         │                   │
                     │                         │         │         │                   ▼
                     │                         │         │         │     Шаг 5: Поиск по ИМЕНИ (byName)
                     │                         │         │         │                   │
                     │                         │         │         │         ┌─────────┴─────────┐
                     │                         │         │         │         ▼                   ▼
                     │                         │         │         │   [ Совпало имя ]     [ Не совпало ]
                     │                         │         │         │         │                   │
                     ▼                         ▼         ▼         ▼         ▼                   ▼
               [ УСПЕШНОЕ ВНЕДРЕНИЕ БИНА ]                                   [ NoUniqueBeanDefinitionException ]
```

1. **Поиск по типу (`byType`):** Контейнер ищет все бины, реализующие нужный интерфейс или наследующие класс. Если найден один — он внедряется.
2. **Проверка `@Qualifier`:** Если кандидатов несколько, отбираются бины с указанным в `@Qualifier("beanName")` идентификатором.
3. **Проверка `@Primary`:** Если квалификатора нет, ищется бин, помеченный аннотацией `@Primary`.
4. **Проверка `@Priority`:** Если аннотации `@Primary` нет, Spring проверяет наличие стандартной аннотации `jakarta.annotation.Priority` (выбирается кандидат с наименьшим числовым значением).
5. **Поиск по имени поля/параметра (`byName` fallback):** Имя переменной или аргумента сопоставляется с именами бинов в контексте.
6. **Ошибка:** Если кандидатов всё еще больше одного, выбрасывается `NoUniqueBeanDefinitionException`.

### Внедрение коллекций и ассоциативных массивов

`@Autowired` позволяет инжектировать сразу все реализации интерфейса:

```java
@Service
public class PaymentProcessor {

    // Внедряются ВСЕ бины, реализующие PaymentService.
    // Порядок элементов в списке регулируется аннотацией @Order!
    @Autowired
    private List<PaymentService> paymentServices;

    // Внедряется Map: Ключ = имя бина в контексте, Значение = экземпляр бина
    @Autowired
    private Map<String, PaymentService> paymentServiceMap;
}
```

## 🔴 Senior Level

### Внутренний механизм: `AutowiredAnnotationBeanPostProcessor`

Обработка аннотации `@Autowired` выполняется специализированным пост-процессором **`AutowiredAnnotationBeanPostProcessor`** (AABPP):

1. **Фаза сбора метаданных (MergedBeanDefinitionPostProcessor):**
   - Метод `postProcessMergedBeanDefinition` инспектирует класс, находит поля и методы с `@Autowired`, `@Value` и `jakarta.inject.Inject`.
   - Метаданные кэшируются в объекте `InjectionMetadata` (набор дескрипторов `AutowiredFieldElement` и `AutowiredMethodElement`), что предотвращает повторные затраты на рефлексию при повторном создании бинов.
2. **Фаза наполнения (InstantiationAwareBeanPostProcessor):**
   - На шаге `populateBean()` вызывается метод `postProcessProperties()`.
   - AABPP извлекает кэшированный `InjectionMetadata` и разрешает зависимости через `beanFactory.resolveDependency(...)`.
   - Для полей рефлексивно вызывается `field.setAccessible(true)` и `field.set(bean, dependency)`.

### Почему `@Autowired` над `static` полями НЕ работает

Частая ошибка начинающих разработчиков:
```java
@Service
public class UtilityService {
    @Autowired // ОШИБКА: dependency будет равен null!
    private static DatabaseClient client;
}
```

#### Почему это происходит:
`AutowiredAnnotationBeanPostProcessor` — это процессор экземпляров бинов (Bean Post Processor). Он работает на фазе `populateBean()` **после создания конкретного экземпляра объекта**. Статические поля принадлежат самому классу (`java.lang.Class`), а не экземпляру в куче. Spring намеренно игнорирует статические поля при инъекции.

#### Как корректно внедрить в статический контекст (если нельзя обойти):
Использовать нестатический сеттер:
```java
@Service
public class UtilityService {
    private static DatabaseClient client;

    @Autowired
    public void setClient(DatabaseClient client) {
        UtilityService.client = client; // Запись в статическое поле из экземпляра
    }
}
```

### Продвинутый инструмент: `ObjectProvider<T>`

Начиная со Spring 4.3 / 5.0, интерфейс `ObjectProvider<T>` является лучшей альтернативой сырому `@Autowired(required = false)`:

```java
@Service
public class MetricsReporter {

    private final ObjectProvider<PushGatewayClient> clientProvider;

    public MetricsReporter(ObjectProvider<PushGatewayClient> clientProvider) {
        this.clientProvider = clientProvider;
    }

    public void report() {
        // 1. Безопасное получение (не бросает NoSuchBeanDefinitionException)
        PushGatewayClient client = clientProvider.getIfAvailable();
        if (client != null) {
            client.push();
        }

        // 2. Fallback со значением по умолчанию
        PushGatewayClient safeClient = clientProvider.getIfAvailable(NoOpClient::new);

        // 3. Итерация по потоку всех доступных бинов
        clientProvider.orderedStream().forEach(PushGatewayClient::flush);
    }
}
```

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> **`@Autowired`** — аннотация автоматического внедрения зависимостей (DI) в Spring.
> - Под капотом обрабатывается компонентом `AutowiredAnnotationBeanPostProcessor`.
> - Алгоритм поиска кандидата: **`byType` → `@Qualifier` → `@Primary` → `@Priority` → `byName`**. Если кандидатов больше одного — `NoUniqueBeanDefinitionException`.
> - Рекомендуется использовать **Constructor Injection** без явной аннотации `@Autowired` (обеспечивает иммутабельность `final`, независимость от Spring-рефлексии и простоту unit-тестов).
> - Поддерживает внедрение коллекций `List<T>` (с сортировкой по `@Order`) и `Map<String, T>`.
> - Не работает на `static`-полях.

### 4 каверзных вопроса с ответами

1. **Каков точный порядок разрешения зависимостей при работе `@Autowired`?**
   *Ответ:* Сначала Spring ищет все бины подходящего типа (`byType`). Если их несколько, отбираются бины с соответствующим `@Qualifier`. Если квалификатора нет, выбирается бин с аннотацией `@Primary`. Если `@Primary` нет, учитывается приоритет `@Priority`. Если приоритетов нет, в качестве последнего шанса сравнивается имя поля/параметра с именем бина (`byName`). Если однозначный кандидат не найден, бросается `NoUniqueBeanDefinitionException`.

2. **Почему `@Autowired` над статическим полем оставляет в нем `null`?**
   *Ответ:* Spring управляет жизненным циклом экземпляров объектов в памяти. Внедрение зависимостей выполняется через `BeanPostProcessor` в фазе `populateBean` конкретного экземпляра. Статические поля принадлежат объекту `Class` в ClassLoader, и Spring намеренно пропускает статические поля при инъекции.

3. **Что произойдет, если внедрить `List<PaymentService>`, если в контексте есть 3 бина этого интерфейса?**
   *Ответ:* Spring найдет все 3 бина и внедрит их в список. Если над классами бинов или их `@Bean`-методами указана аннотация `@Order(n)` или реализован интерфейс `Ordered`, элементы списка будут автоматически отсортированы в соответствии с заданным порядком (меньшее число — выше приоритет).

4. **В чём разница между `@Autowired(required = false)` и `ObjectProvider<T>`?**
   *Ответ:* При `@Autowired(required = false)` в поле просто записывается `null`, что чревато `NullPointerException`. `ObjectProvider<T>` предоставляет типобезопасный API (`getIfAvailable()`, `ifAvailable(Consumer)`, дефолтные значения через `Supplier`, ленивое получение и стриминг бинов через `orderedStream()`).

### Красные флаги (чего категорически нельзя говорить)
- ❌ *«Spring ищет бины для `@Autowired` в первую очередь по имени поля»* — в первую очередь поиск ВСЕГДА идет по типу (`byType`), а поиск по имени — это лишь финальный fallback.
- ❌ *«`@Autowired` обязателен над каждым конструктором в Spring Boot»* — если конструктор в классе один, аннотация `@Autowired` не требуется (начиная со Spring 4.3).
- ❌ *«Можно повесить `@Autowired` на `static`-поле, и оно нормально заинжектится»* — поле останется `null`.
- ❌ *«Field Injection через `@Autowired` работает быстрее Constructor Injection»* — Field Injection использует тяжелую рефлексию `setAccessible(true)` при каждом старте.
