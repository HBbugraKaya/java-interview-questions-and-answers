# Почему иммутабельный класс должен быть final

---

## 🟢 Junior Level

### 30-секундный ответ
Иммутабельный класс обязан быть объявлен с модификатором **`final`**, чтобы **на уровне компилятора и спецификации языка полностью заблокировать наследование**.

Если класс не пометить как `final`:
1. Сторонний разработчик или злоумышленник может создать подкласс (`class Child extends ImmutableClass`).
2. Добавить в этот подкласс **мутабельные поля и сеттеры**.
3. **Переопределить методы-геттеры**, заставив их возвращать динамически изменяемые или фальшивые значения.
4. В результате клиенты, принимающие объект по ссылке базового «иммутабельного» типа, получат мутабельный подкласс, что разрушит потокобезопасность, сломает кэши и приведёт к непредсказуемым ошибкам в продакшене.

---

### Наглядный пример: Взлом класса без модификатора `final`
```java
// ❌ ОШИБКА ПРОЕКТИРОВАНИЯ: класс не объявлен как final
public class Coordinates {
    private final int x;
    private final int y;

    public Coordinates(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() { return x; }
    public int getY() { return y; }
}

// 💥 Коварный подкласс ломает неизменяемость суперкласса:
public class MutableCoordinates extends Coordinates {
    private int mutableX;

    public MutableCoordinates(int x, int y) {
        super(x, y);
        this.mutableX = x;
    }

    public void setX(int newX) { 
        this.mutableX = newX; // Добавлен метод-мутатор!
    }

    @Override
    public int getX() { 
        return mutableX; // Переопределённый геттер возвращает изменяемое значение!
    }
}
```

#### Наглядная аналогия из жизни
Представьте запечатанный сургучной печатью конверт:
- Модификатор `final` у класса — это сургучная печать автора. Конверт нельзя вскрыть, дописать туда другой текст или подменить листок бумаги.
- Если сургучной печати нет, любой злоумышленник может вложить внутрь поддельный листок с тем же заголовком и отправить его дальше от вашего имени.

## 🟡 Middle Level

### 3 критических риска отсутствия `final` в Production

| Вектор риска | Механизм возникновения проблемы | Последствия в Production |
| :--- | :--- | :--- |
| **Уязвимость TOCTOU (Безопасность)** | Метод валидации проверяет объект, а параллельный поток изменяет поля подкласса между проверкой и вызовом сервиса | Обход проверок доступа, выполнение неавторизованных финансовых операций |
| **Повреждение ассоциативных структур (`HashMap`, `HashSet`)** | Подкласс переопределяет `hashCode()` и `equals()` с опорой на свои мутабельные поля | Потеря элементов в бакетах `HashMap`, неудаляемые объекты, утечка памяти в Heap |
| **Разрушение многопоточной безопасности (Thread Safety)** | Поля родителя защищены барьерами JMM §17.5, а добавленные поля подкласса — нет | Гонка данных, чтение дефолтных значений (`0`, `null`) или половинчатых данных |

---

### Примеры из архитектуры стандартной библиотеки JDK
Разработчики платформы Java сделали строго **`final`** абсолютно все базовые классы значений:
- `java.lang.String`
- Все классы-обёртки примитивов: `Integer`, `Long`, `Double`, `Boolean` и т.д.
- Числа произвольной точности: `BigDecimal`, `BigInteger`
- Все классы современной даты и времени пакета `java.time`: `LocalDate`, `LocalDateTime`, `Instant`, `Duration`, `Period`
- Записи (`record`, Java 16+) в байткоде **неявно компилируются со спецификатором `final`**.

---

### Взаимодействие с фреймворками: Spring AOP и Mockito
Исторически модификатор `final` вызывал сложности у библиотек кодогенерации:
1. **Spring AOP / CGLIB:** CGLIB генерирует прокси-класс на лету через создание подкласса (`Proxy extends TargetClass`). Для `final` классов CGLIB выбросит исключение. Решение в современном Spring Boot 3 — использование JDK Dynamic Proxies через интерфейсы.
2. **Mockito 2/3:** не умел создавать моки для `final` классов и методов. 
3. **Mockito 5+ (Spring Boot 3+):** полностью поддерживает мокирование `final` классов и методов «из коробки» благодаря плагину `mock-maker-inline` (на базе Java Agent ByteBuddy), динамически трансформирующему байткод в памяти.

## 🔴 Senior Level

### JIT C2-оптимизации: Devirtualization и Monomorphic Inlining
Модификатор `final` на уровне класса — это сильнейшая директива для оптимизатора HotSpot JIT (C2 Compiler):
1. **Девиртуализация вызовов (Devirtualization):**
   - Для обычного класса компилятор генерирует инструкцию `invokevirtual`, требующую обращения к таблице виртуальных методов (`vtable`) в заголовке объекта.
   - Если класс объявлен как `final`, JVM на этапе компиляции знает, что переопределение методов невозможно в принципе. Инструкция `invokevirtual` преобразуется в прямой машинный вызов (*direct call*), устраняя поиск адреса в памяти.
2. **Агрессивный инлайнинг (Monomorphic Inlining):**
   - Вызовы простых геттеров (`getX()`) полностью инлайнятся в машинный код вызывающего метода: вызов функции заменяется прямым обращением к смещению в памяти или значению в регистре CPU за 0 тактов.
3. **Устранение точек деоптимизации (Uncommon Traps):**
   - Если класс не `final`, JIT использует анализ иерархии классов (**Class Hierarchy Analysis — CHA**). Если загружается новый подкласс, скомпилированный машинный код выбрасывается (деоптимизация). Для `final` классов этот риск исключён.

---

### Архитектурные способы запрета наследования без слова `final`
Если по архитектурным причинам слово `final` нельзя использовать (например, требуется закрытое семейство классов внутри пакета):
- **Паттерн приватного конструктора (Effective Java, Item 17):**
  ```java
  public class SecureConfig {
      private final String apiKey;

      // Приватный конструктор запрещает вызов super() извне класса
      private SecureConfig(String apiKey) {
          this.apiKey = apiKey;
      }

      public static SecureConfig of(String key) {
          return new SecureConfig(key);
      }
  }
  ```
- **Пакетно-приватный конструктор (`package-private`):** разрешает подклассы только внутри своего пакета, защищая от внешних клиентов.
- **`sealed` классы (Java 17+):** `public sealed class MyClass permits SubA, SubB` — фиксирует строгий список разрешённых наследников.

## 4 Tricky Questions

### 1. Как объявление класса `final` помогает компилятору C2 избежать спекулятивного инлайнинга и деоптимизаций (Deoptimization Traps)?
**Ответ:**
Если класс не объявлен как `final`, компилятор C2 выполняет оптимизацию спекулятивно с помощью **Class Hierarchy Analysis (CHA)**: он проверяет, сколько подклассов загружено в данный момент. Если подкласс один, C2 инлайнит метод, но вставляет в машинный код скрытую проверку зависимости (**class dependency check / uncommon trap**). 
Если в рантайме динамически загрузится новый JAR или сработает `ClassLoader.loadClass()`, добавив подкласс, JVM признает скомпилированный код невалидным, выполнит деоптимизацию, сбросит код в режим интерпретатора и будет заново профилировать метод. 
Модификатор **`final`** даёт гарантию на уровне байткода: появление подклассов физически невозможно. Компилятор C2 навсегда компилирует метод по прямому адресу без накладных проверок и без риска деоптимизации.

---

### 2. Если у нефинального класса все методы объявлены как `final`, даёт ли это такую же гарантию безопасности, как объявление всего класса `final`?
**Ответ:**
Нет, это не даёт эквивалентной гарантии безопасности:
1. Подкласс всё ещё может добавить **новые методы-мутаторы** и собственное изменяемое состояние.
2. Подкласс может переопределить методы класса `java.lang.Object` (такие как `equals()`, `hashCode()`, `toString()`), если разработчик забыл объявить их `final` в базовом классе.
3. Клиентский код, проверяющий тип через рефлексию (`obj.getClass() == Base.class`), сломается при получении подкласса.
4. JIT-компилятор C2 не сможет выполнить глобальные оптимизации структуры объекта, которые возможны только для полностью закрытого типа.

---

### 3. Почему JPA-сущности (Hibernate) часто не могут быть `final`, и в чём фундаментальная разница между иммутабельностью сущности JPA и доменного объекта?
**Ответ:**
Hibernate использует динамическое проксирование на основе байткод-генерации (ByteBuddy / CGLIB) для реализации механизма ленивой загрузки (**Lazy Loading**). 
Прокси-объект ленивой связи наследуется от класса сущности (`EntityProxy extends Entity`). Если класс сущности объявить как `final`, Hibernate не сможет создать прокси-класс и выбросит ошибку при старте `SessionFactory`. 
Кроме того, сущность JPA по своей природе мутабельна и управляется контекстом персистентности (*Persistence Context* / *Dirty Checking*). Для моделирования неизменяемости в БД Hibernate предоставляет аннотацию `@Immutable` на уровне сущности, но на уровне Java-кода класс часто оставляют не-final ради проксирования.

---

### 4. Каким образом современный Mockito 5+ мокает `final` классы, если JVM на уровне байткода запрещает создание подклассов?
**Ответ:**
Mockito 5+ использует механизм **ByteBuddy Mock Maker Inline** на основе Java Instrumentation API (`java.lang.instrument`):
1. Mockito регистрирует виртуальный Java Agent при старте JVM.
2. При вызове `mock(FinalClass.class)` Mockito **не создаёт подкласс**.
3. Вместо этого агент переопределяет байткод самого целевого `FinalClass` прямо в оперативной памяти JVM, внедряя в начало каждого метода хук-перехватчик (*Method Dispatcher*).
4. Если вызов выполняется в рамках настроенного мока (`when(...).thenReturn(...)`), перехватчик возвращает стаб, иначе передаёт управление оригинальному телу метода.

## 🎯 Шпаргалка для интервью

### Главное о том, почему иммутабельный класс должен быть final
- **Защита контракта:** подкласс не сможет добавить сеттеры, переопределить геттеры или исказить логику `hashCode/equals`.
- **Защита безопасности:** блокирует атаки подмены данных (TOCTOU) в валидаторах и контроллерах.
- **Производительность:** позволяет C2-компилятору производить девиртуализацию вызовов (Devirtualization) и мономорфный инлайнинг методов без проверок vtable.
- **Стандарты JDK:** все ключевые типы (`String`, `Integer`, `BigDecimal`, `LocalDate`, `Record`) строго закрыты модификатором `final`.

### Красные флаги на собеседовании (Чего говорить нельзя)
- ❌ *«Если все поля помечены private final, класс final делать не обязательно»* — грубая ошибка: подкласс переопределит геттеры и сломает логику.
- ❌ *«Модификатор final у классов вреден для тестов, так как Mockito не может их мокать»* — устарело с Mockito 2.x, в современном Mockito 5+ (Spring Boot 3) мокирование `final` работает по умолчанию.
- ❌ *«Сделать все методы final — то же самое, что сделать класс final»* — нет, подкласс сможет добавить свои мутабельные методы и переопределить `equals/hashCode`.
