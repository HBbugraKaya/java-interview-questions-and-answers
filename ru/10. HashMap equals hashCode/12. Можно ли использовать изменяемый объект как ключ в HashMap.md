# Можно ли использовать изменяемый объект как ключ в HashMap

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
Технически язык Java позволяет использовать любой изменяемый (мутабельный) объект в качестве ключа `HashMap`, так как метод `put(K key, V value)` принимает любой класс, наследующий `Object`. Однако в профессиональной разработке это признано **грубейшим антипаттерном**.

Ключ в `HashMap` **обязан быть иммутабельным (неизменяемым)**. Если изменить состояние полей объекта-ключа после того, как он был помещен в `HashMap`:
1. Значение `key.hashCode()` изменится;
2. При вызове `map.get(key)` мапа вычислит **новый индекс корзины** и пойдет искать элемент в другом бакете;
3. В новом бакете элемента нет — метод вернет **`null`**;
4. Запись физически останется лежать в старом бакете навсегда («зомби-запись»), порождая утечку памяти.

Идеальные ключи для `HashMap` — неизменяемые классы: `String`, `Integer`, `UUID`, `LocalDate` или `record` (Java 16+).

---

### Демонстрация проблемы «сломанного ключа» на Java 21

```java
import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

public class MutableKeyTrapDemo {

    public static class MutableAccount {
        private String accountNumber; // Поле можно мутировать!

        public MutableAccount(String accountNumber) {
            this.accountNumber = accountNumber;
        }

        public void setAccountNumber(String accountNumber) {
            this.accountNumber = accountNumber;
        }

        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (!(o instanceof MutableAccount that)) return false;
            return Objects.equals(accountNumber, that.accountNumber);
        }

        @Override
        public int hashCode() {
            return Objects.hash(accountNumber);
        }
    }

    public static void main(String[] args) {
        Map<MutableAccount, String> accounts = new HashMap<>();

        MutableAccount acc = new MutableAccount("ACC-001");
        accounts.put(acc, "VIP-Client"); // Помещен в корзину на основе хеша "ACC-001"

        // Проверяем: до изменения ключ работает
        System.out.println("До мутации: " + accounts.get(acc)); // VIP-Client

        // ❌ МУТАЦИЯ КЛЮЧА:
        acc.setAccountNumber("ACC-999"); // Хеш-код объекта изменился прямо в куче!

        // ❌ КАТАСТРОФА:
        System.out.println("После мутации: " + accounts.get(acc)); // null!
        System.out.println("Размер мапы: " + accounts.size());     // 1 (элемент застрял внутри!)
    }
}
```

## 🟡 Middle Level

### Паттерн безопасной модификации: Delete-Mutate-Insert

Если бизнес-логика неизбежно требует модификации объекта, который уже используется в качестве ключа, единственный корректный способ — паттерн **«Удалить $\to$ Изменить $\to$ Добавить»**:

```java
public class SafeKeyMutationService {
    private final Map<MutableAccount, String> registry = new HashMap<>();

    public void updateAccountNumber(MutableAccount account, String newNumber) {
        // 1. Извлекаем старое значение и удаляем ключ ДО его мутации (по старому хешу!)
        String value = registry.remove(account);
        if (value == null) {
            throw new IllegalStateException("Аккаунт не найден в реестре");
        }

        // 2. Безопасно мутируем объект вне мапы
        account.setAccountNumber(newNumber);

        // 3. Вставляем обратно (будет вычислен новый хеш и новая корзина)
        registry.put(account, value);
    }
}
```

### Можно ли мутировать поля, НЕ входящие в `equals` и `hashCode`?

Технически — **да, можно**. Если поле не участвует в формулах `equals()` и `hashCode()`, его изменение не повлияет на вычисление корзины и поиск узла:

```java
public class UserKey {
    private final long userId; // Участвует в equals и hashCode (final!)
    private String lastAccessedIp; // НЕ участвует в equals и hashCode (мутабельное)
}
```

> [!WARNING]
> **Архитектурный риск (Code Smell):**  
> Наличие изменяемых полей в объекте-ключе вводит в заблуждение других разработчиков команды. При будущем рефакторинге кто-то может автоматически перегенерировать `equals/hashCode` через IDE или Lombok, включив все поля, что мгновенно сломает продакшен. Ключ должен быть чистым объектом-значением (Value Object).

## 🔴 Senior Level

### Анатомия утечки памяти: Ghost Entries в Heap

Когда ключ мутирует внутри `HashMap`, возникает специфический вид скрытой утечки памяти:

```
Куча (JVM Heap):
table[3] ──► [ Node: key (hash="ACC-001"), value="VIP" ] ◄── Застряло навсегда!
                ▲
                │ acc.setAccountNumber("ACC-999")
                │ Текущий hash(acc) указывает на table[11]!
```

#### Симптомы аномалии в продакшене:
1. **`map.get(key) == null`** и **`map.containsKey(key) == false`**;
2. **`map.remove(key) == null`** — элемент невозможно удалить штатным методом;
3. **Итератор `map.entrySet()` находит элемент!** При полном переборе мапы через `for (var entry : map.entrySet())` элемент отображается, так как итератор обходит все корзины подряд, игнорируя хеши;
4. **Непрерывный рост Old Generation:** старые записи никогда не будут собраны сборщиком мусора, пока жива сама `HashMap`.

---

### Альтернатива: `java.util.IdentityHashMap`

Если вам обязательно требуется хранить мапу по изменяемым объектам (например, при построении графа сериализации, отслеживании циклических зависимостей в Spring IoC или глубоком клонировании), стандартная `HashMap` заменяется на **`IdentityHashMap`**:

```java
Map<MutableAccount, String> identityMap = new IdentityHashMap<>();
MutableAccount acc = new MutableAccount("ACC-001");
identityMap.put(acc, "VIP");

acc.setAccountNumber("ACC-999"); // Мутируем!

// Сработает успешно! Возвращает "VIP":
System.out.println(identityMap.get(acc)); 
```

#### Почему это работает:
- `IdentityHashMap` полностью игнорирует переопределенные методы `equals()` и `hashCode()`;
- Индексация строится на нативном **`System.identityHashCode(acc)`** (хеш адреса из Mark Word, который не меняется при мутации полей);
- Сравнение ключей производится строго по ссылочной идентичности: **`k1 == k2`**.

---

### Архитектурный стандарт Java 21: Records для составных ключей

Для композитных ключей в современной Java стандартом де-факто является `record`:

```java
// Идеальный неизменяемый ключ:
public record OrderKey(long customerId, String regionCode) {
    // Компактный валидационный конструктор
    public OrderKey {
        Objects.requireNonNull(regionCode, "Region code must not be null");
    }
}
```
Все компоненты рекорда по умолчанию `private final`, геттеры не позволяют мутацию, а `equals` и `hashCode` генерируются компилятором на уровне байт-кода, полностью исключая человеческий фактор.

## 🎯 Шпаргалка для интервью

### 1. 30-секундный эссенс (Elevator Pitch)
Технически использовать мутабельный объект как ключ в `HashMap` можно, но категорически **не рекомендуется**. Если после добавления в мапу изменить поле ключа, участвующее в `hashCode()`, объект «потеряется»: при вызове `get()` мапа вычислит новый хеш и пойдет искать ключ в другой корзине, вернув `null`. Старый объект застрянет в памяти навсегда (Ghost Entry), порождая утечку памяти. Ключи `HashMap` обязаны быть строго неизменяемыми (`String`, `Integer`, `UUID`, `record`).

### 2. 4 каверзных вопроса с глубокими ответами

#### Вопрос 1: Что произойдет, если изменить поле объекта-ключа, которое НЕ входит в расчет `hashCode()` и `equals()`?
**Ответ:**
С точки зрения `HashMap` ничего не сломается: вычисление индекса корзины и посимвольное/полейное сравнение ключей в бакете опираются только на поля, участвующие в контракте. Метод `get()` продолжит находить элемент. Однако это считается грубым нарушением чистоты архитектуры (Code Smell), так как объект перестает быть самосогласованным Value Object, и случайный рефакторинг может привести к включению этого поля в контракт.

#### Вопрос 2: Как найти и удалить элемент из `HashMap`, если его ключ был мутирован после добавления?
**Ответ:**
Штатный вызов `map.remove(key)` не сработает, так как он ищет узел в новой корзине. Единственный способ удалить поврежденную запись — воспользоваться полным обходом коллекции через итератор:
```java
Iterator<Map.Entry<MutableKey, Value>> it = map.entrySet().iterator();
while (it.hasNext()) {
    Map.Entry<MutableKey, Value> entry = it.next();
    if (entry.getKey() == brokenKey) { // Сравнение по ссылке!
        it.remove(); // Безопасное удаление из текущей корзины
    }
}
```

#### Вопрос 3: В каких сценариях `IdentityHashMap` подходит для мутабельных ключей, и чем ее семантика отличается от `HashMap`?
**Ответ:**
`IdentityHashMap` идеально подходит для служебных задач анализа графов объектов (сериализация Jackson/Kryo, поиск циклов, отслеживание контекстов Spring BeanPostProcessor), где важен не логический эквивалент данных, а **физическая уникальность экземпляра в куче**. В `IdentityHashMap` ключи сравниваются через `==`, а хеш берется из `System.identityHashCode()`, поэтому мутация полей объекта никак не влияет на поиск.

#### Вопрос 4: Почему `StringBuilder` или `ArrayList` категорически нельзя использовать в качестве ключей `HashMap`?
**Ответ:**
`StringBuilder` вообще не переопределяет `equals` и `hashCode` (использует ссылочное равенство `Object`). Класс `ArrayList` переопределяет оба метода на основе своих элементов: при добавлении или удалении элемента из списка (`list.add("item")`) значение `list.hashCode()` динамически изменяется, что мгновенно разрушает позиционирование списка в `HashMap`.

---

### 3. Типичные ошибки и Red Flags

❌ **"Можно использовать изменяемый ключ, главное не вызывать сеттеры."**  
*Правильно:* Если объект мутабелен, сеттер может быть вызван случайно из другого потока или сторонней библиотеки. Неизменяемость должна гарантироваться структурой класса (`final`).

❌ **"Если ключ мутировал, `map.size()` уменьшится."**  
*Правильно:* Размер мапы не изменится. Элемент останется в старой корзине в виде «призрака».

❌ **"Использование JPA Entity с автоинкрементным ID в качестве ключа."**  
*Правильно:* До сохранения `id == null`, после сохранения `id` присваивается базой данных. Это классическая мутация ключа, ломающая коллекции.
