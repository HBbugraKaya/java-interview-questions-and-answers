# How to implement timeout for CompletableFuture

---

## 🟢 Junior Level

In asynchronous and distributed systems, every external operation (HTTP call, database query, messaging broker interaction) must have an explicit timeout deadline to prevent thread starvation and resource leaks.

The approach depends on the Java version:

### 1. In Java 9+ (Built-in Non-Blocking Methods)

Starting in Java 9, `CompletableFuture` provides two built-in asynchronous methods:

- **`orTimeout(long timeout, TimeUnit unit)`**: If the task does not complete within the specified duration, the future completes exceptionally with **`TimeoutException`**.
- **`completeOnTimeout(T fallbackValue, long timeout, TimeUnit unit)`**: If the timeout expires, the future completes normally with the provided **default fallback value** (without throwing an exception).

```java
CompletableFuture<String> future = externalServiceClient.fetchDataAsync();

// Approach A: Fail fast with TimeoutException after 3 seconds
future.orTimeout(3, TimeUnit.SECONDS)
      .exceptionally(ex -> "Fallback data on timeout");

// Approach B: Return fallback value after 3 seconds without exception
future.completeOnTimeout("Fallback data", 3, TimeUnit.SECONDS)
      .thenAccept(System.out::println);
```

### 2. In Java 8 (Manual Implementation via `ScheduledExecutorService`)

Java 8 lacked built-in non-blocking timeout support, requiring a background scheduler:

```java
// Single shared daemon scheduler across the application:
private static final ScheduledExecutorService SCHEDULER = 
    Executors.newScheduledThreadPool(1, r -> {
        Thread thread = new Thread(r, "cf-timeout-scheduler");
        thread.setDaemon(true);
        return thread;
    });

public static <T> CompletableFuture<T> withTimeout(CompletableFuture<T> target, long timeout, TimeUnit unit) {
    // 1. Schedule exceptional completion when deadline expires
    ScheduledFuture<?> timer = SCHEDULER.schedule(() -> {
        target.completeExceptionally(new TimeoutException("Operation timed out"));
    }, timeout, unit);

    // 2. If the task completes earlier, cancel the timer to prevent memory bloat
    target.whenComplete((res, ex) -> timer.cancel(false));

    return target;
}
```

## 🟡 Middle Level

### Difference Between `Future.get(timeout)` and `CompletableFuture.orTimeout()`

| Characteristic | `future.get(timeout, unit)` | `cf.orTimeout(timeout, unit)` |
| :--- | :--- | :--- |
| **Thread Blocking** | **Blocks** the calling OS thread | **Non-blocking** (reactive scheduler timer) |
| **Return Type** | Value `T` or throws checked exception | Returns modified `CompletableFuture<T>` |
| **Pipeline Integration** | Imperative `try-catch` | Seamless continuation in reactive pipeline |

### Critical Pitfall: Timeout Does NOT Terminate the Underlying Worker Task

When `orTimeout(3, TimeUnit.SECONDS)` fires:
1. The `CompletableFuture` state transitions into exceptionally completed (`TimeoutException`).
2. Downstream dependent stages (`thenApply`, `thenAccept`) receive the error signal or execute recovery stages (`exceptionally`).
3. **However, the original background task executing in the thread pool CONTINUES RUNNING!**

If that task was executing an intensive CPU algorithm or a blocking JDBC query without cancellation hooks, it will continue consuming CPU and connection resources. Under traffic spikes where timeouts cascade, unstopped background tasks cause catastrophic server saturation.

## 🔴 Senior Level

### Internal Architecture of `orTimeout` in Java 9+: The `Delayer` Singleton

Developers often worry whether calling `orTimeout()` spawns a dedicated timer thread per request.
The answer is **no, it does not**.

OpenJDK uses a private static internal class:
```java
static final class Delayer {
    static final ScheduledThreadPoolExecutor delayer;
    static {
        (delayer = new ScheduledThreadPoolExecutor(
            1, new DaemonThreadFactory())).setRemoveOnCancelPolicy(true);
    }
}
```
1. **Single Daemon Thread Per JVM**: One single background daemon thread manages priority delay queues for millions of scheduled timeout futures across the entire virtual machine.
2. **`setRemoveOnCancelPolicy(true)`**: When the primary future completes successfully before timeout expiration, an internal `Canceller` listener calls `scheduledFuture.cancel(false)`. Because `setRemoveOnCancelPolicy(true)` is enabled, the cancelled timer task is **immediately removed from the work queue**, eliminating queue accumulation and heap retention.

### Senior Pattern: Real Network I/O Cancellation on Timeout

To ensure server resources are freed upon timeout, you must explicitly bind timeout triggering to low-level socket or client cancellation:

```java
public CompletableFuture<Response> fetchWithHardTimeout(Request request, Duration timeout) {
    Call httpCall = httpClient.newCall(request); // OkHttp / Spring Reactive Call
    CompletableFuture<Response> promise = new CompletableFuture<>();

    // Execute asynchronous network call:
    httpCall.enqueue(new Callback() {
        @Override
        public void onResponse(Call call, Response response) { promise.complete(response); }
        @Override
        public void onFailure(Call call, IOException e) { promise.completeExceptionally(e); }
    });

    // Attach non-blocking timeout:
    return promise.orTimeout(timeout.toMillis(), TimeUnit.MILLISECONDS)
        .whenComplete((res, ex) -> {
            // When timed out or explicitly cancelled, abort physical socket connection!
            if (ex instanceof TimeoutException || promise.isCancelled()) {
                httpCall.cancel(); // Closes underlying TCP socket, releasing worker thread
            }
        });
}
```

## 4 Tricky Questions

### 1. Does `CompletableFuture.orTimeout()` create a new timer thread for each method call?

**Answer:**
**No, it does not.**
Internally, `CompletableFuture` delegates timeout scheduling to a static singleton class `Delayer`, which holds a single `ScheduledThreadPoolExecutor(1)` with a daemon thread for the entire JVM. This single thread maintains a priority queue of scheduled timeout tasks, ensuring minimal overhead even with hundreds of thousands of concurrent timeouts.

### 2. What happens to the scheduled timeout task if the target CompletableFuture completes successfully within 10 ms under a 60-second timeout?

**Answer:**
It is **immediately cancelled and removed from memory**.
When `orTimeout()` is registered, it attaches an internal `whenComplete` listener (`Canceller`). As soon as the target future completes, the listener cancels the scheduled future (`timerTask.cancel(false)`). Furthermore, because `Delayer` is configured with `setRemoveOnCancelPolicy(true)`, the cancelled task node is immediately purged from the scheduler's internal priority queue rather than waiting for its 60-second delay to elapse, preventing heap bloat.

### 3. Which exception is thrown if you invoke `.join()` on a CompletableFuture that timed out via `.orTimeout()`?

**Answer:**
Calling `.join()` throws an unchecked **`java.util.concurrent.CompletionException`**, whose underlying cause (`getCause()`) is **`java.util.concurrent.TimeoutException`**.
In contrast, calling `.get()` from the legacy `Future` interface throws a checked `java.util.concurrent.ExecutionException` wrapping the `TimeoutException`.

### 4. What is the fundamental behavioral difference between `.orTimeout()` and `.completeOnTimeout()`?

**Answer:**
- `.orTimeout(timeout, unit)` transitions the future into an **exceptional completion** state (`TimeoutException`). Subsequent transformation stages (`thenApply`, `thenAccept`) are skipped, routing execution directly to error-handling handlers (`exceptionally`, `handle`).
- `.completeOnTimeout(fallbackValue, timeout, unit)` transitions the future into a **normal successful completion** state with the provided fallback value. Downstream processing stages continue normally without entering error flows.

## 🎯 Interview Cheat Sheet

### Summary in 60 Seconds
- In Java 9+, use built-in non-blocking methods: `orTimeout()` (fails exceptionally with `TimeoutException`) and `completeOnTimeout()` (completes successfully with fallback value).
- In Java 8, use a shared singleton `ScheduledExecutorService` with daemon threads and cancel the scheduled task in `whenComplete`.
- All `orTimeout` calls across the JVM share a single daemon thread (`Delayer`) with negligible footprint.
- **Critical Catch**: Timeout marks the `CompletableFuture` failed, but **does not stop** the executing worker thread. Sockets and native tasks must be cancelled explicitly.

### Common Interview Traps
- Thinking `orTimeout()` interrupts or kills the background worker thread.
- Instantiating `new ScheduledThreadPoolExecutor` on each request in Java 8 (leads to thread exhaustion).
- Confusing `orTimeout` (error state) with `completeOnTimeout` (normal fallback state).
