# What is auto-configuration in Spring Boot

---

## 🟢 Junior Level

**Auto-Configuration** is Spring Boot's core mechanism that automatically creates, configures, and registers beans in the `ApplicationContext` based on:
1. **Classpath dependencies** (JARs detected in the classpath).
2. **Environment properties** (`application.properties` / `application.yml`).
3. **Existing user-defined beans** already registered in the container.

It embodies the **"Convention over Configuration"** philosophy: instead of forcing developers to write hundreds of lines of boilerplate XML or Java configuration, Spring Boot provides sensible, battle-tested defaults ("opinionated defaults") out of the box.

### Practical Example: Connecting to a Database

In traditional Spring Framework (pre-Spring Boot), connecting to PostgreSQL required manually declaring boilerplate configuration:

```java
// Traditional Spring (without Boot) — 30+ lines of manual boilerplate:
@Configuration
public class ManualDbConfig {

    @Bean
    public DataSource dataSource() {
        HikariConfig config = new HikariConfig();
        config.setJdbcUrl("jdbc:postgresql://localhost:5432/mydb");
        config.setUsername("user");
        config.setPassword("pass");
        return new HikariDataSource(config);
    }

    @Bean
    public LocalContainerEntityManagerFactoryBean entityManagerFactory(DataSource dataSource) { ... }

    @Bean
    public PlatformTransactionManager transactionManager(EntityManagerFactory emf) { ... }
}
```

In **Spring Boot**, the entire process requires only two steps:
1. Add `spring-boot-starter-data-jpa` and `org.postgresql:postgresql` to your build file (`pom.xml` / `build.gradle`).
2. Add connection properties to `application.yml`:
   ```yaml
   spring:
     datasource:
       url: jdbc:postgresql://localhost:5432/mydb
       username: user
       password: pass
   ```
Spring Boot detects `org.postgresql.Driver` and `HikariDataSource` on the classpath and automatically registers pre-configured `DataSource`, `EntityManagerFactory`, and `TransactionManager` beans.

### How to Disable Specific Auto-Configurations

If a particular auto-configuration interferes with custom requirements, it can be excluded explicitly:

**Via Annotation:**
```java
@SpringBootApplication(exclude = { DataSourceAutoConfiguration.class, SecurityAutoConfiguration.class })
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

**Via Configuration Properties:**
```yaml
spring:
  autoconfigure:
    exclude:
      - org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
      - org.springframework.boot.autoconfigure.security.servlet.SecurityAutoConfiguration
```

## 🟡 Middle Level

### The Auto-Configuration Startup Pipeline

Auto-configuration is coordinated by the `@SpringBootApplication` meta-annotation:

```
@SpringBootApplication
         │
         ├──> @Configuration
         ├──> @ComponentScan (Scans and registers user-defined @Component / @Service / @Bean)
         └──> @EnableAutoConfiguration
                   │
                   ▼
         AutoConfigurationImportSelector
                   │
                   ▼
         Reads Auto-Configuration Registry (.imports in Boot 3.x / spring.factories in Boot 2.x)
                   │
                   ▼
         Filters Configurations via @Conditional Annotations (ASM Bytecode Evaluation)
                   │
                   ▼
         Registers Surviving BeanDefinitions in ApplicationContext
```

### The `@Conditional` Annotation Suite

Auto-configuration works dynamically via conditional annotations. A configuration class or bean factory method runs **only if its specific conditions are satisfied**:

| Annotation | Matching Condition |
| :--- | :--- |
| **`@ConditionalOnClass(Foo.class)`** | The class `Foo` is present on the application classpath. |
| **`@ConditionalOnMissingClass`** | The specified class is **absent** from the classpath. |
| **`@ConditionalOnBean(Bar.class)`** | At least one bean of type `Bar` is **already registered** in the context. |
| **`@ConditionalOnMissingBean`** | **No bean** of that type exists yet (the foundation of developer overrides). |
| **`@ConditionalOnProperty`** | A specified property in `application.yml` matches an expected value. |
| **`@ConditionalOnWebApplication`** | The application is running in a web environment (Servlet or Reactive). |
| **`@ConditionalOnResource`** | A specific file resource is available on the classpath (e.g. `schema.sql`). |

### Real-World Example from Spring Boot: `JacksonAutoConfiguration`

```java
@AutoConfiguration
@ConditionalOnClass(ObjectMapper.class) // 1. Only runs if Jackson is on the classpath
public class JacksonAutoConfiguration {

    @Bean
    @Primary
    @ConditionalOnMissingBean // 2. Creates ObjectMapper ONLY if the developer did not define one!
    public ObjectMapper jacksonObjectMapper(Jackson2ObjectMapperBuilder builder) {
        return builder.createXmlMapper(false).build();
    }
}
```

> [!IMPORTANT]
> **The Golden Rule of Spring Boot:**
> `@ConditionalOnMissingBean` is the cornerstone of Spring Boot's non-invasive design. It translates to: *"If the user has not defined their own bean, provide this sensible default; otherwise, step aside completely"*.

### Diagnostics: The Condition Evaluation Report

To determine exactly why a bean was created or why an auto-configuration was skipped, run the application with the `--debug` flag:

```bash
java -jar myapp.jar --debug
```

Spring Boot outputs a comprehensive **`CONDITIONS EVALUATION REPORT`** in the console:
- **Positive matches:** Configurations whose conditions evaluated to `true`.
- **Negative matches:** Configurations that were skipped, along with the exact missing dependency or property (e.g. `@ConditionalOnClass did not find [org.apache.kafka.clients.producer.Producer]`).
- **Exclusions:** Configurations explicitly disabled by the user.

## 🔴 Senior Level

### Evolution of the Discovery Engine: Spring Boot 2.x vs Spring Boot 3.x

Prior to Spring Boot 2.7, auto-configuration classes were registered in `META-INF/spring.factories`:

```properties
# Spring Boot 2.x (Legacy): META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  com.example.autoconfigure.CustomDatabaseAutoConfiguration,\
  com.example.autoconfigure.CustomSecurityAutoConfiguration
```

Starting with **Spring Boot 2.7 and enforced strictly in Spring Boot 3.x**, auto-configurations are registered in dedicated `.imports` files:

```
# Spring Boot 3.x: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.example.autoconfigure.CustomDatabaseAutoConfiguration
com.example.autoconfigure.CustomSecurityAutoConfiguration
```

#### Why the Architecture Changed:
1. **GraalVM Native Image & Spring AOT:** The `.imports` file is a flat, unkeyed text list. Ahead-Of-Time (AOT) static analyzers can scan and process this list significantly faster during build-time native compilation without loading unnecessary classes.
2. **Cold Start Startup Performance:** Eliminates parsing overhead associated with large multi-key `Properties` files in enterprise applications with dozens of third-party starter libraries.

### Safe Classpath Evaluation via ASM (Avoiding `ClassNotFoundException`)

If Spring Boot used standard Java reflection (`Class.forName("org.postgresql.Driver")`) to evaluate `@ConditionalOnClass`, an absent driver JAR would throw a fatal `ClassNotFoundException` and crash JVM startup.

#### The Internal ASM Engine:
Spring Boot reads `.class` bytecode directly using **ASM bytecode parsing** via `SimpleMetadataReaderFactory` and `MetadataReader`. 
- Spring inspects bytecode constant pools and annotation descriptor strings without loading classes into the JVM's Metaspace.
- If a class referenced by `@ConditionalOnClass` cannot be resolved by the current `ClassLoader`, the condition evaluates to `false` and is pruned silently, with zero JVM exceptions.

### Ordering Invariant: Why `@ComponentScan` Must Run BEFORE Auto-Configuration

The timing between component scanning and auto-configuration is critical:
1. The container executes **`@ComponentScan` first**, discovering and registering all application-level `@Component`, `@Service`, `@Repository`, and `@Configuration` beans.
2. Only after application beans are indexed does `AutoConfigurationImportSelector` load auto-configuration definitions.
3. Because user beans are already registered, auto-configuration methods guarded by `@ConditionalOnMissingBean` evaluate the condition against the populated `BeanDefinitionRegistry`. If a user bean matches, the default auto-configuration gracefully backs off.

If auto-configurations were evaluated first, default beans would populate the context prematurely, and user `@Bean` declarations would either cause bean definition conflicts or be ignored.

### Coordinating Auto-Configuration Ordering: `@AutoConfiguration`

In Spring Boot 2.7+ and 3.x, auto-configuration classes should use `@AutoConfiguration` instead of standard `@Configuration`:

```java
package com.example.autoconfigure;

import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnClass;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration;
import org.springframework.context.annotation.Bean;

@AutoConfiguration(after = DataSourceAutoConfiguration.class) // Guaranteed to run AFTER DataSource is configured
@ConditionalOnClass(AuditClient.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public AuditClient auditClient(DataSource dataSource) {
        return new AuditClient(dataSource);
    }
}
```

## 4 Tricky Questions

### 1. How does Spring Boot evaluate `@ConditionalOnClass` without triggering a fatal `ClassNotFoundException` when the class is absent?
**Answer:**
Spring Boot avoids using reflection or `Class.forName()`, which would trigger a `ClassNotFoundException`. Instead, it uses the **ASM bytecode manipulation library** via Spring's `SimpleMetadataReaderFactory`.

ASM parses the raw byte array of `.class` files directly from disk or JAR archives. Spring inspects the class signature and constant pool at the bytecode descriptor level. If an annotated class name cannot be resolved by the active `ClassLoader`, the `OnClassCondition` evaluator catches the resolution failure internally and evaluates the condition to `false` without throwing an unhandled exception.

### 2. Why must `@ComponentScan` execute strictly before auto-configurations are evaluated?
**Answer:**
Because auto-configuration relies fundamentally on **`@ConditionalOnMissingBean`** to allow developers to override framework defaults.

If auto-configuration ran prior to `@ComponentScan`, Spring Boot would inspect an empty `BeanFactory`, assume no user beans exist, and instantiate all its default beans (e.g., default `ObjectMapper`, default `DataSource`). When `@ComponentScan` later encountered the developer's custom `@Bean` methods, it would either fail with a duplicate bean definition exception or fail to override the framework defaults. Running `@ComponentScan` first ensures user definitions take absolute precedence.

### 3. What is the fundamental difference between `spring.factories` in Spring Boot 2.x and `.imports` files in Spring Boot 3.x?
**Answer:**
- **Spring Boot 2.x (`META-INF/spring.factories`):** A single monolithic Java Properties file containing multiple SPI keys (`EnableAutoConfiguration`, `ApplicationListener`, `EnvironmentPostProcessor`, etc.). It requires full properties file parsing and reflection across all registered keys.
- **Spring Boot 3.x (`META-INF/spring/...AutoConfiguration.imports`):** Dedicated, unkeyed flat text files where each line is a fully qualified auto-configuration class name. This structure was designed for **GraalVM Native Image (AOT)** compilation: build tools can analyze and compile static reachability graphs much faster without parsing runtime properties.

### 4. How can you diagnose why a specific auto-configuration was skipped in a production environment?
**Answer:**
1. **CLI Debug Flag:** Launch the application with `--debug` or set `debug=true` in `application.properties`. Spring outputs the **Condition Evaluation Report** detailing Positive Matches, Negative Matches, and Exclusions.
2. **Spring Boot Actuator:** If Actuator is enabled, query the **`/actuator/conditions`** HTTP endpoint. It returns a structured JSON payload of all evaluated conditions, showing exactly which condition failed (e.g., missing class, property mismatch, or bean conflict).

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
> **Auto-Configuration** in Spring Boot is a mechanism implementing "Convention over Configuration". It automatically configures and registers beans based on classpath JARs, properties, and existing user beans.
> - Coordinated by `@SpringBootApplication` $\to$ `@EnableAutoConfiguration` $\to$ `AutoConfigurationImportSelector`.
> - In Spring Boot 3.x, auto-configuration classes are discovered via `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.
> - Uses `@Conditional` annotations (primarily `@ConditionalOnClass` and `@ConditionalOnMissingBean`) to ensure framework defaults step aside whenever a developer provides a custom bean.
> - `@ComponentScan` runs **before** auto-configuration to give developer beans precedence.
> - Debugged via `--debug` (Condition Evaluation Report) or `/actuator/conditions`.

### Key Conditional Annotations Summary

| Annotation | Evaluates | Typical Usage |
| :--- | :--- | :--- |
| **`@ConditionalOnClass`** | Classpath libraries | Check if driver/library JAR is imported |
| **`@ConditionalOnMissingBean`** | Active `ApplicationContext` | Allow user `@Bean` override |
| **`@ConditionalOnProperty`** | `application.yml` | Enable/disable feature via config flag |
| **`@ConditionalOnWebApplication`** | Web environment type | Configure Tomcat vs Netty |

### Red Flags (DO NOT Say)
- ❌ *"Auto-configuration instantiates every single bean found in starter libraries into memory."* (Only beans whose `@Conditional` checks pass are created).
- ❌ *"Spring Boot 3 still uses `spring.factories` to declare auto-configuration classes."* (Boot 3 uses `.imports` files under `META-INF/spring/`).
- ❌ *"Auto-configuration adds latency to every HTTP request."* (Auto-configuration executes strictly once during application startup).
- ❌ *"@ConditionalOnMissingBean checks whether a class exists in the classpath."* (It checks whether a bean instance exists in the `ApplicationContext`).
