# В чём разница между reduce() и collect()

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
Обе операции являются **терминальными операциями редукции (свёртки)**, преобразующими поток элементов в единый результирующий объект. Главное отличие — в **способе формирования результата**:

- **`reduce()`** реализует **иммутабельную редукцию (Immutable Reduction)**: на каждом шаге вычислений порождается **новый объект**. Предназначена для примитивов и неизменяемых типов данных (`int`, `long`, `BigInteger`, `Optional`).
- **`collect()`** реализует **мутабельную редукцию (Mutable Reduction)**: элементы потока последовательно добавляются («накапливаются») в **один существующий изменяемый контейнер** (например, `ArrayList`, `HashSet`, `StringBuilder`). Предназначена для сбора элементов в коллекции и сложные агрегаты.

---

### Сравнительный пример на Java 21

```java
import java.util.List;
import java.util.stream.Collectors;

public class ReduceVsCollectBasicsDemo {

    public static void main(String[] args) {
        List<String> items = List.of("яблоко", "банан", "груша");

        // 1. Использование reduce() для вычисления скалярного значения (числа, строки)
        int totalChars = items.stream()
            .mapToInt(String::length)
            .reduce(0, Integer::sum);
        System.out.println("Всего символов: " + totalChars); // 17

        // 2. Использование collect() для накопления в изменяемый контейнер (List)
        List<String> upperList = items.stream()
            .map(String::toUpperCase)
            .collect(Collectors.toList());
        System.out.println("Список: " + upperList);

        // 3. Конкатенация строк через collect(joining):
        String joined = items.stream()
            .collect(Collectors.joining(", ", "[", "]"));
        System.out.println("Строка: " + joined); // [яблоко, банан, груша]
    }
}
```

## 🟡 Middle Level

### Разбор сигнатур: `BiFunction` против `BiConsumer`

Ключевая архитектурная разница заложена в сигнатурах методов интерфейса `Stream<T>`:

#### 1. Сигнатура `reduce()`:
```java
T reduce(T identity, BinaryOperator<T> accumulator);
<U> U reduce(U identity, BiFunction<U, ? super T, U> accumulator, BinaryOperator<U> combiner);
```
- Аккумулятор является функцией `(U, T) -> U`: он принимает предыдущее значение, новый элемент и **возвращает новое значение**.

#### 2. Сигнатура `collect()`:
```java
<R> R collect(Supplier<R> supplier, BiConsumer<R, ? super T> accumulator, BiConsumer<R, R> combiner);
<R, A> R collect(Collector<? super T, A, R> collector);
```
- `supplier` создает контейнер (например, `ArrayList::new`).
- Аккумулятор является консьюмером `BiConsumer<R, T>`: он принимает существующий контейнер `R` и элемент `T`, добавляя элемент на месте (`(list, item) -> list.add(item)`). Он **возвращает `void`**.
- `combiner` объединяет два контейнера при параллельном исполнении (`list1.addAll(list2)`).

---

### Почему сбор в коллекции через `reduce()` — катастрофа

Попытка собрать элементы в `List` через `reduce()` — классическая ошибка новичков:

```java
// ❌ АНТИПАТТЕРН: Попытка мутабельной редукции через reduce
List<String> broken = items.parallelStream().reduce(
    new ArrayList<>(), // Общий identity!
    (list, item) -> { list.add(item); return list; },
    (l1, l2) -> { l1.addAll(l2); return l1; }
);
```

**Два фатальных недостатка:**
1. **Гонка данных в `parallelStream`:** Объект `identity` (`new ArrayList<>()`) создается один раз. При параллельном выполнении несколько рабочих потоков `ForkJoinPool` одновременно вызывают `.add()` на одном и том же несинхронизированном `ArrayList`, вызывая `ArrayIndexOutOfBoundsException` и потерю элементов.
2. **Квадратичная сложность $O(N^2)$ при создании копий:** Если пытаться создавать новый список на каждом шаге `new ArrayList<>(list)`, копирование элементов на каждой итерации дает алгоритмическую сложность $O(N^2)$ вместо $O(N)$ и колоссальную нагрузку на сборщик мусора (GC).

## 🔴 Senior Level

### Механика параллелизма: Tree Fold против Concurrent Reduction

В параллельном режиме (`parallelStream()`) механизмы работы `reduce()` и `collect()` кардинально различаются.

```
1. Стандартный collect() и reduce():
   Поток 1 ──► Accumulator 1 ──┐
                                ├──► Combiner ──► Финальный результат
   Поток 2 ──► Accumulator 2 ──┘

2. collect() с флагом Characteristics.CONCURRENT:
   Поток 1 ──┐
   Поток 2 ──┼──► ЕДИНЫЙ ConcurrentMap (combiner вообще не вызывается!)
   Поток 3 ──┘
```

1. **`reduce()`:**
   - Всегда требует чистого иммутабельного объединения.
   - Каждый поток вычисляет значение в своем контексте, а затем потоки объединяются вызовами `BinaryOperator combiner`.
   - Не может работать с единым разделяемым контейнером.

2. **`collect()` с `Characteristics.CONCURRENT`:**
   - Если коллектор имеет флаги `CONCURRENT` и `UNORDERED` (например, `Collectors.toConcurrentMap()`), рантайм `ReduceOps` создает **ровно один экземпляр контейнера** на весь параллельный стрим.
   - Все потоки пула `ForkJoinPool` пишут в один потокобезопасный контейнер (например, `ConcurrentHashMap`).
   - Метод `combiner` вообще **не вызывается**, что исключает затраты памяти на промежуточные контейнеры и их слияние.

---

### Анализ производительности: Конкатенация строк

Сравнение создания строки из $N = 100\,000$ элементов:

| Метод | Реализация | Временная сложность | Нагрузка на память (Eden GC) |
|---|---|---|---|
| `reduce((a, b) -> a + b)` | Создание нового `String` на каждом шаге | $O(N^2)$ | Гигантская (миллионы промежуточных `String`) |
| `collect(Collectors.joining())` | Накопление в единый буфер `StringBuilder` | $O(N)$ | Минимальная (один расширяемый массив `byte[]`) |

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> «`reduce()` предназначен для иммутабельной редукции (числа, логические операции, примитивные типы), где на каждом шаге порождается новое неизменяемое значение через `BiFunction`. `collect()` предназначен для мутабельной редукции (коллекции `List`, `Set`, `Map`, строки), где элементы добавляются в существующий контейнер через `BiConsumer`. Использование `reduce()` для мутации коллекций приводит к гонкам данных в parallelStream из-за разделяемого `identity` и падению скорости до $O(N^2)$. В `collect()` флаг `CONCURRENT` позволяет нескольким потокам писать в единую `ConcurrentMap` без фазы слияния через combiner.»

---

### Сводная матрица различий

| Критерий | `reduce()` | `collect()` |
|---|---|---|
| **Тип редукции** | Иммутабельная (порождает новые значения) | Мутабельная (накапливает в контейнер) |
| **Сигнатура аккумулятора** | `BiFunction<U, T, U>` (возвращает `U`) | `BiConsumer<R, T>` (возвращает `void`) |
| **Основное применение** | Сумма, произведение, мин/макс, boolean | `List`, `Set`, `Map`, `StringBuilder` |
| **Сложность при конкатенации** | $O(N^2)$ | $O(N)$ |
| **Поведение identity в parallel** | Разделяется между задачами (опасно мутировать) | `supplier` создает отдельный контейнер на задачу |
| **Флаг CONCURRENT** | Не поддерживается | Поддерживается (сбор в единый concurrent-контейнер) |

### Топ-4 каверзных вопроса на интервью

#### 1. В чем принципиальная разница между функциональными типами аккумуляторов в `reduce` и `collect`?
- В `reduce()` аккумулятор является чистой функцией `BiFunction<U, T, U>` (или `BinaryOperator<T>`), которая принимает текущее агрегированное состояние, новый элемент и возвращает **новое состояние**.
- В `collect()` аккумулятор является процедурой `BiConsumer<R, T>`, которая принимает существующий контейнер и элемент, модифицируя состояние контейнера на месте (возвращает `void`).

#### 2. Почему конкатенация строк через `reduce("", (a, b) -> a + b)` имеет сложность $O(N^2)$, а через `collect(joining())` — $O(N)$?
- Строки в Java неизменяемы (`immutable`). При `reduce` на шаге $i$ создается новая строка длиной $i$, требующая копирования всех предыдущих символов. Суммарное число операций: $\sum_{i=1}^N i = \frac{N(N+1)}{2} = O(N^2)$.
- `Collectors.joining()` внутри использует `StringBuilder` с расширяемым массивом символов/байтов, куда символы дописываются в конец за амортизированное время $O(1)$, что дает общую сложность $O(N)$.

#### 3. Как флаг `Characteristics.CONCURRENT` в `Collector` меняет алгоритм параллельного исполнения стрима?
- При обычном `collect()` (или `reduce`) каждый поток `ForkJoinPool` создает свой собственный независимый аккумулятор, а затем дерево задач попарно объединяет их методом `combiner()`.
- При наличии флага `CONCURRENT` (и `UNORDERED`) рантайм вызывает `supplier()` ровно один раз. Все параллельные потоки вызывают `accumulator()` над одним и тем же общим потокобезопасным объектом (например, `ConcurrentHashMap`), а метод `combiner()` вообще не вызывается.

#### 4. Что произойдет, если в `parallelStream.reduce()` мутировать объект `identity`?
- Произойдет разрушение многопоточного контракта и гонка данных (Race Condition). Ссылка на переданный объект `identity` передается во все ветви дерева задач. Если потоки начнут вызывать мутирующие методы (например, `list.add()`), произойдет повреждение внутренних полей объекта, потеря элементов или исключения вроде `ArrayIndexOutOfBoundsException`.

---

### Типичные ошибки и Red Flags
- 🚩 Попытка сбора стрима в `List` через `reduce(new ArrayList<>(), (l, x) -> { l.add(x); return l; })`.
- 🚩 Конкатенация строк через `reduce("", (a, b) -> a + b)` на больших объемах данных вместо `Collectors.joining()`.
- 🚩 Утверждение, что `reduce()` и `collect()` полностью взаимозаменяемы.
- 🚩 Забывание о примитивных стримах: использование `reduce(0, Integer::sum)` вместо `mapToInt().sum()`.
