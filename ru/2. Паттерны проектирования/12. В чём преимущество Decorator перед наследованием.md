# В чём преимущество Decorator перед наследованием

---

## 🟢 Junior Level

**Decorator (Декоратор / Обертка / Wrapper)** — это структурный паттерн проектирования, предназначенный для динамического добавления объекту новых обязанностей и функциональности без изменения его исходного кода и без использования наследования.

---

### Главная проблема наследования: Комбинаторный взрыв классов

Представим систему расчета стоимости кофе с опциональными добавками (молоко, сахар, сироп). Если использовать обычное наследование, для каждой возможной комбинации придется создавать отдельный класс:

```
Иерархия при наследовании:
                  Coffee
         ┌───────────┼───────────┐
     MilkCoffee  SugarCoffee  SyrupCoffee
         ┌───────────┴───────────┐
  MilkSugarCoffee         MilkSyrupCoffee
         │
  MilkSugarSyrupCoffee (для n добавок потребуется 2^n классов!)
```

При 10 различных добавках вам потребуется создать $2^{10} = 1024$ класса, что делает архитектуру абсолютно неподдерживаемой.

---

### Решение через Decorator

Вместо наследования применяется **композиция**: декоратор реализует тот же самый интерфейс, что и оборачиваемый объект, и хранит ссылку на него:

```java
// Общий интерфейс
public interface Beverage {
    String getDescription();
    double getCost();
}

// Базовый компонент
public class Espresso implements Beverage {
    public String getDescription() { return "Эспрессо"; }
    public double getCost() { return 150.0; }
}

// Базовый абстрактный декоратор
public abstract class BeverageDecorator implements Beverage {
    protected final Beverage wrapped;

    public BeverageDecorator(Beverage wrapped) {
        this.wrapped = wrapped;
    }
}

// Конкретные декораторы
public class MilkDecorator extends BeverageDecorator {
    public MilkDecorator(Beverage wrapped) { super(wrapped); }

    public String getDescription() { return wrapped.getDescription() + ", Молоко"; }
    public double getCost() { return wrapped.getCost() + 40.0; }
}

public class SugarDecorator extends BeverageDecorator {
    public SugarDecorator(Beverage wrapped) { super(wrapped); }

    public String getDescription() { return wrapped.getDescription() + ", Сахар"; }
    public double getCost() { return wrapped.getCost() + 10.0; }
}

// Использование: любая комбинация в runtime без создания новых классов!
Beverage order = new SugarDecorator(new MilkDecorator(new Espresso()));
System.out.println(order.getDescription() + " = " + order.getCost() + " руб.");
// Вывод: Эспрессо, Молоко, Сахар = 200.0 руб.
```

## 🟡 Middle Level

### Сравнительный анализ: Наследование против Декоратора

| Критерий | Наследование (Inheritance) | Декоратор (Decorator) |
|---|---|---|
| **Связывание (Binding)** | **Статическое (Compile-time):** поведение зафиксировано на этапе компиляции. | **Динамическое (Runtime):** поведение конструируется во время работы программы. |
| **Количество классов** | Растет экспоненциально ($2^n$ для $n$ опций). | Растет линейно ($n$ классов декораторов). |
| **Принцип единственной ответственности (SRP)** | Класс-наследник перегружен разнородными функциями. | Каждая новая обязанность изолирована в отдельном декораторе. |
| **Гибкость комбинаций** | Нельзя изменить поведение уже созданного объекта. | Можно оборачивать объект новыми слоями на лету. |

---

### Классический пример из Java SE: Пакет `java.io`

Вся подсистема ввода-вывода стандартной библиотеки Java построена на паттерне Decorator:

```java
InputStream stream = new BufferedInputStream(
                         new GZIPInputStream(
                             new FileInputStream("data.txt.gz")
                         )
                     );
```
- `FileInputStream` — базовый компонент (читает сырые байты из файла).
- `GZIPInputStream` — декоратор (на лету распаковывает сжатый поток).
- `BufferedInputStream` — декоратор (добавляет буфер в оперативной памяти для ускорения чтения).
Клиентский код работает с потоком через единый базовый интерфейс `InputStream`.

---

### Разграничение структурных паттернов: Decorator vs Proxy vs Adapter

| Паттерн | Цель использования | Интерфейс |
|---|---|---|
| **Decorator** | **Расширение функциональности:** добавление нового поведения и обязанностей объекту. | Сохраняет **тот же самый** интерфейс. |
| **Proxy** | **Контроль доступа:** ленивая инициализация, кэширование, проверка прав, логирование. | Сохраняет **тот же самый** интерфейс. |
| **Adapter** | **Согласование контрактов:** преобразование интерфейса одного класса в интерфейс другого. | **Меняет** интерфейс на несовместимый целевой. |

## 🔴 Senior Level

### Принцип Composition over Inheritance и хрупкость базового класса (Fragile Base Class)

Джошуа Блох в *Effective Java* (Item 18: «Отдавайте предпочтение композиции перед наследованием») указывает на фундаментальные риски наследования:
1. **Нарушение инкапсуляции:** Класс-наследник жестко зависит от деталей реализации методов базового класса. Если в новой версии базового класса изменится логика взаимодействия внутренних методов (self-use), поведение наследника может неожиданно сломаться.
2. **Проблема Decorator-оберток (The "SELF" Problem):**
   Обернутый базовый объект ничего не знает о внешнем декораторе. Если метод внутри оборачиваемого объекта вызывает свой собственный метод через `this.method()`, вызов пойдет в базовую реализацию, а **не через декоратор** (self-invocation bypass).
3. **Потеря идентичности объекта (Object Identity):**
   При использовании декораторов ссылка на оригинальный объект `original` и ссылка на декоратор `decorator` — это разные объекты в куче (`original != decorator`). Методы `equals()`, `hashCode()` и сравнение по `==` могут давать неожиданные результаты.

---

### Декораторы в веб-архитектуре и Spring Framework

В корпоративных приложениях паттерн Decorator применяется повсеместно:

#### 1. Сервлетные фильтры: `HttpServletRequestWrapper`
Если в фильтре требуется перехватить входящий JSON, расшифровать его или записать в лог, создается декоратор запроса:
```java
public class DecryptingRequestWrapper extends HttpServletRequestWrapper {
    public DecryptingRequestWrapper(HttpServletRequest request) {
        super(request);
    }

    @Override
    public ServletInputStream getInputStream() {
        // Возвращаем декорированный поток с дешифрацией
        return new DecryptingServletInputStream(super.getInputStream());
    }
}
```

#### 2. Spring AOP как декларативный мета-декоратор
Аннотации `@Transactional`, `@Cacheable`, `@Retryable` под капотом создают динамические прокси / декораторы вокруг бинов с помощью CGLIB или JDK Dynamic Proxy, инкапсулируя сквозную функциональность (cross-cutting concerns).

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «Главное преимущество **Decorator** перед наследованием заключается в следовании принципу **Composition over Inheritance** и предотвращении комбинаторного взрыва классов ($2^n$ классов при наследовании против $n$ классов декораторов). Декоратор позволяет добавлять обязанности объекту **динамически в runtime**, комбинируя поведение в любом порядке без изменения существующего кода (соблюдение принципа **Open/Closed**). В Java классическим примером является пакет `java.io` (`BufferedInputStream` поверх `FileInputStream`), а в Spring — обертки сервлетных запросов (`HttpServletRequestWrapper`) и инфраструктура AOP».

### 3–4 каверзных вопроса с ответами

1. **Чем паттерн Decorator отличается от Proxy, если оба реализуют один и тот же интерфейс и хранят ссылку на целевой объект?**
   - *Ответ:* Разница в семантическом назначении. **Decorator** используется для динамического добавления новой функциональности и расширения поведения (клиент обычно сам конструирует цепочку оберток). **Proxy** предназначен для контроля доступа к объекту (ленивая загрузка, безопасность, удаленный вызов, аудит) и, как правило, сам управляет жизненным циклом целевого объекта, скрывая его от клиента.

2. **Что такое проблема «SELF» (The SELF Problem) при использовании декораторов?**
   - *Ответ:* Декорируемый объект не имеет ссылки на внешний декоратор. Если метод внутри целевого объекта вызывает другой собственный метод через ключевое слово `this`, выполнение не пройдет через переопределенный метод декоратора. Это может приводить к пропуску добавленной декоратором логики.

3. **Почему пакет `java.io` часто критикуют, несмотря на эталонное использование паттерна Decorator?**
   - *Ответ:* Для выполнения простейшей операции (например, прочитать сжатую строку из файла с буферизацией) программист вынужден писать длинные громоздкие цепочки инстанцирования из 3–4 классов-декораторов (`new BufferedReader(new InputStreamReader(new GZIPInputStream(...)))`), что ухудшает читаемость кода и создает избыточные аллокации мелких объектов в куче.

4. **Как Decorator решает проблему хрупкого базового класса (Fragile Base Class)?**
   - *Ответ:* Наследник жестко зависит от внутреннего устройства базового класса и может сломаться при изменении его приватной логики. Декоратор зависит только от публичного контракта **интерфейса**, делегируя вызовы целевому объекту в виде черного ящика, что делает архитектуру слабосвязанной и устойчивой к изменениям.

---

### Типичные ошибки и Red Flags

- 🚩 **Использование наследования для добавления опциональных характеристик** (создание классов вроде `FastEncryptedCompressingFileStream`).
- 🚩 **Путаница между Decorator и Adapter** (декоратор никогда не меняет интерфейс объекта, в отличие от адаптера).
- 🚩 **Использование сравнения по ссылке `==`** между декорированным объектом и оригиналом (ломает логику в коллекциях и кэшах).
- 🚩 **Игнорирование Spring AOP** при попытке вручную писать декораторы для логирования, метрик или транзакций в enterprise-коде.
