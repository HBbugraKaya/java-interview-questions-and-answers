# What is recursive type bound

A **Recursive Type Bound** is a generic type declaration in which a type parameter is bounded by an expression containing the type parameter itself (e.g., `<T extends Comparable<T>>`). This construct expresses mutual type constraints, guaranteeing that instances of a type can interact exclusively with instances of their own type or compatible hierarchy members.

---

## 🟢 Junior Level

### Core Concept and Syntax
In standard bounds like `<T extends Number>`, the constraint states: *"T must be a subtype of Number"*. In a recursive bound like `<T extends Comparable<T>>`, the constraint states: *"T must be comparable to instances of its own type T"*:

```java
public class SortedBox<T extends Comparable<T>> {
    private final T value;

    public SortedBox(T value) {
        this.value = value;
    }

    public boolean isGreaterThan(T other) {
        // Guaranteed safe: other is guaranteed to be of type T!
        return value.compareTo(other) > 0;
    }
}

// Valid invocations:
SortedBox<Integer> intBox = new SortedBox<>(42); // Integer implements Comparable<Integer>
SortedBox<String> strBox = new SortedBox<>("A"); // String implements Comparable<String>

// ❌ Compilation Error: Object does not implement Comparable
// SortedBox<Object> objBox = new SortedBox<>(new Object());
```

## 🟡 Middle Level

### 1. Canonical JDK Implementation: `java.lang.Enum`
The most prominent recursive bound in the standard library is the base class for all enumerations:

```java
public abstract class Enum<E extends Enum<E>> implements Comparable<E>, Serializable {
    private final String name;
    private final int ordinal;

    public final int compareTo(E other) {
        return Integer.compare(this.ordinal, other.ordinal);
    }
}
```

When you declare an enum:
```java
public enum Season { WINTER, SPRING, SUMMER, AUTUMN }
```
The compiler desugars this into:
```java
public final class Season extends Enum<Season> { ... }
```
Because of `<E extends Enum<E>>`, `Season` implements `Comparable<Season>`. This guarantees at compile time that you can compare `Season.WINTER.compareTo(Season.SPRING)`, but cross-enum comparisons (`Season.WINTER.compareTo(OrderStatus.ACTIVE)`) are rejected as compilation errors.

### 2. The Self-Bounding Pattern for Polymorphic Fluent Builders
Recursive bounds enable the **Curiously Recurring Template Pattern (CRTP)**, allowing fluent builders in inheritance hierarchies to return the exact subclass type rather than the base builder:

```java
// Base builder with recursive self-type B:
public abstract class AbstractEntityBuilder<B extends AbstractEntityBuilder<B>> {
    protected Long id;

    @SuppressWarnings("unchecked")
    protected B self() {
        return (B) this; // Safely returns concrete subclass builder
    }

    public B withId(Long id) {
        this.id = id;
        return self(); // Returns B, not AbstractEntityBuilder
    }
}

// Concrete subclass builder:
public class UserBuilder extends AbstractEntityBuilder<UserBuilder> {
    private String username;

    public UserBuilder withUsername(String username) {
        this.username = username;
        return this;
    }

    public User build() {
        return new User(id, username);
    }
}

// Seamless method chaining across base and derived builder layers:
User user = new UserBuilder()
    .withId(100L)              // Inherited method returns UserBuilder!
    .withUsername("Alice")     // Subclass method accessible immediately!
    .build();
```

## 🔴 Senior Level

### The Subclassing Trap and the Relaxed Recursive Bound (`? super T`)
Consider a naive generic maximum element method:
```java
public static <T extends Comparable<T>> T naiveMax(List<T> list) { ... }
```

Now consider an everyday domain hierarchy:
```java
public class Animal implements Comparable<Animal> {
    protected int weight;
    @Override
    public int compareTo(Animal other) {
        return Integer.compare(this.weight, other.weight);
    }
}

public class Dog extends Animal {
    // Dog does NOT implement Comparable<Dog>!
    // Dog inherits Comparable<Animal> from its parent!
}
```

#### What Happens When Calling `naiveMax`:
```java
List<Dog> dogs = List.of(new Dog(), new Dog());
// ❌ COMPILATION ERROR:
// Inference variable T has incompatible bounds:
// equality constraints: Dog
// upper bounds: Comparable<Dog>
Animal maxDog = naiveMax(dogs);
```
Because `Dog` implements `Comparable<Animal>` rather than `Comparable<Dog>`, the strict recursive bound `<T extends Comparable<T>>` fails to resolve.

#### The Production Solution: Relaxed Recursive Bound
Using PECS, relax the bound to accept comparators implemented by any ancestor:
```java
public static <T extends Comparable<? super T>> T max(Collection<? extends T> coll)
```
Now, `max(dogs)` compiles cleanly because `Dog` satisfies `Comparable<? super Dog>` (specifically, `Comparable<Animal>`).

### The JDK Binary Compatibility Secret in `Collections.max`
In `java.util.Collections`, the method signature is declared as:
```java
public static <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll)
```

**Why include the seemingly redundant `<T extends Object & ...>`?**
This is a historic hack preserving **binary backward compatibility with Java 1.4**:
1. In Java 1.4, `Collections.max` returned raw `Object` with descriptor `(Ljava/util/Collection;)Ljava/lang/Object;`.
2. Under type erasure rules (JLS §4.6), a type parameter erases to its **first bound**.
3. If declared as `<T extends Comparable<? super T>>`, $T$ would erase to `Comparable`, changing the return descriptor to `(Ljava/util/Collection;)Ljava/lang/Comparable;`. This would have broken pre-Java 5 compiled classfiles with `NoSuchMethodError`.
4. Adding `Object &` forces the first bound to remain `Object`, ensuring that the compiled method descriptor in bytecode remained identical to Java 1.4 while granting compile-time generic safety to Java 5+ callers.

## 4 Tricky Questions

### 1. Why can't a developer create a fake enum subclass like `class Fake extends Enum<Fake>`?
**Answer:** The Java compiler (`javac`) explicitly forbids direct subclassing of `java.lang.Enum` in user source code: `"classes cannot directly extend java.lang.Enum"`. The only legal way to create an `Enum` subclass is via the `enum` keyword. 

However, at the type system level, the recursive bound `<E extends Enum<E>>` ensures that generic utilities like `EnumSet.noneOf(Class<E> elementType)` or `EnumMap` guarantee that all entries belong strictly to the same enum type family, preventing heterogeneous enum pollution.

### 2. Does the self-bounding pattern `Builder<B extends Builder<B>>` completely prevent passing an incorrect subclass type at compile time?
**Answer:** **No, it does not provide 100% compile-time protection.** 
A developer can make a copy-paste error and instantiate a builder with a sibling's type:
```java
public class SubBuilderA extends AbstractBuilder<SubBuilderA> { ... }
// Error: Programmer mistakenly passes SubBuilderA into SubBuilderB:
public class SubBuilderB extends AbstractBuilder<SubBuilderA> { ... }
```
The compiler accepts this because `SubBuilderA` satisfies `AbstractBuilder<SubBuilderA>`. Java's generic type system cannot enforce that $B$ is *strictly* the currently declaring class without runtime assertions (`getClass().isInstance(self())`) or sealed hierarchies (`sealed interface` / `permits` in Java 17+).

### 3. What does the recursive bound `<T extends Comparable<T>>` erase to in JVM bytecode?
**Answer:** It erases to its **first bound**, which is the raw interface **`java.lang.Comparable`**. 
In bytecode:
- A field `T item;` becomes `Comparable item;`.
- A method parameter `void process(T item)` becomes `void process(Comparable item)`.
- At call sites where members of $T$ are invoked, the compiler synthesizes explicit `checkcast` instructions to the caller's target type.

### 4. Why can't you declare a recursive bound using `super`, such as `<T super MyClass<T>>`?
**Answer:** Because the Java Language Specification (JLS §4.4) strictly prohibits the `super` keyword in type parameter declarations (`type parameters`). Lower bounds with `super` are permitted exclusively on wildcards (`<? super T>`). 

A type bound must specify an upper bound ceiling so the compiler knows what methods are safe to invoke on references of type $T$. A lower bound specifies a floor without a ceiling, leaving the compiler with only `java.lang.Object` methods, rendering method calls on $T$ impossible.

## 🎯 Interview Cheat Sheet

- **Definition:** A type parameter constrained by an expression containing the parameter itself (`<T extends Comparable<T>>`).
- **Purpose:** Enforces that a type parameter can only operate on or be compared with instances of its own type.
- **Top JDK Example:** `Enum<E extends Enum<E>>` prevents cross-enum comparisons (`Season.WINTER.compareTo(Status.ACTIVE)` fails compilation).
- **Subclassing Trap:** Strict `<T extends Comparable<T>>` breaks on subclasses inheriting a parent's comparator (`Dog extends Animal`).
- **Production Standard:** Always use relaxed recursive bounds: `<T extends Comparable<? super T>>`.
- **`Collections.max` Bytecode Secret:** The declaration `<T extends Object & Comparable<? super T>>` uses `Object &` to force type erasure to `Object` for 100% binary compatibility with Java 1.4.
- **Fluent Builders (CRTP):** `AbstractBuilder<B extends AbstractBuilder<B>>` allows base builder methods to return concrete subclass builder instances without manual casting.
