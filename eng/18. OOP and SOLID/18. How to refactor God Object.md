# How to refactor God Object

---

## 🟢 Junior Level

A **God Object** (also known as **The Blob Anti-Pattern**) is a monolithic class that knows too much, does too much, and accumulates control logic across multiple disparate subsystems. It typically aggregates thousands of lines of code, dozens of private mutable fields, and 50+ mixed methods spanning database persistence, business validation, network transport, security, and report formatting.

A God Object represents a simultaneous violation of nearly every SOLID principle, most notably the **Single Responsibility Principle (SRP)**.

### Real-World Analogy
Imagine a company where a single employee simultaneously acts as the Chief Executive Officer, Lead Accountant, Database Administrator, Delivery Courier, and Janitor:
- If this person falls ill, the entire enterprise halts instantly.
- The queue outside their office stretches around the block.
- They constantly make catastrophic errors because no single human can juggle 50 disjoint responsibilities.
- **The Solution:** Hire dedicated domain specialists and distribute operational duties cleanly.

---

### Key Symptoms of a God Object in Java Projects
1. **Source Bloat:** The file spans 2,000 to 5,000+ lines of dense procedural code.
2. **Generic Name Suffixes:** Class names end in `Manager`, `Processor`, `Handler`, `Engine`, or `Controller` (e.g., `AppManager`, `OrderProcessor`).
3. **Constructor Explosion:** The class injects 15–20 distinct collaborators or maintains dozens of mutable instance variables.
4. **Developer Paralysis:** Engineers express a "fear of touching" the class due to unpredicted regression bugs in production.

---

### The Fundamental 4-Step Refactoring Workflow

```
Step 1: [Safety Net]     ──► Write Characterization Tests around the God Object.
Step 2: [Clustering]     ──► Group methods & fields by business domain using LCOM analysis.
Step 3: [Extract Class]  ──► Extract cohesive clusters into independent, focused services.
Step 4: [Facade Bridge]  ──► Convert the God Object into a delegating Facade (Strangler Fig).
```

## 🟡 Middle Level

### The Incremental Refactoring Protocol (Strangler Fig Pattern)

Senior engineers **never** execute a "Big Bang" rewrite of a critical God Object. Rewriting a 5,000-line legacy class from scratch in a weekend guarantees fatal production defects. Instead, Martin Fowler's evolutionary refactoring protocol is applied:

#### Step 1: Characterization Tests (The Safety Net)
Before modifying a single line of production logic, establish automated black-box tests (**Golden Master / Approval Tests**). These tests record current inputs and outputs across all happy paths and edge cases, guaranteeing that subsequent refactoring preserves exact behavioral invariants.

#### Step 2: LCOM-Based Responsibility Clustering
Analyze the field-to-method dependency matrix to identify isolated clusters:

```
            Field:   dbUrl    templateEngine   smsApiKey   taxRates
Method:
calculateTax()         -             -             -         [X]   ──► Cluster 1: TaxCalculator
sendSms()              -             -            [X]         -    ──► Cluster 2: SmsNotificationService
saveOrder()           [X]            -             -          -    ──► Cluster 3: OrderRepository
renderPdf()            -            [X]            -          -    ──► Cluster 4: InvoicePdfRenderer
```

#### Step 3: Extract Role Interfaces (ISP)
Decouple calling clients from the monolithic class by introducing targeted role interfaces:
```java
public interface OrderPersistence { void save(Order order); }
public interface InvoiceGenerator { byte[] generatePdf(Order order); }
```
The legacy class temporarily declares `implements OrderPersistence, InvoiceGenerator`.

#### Step 4: The Strangler Fig Pattern (Delegating Facade)
Extract cluster functionality into a new Spring bean (`TaxCalculator`). The legacy `GodOrderManager` injects this new bean and delegates calls to it without breaking existing callers:

```java
@Service
public class GodOrderManager {
    // Injected new extracted domain service:
    private final TaxCalculator taxCalculator;

    public GodOrderManager(TaxCalculator taxCalculator) {
        this.taxCalculator = taxCalculator;
    }

    public BigDecimal calculateTax(Order order) {
        return taxCalculator.calculateTax(order); // 👈 DELEGATION
    }
}
```

Migrate callers incrementally to inject `TaxCalculator` directly. Once all callers are migrated and all methods extracted, delete `GodOrderManager.java`.

## 🔴 Senior Level

### Advanced Refactoring Challenges: Shared State, Transactions & JIT

#### 1. Eliminating Shared Mutable State: The Context Object Pattern
God Objects frequently share intermediate calculation results via private instance variables:
```java
// Anti-Pattern: Methods mutate shared instance state sequentially
private Order currentOrder;
private BigDecimal calculatedDiscount;

public void calculate() { this.calculatedDiscount = ...; }
public void finalizeOrder() { charge(this.currentOrder, this.calculatedDiscount); }
```
When extracting these methods into separate services, instance variables cannot be shared.
**Solution:** Introduce an immutable **Parameter / Context Object**:
```java
public record OrderProcessingContext(
    Order order,
    Customer customer,
    BigDecimal discount
) {}
```
Pass the context immutably through a pipeline of stateless domain services (*Pipeline Pattern*).

---

#### 2. Restructuring Transactional Boundaries (`@Transactional`)
In a monolithic God Object, a single `@Transactional` method coordinates everything:
```java
@Transactional
public void processAll() {
    orderRepo.save();
    inventoryRepo.decrementStock();
    userRepo.updateLoyaltyPoints();
    billingClient.chargeExternalGateway(); // 💥 Network I/O inside DB transaction!
}
```
When decomposing this logic into independent services:
- Retaining `@Transactional` across external HTTP calls causes HikariCP database connection pool starvation.
- **Senior Solution:** Apply the **Saga Pattern** or explicit application orchestration:
  1. Execute DB updates in isolated local transactions.
  2. Perform external network calls outside the database transaction boundary.
  3. If payment fails, trigger compensating transactions (`inventoryService.rollbackStock()`).

---

#### 3. Hardware & JVM Performance Restoration
In a 4,000-bytecode God Object:
- The HotSpot C2 JIT compiler refuses to inline complex methods due to bytecode size limits (`-XX:MaxInlineSize=35`).
- The processor incurs severe instruction cache misses.
- Decomposing the God Object into small classes (under 300 lines) dramatically improves CPU **L1 Instruction Cache (I-Cache)** hit rates and enables aggressive C2 devirtualization and method inlining.

## 4 Tricky Questions

### 1. How do you resolve a circular dependency between the legacy God class and a newly extracted service?
**Answer:**
A circular dependency (`GodClass <---> ExtractedService`) occurs when the extracted service needs a helper method or state that still resides in the un-refactored portion of the God class.

**Mitigation Strategies:**
1. **Dependency Inversion Principle (DIP):** The new service must not reference `GodClass`. Instead, it declares a callback interface (`OrderValidationCallback`). The `GodClass` implements that interface and passes itself as a listener.
2. **Domain Events:** Decouple direct method calls using Spring's `ApplicationEventPublisher`. The extracted service publishes an `OrderValidatedEvent`, which the God class handles asynchronously or via `@EventListener`.
3. **Extract Shared Context:** Extract the shared state into an independent data record (`OrderExecutionContext`) injected or passed into both components.

---

### 2. How do you refactor a static God Object (e.g., `GlobalUtils` with 3,000 lines of static methods)?
**Answer:**
Static utility methods cannot be mocked via standard interfaces or injected via constructor DI.
1. Group static methods by bounded context (`StringUtils`, `DateUtils`, `SecurityTokenUtils`).
2. Wrap static calls within instance-based Spring service beans backed by interfaces (e.g., `SystemTimeProvider implements TimeProvider` wrapping `System.currentTimeMillis()`).
3. Refactor client code to inject `TimeProvider` via constructor injection, eliminating static references.
4. Mark `GlobalUtils` as `@Deprecated(forRemoval = true)` and enforce Checkstyle / ArchUnit rules to block any new references in pull requests.

---

### 3. Why is an incremental refactoring safer than a "Greenfield Rewrite" from scratch?
**Answer:**
Complete rewrites from scratch fail in the overwhelming majority of enterprise projects (Brooks' *Second-System Effect*).

A legacy God Object that has operated in production for 5 years contains hundreds of obscure bug fixes, compliance patches, and edge-case integrations that exist nowhere in formal documentation. A greenfield rewrite inevitably drops these hard-won business edge cases. 

Using the **Strangler Fig Pattern** keeps existing business functionality continuously working in production while replacing internal mechanics slice by slice, supported by automated regression test suites.

---

### 4. How do you decompose a monolithic 30-case `switch(orderType)` block nested inside a God Object?
**Answer:**
Apply the Fowler refactoring recipe: **Replace Conditional with Polymorphism** via the **Strategy Pattern**:
1. Define a strategy interface:
   ```java
   public interface OrderProcessorStrategy {
       boolean supports(OrderType type);
       void process(OrderProcessingContext ctx);
   }
   ```
2. Extract each individual `case` branch into a dedicated, spring-managed strategy component (`SubscriptionOrderStrategy`, `GiftCardOrderStrategy`).
3. Inject the strategy collection into the coordinator:
   ```java
   @Service
   public class OrderOrchestrator {
       private final List<OrderProcessorStrategy> strategies;
       
       public void process(OrderType type, OrderProcessingContext ctx) {
           strategies.stream()
               .filter(s -> s.supports(type))
               .findFirst()
               .orElseThrow()
               .process(ctx);
       }
   }
   ```
4. The 30-case switch collapses into a single extensible, OCP-compliant routing statement.

## 🎯 Interview Cheat Sheet

### 30-Second Summary
- **Definition:** An anti-pattern class concentrating excessive responsibilities, mutable state, and business domains (severe SRP violation).
- **Core Strategy:** The **Strangler Fig Pattern** — incrementally extract functionality behind role interfaces and delegating facades without Big Bang rewrites.
- **Key Tools:**
  1. *Characterization Tests:* Establish a regression baseline before refactoring.
  2. *LCOM4 Analysis:* Identify cohesive method-field clusters.
  3. *Context Objects:* Replace shared private mutable fields with immutable records.
  4. *Strategy Pattern:* Replace massive nested `switch` statements with polymorphism.
- **Hardware Benefits:** Decomposing God Objects unblocks JIT C2 method inlining and maximizes CPU L1 instruction cache efficiency.

### Common Follow-up Questions
- *"How do you convince product managers to allocate time for God Object refactoring?"* → Quantify the cost using Git Code Churn analytics, incident frequency, and regression bug correlation. Demonstrate that refactoring reduces future feature delivery cycle times.
- *"What is a Golden Master Test?"* → An approval test capturing the exact snapshot of outputs for a wide matrix of legacy inputs, used to verify that refactoring introduces zero behavioral deviations.

### Red Flags (DO NOT Say)
- ❌ *"The fastest way to deal with a God Object is to delete it and rewrite everything from scratch."* (Extreme operational risk; loses edge-case business logic).
- ❌ *"Refactor the code first, and write tests afterward once the architecture is clean."* (Refactoring without an existing test harness is blind coding, not refactoring).
- ❌ *"Move all private methods into static helper classes to make the main class smaller."* (Merely redistributes low cohesion into untestable procedural dumping grounds).
