# Як незмінність впливає на продуктивність

---

## 🟢 Junior Level

### 30-секундна відповідь
Вплив незмінності (ім'ютабельності) на продуктивність — це **класичний інженерний компроміс (Trade-off)**:
- **Накладні витрати (мінуси):**
  1. Будь-яка «зміна» стану вимагає алокації нового об'єкта в купі (Heap) та копіювання полів.
  2. У циклах та при інтенсивному поетапному збиранні даних наївне створення об'єктів породжує квадратичну складність ($O(N^2)$) та навантажує Garbage Collector (*GC Pressure*).
- **Виграш у продуктивності (плюси):**
  1. **Lock-Free Concurrency:** читання із сотень паралельних потоків відбувається без блокувань, м'ютексів, черг очікування та перемикання контексту процесора.
  2. **Zero-Copy Architecture:** передача даних між шарами та сервісами не вимагає захисного копіювання (*Defensive Copying*).
  3. **Глибокі JIT-оптимізації:** C2-компілятор виконує інлайнінг, усунення алокацій (*Scalar Replacement*) та винесення інваріантів із циклів.

---

### Головне емпіричне правило проектування
```text
Локальне збирання / мутація в 1 потоці ──► Мутабельні буфери (StringBuilder, ArrayList)
Передача та читання між 10+ потоками   ──► Незмінні типи (String, Record, List.copyOf)
```

```java
// ❌ АНТИПАТЕРН: 10 000 алокацій у купі в циклі (O(N^2) по пам'яті)
String result = "";
for (int i = 0; i < 10_000; i++) {
    result += i;
}

// ✅ ПРАВИЛЬНИЙ ПІДХІД: Мутабельне локальне збирання -> Незмінний результат
StringBuilder sb = new StringBuilder(50_000);
for (int i = 0; i < 10_000; i++) {
    sb.append(i);
}
String finalResult = sb.toString(); // Зафіксували незмінний знімок
```

## 🟡 Middle Level

### 1. Лінійне масштабування при багатопоточності (Lock Contention)
У високонавантажених багатопотокових бекендах (Spring Boot, Netty, gRPC) головним «вбивцею» пропускної здатності (throughput) є не обчислення CPU, а **конкуренція за блокування (Lock Contention)**:
- Коли кілька потоків намагаються синхронізувати доступ до мутабельного об'єкта через `synchronized` або `ReentrantLock`, потоки, що програли, блокуються.
- Блокування переводить потік у режим сну ядра ОС через системні виклики `park()/unpark()`. Це спричиняє перемикання контексту процесора (**Context Switch**), що коштує від $1000$ до $2000$ тактів CPU плюс скидання конвеєра інструкцій.
- **Ім'ютабельні об'єкти читаються Lock-Free:** потоки ніколи не чекають один одного, забезпечуючи лінійне зростання RPS при збільшенні кількості ядер процесора.

---

### 2. JIT C2 Оптимізації: Constant Folding та Scalar Replacement
Оптимізуючий JIT-компілятор HotSpot C2 генерує машинний код, спираючись на незмінність полів:
1. **Constant Folding:** вирази над константними фінальними полями обчислюються компілятором заздалегідь і вшиваються в опкоди машинного коду.
2. **Loop Invariant Hoisting:** читання `final`-полів гарантовано виноситься за тіло циклу, оскільки значення поля не може мутувати.
3. **Escape Analysis & Scalar Replacement:** якщо короткоживучий незмінний об'єкт (наприклад, `Point`, `Tuple`, `Optional`) не залишає стек поточного методу, JIT-компілятор **повністю скасовує його алокацію в купі**: об'єкт розкладається на примітивні регістри CPU (*Scalar Replacement*), працюючи з максимальною швидкістю машинного коду C.

## 🔴 Senior Level

### Вартість алокацій у JVM: TLAB та Bump-the-Pointer
Існує міф: *«Створення об'єктів у Java дороге, як системний виклик `malloc()` у C»*. Для сучасних версій HotSpot це докорінно неправильно:

1. **TLAB (Thread-Local Allocation Buffer):**
   - Кожному потоку в області Eden молодого покоління виділяється персональний неперервний буфер пам'яті.
   - Алокація нового об'єкта в TLAB не вимагає міжпотокових блокувань та атомарних інструкцій шини пам'яті.
   - Вона зводиться до єдиної процесорної інструкції **Bump-the-Pointer** — простого інкременту регістру вказівника на розмір об'єкта:
     ```asm
     add r10, obj_size   ; зсуваємо вказівник вільної пам'яті TLAB
     ```
   - Створення об'єкта в TLAB займає **всього 1–2 такти CPU** (так само швидко, як алокація на стеку).
2. **Generational Hypothesis та «безкоштовне» очищення:**
   - 98% короткоживучих незмінних об'єктів помирають в Eden space до запуску першого збирання сміття.
   - Збирач сміття (Minor GC) копіює тільки *живі* об'єкти. Мертві об'єкти не скануються і не видаляються окремо: весь простір TLAB очищається миттєвим скиданням вказівника на початок буфера.

---

### Апаратний протокол MESI та усунення Cache Bouncing
На апаратному рівні багатоядерних процесорів:
- Запис у спільний мутабельний об'єкт переводить рядок кешу CPU у стан **Modified (M)** протоколу **MESI**.
- Ядро процесора розсилає сигнал **Invalidate** усім іншим ядрам, викликаючи промах кешу (**Cache Miss**) та апаратне перетягування кеш-ліній між ядрами (**Cache Bouncing**).
- Якщо в одній 64-байтній кеш-лінії опиняються мутабельні змінні різних ядер, виникає катастрофічне хибне розділення (**False Sharing**).
- **Ім'ютабельні структури даних:** кеш-лінії на всіх ядрах стабільно перебувають у стані **Shared (S)**. Читання відбувається паралельно з ультрашвидких кешів L1/L2 з нульовим трафіком по шині пам'яті.

---

### Усунення бар'єрів запису збирача сміття (GC Write Barriers)
У поколінських GC (G1, Parallel) зміна посилання в об'єкті старшого покоління (Old Gen) вимагає виконання інструкції **Card Table Write Barrier**: процесор повинен позначити відповідну картку в пам'яті як `dirty`.
- Довгоживучі незмінні об'єкти в Old Gen **ніколи не перезаписують свої поля**.
- Вони створюють рівно **0 брудних карт пам'яті**, мінімізуючи час сканування Card Table при кожній фазі *Young Collection STW*.

## 4 Tricky Questions

### 1. Чому виділення пам'яті під 1 000 000 короткоживучих незмінних об'єктів у Java часто швидше, ніж виклик `malloc()` у C++, і не викликає затримок Stop-the-World?
**Відповідь:**
У C++ стандартний `malloc()` звертається до глобальної купи процесу, виконуючи пошук вільного блоку в списках вільної пам'яті (freelist) та вимагаючи міжпотокової синхронізації (або звернення до lock-free арен пам'яті).
У Java завдяки **TLAB (Thread-Local Allocation Buffer)** кожен потік володіє приватним буфером в Eden. Алокація об'єкта в TLAB — це інструкція `add` (зсув вказівника *Bump-the-Pointer*) за 1–2 такти CPU без атомарних блокувань.
Більше того, якщо ці об'єкти помирають до збирача сміття, фаза *Young GC* взагалі не витрачає час на їх видалення: GC сканує тільки живі об'єкти, а область мертвих об'єктів обнуляється пакетно, роблячи вартість видалення сміття практично нульовою.

---

### 2. За яких умов JIT-компілятор C2 зазнає невдачі при спробі застосувати Escape Analysis та Scalar Replacement до незмінного об'єкта?
**Відповідь:**
Аналіз втечі (Escape Analysis) не може усунути алокацію об'єкта в таких ситуаціях:
1. **Global Escape:** посилання на об'єкт зберігається в статичне поле, поле іншого довгоживучого об'єкта або передається в інший потік.
2. **Arg Escape:** об'єкт передається параметром у метод, який C2 не зміг заінлайнити (наприклад, метод занадто довгий, поліморфний або нативний JNI-виклик).
3. **Розростання графа керування:** складні цикли з динамічними розгалуженнями, де компілятор не може на етапі компіляції довести скінченну кількість створюваних об'єктів.
4. **Масиви змінної довжини:** якщо розмір внутрішнього масиву невідомий під час компіляції.

---

### 3. Як протокол когерентності кешів MESI впливає на масштабованість читання незмінних структур у порівнянні з атоміками (`AtomicReference`) на 64-ядерному сервері?
**Відповідь:**
При читанні незмінного об'єкта рядки кешу L1/L2 на всіх 64 ядрах перебувають у стані **Shared (S)**. Читання відбувається локально без звернень до шини пам'яті.
Якщо ж ми використовуємо `AtomicReference` або мутабельні volatile-поля:
- Будь-який запис навіть одного потоку через CAS (`compareAndSet`) переводить кеш-лінію в стан **Modified (M)**.
- Процесор розсилає сигнал інвалідації всім іншим 63 ядрам.
- Коли сусідні ядра намагаються прочитати або оновити значення, вони отримують промах кешу (Cache Miss) і чекають на відповідь по шині міжпроцесорної взаємодії. Виникає ефект **вузького місця шини пам'яті (Cache Line Bouncing)**, і масштабованість системи падає з додаванням нових ядер.

---

### 4. В якій точці архітектурний оверхед від створення незмінних копій починає переважувати вигоду від потокобезпечності?
**Відповідь:**
Цей поріг настає у двох сценаріях:
1. **Високочастотні мутації великих графів даних в одному потоці:** якщо сервіс обробляє мільйони транзакцій на секунду, і кожне оновлення вимагає створення копії дерева розміром $N > 1000$ елементів без Structural Sharing, витрати на $O(N)$ копіювання пам'яті в Eden та подальший GC Churn багаторазово перевищать будь-які вигоди.
2. **Екстремальні вимоги до ультранизьких затримок (Ultra-Low Latency / HFT):** коли затримка SLA вимірюється мікросекундами, будь-які паузи Minor GC (навіть на 1–2 мс) є неприйнятними. У таких системах використовують попередньо виділені мутабельні кільцеві буфери (патерн LMAX Disruptor) та off-heap пам'ять.

## 🎯 Interview Cheat Sheet

### Баланс продуктивності: Мутабельність vs Незмінність
| Параметр | Мутабельний підхід | Незмінний підхід |
| :--- | :--- | :--- |
| **Однопотокове збирання** | 🟢 Надшвидко (in-place) | 🔴 Повільно (алокація $O(N)$ копій) |
| **Багатопотокове читання** | 🔴 Повільно (блокування, context switches) | 🟢 Надшвидко (Lock-Free, 0 блокувань) |
| **Захист від змін** | 🔴 Вимагає Defensive Copying | 🟢 Zero-Copy (пряме повернення посилання) |
| **Робота з CPU кешем** | 🔴 Інвалідація кешів, False Sharing | 🟢 Shared (S) стан у MESI |
| **Навантаження на GC** | Забруднення Card Table в Old Gen | Чистий Card Table, швидкий TLAB в Eden |

### Червоні прапорці на співбесіді (Чого говорити не можна)
- ❌ *«Незмінність завжди працює повільніше за мутабельність»* — у багатопотоковому середовищі незмінність на порядок швидша за рахунок усунення contention.
- ❌ *«Кожна алокація об'єкта в Java — це повільний системний виклик malloc»* — в Java працює TLAB з інструкцією Bump-the-pointer за 1 такт CPU.
- ❌ *«Для кращої продуктивності в мікросервісах усі DTO потрібно робити мутабельними»* — призводить до перегонів даних та необхідності постійного копіювання.
