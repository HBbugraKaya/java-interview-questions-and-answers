# Что такое Garbage Collection

---

## 🟢 Junior Level

**Garbage Collection (GC, Сборка мусора)** — это автоматическая подсистема управления оперативной памятью в виртуальной машине Java (JVM). Главная задача GC — непрерывно отслеживать динамически выделенную память в куче (Heap), находить объекты, которые больше не используются приложением, и безопасно освобождать занимаемую ими память без участия разработчика.

---

### Зачем нужен GC?
- **В языках с ручным управлением (C / C++):** Программист обязан вручную освобождать память (`free()` / `delete`). Человеческий фактор неизбежно приводит к двум фатальным проблемам:
  1. *Утечки памяти (Memory Leaks):* забыли вызвать `free()`, процесс съедает всю память и падает.
  2. *Висячие указатели (Dangling Pointers):* память освободили, но продолжили обращаться по старому адресу (повреждение данных, уязвимости безопасности).
- **В Java:** JVM берет управление памятью на себя, гарантируя типобезопасность и отсутствие висячих ссылок.

---

### Как GC определяет, что объект — «мусор»?
В Java используется алгоритм **Tracing (Трассировка достижимости)** от корней (**GC Roots**), а не подсчет ссылок (Reference Counting):
- **GC Roots** — это базовые гарантированно живые ссылки (локальные переменные в Stack фреймах всех потоков, статические поля загруженных классов, JNI-ссылки).
- Если от GC Roots по цепочке ссылок до объекта **нельзя добраться**, объект считается **недостижимым (Unreachable)** и подлежит уничтожению сборщиком мусора.

```java
public class GcEligibilityDemo {
    public static void main(String[] args) {
        Order order1 = new Order("A100"); // order1 достижим из Stack main
        Order order2 = new Order("B200"); // order2 достижим из Stack main

        order1 = order2; // Объект "A100" потерял единственную ссылку!
        // Теперь объект "A100" стал недостижимым и будет собран GC при следующей сборке.
    }
}
```

## 🟡 Middle Level

### Слабая гипотеза о поколениях (Weak Generational Hypothesis)

Практически все сборщики мусора в HotSpot опираются на эмпирический закон:
1. **Подавляющее большинство созданных объектов умирают очень быстро** (локальные DTO, итераторы, строки-конкатенации живут миллисекунды).
2. **Объекты, пережившие несколько сборок мусора, обычно живут очень долго** (пулы соединений, конфигурации, синглтоны Spring).

Исходя из этого, куча Heap разделена на два ключевых поколения:
- **Young Generation (Молодое поколение):** делится на **Eden** (рай для новорожденных объектов) и два полупространства выживших: **Survivor 0 (S0 / From)** и **Survivor 1 (S1 / To)**. Здесь сборка мусора (**Minor GC**) происходит часто и занимает единицы миллисекунд.
- **Old Generation (Старшее поколение / Tenured):** хранит долгоживущие объекты. Сборка здесь (**Major GC / Full GC**) происходит реже, но требует больше времени.

---

### Базовые алгоритмы сборки мусора

| Алгоритм | Принцип работы | Плюсы | Минусы | Где применяется |
|---|---|---|---|---|
| **Copying (Копирование)** | Живые объекты копируются из активной области в пустую соседнюю область. Исходная область очищается одним сбросом указателя. | Экстремально быстрый, нулевая фрагментация | Требует двойного запаса памяти | В Young Gen (Eden $\rightarrow$ Survivor) |
| **Mark-Sweep (Разметка и удаление)** | 1. Размечаются все живые объекты от GC Roots.<br>2. Непомеченные объекты удаляются, их адреса добавляются в Free-List. | Память не копируется, нет оверхеда на дублирование | **Сильная фрагментация памяти** (дыры между объектами) | Старые алгоритмы Old Gen (CMS) |
| **Mark-Compact (Разметка и уплотнение)** | 1. Разметка живых объектов.<br>2. Сдвиг (уплотнение) всех выживших объектов к началу региона памяти. | Устраняет фрагментацию, восстанавливает bump-the-pointer | Высокая длительность пауз STW (многопроходный алгоритм) | Full GC в G1, Parallel Old |

---

### Card Table и Write Barriers: оптимизация Minor GC

Чтобы собрать мусор в Young Generation, GC не должен сканировать гигабайты объектов в Old Generation в поисках ссылок на молодые объекты:
1. Память Old Gen логически нарезается на «карточки» размером **512 байт**.
2. Всякий раз, когда в коде происходит присвоение ссылки `oldObject.field = youngObject;`, JIT-компилятор вставляет инструкцию **Write Barrier**.
3. Write Barrier помечает соответствующую карточку в специальной битовой карте **Card Table** как «грязную» (**Dirty**).
4. Во время Minor GC сканируются только «грязные» карточки Old Gen, экономя до 99% времени сборки.

## 🔴 Senior Level

### Треугольник компромиссов GC (Trade-off Triangle)

Не существует универсально «лучшего» сборщика мусора. Архитектура GC всегда балансирует между тремя взаимоисключающими характеристиками:

```
                  Latency (Минимальные паузы)
                         ▲
                        / \
                       /   \
                      /     \
  Throughput ◄───────┴───────► Footprint
(Пропускная способность)     (Оверхед по памяти/CPU)
```

1. **Throughput (Пропускная способность):** процент времени CPU, затрачиваемый на полезную бизнес-логику приложения, а не на GC.
2. **Latency (Задержка / Паузы):** длительность пауз Stop-The-World (STW), влияющая на SLA ответа API.
3. **Footprint (Размер накладных расходов):** дополнительная оперативная память, требуемая для служебных структур GC (RSet, Card Table, метаданные указателей).

---

### Механика Stop-The-World (STW) и Safepoints

Во время определенных фаз сборки мусора потоки приложения (**Mutators**) обязаны приостановить свою работу, чтобы граф объектов не мутировал в процессе пересчета ссылок:
- Потоки не могут остановиться мгновенно в любой точке байткода. Они обязаны дойти до так называемого **Safepoint (Безопасная точка)**.
- JIT вставляет проверки Safepoint Poll на границах методов и в концах итераций циклов.

> ⚠️ **Критический дефект: Time-To-Safepoint (TTSP):**
> Если один поток крутится в тяжелом оптимизированном цикле со счетчиком (`Counted Loop` без safepoint poll), он может доходить до безопасной точки **несколько секунд**. В это время все остальные потоки приложения уже заморожены и ждут его. В логах это выглядит как секундная пауза GC, хотя сама сборка заняла 10 мс. Лечение: флаг `-XX:+UseCountedLoopSafepoints`.

---

### Палитра сборщиков мусора в HotSpot (Java 17–21+)

#### 1. Parallel GC (`-XX:+UseParallelGC`)
- **Фокус:** Максимальный **Throughput**.
- Сборка мусора в Young и Old Gen выполняется параллельно всеми ядрами CPU, но с полной блокировкой приложения (STW). Идеален для пакетной обработки данных (Batch, Big Data, Hadoop).

#### 2. G1 GC (`-XX:+UseG1GC`) — стандарт по умолчанию с Java 9
- **Фокус:** Баланс между Throughput и Latency.
- Куча разбита на 2048 динамических регионов (от 1 до 32 МБ). Сборщик инкрементально очищает регионы с наибольшим количеством мусора («Garbage-First»).
- Позволяет задать целевой ориентир максимальной паузы: `-XX:MaxGCPauseMillis=200`.

#### 3. ZGC (`-XX:+UseZGC`) / Generational ZGC (Java 21+)
- **Фокус:** Ультранизкие задержки (**Sub-millisecond Latency**, паузы $< 1$ мс).
- Способен управлять терабайтами памяти (до 16 ТБ). Все тяжелые фазы (разметка, перемещение объектов) выполняются параллельно с работой приложения.
- Основан на **Colored Pointers** (метаданные хранятся в старших битах 64-битного указателя) и **Load Barriers** (перехватчик при каждом чтении ссылки из памяти).
- *Цена:* Уступает G1 на 5–15% по пропускной способности из-за постоянной работы Load Barriers на CPU.

#### 4. Epsilon GC (`-XX:+UseEpsilonGC`)
- No-Op сборщик мусора: умеет только выделять память, но никогда её не очищает. При исчерпании кучи процесс падает с `OutOfMemoryError`. Применяется для ультрачистых performance-бенчмарков и serverless-функций (AWS Lambda), живущих несколько секунд.

---

### Опасность: Allocation Stall

Если скорость генерации мусора приложением (**Allocation Rate**) превышает скорость фоновой работы параллельного сборщика (ZGC или G1 Concurrent Mark), куча переполняется до завершения цикла очистки.
- Потоки приложения упираются в **Allocation Stall**: поток при попытке создать `new Object()` принудительно засыпает, ожидая, пока сборщик освободит хоть какой-то объем памяти. Это приводит к непредсказуемым просадкам latency на сотни миллисекунд.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «**Garbage Collection** в Java — это автоматическая система очистки недостижимых объектов в куче с помощью алгоритма трассировки от корней **GC Roots**. Она базируется на **слабой гипотезе о поколениях**: делении Heap на Young Gen (быстрые сборки Minor GC методом Copying) и Old Gen (редкие сборки Mark-Compact). Все сборщики мусора балансируют в треугольнике компромиссов **Latency ↔ Throughput ↔ Footprint**. В Java 9+ стандартом является **G1 GC**, обеспечивающий настраиваемые паузы, а для высоконагруженных систем с жестким SLA (< 1 мс) в Java 21+ применяется **Generational ZGC**, выполняющий перемещение объектов конкурентно через Load Barriers и Colored Pointers».

### 3–4 каверзных вопроса с ответами

1. **Почему в Java используется Tracing (GC Roots), а не Reference Counting (подсчет ссылок)?**
   - *Ответ:* Reference Counting (используемый, например, в Python или COM) имеет фатальный недостаток: он не способен обнаружить и удалить циклические ссылки (когда объект А ссылается на Б, а Б — на А, но внешних ссылок на них больше нет). В Java алгоритм Reachability Analysis стартует строго от внешних корней GC Roots, поэтому изолированные циклические острова объектов гарантированно определяются как мусор и вычищаются.

2. **Что такое Safepoint и почему Time-To-Safepoint (TTSP) может быть опаснее самой сборки мусора?**
   - *Ответ:* Safepoint — это точка в машинном коде, где поток обязан безопасно приостановить выполнение для выполнения фаз STW. Для начала GC необходимо, чтобы **все** потоки приложения пришли на Safepoint. Если один поток исполняет долгий цикл без проверок safepoint poll (например, длинный counted loop), он может задерживать начало GC на секунды. Все остальные потоки в это время уже остановлены. Задержка TTSP проявляется в логах как необъяснимая остановка приложения.

3. **За счет чего ZGC достигает пауз менее 1 миллисекунды даже на кучах в терабайты?**
   - *Ответ:* ZGC перенес самую долгую фазу — перемещение (эвакуацию) выживших объектов и обновление ссылок — из фазы Stop-The-World в параллельный режим работы (Concurrent). Для этого используются **Colored Pointers** (биты статуса прямо внутри адреса указателя) и **Load Barriers** (JIT-инструкции при каждом чтении ссылки): если поток обращается к объекту, который еще не успел переместиться, Load Barrier сам на лету обновляет ссылку и возвращает актуальный адрес без остановки всей JVM.

4. **Что такое Premature Promotion (преждевременное продвижение) и к чему оно приводит?**
   - *Ответ:* Это ситуация, когда короткоживущие объекты не успевают умереть в областях Survivor из-за их недостаточного размера или слишком низкого порога `MaxTenuringThreshold` и выталкиваются в Old Generation. Это приводит к быстрому засорению старшего поколения, частым вызовам дорогостоящих Mixed/Full GC и резкому падению пропускной способности системы.

### Типичные ошибки и Red Flags

- 🚩 **Вызов `System.gc()` в production-коде** (грубейший антипаттерн: провоцирует принудительный синхронный Full GC с остановкой всех потоков).
- 🚩 **Утверждение: «Java использует подсчет ссылок для GC»** (фундаментальное непонимание JVM).
- 🚩 **Слепая уверенность, что «ZGC всегда лучше G1»** (ZGC жертвует 5–15% CPU Throughput и требует больше памяти на служебные барьеры; для Batch processing Parallel или G1 эффективнее).
- 🚩 **Непонимание концепции Safepoint и причин возникновения пауз TTSP.**
