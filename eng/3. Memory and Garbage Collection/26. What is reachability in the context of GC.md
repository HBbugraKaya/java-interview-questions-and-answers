# What is reachability in the context of GC

---

## 🟢 Junior Level

**Reachability** defines the lifecycle status of an object in Java memory, determining whether the running application can access it through active reference paths originating from **GC Roots** (Garbage Collection Roots).

According to the Java Language Specification (JLS §12.6.1) and the `java.lang.ref` package, there are **5 official levels of object reachability**:

1. **Strongly Reachable:** The object can be reached via a chain of normal, direct references without traversing any `Reference` wrapper objects (`Order order = new Order()`). The Garbage Collector never reclaims strongly reachable objects.
2. **Softly Reachable:** The object is not strongly reachable, but can be reached by traversing a `SoftReference`. Retained by the JVM until memory becomes scarce prior to an `OutOfMemoryError`.
3. **Weakly Reachable:** The object is neither strongly nor softly reachable, but can be reached via a `WeakReference`. Guaranteed to be reclaimed during the **very next Garbage Collection cycle**.
4. **Phantom Reachable:** The object has completed its lifecycle (finalized or ready for destruction), but has an active `PhantomReference` registered to monitor post-mortem cleanup. Calling `.get()` **always returns `null`**.
5. **Unreachable:** No active references of any kind lead to the object. The object's memory is eligible for immediate physical deallocation.

## 🟡 Middle Level

### 1. Reference Strength & Reclamation Lifecycle

| Reachability Level | Wrapper Class | Value of `.get()` | Eviction Timing | Primary Production Use Case |
|:---|:---|:---|:---|:---|
| **Strong** | Direct reference | Direct instance | Never, while rooted | Core application domain models |
| **Soft** | `SoftReference<T>` | Instance or `null` | Low heap memory (before OOME) | Memory-sensitive caches |
| **Weak** | `WeakReference<T>` | Instance or `null` | Next GC run (Minor or Major) | `WeakHashMap`, metadata mapping |
| **Phantom** | `PhantomReference<T>` | **Always `null`** | After object reclamation | Off-heap cleanup, `Cleaner` API |

```java
// 1. Direct Strong Reference
User user = new User("Alice");

// 2. Soft Reference (Memory-sensitive fallback)
SoftReference<User> softUser = new SoftReference<>(user);

// 3. Weak Reference (Short-lived association)
WeakReference<User> weakUser = new WeakReference<>(user);

// 4. Phantom Reference (Post-mortem tracking via queue)
ReferenceQueue<User> refQueue = new ReferenceQueue<>();
PhantomReference<User> phantomUser = new PhantomReference<>(user, refQueue);

// Severing the strong link transitions reachability:
user = null;
```

### 2. The `ReferenceQueue` and `Reference Handler` Daemon

When the Garbage Collector discovers that an object's reachability status has degraded:
1. The GC clears the internal `referent` pointer inside `SoftReference` or `WeakReference`.
2. The JVM appends the `Reference` instance to an internal JVM linked list (`jdk.internal.ref.Reference.pending`).
3. A high-priority HotSpot system daemon thread, **`Reference Handler`** (`MAX_PRIORITY = 10`), continuously unlinks references from the pending list and enqueues them into the associated user-level **`ReferenceQueue`**.
4. Application background threads poll `ReferenceQueue.poll()` to perform cleanup operations (such as releasing native buffers or file descriptors) asynchronously without blocking the GC.

```
[GC Detects Reachability Degradation]
                 │
                 ▼
[HotSpot Native pending List]
                 │
                 ▼ (Reference Handler Thread, Priority = 10)
[Application ReferenceQueue]
                 │
                 ▼ (Application poll() loop)
[Deterministic Native Resource Release]
```

### 3. Modern Resource Disposal: `java.lang.ref.Cleaner` (Java 9+)

Because `Object.finalize()` was deprecated in Java 9 (and deprecated for removal in Java 18+), modern code leverages **`java.lang.ref.Cleaner`**, which wraps `PhantomReference` to provide deterministic cleanup without object resurrection:

```java
package com.example.resources;

import java.lang.ref.Cleaner;

public class NativeBufferHolder implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();

    private final long nativeAddress;
    private final Cleaner.Cleanable cleanable;

    public NativeBufferHolder(int sizeBytes) {
        this.nativeAddress = allocateNativeMemory(sizeBytes);
        // CRITICAL: CleaningAction must NEVER capture 'this' (the outer instance)!
        this.cleanable = CLEANER.register(this, new CleaningAction(this.nativeAddress));
    }

    private static class CleaningAction implements Runnable {
        private final long address;

        CleaningAction(long address) {
            this.address = address;
        }

        @Override
        public void run() {
            freeNativeMemory(address);
        }
    }

    @Override
    public void close() {
        cleanable.clean(); // Idempotent explicit cleanup
    }

    private static native long allocateNativeMemory(int bytes);
    private static native void freeNativeMemory(long address);
}
```

## 🔴 Senior Level

### 1. The SoftReference Lifespan Formula in HotSpot

`SoftReference` instances are not cleared randomly. HotSpot calculates their retention lifespan based on elapsed time since last access and the volume of free heap space:

$$\text{Retention Lifespan (ms)} = \text{Free Heap Space (in MB)} \times \text{-XX:SoftRefLRUPolicyMSPerMB}$$

- **Default Flag:** `-XX:SoftRefLRUPolicyMSPerMB=1000` (1,000 milliseconds = 1 second per megabyte of free heap).
- **Example:** On a server with 16 GB of free heap, a soft reference will be retained for:
  $$16{,}384\text{ MB} \times 1{,}000\text{ ms} \approx 16{,}384\text{ seconds } (\sim 4.5\text{ hours})$$
- **High-Load Failure Mode:** Under a sudden burst of memory-intensive requests, available heap drops rapidly. To prevent an imminent `OutOfMemoryError`, HotSpot is forced to trigger an emergency Stop-The-World Full GC to clear all soft references simultaneously. This leads to **GC thrashing** and severe latency spikes. Consequently, production systems avoid `SoftReference` caches in favor of bounded explicit caches (e.g., Caffeine W-TinyLFU).

### 2. The `WeakHashMap` Memory Leak Trap

`java.util.WeakHashMap` stores its **keys as `WeakReference`**, but holds its **values as strong references**:

```java
// ❌ SILENT PRODUCTION MEMORY LEAK:
Map<SessionKey, SessionContext> sessionMap = new WeakHashMap<>();

class SessionContext {
    private final SessionKey key; // Strong back-reference to key!

    public SessionContext(SessionKey key) {
        this.key = key;
    }
}

SessionKey key = new SessionKey("usr_1024");
sessionMap.put(key, new SessionContext(key));
key = null; // External strong reference removed
```

**Why the entry is NEVER garbage collected:**
1. The map's internal `Entry` holds a strong reference to `Value` (`SessionContext`).
2. `SessionContext` holds a strong back-reference to `SessionKey`.
3. An unbroken chain of strong references exists: `WeakHashMap -> Entry -> Value -> Key`.
4. The key never drops to weakly reachable, so the GC never clears the weak reference, preventing the entry from ever being removed from the table.

---

### 3. Object Resurrection and Why `PhantomReference.get()` Returns `null`

Under legacy finalization (`Object.finalize()`), an object in the *Finalizer Reachable* state could resurrect itself by storing its own reference into an active static field:

```java
// ⚠️ THE OBJECT RESURRECTION ANTI-PATTERN
@Override
protected void finalize() {
    GlobalCache.RESURRECTED_LIST.add(this); // Object brought back to life!
}
```

This caused severe memory corruption, non-deterministic lifecycles, and delayed garbage collection.

To eliminate this flaw entirely:
- **`PhantomReference.get()` unconditionally returns `null`** by JVM design.
- Application code can never retrieve a reference to the referent through a `PhantomReference`.
- The phantom reference serves strictly as an immutable notification that the underlying heap object has already been fully reclaimed and finalized, making it safe to free associated off-heap native resources.

## 4 Tricky Questions

### 1. Why is `PhantomReference.get()` designed to unconditionally return `null`, and how does this eliminate the Object Resurrection flaw of `finalize()`?

**Answer:**
Under legacy finalization, an object undergoing finalization could execute arbitrary bytecode inside `finalize()` and assign `this` to an active GC Root (e.g., a static collection). This "resurrected" the dead object back into a strongly reachable state, confusing the Garbage Collector and resulting in delayed memory leaks and undefined object states.

`PhantomReference.get()` hardcodes a `return null` at the JVM level. Because the caller cannot obtain an object pointer to the underlying referent, it is impossible to resurrect the instance. The phantom reference serves purely as a post-mortem cleanup notification sent to a `ReferenceQueue` after the referent has already been finalized and reclaimed.

---

### 2. How can `WeakHashMap` cause a severe memory leak even though all its keys are wrapped in `WeakReference`?

**Answer:**
`WeakHashMap` wraps its keys in `WeakReference`, but its internal hash table array (`Entry[]`) maintains **strong references** to the stored values (`entry.value`).

If a stored value contains a direct or indirect reference back to its own key:
$$\text{WeakHashMap} \longrightarrow \text{Entry} \stackrel{\text{strong}}{\longrightarrow} \text{Value} \stackrel{\text{strong}}{\longrightarrow} \text{Key}$$
A cyclic strong reference path is formed from the active map directly into the key. Because of this strong reference chain originating from the map itself, the key never transitions to the *Weakly Reachable* state. The Garbage Collector cannot clear the key's weak reference, and the map entry remains pinned in memory forever.

---

### 3. Why is using `SoftReference` for high-throughput in-memory caching considered an anti-pattern in production microservices?

**Answer:**
`SoftReference` clearing is non-deterministic and driven by memory starvation. According to HotSpot's `SoftRefLRUPolicyMSPerMB` algorithm, soft references remain pinned in memory as long as free heap is abundant, accumulating millions of stale entries over hours.

When a sudden traffic spike occurs, free heap is rapidly depleted. The JVM responds by triggering emergency Stop-The-World Full Garbage Collection cycles to sweep all softly reachable objects across the entire heap. This induces severe **GC thrashing** (multiple consecutive STW pauses lasting seconds), causing request timeouts and cascading circuit-breaker trips. Modern microservices use bounded in-memory cache libraries (such as Caffeine) that enforce explicit capacity limits (TinyLFU / LRU eviction) and time-to-live policies without relying on JVM memory pressure.

---

### 4. What is the subtle memory leak bug when using `java.lang.ref.Cleaner` with a non-static inner class or lambda expression?

**Answer:**
When registering a cleaning action with `java.lang.ref.Cleaner`:
```java
cleaner.register(this, () -> freeNativeMemory(this.nativeHandle)); // ❌ LEAK!
```
If the cleanup `Runnable` is implemented as an anonymous class, non-static inner class, or a lambda referencing instance fields (`this.nativeHandle`), the compiler automatically generates a hidden, synthetic strong reference to the outer instance (`this`).

The `Cleaner` internal registry holds a strong reference to the `Runnable`, which in turn holds a strong reference to `this`. As a result, the target object is kept strongly reachable by the `Cleaner` itself, preventing the object from ever becoming phantom reachable. The cleaning action is never triggered, and both the Java object and the native resource leak permanently. The cleaning task **must always be a static class** or static lambda capturing only primitive handles.

## 🎯 Interview Cheat Sheet

### 30-Second Summary
> "Reachability defines an object's accessibility status from GC Roots across five official tiers: **Strong** (standard references, never collected), **Soft** (evicted only under heap pressure based on `SoftRefLRUPolicyMSPerMB`), **Weak** (reclaimed on the very next GC cycle, used in `WeakHashMap`), **Phantom** (`.get()` always returns `null`, used with `ReferenceQueue` for safe native cleanup), and **Unreachable** (physically collected). Modern Java uses `java.lang.ref.Cleaner` instead of deprecated `finalize()`, ensuring safe post-mortem cleanup without object resurrection."

### Common Follow-up Questions
- *"At what stage is a WeakReference enqueued vs a PhantomReference?"* → A `WeakReference` is cleared and enqueued *before* finalization when the object is deemed weakly reachable; a `PhantomReference` is enqueued *after* finalization and heap reclamation have completed.
- *"What is Finalizer Reachable?"* → An intermediate legacy state where an object has no strong, soft, or weak references, but has a non-trivial `finalize()` method that has not yet been executed by the `Finalizer` daemon thread.
- *"How does Caffeine Cache avoid the problems of SoftReference?"* → Caffeine uses deterministic memory bounds, Window TinyLFU eviction, and ring buffers for asynchronous eviction events, avoiding GC thrashing.

### Red Flags (DO NOT Say)
- ❌ *"SoftReference and WeakReference are cleared at the same time."* (Weak references are cleared on the next GC run; Soft references survive until low heap memory).
- ❌ *"PhantomReference allows you to resurrect an object before it is reclaimed."* (Phantom reference `.get()` unconditionally returns `null` to eliminate resurrection).
- ❌ *"Using `WeakHashMap` guarantees that entries will never leak."* (If the value holds a strong back-reference to the key, the entry leaks permanently).
