# What thread pool is used by default for async methods

---

## 🟢 Junior Level

By default, all asynchronous methods in `CompletableFuture` called without an explicit `Executor` parameter (e.g., `supplyAsync(supplier)`, `runAsync(runnable)`, `thenApplyAsync(fn)`) execute on the shared JVM-wide thread pool: **`ForkJoinPool.commonPool()`**.

```java
// Executes on a worker thread from ForkJoinPool.commonPool:
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    System.out.println("Thread: " + Thread.currentThread().getName());
    return "Data";
});
```

### Core Properties of `ForkJoinPool.commonPool()`

1. **Parallelism Level**: Defaults to the number of available logical CPU cores minus one:
   $$\text{Parallelism} = \max(1, \text{Runtime.getRuntime().availableProcessors()} - 1)$$
   On an 8-core CPU, the common pool defaults to 7 active worker threads.
2. **Daemon Threads**: All threads in `commonPool` are created as **daemon threads**. If the `main` thread terminates and no other non-daemon threads remain active, the JVM will exit immediately, abandoning any incomplete background tasks.
3. **Work-Stealing Architecture**: Each worker thread maintains a double-ended task queue (deque). Workers push and pop their own sub-tasks from the head (LIFO order for CPU cache locality), and steal pending tasks from the tail of busy peers' queues (FIFO order) when idle.

## 🟡 Middle Level

### The "Tragedy of the Commons" (Noisy Neighbor Hazard)

`ForkJoinPool.commonPool()` is a global JVM singleton shared across multiple components:
- Default `CompletableFuture.*Async` methods.
- Java Parallel Streams (`collection.parallelStream()`).
- Internal mechanisms of various third-party libraries.

If a developer executes a long-running computation or blocks a few threads on network I/O, **all asynchronous operations across the entire application stall in queues**.

### Thread Starvation from Blocking I/O

`ForkJoinPool` is engineered specifically for **fast, compute-intensive, CPU-bound workloads** that do not block threads:

```java
// DANGEROUS: Blocking I/O in the shared common pool
CompletableFuture.supplyAsync(() -> {
    // Blocking HTTP call with 500ms latency:
    return restTemplate.getForObject("https://api.external.com/rates", Rates.class);
});
```

On a 4-core machine, `commonPool` has only 3 worker threads. If 3 concurrent requests perform blocking I/O, all worker threads are parked in `I/O wait`. The entire JVM suffers **Thread Starvation**, freezing parallel streams and other asynchronous tasks.

### Sizing and Inspecting `commonPool`

Parallelism can be customized at JVM launch using a system property:
```bash
-Djava.util.concurrent.ForkJoinPool.common.parallelism=16
```
To check current pool parallelism at runtime:
```java
int parallelism = ForkJoinPool.getCommonPoolParallelism();
```

## 🔴 Senior Level

### The Hidden Fallback: `ThreadPerTaskExecutor`

`CompletableFuture` does **not always** use `ForkJoinPool.commonPool()`. The OpenJDK source contains the following logic:

```java
private static final boolean USE_COMMON_POOL = 
    (ForkJoinPool.getCommonPoolParallelism() > 1);

private static final Executor ASYNC_POOL = USE_COMMON_POOL ?
    ForkJoinPool.commonPool() : new ThreadPerTaskExecutor();

private static final class ThreadPerTaskExecutor implements Executor {
    public void execute(Runnable r) { new Thread(r).start(); }
}
```

> [!CAUTION]
> In containerized deployments (Docker/Kubernetes) configured with 1 core (`resources.limits.cpu <= 1`), or when setting `-Djava.util.concurrent.ForkJoinPool.common.parallelism=0` (or 1), `getCommonPoolParallelism() > 1` evaluates to `false`!
> `CompletableFuture` switches to **`ThreadPerTaskExecutor`**, spawning an unbounded, dedicated native OS `Thread` for **every single asynchronous call**. Under load, this causes thread explosion and `java.lang.OutOfMemoryError: unable to create new native thread`.

### Bulkhead Pattern: Enterprise Thread Pool Segregation

In production enterprise architectures, using `commonPool` for business logic is an anti-pattern. Dedicated pools must be isolated using the Bulkhead Pattern:

```java
@Configuration
public class ThreadPoolConfiguration {

    // 1. Dedicated pool for blocking I/O (Databases, REST/SOAP clients)
    @Bean(name = "ioExecutor")
    public ExecutorService ioExecutor() {
        return new ThreadPoolExecutor(
            16, 64, 60L, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(1000),
            new ThreadFactoryBuilder().setNameFormat("io-pool-%d").setDaemon(true).build(),
            new ThreadPoolExecutor.CallerRunsPolicy() // Graceful backpressure
        );
    }

    // 2. In Java 21+, Virtual Threads are ideal for blocking I/O
    @Bean(name = "virtualThreadExecutor")
    public ExecutorService virtualThreadExecutor() {
        return Executors.newVirtualThreadPerTaskExecutor();
    }
}
```

## 4 Tricky Questions

### 1. What happens to tasks running in `ForkJoinPool.commonPool()` if the `main` thread terminates and no other user threads are active?

**Answer:**
The JVM **exits immediately**, abruptly halting incomplete tasks without running standard `finally` cleanup blocks.
Threads in `ForkJoinPool.commonPool()` are initialized with `daemon = true`. The Java Virtual Machine terminates as soon as all non-daemon user threads have finished. To ensure tasks run to completion, the calling thread must explicitly wait via `join()` or keep at least one non-daemon thread alive.

### 2. In a Kubernetes container with `resources.limits.cpu: 1`, you invoke `CompletableFuture.supplyAsync(...)` 1,000 times concurrently without an explicit executor. What happens?

**Answer:**
The application spawns **1,000 native OS threads**!
Because there is only 1 CPU core, `ForkJoinPool.getCommonPoolParallelism()` returns $\le 1$. `CompletableFuture` triggers its internal fallback to `ThreadPerTaskExecutor`, invoking `new Thread(task).start()` on every async invocation. Rather than throttling via a worker queue, the JVM attempts to allocate 1,000 OS thread stacks (~1 GB RAM), crashing the Linux kernel scheduler or throwing `java.lang.OutOfMemoryError: unable to create new native thread`.

### 3. Can you dynamically change the size of `ForkJoinPool.commonPool()` at runtime?

**Answer:**
**No, runtime reconfiguration of `commonPool` parallelism is impossible.**
The `commonPool` instance is an immutable static singleton whose attributes (`parallelism`, `threadFactory`, `exceptionHandler`) are read from system properties **once during the initialization of the `ForkJoinPool` class**. The only mechanism to adjust its sizing is via the JVM startup parameter `-Djava.util.concurrent.ForkJoinPool.common.parallelism=N` before class loading.

### 4. Why can chaining `cf.supplyAsync(task, customExecutor).thenApplyAsync(fn)` destabilize an application if `customExecutor` is omitted from the second call?

**Answer:**
Because in `CompletableFuture`, **the executor is not inherited downstream**.
While `supplyAsync` executes inside `customExecutor`, the subsequent parameterless `.thenApplyAsync(fn)` call defaults back to `ForkJoinPool.commonPool()`. If `fn` performs blocking I/O or long-running computations, that workload unintentionally escapes into the shared JVM common pool, starving parallel streams and other services.

## 🎯 Interview Cheat Sheet

### Summary in 60 Seconds
- Default executor is `ForkJoinPool.commonPool()`.
- Default sizing: $\text{CPU Cores} - 1$ (minimum 1).
- All common pool worker threads are daemons (`daemon = true`).
- Designed strictly for **non-blocking, CPU-bound computations**. Blocking I/O leads to JVM-wide thread starvation.
- If parallelism $\le 1$ (1-core containers), `CompletableFuture` falls back to `ThreadPerTaskExecutor`, spawning a new native thread per task.
- In production, always supply a custom `ThreadPoolExecutor` or Virtual Threads (`Executors.newVirtualThreadPerTaskExecutor()`).

### Common Interview Mistakes
- Claiming `commonPool` has threads equal to the exact number of CPU cores (it is $\text{cores} - 1$, reserving 1 core for the calling thread).
- Assuming `ForkJoinPool` automatically expands thread counts when threads block on ordinary I/O (it only expands for `ManagedBlocker` tasks).
- Assuming subsequent `*Async` stages automatically inherit the upstream stage's custom executor.
