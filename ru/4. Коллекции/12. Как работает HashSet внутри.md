# Как работает HashSet внутри

---

## 🟢 Junior Level

### 1. Архитектурная суть

Класс **`HashSet`** в Java не реализует собственную низкоуровневую структуру данных для хранения элементов. Вместо этого он является легковесной обёрткой над стандартным **`HashMap`**:

```java
public class HashSet<E> extends AbstractSet<E> implements Set<E>, Cloneable, java.io.Serializable {
    private transient HashMap<E, Object> map;
    
    // Фиктивный объект-заглушка для значения каждого ключа
    private static final Object PRESENT = new Object();

    public HashSet() {
        map = new HashMap<>();
    }
}
```

Все элементы, добавляемые в `HashSet`, сохраняются в качестве **ключей** внутренней `HashMap`. Поскольку `HashMap` гарантирует уникальность своих ключей, `HashSet` автоматически получает свойство уникальности элементов.

В качестве **значения (value)** для всех ключей используется одна и та же статическая ссылка-пустышка — `PRESENT` (`new Object()`).

```
HashSet: ["Apple", "Banana", "Cherry"]
  │
  ▼
HashMap (Внутреннее представление):
  ┌──────────┬─────────────────┐
  │   Key    │      Value      │
  ├──────────┼─────────────────┤
  │ "Apple"  │ ──► PRESENT     │
  │ "Banana" │ ──► PRESENT     │
  │ "Cherry" │ ──► PRESENT     │
  └──────────┴─────────────────┘
```

---

### 2. Базовые операции и их реализация

Все публичные методы `HashSet` просто делегируют вызовы внутреннему экземпляру `map`:

```java
// Добавление элемента:
// put() возвращает null, если ключ новый, или предыдущее значение (PRESENT), если ключ уже был.
public boolean add(E e) {
    return map.put(e, PRESENT) == null;
}

// Проверка наличия:
public boolean contains(Object o) {
    return map.containsKey(o);
}

// Удаление:
// remove() возвращает удаленное значение (PRESENT) или null, если ключа не было.
public boolean remove(Object o) {
    return map.remove(o) == PRESENT;
}

// Очистка и размер:
public int size() {
    return map.size();
}

public void clear() {
    map.clear();
}
```

### Временная сложность основных операций

| Операция | Средний случай | Худший случай (все коллизии) | Примечание |
| :--- | :--- | :--- | :--- |
| `add(E e)` | **$O(1)$** | **$O(\log N)$** / $O(N)$ | $O(\log N)$ при переходе в красно-черное дерево в Java 8+ |
| `contains(Object o)` | **$O(1)$** | **$O(\log N)$** / $O(N)$ | Зависит от равномерности распределения `hashCode()` |
| `remove(Object o)` | **$O(1)$** | **$O(\log N)$** / $O(N)$ | Быстрое удаление по хэшу |
| Итерация | **$O(\text{capacity} + N)$** | $O(\text{capacity} + N)$ | Обход всего массива бакетов, включая пустые |

## 🟡 Middle Level

### 1. Вычисление индекса бакета и разрешение коллизий

Когда вызывается `set.add(e)`, `HashMap` выполняет следующую последовательность шагов:

1. **Хэширование ключа (Perturbation Function):**
   ```java
   static final int hash(Object key) {
       int h;
       return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
   }
   ```
   Сдвиг вправо на 16 бит и операция XOR подмешивают старшие биты хэш-кода к младшим. Это предотвращает кластеризацию коллизий, когда размер таблицы невелик (например, 16), а младшие биты у ключей совпадают.

2. **Определение индекса в массиве бакетов `Node<K,V>[] table`:**
   ```java
   index = (table.length - 1) & hash;
   ```
   Размер таблицы всегда является степенью двойки ($2^k$). Это позволяет заменить медленное деление по модулю `%` на побитовое `AND` за 1 такт процессора.

3. **Поиск элемента в бакете:**
   Если в бакете уже есть нода, `HashMap` проверяет равенство ключей:
   ```java
   if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
   ```
   Сначала сверяются `hash` (примитивный `int`), затем ссылки `==`, и только при несовпадении ссылок вызывается тяжелый метод `.equals()`.

---

### 2. Деревизация коллизий (Treeification) в Java 8+

До Java 8 коллизии в бакетах хранились исключительно в виде односвязного списка (`Node<K,V>`). При намеренной атаке (Hash DoS) или плохом алгоритме `hashCode()` поиск деградировал до $O(N)$.

В Java 8+ внедрен механизм **деревизации (Treeification)**:
- **Условие превращения в дерево:** если в одном бакете накапливается $\ge 8$ элементов (`TREEIFY_THRESHOLD = 8`) **И** общий размер массива бакетов $\ge 64$ (`MIN_TREEIFY_CAPACITY = 64`).
- Если элементов в корзине $\ge 8$, но общая емкость массива $< 64$, дерево **не создается** — вместо этого вызывается `resize()`, удваивающий размер таблицы.
- При деревизации связный список заменяется сбалансированным красно-черным деревом (`TreeNode`), снижая худшую сложность поиска с $O(N)$ до $O(\log N)$.
- **Обратный переход (Untreeify):** если в результате удаления элементов или `resize()` размер дерева уменьшается до $\le 6$ (`UNTREEIFY_THRESHOLD = 6`), дерево превращается обратно в обычный связный список.

```
Бакет с коллизиями:
[0..7 элементов]: Node -> Node -> Node -> Node (Связный список, O(N))
[>= 8 элементов + capacity >= 64]: TreeNode (Красно-черное дерево, O(log N))
```

### 3. Опасность мутации объектов (Mutable Keys Trap)

Поскольку `HashSet` использует элементы как ключи в `HashMap`, **элементы множества должны быть неизменяемыми (immutable)** или хотя бы их поля, участвующие в `hashCode()` и `equals()`, не должны изменяться во время нахождения в сете.

```java
class User {
    private String name;
    public User(String name) { this.name = name; }
    public void setName(String name) { this.name = name; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User user)) return false;
        return Objects.equals(name, user.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(name);
    }
}

Set<User> users = new HashSet<>();
User ivan = new User("Иван");
users.add(ivan);

// Мутация объекта после вставки:
ivan.setName("Петр");

// КАТАСТРОФА:
System.out.println(users.contains(ivan)); // false!
users.remove(ivan);                       // false! (элемент не удалился)
System.out.println(users.size());         // 1 (объект-зомби застрял в сете!)
```

**Что произошло под капотом:**
1. При добавлении объект попал в бакет согласно старому `hashCode("Иван")`.
2. После вызова `setName("Петр")` его `hashCode()` изменился.
3. При поиске `contains(ivan)` `HashSet` вычисляет **новый** хэш-код и ищет в совершенно другом бакете. Бакет оказывается пустым, возвращается `false`.
4. Объект физически остается в старом бакете, создавая скрытую утечку памяти (Memory Leak).

## 🔴 Senior Level

### 1. Детальный анализ оверхеда памяти (Memory Footprint)

`HashSet` расходует огромное количество памяти накладных расходов из-за объектной структуры `HashMap$Node`:

На 64-битной JVM с Compressed OOPs (`-XX:+UseCompressedOops`, включен по умолчанию до 32 ГБ кучи):
- **Заголовок `Node` (Header):** 12 байт (Mark Word 8 байт + compressed Klass 4 байта).
- **Поля `Node`:**
  - `int hash`: 4 байта.
  - `K key` (compressed ref): 4 байта.
  - `V value` (compressed ref): 4 байта.
  - `Node<K,V> next` (compressed ref): 4 байта.
- **Выравнивание (Padding):** дополнение до кратности 8 байт $\to 4$ байта.
- **Итого размер одной ноды:** **32 байта**.
- **Ссылка в массиве бакетов (`table[i]`):** 4 байта на ячейку (при `loadFactor = 0.75` фактически $\approx 5.3$ байта на элемент).

```
Оверхед на 1 элемент HashSet: ~32 байта (нода) + ~5 байт (бакет) = ~37 байт чистой структуры.
Сам объект-элемент (например, Long) требует еще 24 байта (16 байт заголовок + 8 байт value).
```

Для хранения 10 000 000 чисел `long`:
- `HashSet<Long>`: займет $\approx 610$ МБ кучи и породит 20 миллионов объектов (10 млн `Long` + 10 млн `Node`).
- Специализированная коллекция примитивов с открытой адресацией (`it.unimi.dsi.fastutil.longs.LongOpenHashSet`): хранит данные в плоском массиве `long[]` без объектов-оберток и нод. Потребует всего $\approx 80$ МБ ($\approx$ в 7.5 раз меньше) и создаст ровно 0 объектов для GC!

### 2. Особенности сериализации: почему `map` объявлен как `transient`?

В классе `HashSet` внутренняя мапа объявлена с модификатором `transient`:
```java
private transient HashMap<E, Object> map;
```

**Причина:** Хэш-таблица привязана к конкретной реализации `hashCode()` и архитектуре JVM. В частности, хэш-коды некоторых классов (например, `IdentityHashMap` или системный `identityHashCode`) зависят от адреса объекта в памяти. Более того, при развертывании приложения на другой версии JDK или на другой архитектуре процессора распределение по бакетам может измениться.

Если бы `HashSet` просто сериализовал массив бакетов `table`, при десериализации на другой JVM или конфигурации элементы попали бы не в те бакеты, что сломало бы логику работы.

**Решение через кастомную сериализацию:**
`HashSet` реализует приватные методы `writeObject` и `readObject`:
```java
private void writeObject(java.io.ObjectOutputStream s) throws java.io.IOException {
    s.defaultWriteObject();
    s.writeInt(map.capacity());
    s.writeFloat(map.loadFactor());
    s.writeInt(map.size());

    // Сериализуются ТОЛЬКО сами элементы, без структуры бакетов и без нод!
    for (E e : map.keySet())
        s.writeObject(e);
}

private void readObject(java.io.ObjectInputStream s) throws java.io.IOException, ClassNotFoundException {
    s.defaultReadObject();
    // Читаются параметры емкости и коэффициента загрузки
    int capacity = s.readInt();
    float loadFactor = s.readFloat();
    map = new HashMap<>(capacity, loadFactor);

    int size = s.readInt();
    // Каждый элемент заново вставляется через map.put()
    for (int i = 0; i < size; i++) {
        @SuppressWarnings("unchecked")
        E e = (E) s.readObject();
        map.put(e, PRESENT);
    }
}
```

### 3. Скрытый пакетно-приватный конструктор для `LinkedHashSet`

В исходном коде `HashSet` есть неочевидный конструктор с модификатором package-private:
```java
HashSet(int initialCapacity, float loadFactor, boolean dummy) {
    map = new LinkedHashMap<>(initialCapacity, loadFactor);
}
```
Он используется исключительно наследником **`LinkedHashSet`**. Булев аргумент `dummy` служит лишь маркером для перегрузки сигнатуры конструктора. Это изящное архитектурное решение позволило разработчикам JDK повторно использовать весь код `HashSet` для `LinkedHashSet`, подменив базовую реализацию `HashMap` на `LinkedHashMap`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «`HashSet` — это тонкая обёртка над `HashMap`, реализующая интерфейс `Set`. Добавляемые элементы становятся **ключами** внутренней хэш-таблицы, а в качестве значения подставляется единый фиктивный объект-заглушка `PRESENT` (`new Object()`). За счёт этого `HashSet` обеспечивает сложность $O(1)$ в среднем для `add`, `remove` и `contains`. В Java 8+ при большом числе коллизий ($\ge 8$ элементов в бакете и capacity $\ge 64$) связный список бакета трансформируется в красно-чёрное дерево, ограничивая худшее время поиска до $O(\log N)$».

### 3 каверзных вопроса на интервью с ответами

#### 1. Почему `HashSet` не имеет собственного метода `get(Object o)`?
**Ответ:** По контракту множества элемент либо присутствует, либо отсутствует (`contains(o)`). Если у вас уже есть объект `o`, равный искомому по `equals()`, вызывать `get()` бессмысленно, так как объект уже у вас в руках. Если же требуется сопоставление ключа с объектом-хранилищем (например, интернирование или кэширование), следует использовать `Map<K, V>`.

#### 2. Что произойдет, если в класс элемента `HashSet` не реализовать `Comparable`, но в одном бакете возникнет более 8 коллизий?
**Ответ:** Произойдет деревизация (при capacity $\ge 64$). Красно-черное дерево попытается сравнивать ключи через `Comparable.compareTo()`. Если класс ключа не реализует `Comparable`, `HashMap` использует метод `tieBreakOrder(Object a, Object b)`, который сравнивает имена классов через `a.getClass().getName().compareTo(b.getClass().getName())`, а при совпадении классов — системные хэши через `System.identityHashCode(a)`. Дерево будет построено, но с меньшей эффективностью сравнения.

#### 3. Почему создание `new HashSet<>(1_000_000)` без добавления элементов может замедлить работу программы?
**Ответ:** Инициализация выделит массив бакетов `table` на $2^{20} = 1\,048\,576$ ячеек ($\approx 4$ МБ ссылок). Главная ловушка — последующая итерация: итератор `HashSet` имеет сложность $O(\text{capacity} + N)$. Чтобы обойти коллекцию с 0 или 10 элементами, итератор будет вынужден последовательно проверить все 1 048 576 ячеек массива в поисках непустых бакетов, что приведет к тысячам Cache Misses.

---

### Типичные ошибки и Red Flags

- ❌ **Мутация полей объекта после добавления в Set:** Изменение полей, влияющих на `hashCode()`, делает объект невидимым для `contains()` и не удаляемым через `remove()`, вызывая утечку памяти.
- ❌ **Несогласованность `equals()` и `hashCode()`:** Нарушение контракта ведет к появлению дубликатов в множестве или невозможности найти добавленный элемент.
- ❌ **Использование `HashSet<Long>` или `HashSet<Integer>` для миллионов примитивов:** Создает чудовищный оверхед по памяти ($\approx 37$ байт на ноду + 24 байта на боксинг). Для примитивов нужно использовать специализированные библиотеки (`fastutil`, `eclipse-collections`).
- ❌ **Утверждение, что `HashSet` потокобезопасен:** `HashSet` не синхронизирован. Одновременное чтение и запись могут привести к бесконечному циклу (в Java 7) или повреждению структуры данных. В конкурентной среде нужен `ConcurrentHashMap.newKeySet()` или `Collections.synchronizedSet()`.
