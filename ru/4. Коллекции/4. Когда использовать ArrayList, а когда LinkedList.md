# Когда использовать ArrayList, а когда LinkedList

---

## 🟢 Junior Level

**Короткий и категоричный ответ для современной разработки:**
В **99% сценариев** следует использовать **`ArrayList`**.

Класс **`LinkedList`** в промышленном коде сегодня считается практически устаревшим антипаттерном.

### Почему `ArrayList` побеждает по умолчанию:
1. **Быстрое чтение:** доступ к любому элементу по индексу `get(i)` выполняется мгновенно за $O(1)$.
2. **Экономия памяти:** хранит компактный массив ссылок (4–8 байт на элемент), тогда как `LinkedList` создает громоздкий объект узла на каждый элемент (24–32 байта).
3. **Скорость итерации:** благодаря непрерывному расположению в памяти процессор мгновенно читает элементы через кэш L1/L2.

### Когда использовать альтернативы:
- Если вам нужен список объектов по умолчанию $\to$ **`ArrayList`**.
- Если вам нужна очередь (FIFO) или стек (LIFO) $\to$ используйте **`ArrayDeque`**, а не `LinkedList`!
- Если вам нужно хранить уникальные значения $\to$ **`HashSet`**.

```java
// ✅ Стандарт современной Java:
List<User> users = new ArrayList<>();

// ❌ Неоправданное использование:
List<User> users = new LinkedList<>(); // Медленнее и тратит в 6 раз больше памяти!
```

## 🟡 Middle Level

### 1. Матрица выбора по сценариям использования

| Сценарий применения | Рекомендуемая коллекция | Почему именно она |
| :--- | :--- | :--- |
| **Чтение по индексу `get(i)`** | **`ArrayList`** | Прямой расчет адреса в памяти за $O(1)$ против обхода ссылок $O(N)$. |
| **Итерация (`for-each`, Stream API)** | **`ArrayList`** | Кэш-локальность (Cache Locality): процессор читает массив целыми строками по 64 байта. |
| **Добавление в конец `add(e)`** | **`ArrayList`** | Амортизированное $O(1)$ без аллокации промежуточных узлов. |
| **Очередь (FIFO) или Стек (LIFO)** | **`ArrayDeque`** | Кольцевой массив, $O(1)$ на обоих концах, нет мусора для GC. |
| **Удаление по условию (фильтрация)** | **`ArrayList`** (`removeIf`) | Эффективное сжатие массива в один проход за $O(N)$. |
| **Частая вставка в случайную середину** | **Ни одна из них!** | `ArrayList` сдвигает хвост, а `LinkedList` ищет место вставки за $O(N)$. Для таких задач выбирают деревья или хэш-таблицы. |

### 2. Почему аргумент о «быстрой вставке в середину» LinkedList — миф?

Классический довод в пользу `LinkedList`: *«Вставка в середину списка занимает $O(1)$, потому что нужно лишь перепривязать указатели `prev` и `next`»*.

**В чём заключается фатальная ошибка этого рассуждения:**
```
Чтобы вставить элемент в позицию N в LinkedList:
1. Сначала нужно ДОЙТИ до позиции N:
   Node current = first;
   for (int i = 0; i < N; i++) current = current.next; // <-- Это O(N) шагов по медленной RAM!
2. Перепривязать ссылки: O(1).
Итоговая сложность: O(N) + O(1) = O(N)!
```
В `ArrayList` позиция находится за $O(1)$, а сдвиг элементов выполняется нативным методом `System.arraycopy()`, который переносит данные машинными блоками. До размера списка в десятки тысяч элементов `ArrayList` вставляет данные в середину быстрее или наравне с `LinkedList`.

### 3. Оптимизация удаления: `removeIf` против итератора

```java
// ❌ АНТИПАТТЕРН: Удаление через итератор в ArrayList порождает O(N²) из-за многократных сдвигов
Iterator<Order> it = list.iterator();
while (it.hasNext()) {
    if (it.next().isCancelled()) {
        it.remove(); // Каждый вызов сдвигает хвост массива!
    }
}

// ✅ ПРАВИЛЬНО: list.removeIf() (Java 8+)
list.removeIf(Order::isCancelled);
```
**Как работает `removeIf()` в `ArrayList`:**
Он использует двухточечный алгоритм сжатия (Two Pointers) и `BitSet`. За **один проход $O(N)$** находятся все удаляемые элементы, после чего выжившие элементы сдвигаются на свои итоговые позиции за один такт. Никаких квадратичных накладных расходов!

## 🔴 Senior Level

### 1. Архитектурная анатомия Hardware: «Стена памяти» (Memory Wall)

Разрыв между тактовой частотой процессора и скоростью чтения из оперативной памяти DRAM огромен:
- Чтение из регистров CPU: $\sim 0.5$ нс (1 такт);
- Чтение из кэша L1: $\sim 1$ нс (3–4 такта);
- Чтение из кэша L2/L3: $\sim 4–15$ нс;
- Чтение из физической RAM: $\sim 60–100$ нс (**200–300 тактов простоя CPU!**).

```
ArrayList в оперативной памяти (смежные ячейки):
[ Cell 0 ][ Cell 1 ][ Cell 2 ][ Cell 3 ][ Cell 4 ][ Cell 5 ]...
▲───────────────────────────────────────▲
CPU загружает всю 64-байтную строку кэша (Cache Line) за 1 обращение!

LinkedList в оперативной памяти (фрагментированная куча):
[ Node 0 ] ──► ...память... ──► [ Node 1 ] ──► ...память... ──► [ Node 2 ]
     ▲                               ▲                               ▲
Cache Miss!                     Cache Miss!                     Cache Miss!
```

При итерации по `LinkedList` каждое разыменование указателя `node.next` обращается к произвольному адресу в куче, порождая непрерывные **CPU Cache Misses**. Процессор проводит 90% времени в режиме ожидания ответа от шины памяти (*Pipeline Stall*).

### 2. Нагрузка на сборщик мусора (GC Allocation Churn)

При интенсивной обработке потоков данных (например, парсинг сообщений в Kafka consumer):
- `ArrayList`: при заполнении создает массив, при очистке зануляет ссылки. Новых объектов в куче создается минимум.
- `LinkedList`: на каждый добавленный элемент инициируется аллокация объекта `Node` в области TLAB. При удалении элемента узел немедленно становится мусором.
- Миллион событий в секунду через `LinkedList` генерирует **миллион объектов `Node` в секунду** в Young Generation, вызывая непрерывные циклы Minor GC и Stop-The-World паузы.

### 3. Существует ли хоть один сценарий, где `LinkedList` оправдан?

Интерфейс `java.util.LinkedList` **не дает преимуществ практически никогда**, потому что стандартный класс не предоставляет прямого доступа к объектам `Node`. Даже если вам нужен истинный $O(1)$ для вставки и удаления узлов, `LinkedList` скрывает класс `Node` как `private static class`.

**Когда связные списки действительно нужны:**
1. **Кастомные интрузивные связные списки (Intrusive Linked Lists):** когда бизнес-объект сам содержит ссылки `prev` и `next` (например, внутреннее устройство `LinkedHashMap` или LRU-кэши Netty).
2. **Алгоритмы скользящего окна огромного размера (от сотен тысяч элементов):** где перемещение итератора вперед и удаление строго текущего узла `iterator.remove()` выполняется непрерывно и параллельно с добавлением, а доступ по индексу вообще не требуется.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ для собеседования
> «По умолчанию в абсолютном большинстве задач следует выбирать `ArrayList`. Он обладает максимальной скоростью произвольного доступа $O(1)$, минимальным потреблением памяти (в 6–8 раз меньше `LinkedList`) и образцовой кэш-локальностью для процессора. `LinkedList` проигрывает на современных CPU из-за постоянных промахов кэша при обходе разрозненных узлов `Node` и высокого давления на сборщик мусора. Для задач очередей (FIFO) и стеков (LIFO) вместо `LinkedList` необходимо использовать `ArrayDeque`».

### Вопросы повышенной сложности с ответами

1. **Кандидат утверждает: «Я использую `LinkedList`, потому что мне нужно часто вставлять элементы в середину списка». Как вы прокомментируете это решение?**
   *Ответ:* Это классическое заблуждение. Чтобы вставить элемент в середину `LinkedList`, до этой середины сначала нужно дойти по цепочке ссылок от начала или конца списка за $O(N)$ операций. Каждый шаг обхода сопровождается промахами кэша процессора. В `ArrayList` позиция вставки находится мгновенно за $O(1)$, а сдвиг оставшихся элементов выполняется через оптимизированную функцию `System.arraycopy()`. На практике для списков реального размера (до 20–50 тысяч элементов) `ArrayList` выполняет вставку в середину быстрее, чем `LinkedList`.

2. **Почему метод `list.removeIf(predicate)` в `ArrayList` работает за $O(N)$, тогда как цикл с `iterator.remove()` работает за $O(N^2)$?**
   *Ответ:* При вызове `iterator.remove()` в `ArrayList` каждый раз вызывается сдвиг всех правых элементов влево на одну позицию. Если удаляется много элементов, массив сдвигается заново при каждом удалении, приводя к квадратичной сложности $O(N^2)$. Метод `removeIf()` использует двухпроходный алгоритм: сначала за один проход $O(N)$ фиксирует позиции удаляемых элементов, а затем за второй проход аккуратно перемещает выжившие элементы на новые места единым непрерывным алгоритмом сжатия за $O(N)$.

3. **Что эффективнее использовать в качестве реализации стека: `java.util.Stack`, `LinkedList` или `ArrayDeque`?**
   *Ответ:* `ArrayDeque`. Класс `Stack` устарел, так как наследует `Vector` и синхронизирует каждый метод монитором `synchronized`, что избыточно замедляет код. `LinkedList` расходует лишнюю память на объекты `Node` и создает мусор для GC. `ArrayDeque` работает на плоском циклическом массиве, не имеет накладных расходов на синхронизацию и узлы, а операции `push()` и `pop()` выполняются за амортизированное $O(1)$ с максимальной кэш-локальностью.

4. **Как влияет флаг `-XX:+UseCompressedOops` на размер `LinkedList`?**
   *Ответ:* Узел `LinkedList$Node` хранит 3 ссылки (`item`, `next`, `prev`). При включенном Compressed OOPs ссылки 32-битные (4 байта), заголовок объекта занимает 12 байт, суммарный размер ноды составляет 24 байта (с выравниванием). При отключении Compressed OOPs (или куче $>32$ ГБ) ссылки становятся 64-битными (8 байт), заголовок занимает 16 байт, и размер ноды возрастает до 40 байт, увеличивая перерасход памяти `LinkedList` по сравнению с `ArrayList` еще сильнее.

### Типичные ошибки и Red Flags
- ❌ **Считать, что `LinkedList` быстрее `ArrayList` при добавлении в начало на любых коллекциях.** (Для небольших и средних коллекций `ArrayList` опережает `LinkedList` за счет исключения аллокации `Node` и работы SIMD).
- ❌ **Рекомендовать `LinkedList` в качестве очереди сообщений.** (Red Flag: незнание `ArrayDeque`).
- ❌ **Не знать о существовании метода `removeIf()` и предлагать удаление через цикл `for(int i=0; ...)`.**
