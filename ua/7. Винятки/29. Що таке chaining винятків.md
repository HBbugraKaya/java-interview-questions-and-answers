# Що таке chaining винятків

---

## 🟢 Junior Level

### Коротка відповідь для співбесіди (30 секунд)
**Exception Chaining (ланцюжок винятків)** — це вбудований механізм Java (запроваджений у Java 1.4), що дозволяє пов'язати один виняток з іншим як його першопричину (`cause`).

Коли на низькому рівні архітектури виникає технічна помилка (наприклад, `SQLException`), сервісний шар перехоплює її і викидає новий високорівневий бізнес-виняток (`OrderProcessingException`), передаючи початковий виняток у конструктор: `throw new OrderProcessingException("Order failed", e);`. У логах формується ієрархічний звіт із секціями **`Caused by:`**, який зберігає оригінальний стек-трейс і дозволяє інженерам миттєво локалізувати корінь проблеми.

---

### Конструктори та методи класу `Throwable`
Підтримка ланцюжків винятків вбудована в базовий клас `java.lang.Throwable`:
- **Конструктори зв'язування:**
  - `public Throwable(String message, Throwable cause)`
  - `public Throwable(Throwable cause)`
- **Методи читання та модифікації:**
  - `public Throwable getCause()` — повертає початкову причину (або `null`, якщо причини немає).
  - `public synchronized Throwable initCause(Throwable cause)` — зв'язує причину постфактум, якщо вона не була передана в конструктор.

---

### Базовий приклад на Java 21

```java
import java.sql.SQLException;

public class OrderService {

    public void processPayment(String orderId) {
        try {
            chargeDatabase(orderId);
        } catch (SQLException e) {
            // Зв'язуємо низькорівневий SQLException із доменним OrderPaymentException
            throw new OrderPaymentException("Payment processing failed for order " + orderId, e);
        }
    }

    private void chargeDatabase(String id) throws SQLException {
        throw new SQLException("Connection timed out to pool [192.168.1.50:5432]");
    }

    public static class OrderPaymentException extends RuntimeException {
        public OrderPaymentException(String message, Throwable cause) {
            super(message, cause);
        }
    }
}
```

Вивід стек-трейсу в лозі:
```text
OrderService$OrderPaymentException: Payment processing failed for order 12345
    at OrderService.processPayment(OrderService.java:10)
    at App.main(App.java:5)
Caused by: java.sql.SQLException: Connection timed out to pool [192.168.1.50:5432]
    at OrderService.chargeDatabase(OrderService.java:15)
    at OrderService.processPayment(OrderService.java:8)
    ... 1 more
```

## 🟡 Middle Level

### Внутрішня будова механізму Chaining у `Throwable`
У вихідному коді JDK клас `java.lang.Throwable` керує ланцюжком через спеціальне приватне поле:
```java
private Throwable cause = this; // Значення "this" — sentinel (причина ще не визначена)
```

#### Тонкощі стану `cause`:
1. **Sentinel `this`:** Якщо поле дорівнює `this`, це означає, що причина ще **не була ініціалізована**.
2. **Значення `null`:** Означає, що у винятку **гарантовано немає причини** (причина відсутня в принципі).
3. **Метод `initCause()`:**
   - З'явився в Java 1.4 для забезпечення зворотної сумісності зі старими бібліотеками, класи яких не мали конструкторів із параметром `Throwable cause`.
   - Метод дозволено викликати **суворо один раз**. Спроба викликати `initCause()` повторно або викликати його в об'єкта, в конструктор якого вже було передано `cause`, призводить до `IllegalStateException: Can't overwrite cause with [Throwable]`.
4. **Захист від самопричинності (Self-causation):**
   - Виклик `e.initCause(e)` або створення циклічної залежності (`a.initCause(b); b.initCause(a);`) негайно блокується викиданням `IllegalArgumentException("Self-causation not permitted")`.

---

### Архітектурні шари та трансляція винятків (Layered Translation)
Ланцюжок винятків відображає архітектурні шари корпоративного застосунку:

```
[ Web Controller ]    <-- Ловить OrderException -> повертає HTTP 500 / 400
       ▲
       │ Caused by:
[ Domain Service ]    <-- Загортає DataAccessException у OrderException
       ▲
       │ Caused by:
[ DAO / Repository ]  <-- Загортає SQLException у Spring DataAccessException
       ▲
       │ Caused by:
[ JDBC Driver / OS ]  <-- Початковий SocketTimeoutException ("Read timed out")
```
Кожен шар додає специфічний контекст свого рівня (номер замовлення, ім'я таблиці, мережевий порт), зберігаючи повну історію поширення збою.

---

### Алгоритм пошуку кореневої причини (Root Cause Analysis)
Під час аналізу інцидентів та обробки телеметрії часто потрібно знайти найперший початковий виняток (Root Cause):

```java
import java.util.Collections;
import java.util.IdentityHashMap;
import java.util.Set;

public class RootCauseFinder {

    public static Throwable findRootCause(Throwable throwable) {
        if (throwable == null) {
            return null;
        }

        Set<Throwable> visited = Collections.newSetFromMap(new IdentityHashMap<>());
        Throwable current = throwable;

        // Обходимо ланцюжок углиб, захищаючись від можливих пошкоджених циклів
        while (current.getCause() != null && visited.add(current)) {
            current = current.getCause();
        }
        return current;
    }
}
```

## 🔴 Senior Level

### Стиснення стек-трейсу: що означає `... X more`?
Під час виведення ланцюжків винятків у лог розробники часто бачать конструкцію вигляду:
```text
Caused by: java.io.IOException: Connection reset
    at com.client.HttpTransport.send(HttpTransport.java:42)
    ... 24 more
```

#### Механізм JVM:
Кожен виняток у ланцюжку містить свій власний знімок стека викликів (`StackTraceElement[]`). Проте фрейми викликаючих методів вище точки перехоплення у причини й у обгортки **абсолютно ідентичні**.
JVM (метод `Throwable.printEnclosedStackTrace`) порівнює масив стека причини з масивом стека обгорткового винятку з кінця. Однакові кадри стискаються в рядок `... X more`, що запобігає квадратичному зростанню обсягу логів.

---

### Ризики серіалізації та Classpath Coupling у розподілених системах
Спроба передати ланцюжок винятків цілком через мережу (наприклад, у мікросервісній архітектурі через gRPC, RMI або через серіалізовані повідомлення брокера Kafka) створює серйозні архітектурні ризики:
1. **`ClassNotFoundException` на клієнті:** Якщо в глибині ланцюжка `cause` міститься клас `org.postgresql.util.PSQLException`, клієнтський мікросервіс зобов'язаний мати у своєму Classpath драйвер PostgreSQL лише для того, щоб десеріалізувати об'єкт помилки!
2. **Витік внутрішньої топології:** Клієнт бачить фізичні IP-адреси баз даних, версії ORM і структуру таблиць.
3. **Рішення:** На межах мікросервісів ланцюжки винятків Java **ніколи не серіалізуються в бінарному вигляді**. Помилки перетворюються на платформонезалежні структури: JSON-відповіді стандарту **RFC 7807 (Problem Details)** або protobuf-статуси gRPC.

---

### Навантаження на пам'ять та Garbage Collection
Кожна ланка ланцюжка є сильним посиланням на попередню:
- Доки живе зовнішнє посилання на виняток, жоден об'єкт із ланцюжка `cause` не може бути зібраний збирачем сміття.
- Якщо кастомні винятки містять важкі контекстні поля (наприклад, "сире" тіло HTTP-запиту, буфери даних або дампи сутностей), ланцюжок може утримувати мегабайти пам'яті в купі.
- Уникайте збереження важких корисних навантажень у полях винятків, якщо вони плануються до довгоживучого кешування.

## 🎯 Шпаргалка для інтерв'ю

### Питання для швидкої перевірки
1. **Навіщо в класі `Throwable` поле `cause` спочатку ініціалізовано як `this`, а не `null`?**
   *Відповідь:* Значення `this` слугує sentinel-маркером («причину ще не встановлено»). Це дозволяє відрізнити ситуацію, коли причина ще не була задана (і її можна встановити через `initCause()`), від ситуації, коли причина була явно задана як відсутня (`cause == null`).
2. **Чи можна викликати метод `initCause()` у винятку повторно?**
   *Відповідь:* Ні, не можна. Метод `initCause()` може бути викликаний лише один раз і тільки за умови, що причина не була передана в конструктор. Повторний виклик викине `IllegalStateException`.
3. **Що означає напис `... 15 more` у блоці `Caused by:` стек-трейсу?**
   *Відповідь:* Це оптимізація форматування JVM: вона вказує, що останні 15 фреймів стека викликів цього винятку в точності збігаються з нижніми фреймами вищого винятку, який його загорнув, і пропущені заради економії місця.
4. **У чому різниця між `Exception Chaining` (`cause`) та `Suppressed Exceptions`?**
   *Відповідь:* `Cause` виражає вертикальну причинно-наслідкову залежність («помилка А сталася через помилку Б»), а `Suppressed` виражає горизонтальне супутнє накопичення помилок, що виникли під час звільнення ресурсів або аварійного виходу в `try-with-resources`.

### Типові помилки та Red Flags
- ❌ **Твердження: "Ланцюжок винятків можна модифікувати в будь-який момент через `initCause()`":** Метод одноразовий і падає з `IllegalStateException`, якщо причина вже була задана.
- ❌ **Втрата ланцюжка причинності:** Написання `throw new CustomException(e.getMessage())` замість `throw new CustomException(msg, e)`.
- ❌ **Передача бінарно серіалізованих ланцюжків винятків між мікросервісами:** Порушує ізоляцію сервісів і призводить до збоїв десеріалізації (`ClassNotFoundException`).
- ❌ **Плутанина між маркерами `Caused by:` (причина) та `Suppressed:` (пригнічена супутня помилка).**
