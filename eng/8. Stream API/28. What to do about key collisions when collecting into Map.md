# What to do about key collisions when collecting into Map

---

## 🟢 Junior Level

### 30-Second Summary
A **Key Collision** occurs when two or more elements in a stream evaluate to the identical key after application of the `keyMapper` function.

By default, the two-argument method `Collectors.toMap(keyMapper, valueMapper)` cannot resolve key conflicts. Encountering a duplicate key immediately throws a runtime exception:
`IllegalStateException: Duplicate key <key> (attempted merging values <v1> and <v2>)`.

To handle collisions safely, you must use the three- or four-argument overload of `Collectors.toMap` by providing a **merge function (`BinaryOperator<U> mergeFunction`)**. This lambda determines which value to retain when a collision is detected:
```java
// Retain the first encountered value (Keep First):
(existing, replacement) -> existing

// Retain the newest/latest value (Keep Last / Overwrite):
(existing, replacement) -> replacement
```

---

### Java 21 Code Examples

```java
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

public class KeyCollisionDemo {

    public record Employee(int id, String name, double salary) {}

    public static void main(String[] args) {
        List<Employee> staff = List.of(
            new Employee(101, "Ivan (Junior)", 80_000),
            new Employee(102, "Anna (Middle)", 160_000),
            new Employee(101, "Ivan (Senior)", 250_000) // Duplicate ID 101!
        );

        // Strategy 1: Retain the first encountered value (Keep First)
        Map<Integer, Employee> firstStaff = staff.stream()
            .collect(Collectors.toMap(
                Employee::id,
                e -> e,
                (existing, replacement) -> existing
            ));
        System.out.println("First: " + firstStaff.get(101).name()); // Ivan (Junior)

        // Strategy 2: Overwrite with latest value (Keep Last)
        Map<Integer, Employee> latestStaff = staff.stream()
            .collect(Collectors.toMap(
                Employee::id,
                e -> e,
                (existing, replacement) -> replacement
            ));
        System.out.println("Latest: " + latestStaff.get(101).name()); // Ivan (Senior)

        // Strategy 3: Domain aggregation (Select highest compensation)
        Map<Integer, Employee> highestPaid = staff.stream()
            .collect(Collectors.toMap(
                Employee::id,
                e -> e,
                (e1, e2) -> e1.salary() >= e2.salary() ? e1 : e2
            ));
        System.out.println("Top Salary: " + highestPaid.get(101).salary()); // 250000.0
    }
}
```

## 🟡 Middle Level

### The 4 Core Collision Resolution Strategies

The `BinaryOperator<U>` functional interface accepts `(U existingValue, U newValue)` and produces a single unified value of type `U`:

#### 1. Deduplication (Keep First):
Used when the earliest encountered entity is considered canonical:
```java
(oldVal, newVal) -> oldVal
```

#### 2. Upsert / State Update (Keep Last):
Used when a stream is ordered chronologically by timestamp or sequence, and the newest state should overwrite previous values:
```java
(oldVal, newVal) -> newVal
```

#### 3. Arithmetic Aggregation:
Used to aggregate counts, volumes, or summaries across records:
```java
Map<String, Integer> productTotals = orders.stream()
    .collect(Collectors.toMap(Order::product, Order::quantity, Integer::sum));
```

#### 4. Domain Priority Reducer:
Resolves collisions using domain business logic (e.g. keeping highest priority or status):
```java
(v1, v2) -> v1.priority() >= v2.priority() ? v1 : v2
```

---

### When `toMap` with `mergeFunction` is an Architectural Anti-Pattern

If a business requirement mandates preserving **all** entities associated with a duplicate key, using `toMap()` is an architectural anti-pattern. You must use **`Collectors.groupingBy()`** instead:

```java
// ❌ WRONG: Attempting manual list accumulation inside toMap
// .toMap(User::dept, u -> new ArrayList<>(List.of(u)), (l1, l2) -> { l1.addAll(l2); return l1; })

// ✅ IDIOMATIC & OPTIMAL: groupingBy cleanly aggregates into Map<String, List<User>>
Map<String, List<User>> usersByDept = users.stream()
    .collect(Collectors.groupingBy(User::department));
```

## 🔴 Senior Level

### Associativity Requirement in `parallelStream()`

In parallel pipelines (`parallelStream()`), the stream is split across worker threads in the `ForkJoinPool`:
1. Each worker thread constructs its own partial sub-map.
2. When merging partial results across thread boundaries, `combiner` invokes `Map.merge()`, calling `mergeFunction` whenever identical keys were generated in different subtasks.
3. For parallel execution to guarantee deterministic results, the `mergeFunction` **must be strictly associative**:
   $$(v_1 \circ v_2) \circ v_3 = v_1 \circ (v_2 \circ v_3)$$

```
Worker 1: Map [Key=A -> Val 1] \
                                ──► mergeFunction(Val 1, Val 2) \
Worker 2: Map [Key=A -> Val 2] /                                 ──► mergeFunction(Res1, Val 3)
                                                                /
Worker 3: Map [Key=A -> Val 3] ────────────────────────────────
```

> [!WARNING]
> In `parallelStream()`, the "Keep Last" strategy `(v1, v2) -> v2` **does not guarantee** which element is retained because the merge order of completion tasks across `ForkJoinPool` threads is non-deterministic. To guarantee deterministic resolution in parallel pipelines, elements must contain an explicit ordering attribute (e.g., version number or timestamp comparator).

### Production Audit and Collision Logging

In financial and transactional architectures, silently discarding duplicate records leads to catastrophic data loss. Production systems should log collisions:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import java.util.List;
import java.util.Map;
import java.util.function.Function;
import java.util.stream.Collectors;

public class SafeMergeCollector {
    private static final Logger log = LoggerFactory.getLogger(SafeMergeCollector.class);

    public static <T, K, V> Map<K, V> toMapWithAudit(
            List<T> items, 
            Function<T, K> keyMapper,
            Function<T, V> valueMapper) {
        
        return items.stream().collect(Collectors.toMap(
            keyMapper,
            valueMapper,
            (existing, replacement) -> {
                log.warn("KEY COLLISION DETECTED! Key collided. Retaining: [{}], Discarded: [{}]", 
                         existing, replacement);
                return existing;
            }
        ));
    }
}
```

### Static Analysis Guardrails (SonarQube & Google Error-Prone)

Enterprise static code analyzers, including **Google Error-Prone** and **SonarQube** (Rule `java:S2201` / `DuplicateKeyException`), flag the two-argument `Collectors.toMap(keyMapper, valueMapper)` as a **High-Risk Code Smell**.

Production guidelines mandate supplying an explicit `mergeFunction` or refactoring to `groupingBy()`.

## 4 Tricky Questions

### 1. Why is the two-argument `Collectors.toMap(k, v)` considered a high-risk code smell in enterprise production applications?
**Answer:**
The two-argument `Collectors.toMap()` internally delegates to a merge function (`throwingMerger()`) that unconditionally throws `IllegalStateException`.

If input datasets from external systems, user inputs, or database queries contain unforeseen duplicate keys, the entire application request crashes with an unhandled exception. Providing an explicit `mergeFunction` guarantees resilient behavior by defining how conflicts are resolved gracefully without throwing runtime errors.

---

### 2. What happens if a `mergeFunction` returns `null` when a collision occurs?
**Answer:**
If the `mergeFunction` evaluates to `null`, `Map.merge()` removes the entry for that key from the target map entirely:
```java
// OpenJDK Map.java merge contract:
if (value != null) {
    V newValue = remappingFunction.apply(oldValue, value);
    if (newValue != null)
        put(key, newValue);
    else
        remove(key);
}
```
Returning `null` acts as a deletion instruction, causing the key to vanish from the final `Map`.

---

### 3. Why can the "Keep Last" strategy `(v1, v2) -> v2` yield non-deterministic results in a multi-threaded `parallelStream()`?
**Answer:**
In `parallelStream()`, the dataset is partitioned into multiple chunks processed by separate worker threads in `ForkJoinPool`. The completion order and task tree combination order depend on OS thread scheduling and work-stealing dynamics.

Because the order in which thread-local maps are combined is non-deterministic, `v2` might represent an element that originated from an earlier index in the source collection if that partition completed later. To achieve deterministic behavior in parallel mode, use a comparator-based merge function (e.g. `(a, b) -> a.timestamp() >= b.timestamp() ? a : b`).

---

### 4. How does `Collectors.toMap()` with a merge function differ fundamentally from `Collectors.groupingBy()`?
**Answer:**
- **`Collectors.toMap()` with a merge function:** Enforces a **1-to-1** mapping. The map retains exactly one value per key by applying a reduction operator to reduce conflicting elements into a single entity ($O(1)$ value cardinality).
- **`Collectors.groupingBy()`:** Enforces a **1-to-Many** mapping. It preserves all elements associated with each key by accumulating them into a collection (`Map<K, List<V>>`), guaranteeing that zero information is discarded.

## 🎯 Interview Cheat Sheet

### Collision Handling Strategy Matrix
| Strategy | `mergeFunction` Implementation | When to Use | `parallelStream()` Behavior |
| :--- | :--- | :--- | :--- |
| **Fail-Fast Crash** | None (2-arg `toMap`) | Uniqueness is a strict data invariant | 💥 Throws `IllegalStateException` |
| **Keep First** | `(oldVal, newVal) -> oldVal` | Retain earliest canonical record | Deterministic on ordered sources |
| **Keep Last** | `(oldVal, newVal) -> newVal` | Overwrite with newest record | Non-deterministic across threads |
| **Numeric Sum** | `Integer::sum` | Accumulate metrics by key | 🟢 Deterministic (Associative) |
| **Comparator Pick** | `(a, b) -> a.val() >= b.val() ? a : b`| Select highest priority or version | 🟢 Deterministic |
| **Group Multiples** | `Collectors.groupingBy()` | Preserve all elements per key | 🟢 Deterministic (`Map<K, List<V>>`) |

---

### Key Takeaways
- **Collision Root Cause:** Duplicate keys evaluate through `keyMapper` into the same bucket.
- **Fail-Fast Default:** 2-arg `toMap()` throws `IllegalStateException`.
- **Merge Function:** 3-arg `toMap(k, v, mergeFn)` specifies resolution rules.
- **Associativity Constraint:** Parallel stream mergers require associative merge operations.
- **1-to-Many Alternative:** Use `Collectors.groupingBy()` when values must not be discarded.

---

### Red Flags & Anti-Patterns to Avoid
- ❌ **Omitting `mergeFunction` when consuming untrusted data:** Unchecked duplicate keys will crash production threads.
- ❌ **Using `(v1, v2) -> v2` in `parallelStream()` expecting chronologically last items:** Parallel task combinations are non-deterministic.
- ❌ **Manually collecting lists inside `toMap()`:** Violates idiomatic design; use `groupingBy()`.
- ❌ **Returning `null` inside `mergeFunction` inadvertently:** Silently removes entries from the map.
