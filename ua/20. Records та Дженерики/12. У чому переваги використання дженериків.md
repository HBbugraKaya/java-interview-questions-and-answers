# У чому переваги використання дженериків

---

## 🟢 Junior Level

**Дженерики (узагальнення)** в Java надають три базові переваги, які кардинально покращують якість, надійність та читабельність коду:

### 1. Безпека типів на етапі компіляції (Compile-Time Type Safety)
До появи дженериків у Java 5 будь-яка колекція зберігала елементи як `Object`. Помилки невідповідності типів виявлялися лише в рантаймі у вигляді аварійного завершення програми з `ClassCastException`. З дженериками компілятор блокує додавання об'єктів несумісних типів ще на етапі компіляції.

```java
// ❌ Без дженериків: помилка спливе лише в користувача в продакшені!
List rawList = new ArrayList();
rawList.add("Apple");
rawList.add(100); // Помилки немає під час компіляції

String item = (String) rawList.get(1); // 💥 ClassCastException під час роботи програми!

// ✅ З дженериками: помилка блокується компілятором
List<String> typedList = new ArrayList<>();
typedList.add("Apple");
// typedList.add(100); // ❌ Помилка компіляції: incompatible types!
```

### 2. Усунення явного приведення типів (Elimination of Casts)
Код звільняється від нескінченних перевірок і кастів `(String)`, `(User)` при витягуванні елементів з колекцій або контейнерів:

```java
// Без дженериків:
User user = (User) userList.get(0);

// З дженериками: компілятор вставляє неявний cast автоматично
User user = userList.get(0);
```

### 3. Перевикористання алгоритмів (Code Reusability)
Один і той самий алгоритм можна написати один раз і використовувати для будь-яких типів даних:

```java
public class Box<T> {
    private T item;
    public void put(T item) { this.item = item; }
    public T get() { return item; }
}

Box<String> stringBox = new Box<>(); // Коробка для рядків
Box<Order> orderBox = new Box<>();   // Та сама коробка для замовлень
```

## 🟡 Middle Level

### 1. Параметричний поліморфізм проти поліморфізму підтипів

Часто виникає питання: *«Навіщо потрібні дженерики, якщо можна просто приймати `Object`?»*

Різниця полягає у збереженні інформації про конкретний тип даних:

```java
// Підхід на Object (втрачає зв'язок між аргументом і результатом):
public static Object echoObject(Object input) {
    return input;
}
String s = (String) echoObject("Hello"); // Втрачаємо тип, потрібен каст

// Підхід на Generics (пов'язує тип входу з типом виходу):
public static <T> T echoGeneric(T input) {
    return input;
}
String s = echoGeneric("Hello"); // Компілятор знає, що T = String!
```

### 2. Самодокументований та виразний API

Дженерики роблять контракти методів зрозумілими та однозначними без необхідності читати документацію:
- Сигнатура `Optional<User> findById(Long id)` відразу повідомляє розробнику: метод поверне або `User`, або порожній контейнер.
- Сигнатура `CompletableFuture<List<Order>> fetchOrders()` гарантує, що результатом асинхронної задачі буде суворо список замовлень.

### 3. Узагальнені алгоритми з обмеженнями (Bounded Algorithms)

Дженерики дозволяють писати алгоритми, що гарантують наявність певних методів у аргументів:

```java
// Алгоритм працює з БУДЬ-ЯКИМ типом, який вміє порівнюватися з собою:
public static <T extends Comparable<T>> T findMax(List<T> items) {
    if (items.isEmpty()) return null;
    T max = items.get(0);
    for (T item : items) {
        if (item.compareTo(max) > 0) { // compareTo гарантовано існує!
            max = item;
        }
    }
    return max;
}

// Працює з коробки для чисел, рядків, дат:
Integer maxInt = findMax(List.of(1, 5, 3));
String maxStr = findMax(List.of("apple", "zebra", "banana"));
```

## 🔴 Senior Level

### Архітектурні переваги стирання типів (Type Erasure)

Парадоксально, але реалізація дженериків через стирання типів (Type Erasure) надала Java дві найважливіші системні переваги:

1. **Бінарна сумісність (Migration Compatibility)**:
   При переході з Java 1.4 на Java 5 корпоративний світ не довелося перекомпільовувати заново. Старий код, що використовує сирі типи `List`, працює в одній JVM з новим кодом `List<String>` без необхідності дублювання класів.
2. **Відсутність роздування коду (Zero Code Bloat)**:
   У мовах із мономорфізацією (C++ шаблони) компілятор генерує окрему копію машинного коду під кожну комбінацію параметрів (`std::vector<int>`, `std::vector<double>`, `std::vector<string>`), що призводить до колосального роздування розміру виконуваних файлів. У Java компілюється **рівно один клас `ArrayList.class`**, що працює з усіма типами.

### Приховані накладні витрати: Примітиви та Автоупакування

Хоча на рівні логіки дженерики мають Zero Runtime Overhead, вони несуть приховані накладні витрати при роботі з примітивами:

```java
List<Integer> list = new ArrayList<>();
list.add(42); // Автоупакування: int 42 загортається в об'єкт new Integer(42)!
```

- **Оверхед по пам'яті**: Примітив `int` займає 4 байти. Об'єкт `Integer` у 64-бітній JVM з Compressed OOPs займає **16–24 байти** (12 байтів заголовок + 4 байти значення + вирівнювання) плюс 8 байтів на посилання в масиві. Витрата пам'яті зростає у 4–6 разів!
- **CPU Cache Misses**: При ітерації по масиву `int[]` процесор читає неперервний блок пам'яті в L1/L2 кеш. У `List<Integer>` масив містить посилання на розрізнені об'єкти в купі, породжуючи постійні промахи кешу процесора.
*(Ця проблема вирішуватиметься в межах **Project Valhalla** через спеціалізовані Generic Value Types).*

### Трюк Sneaky Throws через Generics

Дженерики дозволяють легально обійти перевірку перевірюваних винятків (`checked exceptions`) компілятором без зміни сигнатури методу:

```java
public final class SneakyThrows {
    @SuppressWarnings("unchecked")
    public static <E extends Throwable> void sneakyThrow(Throwable t) throws E {
        throw (E) t; // Каст до T стирається до Throwable в рантаймі!
    }
}

// Використання: кидаємо IOException без блоку try-catch та throws!
public void execute() {
    SneakyThrows.sneakyThrow(new IOException("Disk failure"));
}
```

## 4 Tricky Questions

### 1. Яким чином дженерики дозволяють реалізувати трюк Sneaky Throws (викидання перевірюваного винятку без оголошення `throws`)?
**Відповідь:** 
Трюк заснований на стиранні типів. Оголошується параметризований метод:
```java
@SuppressWarnings("unchecked")
public static <E extends Throwable> void sneakyThrow(Throwable t) throws E {
    throw (E) t;
}
```
При виклику `SneakyThrows.<RuntimeException>sneakyThrow(new IOException())` компілятор звіряє оголошений тип $E$ (`RuntimeException`) і вважає, що викидається неперевірюваний виняток, тому не вимагає додавання `throws IOException` у сигнатуру викликаючого методу. 

У рантаймі ж через стирання типів приведення `(E) t` перетворюється на звичайний `throw (Throwable) t`, і перевірюваний виняток `IOException` безперешкодно летить вгору по стеку викликів.

### 2. Чому в Java заборонено створювати дженерик-винятки (`class MyException<T> extends Exception`)?
**Відповідь:** 
Тому що механізм обробки винятків (`try-catch`) цілком працює **під час виконання програми (в рантаймі)**. 

Якби параметризовані винятки були дозволені:
```java
try {
    doWork();
} catch (MyException<String> e) {
    // ...
} catch (MyException<Integer> e) { // ❌ Помилка!
    // ...
}
```
Через стирання типів віртуальна машина в рантаймі бачить обидва блоки як `catch (MyException e)`. JVM не змогла б розрізнити, який саме блок `catch` повинен перехопити виняток, що повністю зламало б логіку обробки помилок. Тому JLS §8.1.2 суворо забороняє оголошення підкласів `Throwable` з параметрами типів.

### 3. У чому фундаментальна різниця між перевикористанням коду через поліморфізм підтипів (`Object` / базові інтерфейси) та параметричний поліморфізм (Дженерики)?
**Відповідь:** 
- **Поліморфізм підтипів (Subtyping)** стирає знання про конкретний тип на вході: метод приймає базовий тип (`Object` або `Shape`) і повертає базовий тип. Викликаючий код втрачає інформацію про те, який саме конкретний клас був переданий, і змушений робити небезпечне низхідне приведення (downcasting).
- **Параметричний поліморфізм (Generics)** створює суворий типізований зв'язок між аргументами та результатом: тип фіксується змінною $T$. Метод може приймати `T` і повертати `List<T>`, гарантуючи викликаючому коду збереження типу без кастів та втрати інформації.

### 4. Чи правда, що дженерики не дають накладних витрат у runtime (Zero Runtime Overhead)?
**Відповідь:** 
Для посилальних типів це твердження практично вірне: дженерики дають нульовий оверхед по пам'яті та коду (один клас на всі типи, а неявні інструкції `checkcast` оптимізуються JIT-компілятором). 

Однак при роботі з числовими та логічними типами дженерики призводять до **значних накладних витрат через автоупакування**: примітиви вимушено упаковуються в посилальні класи-обгортки (`int` $\rightarrow$ `Integer`, `double` $\rightarrow$ `Double`). Це збільшує споживання пам'яті в кілька разів, перевантажує збирач сміття та руйнує кеш-локальність процесора (CPU cache locality).

## 🎯 Шпаргалка для інтерв'ю

### Топ-5 переваг дженериків

1. **Compile-Time Type Safety**: Помилки ловляться компілятором, запобігаючи `ClassCastException` у production.
2. **Elimination of Casts**: Позбавляє код від сотень ручних приведень типів.
3. **Parametric Polymorphism**: Алгоритми пишуться один раз для будь-яких типів (`Collections.sort`, `Optional<T>`).
4. **Self-Documenting Code**: Сигнатури методів явно оголошують типи даних, що повертаються.
5. **No Code Bloat**: Стирання типів генерує рівно один `.class` файл на весь параметризований тип, на відміну від C++ шаблонів.

### На чому ловлять на співбесіді
- ❌ *«Дженерик-винятки корисні»*: `class E<T> extends Exception` заборонений у Java.
- ❌ *«Дженерики для примітивів безкоштовні»*: `List<Integer>` у рази повільніший і важчий за `int[]` через боксинг.
- ❌ *«Дженерики стираються без сліду»*: Сигнатури зберігаються в атрибуті `Signature` (рефлексія через `TypeToken`).
