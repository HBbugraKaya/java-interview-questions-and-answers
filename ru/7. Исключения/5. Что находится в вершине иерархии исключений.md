# Что находится в вершине иерархии исключений

---

## 🟢 Junior Level

В самой вершине иерархии всех исключений и ошибок в языке Java находится класс **`java.lang.Throwable`** (наследующийся напрямую от `java.lang.Object`).

Только объекты класса `Throwable` или его наследников могут быть:
1. Выброшены с помощью ключевого слова **`throw`**.
2. Объявлены в сигнатуре метода с помощью ключевого слова **`throws`**.
3. Перехвачены в секции **`catch (...)`** блока `try-catch`.

Попытка написать `throw new String("Error");` или `catch (Object obj)` приведет к ошибке компиляции.

### Древовидная структура иерархии

```
                           java.lang.Object
                                  │
                        java.lang.Throwable
                                  │
                 ┌────────────────┴────────────────┐
                 ▼                                 ▼
         java.lang.Error                 java.lang.Exception
      (Системные аварии JVM)           (Ошибки логики и среды)
                 │                                 │
     ┌───────────┴───────────┐         ┌───────────┴───────────┐
     ▼                       ▼         ▼                       ▼
OutOfMemoryError   StackOverflowError Checked Exceptions  RuntimeException
                                      (IOException,       (Unchecked: NPE,
                                       SQLException)       IllegalArgument)
```

### Две главные ветви

1. **`java.lang.Error`:** Сигнализирует о критических аппаратных или системных сбоях виртуальной машины JVM (нехватка физической памяти, переполнение стека потока, повреждение байткода). Обычный прикладной код **не должен пытаться перехватывать `Error`**.
2. **`java.lang.Exception`:** Сигнализирует об ошибках уровня приложения и инфраструктуры (не найден файл, отвалилась сеть, переданы неверные данные). Должен обрабатываться программно.

## 🟡 Middle Level

### Внутреннее устройство класса Throwable

Класс `Throwable` инкапсулирует 5 ключевых полей, определяющих состояние любой ошибки:

```java
public class Throwable implements Serializable {
    private String detailMessage;             // Текстовое описание ошибки
    private Throwable cause = this;          // Причина (вложенное исключение)
    private StackTraceElement[] stackTrace;  // Массив фреймов стека вызовов
    private List<Throwable> suppressedExceptions; // Подавленные исключения (Java 7+)
    private transient Object backtrace;      // Нативный указатель на стек JVM
}
```

1. **`detailMessage`:** Сообщение, передаваемое в конструктор и возвращаемое методом `getMessage()`.
2. **`cause` (Chained Exceptions):** Ссылка на первопричину сбоя (инициализируется в конструкторе или через метод `initCause(Throwable)`). Позволяет исследовать цепочку причин с помощью `getCause()`.
3. **`backtrace`:** Скрытое `transient` поле, заполняемое нативным методом **`fillInStackTrace()`** при создании объекта. Хранит снимок кадров выполнения потока на уровне ядра JVM.
4. **`suppressedExceptions`:** Список исключений, подавленных в конструкции `try-with-resources` (доступен через `getSuppressed()`).

### Почему Throwable реализует java.io.Serializable?

Исторически во времена создания Java (1995–1997 гг.) ключевой распределенной технологией был протокол **RMI (Remote Method Invocation)** и спецификация EJB. 
Если метод удаленного сервера завершался ошибкой, JVM обязана была сериализовать объект исключения по сети и передать его клиенту.

*Современный подводный камень:* При сериализации нативный указатель `backtrace` недоступен. JVM вынуждена «материализовать» нативную структуру в огромный массив тяжеловесных Java-объектов `StackTraceElement[]`, что приводит к сильному раздуванию сетевого трафика и расходу памяти.

## 🔴 Senior Level

### StackWalker API (Java 9+): Современная альтернатива Throwable

До Java 9 единственным способом программного анализа стека вызовов было создание фиктивного исключения:
```java
StackTraceElement[] frames = new Throwable().getStackTrace();
```
Этот подход крайне неэффективен: JVM делает полную остановку потока, собирает абсолютно все фреймы до самого основания (до `main` или треда Tomcat) и выделяет память под весь массив.

Начиная с Java 9, стандартом анализа стека стал **`java.lang.StackWalker`**:
- Поддерживает **ленивую (lazy) вычитку**: фреймы парсятся только до тех пор, пока вы читаете поток `Stream<StackFrame>`.
- Позволяет отфильтровывать внутренние классы рефлексии и Spring CGLIB прокси без выделения лишней памяти в куче.

```java
package com.example.diagnostic;

import java.lang.StackWalker.StackFrame;
import java.util.List;

public class StackInspector {

    private static final StackWalker WALKER = 
            StackWalker.getInstance(StackWalker.Option.RETAIN_CLASS_REFERENCE);

    // Извлекает имя непосредственного вызывающего метода за O(1) без создания Exception
    public static String getImmediateCaller() {
        return WALKER.walk(frames -> frames
                .skip(1) // Пропускаем сам метод getImmediateCaller
                .findFirst()
                .map(StackFrame::getMethodName)
                .orElse("UNKNOWN"));
    }

    // Поиск первого класса вне текущего пакета
    public static List<String> getExternalCallers() {
        return WALKER.walk(frames -> frames
                .map(StackFrame::getClassName)
                .filter(className -> !className.startsWith("com.example.diagnostic"))
                .limit(5)
                .toList());
    }
}
```

### Конструктор Java 7+ с флагами подавления и стека

В классе `Throwable` присутствует защищенный конструктор:
```java
protected Throwable(String message, Throwable cause,
                    boolean enableSuppression,
                    boolean writableStackTrace)
```
- **`enableSuppression = false`:** Запрещает накопление подавленных исключений (экономит память, `getSuppressed()` вернет пустой массив).
- **`writableStackTrace = false`:** Полностью блокирует вызов `fillInStackTrace()`. Поле `backtrace` остается `null`, стек-трейс не формируется. Это ускоряет создание экземпляра исключения в десятки раз.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> В вершине иерархии исключений Java находится класс **`java.lang.Throwable`**. Только его потомки могут передаваться в операторы `throw`, `throws` и `catch`. 
> 
> `Throwable` делится на две фундаментальные ветви:
> 1. **`java.lang.Error`** — неустранимые системные отказы виртуальной машины JVM (`OutOfMemoryError`, `StackOverflowError`), которые прикладной код не должен перехватывать.
> 2. **`java.lang.Exception`** — прикладные ошибки (делятся на checked и unchecked `RuntimeException`).
> 
> Внутри `Throwable` содержит `message`, первопричину `cause`, массив `suppressedExceptions` и скрытое нативное поле `backtrace`, заполняемое методом `fillInStackTrace()`. Начиная с Java 9, для высокопроизводительного анализа стека вызовов вместо `new Throwable().getStackTrace()` используется потоковый **`StackWalker`**.

### 4 каверзных вопроса с ответами

1. **Можно ли выбросить экземпляр класса `Object`, написав `throw new Object();`?**
   *Ответ:* Нет, код не скомпилируется. Спецификация Java (JLS §14.18) требует, чтобы операнд оператора `throw` имел тип, приводимый к `java.lang.Throwable`.

2. **Зачем в Java 7 в класс Throwable добавили механизм Suppressed Exceptions?**
   *Ответ:* Механизм добавлен для поддержки конструкции `try-with-resources`. Если исключение выброшено из тела блока `try`, а при закрытии ресурса в `close()` возникает второе исключение, первое исключение выбрасывается как основное, а второе прикрепляется к нему вызовом `addSuppressed()`, предотвращая потерю информации о сбое.

3. **Почему StackWalker работает быстрее, чем `Thread.currentThread().getStackTrace()` или `new Throwable().getStackTrace()`?**
   *Ответ:* Старый подход монолитно собирает полный стек вызовов и материализует все элементы в массив `StackTraceElement[]`. `StackWalker` работает лениво (lazily) через `Stream<StackFrame>`, позволяя прервать чтение стека на нужной глубине (например, взять только 1-й фрейм вызывающего) без разбора остальных 50 фреймов.

4. **Почему перехват `catch (Throwable t)` в сервисе приводит к зомби-процессам при утечке памяти?**
   *Ответ:* Потому что блок перехватит `java.lang.OutOfMemoryError`. Память кучи не освободится, но процесс продолжит жить с нарушенными инвариантами и зависшими локами, не отвечая на запросы и не падая, что препятствует оркестратору (Kubernetes) перезапустить дефектный под.

### Красные флаги (чего категорически нельзя говорить)
- ❌ *«В вершине иерархии исключений находится класс Exception»* (в вершине находится `Throwable`, а над ним только `Object`).
- ❌ *«Error наследуется от Exception»* (`Error` и `Exception` — параллельные независимые ветви, наследующиеся от `Throwable`).
- ❌ *«Чтобы узнать, кто вызвал мой метод, нужно создать new Throwable() и посмотреть нулевой элемент массива»* (с Java 9 для этого существует легковесный `StackWalker`).
- ❌ *«Throwable перехватывать полезно в каждом методе, это гарантирует 100% аптайм»* (перехват `Error` ломает стабильность JVM).
