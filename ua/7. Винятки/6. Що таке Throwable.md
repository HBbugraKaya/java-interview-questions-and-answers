# Що таке Throwable

---

## 🟢 Junior Level

**`java.lang.Throwable`** — це суперклас усіх винятків та помилок у мові Java. Лише екземпляри цього класу (або його нащадків) можуть бути передані в інструкцію **`throw`**, оголошені в секції **`throws`** методу або перехоплені блоком **`catch`**.

Він успадковується безпосередньо від `java.lang.Object` і реалізує інтерфейс `java.io.Serializable`.

### Ієрархія нащадків

```
                           java.lang.Throwable
                                  │
                 ┌────────────────┴────────────────┐
                 ▼                                 ▼
         java.lang.Error                 java.lang.Exception
     (Фатальні аварії JVM)             (Прикладні винятки)
                 │                                 │
     ┌───────────┴───────────┐         ┌───────────┴───────────┐
     ▼                       ▼         ▼                       ▼
OutOfMemoryError   StackOverflowError Перевірювані винятки  RuntimeException
                                     (IOException тощо)   (NPE, IllegalArgument)
```

### Ключові методи класу Throwable

| Метод | Призначення |
| :--- | :--- |
| **`getMessage()`** | Повертає рядковий опис помилки, переданий у конструктор. |
| **`getCause()`** | Повертає причину збою (вихідний виняток) або `null`, якщо причини немає. |
| **`initCause(Throwable)`** | Встановлює першопричину (якщо вона не була задана в конструкторі). Можна викликати лише один раз. |
| **`getStackTrace()`** | Повертає масив елементів стека `StackTraceElement[]` для програмного аналізу. |
| **`addSuppressed(Throwable)`** | Додає пригнічений (suppressed) виняток (використовується в `try-with-resources`). |
| **`getSuppressed()`** | Повертає масив усіх пригнічених винятків `Throwable[]`. |
| **`printStackTrace()`** | Виводить текстовий стек-трейс у стандартний потік помилок `System.err` *(у продакшені категорично не використовується!)*. |

## 🟡 Middle Level

### Чому Throwable — це абстрактний за задумом клас, а не інтерфейс?

На співбесідах часто запитують: *«Чому автори Java спроєктували Throwable як клас, а не як інтерфейс Throwableable?»*

**Архітектурні причини:**
1. **Необхідність зберігання стану:** Для формування винятку потрібно інкапсулювати стан: повідомлення `detailMessage`, посилання на причину `cause`, список `suppressedExceptions` та нативний вказівник `backtrace`. Інтерфейси в Java не можуть мати полів екземпляра.
2. **Специфіка взаємодії з JVM:** Віртуальна машина JVM при створенні об'єкта винятку зобов'язана викликати нативний код заповнення стека викликів (`fillInStackTrace()`). Інтерфейс не може гарантувати наявність необхідної структури пам'яті та нативних хуків усередині C++ ядра JVM (HotSpot).
3. **Типобезпека та цілісність моделі:** Якби `Throwable` був інтерфейсом, розробник міг би оголосити `class MyService implements Throwable` і передати робочий Spring-бін сервісу в інструкцію `throw`, що призвело б до порушення архітектурної семантики мови.

### Небезпека перехоплення `catch (Throwable t)`

Перехоплення `catch (Throwable t)` у прикладних методах вважається серйозним антипатерном, оскільки воно перехоплює не лише помилки застосунку, а й **`java.lang.Error`**:
- Якщо у JVM вичерпується оперативна пам'ять (`OutOfMemoryError`), перехоплення `Throwable` завадить природному падінню або аварійному перезапуску контейнера.
- Потік продовжить виконання в умовах пошкодженої купи (Heap Corruption), утримуючи розділювані блокування моніторів і викликаючи каскадне зависання всієї системи.
- **Єдине місце, де допустимий `catch (Throwable t)`** — це зовнішній цикл фонового потоку-демона найвищого рівня або обробник вхідних повідомлень (наприклад, Kafka Consumer Loop), де необхідно залогувати критичний збій та виконати контрольовану аварійну зупинку через `System.exit(1)`.

### Чому метод `printStackTrace()` заборонений у продакшені?

1. **Блокування потоків (Thread Contention):** `System.err` усередині використовує блокування (`PrintStream.println()` синхронізований за внутрішнім монітором). За одночасного сплеску помилок сотні потоків блокуватимуть один одного на виведенні в консоль.
2. **Руйнування структури логів у Kubernetes:** У сучасних хмарних середовищах логи збираються демонами (Fluentd, Promtail, Vector) у форматі JSON. Виклик `printStackTrace()` випльовує десятки окремих рядків у `stderr`, розбиваючи один виняток на безліч розрізнених записів у Kibana / Grafana Loki.
3. **Втрата контексту (MDC):** `printStackTrace()` не виводить контекст логування (MDC): `traceId`, `spanId`, `userId`, що унеможливлює трейсинг у мікросервісній архітектурі.

*Замість цього завжди використовують структурований логер:*
```java
log.error("Failed to process transaction for account {}", accountId, exception);
```

### Конструктор для оптимізації продуктивності

Починаючи з Java 7, клас `Throwable` надає спеціальний `protected`-конструктор:
```java
protected Throwable(String message, Throwable cause,
                    boolean enableSuppression,
                    boolean writableStackTrace)
```
Якщо встановити `writableStackTrace = false`, нативний виклик `fillInStackTrace()` пропускається. Це прискорює створення об'єкта винятку в десятки разів, що критично для високонавантажених бібліотек (наприклад, валідаторів або парсерів), де винятки використовуються для внутрішнього управління потоком керування.

## 🔴 Senior Level

### Асинхронне «зшивання» стек-трейсів (Stack Trace Stitching)

У сучасних реактивних та асинхронних фреймворках (Project Reactor, CompletableFuture, Virtual Threads) завдання постійно перемикається між різними потоками пулу. Коли виникає помилка, стандартний стек-трейс `Throwable` містить лише 2–3 фрейми робочого потоку `ForkJoinPool.worker`, повністю приховуючи бізнес-контекст точки створення завдання.

Для розв'язання цієї проблеми архітектори застосовують методи **`setStackTrace()`** та **`initCause()`** для програмного об'єднання контекстів:

```java
package com.example.async;

import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CompletionException;

public class AsyncStackStitcher {

    public static <T> CompletableFuture<T> withCallerStack(CompletableFuture<T> future) {
        // Фіксуємо стек потоку, який ініціював асинхронне завдання
        StackTraceElement[] callerStack = Thread.currentThread().getStackTrace();

        return future.exceptionally(ex -> {
            // Зшиваємо асинхронний стек з оригінальним стеком ініціатора
            StackTraceElement[] asyncStack = ex.getStackTrace();
            StackTraceElement[] combined = new StackTraceElement[asyncStack.length + callerStack.length];

            System.arraycopy(asyncStack, 0, combined, 0, asyncStack.length);
            System.arraycopy(callerStack, 0, combined, asyncStack.length, callerStack.length);

            ex.setStackTrace(combined);
            throw new CompletionException("Asynchronous execution failed", ex);
        });
    }
}
```

### Захист від циклічних залежностей у Cause і Suppressed

Клас `Throwable` містить вбудований захист від нескінченних циклів:
1. Якщо спробувати зробити `t1.initCause(t2)` і `t2.initCause(t1)`, метод `initCause()` викине:
   `IllegalArgumentException: Self-causation not permitted`.
2. Якщо викликати `t1.addSuppressed(t1)`, метод викине:
   `IllegalArgumentException: Self-suppression not permitted`.

При програмному обході ланцюжка причин (`getCause()`) Senior-розробник зобов'язаний використовувати виявлення циклів (наприклад, за допомогою `Set<Throwable> visited = Collections.newSetFromMap(new IdentityHashMap<>())`), щоб захиститися від зависання або переповнення стека при десеріалізації сторонніх винятків або кастомних реалізаціях.

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь
> **`Throwable`** — це базовий клас усієї системи обробки винятків у Java. Лише його прямі або непрямі нащадки можуть використовуватися з ключовими словами `throw`, `throws` і `catch`.
>
> Він розділяється на дві головні гілки:
> - **`Error`** — системні невиправні аварії JVM (`OutOfMemoryError`, `StackOverflowError`), перехоплювати які в бізнес-коді категорично заборонено.
> - **`Exception`** — прикладні помилки (включно з неперевірюваними `RuntimeException`).
>
> `Throwable` інкапсулює повідомлення, причину (`cause`), пригнічені винятки (`suppressed`) та нативний вказівник на стек `backtrace`. Виклик `printStackTrace()` у реальних застосунках заборонений через синхронізацію на `System.err` та розбиття JSON-логів у контейнерах; логувати винятки слід виключно через SLF4J / Logback, передаючи об'єкт помилки останнім аргументом.

### 4 каверзних питання з відповідями

1. **Чому клас Throwable спроєктований як клас, а не як інтерфейс?**
   *Відповідь:* `Throwable` повинен містити стан (`cause`, `suppressedExceptions`, `detailMessage`) та нативну структуру даних `backtrace`, що заповнюється ядром JVM при обході стека потоку через `fillInStackTrace()`. Інтерфейси не можуть містити полів екземпляра і не можуть гарантувати пряму взаємодію з C++ ядром HotSpot JVM.

2. **Чим загрожує виклик `e.printStackTrace()` у високонавантаженому багатопотоковому сервісі?**
   *Відповідь:* Потік `System.err` синхронізований на рівні `PrintStream`. За одночасного виникнення винятків у десятках потоків виникне жорстка конкуренція за блокування (Thread Contention) консольного виведення, що призведе до різкого падіння пропускної здатності всього застосунку.

3. **Що робить метод `Throwable.addSuppressed(Throwable exception)` і в якому сценарії він використовується?**
   *Відповідь:* Метод прикріплює вторинний (пригнічений) виняток до первинного. Він автоматично викликається компілятором у конструкції `try-with-resources`: якщо під час виконання блоку `try` виникла помилка, а потім метод `AutoCloseable.close()` також викинув виняток, виняток закриття додається до списку пригнічених, щоб не затерти вихідну першопричину аварії.

4. **Як програмно захиститися від зациклення при обході ланцюжка `t.getCause()`?**
   *Відповідь:* Хоча метод `initCause()` валідує прямі цикли, при складній десеріалізації або перевизначенні `getCause()` можливі циклічні посилання. Для безпечного пошуку кореневої причини (Root Cause) запам'ятовують відвідані об'єкти в `IdentityHashMap` (перевірка за посилальною ідентичністю `==`).

### Червоні прапорці (чого категорично не можна говорити)
- ❌ *«Throwable — це інтерфейс, який можна імплементувати в будь-якому класі»* (це клас, що наслідується від Object).
- ❌ *«printStackTrace() — це стандартний і правильний спосіб логування помилок у продакшені»* (груба помилка; потрібно використовувати структурований логер SLF4J).
- ❌ *«Перехоплення catch (Throwable t) у сервісі гарантує надійність застосунку»* (навпаки, призводить до зомбі-процесів при `OutOfMemoryError`).
- ❌ *«Виняток можна викинути через throw без успадкування від Throwable»* (оператор `throw` суворо вимагає екземпляр класу `Throwable`).
