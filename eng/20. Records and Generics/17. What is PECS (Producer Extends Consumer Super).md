# What is PECS (Producer Extends Consumer Super)

**PECS** is the fundamental design mnemonic coined by Joshua Bloch in *Effective Java* (Item 31) to guide the selection of bounded wildcards in generic method signatures and API design:

> **P**roducer **E**xtends, **C**onsumer **S**uper

---

## 🟢 Junior Level

### Core Definitions
- **Producer Extends (`? extends T`):** If a parameterized container or parameter is a **supplier/source of data** (your method only *reads* elements from it), declare it with `? extends T`.
- **Consumer Super (`? super T`):** If a parameterized container or parameter is a **receiver/sink of data** (your method *writes* elements into it), declare it with `? super T`.

```java
// Classic PECS example: copying items from a source to a destination
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (T item : src) { // src is a PRODUCER: provides items of type T
        dest.add(item);  // dest is a CONSUMER: accepts items of type T
    }
}

List<Integer> integers = List.of(1, 2, 3);
List<Number> numbers = new ArrayList<>();

// Without PECS, this would fail compilation due to generic invariance:
copy(numbers, integers); // Compiles cleanly: dest = List<Number>, src = List<Integer>
```

If the method signature were declared without wildcards (`copy(List<T> dest, List<T> src)`), the call `copy(numbers, integers)` would fail compilation because `List<Integer>` is not a subtype of `List<Number>`.

## 🟡 Middle Level

### 1. Achieving Public API Flexibility
The primary purpose of PECS is to make public methods flexible for callers without compromising compile-time type safety.

Consider a utility calculating the sum of numbers:
```java
// Rigid API (without wildcards):
public static double sumRigid(List<Number> numbers) {
    double total = 0.0;
    for (Number n : numbers) total += n.doubleValue();
    return total;
}

List<Integer> intList = List.of(1, 2, 3);
// sumRigid(intList); // Compilation Error: List<Integer> is NOT a List<Number>!

// Flexible API adhering to PECS (numbers is only read -> Producer Extends):
public static double sumFlexible(List<? extends Number> numbers) {
    double total = 0.0;
    for (Number n : numbers) total += n.doubleValue();
    return total;
}

sumFlexible(intList); // Compiles cleanly for List<Integer>, List<Double>, List<BigDecimal>
```

### 2. PECS in Java Functional Interfaces and Streams
The Java 8 standard library functional interfaces are designed around PECS:

```java
// Function consumes T (Consumer) and produces R (Producer):
@FunctionalInterface
public interface Function<T, R> {
    // Higher-order composition uses PECS:
    default <V> Function<T, V> andThen(Function<? super R, ? extends V> after) { ... }
}

// java.util.stream.Stream:
<R> Stream<R> map(Function<? super T, ? extends R> mapper);
```
- `Function<? super T, ...>`: The mapper can accept an argument of type $T$ or any supertype of $T$ (e.g., passing a `Function<Object, String>` to map a `Stream<Integer>`).
- `Function<..., ? extends R>`: The mapper can produce any subtype of $R$ into the resulting stream.

## 🔴 Senior Level

### The Golden Rule of Return Types: Never Return Wildcards
Joshua Bloch states: *"Do not use wildcard types as return types. Rather than providing additional flexibility for your users, it forces them to use wildcard types in client code."*

```java
// Anti-Pattern: Wildcard return type
public List<? extends User> getActiveUsers() { ... }

// Client code becomes severely degraded:
List<? extends User> users = service.getActiveUsers();
// users.add(new User()); // Compilation Error: Cannot add elements to ? extends!
```

When a method returns a wildcard:
1. Callers cannot invoke write operations on the returned collection (it only accepts `null`).
2. Callers are forced to propagate wildcard declarations through their own variables and method boundaries.
3. Follow Postel's Law: **Be liberal in what you accept (use wildcards for input parameters), and strict in what you return (return precise, concrete types).**

```java
// Idiomatic API:
public List<User> getActiveUsers() { ... }
```

### Deconstructing `Collections.max`
The standard library declaration of `Collections.max` represents the pinnacle of PECS design:

```java
public static <T extends Comparable<? super T>> T max(Collection<? extends T> coll)
```

1. **`Collection<? extends T> coll` (Producer):**
   The collection parameter only supplies elements for the search algorithm. Marking it `? extends T` allows callers to pass a `List<Integer>` when $T$ is inferred as `Number`, or a `List<SubTask>` when $T$ is `Task`.
2. **`<T extends Comparable<? super T>>` (Consumer):**
   The `Comparable` interface is a **consumer** because `compareTo(T o)` takes another object as an input argument.
   If declared strictly as `Comparable<T>`, a subclass hierarchy such as:
   ```java
   public class BaseEntity implements Comparable<BaseEntity> { ... }
   public class OrderEntity extends BaseEntity { ... }
   ```
   would fail compilation when calling `Collections.max(orders)`. `OrderEntity` does not implement `Comparable<OrderEntity>`; it implements `Comparable<BaseEntity>`. Marking it `Comparable<? super T>` allows `OrderEntity` to use its ancestor's comparison logic seamlessly.

## 4 Tricky Questions

### 1. Why does Joshua Bloch strictly caution against using wildcards in method return types?
**Answer:** Wildcard return types provide zero benefits to the caller while imposing major restrictions. If a method returns `List<? extends User>`, the caller cannot add any elements into that list (the compiler rejects all `.add()` calls except `null`). Furthermore, it forces callers to declare their own variables and downstream parameters with wildcards, polluting the client codebase. Method return types should always be concrete (e.g., `List<User>`) so callers retain full read and write capabilities.

### 2. How does the PECS principle justify the signature of `Stream.map(Function<? super T, ? extends R> mapper)`?
**Answer:** The `Function` argument plays two distinct roles:
1. **Consumer of $T$ (`? super T`):** The function takes elements of type $T$ from the stream to transform them. Allowing `? super T` permits callers to pass a generalized mapper function that operates on a supertype (e.g., passing a function accepting `Number` or `Object` to process a `Stream<Integer>`).
2. **Producer of $R$ (`? extends R`):** The function outputs values that populate the new stream. Allowing `? extends R` ensures that if the stream is typed to `Stream<Number>`, the mapper function is allowed to return specific subtypes such as `Integer` or `Double`.

### 3. If a method must both read elements from a collection and write new elements into it, what generic declaration should you use?
**Answer:** **Do not use wildcards.** You must use an exact, invariant type parameter `<T>`. 

Under the PECS rule, `? extends` is strictly read-only and `? super` is strictly write-only (returning bare `Object` on read). If a container must perform both roles (both Producer and Consumer), type relaxing via wildcards is unsound. The method signature must enforce an invariant type:
```java
public static <T> void replaceElement(List<T> list, int index, T replacement) {
    T old = list.get(index);  // Read as T
    list.set(index, replacement); // Write as T
}
```

### 4. Will calling `addToList(new ArrayList<Cat>())` compile if the method is declared as `void addToList(List<? super Animal> list)`?
**Answer:** **No, it will fail to compile.** 
The wildcard `? super Animal` denotes a collection of some unknown type that is a **superclass** of `Animal` (such as `List<Animal>` or `List<Object>`). 

`Cat` is a **subclass** of `Animal`, not a superclass. If the compiler permitted passing `List<Cat>` into `List<? super Animal>`, the method could legitimately execute `list.add(new Dog())` (since `Dog` is an `Animal`), which would corrupt the `List<Cat>` with a `Dog` instance. The compiler detects this type incompatibility and rejects the call.

## 🎯 Interview Cheat Sheet

- **Core Formula:** **P**roducer **E**xtends, **C**onsumer **S**uper.
- **Producer (`? extends T`):** Source of data. Reading returns $T$. Writing is prohibited (only `null` allowed).
- **Consumer (`? super T`):** Sink of data. Accepts $T$ and its subtypes on write. Reading returns bare `Object`.
- **Both Roles:** Do not use wildcards! Use invariant `<T>`.
- **Return Type Rule:** **Never return wildcards** from methods (`List<T>`, never `List<? extends T>`). Be liberal in what you accept, strict in what you return.
- **Comparators & Functions:** Consumers of data must use `super` (e.g., `Comparable<? super T>`, `Consumer<? super T>`).
- **JDK Hallmark:** `Collections.copy(List<? super T> dest, List<? extends T> src)`.
