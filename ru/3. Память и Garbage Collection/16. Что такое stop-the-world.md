# Что такое stop-the-world

---

## 🟢 Junior Level

**Stop-The-World (STW)** — это специальное состояние виртуальной машины Java, при котором выполнение абсолютно всех прикладных потоков приложения (**Mutator Threads**) принудительно приостанавливается. В это время процессорное время полностью передается системному потоку виртуальной машины (**VM Thread**) для выполнения критически важных системных операций.

---

### Зачем нужен STW?
Главная цель STW — **гарантия консистентности графа памяти**:
- Если бы потоки приложения продолжали менять ссылки и создавать объекты в тот момент, когда сборщик мусора обходит память, адреса объектов постоянно мутировали бы под ногами у GC.
- **Бытовая аналогия:** Групповая фотография на свадьбе. Чтобы снимок получился четким, фотограф кричит: «Замрите на секунду!». Если гости продолжат ходить, снимок получится размытым, а кто-то выйдет за пределы кадра.

---

### Вызывается ли STW только сборщиком мусора?
**НЕТ!** Это один из любимых вопросов на собеседованиях. STW требуется не только для Garbage Collector, но и для множества внутренних операций JVM:
1. **Снятие Thread Dump:** Получение снимка стеков всех потоков (через `jstack` или VisualVM).
2. **Отзыв смещенных блокировок (Biased Lock Revocation):** До Java 15 переключение монитора синхронизации требовало остановки потока.
3. **Деоптимизация кода:** Замена скомпилированного JIT машинного кода обратно на байткод интерпретатора при нарушении оптимистичных спекуляций компилятора.
4. **Горячая замена классов (HotSwap / Class Redefinition):** Перезагрузка байткода классов через JVM Tool Interface (JVMTI) во время отладки.

---

## 🟡 Middle Level

### Механизм безопасных точек (Safepoints)

Потоки приложения не могут остановиться мгновенно на произвольной ассемблерной инструкции (например, на середине создания объекта или между вычислением операндов). Они обязаны дойти до так называемой **Безопасной точки (Safepoint)**.

**Safepoint** — это инструкция в машинном коде, в которой состояние стека потока полностью согласовано, а все указатели на объекты в регистрах и стеке зафиксированы в специальной карте (**OopMap**).

```
┌────────────────────────────────────────────────────────┐
│               ГДЕ JIT РАССТАВЛЯЕТ SAFEPOINTS:          │
├────────────────────────────────────────────────────────┤
│ 1. В точках возврата из методов (Method Exit).         │
│ 2. На обратных переходах не счетных циклов (Backedge). │
│ 3. Перед инструкциями аллокации памяти (new).          │
│ 4. При переходах между Java и нативным кодом (JNI).    │
└────────────────────────────────────────────────────────┘
```

---

### Как аппаратно устроен опрос (Safepoint Polling)

Чтобы остановить потоки, VM Thread не отправляет каждому потоку дорогой системный сигнал ОС:
1. JIT вставляет в каждую точку Safepoint ультрабыструю инструкцию чтения из тестовой страницы памяти (**Safepoint Polling Page**):
   ```assembly
   test %eax, 0x160(%r15)   ; Чтение из специальной страницы опроса
   ```
2. **В нормальном режиме:** Страница доступна для чтения. Чтение происходит мгновенно (попадание в кэш L1, задержка $\approx 1$ такт процессора).
3. **Когда нужен STW:** JVM через системный вызов `mprotect` делает страницу недоступной для чтения (`PROT_NONE`).
4. Следующий же поток, выполняющий чтение, вызывает аппаратное исключение процессора **SIGSEGV** (Page Fault). Системный обработчик сигналов JVM перехватывает его и переводит поток в режим ожидания (Sleep).

---

### Время входа в паузу: TTSP (Time-To-Safepoint)

Общая длительность задержки сервиса складывается из двух фаз:
$$\text{Total Pause Time} = \text{TTSP (Time To Safepoint)} + \text{Operation Time (GC Execution)}$$

- **TTSP** — это время с момента, когда JVM потребовала остановки, до момента, когда **последний медленный поток** приложения дошел до своего Safepoint.
- Все остальные потоки, дошедшие до точки первыми, **уже стоят и ждут**.

## 🔴 Senior Level

### Проблема счетных циклов (Counted Loops Bug)

Классический сценарий многосекундных «зависаний» высоконагруженных систем:

```java
// ❌ COUNTED LOOP: миллионы итераций без Safepoint!
for (int i = 0; i < 1_000_000_000; i++) {
    sum += array[i]; // JIT агрессивно оптимизирует цикл int и вырезает safepoint poll!
}
```

#### Почему это происходит:
JIT-компилятор (C2) предполагает, что цикл со счетчиком типа `int` является коротким. Чтобы выполнить векторизацию (SIMD) и инлайнинг, компилятор **полностью удаляет проверку Safepoint из тела цикла**.

Если такой цикл крутится 2 секунды, **вся JVM будет заблокирована на 2 секунды**, даже если сама сборка мусора занимает всего 2 миллисекунды! В логах GC это выглядит так:
```
[GC(12) Total time for which application threads were stopped: 2.0520000 seconds, Stopping threads took: 2.0490000 seconds]
```
*(Сама сборка мусора заняла 3 мс, а остановка потоков — более 2 секунд!)*

#### Способы решения проблемы Counted Loops:
1. Включить принудительные безопасные точки в счетных циклах:
   ```bash
   -XX:+UseCountedLoopSafepoints
   ```
2. Заменить тип переменной цикла с `int` на `long` (`for (long i = 0; ...)`): для циклов с `long` JIT не считает цикл счетным и гарантированно сохраняет Safepoints.

---

### Локальные рукопожатия: Thread-Local Handshakes (Java 10+, JEP 312)

До Java 10 любая операция, требующая взаимодействия даже с одним потоком (например, снятие стека отдельного потока), вызывала глобальный Stop-The-World для всех сотен потоков в процессе.

В Java 10 представлен механизм **Thread-Local Handshakes**:
- JVM нарезает персональные страницы опроса для каждого потока отдельно.
- Виртуальная машина может инициировать рукопожатие (**Handshake**) с **одним конкретным потоком**, остановив только его, в то время как остальные 999 потоков приложения продолжают обрабатывать боевой трафик.
- Это радикально снизило число глобальных STW-пауз в JVM.

---

### JNI и безопасные точки

Частый вопрос: *«Что происходит с потоком, исполняющим нативный C/C++ код через JNI во время STW?»*
- Поток, находящийся внутри нативного JNI-метода, **не останавливается** во время фазы STW! Поскольку он исполняет нативный код, JVM знает, что он не может манипулировать объектами Java Heap напрямую без JNI-функций.
- Однако в момент, когда нативный метод попытается **вернуться обратно в Java-код** или вызвать JNIEnv-функцию, барьер JNI обнаружит активный Safepoint и заблокирует поток до завершения фазы STW.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «**Stop-The-World (STW)** — это полная приостановка всех прикладных потоков приложения для выполнения системных операций JVM, требующих консистентного состояния памяти. STW используется не только для фаз Garbage Collection, но и для снятия **Thread Dumps**, отзыва блокировок и деоптимизации JIT-кода. Потоки останавливаются в специальных точках — **Safepoints**, опрос которых выполняется через проверку защищенной страницы памяти. Ключевая скрытая проблема задержек — **TTSP (Time-To-Safepoint)**: если один поток застрял в счетном цикле без безопасных точек (`Counted Loop`), все остальные потоки будут ждать его секундами (решается флагом `-XX:+UseCountedLoopSafepoints`)».

---

### 3–4 каверзных вопроса с ответами

1. **Для каких операций JVM, помимо сборки мусора, требуется вызов Stop-The-World?**
   - *Ответ:* STW необходим при снятии полного дампа потоков (Thread Dump через `jstack`), при деоптимизации скомпилированного машинного кода JIT-компилятором, при горячей замене байткода классов (Class Redefinition / HotSwap через JVMTI агенты), при расширении пула дескрипторов и (до Java 15) при отзыве смещенных блокировок (Biased Lock Revocation).

2. **Что такое Time-To-Safepoint (TTSP) и почему он опаснее самой сборки мусора?**
   - *Ответ:* TTSP — это время с момента выставления флага паузы до момента, когда последний работающий поток дойдет до ближайшего Safepoint и уснет. Опасность в том, что все остальные потоки, которые уже дошли до Safepoints, полностью заморожены и простаивают. Если хотя бы один поток застрял в длинном цикле или блокирующем системном вызове ввода-вывода, время общего зависания системы может составить секунды, хотя сам сборщик мусора отработает за пару миллисекунд.

3. **Почему в циклах `for (int i = 0; i < N; i++)` по умолчанию нет Safepoint?**
   - *Ответ:* Чтобы не снижать производительность численных вычислений. Добавление инструкции чтения из страницы памяти на каждой итерации цикла блокирует векторизацию (SIMD-инструкции) и инлайнинг. JIT оптимизирует такие счетные циклы (Counted Loops), считая, что они завершатся быстро. Для предотвращения задержек TTSP на длинных вычислениях используют флаг `-XX:+UseCountedLoopSafepoints`.

4. **Как механизм Thread-Local Handshakes в Java 10+ снизил влияние пауз на систему?**
   - *Ответ:* До появления Handshakes любая операция над потоком требовала глобальной остановки всей JVM. Механизм Thread-Local Handshakes позволил адресно выставлять защитные барьеры индивидуальным потокам. Теперь такие операции, как снятие стека одного потока, отзыв блокировки или остановка потока профилировщиком, выполняются точечно, не затрагивая остальные параллельные потоки приложения.

---

### Типичные ошибки и Red Flags

- 🚩 **Утверждение: «Stop-The-World вызывается ТОЛЬКО сборщиком мусора»** (STW используется для thread dumps, деоптимизаций, смены классов).
- 🚩 **Слепая вера в то, что «пауза GC равна времени работы самого алгоритма сборщика»** (время TTSP часто превышает время самого GC).
- 🚩 **Заблуждение: «JNI-потоки мгновенно блокируются при начале STW»** (JNI-поток продолжает работу в нативном коде и блокируется только при попытке вернуться в Java).
- 🚩 **Игнорирование проблемы Counted Loops при расследовании нерегулярных выбросов Latency (Spikes).**
