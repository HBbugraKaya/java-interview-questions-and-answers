# Можно ли повторно бросить исключение

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
Да, в Java можно повторно выбросить перехваченное исключение с помощью оператора **`throw e;`** внутри блока `catch`. 

Эта техника называется **Rethrowing** и используется тогда, когда текущему методу необходимо выполнить локальное компенсирующее действие (откатить транзакцию, освободить замок, зафиксировать метрику сбоя), но при этом сообщить вышестоящему коду, что операция не удалась.

Критически важно: при выполнении `throw e;` **стек-трейс объекта исключения не перезаписывается** — он сохраняет точную строку и кадры стека первоначального возникновения сбоя.

---

### Базовый пример на Java 21

```java
import java.sql.Connection;
import java.sql.SQLException;

public class TransactionService {

    public void transferFunds(Connection conn, long from, long to, double amount) throws SQLException {
        try {
            conn.setAutoCommit(false);
            debit(conn, from, amount);
            credit(conn, to, amount);
            conn.commit();
        } catch (SQLException e) {
            // 1. Выполняем компенсирующее действие
            conn.rollback();
            // 2. Повторно бросаем ТОТ ЖЕ объект исключения вызывающему коду
            throw e; 
        }
    }

    private void debit(Connection c, long acc, double amt) throws SQLException { }
    private void credit(Connection c, long acc, double amt) throws SQLException { }
}
```

## 🟡 Middle Level

### Два подхода к повторному броску: Pure Rethrow vs Wrapped Rethrow

```
                        Исключение в блоке catch
                                   │
         ┌─────────────────────────┴─────────────────────────┐
         ▼                                                   ▼
[ Pure Rethrow: throw e; ]                  [ Wrapped Rethrow: throw new CustomException(e); ]
- Сохраняет исходный объект и класс         - Переводит ошибку на новый уровень абстракции
- Стек-трейс неизменен                      - Обогащает ошибку контекстом текущего слоя
- Требует throws или перехвата выше         - Создает цепочку причинности (Caused by:)
```

---

### Механика JVM и инструкция `athrow`
На уровне байткода повторный бросок транслируется в стандартную инструкцию `athrow`:
1. Виртуальная машина извлекает ссылку на уже существующий в куче объект исключения `e`.
2. Инструкция `athrow` инициирует немедленную раскрутку стека вызовов (Stack Unwinding) текущего потока в поисках следующего подходящего обработчика в вызывающих методах.
3. Поскольку метод `fillInStackTrace()` повторно не вызывался, массив `StackTraceElement[]` остается неизменным.

---

### Precise Rethrow (Точный проброс в Java 7+)
До Java 7 при перехвате общего предка `catch (Exception e)` компилятор заставлял объявлять `throws Exception` в заголовке метода, даже если в `try` бросались только конкретные checked-исключения.

Начиная с Java 7, компилятор `javac` выполняет статический анализ потока управления:
```java
public class PreciseRethrowService {

    // Компилятор разрешает точные типы, несмотря на catch (Exception e)!
    public void execute() throws IOException, SQLException {
        try {
            readData(); // бросает IOException
            saveData(); // бросает SQLException
        } catch (Exception e) {
            recordFailureMetric(e);
            // Если e не переприсваивалось (effectively final),
            // javac точно знает: вылететь могут ТОЛЬКО IOException или SQLException!
            throw e; 
        }
    }

    private void readData() throws IOException { }
    private void saveData() throws SQLException { }
    private void recordFailureMetric(Exception e) { }
}
```

### Антипаттерны повторного броска

#### 1. Бесполезный Rethrow (No-Op Catch)
```java
// ❌ АНТИПАТТЕРН: нулевая ценность, лишний код
try {
    service.doWork();
} catch (Exception e) {
    throw e; // Зачем перехватывать, если ничего не делается?
}
```

#### 2. Log and Rethrow (Залогируй и пробрось)
```java
// ❌ АНТИПАТТЕРН: дублирование логов
try {
    service.doWork();
} catch (Exception e) {
    log.error("Failed to do work", e); // Залогировали здесь...
    throw e;                           // ...и слой выше залогирует это же исключение еще раз!
}
```
*Правило:* Если вы повторно бросаете исключение, логировать его должен самый верхний слой приложения (например, `@RestControllerAdvice` в Spring).

## 🔴 Senior Level

### Риск вытеснения ошибки при сбое компенсации (Compensation Failure)
Что произойдет, если компенсирующее действие внутри `catch` само завершится ошибкой?

```java
// ❌ ОПАСНОСТЬ: потеря первичного исключения e!
try {
    processPayment();
} catch (PaymentException e) {
    // Если rollback() упадет с SQLException...
    databaseConnection.rollback(); 
    // ...эта строка НИКОГДА НЕ ВЫПОЛНИТСЯ! Первичный PaymentException стерт!
    throw e; 
}
```

#### Идиоматическое решение для Enterprise:
Компенсирующие вызовы внутри блока `catch` оборачиваются в защищенный блок, а возникшая вторичная ошибка прикрепляется через `addSuppressed()`:

```java
try {
    processPayment();
} catch (PaymentException e) {
    try {
        databaseConnection.rollback();
    } catch (Exception rollbackEx) {
        // Сохраняем ошибку отката как подавленную, не теряя первичное исключение!
        e.addSuppressed(rollbackEx);
    }
    throw e; // Гарантированно пробрасываем первичное исключение
}
```

---

### Модификация стека: метод `fillInStackTrace()`
В исключительных случаях (например, при реализации асинхронных мостов или передачи ошибок между потоками) разработчику требуется, чтобы стек-трейс отражал точку повторного выброса, а не точку оригинального создания:

```java
try {
    runWorkerTask();
} catch (CustomException e) {
    // ПЕРЕЗАПИСЬ СТЕКА: нативный вызов fillInStackTrace перезаписывает кадры стека!
    // Оригинальное место возникновения внутри runWorkerTask() будет стерто!
    throw (CustomException) e.fillInStackTrace();
}
```
*Предостережение:* Этот прием стирает оригинальный контекст ошибки и должен применяться только в специализированном системном коде (например, в диспетчерах реактивных потоков).

---

### Влияние на Spring `@Transactional`
Повторный бросок напрямую влияет на транзакционную границу Spring:
- Если из метода с `@Transactional` повторно выбрасывается `RuntimeException` или `Error`, транзакция **автоматически откатывается**.
- Если повторно выбрасывается проверяемый `Exception`, по умолчанию транзакция **НЕ откатится**, если в аннотации не указан атрибут `@Transactional(rollbackFor = Exception.class)`.

## 🎯 Шпаргалка для интервью

### Вопросы для быстрой проверки
1. **Перезаписывается ли стек-трейс исключения при вызове `throw e;` в блоке `catch`?**
   *Ответ:* Нет, стек-трейс не изменяется. Он сохраняет информацию о месте первоначального возникновения сбоя.
2. **Как работает механизм Precise Rethrow в Java 7+?**
   *Ответ:* Компилятор `javac` отслеживает типы исключений, которые реально могут быть выброшены в блоке `try`. При повторном `throw e` из блока `catch (Exception e)` компилятор требует декларировать в `throws` только конкретные типы исходного блока, а не широкий `Exception`.
3. **Что произойдет, если в блоке `catch` перед строкой `throw e;` вызовется метод, который сам выбросит исключение?**
   *Ответ:* Новое исключение прервет выполнение блока `catch`, вытеснит первичное исключение `e` и полетит вверх по стеку. Первичное исключение `e` будет безвозвратно потеряно, если вторичный вызов не был защищен блоком `try-catch` с вызовом `e.addSuppressed(...)`.
4. **Зачем использовать метод `e.fillInStackTrace()` при повторном броске исключения?**
   *Ответ:* Метод `fillInStackTrace()` принудительно перезаписывает стек вызовов текущими фреймами на момент вызова. Это позволяет скрыть внутренние фреймы реализации или зафиксировать точку диспетчеризации в новом потоке, однако полностью стирает исходное место ошибки.

### Типичные ошибки и Red Flags
- ❌ **Утверждение: "При выполнении `throw e;` стек-трейс обновляется текущей строкой":** Классическое непонимание устройства `Throwable`. Стек перезаписывается только при явном вызове `fillInStackTrace()`.
- ❌ **Практика "Log and Throw" (одновременное логирование и проброс):** Порождает каскад одинаковых сообщений об ошибках в логах сервиса.
- ❌ **Незастрахованные компенсирующие действия в `catch`:** Падение отката транзакции затирает первичное бизнес-исключение.
- ❌ **Пустой перехват и бросок `catch (Exception e) { throw e; }`:** Избыточный код, не несущий полезной нагрузки.
