# Какие основные преимущества CompletableFuture перед Future

---

## 🟢 Junior Level

Интерфейс `Future<T>`, появившийся в Java 5, был огромным шагом вперёд по сравнению с прямым управлением `Thread`, однако обладал серьёзным фундаментальным ограничением: он был **пассивным контейнером**. Чтобы узнать статус или получить результат, приходилось блокировать поток через `get()` или опрашивать `isDone()` в цикле.

`CompletableFuture<T>` (Java 8+) предоставил полноценную неблокирующую реактивную модель работы с будущими результатами.

### 5 ключевых преимуществ `CompletableFuture`

1. **Неблокирующая модель (Non-blocking)**: выполнение действий по завершении вычисления через функции обратного вызова (колбэки `thenApply`, `thenAccept`, `thenRun`) без заморозки вызывающего потока.
2. **Монадическая компонуемость (Composability)**: возможность связывать зависимые задачи в конвейеры (пайплайны), где результат одного вычисления автоматически передаётся на вход следующему (`thenCompose`).
3. **Параллельное комбинирование (Fan-out / Fan-in)**: возможность дождаться завершения нескольких параллельных независимых задач (`allOf`, `anyOf`, `thenCombine`).
4. **Декларативная обработка исключений**: обработка ошибок прямо в цепочке вызовов (`exceptionally`, `handle`), аналогично блокам `catch` в синхронном коде.
5. **Явное ручное завершение (Manual Completion / Promise)**: возможность завершить вычисление вручную из любого потока (`complete()`, `completeExceptionally()`), что делает его идеальным мостом для асинхронных событий, веб-сокетов или сетевых колбэков.

### Наглядное сравнение в коде

```java
// ❌ С использованием классического Future:
Future<String> userFuture = executor.submit(() -> fetchUser(userId));
String user = userFuture.get(); // БЛОКИРОВКА ПОТОКА

Future<List<Order>> ordersFuture = executor.submit(() -> fetchOrders(user));
List<Order> orders = ordersFuture.get(); // ЕЩЁ ОДНА БЛОКИРОВКА ПОТОКА

// ✅ С использованием CompletableFuture:
CompletableFuture.supplyAsync(() -> fetchUser(userId), ioExecutor)
    .thenCompose(user -> CompletableFuture.supplyAsync(() -> fetchOrders(user), ioExecutor))
    .thenAccept(orders -> renderOrders(orders));
// Ни один поток не блокируется в ожидании ответа по сети!
```

## 🟡 Middle Level

### 1. Композиция зависимых задач (`thenCompose`) vs Независимых (`thenCombine`)

В классическом `Future` невозможно связать две задачи так, чтобы вторая стартовала автоматически только после завершения первой с её результатом, не блокируя при этом промежуточный поток.

- **`thenCompose` (аналог `flatMap`)**: используется, когда следующая функция сама возвращает `CompletableFuture`:
  ```java
  CompletableFuture<Double> priceFuture = fetchProduct(productId)
      .thenCompose(product -> fetchDiscount(product)); // Избегает вложенности CompletableFuture<CompletableFuture<Double>>
  ```
- **`thenCombine` (аналог `zip`)**: используется, когда две независимые задачи запускаются параллельно, а их результаты объединяются третьей функцией:
  ```java
  CompletableFuture<String> weatherFuture = CompletableFuture.supplyAsync(() -> getWeather());
  CompletableFuture<String> trafficFuture = CompletableFuture.supplyAsync(() -> getTraffic());

  CompletableFuture<String> reportFuture = weatherFuture.thenCombine(
      trafficFuture, 
      (weather, traffic) -> "Погода: " + weather + ", Пробки: " + traffic
  );
  ```

### 2. Декларативная обработка ошибок и восстановление

В `Future` любая ошибка заворачивается в `ExecutionException` при вызове `get()`. Это заставляет оборачивать весь клиентский код в громоздкие блоки `try-catch`.

В `CompletableFuture` ошибка переводит весь последующий конвейер в состояние сбоя (все обычные трансформации пропускаются), пока поток управления не встретит обработчик:
- `exceptionally(Function<Throwable, T> fallback)`: перехватывает исключение и возвращает дефолтное безопасное значение.
- `handle(BiFunction<T, Throwable, R> fn)`: вызывается **всегда** (и при успехе, и при ошибке), позволяя трансформировать оба исхода.

```java
CompletableFuture.supplyAsync(() -> externalPaymentGateway.charge(orderId), ioExecutor)
    .thenApply(receipt -> processReceipt(receipt))
    .exceptionally(ex -> {
        log.warn("Платеж не удался, включаем резервный сценарий: {}", ex.getMessage());
        return createPendingReceipt(orderId);
    });
```

### 3. Механизм тайм-аутов (Java 9+)

В Java 5 `Future.get(long timeout, TimeUnit unit)` выбрасывал `TimeoutException`, но блокировал поток до истечения срока. В Java 9 в `CompletableFuture` появились элегантные неблокирующие методы:
- `orTimeout(timeout, unit)`: если операция не завершилась за отведенное время, фьючер завершается с `TimeoutException`.
- `completeOnTimeout(fallbackValue, timeout, unit)`: если вычисление просрочено, фьючер плавно завершается с переданным значением по умолчанию вместо ошибки.

## 🔴 Senior Level

### Экономика потоков и потребление системных ресурсов

Главное архитектурное преимущество `CompletableFuture` перед `Future` кроется не в удобстве синтаксиса, а в **кардинально иной модели утилизации аппаратных ресурсов**.

1. **Проблема блокирующего ожидания (`Future.get()`):**
   - Каждый заблокированный поток ОС удерживает ~1 МБ стековой памяти (`-Xss`).
   - 10 000 параллельных внешних I/O вызовов через классический `Future` потребуют 10 000 потоков ОС (~10 ГБ только на стеки потоков), что неизбежно приведёт к `java.lang.OutOfMemoryError: unable to create new native thread` и колоссальным задержкам на переключение контекста процессора (Context Switching).
2. **Асинхронный конвейер (`CompletableFuture`):**
   - Задачи находятся в состоянии ожидания (например, зарегистрированы в селекторе NIO или Netty EventLoop) в виде легковесных узлов в куче (heap).
   - Десятки тысяч таких задач могут обслуживаться пулом всего из пары десятков потоков. Потоки не простаивают, а выполняют полезную работу.

### Паттерн Promise и интеграция с внешними событиями

`CompletableFuture` реализует паттерн **Promise** — возможность отвязать завершение вычисления от треда-производителя:

```java
@Service
public class AsyncGatewayClient {
    private final ConcurrentMap<String, CompletableFuture<Response>> inFlight = new ConcurrentHashMap<>();

    public CompletableFuture<Response> sendRequest(Request request) {
        CompletableFuture<Response> promise = new CompletableFuture<>();
        inFlight.put(request.correlationId(), promise);

        // Отправка по сокету/Kafka без ожидания ответа
        socketClient.send(request); 
        return promise;
    }

    // Вызывается потоком-слушателем входящих сетевых пакетов:
    public void onMessageReceived(Response response) {
        CompletableFuture<Response> promise = inFlight.remove(response.correlationId());
        if (promise != null) {
            promise.complete(response); // Завершаем фьючер асинхронно!
        }
    }
}
```

С классическим `FutureTask` реализовать такую связку невозможно, так как `FutureTask` требует передачи `Callable` в момент создания и закрыт для внешнего завершения.

### CompletableFuture против Virtual Threads (Java 21+)

С появлением Virtual Threads (Project Loom) писать синхронный блокирующий код снова стало дешево:
```java
// В Java 21+ виртуальный поток паркуется без удержания потока ОС:
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> f1 = executor.submit(() -> fetchA());
    Future<String> f2 = executor.submit(() -> fetchB());
    String res = f1.get() + f2.get(); // Блокировка виртуального потока почти бесплатна
}
```
**Почему `CompletableFuture` остаётся актуальным:**
1. **Реактивные интерфейсы и интеграция**: сторонние асинхронные SDK (AWS SDK v2, Netty, gRPC, Spring WebClient) возвращают `CompletableFuture` или `Publisher`.
2. **Сложная комбинаторная логика**: паттерны "гонки" (`anyOf`), конкурентное ветвление, кэширование промисов с повторным чтением реализуются через `CompletableFuture` декларативно в одну строку.

## 4 Tricky Questions

### 1. Если при вызове `cf1.thenCombine(cf2, (a, b) -> a + b)` первый фьючер `cf1` завершается аварийно (исключением), что произойдёт со вторым фьючером `cf2`?

**Ответ:**
Фьючер `cf2` **продолжит своё выполнение в фоне**. 
Результирующий фьючер (возвращённый `thenCombine`) немедленно перейдёт в состояние ошибки (`CompletionException`), но вызов `thenCombine` **не отменяет** и не прерывает второй фьючер автоматически. Если `cf2` выполнял тяжёлую операцию или запись в базу данных, она выполнится до конца, если вы вручную не настроите отмену `cf2` через `handle`/`whenComplete`.

### 2. Как избежать "ада колбэков" (Callback Hell) при построении длинных цепочек зависимых CompletableFuture?

**Ответ:**
Ад колбэков в `CompletableFuture` возникает при глубокой вложенности лямбд (когда каждой следующей операции нужны результаты всех предыдущих):
```java
// ❌ Глубокая вложенность (Pyramid of Doom):
fetchUser(id).thenCompose(user -> 
    fetchAccount(user).thenCompose(account -> 
        fetchHistory(account).thenApply(history -> buildReport(user, account, history))
    )
);
```
**Решения:**
1. Использовать промежуточные кортежи/DTO-объекты или `record` для проброса контекста вниз по цепочке.
2. Использовать параллельную группировку через `thenCombine`, если зависимости независимы.
3. В Java 21+ переписать конвейер на синхронный императивный стиль внутри **Virtual Threads** с использованием `StructuredTaskScope`.

### 3. В чём разница между `completeExceptionally(Throwable ex)` и `obtrudeException(Throwable ex)`?

**Ответ:**
- `completeExceptionally(ex)` переводит фьючер в ошибочное состояние **только если он ещё не был завершён** (первое завершение выигрывает по правилу CAS). Если фьючер уже имел результат, метод вернёт `false` и ничего не изменит.
- `obtrudeException(ex)` (и аналогично `obtrudeValue(v)`) **принудительно перезаписывает** результат фьючера, даже если он уже давно успешно завершился другим значением! Этот метод предназначен исключительно для сценариев аварийного восстановления и пост-мортем очистки после сбоев. Использование `obtrude*` в бизнес-логике категорически не рекомендуется, так как это грубо нарушает контракт неизменяемости завершённых промисов и порождает трудноуловимые гонки данных.

### 4. Что произойдёт, если цепочка CompletableFuture завершилась исключением, но ни `join()`, ни `get()`, ни `exceptionally()` не были вызваны?

**Ответ:**
Исключение останется **абсолютно незамеченным (silent failure)**.
Внутри объекта `CompletableFuture` в поле `result` запишется объект `AltResult(ex)`. Поскольку нет подписчиков на ошибку и никто не считывает результат через блокирующие методы, исключение не попадёт ни в `System.err`, ни в логгер, ни в `UncaughtExceptionHandler` потока. Задача завершится тихо, а объект со временем утилизируется сборщиком мусора. Это одна из самых коварных ловушек асинхронного программирования.

## 🎯 Шпаргалка для интервью

### Главное за 60 секунд
- Основные преимущества `CompletableFuture` перед `Future`: неблокирующие колбэки, монадическая композиция (`thenApply`/`thenCompose`), комбинирование нескольких задач (`allOf`/`anyOf`/`thenCombine`), декларативная обработка ошибок (`exceptionally`/`handle`) и возможность ручного перевода в завершённое состояние (`complete`).
- Позволяет масштабировать систему до сотен тысяч параллельных операций ввода-вывода без выделения индивидуального потока ОС под каждую задачу.
- Начиная с Java 9, добавлены встроенные неблокирующие тайм-ауты: `orTimeout()` и `completeOnTimeout()`.

### Типичные ошибки на интервью
- Путать `thenApply` (синхронная трансформация значения, `map`) и `thenCompose` (связывание с возвратом нового `CompletableFuture`, `flatMap`).
- Считать, что `allOf` возвращает результаты всех фьючеров в виде списка (метод возвращает `CompletableFuture<Void>`, сбор результатов нужно выполнять вручную).
- Забывать о проглатывании исключений при отсутствии терминальных методов или обработчиков ошибок.
