# Почему String часто используется как ключ в HashMap

---

## 🟢 Junior Level

Класс `String` — самый популярный и рекомендуемый тип ключа для `HashMap` в Java. Основные причины такого выбора:

1. **Неизменяемость (Immutability):** Объект `String` невозможно изменить после создания. Состояние ключа стабильно, а значит, его хеш-код никогда не изменится во время нахождения в коллекции.
2. **Кэширование `hashCode()`:** Хеш-код вычисляется один раз при первом обращении и сохраняется во внутреннем поле. Повторные вызовы работают мгновенно со сложностью $O(1)$.
3. **Качественная хеш-функция:** Встроенный алгоритм хеширования строк обеспечивает хорошее равномерное распределение по бакетам, минимизируя вероятность коллизий.
4. **Реализация `equals()` и `Comparable`:** Строки корректно сравниваются по содержимому (`equals`), а реализация интерфейса `Comparable<String>` позволяет `HashMap` эффективно строить красно-чёрные деревья (`TreeNode`) при возникновении коллизий.

### Пример базового использования

```java
import java.util.HashMap;
import java.util.Map;

public class StringKeyDemo {
    public static void main(String[] args) {
        Map<String, String> cache = new HashMap<>();

        // Строковые литералы безопасно и быстро служат ключами
        cache.put("user_101", "Slava");
        cache.put("user_102", "Elena");

        System.out.println(cache.get("user_101")); // Slava
    }
}
```

> **Аналогия:** Строковый ключ — это несмываемый инвентарный номер, выгравированный на ячейке хранения. Он никогда не сотрется, не деформируется, и по нему всегда гарантированно можно найти нужный предмет.

## 🟡 Middle Level

### 1. Анатомия иммутабельности и безопасность в коллекциях

Если бы ключ был изменяемым, изменение его поля привело бы к изменению хеш-кода. В результате объект навсегда «потерялся» бы в `HashMap`, так как метод `get()` искал бы его в другом бакете.

Класс `String` объявлен как `public final class String`. Его внутренний массив символов `byte[] value` является `private final`, а класс не предоставляет ни одного метода-мутатора (любые методы вроде `trim()`, `toUpperCase()`, `replace()` возвращают новый экземпляр строки). Это дает полную потокобезопасность ключа без синхронизации.

### 2. Механизм ленивого кэширования `hashCode()`

В классе `String` хеш-код вычисляется не в конструкторе, а отложено (lazy initialization) при первом вызове `hashCode()`:

```java
// Упрощенная логика из java.lang.String (Java 13+)
public final class String implements Serializable, Comparable<String>, CharSequence {
    private int hash; // По умолчанию 0
    private boolean hashIsZero; // Флаг для строк, чей реальный хеш равен 0 (Java 13+)

    public int hashCode() {
        int h = hash;
        if (h == 0 && !hashIsZero) {
            h = isLatin1() ? StringLatin1.hashCode(value) : StringUTF16.hashCode(value);
            if (h == 0) {
                hashIsZero = true;
            } else {
                hash = h;
            }
        }
        return h;
    }
}
```

* **Первое добавление в Map (`put`):** Для строки длины $N$ хеш вычисляется за $O(N)$.
* **Последующие операции (`get`, `containsKey`, `remove`):** Возврат значения из поля `hash` за $O(1)$.
* **Оптимизация `hashIsZero`:** До Java 13 для строк с реальным хешем `0` (например, пустая строка `""` или строка `"polygenelubricants"`) условие `h == 0` было истинным всегда, из-за чего хеш пересчитывался заново при каждом вызове. Введение флага `hashIsZero` устранило этот регресс.

### 3. Оптимизация `equals()` и роль String Pool

В `HashMap.getNode(...)` проверка совпадения ключа происходит по цепочке:

```java
// Внутри HashMap:
if (first.hash == hash &&
    ((k = first.key) == key || (key != null && key.equals(k))))
```

1. **Сравнение хешей:** Сначала сравниваются 32-битные примитивы `first.hash == hash`. Если они не равны, вызов дорогостоящего `equals()` отсекается.
2. **Сравнение по ссылке (`k == key`):** Благодаря пулу строк (`String Pool`) строковые литералы с одинаковым текстом указывают на один и тот же объект в `Heap`. В этом случае проверка `k == key` возвращает `true`, и посимвольный обход `equals()` даже не начинается.
3. **Векторизованный `equals()`:** Если ссылки разные, современная JVM применяет SIMD-интринсики (`ArraysSupport.mismatch`), сравнивая байты целыми машинными словами (64/128/256 бит за такт).

## 🔴 Senior Level

### 1. Влияние `Comparable<String>` на Treeification (RB-Tree)

Когда число коллизий в бакете достигает 8 и размер таблицы $\ge 64$, связанный список `Node` преобразуется в красно-чёрное дерево `TreeNode`.

Построение и балансировка бинарного дерева поиска требует сравнения узлов. `String` реализует интерфейс `Comparable<String>`:

```java
// HashMap определяет, реализует ли ключ Comparable
static Class<?> comparableClassFor(Object x) {
    if (x instanceof Comparable) {
        Class<?> c = x.getClass();
        if (c == String.class) // Быстрый шорткат для String!
            return c;
        // ... проверка generic-параметра через reflection
    }
    return null;
}
```

Благодаря реализации `Comparable<String>`, `HashMap` сравнивает узлы дерева вызовом `k.compareTo(pk)` со сложностью $O(\log k)$. Если бы класс не реализовывал `Comparable`, `HashMap` была бы вынуждена сканировать ветви или прибегать к запасному методу `tieBreakOrder(...)` на основе `System.identityHashCode(a)`.

### 2. Compact Strings (JEP 254) и Memory Footprint

Начиная с Java 9, строки хранятся в виде `byte[] value` плюс байт кодировщика `byte coder` (`LATIN1 = 0`, `UTF16 = 1`).

Подавляющее большинство ключей в приложениях (UUID, SKU, имена колонок, enum-строки) состоят исключительно из символов Latin-1 (ASCII). Это сокращает потребление памяти на массив символов ровно в 2 раза по сравнению с `char[]` в Java 8:

| JVM (64-bit, Compressed OOPs) | Java 8 (`char[]`) | Java 9+ Compact (`byte[]`) |
| :--- | :--- | :--- |
| Заголовок `String` + поля | 24 байта | 24 байта |
| Массив символов (длина $N=16$) | $16 + (16 \times 2) = 48$ байт | $16 + (16 \times 1) = 32$ байта |
| **Итоговый размер одного ключа** | **72 байта** | **56 байт** |

Снижение расхода памяти на 22–30% для каждого строкового ключа существенно снижает давление на сборщик мусора (GC pressure) и улучшает утилизацию кэша L1/L2/L3 процессора.

### 3. Уязвимость Hash Flooding (DoS) и устойчивость Java 8+

Алгоритм вычисления хеша строки фиксирован спецификацией Java:
$$s[0] \cdot 31^{n-1} + s[1] \cdot 31^{n-2} + \dots + s[n-1]$$

Так как алгоритм детерминирован и не использует случайную соль (seed), злоумышленник может заранее сгенерировать миллионы различных строк, дающих абсолютно одинаковый `hashCode()` (например, комбинации `"Aa"`, `"BB"`: `"AaAa"`, `"BBBB"`, `"AaBB"`, `"BBAa"` имеют хеш `2060436`).

* **В Java 7:** Отправка таких строк в HTTP-заголовках или JSON-телах превращала `HashMap` в веб-сервере в длинный односвязный список, деградируя поиск до $O(N)$ и вызывая 100% загрузку CPU (Denial of Service).
* **В Java 8+:** Превращение бакета в красно-чёрное дерево гарантирует предельную сложность поиска $O(\log N)$ даже при 100% совпадении хешей у всех ключей.

### 4. Когда `String` не подходит на роль ключа

1. **Хранение секретов (пароли, API-токены):** Строки являются иммутабельными и остаются в куче до сборки мусора (или навечно в String Pool). Их невозможно принудительно обнулить (zero out) в памяти. Для конфиденциальных данных следует использовать массивы `char[]` или защищенные структуры.
2. **Экстремально длинные строки:** Если ключами служат сырые XML/JSON-документы длиной в десятки килобайт, первый расчет хеша займет $O(N)$ времени процессора. Лучше использовать хеш-дайджест (SHA-256) в виде байтового массива или обертки.
3. **Ненормализованный Unicode:** Строки `"café"` (где `é` — один символ `\u00E9`) и `"cafe\u0301"` (буква `e` + комбинируемый диакритический знак) выглядят на экране одинаково, но имеют разные `hashCode()` и не равны по `equals()`. Перед использованием интернационализированных строк необходима нормализация (`java.text.Normalizer`).

## 4 Tricky Questions

### 1. Что произойдет, если выполнить `new String("key")` вместо литерала `"key"` при добавлении в `HashMap`? Будет ли разница при поиске?

**Ответ:**
С точки зрения функциональности `map.get("key")` вернет значение без ошибок:
- `hashCode()` у обеих строк идентичен, так как зависит только от содержимого.
- `equals()` вернет `true`.

Однако с точки зрения производительности и памяти:
1. `new String("key")` создает новый объект в куче (`Heap`), минуя String Pool, что увеличивает нагрузку на GC.
2. В `HashMap.getNode(...)` быстрая проверка идентичности ссылок `first.key == key` вернет `false`, и JVM будет вынуждена вызывать полноценный метод `equals()`.

---

### 2. Может ли `String.intern()` вызвать `OutOfMemoryError: Metaspace`?

**Ответ:**
**Нет, начиная с Java 7 это невозможно.**
Исторически в Java 6 пул строк располагался в области памяти `PermGen` (Permanent Generation), которая имела фиксированный размер и при чрезмерном интернировании действительно приводила к `OutOfMemoryError: PermGen space`.

Начиная с Java 7 (и во всех современных версиях, включая Java 8, 17, 21), сами объекты `String` при вызове `intern()` размещаются в **основной куче (Java Heap)**. В области `Metaspace` хранятся только метаданные классов. Чрезмерное наполнение пула строк может привести исключительно к `java.lang.OutOfMemoryError: Java heap space` либо к замедлению работы внутренней нативной хеш-таблицы строк (`StringTable`), если ее размер недостаточен.

### 3. Почему в алгоритме `String.hashCode()` используется множитель 31?

**Ответ:**
Число 31 было выбрано создателями языка (Джошуа Блох, Джеймс Гослинг) по двум ключевым причинам:
1. **Нечетное простое число:** Умножение на четное число привело бы к сдвигу битов влево и потере старших битов при переполнении (умножение на 2 эквивалентно сдвигу `<< 1`). Использование простого числа минимизирует вероятность дублирования остатков от деления при распределении по хеш-таблицам.
2. **Аппаратная оптимизация JIT-компилятором:** Умножение на 31 на уровне ассемблерного кода автоматически заменяется быстрой комбинацией сдвига и вычитания:
   $$31 \cdot i == (i \ll 5) - i$$
   Операции побитового сдвига и вычитания выполняются за 1 такт процессора и значительно быстрее инструкции аппаратного умножения (`imul`).

---

### 4. Почему в Java 13 в класс `String` было добавлено приватное поле `hashIsZero`?

**Ответ:**
До Java 13 реализация `hashCode()` использовала проверку:
```java
if (hash == 0 && value.length > 0) {
    hash = calculateHash();
}
return hash;
```
Если строка имела вычисленный хеш-код, в точности равный `0` (классический пример — строка `"polygenelubricants"` или пустая строка `""`), поле `hash` после вычисления оставалось равным `0`.
В результате при каждом последующем вызове `hashCode()` условие `hash == 0` снова оказывалось истинным, и JVM каждый раз заново посимвольно пересчитывала хеш за $O(N)$. Поле `hashIsZero` (типа `boolean`) служит индикатором того, что хеш уже был рассчитан и его значение действительно равно нулю, предотвращая повторные вычисления.

## 🎯 Шпаргалка для интервью

* **Главные преимущества `String` как ключа:**
  - Полная иммутабельность (`final class`, неизменяемый `byte[]`).
  - Кэширование `hashCode` (первый расчет $O(N)$, далее $O(1)$).
  - Быстрый `equals`: отсечение по `hash`, сравнение по ссылке `==` благодаря String Pool, SIMD-векторизация.
  - Реализация `Comparable<String>`: автоматическое ускорение красно-черного дерева в `HashMap` при коллизиях.
  - Compact Strings (Java 9+): экономия 50% памяти под символы Latin-1.
* **Подводные камни:**
  - Строки из внешних источников могут служить вектором атаки Hash Flooding (смягчено в Java 8+ с помощью Treeification).
  - Нельзя использовать для паролей/секретов (невозможно стереть из RAM).
  - Ненормализованный Unicode может давать разные хеши для визуально одинаковых слов.
* **Частые заблуждения:**
  - «Пул строк находится в Metaspace» — **нет**, начиная с Java 7 интернированные строки живут в обычной куче (Heap).
  - «`hashCode()` строки — это адрес объекта в памяти» — **нет**, это детерминированная функция от символов $s[0] \cdot 31^{n-1} + \dots$.
