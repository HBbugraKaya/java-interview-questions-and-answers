# Какие типы Thread Pool существуют в Java

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
В стандартной библиотеке Java создание пулов потоков организовано через утилитный фабричный класс **`java.util.concurrent.Executors`** либо через прямое инстанцирование **`ThreadPoolExecutor`**, **`ScheduledThreadPoolExecutor`** и **`ForkJoinPool`**.

Выделяют 6 основных типов пулов потоков:
1. **`FixedThreadPool`:** пул с фиксированным числом потоков и неограниченной очередью задач.
2. **`CachedThreadPool`:** динамический эластичный пул, создающий новые потоки по мере необходимости и уничтожающий простаивающие через 60 секунд.
3. **`SingleThreadExecutor`:** пул из строго одного рабочего потока с гарантией последовательного исполнения задач (FIFO).
4. **`ScheduledThreadPool`:** пул для отложенного и периодического выполнения задач (по таймеру/расписанию).
5. **`WorkStealingPool` (Java 8+):** пул на базе `ForkJoinPool`, реализующий алгоритм кражи задач (Work-Stealing) для высокопараллельных рекурсивных вычислений.
6. **`VirtualThreadPerTaskExecutor` (Java 21):** специализированный непулирующий исполнитель, создающий новый легковесный виртуальный поток на каждую поступившую задачу.

---

### Сводная таблица стандартных фабрик `Executors`

| Фабричный метод | `corePoolSize` | `maximumPoolSize` | Тип внутренней очереди | Основной риск в Production |
|---|:---:|:---:|---|---|
| **`newFixedThreadPool(n)`** | `n` | `n` | `LinkedBlockingQueue` (неограниченная) | **Heap OOM** при накоплении задач |
| **`newCachedThreadPool()`** | `0` | `Integer.MAX_VALUE` | `SynchronousQueue` (ёмкость 0) | **Native Thread OOM** (Thread Explosion) |
| **`newSingleThreadExecutor()`** | `1` | `1` | `LinkedBlockingQueue` (неограниченная) | **Heap OOM** при медленной обработке |
| **`newScheduledThreadPool(n)`** | `n` | `Integer.MAX_VALUE` | `DelayedWorkQueue` (на базе min-heap) | Очередь не ограничена по размеру |
| **`newWorkStealingPool()`** | Parallelism | Parallelism | Двусторонние очереди потоков (`Deque`) | Не подходит для блокирующих I/O |
| **`newVirtualThreadPerTaskExecutor()`** | Н/Д | $\infty$ (Virtual) | Не пулирует (создаёт на задачу) | Нельзя использовать для CPU-bound |

---

### Примеры на Java 21

```java
import java.util.concurrent.*;

public class ThreadPoolTypesDemo {
    public static void main(String[] args) throws InterruptedException {
        // 1. Фиксированный пул для стабильной предсказуемой нагрузки
        try (ExecutorService fixed = Executors.newFixedThreadPool(4)) {
            fixed.submit(() -> System.out.println("Fixed task on " + Thread.currentThread()));
        }

        // 2. Однопоточный пул для строгой очередности выполнения
        try (ExecutorService single = Executors.newSingleThreadExecutor()) {
            single.submit(() -> System.out.println("Single task 1"));
            single.submit(() -> System.out.println("Single task 2"));
        }

        // 3. Планировщик периодических задач
        try (ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2)) {
            scheduler.scheduleAtFixedRate(
                () -> System.out.println("Heartbeat: " + System.currentTimeMillis()),
                0, 1, TimeUnit.SECONDS
            );
            Thread.sleep(3000);
        }

        // 4. Виртуальные потоки Java 21 для массового сетевого I/O
        try (ExecutorService virtual = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 1000; i++) {
                virtual.submit(() -> {
                    // Имитация вызова стороннего API
                    Thread.sleep(100);
                    return "Result";
                });
            }
        }
    }
}
```

## 🟡 Middle Level

### Внутреннее устройство фабричных методов

Разберём, как именно фабрика `Executors` конструирует `ThreadPoolExecutor`:

#### 1. `newFixedThreadPool(int nThreads)`
```java
public static ExecutorService newFixedThreadPool(int nThreads) {
    return new ThreadPoolExecutor(
        nThreads, 
        nThreads,
        0L, TimeUnit.MILLISECONDS,
        new LinkedBlockingQueue<Runnable>() // Опасность: Integer.MAX_VALUE
    );
}
```
Поскольку `corePoolSize == maximumPoolSize`, пул никогда не создаёт потоков сверх `nThreads`. Однако использование `LinkedBlockingQueue` без указания лимита ёмкости означает, что при медленных операциях очередь задач будет бесконечно разрастаться в куче, пока не вызовет `OutOfMemoryError: Java heap space`.

#### 2. `newCachedThreadPool()`
```java
public static ExecutorService newCachedThreadPool() {
    return new ThreadPoolExecutor(
        0, 
        Integer.MAX_VALUE, // Опасность: потоки создаются бесконечно
        60L, TimeUnit.SECONDS,
        new SynchronousQueue<Runnable>() // Прямая передача без буфера
    );
}
```
`SynchronousQueue` не хранит задачи: каждый вызов `offer()` блокируется до тех пор, пока другой поток не сделает `take()`. Если свободного потока нет, пул обязан создать **новый поток ОС**. При резком всплеске трафика в 10 000 параллельных запросов пул попытается выделить 10 000 нативных потоков, что приведёт к фатальному сбою операционной системы: `OutOfMemoryError: unable to create native thread`.

#### 3. `newSingleThreadExecutor()`
В отличие от `newFixedThreadPool(1)`, данный метод оборачивает `ThreadPoolExecutor` в защитную обёртку **`FinalizableDelegatedExecutorService`**:
- Пользовательский код не может привести полученный интерфейс к `ThreadPoolExecutor` (`(ThreadPoolExecutor) executor` выбросит `ClassCastException`).
- Это гарантирует, что сторонний код не сможет переконфигурировать пул на лету (например, вызвать `setCorePoolSize(10)`), нарушив инвариант строгой однопоточности.
- Если единственный рабочий поток упадёт с необработанным `Throwable`, пул автоматически создаст **новый поток** взамен погибшего для обработки оставшихся задач из очереди.

### Специфика `ScheduledThreadPoolExecutor`: Периодическое исполнение

`ScheduledThreadPoolExecutor` использует специальную очередь **`DelayedWorkQueue`**, представляющую собой потокобезопасную двоичную кучу (min-heap), отсортированную по времени следующего срабатывания задачи.

Два ключевых метода планирования имеют принципиальную разницу:

```
1. scheduleAtFixedRate(task, initialDelay, period = 5s):
   [Старт: 0s] ───── (выполняется 2s) ─────> [Завершено: 2s] ── (ждёт 3s) ──> [Старт: 5s]
   [Старт: 5s] ───── (выполняется 7s!) ─────────────────────────────────────> [Завершено: 12s]
                                                                                │
                                           Следующий старт запустится СРАЗУ же! v [Старт: 12s]

2. scheduleWithFixedDelay(task, initialDelay, delay = 5s):
   [Старт: 0s] ───── (выполняется 7s!) ────> [Завершено: 7s] ── (ждёт 5s) ──> [Старт: 12s]
```

- **`scheduleAtFixedRate`:** интервал отсчитывается **от времени начала** предыдущего запуска. Если задача задерживается и исполняется дольше периода, следующая итерация запустится немедленно без паузы. Задачи никогда не запускаются параллельно на одном потоке, но при накоплении отставания возникает эффект «очереди запусков».
- **`scheduleWithFixedDelay`:** гарантирует паузу фиксированной длительности **между окончанием** предыдущего выполнения и началом следующего.

## 🔴 Senior Level

### Почему в Production запрещён вызов фабрик `Executors`?

В регламентах разработки высоконагруженных систем (включая SonarQube, Alibaba Java Guidelines и банковский софт) использование фабричных методов `Executors.newFixedThreadPool`, `newCachedThreadPool` и `newScheduledThreadPool` категорически запрещено.

#### Причины запрета:
1. **Неограниченные ресурсы:** фабрики используют либо бесконечную очередь (`LinkedBlockingQueue`), приводящую к Heap OOM, либо бесконечное число потоков (`SynchronousQueue`), приводящее к Native Thread OOM.
2. **Анонимные потоки:** фабрики используют `Executors.defaultThreadFactory()`, именующий потоки как `pool-1-thread-1`. В дампе потоков (`jstack`) невозможно понять, какому бизнес-модулю (платежам, экспорту, аналитике) принадлежит зависший поток.
3. **Отсутствие Back-pressure:** используется стандартная `AbortPolicy`, выбрасывающая исключение и обрывающая вызов клиента без возможности притормозить генератор задач.

#### Production-Ready эталон конфигурации:

```java
public class SafeThreadPoolConfiguration {

    public static ExecutorService createProductionPool(String poolName, int poolSize, int queueCapacity) {
        // Кастомная фабрика с понятными именами и правильными флагами
        ThreadFactory customFactory = new ThreadFactory() {
            private final AtomicInteger threadNum = new AtomicInteger(1);

            @Override
            public Thread newThread(Runnable r) {
                Thread t = new Thread(r, poolName + "-worker-" + threadNum.getAndIncrement());
                t.setDaemon(false); // Рабочие потоки приложения не должны быть демонами
                t.setPriority(Thread.NORM_PRIORITY);
                // Обработчик критических сбоев
                t.setUncaughtExceptionHandler((thread, ex) -> 
                    System.err.printf("Критический сбой в потоке %s: %s%n", thread.getName(), ex.getMessage())
                );
                return t;
            }
        };

        return new ThreadPoolExecutor(
            poolSize,                           // corePoolSize
            poolSize,                           // maximumPoolSize (фиксированный)
            0L, TimeUnit.MILLISECONDS,          // keepAliveTime
            new ArrayBlockingQueue<>(queueCapacity), // ОГРАНИЧЕННАЯ ОЧЕРЕДЬ
            customFactory,
            new ThreadPoolExecutor.CallerRunsPolicy() // ОБРАТНОЕ ДАВЛЕНИЕ (Back-pressure)
        );
    }
}
```

### Архитектура `WorkStealingPool`: Как устроен Work-Stealing

`Executors.newWorkStealingPool()` возвращает экземпляр `ForkJoinPool`. В отличие от `ThreadPoolExecutor`, где все потоки конкурируют за одну общую очередь `workQueue`, в `ForkJoinPool`:
1. Каждый рабочий поток (`ForkJoinWorkerThread`) владеет собственной двусторонней очередью (**WorkQueue / Deque**).
2. **Владелец очереди** забирает задачи с **головы (LIFO)**. Это максимизирует локальность данных в процессорном кеше (L1/L2), так как свежесозданная подзадача с наибольшей вероятностью находится в кеше.
3. **Праздный поток (вор)** при исчерпании своих задач обращается к чужим очередям и крадёт задачи с **хвоста (FIFO)**. Это минимизирует конкуренцию за указатели с потоком-владельцем и берёт наиболее крупные подзадачи.

---

### Революция Java 21: `newVirtualThreadPerTaskExecutor()`

Виртуальные потоки кардинально изменили выбор исполнителя для **I/O-bound** задач:

```java
// Java 21: Больше нет очередей задач, нет настройки core/max pool size
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(this::blockingHttpCall);
}
```

#### Почему отпала необходимость в `newCachedThreadPool`:
- Виртуальный поток занимает всего **~1 КБ** в куче против **1 МБ** стека платформенного потока.
- При выполнении блокирующего I/O (сеть, файл) виртуальный поток автоматически размонтируется (unmount) от несущего потока ОС (Carrier Thread).
- Пул потоков больше не нужен как механизм экономии ресурсов для I/O.
- **Но пулы потоков сохраняются:** для **CPU-bound** задач (вычислений), где количество параллельных задач обязано строго соответствовать числу физических ядер процессора во избежание деградации планировщика.

## 🎯 Шпаргалка для интервью

### 1. 30-секундный эссенс (Elevator Pitch)
В Java доступно несколько ключевых типов пулов потоков: `FixedThreadPool` (фиксированный размер, LinkedBlockingQueue), `CachedThreadPool` (эластичный размер, SynchronousQueue), `SingleThreadExecutor` (один поток, последовательное исполнение), `ScheduledThreadPool` (выполнение по расписанию через min-heap очередь) и `WorkStealingPool` (ForkJoinPool с локальными деками). В Production утилитные методы `Executors.*` не используются из-за риска OOM (неограниченные очереди или неограниченные потоки); вместо них вручную конфигурируется `ThreadPoolExecutor` с `ArrayBlockingQueue` и `CallerRunsPolicy`. В Java 21 для сетевых I/O задач внедрён `newVirtualThreadPerTaskExecutor()`.

### 2. 4 каверзных вопроса с глубокими ответами

#### Вопрос 1: В чём разница между `scheduleAtFixedRate()` и `scheduleWithFixedDelay()`, если задача выполняется дольше заданного интервала?
**Ответ:**
- В **`scheduleAtFixedRate(task, 0, 5, SECONDS)`**: интервал рассчитывается строго от времени старта первой задачи ($T_0, T_0+5, T_0+10$). Если задача длилась 7 секунд (дольше периода), пул **не запускает** вторую задачу параллельно (одна и та же задача никогда не дублируется), но запускает следующую итерацию **немедленно** после завершения текущей, пытаясь нагнать график.
- В **`scheduleWithFixedDelay(task, 0, 5, SECONDS)`**: интервал отсчитывается строго от момента **физического завершения** предыдущей итерации. Если задача выполнялась 7 секунд, следующая начнётся ровно через $7 + 5 = 12$ секунд. Никакого наслоения или догоняющих запусков не происходит.

#### Вопрос 2: Что произойдёт, если задача, запущенная через `ScheduledExecutorService.scheduleAtFixedRate()`, выбросит необработанный `RuntimeException`?
**Ответ:**
Это опаснейшая скрытая ловушка Java: если очередная итерация выбросит любое необработанное исключение (`RuntimeException` или `Error`), задача **молча прекратит своё периодическое выполнение навсегда**! При этом сам рабочий поток не умирает, пул продолжает работать, но таймер для этой конкретной задачи больше никогда не сработает, и в консоль ничего не напечатается.  
*Правило:* тело периодической задачи обязано быть полностью обёрнуто в защитный блок `try-catch(Throwable t)` с явным логированием.

#### Вопрос 3: Почему `Executors.newSingleThreadExecutor()` возвращает скрытую обёртку `FinalizableDelegatedExecutorService`, а не открытый `ThreadPoolExecutor`?
**Ответ:**
Для обеспечения архитектурного инварианта: метод гарантирует, что пул выполняет задачи **строго последовательно в один поток**. Если бы метод возвращал обычный `ThreadPoolExecutor`, клиентский код мог бы выполнить приведение типов `(ThreadPoolExecutor) executor` и вызвать `setCorePoolSize(10)` или `setMaximumPoolSize(10)`, превратив последовательный пул в параллельный. Обёртка делегирует методы интерфейса `ExecutorService`, но скрывает внутренние методы управления конфигурацией.

#### Вопрос 4: Как изменилась роль `newCachedThreadPool()` с появлением `Executors.newVirtualThreadPerTaskExecutor()` в Java 21?
**Ответ:**
Метод `newCachedThreadPool()` создавался для короткоживущих асинхронных задач, но всегда страдал от риска аварийного создания тысяч системных потоков (Thread Explosion). С появлением виртуальных потоков в Java 21 метод `newCachedThreadPool()` для задач ввода-вывода (I/O, сетевые запросы, обращения к БД) стал **устаревшим антипаттерном**. `newVirtualThreadPerTaskExecutor()` масштабируется до миллионов легковесных задач без риска исчерпания памяти ОС, размонтируя виртуальные потоки во время блокировок.

### 3. Типичные ошибки и Red Flags

❌ **"Использование `Executors.newFixedThreadPool(100)` в критическом микросервисе."**  
*Правильно:* Неограниченная очередь `LinkedBlockingQueue` гарантированно приведёт к Heap OutOfMemoryError при всплеске нагрузки.

❌ **"Использование `newWorkStealingPool()` для вызовов медленных внешних SOAP/REST API."**  
*Правильно:* `WorkStealingPool` построен на `ForkJoinPool` и оптимизирован для быстрых CPU-задач без блокировок. Блокирующий ввод-вывод внутри рабочих потоков приводит к блокировке очередей кражи и деградации пула.

❌ **"Игнорирование обработки исключений в `scheduleWithFixedDelay`."**  
*Правильно:* Любой необработанный `RuntimeException` навсегда убивает расписание задачи без следов в логах.
