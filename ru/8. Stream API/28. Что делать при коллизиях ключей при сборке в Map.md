# Что делать при коллизиях ключей при сборке в Map

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**Коллизия ключей** возникает, когда два или более элемента стрима после преобразования функцией `keyMapper` дают одинаковый ключ для `Map`.

По умолчанию метод с двумя аргументами `Collectors.toMap(keyMapper, valueMapper)` не умеет разрешать такие конфликты и при первом же дубликате ключа выбрасывает исключение:
`IllegalStateException: Duplicate key <key> (attempted merging values <v1> and <v2>)`.

Чтобы обработать коллизию, необходимо использовать перегрузку метода `Collectors.toMap` с **третьим аргументом — функцией слияния (`BinaryOperator<U> mergeFunction`)**, которая определяет, какое значение сохранить при конфликте:
```java
// Оставить первое встреченное значение (Keep First):
(existing, replacement) -> existing

// Оставить последнее встреченное значение (Keep Last / Overwrite):
(existing, replacement) -> replacement
```

---

### Примеры стратегий разрешения коллизий на Java 21

```java
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

public class KeyCollisionDemo {

    public record Employee(int id, String name, double salary) {}

    public static void main(String[] args) {
        List<Employee> staff = List.of(
            new Employee(101, "Иван (Junior)", 80_000),
            new Employee(102, "Анна (Middle)", 160_000),
            new Employee(101, "Иван (Senior)", 250_000) // Дубликат ID 101!
        );

        // Стратегия 1: Оставить первое значение (Keep First)
        Map<Integer, Employee> firstStaff = staff.stream()
            .collect(Collectors.toMap(
                Employee::id,
                e -> e,
                (existing, replacement) -> existing
            ));
        System.out.println("First: " + firstStaff.get(101).name()); // Иван (Junior)

        // Стратегия 2: Перезаписать последним значением (Keep Last)
        Map<Integer, Employee> latestStaff = staff.stream()
            .collect(Collectors.toMap(
                Employee::id,
                e -> e,
                (existing, replacement) -> replacement
            ));
        System.out.println("Latest: " + latestStaff.get(101).name()); // Иван (Senior)

        // Стратегия 3: Агрегация (выбор максимальной зарплаты)
        Map<Integer, Employee> highestPaid = staff.stream()
            .collect(Collectors.toMap(
                Employee::id,
                e -> e,
                (e1, e2) -> e1.salary() > e2.salary() ? e1 : e2
            ));
        System.out.println("Max salary: " + highestPaid.get(101).salary()); // 250000.0
    }
}
```

## 🟡 Middle Level

### 4 типовые стратегии в `mergeFunction`

Интерфейс `BinaryOperator<U>` принимает `(U existingValue, U newValue)` и возвращает итоговое значение типа `U`:

#### 1. Дедупликация (Keep First):
Применяется, когда первый элемент считается каноническим:
```java
(oldVal, newVal) -> oldVal
```

#### 2. Актуализация (Keep Last):
Применяется, когда стрим упорядочен хронологически (по времени события), и нужно сохранить самое свежее состояние:
```java
(oldVal, newVal) -> newVal
```

#### 3. Арифметическое сложение / Конкатенация:
Суммирование количеств или объединение строк:
```java
// Подсчет суммарного объема продаж по товарам:
Map<String, Integer> totalSales = orders.stream()
    .collect(Collectors.toMap(Order::product, Order::quantity, Integer::sum));
```

#### 4. Бизнес-выбор (Custom Reducer):
Выбор по бизнес-правилу (например, выбор по приоритету статуса заказа):
```java
(v1, v2) -> v1.priority() > v2.priority() ? v1 : v2
```

---

### Когда `toMap` с `mergeFunction` — архитектурная ошибка

Если задача требует сохранить **все** элементы, соответствующие ключу, использовать `toMap()` категорически нельзя. Правильное решение — использовать **`Collectors.groupingBy()`**:

```java
// ❌ ПЛОХО: попытка собрать список вручную через toMap
// .toMap(User::dept, u -> new ArrayList<>(List.of(u)), (l1, l2) -> { l1.addAll(l2); return l1; })

// ✅ ПРАВИЛЬНО: groupingBy возвращает Map<String, List<User>>:
Map<String, List<User>> usersByDept = users.stream()
    .collect(Collectors.groupingBy(User::department));
```

## 🔴 Senior Level

### Требование ассоциативности `mergeFunction` в `parallelStream()`

В параллельном стриме (`parallelStream()`) данные разбиваются на чанки между потоками пула `ForkJoinPool`:
1. Каждый поток формирует частичные `Map`.
2. На этапе слияния веток рантайм `Map.putAll()` и `Map.merge()` вызывает `mergeFunction` для ключей, встретившихся в разных подзадачах.
3. Чтобы результат многопоточной сборки был строго детерминированным, `mergeFunction` **обязана быть ассоциативной (Associative)**:
   $$(v_1 \circ v_2) \circ v_3 = v_1 \circ (v_2 \circ v_3)$$

```
Worker 1: Map [Key=A -> Val 1] \
                                ──► mergeFunction(Val 1, Val 2) \
Worker 2: Map [Key=A -> Val 2] /                                 ──► mergeFunction(Res1, Val 3)
                                                                /
Worker 3: Map [Key=A -> Val 3] ────────────────────────────────
```

> **Senior Warning:** Стратегия `Keep Last ((v1, v2) -> v2)` в `parallelStream()` **не гарантирует**, какой именно элемент станет последним, если порядок слияния задач в `ForkJoinPool` изменится. Для гарантии детерминированного выбора в параллельном режиме элементы должны содержать независимый компаратор (например, отметку времени `timestamp` или версию).

### Аудит и логирование коллизий в Production

В критических финансовых сервисах потеря данных при молчаливом отбрасывании дубликатов недопустима:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class SafeMergeCollector {
    private static final Logger log = LoggerFactory.getLogger(SafeMergeCollector.class);

    public static <T, K, V> Map<K, V> toMapWithAudit(
            List<T> items, 
            java.util.function.Function<T, K> keyMapper,
            java.util.function.Function<T, V> valueMapper) {
        
        return items.stream().collect(Collectors.toMap(
            keyMapper,
            valueMapper,
            (existing, replacement) -> {
                log.warn("ОБНАРУЖЕН ДУБЛИКАТ КЛЮЧА! Существующее: [{}], Новое: [{}]", existing, replacement);
                return existing; // Сохраняем исходное
            }
        ));
    }
}
```

### Анализаторы качества кода (SonarQube & Error-Prone)

Статические анализаторы Google Error-Prone и SonarQube (правило `S2201` / `DuplicateKeyException`) относят использование двухпараметрического `Collectors.toMap(k, v)` к категории **High-Risk Code Smells**.
В production-коде рекомендуется либо явно передавать `mergeFunction`, либо использовать `groupingBy()`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> «При коллизии ключей метод `Collectors.toMap(k, v)` без функции слияния выбрасывает `IllegalStateException`. Чтобы корректно обработать дубликаты, передают третий параметр — `mergeFunction` (`BinaryOperator<V>`). Основные стратегии: `(v1, v2) -> v1` (Keep First для дедупликации), `(v1, v2) -> v2` (Keep Last для перезаписи более свежим значением) или агрегация через `Integer::sum`. Если требуется сохранить все элементы по общему ключу, правильным решением является `Collectors.groupingBy()`, собирающий элементы в `Map<K, List<V>>`.»

---

### Сравнение подходов при коллизиях

| Стратегия | Реализация mergeFunction | Когда использовать | Поведение в parallelStream |
|---|---|---|---|
| **Выброс ошибки** | Без 3-го аргумента | Инвариант: дубликаты в БД/API невозможны | 💥 `IllegalStateException` |
| **Keep First** | `(oldVal, newVal) -> oldVal` | Дедупликация (берем первый найденный) | Детерминированно при упорядоченном источнике |
| **Keep Last** | `(oldVal, newVal) -> newVal` | Сохранение последнего состояния | Недетерминированно в parallel (зависит от потоков) |
| **Агрегация** | `Integer::sum` / `(a, b) -> a + b` | Подсчет сумм, объединение текстов | 🟢 Идеально (ассоциативная операция) |
| **Выбор по полю** | `(a, b) -> a.val() > b.val() ? a : b` | Выбор максимального/лучшего | 🟢 Идеально |
| **Группировка** | `Collectors.groupingBy()` | Нужно сохранить ВСЕ элементы | 🟢 Идеально (`Map<K, List<V>>`) |

### Топ-4 каверзных вопроса на интервью

#### 1. Почему в production-коде запрещено использовать `Collectors.toMap(k, v)` с двумя аргументами?
- Двухпараметрический метод предполагает стопроцентную уникальность ключей. Если на вход сервиса поступят непредвиденные данные из БД или внешнего API с дубликатом ключа, метод немедленно упадет с `IllegalStateException`, прервав обработку пользовательского запроса. Добавление `mergeFunction` делает код отказоустойчивым.

#### 2. Что произойдет, если в `mergeFunction` передать `(oldVal, newVal) -> null`?
- Если функция слияния вернет `null`, метод `Map.merge()` удалит запись с этим ключом из итоговой мапы. Это стандартное поведение контракта метода `Map.merge(key, value, remappingFunction)`.

#### 3. Почему стратегия `Keep Last` `(v1, v2) -> v2` может вернуть непредсказуемый результат в `parallelStream()`?
- В параллельном стриме порядок слияния результатов рабочих потоков `ForkJoinPool` недетерминирован. Ветка с более поздним индексом может завершиться и быть объединена раньше, чем ветка с предшествующим индексом. В итоге победит то значение, которое рантайм передаст вторым аргументом в `mergeFunction` во время сборки дерева задач.

#### 4. В чем разница между `Collectors.toMap(k, v, merge)` и `Collectors.groupingBy(k)`?
- `toMap` всегда сохраняет в качестве значения единичный объект типа `V` (размер мапы равен числу уникальных ключей, коллизии разрешаются сжатием в один элемент).
- `groupingBy` группирует все элементы в коллекцию `Map<K, List<V>>`, не теряя ни одного объекта при совпадении ключей.

---

### Типичные ошибки и Red Flags
- 🚩 Забывание `mergeFunction` при обработке данных из внешних ненадежных источников.
- 🚩 Попытка накопления списка объектов вручную через `toMap()` вместо использования `groupingBy()`.
- 🚩 Использование неассоциативной логики слияния в параллельных стримах.
- 🚩 Подавление коллизий через `(a, b) -> a` без логирования в критически важных бизнес-транзакциях.
