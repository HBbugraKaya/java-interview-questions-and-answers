# Почему важно избегать блокирующих операций в CompletableFuture

---

## 🟢 Junior Level

Класс `CompletableFuture` был создан специально для построения **неблокирующих (non-blocking) реактивных конвейеров**. Блокирующие операции (такие как `Thread.sleep()`, `future.get()`, синхронные походы в БД через JDBC или медленные сетевые вызовы) внутри асинхронных цепочек нивелируют всю пользу от асинхронности.

### Главные причины избегать блокировок:

1. **Голодание пула потоков (Thread Pool Starvation)**: по умолчанию методы `CompletableFuture` используют `ForkJoinPool.commonPool()`. Количество потоков в нём ограничено ($\text{CPU cores} - 1$). Если в 8-ядерной системе 7 потоков встанут в блокирующее ожидание ответа от базы данных или стороннего API, **вся асинхронная работа в JVM остановится**.
2. **Взаимные блокировки (Deadlocks)**: если задача, исполняющаяся в пуле, блокирующе ожидает (`join()`) другую задачу, стоящую в очереди того же самого пула, наступает гарантированный дедлок.
3. **Бесполезный расход памяти**: каждый заблокированный поток операционной системы удерживает стек памяти (~1 МБ), создавая колоссальные накладные расходы при нулевой утилизации CPU.

```java
// ❌ АНТИПАТТЕРН: блокирующий вызов замораживает поток воркера
CompletableFuture.supplyAsync(() -> {
    Thread.sleep(5000); // Блокировка! Воркер простаивает 5 секунд
    return "done";
});

// ✅ ПРАВИЛЬНО: использование неблокирующих API и специализированных таймеров
CompletableFuture.supplyAsync(() -> "done", 
    CompletableFuture.delayedExecutor(5, TimeUnit.SECONDS) // Не держит поток 5 секунд!
);
```

## 🟡 Middle Level

### 1. Анатомия самоблокировки пула (Self-Deadlock)

Один из самых коварных дефектов в многопоточном программировании — запуск зависимых задач с блокирующим ожиданием в одном пуле:

```java
ExecutorService pool = Executors.newFixedThreadPool(2);

// Отправляем две внешние задачи:
CompletableFuture<String> task1 = CompletableFuture.supplyAsync(() -> {
    // Внутри запускаем подзадачу в ТОТ ЖЕ пул и блокируемся в ожидании!
    CompletableFuture<String> subTask = CompletableFuture.supplyAsync(() -> "sub1", pool);
    return subTask.join(); // Поток 1 ждет sub1
}, pool);

CompletableFuture<String> task2 = CompletableFuture.supplyAsync(() -> {
    CompletableFuture<String> subTask = CompletableFuture.supplyAsync(() -> "sub2", pool);
    return subTask.join(); // Поток 2 ждет sub2
}, pool);
```
**Что происходит:**
1. Поток 1 занят `task1`, поток 2 занят `task2`. Свободных потоков в пуле больше нет ($2/2$).
2. Задачи `sub1` и `sub2` встают в очередь задач пула.
3. `task1` и `task2` бесконечно ждут выполнения `sub1` и `sub2`, а `sub1` и `sub2` не могут начаться, пока не освободятся потоки.
4. **Результат: мгновенный взаимный дедлок (Pool Deadlock).**

### 2. Почему Work-Stealing не спасает от блокировок?

В `ForkJoinPool` реализован механизм Work-Stealing: если воркер свободен, он может "украсть" задачу из очереди соседа. 
Но если поток ушёл в синхронный системный вызов ядра ОС (например, `SocketInputStream.read()` или `ReentrantLock.lock()`), процессор переводит поток в режим сна (`WAITING`/`BLOCKED`).
Поток **не может выполнять алгоритм кражи задач**, потому что он заморожен ядром операционной системы! Вся его локальная очередь задач остаётся мёртвым грузом.

## 🔴 Senior Level

### Проблема "Пиннинга" (Thread Pinning) в Virtual Threads (Java 21+)

С появлением Virtual Threads многие разработчики решили, что о блокировках можно забыть. Однако в связке с `CompletableFuture` существует критическая ловушка — **Pinning (привязка виртуального потока к несущему потоку ОС)**.

Виртуальный поток при блокировке отмонтируется от Carrier Thread ядра, **ЕСЛИ ТОЛЬКО блокировка не происходит внутри `synchronized`-блока или нативного метода**:
```java
// ❌ ОПАСНО: блокировка внутри synchronized
CompletableFuture.supplyAsync(() -> {
    synchronized (lock) {
        // Если здесь произойдёт блокирующий вызов I/O или JDBC:
        return httpClient.sendBlocking(request); 
    }
}, virtualThreadExecutor);
```
В этот момент виртуальный поток **пришпиливается (pinned)** к потоку платформы (Carrier Thread). Если таких операций станет много, пул несущих потоков платформы (`ForkJoinPool` под капотом Project Loom) окажется полностью заблокирован, вернув систему к классическому Thread Starvation!
*Решение:* Заменять `synchronized` на `ReentrantLock`, который в Java 21 полностью поддерживает неблокирующее отмонтирование виртуальных потоков.

### Использование `ManagedBlocker` при неизбежных блокировках

Если в архитектуре невозможно избавиться от синхронной блокирующей библиотеки внутри `ForkJoinPool`, единственным безопасным способом является использование контракта **`ForkJoinPool.ManagedBlocker`**:

```java
public class ManagedDbQuery<T> implements ForkJoinPool.ManagedBlocker {
    private final Supplier<T> query;
    private T result;
    private boolean done = false;

    public ManagedDbQuery(Supplier<T> query) { this.query = query; }

    @Override
    public boolean block() {
        result = query.get(); // Блокирующий вызов JDBC
        done = true;
        return true;
    }

    @Override
    public boolean isReleasable() { return done; }

    public T getResult() { return result; }
}

// Использование:
CompletableFuture.supplyAsync(() -> {
    ManagedDbQuery<User> blocker = new ManagedDbQuery<>(() -> userRepository.findById(id));
    ForkJoinPool.managedBlock(blocker); // ForkJoinPool ВРЕМЕННО СОЗДАЁТ НОВЫЙ ПОТОК взамен заблокированного!
    return blocker.getResult();
});
```

## 4 Tricky Questions

### 1. Что произойдёт, если внутри `cf.thenApply(...)` вызвать `anotherCf.join()`, и почему это считается худшим антипаттерном в асинхронном коде?

**Ответ:**
Это приводит к двум катастрофическим последствиям:
1. **Разрушение неблокирующего конвейера**: поток, завершивший родительский фьючерс, вместо быстрой передачи данных замораживается в ожидании `anotherCf`.
2. **Риск самоблокировки пула (Self-Deadlock)**: если `anotherCf` должен выполниться в том же пуле потоков, а все потоки уже заблокированы аналогичными вызовами `join()`, система встанет намертво.
*Правильное решение:* Использовать монадическую композицию — вместо `thenApply + join` всегда вызывать **`thenCompose`** или **`thenCombine`**.

### 2. Как обнаружить скрытое голодание пула потоков (Thread Starvation) в продакшене под мониторингом Prometheus/Grafana?

**Ответ:**
Симптомы голодания пула потоков на графиках:
1. **Queue Size растёт**: размер очереди задач (`executor.queue.size`) лавинообразно увеличивается при неизменном или даже снижающемся количестве активных вычислений.
2. **Active Threads = Max Threads**: количество активных воркеров постоянно упирается в потолок пула.
3. **Резкий скачок Latency (P99/P99.9)**: время ожидания задачи в очереди (`task.wait.time`) превышает само время её выполнения в сотни раз.
4. **Снятие `jstack` / thread dump**: показывает десятки потоков воркеров в состоянии `WAITING (parking)` на `CompletableFuture.waitingGet` или `SocketInputStream.socketRead0`.

### 3. Почему блокирующий I/O внутри `ForkJoinPool.commonPool()` наносит больший ущерб, чем блокирующий I/O в обычном `ThreadPoolExecutor`?

**Ответ:**
Потому что `ThreadPoolExecutor` обычно изолирован для конкретного сервиса, а `ForkJoinPool.commonPool()` — **глобальный синглтон на всю JVM**. 
Блокировка потоков в `commonPool` парализует не только ваш метод, но и:
- Параллельную обработку потоков данных `stream().parallel()`.
- Системные асинхронные операции JDK (например, реактивные интерфейсы `HttpClient`).
- Асинхронные задачи во всех остальных модулях приложения, использующих `CompletableFuture` без кастомного экзекутора.

### 4. Допустим, мы вызываем метод с задержкой: что лучше использовать — `Thread.sleep(5000)` внутри `supplyAsync` или `CompletableFuture.delayedExecutor(5, SECONDS)`? В чём разница по ресурсам?

**Ответ:**
Разница колоссальна:
- `Thread.sleep(5000)` внутри задачи пула **захватывает и удерживает живой системный поток ОС на 5 секунд**. Поток простаивает, потребляя память стека и уменьшая пропускную способность пула.
- `CompletableFuture.delayedExecutor(5, SECONDS)` (появился в Java 9) использует внутренний высокооптимизированный системный таймер (`ScheduledThreadPoolExecutor`). Он **не занимает поток пула во время ожидания**! Задача физически отправляется в пул потоков только по истечении 5 секунд, не расходуя вычислительные потоки во время паузы.

## 🎯 Шпаргалка для интервью

### Главное за 60 секунд
- Блокировки в `CompletableFuture` приводят к **Thread Pool Starvation** (голоданию пула) и **Pool Deadlock** (взаимным блокировкам).
- Пул по умолчанию `ForkJoinPool.commonPool()` имеет всего $\text{cores} - 1$ потоков и предназначен **только для CPU-bound вычислений**.
- Алгоритм Work-Stealing бессилен против потоков, заблокированных на уровне ядра ОС (I/O, мьютексы, `Thread.sleep`).
- Для любых блокирующих операций обязательно использовать:
  - Изолированный `ThreadPoolExecutor` с ограниченной очередью.
  - Virtual Threads (`newVirtualThreadPerTaskExecutor`) в Java 21+.
  - `CompletableFuture.delayedExecutor` вместо `Thread.sleep`.
  - Замену `thenApply + join()` на `thenCompose()` / `thenCombine()`.

### Типичные ошибки на интервью
- Вызывать `.get()` или `.join()` внутри лямбд `CompletableFuture` (грубейший антипаттерн, ведущий к дедлокам).
- Считать, что `ForkJoinPool` автоматически увеличивает число потоков при обычных блокировках (он делает это только через `ManagedBlocker`).
- Полагать, что Virtual Threads в Java 21 полностью избавляют от проблем блокировок (опасность Thread Pinning внутри `synchronized`).
