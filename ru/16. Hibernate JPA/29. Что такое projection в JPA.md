# Что такое projection в JPA

Проекция (Projection) в JPA и Spring Data — это механизм выборки строго определенного подмножества полей или вычисляемых выражений вместо загрузки полной сущности. Использование проекций — один из самых мощных способов оптимизации производительности: оно сокращает сетевой трафик между СУБД и JVM, экономит оперативную память кучи (Heap) и полностью исключает накладные расходы Hibernate на отслеживание изменений (Dirty Checking) и управление контекстом постоянства (`PersistenceContext`).

---

## 🟢 Junior Level

### Зачем нужны проекции

Когда вы выполняете стандартный запрос `SELECT u FROM User u`, Hibernate:
1. Выполняет `SELECT *` со всеми колонками таблицы (включая тяжелые текстовые описания, аватары и метаданные).
2. Создает полноценный экземпляр Java-объекта `User`.
3. Сохраняет точный дубликат состояния в снимок `loadedState` кэша L1 для отслеживания Dirty Checking.
4. Привязывает к объекту прокси-обработчики связей.

Если вам нужно лишь отобразить имя и email в таблице пользователей, 90% этой работы — пустая трата ресурсов. **Проекция запрашивает только то, что нужно:**

```java
// Проекция в Java Record:
public record UserSummary(String name, String email) {}

// JPQL через конструктор (Constructor Expression):
TypedQuery<UserSummary> query = entityManager.createQuery("""
    SELECT new com.example.dto.UserSummary(u.name, u.email)
    FROM User u
    """, UserSummary.class);

List<UserSummary> summaries = query.getResultList();
// Сгенерированный SQL: SELECT name, email FROM users;
// Никакого L1 кэша, никаких снимков, минимальный трафик!
```

## 🟡 Middle Level

### 5 разновидностей проекций в JPA и Spring Data

#### 1. Нетипизированный массив `Object[]` (Raw Array)
```java
List<Object[]> rows = entityManager.createQuery("SELECT u.name, u.email FROM User u").getResultList();
String name = (String) rows.get(0)[0]; // Опасно: легко ошибиться индексом
```
*Минусы:* Отсутствие типобезопасности, подвержен поломкам при рефакторинге.

#### 2. Проекция на базе `jakarta.persistence.Tuple`
Позволяет обращаться к колонкам по строковым псевдонимам (псевдо-типобезопасно):
```java
List<Tuple> tuples = entityManager.createQuery("""
    SELECT u.name AS userName, u.email AS userEmail FROM User u
    """, Tuple.class).getResultList();

String name = tuples.get(0).get("userName", String.class);
```

#### 3. DTO Constructor Expression (`SELECT new ...`)
Классический JPA-стандарт. Работает как с обычными классами, так и с **Java Records**:
```java
public record UserInfoDto(Long id, String email) {}

@Query("SELECT new com.example.dto.UserInfoDto(u.id, u.email) FROM User u")
List<UserInfoDto> fetchUsers();
```
*Обязательное условие:* В JPQL необходимо указывать **полное имя класса с пакетом** (`new com.example.dto.UserInfoDto(...)`).

#### 4. Закрытые интерфейсные проекции Spring Data (Closed Projections)
Spring Data позволяет объявить простой интерфейс с геттерами:
```java
public interface UserContactView {
    String getName();
    String getEmail();
}

public interface UserRepository extends JpaRepository<User, Long> {
    List<UserContactView> findAllByActiveTrue();
}
```
Spring Data анализирует геттеры интерфейса и генерирует оптимальный SQL, запрашивающий только колонки `name` и `email`.

#### 5. Динамические проекции (Dynamic Projections)
Один метод репозитория может возвращать разные проекции в зависимости от переданного класса:
```java
public interface UserRepository extends JpaRepository<User, Long> {
    <T> List<T> findByStatus(String status, Class<T> type);
}

// Использование:
List<UserSummary> list1 = repo.findByStatus("ACTIVE", UserSummary.class);
List<UserDetailDto> list2 = repo.findByStatus("ACTIVE", UserDetailDto.class);
```

## 🔴 Senior Level

### Ловушка открытых проекций (Open Projections) в Spring Data

Spring Data поддерживает так называемые «открытые проекции» через SpEL-выражения (Spring Expression Language):

```java
// ❌ СКРЫТАЯ ДЕГРАДАЦИЯ ПРОИЗВОДИТЕЛЬНОСТИ:
public interface UserFullNameView {
    @Value("#{target.firstName + ' ' + target.lastName}")
    String getFullName();
}
```

#### Почему это опасно:
- При **Closed Projection** (`String getFirstName()`) Spring Data оптимизирует SQL: `SELECT first_name FROM users`.
- При **Open Projection** с `@Value` Spring Data **не может знать**, какие именно поля понадобятся выражению SpEL во время вычисления.
- **Следствие:** Spring Data **вынужден выполнить полный `SELECT *`**, выгрузить всю сущность со всеми колонками в память, создать JDK Dynamic Proxy и только потом вычислить выражение в JVM! Выигрыш в производительности обнуляется.

### Проекции и коллекции: Ограничение спецификации JPA

Спецификация JPA прямо запрещает передавать коллекции в конструкторные проекции:

```java
// ❌ ОШИБКА КОМПИЛЯЦИИ JPQL:
public record OrderWithItemsDto(Long orderId, List<ItemDto> items) {}

// Попытка написать такое завершится ошибкой парсинга:
@Query("SELECT new com.example.OrderWithItemsDto(o.id, o.items) FROM Order o")
List<OrderWithItemsDto> findOrders();
```

#### Как правильно проецировать отношения $1:N$:
1. **Подход в два запроса:** Загрузить DTO заказов, затем отдельным запросом загрузить DTO позиций с `WHERE order_id IN (:ids)` и сгруппировать в памяти через `Collectors.groupingBy()`.
2. **Использование Hibernate `TupleTransformer`:** В Hibernate 6 преобразовать плоский результат `JOIN` в иерархический DTO с помощью кастомного `ResultListTransformer`.
3. **Использование библиотеки Blaze-Persistence:** Расширение поверх JPA, официально поддерживающее вложенные DTO-коллекции прямо в запросах.

## 4 Tricky Questions

### 1. Будут ли сущности или DTO, полученные через конструкторную проекцию (`SELECT new UserDto(...)`), отслеживаться механизмом Dirty Checking?

**Ответ:**
1. **Категорически нет.**
2. Объекты DTO не являются сущностями JPA (`@Entity`). Они инстанциируются через обычный вызов Java-конструктора `new UserDto(...)` прямо из сырых колонок `ResultSet`.
3. Они не регистрируются в карте `StatefulPersistenceContext.entitiesByKey` и не создают записей `EntityEntry`.
4. Любые изменения полей в таком DTO не приведут к генерации SQL `UPDATE` при коммите транзакции.

### 2. Почему в высоконагруженных системах (HighLoad) использование Java Records предпочтительнее интерфейсных проекций Spring Data?

**Ответ:**
1. Для интерфейсных проекций Spring Data на каждую строку результата создает динамический JDK-прокси (`java.lang.reflect.Proxy`), оборачивающий `Map<String, Object>`.
2. Создание прокси и обращение к геттерам через Reflection создает ощутимый оверхед по CPU и аллокации памяти при выборках от 10 000 строк.
3. Java Records компилируются в нативный байткод. Создание рекорд-объекта через конструктор выполняется мгновенно с нулевым рефлексивным оверхедом и оптимальной упаковкой памяти в куче JVM.

### 3. Можно ли объединить пагинацию (`Pageable`) и интерфейсную проекцию в Spring Data JPA репозитории?

**Ответ:**
1. **Да, полностью поддерживается.**
2. Метод `Page<UserView> findByActive(boolean active, Pageable pageable)` корректно генерирует два запроса:
   - `SELECT COUNT(id) FROM users WHERE active = ?` (для подсчета общего числа страниц).
   - `SELECT id, name, email FROM users WHERE active = ? LIMIT ? OFFSET ?` (точечная выборка нужных колонок страницы).

### 4. Что произойдет, если в классе DTO типы аргументов конструктора не совпадут по типам данных с колонками JPQL запроса (например, `Long` в конструкторе против `Integer` из базы)?

**Ответ:**
1. Hibernate пытается найти конструктор с точным совпадением типов аргументов через Java Reflection.
2. Автоматического расширения примитивных типов (например, каста `Integer` к `Long` или `BigDecimal` к `Double`) движок JPA не делает.
3. Если конструктор с сигнатурой, точно соответствующей типам выражений `SELECT`, не найден, запрос упадет в Runtime с исключением:
   `org.hibernate.query.SemanticException: Unable to locate appropriate constructor on class [com.example.UserDto]`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «Проекции в JPA позволяют выбирать только необходимые поля вместо загрузки полной сущности со всеми колонками. Это снижает сетевой трафик, экономит память кучи JVM и исключает накладные расходы на Dirty Checking в кэше L1. Основные способы реализации: DTO Constructor Expressions (через Java Records `SELECT new ...`) и закрытые интерфейсы Spring Data. Важный senior-нюанс: открытые интерфейсные проекции со SpEL-аннотацией `@Value` нивелируют оптимизацию, так как Spring вынужден выгружать всю сущность целиком. Для read-only операций и отдачи данных в REST API проекции в Java Records являются абсолютным стандартом индустрии».

### Ключевые метрики для Production-мониторинга
- **Allocated Memory per Request (GC Allocation Rate)**: замена полных сущностей на DTO-проекции снижает выделение памяти в 3–5 раз.
- **Database Network Traffic / Egress Bytes**: уменьшение объема сетевого трафика между сервером приложений и СУБД.

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«Проекции обновляют базу данных через dirty checking»* — DTO не управляются сессией Hibernate, dirty checking для них не работает.
- ❌ *«Использую открытые проекции с @Value("#{target...}") ради максимальной производительности»* — Наоборот, `@Value` выкачивает всю строку таблицы целиком.
- ❌ *«В конструкторную проекцию можно легко передать вложенную коллекцию @OneToMany»* — Запрещено JPA, приведет к ошибке компиляции запроса.
- ❌ *«Для read-only отчетов лучше загружать полные JPA-сущности»* — Грубый антипаттерн, приводящий к перегрузке памяти и риску N+1.
