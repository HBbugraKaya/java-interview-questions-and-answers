# Які інструменти допомагають аналізувати пам'ять

---

## 🟢 Junior Level

Для аналізу пам'яті в Java існує широкий спектр інструментів: від стандартних консольних утиліт JDK до потужних графічних аналізаторів дампів і профілювальників реального часу.

### Основні категорії інструментів

| Інструмент | Тип | Призначення | Коли застосовується |
| :--- | :--- | :--- | :--- |
| **Eclipse MAT** | GUI (Десктоп) | Глибокий офлайн-аналіз дампів пам'яті (HPROF) | Після `OutOfMemoryError` або для пошуку витоків пам'яті. |
| **VisualVM** | GUI (Десктоп) | Моніторинг у реальному часі, легковаге профілювання | Локальна розробка та тестові стенди. |
| **`jcmd`** | CLI (Консоль JDK) | Універсальний інтерфейс керування та діагностики JVM | Production-сервери (мінімальний вплив). |
| **JFR / JMC** | Профайлер (JDK) | Надлегковага телеметрія подій JVM (< 1% оверхеду) | Безперервний моніторинг і трасування під бойовим навантаженням. |
| **JProfiler / YourKit** | GUI (Комерційний) | Інтерактивне профілювання алокацій і потоків | Глибока оптимізація коду на етапі розробки. |

### Базовий сценарій: Eclipse MAT
**Eclipse Memory Analyzer (MAT)** — провідний безкоштовний інструмент з відкритим вихідним кодом для аналізу файлів дампів купи (`.hprof`):
- Обчислює **Retained Heap** (скільки пам'яті реально звільниться при видаленні об'єкта);
- Будує **Dominator Tree** (дерево домінаторів володіння пам'яттю);
- Надає автоматичний звіт **Leak Suspects Report**, що самостійно визначає підозрілі компоненти з імовірністю витоку.

## 🟡 Middle Level

### 1. Універсальна консольна утиліта `jcmd`

Починаючи з Java 7/8, утиліта `jcmd` є офіційним рекомендованим стандартом командного рядка HotSpot, що замінив застарілі та нестабільні інструменти (`jmap`, `jinfo`).

```bash
# Отримати список доступних Java-процесів
jcmd -l

# 1. Швидка гістограма класів (пауза частки секунди)
# Показує топ класів за кількістю об'єктів та обсягом пам'яті
jcmd <pid> GC.class_histogram

# 2. Зняття повного дампу купи у файл
jcmd <pid> GC.heap_dump /dumps/heap_analysis.hprof

# 3. Зведення споживання Native Memory (вимагає -XX:NativeMemoryTracking)
jcmd <pid> VM.native_memory summary

# 4. Аналіз метаданих класів у Metaspace
jcmd <pid> VM.metaspace show-loaders
```

> [!TIP]
> **Чому `GC.class_histogram` безпечніший за `GC.heap_dump`?**
> Гістограма класів обходить заголовки об'єктів у пам'яті й агрегує лічильники за дуже коротку паузу (зазвичай < 1 сек), не виконуючи серіалізацію графу посилань на диск. Це ідеальний перший крок експрес-діагностики прямо на бойовому сервері.

### 2. Java Flight Recorder (JFR) та JDK Mission Control (JMC)

**JFR** вбудовано безпосередньо в ядро HotSpot JVM. Він збирає детальні метрики віртуальної машини з апаратною підтримкою та накладними витратами процесора менше 1%:
- **Подія `jdk.OldObjectSample`:** алгоритмічна вибірка довгоживучих об'єктів старшого покоління, що дозволяє відстежувати шлях до GC Roots і стек-трейс алокації в бойовому проді без зупинки JVM;
- **Allocation Profiling:** фіксація темпу алокацій усередині TLAB (*Thread Local Allocation Buffer*) та поза TLAB (виділення великих об'єктів безпосередньо в купу).

```bash
# Запуск запису JFR тривалістю 15 хвилин у production:
jcmd <pid> JFR.start name=Profile memory=100m duration=15m filename=recording.jfr settings=profile
```

Отриманий `.jfr` файл відкривається в **JDK Mission Control (JMC)**, де на графіках відображаються витоки пам'яті, фази збирання сміття та час пауз.

### 3. Порівняння підходів до профілювання

```
+-------------------------------------------------------------------------+
|                  Методи аналізу пам'яті застосунку                      |
+-------------------------------------------------------------------------+
| 1. Live Sampling / Instrumentation (JProfiler, YourKit, VisualVM)       |
|    - Перехоплення кожної алокації (Bytecode instrumentation / BCI)      |
|    - Сповільнює роботу застосунку в 2-10 разів (неприйнятно в Prod)     |
+-------------------------------------------------------------------------+
| 2. Event-based / Asynchronous Sampling (JFR, Async-profiler)            |
|    - Статистична вибірка алокацій через perf_events / safepoints        |
|    - Накладні витрати < 1-2% (безпечно для Production)                  |
+-------------------------------------------------------------------------+
| 3. Post-Mortem Snapshot (Eclipse MAT)                                   |
|    - Статичний знімок (Dump) замороженого стану купи                    |
|    - Вимагає STW-паузи при створенні, але дає 100% точність графу       |
+-------------------------------------------------------------------------+
```

## 🔴 Senior Level

### 1. Аналіз позакучевої пам'яті: Native Memory Tracking (NMT)

Якщо метрики Java Heap стабільні, але фізичне споживання процесу (RSS у Linux) зростає і загрожує OOM Killer, проблема криється в **Native Memory** (Off-Heap).

Для увімкнення NMT JVM запускається з прапорцем:
```bash
-XX:NativeMemoryTracking=summary  # або =detail для точних адрес алокацій
```

#### Методологія пошуку нативних витоків через NMT Baseline & Diff:
```bash
# Крок 1: Фіксуємо базову точку після старту і прогріву сервісу
jcmd <pid> VM.native_memory baseline

# Крок 2: Виконуємо навантаження або очікуємо деградації пам'яті

# Крок 3: Отримуємо дельту (що саме зросло в нативній пам'яті)
jcmd <pid> VM.native_memory detail.diff
```

Приклад виводу дельти:
```
Total: reserved=5840MB +120MB, committed=3410MB +85MB
-                 Java Heap (reserved=4096MB, committed=2048MB)
-                    Class (reserved=1085MB +5MB, committed=65MB +3MB)
-                   Thread (reserved=120MB +45MB, committed=120MB +45MB)  <-- Витік: +45 нових потоків!
-            Internal (NIO) (reserved=250MB +60MB, committed=250MB +60MB) <-- Витік DirectByteBuffer!
```

### 2. Async-Profiler для відстеження алокацій пам'яті

**Async-profiler** — високопродуктивний низькорівневий профілювальник для Linux та macOS, що не страждає від проблеми *Safepoint Bias* (викривлення даних через збір метрик лише в точках зупинки).

Він вміє профілювати не лише процесор, але й алокації пам'яті:
```bash
# Профілювання алокацій у Java Heap (генерація FlameGraph):
./asprof -d 60 -e alloc -f alloc_flamegraph.html <pid>

# Профілювання нативних алокацій malloc() ядра C/C++:
./asprof -d 60 -e malloc -f native_malloc.html <pid>
```
Полум'яні графіки (*Flame Graphs*) алокацій миттєво показують методи, які створюють найбільше тимчасових об'єктів і навантажують Garbage Collector.

### 3. Інтерактивна діагностика через Arthas (Alibaba)

**Arthas** дозволяє підключатися до працюючого production-процесу без зміни конфігурації та прапорців запуску:

```bash
# Запуск консолі Arthas
java -jar arthas-boot.jar

# В інтерактивній консолі:
[arthas]$ dashboard         # Монітор стану пам'яті (Heap, Non-Heap, GC, Threads)
[arthas]$ memory            # Детальна розбивка пулів пам'яті JVM
[arthas]$ vmtool --action getInstances --className com.example.OrderService --limit 5
[arthas]$ heapdump /tmp/dump.hprof --live  # Зняти дамп тільки живих об'єктів
```

### 4. Небезпеки та ризики використання інструментів

1. **`GC.heap_dump` на терабайтних купах:** Переводить усі потоки застосунку в Safepoint на десятки секунд. Для високонавантажених вузлів вузол необхідно попередньо відключати від балансувальника навантаження (*traffic drain*).
2. **Прапорець `-XX:NativeMemoryTracking=detail`:** Збільшує затримки системних викликів `malloc` та `mmap`, створюючи накладні витрати 5–10% CPU. У production для постійної роботи рекомендується використовувати лише рівень `summary`.
3. **`jstack -F` або `jmap -F`:** Використання примусового прапорця `-F` чіпляється до процесу через системний налагоджувач `ptrace`, що в разі збою може повністю підвісити або аварійно завершити JVM процес.

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь для співбесіди
> «Інструменти аналізу пам'яті поділяються на три ключові групи:
> 1) **CLI-інструменти JVM** (`jcmd`) для оперативної телеметрії на сервері: зняття гістограми класів (`GC.class_histogram`), відстеження нативної пам'яті (NMT) та зняття дампів;
> 2) **Офлайн-аналізатори дампів** (Eclipse MAT), що використовуються для глибокого розслідування причин OOME через Dominator Tree, обчислення Retained Heap та аналіз шляхів до GC Roots;
> 3) **Низькооверхедні профайлери** (JFR/JMC та Async-profiler), що дозволяють безпечно відстежувати алокації та витоки (`jdk.OldObjectSample`) безпосередньо під навантаженням у бойовому production з накладними витратами менше 1%».

---

### Питання підвищеної складності з відповідями

1. **Чому `jcmd <pid> GC.class_histogram` набагато безпечніше запускати в production, ніж `jcmd <pid> GC.heap_dump`?**
   - *Відповідь:* Команда `GC.class_histogram` лише швидко сканує заголовки об'єктів у пам'яті й агрегує кількість екземплярів та їхній розмір за типами. Пауза Safepoint при цьому зазвичай не перевищує сотень мілісекунд. Навпаки, `GC.heap_dump` виконує повну серіалізацію складного графу об'єктів з усіма посиланнями та примітивними полями на диск. Для купи в десятки гігабайтів запис на диск блокує застосунок на десятки секунд, що гарантовано призводить до таймаутів клієнтів і збою перевірок працездатності (health checks).

2. **Як знайти витік нативної пам'яті (Off-Heap / Direct Memory), якщо Heap Dump показує, що купа майже порожня?**
   - *Відповідь:* У кучевому дампі нативна пам'ять не відображається. Для пошуку off-heap витоків використовують:
     - Прапорець `-XX:NativeMemoryTracking=summary` (або `detail`) і команду `jcmd <pid> VM.native_memory detail.diff`, яка наочно покаже зростання секцій `Internal (Direct buffers)`, `Thread (стеки)`, `Class` або `GC`;
     - Профілювання системних викликів виділення пам'яті за допомогою `async-profiler` з параметром `-e malloc`;
     - Аналіз системних інструментів операційної системи: `pmap -x <pid>` та утиліти трасування пам'яті glibc (jemalloc / jemalloc profiling).

3. **Чим інструмент `jcmd` принципово перевершує старий `jmap`?**
   - *Відповідь:* `jmap` розроблявся як окрема сервісна утиліта (`Serviceability Agent`), яка часто вимагала збігу точних версій бінарників, при збоях могла підвісити процес сигналом ptrace і не підтримувала динамічне керування новими підсистемами HotSpot. `jcmd` — це єдина консольна точка входу, що працює через офіційний JVM Attach API. `jcmd` підтримує десятки підсистем (керування GC, JFR, NMT, компілятором JIT, потоками), активно розвивається і є рекомендованим стандартом Oracle та OpenJDK.

4. **Як механізм JFR `OldObjectSample` допомагає знаходити витоки пам'яті без зняття важкого Heap Dump?**
   - *Відповідь:* JFR безперервно підтримує кільцевий буфер об'єктів-вибірки (зазвичай 256–512 екземплярів), алокованих застосунком. Якщо ці об'єкти переживають безліч циклів збирання сміття та просуваються у старше покоління (Tenured), JFR фіксує стек виклику моменту їхнього створення і динамічно відстежує ланцюжок посилань до GC Roots. Інженер у JMC бачить реальний шлях утримання і точний рядок коду, що створив об'єкт, який витік, без необхідності заморожувати застосунок і скидати десятки гігабайтів на диск.

---

### Типові помилки та Red Flags

- 🚩 **Знімати повний Heap Dump на терабайтній купі бойового сервісу в пік навантаження.** (Red Flag: гарантована відмова сервісу за таймаутами та падіння пода за Liveness Probe).
- 🚩 **Використовувати важке профілювання з інструментацією байткоду (Live BCI profiling) у бойовому production.** (Накладні витрати можуть сповільнити застосунок у 5–10 разів).
- 🚩 **Намагатися шукати нативні витоки (Direct ByteBuffer / Netty / JNI) в Eclipse MAT.** (У дампі купи видно лише 64-байтні Java-обгортки `DirectByteBuffer`, але не самі гігабайти виділеної нативної пам'яті).
