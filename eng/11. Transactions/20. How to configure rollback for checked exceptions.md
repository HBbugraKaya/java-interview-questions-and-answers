# How to Configure Rollback for Checked Exceptions

---

## 🟢 Junior Level

By default, Spring Framework's `@Transactional` annotation **does NOT roll back** when a **Checked Exception** occurs (any subclass of `java.lang.Exception`, excluding `RuntimeException`). When a checked exception is thrown, Spring treats it as an expected business outcome and executes a **`COMMIT`**.

To instruct Spring to roll back when checked exceptions occur, configure the **`rollbackFor`** attribute.

### The Industry Standard in 30 Seconds
The universal best practice across enterprise Spring applications:
```java
@Transactional(rollbackFor = Exception.class)
```
Configuring `rollbackFor = Exception.class` instructs Spring's AOP interceptor:
> *"Roll back the transaction upon encountering **any exception** (`Exception`), including `IOException`, `SQLException`, and all custom checked business exceptions."*

### Practical Example: Safe Bank Withdrawal

```java
package com.example.service;

import com.example.exception.InsufficientFundsException; // Checked exception: extends Exception
import com.example.repository.AccountRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.math.BigDecimal;

@Service
public class AccountService {

    private final AccountRepository accountRepository;

    public AccountService(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    // SAFE CONFIGURATION:
    @Transactional(rollbackFor = Exception.class)
    public void withdraw(Long accountId, BigDecimal amount) throws InsufficientFundsException {
        var account = accountRepository.findById(accountId).orElseThrow();

        if (account.getBalance().compareTo(amount) < 0) {
            // Because rollbackFor = Exception.class is set, this checked exception
            // is guaranteed to trigger a database ROLLBACK!
            throw new InsufficientFundsException("Insufficient funds on account");
        }

        account.setBalance(account.getBalance().subtract(amount));
        accountRepository.save(account);
    }
}
```

### Common Variations of `rollbackFor`

1. **For all checked and unchecked exceptions (Recommended):**
   ```java
   @Transactional(rollbackFor = Exception.class)
   ```
2. **For a specific checked exception:**
   ```java
   @Transactional(rollbackFor = InsufficientFundsException.class)
   ```
3. **For multiple specific exceptions:**
   ```java
   @Transactional(rollbackFor = {IOException.class, InsufficientFundsException.class})
   ```

## 🟡 Middle Level

### Three Architectural Strategies for Checked Exceptions

When designing enterprise systems dealing with checked exceptions, senior engineers evaluate three strategies:

| Strategy | Implementation | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **1. Declarative `rollbackFor`** | `@Transactional(rollbackFor = Exception.class)` | Preserves existing legacy code and `throws` contracts | Developers can easily forget to specify the attribute |
| **2. Unchecked Hierarchy (Best Practice)** | Refactor `extends Exception` to `extends RuntimeException` | Automatic rollback out of the box; clean stream/lambda signatures | Requires refactoring existing exception hierarchies |
| **3. Programmatic Rollback** | `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` | Allows graceful error handling without raising HTTP 500 errors | Couples application code to Spring's internal transaction API |

### Programmatic Rollback Inside `catch` Blocks

When a method must catch a checked exception, log the incident, and return a clean failure indicator to the client while still discarding all database writes:

```java
@Slf4j
@Service
public class DocumentExportService {

    @Transactional
    public boolean processAndArchiveDocument(Long docId) {
        updateDocumentStatus(docId, "PROCESSING");

        try {
            writePdfToNetworkShare(docId); // Throws checked IOException
            return true;
        } catch (IOException ex) {
            log.error("Network storage unreachable: {}", ex.getMessage());
            // Programmatically mark the active transaction for rollback:
            TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
            return false; // Returns false to client; database mutations will be completely undone!
        }
    }
}
```

## 🔴 Senior Level

### Global Application-Wide `rollbackFor` Configuration

To eliminate human error across hundreds of service methods, teams adopt global rollback enforcement:

#### Approach A: Custom Composed Meta-Annotation (Clean & Type-Safe)
Spring supports composed meta-annotations:

```java
package com.example.annotation;

import org.springframework.core.annotation.AliasFor;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;
import java.lang.annotation.*;

@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Inherited
@Documented
@Transactional(rollbackFor = Exception.class) // Default base rule: Rollback on EVERYTHING!
public @interface Tx {

    @AliasFor(annotation = Transactional.class, attribute = "readOnly")
    boolean readOnly() default false;

    @AliasFor(annotation = Transactional.class, attribute = "propagation")
    Propagation propagation() default Propagation.REQUIRED;

    @AliasFor(annotation = Transactional.class, attribute = "timeout")
    int timeout() default -1;
}
```
Now services simply declare `@Tx`, guaranteeing enterprise-wide checked exception rollbacks automatically.

#### Approach B: Customizing the `TransactionInterceptor` Bean
Configure a global fallback rule programmatically in Spring's configuration:

```java
@Configuration
public class GlobalTransactionConfig {

    @Bean
    public TransactionInterceptor transactionInterceptor(PlatformTransactionManager txManager) {
        RuleBasedTransactionAttribute defaultRule = new RuleBasedTransactionAttribute();
        // Add global rollback rule for Exception.class:
        defaultRule.setRollbackRules(Collections.singletonList(new RollbackRuleAttribute(Exception.class)));

        NameMatchTransactionAttributeSource source = new NameMatchTransactionAttributeSource();
        source.addTransactionalMethod("*", defaultRule);

        return new TransactionInterceptor(txManager, source);
    }
}
```

### Rule Matching Algorithm When Combining Rules

When `@Transactional` combines both `rollbackFor` and `noRollbackFor`:

```java
@Transactional(
    rollbackFor = Exception.class,
    noRollbackFor = EntityNotFoundBusinessException.class
)
public void syncCatalog() throws Exception { ... }
```
1. Spring traverses the class hierarchy recursively to calculate the inheritance distance (`depth`):
   $$\text{depth}(\text{TargetClass}, \text{CurrentClass}) = \begin{cases} 0, & \text{if } \text{TargetClass} == \text{CurrentClass} \\ 1 + \text{depth}(\text{TargetClass.superclass}), & \text{otherwise} \end{cases}$$
2. If `EntityNotFoundBusinessException` is thrown, the depth for the `noRollbackFor` rule equals `0` (exact type match).
3. The depth for `rollbackFor = Exception.class` equals `2` (`EntityNotFoundBusinessException` $\rightarrow$ `BusinessException` $\rightarrow$ `Exception`).
4. **The rule with the lowest depth (`depth = 0`) wins:** Spring **COMMITS** the transaction, overriding the broad `rollbackFor = Exception.class`!

## 4 Tricky Questions

### 1. What is the difference between `rollbackFor = Exception.class` and `rollbackFor = Throwable.class`?

**Answer:**
- `Exception.class` covers all checked exceptions and all unchecked exceptions (`RuntimeException`). However, it **does not cover direct subclasses of `Throwable`** that do not inherit from `Exception` (though creating direct subclasses of `Throwable` is strongly discouraged in Java).
- `Throwable.class` sits at the absolute root of Java's error hierarchy (`Throwable` $\rightarrow$ `Exception` and `Error`). Specifying `rollbackFor = Throwable.class` guarantees a rollback on literally any object that can be thrown via the `throw` keyword in Java.
In practice, `rollbackFor = Exception.class` is 100% sufficient for 99.9% of enterprise applications because `Error` is already included in Spring's built-in default rollback rules.

---

### 2. What happens if an outer method with `rollbackFor = Exception.class` calls an inner method declared with `noRollbackFor = IOException.class` (both using `REQUIRED`), and the inner method throws an `IOException`?

**Answer:**
The transaction **ROLLS BACK**!
**Internal Execution Flow:**
1. Both methods run within the same shared physical transaction.
2. When the inner method throws an `IOException`, the inner `TransactionInterceptor` inspects its local metadata (`noRollbackFor = IOException.class`). It therefore **does not** mark the transaction status as `setRollbackOnly()`.
3. The exception propagates upward and escapes the outer method boundary.
4. The outer method's `TransactionInterceptor` intercepts the `IOException` and checks its own rules (`rollbackFor = Exception.class`).
5. Because `IOException instanceof Exception`, the outer interceptor issues a physical database `connection.rollback()`.

---

### 3. Why is using `rollbackForClassName = "MyException"` considered a dangerous production anti-pattern?

**Answer:**
Because Spring **does not validate string class names at compilation time or application startup**.
The class lookup is resolved lazily via substring pattern matching at runtime. If a developer makes a typographical error (e.g., `rollbackForClassName = "IOExcepshon"`), Spring boots without any warning. When the real `IOException` is thrown at runtime, the string rule fails to match (`depth == -1`). Spring silently falls back to its default rule and **commits the transaction**, permanently corrupting database state. Always use type-safe class literals: `rollbackFor = IOException.class`.

---

### 4. Why does modern Spring Boot architecture recommend replacing checked exceptions with `RuntimeException` or Result types?

**Answer:**
1. **Functional Programming Compatibility:** Standard Java 8+ functional interfaces (`Function`, `Consumer`, `Supplier`, and Stream pipelines) do not declare `throws Exception`. Throwing checked exceptions inside `.map()` or `.filter()` requires verbose `try-catch` wrappers or Lombok `@SneakyThrows`.
2. **Elimination of Silent Commits:** With checked exceptions, any forgotten `rollbackFor` attribute leads to silent data corruption on error. Inheriting domain exceptions from `RuntimeException` guarantees rollback out of the box.
3. **Architectural Decoupling:** Unchecked exceptions decouple service contracts from interface method signatures, allowing centralized error translation via `@RestControllerAdvice`.

---

## 🎯 Interview Cheat Sheet

- **Core Problem:** Spring commits on checked exceptions by default.
- **The Solution:** Add `@Transactional(rollbackFor = Exception.class)`.
- **Modern Best Practice:** Subclass custom domain exceptions from `RuntimeException` rather than `Exception`.
- **Programmatic Alternative:** Use `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`.
- **Rule Precedence:** When `rollbackFor` and `noRollbackFor` conflict, the rule closest in inheritance distance (`depth`) wins.
- **String Danger:** Never use `rollbackForClassName`; typographical errors fail silently and cause unintended commits.
- **Composed Annotations:** Use custom meta-annotations (e.g., `@Tx`) to standardize `rollbackFor = Exception.class` project-wide.
