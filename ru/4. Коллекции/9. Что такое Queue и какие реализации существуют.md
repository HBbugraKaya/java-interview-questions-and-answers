# Что такое Queue и какие реализации существуют

---

## 🟢 Junior Level

**`Queue` (Очередь)** — это интерфейс Java Collections Framework, предназначенный для хранения элементов в порядке их последующей обработки.

В большинстве реализаций очередь работает по принципу **FIFO** (*First-In, First-Out* — «первым пришел, первым обслужен»), аналогично реальной очереди покупателей в кассу.

### Две группы методов интерфейса `Queue`

Интерфейс предоставляет парные методы для каждой операции: одни бросают исключение при сбое, другие возвращают специальное значение (`false` или `null`):

| Действие с очередью | Бросает исключение при ошибке | Возвращает специальное значение |
| :--- | :--- | :--- |
| **Добавить в конец** | `add(e)` (бросает `IllegalStateException`, если очередь полна) | **`offer(e)`** (возвращает `false`, если нет места) |
| **Извлечь из начала (с удалением)**| `remove()` (бросает `NoSuchElementException`, если очередь пуста)| **`poll()`** (возвращает `null`, если очередь пуста) |
| **Посмотреть начало (без удаления)**| `element()` (бросает `NoSuchElementException`, если очередь пуста)| **`peek()`** (возвращает `null`, если очередь пуста) |

```java
// Пример стандартного использования очереди FIFO
Queue<String> queue = new ArrayDeque<>();

queue.offer("Заказ #1");
queue.offer("Заказ #2");

System.out.println(queue.peek()); // "Заказ #1" (просмотр головы)
System.out.println(queue.poll()); // "Заказ #1" (извлечение и удаление)
System.out.println(queue.poll()); // "Заказ #2"
System.out.println(queue.poll()); // null (очередь пуста, без исключений)
```

## 🟡 Middle Level

### 1. Основные реализации в стандартной библиотеке

В Java не существует одного «универсального» класса очереди. Реализация выбирается под конкретные требования алгоритма:

```
                          java.util.Queue<E>
                                  │
      ┌───────────────────────────┼───────────────────────────┐
      ▼                           ▼                           ▼
ArrayDeque<E>              PriorityQueue<E>            BlockingQueue<E>
(быстрый кольцевой          (двоичная куча,             (многопоточные
 массив без блокировок)      сортировка по весу)         блокирующие очереди)
```

1. **`ArrayDeque`:**
   - Высокопроизводительный кольцевой динамический массив.
   - Идеальный выбор для однопоточного кода (быстрее `LinkedList` в несколько раз).
   - Вставка и извлечение выполняются за строгое константное время $O(1)$.
2. **`PriorityQueue`:**
   - Очередь с приоритетом на базе **двоичной кучи (Binary Min-Heap)** в непрерывном массиве.
   - Элементы извлекаются не по порядку добавления, а по их приоритету. По умолчанию извлекается **наименьший элемент** согласно `Comparable` или переданному `Comparator`.
   - Сложность: `offer()` — $O(\log N)$, `poll()` — $O(\log N)$, `peek()` — $O(1)$.
3. **`LinkedList`:**
   - Реализует интерфейс `Queue`, но не рекомендуется к использованию из-за высоких накладных расходов памяти и кэш-промахов.

### 2. Почему очереди запрещают значение `null`?

Подавляющее большинство реализаций `Queue` (включая `ArrayDeque`, `PriorityQueue` и все классы из `java.util.concurrent`) выбрасывают **`NullPointerException`** при попытке добавить `null`.

**Причина запрета:**
Методы `poll()` и `peek()` используют значение `null` как индикатор того, что **очередь в данный момент пуста**. Если бы в очередь разрешалось помещать `null`, то возвращаемое значение `null` создавало бы неразрешимую двусмысленность: означает ли это, что очередь пуста, или что из нее был успешно извлечен валидный элемент `null`?

## 🔴 Senior Level

### 1. Многопоточные очереди в `java.util.concurrent`

В параллельном программировании очереди являются фундаментом архитектурного паттерна **«Производитель — Потребитель» (Producer-Consumer)**:

| Класс очереди | Принцип работы | Ограничение емкости (Bounded) | Механизм синхронизации |
| :--- | :--- | :--- | :--- |
| **`ConcurrentLinkedQueue`** | Lock-Free очередь на базе CAS | Неограниченная (Unbounded) | Алгоритм Майкла и Скотта (AtomicReference) |
| **`ArrayBlockingQueue`** | Блокирующий кольцевой массив | **Строго ограниченная (Bounded)** | Один общий `ReentrantLock` на чтение и запись |
| **`LinkedBlockingQueue`** | Блокирующий связный список | Настраиваемая (по умолчанию $2^{31}-1$) | **Две раздельные блокировки:** `takeLock` и `putLock` |
| **`SynchronousQueue`** | Очередь с нулевой емкостью (Rendezvous) | Емкость = 0 | Поток-писатель ждет поток-читатель напрямую |
| **`DelayQueue`** | Очередь задач с временной задержкой | Неограниченная | На базе `PriorityQueue` + блокировки |
| **`LinkedTransferQueue`** | Гибрид `LinkedBlockingQueue` и `SynchronousQueue` | Неограниченная | Алгоритм Dual Queue (CAS + парковка потоков) |

### 2. Опасность неограниченных очередей (Unbounded Queues) и Backpressure

Одна из главных причин падения приложений по `OutOfMemoryError` в production — создание пулов потоков с неограниченной очередью:

```java
// ❌ СКРЫТАЯ УГРОЗА OOM:
ExecutorService executor = Executors.newFixedThreadPool(10);
// Под капотом создается LinkedBlockingQueue с емкостью Integer.MAX_VALUE!
```
Если скорость поступления задач (Producer) превышает скорость их обработки пулом (Consumer), очередь начинает бесконтрольно расти, накапливая миллионы объектов в куче, пока JVM не погибнет от `OutOfMemoryError: Java heap space`.

#### Решение: Ограниченные очереди (Bounded Queue) и Backpressure
```java
// ✅ PRODUCTION-READY ПОДХОД:
BlockingQueue<Runnable> queue = new ArrayBlockingQueue<>(1000);
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4, 8, 60L, TimeUnit.SECONDS, queue,
    new ThreadPoolExecutor.CallerRunsPolicy() // Политика противодавления!
);
```
- Когда очередь заполняется до 1000 элементов, срабатывает механизм противодавления (**Backpressure**).
- Политика `CallerRunsPolicy` заставляет поток, отправивший задачу, выполнять ее самостоятельно. Это естественным образом замедляет прием новых запросов снаружи, защищая сервис от деградации памяти.

### 3. Раздельные блокировки в `LinkedBlockingQueue`: Two-Lock Queue

В `ArrayBlockingQueue` используется один мьютекс `ReentrantLock`. Это означает, что операции записи `put()` и чтения `take()` не могут выполняться одновременно: продюсер блокирует консьюмера.

В `LinkedBlockingQueue` реализован алгоритм с **двумя независимыми блокировками**:
- `putLock` защищает только хвост очереди (вставку);
- `takeLock` защищает только голову очереди (извлечение);
- Потоки-писатели и потоки-читатели работают **параллельно**, не мешая друг другу. Это обеспечивает кратно больший throughput на многоядерных серверах.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ для собеседования
> «`Queue` — это интерфейс для упорядоченной обработки элементов (обычно по принципу FIFO). Его методы разделены на две группы: выбрасывающие исключения (`add`, `remove`, `element`) и возвращающие специальные значения (`offer`, `poll`, `peek`), которые предпочтительны в боевом коде. В однопоточных сценариях стандартом является `ArrayDeque` ($O(1)$ без накладных расходов памяти), а для упорядочивания по приоритету — `PriorityQueue` (Min-Heap). В многопоточных задачах используются реализации `BlockingQueue`, где критически важно использовать строго ограниченную емкость (Bounded Queue) для обеспечения противодавления (Backpressure) и защиты от OOM».

### Вопросы повышенной сложности с ответами

1. **Почему в большинстве реализаций `Queue` запрещено хранить `null`?**
   *Ответ:* Методы `poll()` и `peek()` используют возвращаемое значение `null` в качестве специального индикатора того, что очередь пуста. Если бы в очередь можно было положить значение `null`, то возвращенный `null` порождал бы неустранимую двусмысленность: то ли очередь пуста, то ли из нее прочитан элемент со значением `null`. Чтобы исключить эту неопределенность и избавиться от лишних проверок, спецификация очередей требует выбрасывать `NullPointerException` при попытке добавить `null`.

2. **Как устроен класс `PriorityQueue` и какой элемент извлекается первым по умолчанию?**
   *Ответ:* `PriorityQueue` реализован на базе структуры данных «двоичная куча» (Binary Heap), упакованной в обычный массив. По умолчанию `PriorityQueue` является **минимальной кучей (Min-Heap)**, то есть первым извлекается **наименьший** элемент в соответствии с естественным порядком (`Comparable`) или компаратором (`Comparator`). Вставка нового элемента (`offer`) и извлечение корня (`poll`) требуют $O(\log N)$ шагов для просеивания (sift-up / sift-down), а просмотр вершины (`peek`) выполняется за $O(1)$.

3. **В чём заключается принципиальная разница в синхронизации между `ArrayBlockingQueue` и `LinkedBlockingQueue`?**
   *Ответ:* `ArrayBlockingQueue` использует единственный общий объект блокировки `ReentrantLock` для всех операций. Из-за этого потоки, добавляющие элементы (`put`), и потоки, извлекающие элементы (`take`), конкурируют за один и тот же мьютекс. `LinkedBlockingQueue` использует два независимых замка: `putLock` для добавления в хвост и `takeLock` для удаления из головы. Это позволяет продюсерам и консьюмерам работать полностью параллельно, исключая взаимную блокировку.

4. **Что представляет собой `SynchronousQueue` и каков её размер?**
   *Ответ:* `SynchronousQueue` — это специализированная блокирующая очередь с емкостью строго равной нулю. В ней каждый вызов `put()` блокирует поток до тех пор, пока другой поток не вызовет `take()` для непосредственного приема этого элемента «из рук в руки» (механизм рандеву). Вызов `size()` всегда возвращает 0, а итератор всегда пуст. Она используется в сценариях мгновенной передачи задач между потоками, например в `Executors.newCachedThreadPool()`.

### Типичные ошибки и Red Flags
- ❌ **Считать, что `PriorityQueue` по умолчанию извлекает самый большой элемент.** (Red Flag: по умолчанию это Min-Heap, извлекается наименьший элемент).
- ❌ **Использовать `Executors.newFixedThreadPool()` с дефолтной неограниченной очередью под высокой нагрузкой.** (Гарантированный риск падения сервиса по OOM).
- ❌ **Пытаться сохранить `null` в `ArrayDeque` или `BlockingQueue`.** (Приведет к мгновенному `NullPointerException`).
