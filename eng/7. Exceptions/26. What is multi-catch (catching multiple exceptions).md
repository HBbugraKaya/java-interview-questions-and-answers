# What is multi-catch (catching multiple exceptions)

---

## 🟢 Junior Level

### Short Interview Answer (30 seconds)
**Multi-Catch** is a language feature introduced in Java 7 (Project Coin / JSR 334) that allows a single `catch` block to handle **multiple distinct, unrelated exception types** using the pipe (`|`) delimiter: `catch (IOException | SQLException e)`.

It eliminates boilerplate code by sharing identical error-handling logic across multiple exception pathways without forcing developers to catch an overly broad superclass like `Exception`.

When using `multi-catch`, the compiler enforces two strict rules:
1. **The exception parameter `e` is implicitly `final`:** Its reference cannot be reassigned (e.g., `e = new IOException();` causes a compilation error).
2. **Alternatives cannot be related by inheritance:** Declaring `catch (FileNotFoundException | IOException e)` is prohibited because the subclass is already encompassed by the superclass.

---

### Canonical Java 21 Example

```java
import java.io.IOException;
import java.sql.SQLException;

public class MultiCatchDemo {

    public void processDataPipeline() {
        try {
            readExternalConfiguration();
            persistDatabaseRecords();
        } catch (IOException | SQLException e) {
            // ✅ Single handler for multiple disjoint failures
            // e.getClass() returns the actual runtime instance type
            System.err.println("Infrastructure pipeline failure: " + e.getMessage());
            throw new PipelineExecutionException("Failed data pipeline processing", e);
        }
    }

    private void readExternalConfiguration() throws IOException { }
    private void persistDatabaseRecords() throws SQLException { }

    static class PipelineExecutionException extends RuntimeException {
        public PipelineExecutionException(String message, Throwable cause) {
            super(message, cause);
        }
    }
}
```

## 🟡 Middle Level

### Rule 1: The Inheritance Prohibition (Disjoint Types Requirement)

If a developer attempts to combine exception types belonging to the same inheritance lineage in a `multi-catch` clause, the `javac` compiler halts with an error:

```java
// ❌ COMPILATION ERROR:
// Alternatives in a multi-catch statement cannot be related by subclassing
// Alternative 'java.io.FileNotFoundException' is a subclass of 'java.io.IOException'
try {
    readFile();
} catch (FileNotFoundException | IOException e) {
    log.error("Failed to read file", e);
}
```

#### Why the Specification Forbids This:
Under the Java Language Specification (JLS §14.20), listing `FileNotFoundException | IOException` is redundant dead code. Because `FileNotFoundException` is a subclass of `IOException`, `IOException` alone already catches every possible instance of `FileNotFoundException`. Disallowing subtype alternatives prevents semantic confusion and code bloat.

**How to Resolve:**
- If the handling logic is **identical**: declare only the superclass (`catch (IOException e)`).
- If the handling logic is **different**: separate them into distinct `catch` blocks, placing the specific subclass first.

---

### Rule 2: Why the Multi-Catch Parameter is Strictly `final`

In a traditional single `catch (IOException e)` block, the variable `e` is non-final by default and may be reassigned. In a `multi-catch` block, however, the variable `e` is **implicitly `final`**:

```java
try {
    executeTask();
} catch (IOException | SQLException e) {
    // ❌ COMPILATION ERROR:
    // Multi-catch parameter e is final and cannot be assigned
    // e = new IOException("Overwritten"); 
}
```

#### Architectural Rationale:
The static compile-time type of `e` is the **Least Upper Bound (LUB)** of the listed alternatives (typically `Exception`). If Java permitted reassigning `e = new IOException()`, a type-safety loophole would open: if the block was originally entered due to an `SQLException`, reassigning `e` to an `IOException` would break the type invariant for subsequent operations expecting `SQLException`.

---

### Under the Hood: JVM Bytecode Representation

At the JVM bytecode level, there is **no special "multi-catch" opcode or compound type**.

The `javac` compiler maps the multi-catch clause to **multiple independent entries in the method's `Exception_table`**, each referencing the exact same bytecode entry offset (`target`):

```text
// Disassembled via javap -c -v MultiCatchDemo.class:
Exception table:
   from    to  target type
       0     8    12   Class java/io/IOException
       0     8    12   Class java/sql/SQLException
```
**Advantage:** The developer avoids duplicating Java source code, while the compiled classfile generates only **a single copy of the catch block body**, reducing classfile size and optimizing CPU instruction cache locality.

## 🔴 Senior Level

### Precise Rethrow (Java 7+ Flow Analysis)

Introduced alongside multi-catch in Java 7, **Precise Rethrow** allows a method to catch a broad `Exception` and rethrow it while preserving the exact checked exception types in the method's `throws` signature:

```java
public class PreciseRethrowDemo {

    // ✅ Signature advertises EXACT checked types, NOT 'throws Exception'!
    public void execute() throws IOException, SQLException {
        try {
            if (System.currentTimeMillis() % 2 == 0) {
                throw new IOException("Storage disk full");
            } else {
                throw new SQLException("Deadlock detected");
            }
        } catch (Exception e) { // Catch broad Exception
            System.err.println("Logging failure before propagation: " + e.getMessage());
            // ✅ javac performs definite assignment and type analysis:
            // Since 'e' is effectively final, javac proves 'e' can ONLY be IOException or SQLException!
            throw e; 
        }
    }
}
```
Prior to Java 7, writing `throw e` inside `catch (Exception e)` forced the enclosing method header to declare `throws Exception`, polluting the public API contract.

### Production Use Case: Java Reflection API

Before Java 7, invoking reflective operations required verbose, repetitive catch ladders. Multi-catch condenses reflection handling into a clean, unified block:

```java
try {
    Class<?> clazz = Class.forName("com.enterprise.PaymentWorker");
    Method method = clazz.getDeclaredMethod("processPayment", Long.class);
    method.invoke(clazz.getDeclaredConstructor().newInstance(), orderId);
} catch (ClassNotFoundException | NoSuchMethodException | 
         InstantiationException | IllegalAccessException | 
         InvocationTargetException e) {
    log.error("Reflection dispatch failed for orderId={}", orderId, e);
    throw new ServiceInitializationException("Failed to invoke payment worker reflectively", e);
}
```

### The InterruptedException Trap in Multi-Catch

A critical production bug arises when mixing `InterruptedException` with ordinary I/O exceptions in a multi-catch block:

```java
// ❌ CRITICAL CONCURRENCY BUG: Silent clearing of thread interrupt status
try {
    Thread.sleep(500);
    socket.read();
} catch (InterruptedException | IOException e) {
    log.error("Communication interrupted or failed", e);
    // 💥 If e was InterruptedException, the interrupt flag was cleared upon throw!
    // The thread pool / container orchestrator cannot detect cancellation!
}

// ✅ PRODUCTION FIX: Explicitly restore interruption status
try {
    Thread.sleep(500);
    socket.read();
} catch (InterruptedException | IOException e) {
    if (e instanceof InterruptedException) {
        Thread.currentThread().interrupt(); // Restore interrupt status flag!
    }
    log.error("Communication interrupted or failed", e);
}
```

## 4 Tricky Questions

### 1. What methods can you invoke on parameter `e` inside `catch (IOException | SQLException e)` without casting?
**Answer:** You can invoke **only the methods declared in their Least Upper Bound (LUB)**. Because the lowest common superclass of `IOException` and `SQLException` is `java.lang.Exception`, you can only invoke methods available on `Exception` (and `Throwable`), such as `getMessage()`, `getCause()`, `getStackTrace()`, and `printStackTrace()`. You cannot invoke `SQLException.getErrorCode()` or `IOException.getCause()` without an explicit `instanceof` pattern check.

---

### 2. Is it legal to explicitly add the `final` keyword to a multi-catch clause: `catch (final IOException | SQLException e)`?
**Answer:** **Yes, it is completely legal syntax.** Although the parameter `e` in a multi-catch clause is already **implicitly `final`**, the Java grammar permits explicitly writing `final` for stylistic clarity. Reassignment remains forbidden regardless of whether `final` is written explicitly.

---

### 3. What runtime class is returned by `e.getClass()` when executing inside `catch (IOException | SQLException e)`?
**Answer:** It returns the **exact concrete runtime class** of the actual thrown exception (e.g., `class java.io.FileNotFoundException` or `class org.postgresql.util.PSQLException`). Java's runtime reflection has no synthetic "union" types; `e` points directly to the real heap object instantiated at the point of failure.

---

### 4. What happens if you catch `Exception | RuntimeException e`?
**Answer:** It triggers a **compilation error**. `RuntimeException` is a direct subclass of `Exception`. Under JLS §14.20, multi-catch alternatives cannot have a subclass/superclass relationship.

### Core Concepts Matrix
```
┌───────────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────┐
│ Feature                   │ Single Catch (catch (IOException e))     │ Multi-Catch (catch (IOEx | SQLEx e))     │
├───────────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────┤
│ Parameter Mutability      │ Non-final by default (can reassign)      │ Implicitly final (reassignment ILLEGAL)  │
│ Type Relationship         │ Any valid class type                     │ Must be disjoint (no inheritance links)  │
│ Compile-Time Static Type  │ Exact declared class                     │ Least Upper Bound (LUB) of alternatives  │
│ Bytecode Exception Table  │ Single row pointing to handler           │ Multiple rows pointing to SAME handler   │
│ Code Duplication          │ Requires copy-pasting for each type      │ Single unified handler body              │
└───────────────────────────┴──────────────────────────────────────────┴──────────────────────────────────────────┘
```

### Key Takeaways
1. Multi-catch (`catch (A | B e)`) groups multiple disjoint exception types into a single handler.
2. Alternatives in multi-catch must NOT be related by subclassing (e.g., `FileNotFoundException | IOException` fails compilation).
3. The parameter `e` is implicitly `final` and cannot be reassigned.
4. In bytecode, multi-catch generates separate entries in the `Exception_table` sharing the same execution `target`.
5. When catching `InterruptedException` in multi-catch, always check `instanceof InterruptedException` and invoke `Thread.currentThread().interrupt()`.

### Red Flags to Avoid
- ❌ Listing parent and child exceptions together in a multi-catch block.
- ❌ Attempting to reassign the multi-catch parameter `e`.
- ❌ Swallowing or failing to restore thread interruption when catching `InterruptedException` alongside other exceptions.
- ❌ Assuming multi-catch generates a new compound runtime exception class in the JVM.
