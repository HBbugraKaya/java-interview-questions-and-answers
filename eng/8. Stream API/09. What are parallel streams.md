# What are parallel streams

---

## 🟢 Junior Level

### 30-Second Summary
**Parallel Streams** are a mechanism within the Java Stream API that automatically distributes stream processing across multiple CPU cores without requiring developers to manually manage threads, locks, or synchronization.

Under the hood, parallel streams leverage the JVM-wide **`ForkJoinPool.commonPool()`** and a recursive **Divide-and-Conquer** algorithm. You can create a parallel stream either by invoking `collection.parallelStream()` on any `Collection`, or by switching an existing sequential stream pipeline using the intermediate `.parallel()` method.

---

### Basic Java 21 Examples

```java
import java.util.List;
import java.util.stream.LongStream;

public class ParallelStreamBasicsDemo {

    public static void main(String[] args) {
        // 1. Parallel reduction over a numeric range
        long sum = LongStream.rangeClosed(1, 10_000_000)
            .parallel()
            .filter(n -> n % 2 == 0)
            .map(n -> n * 3)
            .sum();

        System.out.println("Computed sum: " + sum);

        // 2. Observing multi-threaded worker execution
        List<String> items = List.of("A", "B", "C", "D", "E", "F");

        System.out.println("Processing elements across threads:");
        items.parallelStream().forEach(item -> {
            System.out.printf("Item: %s, Executed by: %s%n",
                item, Thread.currentThread().getName());
        });
    }
}
```

> [!IMPORTANT]
> **Encounter Order Warning:** The standard `forEach()` terminal operation processes elements in **non-deterministic order** across worker threads. If preserving input order is mandatory, use `forEachOrdered()`, but be aware that forcing sequential ordering introduces synchronization barriers that significantly diminish parallel performance gains.

## 🟡 Middle Level

### Data Partitioning: `Spliterator.trySplit()`

A parallel stream breaks an input dataset into discrete subtasks via recursive calls to **`Spliterator.trySplit()`**:
1. The root `Spliterator` splits its sequence into halves, returning a new `Spliterator` covering the first half while retaining the second half.
2. The runtime recursively repeats this division until chunks reach a threshold suitable for sequential execution.
3. Chunks are dispatched to worker threads in `ForkJoinPool`, and intermediate results are merged via the collector or reducer's `combiner()`.

```
                  [ 1, 2, 3, 4, 5, 6, 7, 8 ]
                             │
                     trySplit() (O(1))
                    ┌─────────┴─────────┐
              [ 1, 2, 3, 4 ]       [ 5, 6, 7, 8 ]
                    │                     │
               trySplit()            trySplit()
              ┌─────┴─────┐         ┌─────┴─────┐
           [ 1, 2 ]    [ 3, 4 ]  [ 5, 6 ]    [ 7, 8 ]
              │           │         │           │
           Worker 1    Worker 2  Worker 3    Worker 4
              │           │         │           │
              └─────┬─────┘         └─────┬─────┘
                Combiner                Combiner
                    └──────────┬──────────┘
                         Final Result
```

#### Splitting Efficiency by Data Structure:

| Data Structure | Splitting Complexity | Quality of Split | Parallel Suitability |
| :--- | :--- | :--- | :--- |
| `ArrayList`, arrays, `IntStream.range` | $O(1)$ | Perfect (exact midpoint calculation by index) | 🟢 Excellent |
| `HashSet`, `TreeSet` | $O(1)$ amortized / $O(\log N)$ | Good (partitions buckets or subtrees) | 🟡 Moderate |
| `LinkedList` | $O(N)$ | Terrible (requires traversing $N/2$ pointers to find middle) | 🔴 Poor |
| `Stream.iterate()` | $O(N)$ | Impossible to split ahead (serial dependency on previous item) | 🔴 Non-viable |

---

### The Global Pool: `ForkJoinPool.commonPool()`

By default, all parallel streams across the entire JVM process share a single static thread pool: **`ForkJoinPool.commonPool()`**.

- **Default Worker Count:** `Runtime.getRuntime().availableProcessors() - 1`.
- **Why `- 1`?** The calling thread (the thread that invokes the stream's terminal operation) directly participates in task execution alongside the pool's worker threads. Therefore, total executing threads equal the exact number of available CPU cores.
- **Tuning Configuration:** Parallelism can be configured via JVM startup flag:
  `-Djava.util.concurrent.ForkJoinPool.common.parallelism=N`

## 🔴 Senior Level

### Internal Concurrency Engine: `CountedCompleter` & Work-Stealing

Parallel stream reductions are orchestrated by internal subclasses of `ForkJoinTask`, predominantly **`CountedCompleter`** (such as `ReduceTask`, `ForEachTask`, and `MatchTask`).

```
Worker Thread 1 Deque:  [Task A] [Task B] [Task C] <--- Push / Pop (LIFO: Cache Locality)
Worker Thread 2 Deque:  (Empty) --------------------> Steal Task A (FIFO: Contention-Free)
```

1. **Work-Stealing Architecture:**
   - Each worker thread maintains an independent double-ended task queue (deque).
   - A thread pushes and pops its own subtasks from the **tail** (LIFO), maximizing CPU L1/L2 cache locality.
   - When a thread exhausts its queue, it "steals" tasks from the **head** (FIFO) of another thread's deque, minimizing lock contention.
2. **Non-Blocking Tree Completion:**
   - Traditional `ForkJoinTask.join()` blocks the waiting thread.
   - `CountedCompleter` eliminates thread blocking: each completing child task atomically decrements a parent `pendingCount`. The last completing thread automatically invokes `onCompletion()`, hierarchically folding sibling results upward without sleeping or blocking OS threads.

---

### Feasibility Formula: The $N \times Q > 10,000$ Heuristic

Parallelism introduces non-trivial overhead: task splitting, deque synchronization, context switching, memory cache invalidation, and container merging. According to Brian Goetz (Java Language Architect), parallel streams yield net performance speedups only when:

$$N \times Q > 10{,}000$$

- $N$: Total number of stream elements.
- $Q$: Computational cost (CPU clock cycles/instructions) required to process a single element.

If $Q$ is low (e.g., trivial integer addition `x -> x + 1`), $N$ must exceed several hundred thousand or millions of items. If $N \times Q$ is small, the coordination overhead exceeds the multi-core computation savings, making the parallel stream **substantially slower than a basic sequential `for` loop**.

---

### Architectural Hazards of `commonPool()`

#### 1. Blocking I/O Starvation
Because `commonPool()` is shared across the entire JVM process, executing blocking operations (HTTP requests, JDBC queries, or file access) inside a parallel stream causes worker threads to sleep.
- Other application components relying on `commonPool()` (unrelated user streams, `CompletableFuture.supplyAsync()`) stall due to thread starvation.
- In Spring Boot or microservice architectures, this causes catastrophic cascading latency spikes and thread exhaustion.

#### 2. Isolation via Custom `ForkJoinPool`
To prevent starving `commonPool()`, heavy parallel operations can be submitted to an isolated, dedicated pool:

```java
import java.util.List;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ForkJoinPool;

public class CustomPoolStreamDemo {

    public static void main(String[] args) throws ExecutionException, InterruptedException {
        List<Integer> data = List.of(1, 2, 3, 4, 5, 6, 7, 8);
        ForkJoinPool customPool = new ForkJoinPool(4);

        try {
            long result = customPool.submit(() ->
                // Inside customPool.submit(), parallelStream identifies that the current
                // thread belongs to customPool, executing tasks exclusively within it!
                data.parallelStream()
                    .mapToInt(x -> x * 2)
                    .sum()
            ).get();

            System.out.println("Result: " + result);
        } finally {
            customPool.shutdown();
        }
    }
}
```

> [!WARNING]
> **Specification Caveat:** Although running parallel streams inside `customPool.submit()` works consistently across all OpenJDK HotSpot versions, it is **not formally guaranteed by the Java SE Specification** (it relies on an internal HotSpot implementation detail where `ForkJoinTask.getPool()` intercepts the current thread context).

## 4 Tricky Questions

### 1. Why is the default parallelism level of `ForkJoinPool.commonPool()` set to `availableProcessors() - 1` instead of `availableProcessors()`?
**Answer:**
The parallelism parameter in `ForkJoinPool` specifies the number of background worker threads in the pool. When a parallel stream executes a terminal operation, the **calling thread** (e.g., the `main` application thread or a Tomcat request-handling thread) does not block passively waiting for results; it actively participates in the computation by popping and processing tasks from the queues.

Therefore, total active threads executing work equal:
$$\text{Active Threads} = (\text{Worker Threads}) + (\text{Calling Thread}) = (\text{Processors} - 1) + 1 = \text{Processors}$$
This perfectly saturates available hardware cores without triggering wasteful OS thread context switches.

---

### 2. How can you execute a parallel stream inside a dedicated custom `ForkJoinPool`, and does the Java SE specification guarantee this behavior?
**Answer:**
You can submit the parallel stream pipeline inside a `Callable` or `Runnable` to a dedicated `ForkJoinPool`:
```java
customPool.submit(() -> stream.parallel().filter(...).collect(...)).get();
```
In OpenJDK HotSpot, when a parallel stream task is created, the runtime inspects `Thread.currentThread()`. If the current thread is a worker belonging to a `ForkJoinPool`, the stream attaches its tasks to that specific pool instead of `ForkJoinPool.commonPool()`.

However, **the Java SE Specification makes no formal guarantee** that parallel streams must honor the enclosing thread pool. It remains an implementation-specific artifact of HotSpot. In future Java specifications or non-standard JVMs, parallel streams could theoretically continue dispatching to `commonPool()`.

---

### 3. Why does `Stream.iterate(0, i -> i + 1).parallel().limit(100)` suffer from disastrous CPU saturation and near-zero parallel speedup?
**Answer:**
`Stream.iterate()` generates elements via a sequential recurrence relation where element $n$ strictly depends on element $n-1$. Because of this sequential dependency:
1. `Spliterator.trySplit()` cannot divide the sequence ahead of time into independent sub-ranges.
2. A single thread is forced to generate elements sequentially while other worker threads in the pool sit in busy-spin loops or lock synchronizations waiting for tasks.
3. Furthermore, stateful operations like `.limit(100)` require tracking global encounter order across threads, triggering heavy synchronization barriers.

To generate numeric ranges efficiently in parallel, always use indexed generators like `IntStream.rangeClosed(1, 100).parallel()`, whose `Spliterator` supports $O(1)$ midpoint splitting.

---

### 4. What are the performance and semantic consequences of using `forEachOrdered()` versus `forEach()` on a parallel stream?
**Answer:**
- **`forEach()`:** Has no ordering constraints. Each worker thread invokes the `Consumer` on its local chunk as soon as processing finishes. Output is non-deterministic and highly concurrent, fully utilizing multi-core throughput.
- **`forEachOrdered()`:** Enforces the upstream stream encounter order. Even though earlier operations (such as `filter()` or `map()`) execute concurrently across cores, the final consumer execution must be buffered and serialized. The runtime holds finished elements in internal buffers until all preceding elements in the stream have been emitted, introducing synchronization locks, increased memory consumption, and potential thread stalling.

### Key Takeaways
- **Engine:** Parallel streams utilize `ForkJoinPool.commonPool()` and `Spliterator.trySplit()`.
- **Calling Thread Participates:** Default pool size is `processors - 1` because the calling thread acts as an active worker.
- **$N \times Q > 10,000$ Rule:** Only parallelize when dataset size multiplied by computation per element is sufficiently high.
- **Avoid Blocking I/O:** Never perform database or network calls inside parallel streams; it exhausts the JVM-wide common pool.

---

### Red Flags & Anti-Patterns to Avoid
- ❌ **Adding `.parallel()` indiscriminately to all streams:** Small collections ($N < 1{,}000$) run slower due to task splitting and merge coordination overhead.
- ❌ **Performing blocking HTTP/SQL calls in `parallelStream()`:** Causes JVM-wide thread starvation in `ForkJoinPool.commonPool()`.
- ❌ **Mutating shared state without synchronization:** Operations like `list.add(item)` inside parallel streams trigger race conditions, corrupted internal arrays, and lost updates.
- ❌ **Relying on `ThreadLocal` inside parallel streams:** Worker threads are reused from the common pool, leading to memory leaks and cross-request state contamination.
