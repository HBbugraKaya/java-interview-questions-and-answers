# What is Circuit Breaker Pattern

---

## 🟢 Junior Level

The **Circuit Breaker Pattern** is an architectural stability pattern in distributed systems designed to prevent cascading failures. It wraps network calls to remote microservices, automatically tripping open when the downstream dependency fails or degrades, failing fast immediately without wasting critical system resources on hopeless timeouts.

```
Without Circuit Breaker (Cascading Failure):
[Clients] ──► [Order Service] ──(5s HTTP Timeout)──► [Payment Service (FROZEN)]
                    │ (All 200 Tomcat worker threads blocked waiting)
                    ▼
              [ENTIRE SYSTEM CRASHES 💥]

With Circuit Breaker (Fail-Fast & Isolation):
[Clients] ──► [Order Service] ──► [Circuit Breaker: OPEN ⚡]
                                       │ (Instant Fallback response in 1ms)
                                       ▼
                                 [Graceful Degradation ✅]
```

### The Real-World Analogy
In residential electrical wiring, a physical **fuse box / circuit breaker** trips (breaks the circuit) when an electrical appliance short-circuits or draws dangerous levels of current. This prevents electrical fires. In microservices, when a downstream service hangs or errors out, the software Circuit Breaker trips to `OPEN`, cutting off outbound traffic so the caller's thread pool does not catch fire.

### The 3 Core States

| State | Status | Behavior |
| :--- | :--- | :--- |
| **`CLOSED`** | 🟢 Normal Operation | All requests pass through to the remote service. Call metrics (successes, errors, latencies) are tracked in a sliding window. |
| **`OPEN`** | 🔴 Outage Detected | The downstream dependency is down. Outbound network requests are **blocked completely**. Calls immediately fail fast or execute a fallback method. |
| **`HALF-OPEN`** | 🟡 Recovery Trial | After a cool-down period, a limited number of probe requests are allowed through. If they succeed, the breaker resets to `CLOSED`. If any fail, it trips back to `OPEN`. |

## 🟡 Middle Level

### 1. Spring Boot 3 Implementation with Resilience4j

**Resilience4j** is the modern, lightweight fault tolerance library for Java (fully superseding the deprecated Netflix Hystrix):

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class PaymentClient {

    private final RestClient restClient;

    @CircuitBreaker(name = "paymentService", fallbackMethod = "processPaymentFallback")
    public PaymentResponse processPayment(PaymentRequest request) {
        return restClient.post()
            .uri("https://payment-service/api/v1/charge")
            .body(request)
            .retrieve()
            .body(PaymentResponse.class);
    }

    // Fallback Method: MUST have the exact same parameters + Throwable appended at the end
    public PaymentResponse processPaymentFallback(PaymentRequest request, Throwable ex) {
        log.warn("Payment service unavailable ({}). Initiating deferred processing.", ex.getMessage());
        return PaymentResponse.builder()
            .status(PaymentStatus.DEFERRED_PENDING)
            .orderId(request.orderId())
            .build();
    }
}
```

### 2. Enterprise Configuration (`application.yml`)

```yaml
resilience4j:
  circuitbreaker:
    instances:
      paymentService:
        sliding-window-type: COUNT_BASED             # Evaluate metrics over request count
        sliding-window-size: 20                      # Number of calls in the sliding window
        minimum-number-of-calls: 10                  # Minimum calls before error rate is computed
        failure-rate-threshold: 50                   # Trip to OPEN if >= 50% calls return errors
        slow-call-rate-threshold: 70                 # Trip to OPEN if >= 70% calls are slow
        slow-call-duration-threshold: 2000ms         # Call considered slow if execution > 2s
        wait-duration-in-open-state: 15s             # Cooldown time in OPEN state before HALF_OPEN
        permitted-number-of-calls-in-half-open-state: 5 # Trial probe requests allowed in HALF_OPEN
        automatic-transition-from-open-to-half-open-enabled: true
```

### 3. Comparing Stability Patterns

| Pattern | Primary Purpose | Behavior on Failure |
| :--- | :--- | :--- |
| **Circuit Breaker** | Prevents cascading failures; protects thread pools | Trips open to immediately reject outbound traffic (**Fail-Fast**) |
| **Retry** | Overcomes transient, momentary network blips | Resends the identical request after a backoff delay |
| **Rate Limiter** | Prevents resource overload and enforces API quotas | Blocks or queues incoming requests exceeding TPS/RPS limit |
| **Bulkhead** | Isolates thread pools or semaphores per dependency | Bounds maximum concurrent executions dedicated to one service |

> [!WARNING]
> **The Retry Storm Hazard:** Using the **Retry pattern without a Circuit Breaker** against a struggling downstream service triggers a catastrophic **Retry Storm**. Thousands of clients repeatedly retrying failed requests will generate an accidental distributed denial-of-service (DDoS) attack that destroys the recovering service.

## 🔴 Senior Level

### 1. Slow Calls vs Fast HTTP 500 Errors (The Thread Starvation Crisis)

In production microservices, **slow calls are exponentially more lethal than immediate HTTP 500 errors**:

- **Fast HTTP 500 Error:** When the downstream service fails immediately and responds with HTTP 500, the caller's HTTP client unblocks and frees the Tomcat worker thread within $5\text{ ms}$.
- **Slow Call (15-second hang):** When the downstream service hangs due to database row locking or connection starvation, each caller thread remains blocked for the full 15 seconds.
- **The Mathematical Reality:** With a standard Spring Boot Tomcat thread pool of 200 threads (`server.tomcat.threads.max=200`) and an incoming load of 50 requests/sec, **all 200 server threads are completely saturated and exhausted in exactly 4 seconds** ($200 / 50 = 4\text{s}$).

Once the thread pool is exhausted, the service stops responding to Kubernetes Liveness and Readiness probes. Kubernetes marks the pod unready, kills it, and schedules a restart, creating a cascading domino collapse across the entire cluster. Therefore, a production Circuit Breaker **must** configure `slow-call-rate-threshold` alongside `failure-rate-threshold`.

### 2. In-Memory (JVM-Local) vs Distributed (Redis) Circuit Breakers

Why does Resilience4j maintain its sliding window metrics strictly in local JVM memory rather than sharing state across pods in a centralized Redis cluster?

```
In-Memory (Recommended Standard):
[Pod 1 (Local CB)] ──► [Remote API]
[Pod 2 (Local CB)] ──► [Remote API]
[Pod 3 (Local CB)] ──► [Remote API]
(Zero network hops, sub-microsecond latency, zero external failure dependencies)

Distributed via Redis (Anti-Pattern):
[Pod 1] ───(Check Redis state on every HTTP call: +2ms)───► [Redis Cluster]
(If Redis experiences network latency or fails, the Circuit Breaker crashes the system!)
```

1. **Network Latency Overhead:** Querying Redis before every outbound microservice call adds $1\text{–}3\text{ ms}$ of network round-trip overhead to every single request.
2. **Single Point of Failure:** If the shared Redis cluster degrades or experiences network partitions, every microservice's resilience layer freezes simultaneously.
3. **Horizontal Pod Autoscaling (HPA) Consideration:** When a new pod spawns during traffic spikes, it starts cold in `CLOSED` state. Setting an appropriate `minimum-number-of-calls` (e.g., 20–50) prevents newly launched pods from tripping falsely on sporadic initial cold-start spikes.

### 3. Spring AOP Aspect Ordering Pitfall

When combining `@CircuitBreaker`, `@Retry`, and `@Bulkhead` on the same Spring bean method, the execution order of Spring AOP aspects is critical:

```
Correct Aspect Execution Order (Outside In):
[Incoming Request]
       │
       ▼
1. @Bulkhead        ──► Bounds concurrent threads (prevents thread pool depletion)
       │
       ▼
2. @CircuitBreaker  ──► Evaluates circuit state (CLOSED vs OPEN)
       │
       ▼
3. @Retry           ──► Executes retries ONLY if Circuit Breaker is CLOSED
       │
       ▼
4. [Target Method]  ──► Remote HTTP/gRPC invocation
```

If `@CircuitBreaker` is erroneously placed **inside** `@Retry`, each internal retry attempt will be recorded by the Circuit Breaker as a separate, distinct failure. A single user call that retries 3 times registers as 3 separate failures in the sliding window, artificially tripling the error rate and causing the Circuit Breaker to trip prematurely.

In Resilience4j Spring Boot Starter, the default aspect order is properly configured:
$$\text{Bulkhead} \to \text{TimeLimiter} \to \text{RateLimiter} \to \text{CircuitBreaker} \to \text{Retry}$$

## 4 Tricky Questions

### 1. Why are slow responses ("Slow Calls") far more dangerous to microservices than immediate HTTP 500 errors?
**Answer:**
Immediate HTTP 500 errors allow the calling thread to terminate within a few milliseconds, instantly returning the thread to the servlet container's thread pool. Conversely, slow calls (e.g., 10–30 second timeouts caused by database locks or resource starvation) hold worker threads hostage. In a thread-per-request model (such as Tomcat's default 200 worker threads), a sustained incoming rate of only 20–50 requests per second will completely deplete the thread pool within 4 to 10 seconds. This locks out all other endpoints, causes Kubernetes readiness probes to time out, and induces a cascading failure across unrelated microservices.

### 2. What happens if a Fallback method executes a remote network request and fails?
**Answer:**
Executing remote network calls inside a fallback method is a severe anti-pattern that violates the core principle of fault tolerance. 
If the fallback method itself performs an unhedged remote HTTP/database call:
1. It is susceptible to the same cascading failure that triggered the original circuit break.
2. If the fallback throws an unhandled exception, it bubbles up to the caller, completely negating the benefit of the Circuit Breaker.
A fallback method must be strictly non-blocking and in-memory: returning hardcoded static defaults, reading from a local in-memory cache (e.g., Caffeine), or asynchronously appending a message to a local disk/memory buffer for deferred processing.

### 3. How do you properly test Circuit Breakers in automated integration tests?
**Answer:**
Proper Circuit Breaker testing verifies both state transitions and fallback invocations:
1. **WireMock / MockServer:** Configure WireMock to simulate HTTP 500 errors or inject latency using `withFixedDelay(3000)`.
2. **Programmatic State Transitions via `CircuitBreakerRegistry`:** In Spring Boot tests, inject `CircuitBreakerRegistry` to force specific states without executing dozens of HTTP requests:
   ```java
   circuitBreakerRegistry.circuitBreaker("paymentService").transitionToOpenState();
   ```
3. **Verify Zero Network Calls in OPEN State:** Assert that while in `OPEN` state, the fallback is executed instantly and WireMock records exactly `0` received requests (`verify(0, postRequestedFor(...))`).

### 4. Why doesn't Circuit Breaker automatically protect non-blocking reactive stacks (WebFlux/Netty) from OutOfMemoryError, and how do you mitigate it?
**Answer:**
In non-blocking reactive frameworks (Spring WebFlux on Netty), worker threads (Event Loops) are not blocked while waiting for I/O; a few threads handle thousands of concurrent requests. Therefore, thread starvation does not occur. 
However, if a downstream service hangs, incoming requests continue to create reactive publisher chains (`Mono`/`Flux`) and allocate memory buffers for request payloads. Under high traffic, millions of pending reactive subscriptions accumulate in JVM Heap memory, resulting in an `OutOfMemoryError`. 
To mitigate this, reactive Circuit Breakers must use the reactive operator (`transformDeferred(CircuitBreakerOperator.of(...))`) coupled with an explicit `.timeout(Duration)` operator to cancel downstream subscriptions promptly and relieve heap memory backpressure.

## 🎯 Interview Cheat Sheet

### Must Know
- **Definition:** An architectural pattern that prevents cascading failures by isolating degraded downstream services and failing fast.
- **3 States:** `CLOSED` (normal traffic), `OPEN` (traffic blocked, fails fast to fallback), `HALF-OPEN` (probe requests to test recovery).
- **Core Triggers:** Both `failureRateThreshold` (percentage of errors) and `slowCallRateThreshold` (percentage of calls exceeding latency limit).
- **Modern Java Standard:** **Resilience4j** is the standard; Netflix Hystrix is deprecated.
- **Architecture Principle:** Runs **in-memory within each JVM pod**, never as a shared distributed cache over Redis.

### Architectural Resilience Pipeline
$$\text{Bulkhead (Resource Isolation)} \to \text{Circuit Breaker (Fail-Fast)} \to \text{Retry (Transient Glitches)} \to \text{Fallback (Graceful Degradation)}$$

### Common Follow-up Questions
- *"What is the difference between Circuit Breaker and Retry?"* $\to$ Retry repeats a failed request; Circuit Breaker prevents requests from being sent at all when a dependency is broken.
- *"Why are slow calls worse than fast errors?"* $\to$ Slow calls tie up servlet container threads, causing thread pool starvation and pod crashes.
- *"Can a fallback method call another remote service?"* $\to$ No; fallbacks must be fast, local in-memory operations to guarantee reliability.

### Red Flags (DO NOT Say)
- ❌ *"Circuit Breaker retries the failed requests automatically."* (Retry handles retries; Circuit Breaker blocks requests to allow the downstream system to recover).
- ❌ *"We share Circuit Breaker state across all microservice instances via Redis."* (Introduces a single point of failure and network latency on every call).
- ❌ *"Netflix Hystrix is what we use in modern Spring Boot 3 projects."* (Hystrix has been officially deprecated since 2018; use Resilience4j).
