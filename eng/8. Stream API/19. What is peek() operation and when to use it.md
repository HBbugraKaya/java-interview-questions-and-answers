# What is peek() operation and when to use it

---

## 🟢 Junior Level

### 30-Second Summary
**`peek(Consumer<T>)`** is an intermediate operation in the Java Stream API that applies an action to each element as it passes through the pipeline and **forwards the element unchanged downstream**.

The official Java API documentation explicitly defines its singular legitimate purpose:
> *"This method exists mainly to support debugging, where you want to see the elements as they flow past a certain point in a pipeline."*

Using `peek()` to execute business logic (such as mutating object properties, persisting to a database, or publishing metrics) is **strictly forbidden**. Due to the lazy nature of streams, short-circuiting operations, and compiler/runtime optimizations, `peek()` is never guaranteed to execute for all elements—or even execute at all.

---

### Basic Debugging Example in Java 21

```java
import java.util.List;

public class PeekBasicsDemo {

    public static void main(String[] args) {
        List<String> words = List.of("cat", "elephant", "hippopotamus", "tiger");

        List<String> result = words.stream()
            .filter(w -> w.length() > 3)
            .peek(w -> System.out.println("[DEBUG After filter]: " + w))
            .map(String::toUpperCase)
            .peek(w -> System.out.println("[DEBUG After map]: " + w))
            .toList();

        System.out.println("Final Result: " + result);
    }
}
```

**Console Output:**
```text
[DEBUG After filter]: elephant
[DEBUG After map]: ELEPHANT
[DEBUG After filter]: hippopotamus
[DEBUG After map]: HIPPOPOTAMUS
[DEBUG After filter]: tiger
[DEBUG After map]: TIGER
Final Result: [ELEPHANT, HIPPOPOTAMUS, TIGER]
```

## 🟡 Middle Level

### Internal Architecture: `Sink.ChainedReference`

In the OpenJDK reference implementation (`ReferencePipeline.java`), `peek()` wraps the downstream data sink into a chained consumer stage:

```java
// OpenJDK ReferencePipeline.java implementation fragment:
@Override
public Sink<P_OUT> opWrapSink(int flags, Sink<P_OUT> sink) {
    return new Sink.ChainedReference<P_OUT, P_OUT>(sink) {
        @Override
        public void accept(P_OUT u) {
            action.accept(u);       // 1. Execute the diagnostic Consumer action
            downstream.accept(u);   // 2. Pass the unmodified element downstream
        }
    };
}
```

---

### Comparison: `peek()` vs. `map()` vs. `forEach()`

| Dimension | `peek()` | `map()` | `forEach()` |
| :--- | :--- | :--- | :--- |
| **Operation Category** | Intermediate | Intermediate | **Terminal** |
| **Return Type** | `Stream<T>` (Same type) | `Stream<R>` (Transformed type) | `void` (Closes pipeline) |
| **Primary Intent** | Diagnostic tracing & debugging | Pure functional transformation | Executing final side effects |
| **Execution Guarantee** | **None** (Subject to optimizer elision) | **None** (Dependent on terminal call) | **Guaranteed** upon invocation |

### The Object Mutation Anti-Pattern

```java
// ❌ CRITICAL ANTI-PATTERN: Mutating entity state inside peek()
users.stream()
    .peek(user -> user.setStatus("PROCESSED")) // Side effect!
    .toList();

// ✅ IDIOMATIC FUNCTIONAL APPROACH: Pure immutable transformation via map()
List<User> processedUsers = users.stream()
    .map(user -> user.withStatus("PROCESSED"))
    .toList();
```

Mutating state inside `peek()` violates functional purity, introduces hidden side effects, and causes non-deterministic concurrency bugs when the stream is switched to `parallelStream()`.

## 🔴 Senior Level

### The Java 9+ Optimization Trap: Stream Pruning (JDK-8075056)

Starting with Java 9, the Stream API runtime implements **Stream Pruning**. If a terminal operation like `.count()` is invoked on a stream source that reports the `Spliterator.SIZED` characteristic, and there are no operations that alter the element count (such as `filter()` or `flatMap()`), the runtime reads the collection's size directly and **completely eliminates intermediate pipeline stages without traversing elements**:

```java
import java.util.List;

public class PeekPruningDemo {

    public static void main(String[] args) {
        List<String> items = List.of("A", "B", "C");

        // ❌ PRODUCTION HAZARD: Relying on peek() for business-critical execution
        long total = items.stream()
            .peek(item -> System.out.println("Processing audit log: " + item))
            .count();

        System.out.println("Total items: " + total);
        // In Java 9+, the text "Processing audit log: ..." IS NEVER PRINTED!
        // The JVM retrieves items.size() directly from the SIZED spliterator,
        // and peek() is entirely pruned from execution.
    }
}
```

---

### Short-Circuiting Truncation

Short-circuiting operations (`findFirst()`, `findAny()`, `anyMatch()`, `limit()`) abort pipeline execution as soon as their termination condition is met:

```java
List<String> items = List.of("A", "B", "C", "D", "E");

// peek() executes ONLY for "A" and "B"!
items.stream()
    .peek(x -> auditService.save(x)) // Elements "C", "D", "E" are never processed!
    .filter("B"::equals)
    .findFirst();
```

---

### Highload Considerations & Static Analysis

1. **Virtual Call Overhead:** Every `peek()` introduces a virtual method dispatch (`Consumer.accept()`) per element. In high-throughput pipelines, this prevents the HotSpot C2 compiler from performing aggressive method inlining and loop vectorization (SIMD).
2. **Static Code Analysis Rules:** Enterprise linters strictly forbid `peek()` in production codebases (e.g., **SonarQube Rule `S3864: "peek" should be used only for debugging`**).
3. **IDE Stream Debugger:** Rather than polluting production code with `peek()`, use the **IntelliJ IDEA Java Stream Debugger**, which visually renders intermediate inputs and outputs across all pipeline stages without requiring source changes.

## 4 Tricky Questions

### 1. Why does `stream.peek(System.out::println).count()` print nothing to standard output in Java 9+?
**Answer:**
Under JDK-8075056 (introduced in Java 9), the implementation of `.count()` optimizes execution when the stream source possesses the `Spliterator.SIZED` characteristic. If no intermediate stages alter the stream's cardinality (such as `filter()` or `flatMap()`), `.count()` reads the size directly via `spliterator.getExactSizeIfKnown()`.

Because the stream engine does not need to traverse individual elements to determine the total count, it prunes the pipeline and discards all intermediate stateless stages. Consequently, the `peek()` consumer is never invoked.

---

### 2. What is the difference between `peek()` and `forEach()` in terms of lifecycle and return types?
**Answer:**
- **`peek()`** is an **intermediate operation** returning `Stream<T>`. It does not initiate stream evaluation; it merely registers an inspection callback within the pipeline sink chain, waiting for a terminal operation to trigger execution.
- **`forEach()`** is an **eager terminal operation** returning `void`. Its invocation closes the stream pipeline, pulls elements from the source through all intermediate stages, and executes the provided action as the final consumer of the pipeline.

---

### 3. Why do static code analyzers (e.g., SonarQube rule S3864) flag the use of `peek()` in production code?
**Answer:**
Static analysis rules flag `peek()` because developers frequently misuse it as a procedural loop or to apply stateful mutations (e.g., setting entity flags or writing audit entries).

Because stream execution is lazy, prone to short-circuiting truncation, and subject to JVM compiler pruning, code inside `peek()` has no guarantee of execution. Linters ban `peek()` in production code to prevent silent logic omissions and enforce functional purity.

---

### 4. How does `peek()` behave in a parallel stream (`parallelStream()`)?
**Answer:**
In a parallel stream, `peek()` executes concurrently across worker threads in `ForkJoinPool`.
- The invocations of `Consumer.accept()` happen in non-deterministic order across multiple CPU cores.
- If the lambda inside `peek()` mutates shared variables or performs unsynchronized logging, it introduces severe multi-threading bugs, data races, and thread lock contention on shared output streams (such as standard output or logger appenders).

## 🎯 Interview Cheat Sheet

### `peek()` Usage Risks Matrix
| Pipeline Scenario | Execution Behavior | Technical Reason |
| :--- | :--- | :--- |
| `stream.peek(...).count()` (Java 9+) | 🔴 **Never executes** | Stream Pruning optimization on `SIZED` sources |
| `stream.peek(...).findFirst()` | 🟡 **Executes partially** | Short-circuiting aborts traversal on first match |
| `stream.peek(...);` (No terminal op) | 🔴 **Never executes** | Lazy evaluation (pipeline is not triggered) |
| `stream.peek(u -> u.setX()).toList()` | 🔴 **Anti-Pattern** | Violates functional purity; breaks concurrency |
| `stream.filter(...).peek(log).toList()` | 🟢 **Valid for debug** | Temporary development inspection |

---

### Key Takeaways
- **Debugging Only:** `peek()` is strictly a diagnostic tool for temporary debugging and pipeline tracing.
- **No Execution Guarantees:** JVM optimizers (Java 9+ stream pruning) and short-circuiting operations can skip `peek()` entirely.
- **Never for Business Logic:** Never perform data mutation, audits, or database writes inside `peek()`.
- **Production Cleanliness:** Remove all `peek()` calls prior to merging code to pass static analysis rules (SonarQube S3864).

---

### Red Flags & Anti-Patterns to Avoid
- ❌ **Using `peek()` to mutate domain objects:** `peek(user -> user.setActive(true))` is an anti-pattern; use `map()` to create transformed instances.
- ❌ **Relying on `peek()` before `.count()`:** In Java 9+, `peek()` is completely omitted on `SIZED` collections.
- ❌ **Leaving `peek(System.out::println)` in production code:** Degrades performance and violates enterprise logging guidelines.
- ❌ **Expecting encounter order in parallel `peek()`:** Worker threads process items concurrently in non-deterministic order.
