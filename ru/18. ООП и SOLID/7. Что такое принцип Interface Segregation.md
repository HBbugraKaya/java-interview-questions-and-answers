# Что такое принцип Interface Segregation

---

## 🟢 Junior Level

**Принцип разделения интерфейсов (Interface Segregation Principle, ISP)** — это четвертый принцип SOLID, сформулированный Робертом Мартином:
> **"Клиенты не должны зависеть от методов, которые они не используют."**

### Что это означает простыми словами
- **Клиент** — это вызывающий код или класс-реализация, использующий интерфейс.
- Если вы создаете гигантский («жирный») интерфейс, содержащий десятки разнородных методов, все реализующие его классы вынуждены писать заглушки или выбрасывать ошибки на методы, которые им совершенно не нужны.
- Принцип ISP требует дробить монолитные интерфейсы на маленькие, узкоспециализированные контракты, чтобы классы реализовывали **только те методы, которые им действительно требуются**.

### Житейская аналогия
Пульт управления бытовой техникой:
- Представьте универсальный пульт, на котором одновременно расположены 200 кнопок: переключение каналов телевизора, выставление температуры кондиционера, запуск стиральной машины и взлет квадрокоптера.
- Чтобы просто включить лампочку, вам приходится держать в руках громоздкий пульт с сотней лишних кнопок.
- Правильный подход: иметь отдельный выключатель света (`Switchable`), отдельный пульт для ТВ (`ChannelSwitchable`) и термостат (`TemperatureRegulated`).

### Пример нарушения ISP («Жирный» интерфейс)

```java
// Плохо: интерфейс заставляет уметь всё подряд
public interface SmartDevice {
    void printDocument(byte[] doc);
    void scanDocument();
    void sendFax(String number);
    void brewCoffee();
}

// Обычный офисный принтер не умеет сканировать, отправлять факсы и варить кофе!
public class BasicOfficePrinter implements SmartDevice {
    @Override
    public void printDocument(byte[] doc) {
        System.out.println("Печатаем документ...");
    }

    @Override
    public void scanDocument() {
        // Нарушение ISP: метод-заглушка!
        throw new UnsupportedOperationException("Сканер отсутствует!");
    }

    @Override
    public void sendFax(String number) {
        throw new UnsupportedOperationException("Факс не поддерживается!");
    }

    @Override
    public void brewCoffee() {
        throw new UnsupportedOperationException("Принтер не варит кофе!");
    }
}
```

### Исправление по ISP: Интерфейсы ролей (Role Interfaces)

Разбиваем монолитный интерфейс на сфокусированные роли:

```java
// Узкие специализированные интерфейсы
public interface Printer {
    void printDocument(byte[] doc);
}

public interface Scanner {
    void scanDocument();
}

public interface Fax {
    void sendFax(String number);
}

// Простой принтер реализует только то, что умеет:
public class BasicOfficePrinter implements Printer {
    @Override
    public void printDocument(byte[] doc) {
        System.out.println("Печатаем документ...");
    }
}

// Многофункциональное устройство (МФУ) комбинирует нужные интерфейсы:
public class MultifunctionCopier implements Printer, Scanner, Fax {
    @Override
    public void printDocument(byte[] doc) { /* печать */ }
    @Override
    public void scanDocument() { /* сканирование */ }
    @Override
    public void sendFax(String number) { /* факс */ }
}
```

Клиентский код, которому требуется только печать, принимает параметр типа `Printer` и даже не подозревает о существовании факсов или сканеров.

## 🟡 Middle Level

### Role Interfaces против Header Interfaces

Роберт Мартин и Мартин Фаулер выделяют две диаметрально противоположные концепции интерфейсов:

| Характеристика | Header Interface (Антипаттерн) | Role Interface (Best Practice) |
|---|---|---|
| **Идея** | Интерфейс механически дублирует все публичные методы одного конкретного сервиса (`UserService` $\rightarrow$ `IUserService`). | Интерфейс моделирует конкретную **роль** в сценарии взаимодействия (`UserLookup`, `PasswordResetter`, `Auditable`). |
| **Кому принадлежит** | Принадлежит пакету реализации (поставщику). | Принадлежит **клиенту** (потребителю контракта). |
| **Количество методов** | 10–50 методов (разрастается с развитием сервиса). | 1–3 метода (сфокусирован на единой задаче). |
| **Эволюция** | Любое изменение метода ломает всех клиентов и моки в тестах. | Изменения изолированы внутри узких контекстов. |

---

### ISP в стандартных библиотеках Java и Spring Data

1. **Java Core API:**
   - Интерфейсы стандартной библиотеки — образцы ISP: `Runnable` (1 метод: `run()`), `Callable` (1 метод: `call()`), `Comparable` (1 метод: `compareTo()`), `AutoCloseable` (1 метод: `close()`), `Readable`, `Appendable`.
   - Потоки ввода-вывода `InputStream` разделены по возможностям: `DataInput`, `ObjectInput`.

2. **Эволюция Spring Data Repositories:**
   - В ранних версиях разработчики часто объявляли огромные интерфейсы.
   - Spring Data декомпозировал работу с данными на узкие слои:
     - `Repository<T, ID>` — маркерный корень.
     - `CrudRepository<T, ID>` — только базовый CRUD.
     - `PagingAndSortingRepository<T, ID>` — только пагинация и сортировка.
     - `QueryByExampleExecutor<T>` — динамический поиск по образцу.
   - Клиентский сервис инжектирует ровно ту грань репозитория, которая ему необходима для работы.

---

### Симптомы нарушения ISP в проекте

1. **`UnsupportedOperationException` / пустые методы (`// do nothing`):** вернейший признак того, что интерфейс заставил класс взять чужую ответственность.
2. **Раздутые моки в Unit-тестах:** чтобы протестировать класс, вызывающий 1 метод, разработчик вынужден писать 15 строк моков `when(service.unrelatedMethod()).thenReturn(...)`.
3. **Частые merge-конфликты в интерфейсах:** несколько независимых фиче-команд одновременно редактируют один и тот же интерфейс общего назначения.

## 🔴 Senior Level

### Исторический контекст Xerox и физический дизайн архитектуры

Принцип ISP родился во время работы Роберта Мартина консультантом в компании **Xerox** в начале 1990-х:
- Новое программное обеспечение для многофункционального копировального аппарата состояло из сотен классов, завязанных на единый гигантский класс/интерфейс `Job`.
- Любое изменение в коде степлирования или подсчета страниц приводило к изменению `Job.h` в C++.
- Это вызывало полную перекомпиляцию сотен исходных файлов, линковку и повторное многочасовое тестирование всей системы, парализуя релизный цикл.
- Мартин применил разделение интерфейсов по клиентам: клиент печати зависит только от `PrintJob`, клиент сетевой передачи — от `NetworkJob`, а класс физического принтера реализует оба эти узких интерфейса.

```
[PrintClient] ──> [PrintJob Interface]   \
                                          ===> [Job Implementation Class]
[BillingClient] ─> [BillingJob Interface] /
```

### Влияние на бинарную совместимость JVM и загрузку классов

В виртуальной машине Java монолитные интерфейсы несут скрытые системные издержки:

1. **Binary Compatibility и Constant Pool:**
   - Каждый метод, объявленный в интерфейсе, добавляет записи `CONSTANT_Methodref_info` / `CONSTANT_NameAndType_info` в Constant Pool `.class`-файлов всех его потребителей.
   - Если две библиотеки в classpath используют разные версии широкого интерфейса, компиляция может пройти успешно, но в рантайме вызов отсутствующего метода вызовет фатальный `java.lang.NoSuchMethodError`. Дробление интерфейсов кардинально снижает вероятность конфликта транзитивных зависимостей (*Jar Hell / Dependency Hell*).

2. **Полиморфный диспатчинг (`itable`):**
   - Вызовы методов интерфейсов компилируются в байткод `invokeinterface`.
   - Для каждого класса JVM строит таблицу интерфейсных методов (**itable**).
   - Если класс реализует несколько гигантских интерфейсов, `itable` разрастается, увеличивая размер структур в `Metaspace` и снижая локальность данных в кэше процессора (L1/L2 data cache misses) при обходе таблицы интерфейсов.

### Решение конфликтов ISP со сторонними SDK: Паттерн Adapter

Если вы используете стороннюю Enterprise-библиотеку (AWS SDK, Kafka Client, Spring Cloud) с монолитным интерфейсом, который невозможно отредактировать:

```java
// Сторонний "жирный" интерфейс из внешней зависимости
public interface HeavyCloudClient {
    void putObject(String bucket, String key, byte[] bytes);
    byte[] getObject(String bucket, String key);
    void deleteBucket(String bucket);
    void setBucketLifecyclePolicy(String bucket, Policy policy);
    void rotateAccessKeys();
}

// Наш доменный узкий контракт (Client-driven ISP)
public interface DocumentStorage {
    void store(String documentId, byte[] content);
}

// Адаптер изолирует ядро домена от раздутого SDK
@Component
public class S3DocumentStorageAdapter implements DocumentStorage {
    private final HeavyCloudClient s3Client;
    private final String bucketName;

    public S3DocumentStorageAdapter(HeavyCloudClient s3Client, @Value("${app.s3.bucket}") String bucketName) {
        this.s3Client = s3Client;
        this.bucketName = bucketName;
    }

    @Override
    public void store(String documentId, byte[] content) {
        s3Client.putObject(bucketName, documentId, content);
    }
}
```

## 4 Tricky Questions

### 1. Решают ли Default Methods (Java 8+) проблему нарушения ISP?
**Ответ:**
Нет, default-методы решают проблему обратной совместимости при эволюции интерфейсов библиотек, но не устраняют нарушение ISP. Добавление default-метода избавляет классы-реализации от необходимости писать пустые тела методов, однако интерфейс для вызывающего кода (клиента) по-прежнему остается раздутым («жирным»). Клиент видит в автодополнении IDE и публичном API десятки методов, которые не относятся к его задаче, что провоцирует ошибочные вызовы и увеличивает связность системы.

### 2. Может ли разделение интерфейсов привести к антипаттерну Interface Explosion (Взрыв интерфейсов)?
**Ответ:**
Да. Если следовать ISP догматично и создавать интерфейс под каждый отдельный метод (SAM-интерфейсы для всего подряд), навигация по кодовой базе усложняется, число файлов удваивается, а связность абстракций падает.
Критерий разумного баланса: интерфейс должен дробиться только тогда, когда **существуют разные клиенты**, использующие непересекающиеся группы методов, либо разные классы-реализации, которые не могут предоставить валидную семантику для части методов. Если методы семантически неразрывны (например, `Iterator.hasNext()` и `Iterator.next()`), разделять их запрещено.

### 3. Как ISP соотносится с микросервисной архитектурой и REST / gRPC API?
**Ответ:**
Принцип ISP прямо транслируется на распределенные системы:
- Монолитный REST API с сотней эндпоинтов на все случаи жизни нарушает ISP на уровне сети.
- Архитектурный паттерн **BFF (Backend for Frontend)** — это реализация ISP в микросервисах: мобильное приложение получает свой узкий легковесный API (`/mobile/orders`), а Web-портал оператора — расширенный (`/backoffice/orders`).
- В gRPC и Protobuf разделение сервисов (`service OrderReaderService`, `service OrderWriterService`) позволяет клиентам подписываться только на нужные RPC-контракты без загрузки тяжелых схем данных.

### 4. В чем разница между ISP и SRP (Single Responsibility Principle)?
**Ответ:**
- **SRP** ориентирован на **реализацию и причины для изменения:** «У класса должна быть одна причина для изменения (один актор/бизнес-роль)». SRP отвечает на вопрос: *«Что делает этот класс внутри?»*
- **ISP** ориентирован на **потребителя (клиента):** «Клиент не должен зависеть от методов, которые ему не нужны». Класс может иметь одну ответственность (например, `DatabaseManager`), но если он выставляет наружу единый широкий интерфейс для администратора, аналитика и обычного пользователя, он нарушает ISP.

## 🎯 Шпаргалка для интервью

**Главные тезисы (30 секунд на ответ):**
- **Суть:** Клиенты не должны зависеть от методов, которые они не используют. Множество узких интерфейсов лучше одного «жирного».
- **Интерфейс принадлежит клиенту:** Контракты определяются потребностями вызывающего кода, а не удобством автора реализации.
- **Главный симптом нарушения:** `UnsupportedOperationException` или пустые методы в классах-наследниках; избыточные моки в юнит-тестах.
- **Паттерн решения:** Adapter для изоляции сторонних раздутых API; выделение Role Interfaces вместо механических Header Interfaces.

**Чего избегать (Red Flags):**
- ❌ Создавать интерфейс-копию `IClass` для каждого класса с 30 методами и называть это абстракцией.
- ❌ Думать, что default methods в Java 8+ исправляют нарушение ISP.
- ❌ Разделять семантически неразделимые методы (например, делить `hasNext()` и `next()`).
