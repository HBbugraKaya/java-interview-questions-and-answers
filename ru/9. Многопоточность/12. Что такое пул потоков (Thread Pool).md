# Что такое пул потоков (Thread Pool)

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**Пул потоков (Thread Pool)** — это архитектурный шаблон и компонент среды исполнения Java, представляющий собой управляемый набор предварительно созданных рабочих потоков, которые многократно переиспользуются для асинхронного выполнения поступающих задач.

В Java пул потоков представлен интерфейсом `ExecutorService` и его базовой реализацией **`ThreadPoolExecutor`** из пакета `java.util.concurrent`.

Создание отдельного платформенного потока операционной системы через `new Thread().start()` на каждую входящую задачу в высоконагруженных системах недопустимо:
1. **Выделение памяти:** каждый платформенный поток резервирует отдельный стек вызовов (~1 МБ по умолчанию по флагу `-Xss`). Создание 10 000 потоков приведёт к исчерпанию оперативной памяти и падению JVM с ошибкой `OutOfMemoryError: unable to create native thread`.
2. **Накладные расходы ОС:** инициализация системного дескриптора ядра и переключение контекста процессора (Context Switching) между тысячами потоков отнимают больше ресурсов CPU, чем полезная бизнес-логика.

Пул потоков ограничивает максимальное число активных потоков, организует очередь ожидания задач и повторно использует свободные потоки.

---

### Базовый пример на Java 21

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class ThreadPoolBasicDemo {
    public static void main(String[] args) throws InterruptedException {
        // Создание пула фиксированного размера на 4 рабочих потока
        ExecutorService executor = Executors.newFixedThreadPool(4);

        for (int i = 1; i <= 10; i++) {
            final int taskId = i;
            // Передача задачи на исполнение в пул
            executor.submit(() -> {
                System.out.println("Задача " + taskId + " выполняется потоком: " +
                        Thread.currentThread().getName());
            });
        }

        // Корректное завершение работы пула
        executor.shutdown();
        if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
            executor.shutdownNow();
        }
    }
}
```

## 🟡 Middle Level

### Анатомия конструктора `ThreadPoolExecutor`

Гибкая конфигурация пула осуществляется через конструктор `ThreadPoolExecutor`:

```java
public ThreadPoolExecutor(
    int corePoolSize,                   // 1. Базовое количество постоянно активных потоков
    int maximumPoolSize,                // 2. Максимальный предел потоков при перегрузке
    long keepAliveTime,                 // 3. Время простоя избыточных потоков до уничтожения
    TimeUnit unit,                      // 4. Единица измерения keepAliveTime
    BlockingQueue<Runnable> workQueue,  // 5. Очередь для ожидания поступающих задач
    ThreadFactory threadFactory,        // 6. Фабрика создания потоков (именование, демоны)
    RejectedExecutionHandler handler    // 7. Политика обработки переполнения
)
```

---

### Алгоритм приёма и распределения задач (Критический вопрос!)

Когда в метод `execute(Runnable)` поступает новая задача, `ThreadPoolExecutor` следует строгому 4-этапному алгоритму:

```
                      Поступление задачи: execute(Runnable)
                                       │
                                       v
               Число активных потоков < corePoolSize?
                       │                           │
                   [Да]│                       [Нет]│
                       v                           v
              Создать новый поток           Очередь workQueue полна?
             и запустить задачу                    │               │
                                               [Нет]│           [Да]│
                                                   v               v
                                            Поместить задачу   Число потоков < maximumPoolSize?
                                            в очередь ожидания         │                      │
                                                                   [Да]│                  [Нет]│
                                                                       v                      v
                                                              Создать новый поток    Вызвать обработчик
                                                              сверх corePoolSize     RejectedExecutionHandler
```

> [!IMPORTANT]
> **Золотое правило:** Дополнительные потоки (между `corePoolSize` и `maximumPoolSize`) создаются виртуальной машиной **ТОЛЬКО ТОГДА**, когда очередь задач `workQueue` **полностью заполнена**! Если очередь неограниченна (`LinkedBlockingQueue` без лимита), пул никогда не вырастет больше `corePoolSize`.

---

### Политики отклонения задач (`RejectedExecutionHandler`)

Если очередь заполнена, а число потоков достигло `maximumPoolSize` (или пул находится в состоянии `SHUTDOWN`), срабатывает одна из встроенных политик:

| Политика | Поведение при переполнении | Сценарий применения |
|---|---|---|
| **`AbortPolicy`** (дефолт) | Выбрасывает исключение `RejectedExecutionException` | Критические системы, где потеря задачи недопустима |
| **`CallerRunsPolicy`** | Задача выполняется синхронно в потоке, вызвавшем `execute()` | Создание естественного обратного давления (Back-pressure) |
| **`DiscardPolicy`** | Задача молча отбрасывается без уведомлений и ошибок | Некритичные метрики, телеметрия, логирование |
| **`DiscardOldestPolicy`** | Удаляет самую старую задачу из головы очереди и пробует снова | Обработка актуальных данных (тикеры акций, датчики) |

```java
// Настройка пула с политикой обратного давления (Back-pressure):
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4, 8, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

## 🔴 Senior Level

### Управление состоянием: Упаковка в `AtomicInteger ctl`

Для максимальной производительности в `ThreadPoolExecutor` объединены два параметра в одном атомарном слове `AtomicInteger ctl` (32 бита):
- **Старшие 3 бита:** отражают текущую стадию жизненного цикла пула.
- **Младшие 29 бит:** отражают точное число активных рабочих потоков (`workerCount`, лимит до $2^{29}-1 \approx 500$ млн).

```
   31 30 29 28 ...                           0
  ┌────────┬──────────────────────────────────┐
  │ Status │       workerCount (29 бит)       │
  └────────┴──────────────────────────────────┘
```

#### Фазы жизненного цикла:
1. **`RUNNING` (`111...`):** нормальная работа, принимает новые задачи и обрабатывает очередь.
2. **`SHUTDOWN` (`000...`):** не принимает новые задачи, но обязан доработать задачи из очереди.
3. **`STOP` (`001...`):** не принимает задачи, очищает очередь и прерывает (`interrupt`) работающие задачи.
4. **`TIDYING` (`010...`):** все задачи завершены, число рабочих потоков равно 0, вызывается хук `terminated()`.
5. **`TERMINATED` (`011...`):** метод `terminated()` завершён, пул полностью остановлен.

### Архитектура `Worker` и почему он наследует `AQS`

Рабочий поток внутри пула инкапсулирован во внутренний класс `Worker`:
```java
private final class Worker extends AbstractQueuedSynchronizer implements Runnable { ... }
```

#### Зачем `Worker` реализует нереентерабельную блокировку через AQS?
- Чтобы предотвратить прерывание потока во время реального выполнения бизнес-задачи!
- Метод пула `interruptIdleWorkers()` пытается захватить блокировку `Worker.tryLock()`.
- Если поток сейчас выполняет задачу, блокировка занята, и метод его не прерывает.
- Если поток заснул в очереди `workQueue.take()`, лок свободен, и поток корректно прерывается для уменьшения пула.
- Нереентерабельность исключает повторный захват потоком своего же лока при вызове управляющих методов.

### Формулы сайзинга пулов (Математика Брайана Гетца)

#### 1. CPU-bound задачи (математика, сериализация, криптография)
Процессор занят на 100%. Лишние потоки вызывают накладные расходы на смену контекста:
$$N_{threads} = N_{cpu} + 1$$
*(Дополнительный поток «+1» компенсирует редкие прерывания и page faults памяти).*

#### 2. I/O-bound задачи (БД, REST API, файловая система)
Потоки большую часть времени простаивают в ожидании ответов внешних систем:
$$N_{threads} = N_{cpu} \times U_{cpu} \times \left(1 + \frac{W}{C}\right)$$
Где:
- $N_{cpu}$ — число доступных логических ядер процессора (`Runtime.getRuntime().availableProcessors()`).
- $U_{cpu}$ — целевая утилизация процессора ($0 \le U_{cpu} \le 1$, обычно $0.8–0.9$).
- $W$ (Wait Time) — время ожидания ответа по сети/диску.
- $C$ (Compute Time) — время непосредственного расчёта на CPU.

### Опасность `ThreadLocal` в пулах потоков

Поскольку потоки пула переиспользуются, значения `ThreadLocal`, записанные одной задачей, **сохраняются в памяти потока** при его возврате в очередь ожидания.

#### Последствия:
1. **Утечки конфиденциальности:** следующая задача другого пользователя, выполняясь на этом же потоке, может прочитать чужой контекст безопасности (`SecurityContextHolder`).
2. **Утечки памяти (Memory Leaks):** если в `ThreadLocal` сохранялись объекты, загруженные кастомным `ClassLoader`, сборщик мусора не сможет выгрузить весь ClassLoader из Metaspace.

**Решение:** гарантированная очистка в блоке `finally`:
```java
pool.submit(() -> {
    try {
        UserContext.set(currentUser);
        executeBusinessLogic();
    } finally {
        UserContext.remove(); // КРИТИЧЕСКИ ВАЖНО!
    }
});
```

### Парадигма Virtual Threads в Java 21

В **Java 21** виртуальные потоки (Virtual Threads / JEP 444) изменили подход к проектированию:
- Для I/O-bound задач традиционные пулы потоков с `corePoolSize`/`maximumPoolSize` становятся антипаттерном.
- Вместо пула фиксированного размера используется фабрика **`Executors.newVirtualThreadPerTaskExecutor()`**, создающая лёгкий виртуальный поток на каждую задачу.
- **Когда пулы всё ещё нужны:** для **CPU-bound задач** (чтобы не перегружать планировщик ОС) и для **пулов ресурсов/подключений** (ограничение параллельных соединений к внешней БД через `Semaphore`).

## 🎯 Шпаргалка для интервью

### 1. 30-секундный эссенс (Elevator Pitch)
Пул потоков (`ThreadPoolExecutor`) управляет жизненным циклом и повторным использованием потоков, решая проблемы расхода памяти (1 МБ на стек) и оверхеда переключения контекста ОС. Новые задачи сначала занимают потоки до `corePoolSize`, затем направляются в `workQueue`, и только при переполнении очереди создаются дополнительные потоки до `maximumPoolSize`. При отказе срабатывает `RejectedExecutionHandler`. В Java 21 виртуальные потоки исключают необходимость пулинга для I/O-задач, оставляя пулы преимущественно для CPU-нагрузок и ограничения доступа к внешним ресурсам.

### 2. 4 каверзных вопроса с глубокими ответами

#### Вопрос 1: Почему `ThreadPoolExecutor` начинает создавать потоки сверх `corePoolSize` только ПОСЛЕ того, как полностью заполнится очередь задач?
**Ответ:**
Такова архитектурная философия: создание потока ОС — это тяжёлая и дорогая операция (выделение системного стека, регистрация в ядре ОС). Помещение задачи в очередь в памяти (`BlockingQueue`) — практически бесплатная in-memory операция. Поэтому пул проектируется так, чтобы максимально долго утилизировать существующие потоки ядра через очередь, и обращаться к масштабированию системных потоков только в ситуации явной перегрузки, когда очередь исчерпана.

#### Вопрос 2: В чём опасность вызова `Executors.newFixedThreadPool(10)` в Production под высокой нагрузкой?
**Ответ:**
Метод `Executors.newFixedThreadPool(n)` внутри создаёт экземпляр с **неограниченной очередью**: `new LinkedBlockingQueue<Runnable>()` с ёмкостью по умолчанию `Integer.MAX_VALUE` ($2^{31}-1$). Если входящий трафик превысит скорость обработки пула, задачи начнут бесконечно накапливаться в куче (Heap), что неизбежно приведёт к аварийному падению приложения с **`OutOfMemoryError: Java heap space`**.  
*Правило Production:* всегда создавать `ThreadPoolExecutor` вручную с ограниченной очередью (`ArrayBlockingQueue`) и явно заданной политикой отказа.

#### Вопрос 3: Зачем внутренний класс `Worker` наследуется от `AbstractQueuedSynchronizer` (AQS), реализуя собственный замок?
**Ответ:**
`Worker` использует AQS для реализации **нереентерабельной блокировки**, сигнализирующей о статусе выполнения задачи. Когда рабочий поток исполняет задачу, он вызывает `Worker.lock()`. Управляющие методы пула (например, `shutdown()` или уменьшение пула по таймауту) вызывают `Worker.tryLock()` перед отправкой прерывания (`interrupt()`). Если замок занят, поток считается занятым и не прерывается посреди исполнения задачи. Нереентерабельность гарантирует, что методы самого пула не смогут повторно войти в замок.

#### Вопрос 4: Как правильно выполнить остановку (Graceful Shutdown) пула потоков?
**Ответ:**
Стандартный двухфазный паттерн из документации Oracle:
1. Вызвать `executor.shutdown()` — пул прекращает приём новых задач и завершает задачи из очереди.
2. Подождать завершения через `executor.awaitTermination(timeout, unit)`.
3. Если таймаут истёк — вызвать `executor.shutdownNow()`, который отменяет ожидающие задачи из очереди и рассылает `Thread.interrupt()` активным потокам.
4. Повторно подождать завершения через второй `awaitTermination()`.

### 3. Типичные ошибки и Red Flags

❌ **"Использование `Executors.newCachedThreadPool()` для открытых веб-сервисов."**  
*Правильно:* `newCachedThreadPool()` имеет `maximumPoolSize = Integer.MAX_VALUE` с `SynchronousQueue`. При всплеске трафика в 10 000 RPS он попытается создать 10 000 системных потоков, убив сервер по OOM.

❌ **"Создание нового экземпляра пула локально внутри метода."**  
*Правильно:* Пул потоков — это долгоживущий тяжеловесный компонент. Создание пула внутри метода приводит к утечке неуправляемых системных потоков при каждом вызове. Пул должен быть синглтоном или управляемым бином Spring.

❌ **"Забытый `ThreadLocal.remove()` при использовании пулов."**  
*Правильно:* Неочищенный `ThreadLocal` приводит к утечке контекстов между независимыми запросами и утечкам памяти в Metaspace.
