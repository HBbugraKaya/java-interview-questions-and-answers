# Чи є недоліки у незмінних об'єктів

---

## 🟢 Junior Level

### 30-секундна відповідь
**Так, безумовно.** У розробці програмного забезпечення немає «срібних куль», і незмінність — це усвідомлений інженерний компроміс (*Trade-off*). 

Головні недоліки незмінних об'єктів:
1. **Накладні витрати на створення копій (Allocation Overhead):** щоб змінити бодай одне поле в об'єкті, доводиться створювати **абсолютно новий екземпляр** у купі та копіювати в нього всі інші поля.
2. **Навантаження на збирач сміття (GC Pressure):** у циклах та при частих оновленнях створюються мільйони тимчасових об'єктів, породжуючи часті паузи збирача сміття (*GC Jitter*).
3. **Незручність оновлення окремих полів:** якщо об'єкт містить 10 полів, для зміни одного поля доводиться або писати довгий конструктор, або використовувати методи-«візери» (*withers*).
4. **Труднощі інтеграції зі старими фреймворками:** ORM-бібліотеки (Hibernate, JPA) історично розраховані на мутабельні сутності з порожніми конструкторами та сетерами.

---

### Наочний приклад проблеми: Алокації в циклі
```java
// ❌ АНТИПАТЕРН: Незмінний клас у високочастотному циклі
String report = "Header\n";
for (int i = 0; i < 10_000; i++) {
    // На кожній ітерації виділяється новий масив і новий String:
    report += "Line " + i + "\n"; 
}

// ✅ ПОМ'ЯКШЕННЯ: Мутабельний буфер для локального збирання
StringBuilder sb = new StringBuilder();
sb.append("Header\n");
for (int i = 0; i < 10_000; i++) {
    sb.append("Line ").append(i).append("\n"); // In-place мутація
}
String finalReport = sb.toString(); // Фіксація незмінного результату
```

## 🟡 Middle Level

### 5 ключових недоліків незмінності в реальних проєктах

#### 1. Деградація продуктивності при частих оновленнях (High-Frequency Updates)
У сценаріях, де стан змінюється сотні тисяч разів на секунду (ігрові рушії, розрахунок фізики, обробка котирувань на біржі, аудіопотоки):
- Постійна алокація об'єктів у Eden перевантажує збирач сміття.
- Накладні витрати на копіювання даних переважають будь-які переваги багатопотоковості.

#### 2. Проблема оновлення окремих полів (Wither Pattern Boilerplate)
У змінному об'єкті достатньо викликати `user.setAge(30)`. 
У незмінному об'єкті потрібно створювати новий екземпляр через громіздкий виклик:
```java
// Доводиться передавати всі 8 незмінених полів заново:
User updated = new User(old.id(), old.name(), old.email(), 30, old.address(), old.roles(), old.createdAt(), old.status());
```
Для вирішення пишуть спеціальні методи-трансформери (Wither): `user.withAge(30)`.

#### 3. Складність досягнення глибокої незмінності (Deep Immutability)
Незмінність крихка: якщо клас містить хоча б одну змінну колекцію або мутабельний об'єкт (`Date`, масив `byte[]`), і розробник забув зробити захисну копію в конструкторі чи гетері, **весь клас миттєво стає вразливим**.

#### 4. Заборона класичного поліморфного успадкування
Щоб гарантувати незмінність, клас зобов'язаний бути оголошений як **`final`**. Це унеможливлює використання класичних ООП-патернів, заснованих на розширенні класів через `extends`.

#### 5. Несумісність із циклічними графами об'єктів
Незмінні об'єкти конструюються «знизу вгору». Створити циклічну залежність ($A \to B \to A$) із чистих незмінних об'єктів неможливо без брудних хаків через рефлексію або ліниві тримачі (*Lazy Holders*).

## 🔴 Senior Level

### Проблема інтеграції з Enterprise-фреймворками (JPA / Hibernate)
Архітектура **JPA (Java Persistence API)** створювалася в епоху домінування патерну JavaBeans:
1. **Проксування та Lazy Loading:** Hibernate генерує проксі-підкласи сутностей на льоту через ByteBuddy (`Proxy extends Entity`). Якщо оголосити сутність як `final class`, ліниве завантаження зв'язків ламається.
2. **Конструктор за замовчуванням:** специфікація JPA вимагає наявності `protected` або `public` конструктора без аргументів для рефлексивного створення екземплярів.
3. **Dirty Checking:** Hibernate відстежує зміни сутностей (*Dirty Checking*), порівнюючи поточний стан полів із моменту завантаження транзакції, та генерує точкові SQL `UPDATE`. Незмінні об'єкти ламають цей механізм.
- **Рішення в Enterprise-архітектурі:** розділення шарів! Сутності БД у шарі репозиторіїв (JPA Entities) проєктуються для Hibernate, а в усіх внутрішніх шарах бізнес-логіки та REST API використовуються чисті **Records / DTO**.

---

### Проблема затримок GC Jitter у розподілених мікросервісах
У хмарних мікросервісах під високими навантаженнями часті алокації тимчасових незмінних структур призводять до ефекту **GC Jitter**:
- Хоча більшість об'єктів помирає в Eden, збирачу сміття (G1 / Parallel) все одно доводиться регулярно зупиняти потоки застосунку (*Minor GC STW Pause* на 2–10 мс).
- Для середнього часу відповіді (*p50*) це непомітно.
- Проте на високих перцентилях затримки (**p99 / p99.9 Latency**) ці міні-паузи накопичуються в каскадних викликах між мікросервісами, спричиняючи таймаути клієнтських запитів.

---

### Чому Low-Latency та HFT уникають незмінності в Hot Path
У системах високочастотного трейдингу (High-Frequency Trading) та мережевих шлюзах:
- Застосовується архітектура з нульовим виділенням пам'яті (**Zero Garbage Architecture**).
- Замість створення нових незмінних об'єктів використовують архітектуру **LMAX Disruptor**: масив змінних об'єктів попередньо виділяється при старті JVM у вигляді кільцевого буфера (*RingBuffer*).
- Потоки просто перезаписують примітивні поля у вже наявних слотах пам'яті по колу, повністю виключаючи алокації в купі та зводячи паузи GC до абсолютного нуля.

## 4 Tricky Questions

### 1. Чому Java Records важко використовувати безпосередньо як JPA `@Entity` в Hibernate, і як правильно організувати архітектуру?
**Відповідь:**
Java Record не може бути JPA-сутністю з трьох фундаментальних причин:
1. `record` неявно компілюється як `final class`, а Hibernate вимагає нефінального класу для генерації проксі лінивого завантаження (CGLIB/ByteBuddy).
2. `record` не може мати конструктор без аргументів (no-arg constructor), обов'язковий за специфікацією JPA.
3. Усі поля `record` незмінні (`final`), що виключає мутацію полів Hibernate'ом при вибірці з бази та роботу механізму Dirty Checking.
**Правильна архітектура:** 
Використовувати класичні мутабельні сутності з анотаціями JPA виключно всередині шару доступу до даних (DAL/Repository), а назовні (у сервісний шар та контролери) мапити їх у незмінні `record` (DTO/Read Models) за допомогою MapStruct.

---

### 2. Як патерн «Wither» вирішує проблему часткової модифікації незмінних об'єктів? Наведіть приклад на чистій Java.
**Відповідь:**
Патерн «Wither» надає методи, що повертають копію об'єкта з одним зміненим полем, залишаючи решту полів недоторканими:
```java
public record UserConfig(String theme, int fontSize, boolean notificationsEnabled) {
    // Wither-метод:
    public UserConfig withTheme(String newTheme) {
        return new UserConfig(newTheme, this.fontSize, this.notificationsEnabled);
    }
    public UserConfig withFontSize(int newSize) {
        return new UserConfig(this.theme, newSize, this.notificationsEnabled);
    }
}
// Використання:
UserConfig config = new UserConfig("Dark", 14, true);
UserConfig updated = config.withFontSize(16); // Змінили тільки шрифт
```
Це робить часткове оновлення лаконічним, типобезпечним та легким для читання.

### 3. Чому в архітектурі LMAX Disruptor для високонавантажених черг навмисно відмовилися від незмінних повідомлень?
**Відповідь:**
В архітектурі LMAX Disruptor критичною вимогою є ультранизька затримка порядку сотень наносекунд. 
Якби кожна подія в черзі породжувала новий незмінний об'єкт (як у стандартній `BlockingQueue`), швидкість генерації об'єктів сягала б мільйонів екземплярів на секунду, викликаючи безперервний GC Churn та фатальні для HFT паузи Stop-the-World. 
Disruptor виділяє фіксований масив мутабельних об'єктів-контейнерів при старті JVM у вигляді кільця. Потоки-виробники просто перезаписують поля наявного об'єкта за обчисленою позицією послідовності (Sequence), забезпечуючи нульове виділення пам'яті (**Zero Garbage**) та роботу строго в кеші L1/L2 процесора.

---

### 4. Як впоратися зі створенням циклічного графа залежностей (наприклад, Parent $\leftrightarrow$ Child) у суто незмінній моделі?
**Відповідь:**
Створити циклічний граф зі строго незмінних об'єктів неможливо, оскільки для створення Parent потрібен готовий Child, а для створення Child потрібен готовий Parent (проблема курки та яйця). 
Способи вирішення:
1. **Розрив циклу через ідентифікатори (Id-based references):** замість прямих посилань на об'єкти зберігати їхні незмінні ID (`parentId`, `childId`), а самі об'єкти резолвити через незмінний контекст/репозиторій.
2. **Ліниві обчислення (Lazy Evaluation):** поле посилання оголошується як `Supplier<Parent>` або лямбда, що обчислюється при першому зверненні.
3. **Двофазна ініціалізація через Builder:** поки граф будується, він мутабельний; після завершення всі посилання заморожуються.

## 🎯 Шпаргалка для інтерв'ю

### Зведена таблиця недоліків незмінності
| Недолік | Де проявляється | Спосіб вирішення / Пом'якшення |
| :--- | :--- | :--- |
| **GC Pressure на алокацію** | Високочастотні цикли, стрімінг | Локальні мутабельні буфери (`StringBuilder`) |
| **Накладні витрати $O(N)$** | Модифікація великих колекцій | Персистентні структури даних (Vavr, HAMT) |
| **Незручність оновлення полів** | Об'єкти з великою кількістю полів | Патерн Wither (`withX()`), Builder pattern |
| **Конфлікт із Hibernate/JPA** | Шар персистентності та ORM | JPA-сутності лише в DAL, бізнес-логіка на Records |
| **Неможливість циклів** | Графи з циклічними посиланнями | Зберігання ID замість об'єктів, ліниві посилання `Supplier` |

### Червоні прапорці на співбесіді (Чого говорити не можна)
- ❌ *«Незмінність ідеальна всюди й не має жодних недоліків»* — ознака незрілості; у будь-якого архітектурного рішення є ціна.
- ❌ *«У мікросервісах JPA-сутності завжди повинні бути Records»* — Hibernate вимагає не-final класи та конструктори без аргументів.
- ❌ *«Незмінні об'єкти завжди працюють повільніше»* — у багатопотоковому середовищі Lock-Free читання робить їх у рази швидшими за мутабельні аналоги.
