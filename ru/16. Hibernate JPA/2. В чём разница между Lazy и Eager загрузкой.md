# В чём разница между Lazy и Eager загрузкой

---

## 🟢 Junior Level

### Суть концепций простыми словами

Параметр `fetch` (стратегия выборки данных) в аннотациях связей JPA определяет, **в какой момент времени связанные сущности загружаются из базы данных в оперативную память**:

- **`FetchType.EAGER` (жадная / немедленная загрузка):** Связанная сущность или коллекция загружается **сразу же** в момент извлечения родительского объекта, независимо от того, понадобятся эти данные приложению или нет.
- **`FetchType.LAZY` (ленивая / отложенная загрузка):** В момент загрузки родительского объекта связанное поле заполняется пустышкой-оберткой (**прокси-объектом** или коллекцией-оберткой `PersistentCollection`). Реальный SQL-запрос к базе данных выполняется **только в момент первого фактического обращения к содержимому этого поля** (вызов геттера, обращение к методам коллекции).

```
EAGER:
SELECT o FROM Order o WHERE o.id = 1
├── Заказ загружен
└── Связанный User загружен СРАЗУ ЖЕ (даже если нам нужен был только номер заказа)

LAZY:
SELECT o FROM Order o WHERE o.id = 1
├── Заказ загружен
└── Поле user = User$$ByteBuddy$Proxy (SQL-запроса за User НЕТ)
          │
          └── При вызове order.getUser().getName() ──> Выполняется SQL: SELECT * FROM users WHERE id = ?
```

### Значения по умолчанию в JPA

В спецификации Jakarta Persistence (JPA) стратегии по умолчанию зависят от кардинальности связи:

| Связь | По умолчанию | Рекомендация в Production |
| :--- | :--- | :--- |
| **`@OneToOne`** | **`EAGER`** | Переопределять на **`LAZY`** |
| **`@ManyToOne`** | **`EAGER`** | Переопределять на **`LAZY`** |
| **`@OneToMany`** | **`LAZY`** | Оставлять **`LAZY`** |
| **`@ManyToMany`** | **`LAZY`** | Оставлять **`LAZY`** |

> **Мнемоническое правило:** Все связи, оканчивающиеся на `*ToOne`, по умолчанию жадные (`EAGER`), а все связи на `*ToMany` — ленивые (`LAZY`). В современном энтерпрайз-коде **абсолютно все связи должны быть явно переопределены на `LAZY`**.

### Базовый пример настройки на Java

```java
@Entity
@Table(name = "orders")
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // ВАЖНО: Переопределяем дефолтный EAGER на LAZY
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")
    private User user;

    // По умолчанию уже LAZY, но рекомендуется указывать явно для прозрачности
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    private List<OrderItem> items = new ArrayList<>();
}
```

## 🟡 Middle Level

### Механика работы Lazy: Прокси и PersistentCollection

Когда Hibernate загружает сущность с ленивыми полями:
1. Для связей `*ToOne` создается **динамический прокси-класс** с помощью библиотеки `ByteBuddy` (например, `User$ByteBuddy$a1b2c3d4`), который наследует реальный класс `User`.
2. Для коллекций `*ToMany` стандартный `ArrayList` или `HashSet` подменяется служебной реализацией Hibernate: `PersistentBag`, `PersistentSet` или `PersistentList`.
3. Прокси содержит идентификатор сущности (`id`), признак инициализации `initialized = false` и ссылку на текущую открытую сессию (`SessionImplementor`).

```
order.getUser();           // Возвращает ссылку на прокси. SQL-запрос НЕ выполняется!
order.getUser().getId();   // Возвращает ID из прокси. SQL-запрос НЕ выполняется! (если AccessType.FIELD)
order.getUser().getEmail();// initialized == false! Hibernate делает SQL-запрос к таблице users.
```

### Главная ловушка: `LazyInitializationException`

Если обращение к ленивому полю происходит **после закрытия сессии Hibernate (вне транзакции)**, прокси не может выполнить SQL-запрос к БД, так как физическое соединение уже возвращено в пул соединений (HikariCP):

```java
@Service
public class OrderService {
    @Transactional(readOnly = true)
    public Order getOrder(Long id) {
        return orderRepository.findById(id).orElseThrow();
    } // Транзакция завершена, Session закрыта!
}

// Контроллер или маппер:
Order order = orderService.getOrder(1L);
// ВЫБРОС ИСКЛЮЧЕНИЯ:
// org.hibernate.LazyInitializationException: could not initialize proxy [com.example.User#42] - no Session
String email = order.getUser().getEmail(); 
```

### Как ПРАВИЛЬНО бороться с `LazyInitializationException`

| Метод | Описание | Оценка |
| :--- | :--- | :--- |
| **`JOIN FETCH` в JPQL** | Загрузить необходимые связи жадно в рамках одной конкретной транзакции | ⭐⭐⭐ **Рекомендуется** |
| **`@EntityGraph`** | Переопределить `LAZY` на `EAGER` декларативно в репозитории | ⭐⭐⭐ **Рекомендуется** |
| **DTO-проекция** | Выбрать только нужные поля сразу в DTO / Record | ⭐⭐⭐ **Лучшая практика** |
| **`Hibernate.initialize(proxy)`** | Принудительно инициализировать прокси внутри `@Transactional` метода сервиса | ⭐⭐ Допустимо |
| **Смена на `fetch = EAGER`** | Сделать связь жадной глобально в Entity | ❌ **Антипаттерн** (порождает N+1) |
| **Open Session in View (OSIV)** | Держать сессию БД открытой на протяжении всего HTTP-запроса | ❌ **Антипаттерн** (утечка коннектов) |

## 🔴 Senior Level

### Почему `FetchType.EAGER` — архитектурная ошибка в JPA

В спецификации JPA 1.0 разработчики предположили, что если сущность ссылается на одного родителя (`@ManyToOne`), то этот родитель почти наверняка нужен. На практике это породило системные проблемы:

1. **EAGER невозможно отменить в JPQL-запросе:**
   Если над полем в Entity написано `FetchType.LAZY`, вы всегда можете превратить его в EAGER для конкретного сценария с помощью `JOIN FETCH`.
   Но если над полем объявлен `FetchType.EAGER`, **вы не сможете сделать его ленивым ни в одном JPQL-запросе**! Даже если вызывается `SELECT o.id FROM Order o`, Hibernate будет обязан подтянуть все связанные EAGER-сущности.
2. **Гарантированное порождение проблемы N+1:**
   При вызове `orderRepository.findAll()` EAGER не объединяет таблицы в `JOIN`, а выполняет $N$ дополнительных запросов для каждой сущности.
3. **Каскадная перегрузка памяти (EAGER Chain Reaction):**
   Сущность `Order` имеет EAGER-связь с `User`, `User` имеет EAGER-связь с `Company`, `Company` — с `Address`. Чтение одного заказа незаметно вытягивает половину базы данных в память JVM.

### Анатомия Open Session in View (OSIV) и истощение пула HikariCP

В Spring Boot по умолчанию параметр `spring.jpa.open-in-view` выставлен в `true`.
- Режим регистрирует перехватчик `OpenEntityManagerInViewInterceptor`, который открывает Session в самом начале HTTP-запроса (при входе в фильтр сервлета) и закрывает ее **только после завершения рендеринга JSON/HTML в ответе контроллера**.
- Это позволяет разработчикам обращаться к ленивым геттерам прямо в мапперах (MapStruct, Jackson) без `LazyInitializationException`.

```
                    ОПАСНОСТЬ OPEN SESSION IN VIEW (OSIV = true)
                    
HTTP Request ──> [Filter: Session Open] ──> [Controller] ──> [Service: @Transactional]
                                                                        │
                                                          Захват коннекта из HikariCP
                                                                        │
HTTP Response <── [Filter: Session Close] <── [Jackson JSON] <── [Service: Конец транзакции]
       ▲                                              ▲
       │                                              │
Сессия закрывается здесь!            Если Jackson дергает LAZY геттер во время сериализации,
                                     коннект удерживается во время сетевой отдачи клиенту!
```

**Почему OSIV запрещен в Highload:**
Если клиент медленно вычитывает HTTP-ответ через нестабильный мобильный интернет, поток удерживает физическое соединение с БД из пула HikariCP все это время. Пул из 10–30 коннектов исчерпывается за секунды, и всё приложение перестает отвечать (`Connection is not available, request timed out after 30000ms`).
**Production-стандарт:** всегда выставлять `spring.jpa.open-in-view: false`.

### Тонкости прокси ByteBuddy: `instanceof` против `getClass()`

Поскольку LAZY-связь представлена прокси-объектом `User$ByteBuddy$...`:
- Сравнение через `order.getUser().getClass() == User.class` вернет **`false`**!
- Проверка через `order.getUser() instanceof User` вернет **`true`** (так как прокси наследуется от `User`).
- Именно поэтому в классах Entity реализация метода `equals()` **никогда не должна использовать `getClass()`** — только `instanceof`, а обращение к полям другого объекта должно происходить через геттеры (`other.getId()`), чтобы прокси мог перехватить вызов!

### Ленивая загрузка базовых колонок (`@Basic(fetch = FetchType.LAZY)`)

Иногда требуется сделать ленивой не связь, а тяжелую колонку таблицы (например, `byte[] documentScan` или большой JSON/TEXT `String description`):

```java
@Lob
@Basic(fetch = FetchType.LAZY)
@Column(name = "document_scan")
private byte[] documentScan;
```

> **Важно:** В чистом виде аннотация `@Basic(fetch = FetchType.LAZY)` **игнорируется Hibernate**!
> Динамические прокси оборачивают только связи между таблицами. Чтобы ленивая загрузка колонок заработала, требуется включить **инструментацию байткода во время сборки проекта (Bytecode Enhancement)** через плагин `hibernate-enhance-maven-plugin`:

```xml
<plugin>
    <groupId>org.hibernate.orm.tooling</groupId>
    <artifactId>hibernate-enhance-maven-plugin</artifactId>
    <version>${hibernate.version}</version>
    <executions>
        <execution>
            <configuration>
                <enableLazyInitialization>true</enableLazyInitialization>
            </configuration>
            <goals>
                <goal>enhance</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

## 4 Tricky Questions

### 1. Почему вызов `order.getUser().getId()` не инициирует SQL-запрос к базе данных, если поле `user` объявлено как `LAZY`?

**Ответ:**
Поведение зависит от типа доступа (Access Type), определенного в сущности:
1. **Property Access (`@Id` над геттером `getId()`):** Hibernate знает, что вызов геттера идентификатора возвращает сам первичный ключ, который уже известен прокси (он был сохранен в прокси при чтении внешнего ключа `user_id` из таблицы `orders`). Поэтому вызов `getId()` возвращает значение из локального поля прокси без обращения к БД.
2. **Field Access (`@Id` над полем `id`):** Начиная с Hibernate 5, Hibernate оптимизирует вызов `getId()` даже при доступе по полям, если метод распознан как стандартный геттер идентификатора.
3. Однако любой другой вызов (например, `order.getUser().getName()`, `hashCode()` или прямое обращение к полю) немедленно триггерит инициализацию прокси и отправку SQL-запроса в базу данных.

### 2. Может ли связь `@OneToOne(fetch = FetchType.LAZY)` проигнорировать настройку и загрузиться жадно?

**Ответ:**
**Да, и это классическая ловушка на не-владеющей стороне (non-owning side).**
- В связи `@OneToOne` сторона, содержащая атрибут `mappedBy`, не имеет колонки внешнего ключа в своей таблице (внешний ключ лежит в таблице партнера).
- Прокси-объект в Java может представлять собой только не-null ссылку. Но если в связанной таблице строки нет, поле в Java должно содержать значение `null`.
- Чтобы узнать, нужно положить в поле `null` или прокси-объект, Hibernate **обязан заранее знать о факте существования записи**.
- Так как в локальной строке внешнего ключа нет, Hibernate выполняет немедленный SQL-запрос `SELECT` в связанную таблицу. Ленивая загрузка превращается в немедленную (`EAGER`), порождая N+1.
- **Решение:** Либо использовать Bytecode Enhancement, либо моделировать связь как `@ManyToOne` с уникальным ограничением (`unique = true`).

### 3. Почему при наследовании сущностей (`InheritanceType.JOINED`) ленивая загрузка родительского прокси может сломать полиморфизм?

**Ответ:**
1. Если сущность `Payment` имеет наследников `CreditCardPayment` и `CashPayment`, а заказ содержит связь `@ManyToOne(fetch = FetchType.LAZY) private Payment payment;`.
2. При загрузке заказа Hibernate создает прокси для базового класса `Payment`.
3. Java — статически типизированный язык. Прокси-объект, сгенерированный ByteBuddy, является экземпляром класса `Payment$ByteBuddy$Proxy`. Он **не может на лету изменить свой класс** на `CreditCardPayment` после того, как прочитает данные из базы данных!
4. В результате проверка `order.getPayment() instanceof CreditCardPayment` вернет `false`, а явный каст `(CreditCardPayment) order.getPayment()` завершится исключением `ClassCastException`.
5. **Решение:** Использовать утилиту `Hibernate.unproxy(order.getPayment())` для извлечения реального лежащего внутри экземпляра целевого подкласса.

### 4. В чем разница между `Hibernate.initialize(proxy)` и простым вызовом геттера `proxy.getName()`?

**Ответ:**
- `proxy.getName()` — это неявная инициализация. Если метод `getName()` возвращает `null`, разработчик не всегда может быть уверен, произошла ли инициализация (хотя прокси перехватит вызов любого метода, кроме `getId()`).
- `Hibernate.initialize(proxy)` — это официальный декларативный API Hibernate. Метод безопасно проверяет, является ли переданный объект прокси или ленивой коллекцией. Если объект уже инициализирован или равен `null`, метод ничего не делает. Если это неинициализированный прокси, он принудительно подгружает данные из текущей сессии. Если сессия закрыта, он сразу бросает явный `LazyInitializationException`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «**LAZY и EAGER** определяют момент выборки связанных данных из БД: при **EAGER** связанные сущности загружаются сразу вместе с родителем, а при **LAZY** поле заполняется легковесным прокси (`ByteBuddy`) или `PersistentCollection`, а SQL-запрос откладывается до первого фактического обращения к данным. В продакшене действует строгое правило: **все связи без исключения должны объявляться как LAZY**. Дефолтный `EAGER` для связей `@ManyToOne` и `@OneToOne` — это исторический легаси JPA, приводящий к проблеме N+1 и деградации производительности. Для устранения `LazyInitializationException` используются `JOIN FETCH`, `@EntityGraph` или DTO-проекции, а использование Open Session in View (OSIV) в микросервисах считается опасным антипаттерном».

### Ключевые метрики для Production-мониторинга
- `HikariCP: ActiveConnections` vs `PendingConnections`: резкий рост ожидания коннектов при включенном OSIV.
- `hibernate.stat.entity_fetch_count`: количество ленивых подгрузок сущностей.
- `org.hibernate.LazyInitializationException` в логах ошибок мониторинга (Sentry, ELK).

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«Если вылетает LazyInitializationException, я просто меняю связь на FetchType.EAGER»* — Фатальная ошибка. Это маскирует проблему, создавая неустранимый N+1 и проблемы с памятью.
- ❌ *«Связи @ManyToOne по умолчанию ленивые»* — Нет, в JPA они по умолчанию EAGER, их нужно принудительно объявлять как LAZY.
- ❌ *«Open Session in View — отличная и рекомендуемая практика для микросервисов»* — OSIV приводит к истощению пула коннектов БД и непредсказуемым запросам на этапе сериализации JSON.
- ❌ *«@Basic(fetch = LAZY) работает из коробки просто по аннотации»* — Для базовых полей ленивая загрузка требует включения Bytecode Enhancement плагина при сборке.
