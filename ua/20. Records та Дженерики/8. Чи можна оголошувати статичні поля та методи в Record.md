# Чи можна оголошувати статичні поля та методи в Record

---

## 🟢 Junior Level

**Так, можна.** `Record` у Java повністю підтримує оголошення **статичних полів, статичних методів і статичних блоків ініціалізації**.

Статичні члени належать самому класу, а не його конкретним екземплярам, тому вони не порушують фундаментальне правило: *«стан екземпляра визначається виключно компонентами його заголовка»*.

```java
public record User(String name, int age) {
    // 1. Статична константа:
    public static final int ADULT_AGE = 18;

    // 2. Статичний фабричний метод:
    public static User anonymous() {
        return new User("Guest", 0);
    }

    // 3. Статичний предикат:
    public static boolean isValidAge(int age) {
        return age >= 0 && age <= 150;
    }
}

// Використання:
boolean valid = User.isValidAge(25); // true
User guest = User.anonymous();       // User[name=Guest, age=0]
```

### Головна заборона

Дозволені **тільки статичні** додаткові поля. Оголошення будь-яких нестатичних полів екземпляра (`instance fields`) усередині тіла `{ ... }` викличе помилку компіляції.

## 🟡 Middle Level

### 1. Статичні фабрики та попередньо створені константи

Найчастіший сценарій використання статичних членів у Record — оголошення іменованих фабрик і типових констант:

```java
public record Money(BigDecimal amount, Currency currency) {
    // Попередньо створені популярні константи (кеш значень):
    public static final Money ZERO_USD = new Money(BigDecimal.ZERO, Currency.getInstance("USD"));
    public static final Money ZERO_EUR = new Money(BigDecimal.ZERO, Currency.getInstance("EUR"));

    // Статичний фабричний метод із парсингом:
    public static Money of(double amount, String currencyCode) {
        return new Money(BigDecimal.valueOf(amount), Currency.getInstance(currencyCode));
    }
}
```

### 2. Статичний блок ініціалізації (`static { ... }`)

У `Record` дозволено оголошувати статичні блоки ініціалізації для складного попереднього налаштування (наприклад, компіляції `Regex` або наповнення незмінних довідників):

```java
public record OrderId(String value) {
    private static final Pattern UUID_PATTERN;

    static {
        // Виконується один раз під час завантаження класу в JVM
        UUID_PATTERN = Pattern.compile("^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$");
    }

    public OrderId {
        if (!UUID_PATTERN.matcher(value).matches()) {
            throw new IllegalArgumentException("Invalid UUID format: " + value);
        }
    }
}
```

## 🔴 Senior Level

### Ізоляція від семантики екземпляра та метаданих JVM

Статичні члени класу Record повністю ізольовані від механіки роботи з компонентами:

1. **Виключення з метаданих `RecordComponents`**:
   Статичні поля **не потрапляють** в атрибут байткоду `Record` і не повертаються методом `Class.getRecordComponents()`. Фреймворки рефлексії (Jackson, Hibernate) їх ігнорують.
2. **Виключення з `equals()` та `hashCode()`**:
   Методи порівняння, генеровані через `invokedynamic` та `ObjectMethods.bootstrap`, узагалі не читають статичні поля. Зміна статичного поля жодним чином не впливає на рівність двох екземплярів рекорду.
3. **Виключення із серіалізації**:
   Статичні поля не серіалізуються в `ObjectOutputStream` і не передаються в канонічний конструктор при відновленні об'єкта.

### Вкладені Records неявно статичні (Implicitly Static)

Важлива архітектурна особливість мови (JLS §8.10): **будь-який локальний або вкладений Record є неявно статичним (`implicitly static`)**:

```java
public class OuterService {
    private String secret = "123";

    // Навіть без ключового слова static:
    public record NestedPayload(String data) {
        public void print() {
            // System.out.println(secret); // ❌ Помилка компіляції: non-static variable secret cannot be referenced from static context
        }
    }
}
```

**Чому це критично:**
На відміну від звичайних внутрішніх класів (Inner Classes), вкладений `record` **ніколи не зберігає неявне посилання на охоплюючий об'єкт** (`OuterService.this`). Це:
- Запобігає витокам пам'яті (Memory Leaks), коли маленьке DTO утримує в купі важкий батьківський сервіс.
- Знижує оверхед за пам'яттю на 8 байтів (відсутнє поле `this$0`).

## 4 Tricky Questions

### 1. Чи враховуються статичні поля в `equals()`, `hashCode()`, `toString()` та при десеріалізації Record?

**Відповідь:**
**Ні, абсолютно не враховуються.**

Статичні поля належать метаданим класу в Metaspace, а не конкретному об'єкту в купі (Heap). Байткод методів `equals()`, `hashCode()` і `toString()`, сформований бутстрап-методом `ObjectMethods.bootstrap`, оперує виключно списком дескрипторів `MethodHandle` компонентів запису.

При Java-серіалізації (`Serializable`) у потік записуються лише компоненти, і десеріалізатор передає в канонічний конструктор лише значення із заголовка. Статичні поля існують в єдиному екземплярі на весь `ClassLoader`.

### 2. Чи є вкладений Record всередині іншого класу статичним за замовчуванням, якщо не вказати `static`?

**Відповідь:**
**Так, є.**

Згідно зі специфікацією Java (JLS §8.10), будь-який `record`, оголошений усередині іншого класу, інтерфейсу або навіть методу (локальний рекорд), є **неявно статичним (`implicitly static`)**, навіть якщо модифікатор `static` опущений.

Він не має прихованого поля посилання на зовнішній клас (`this$0`) і не має доступу до нестатичних полів та методів зовнішнього класу. Це зроблено навмисно, щоб гарантувати чистоту і незалежність моделі даних.

### 3. Чи можна оголосити статичний блок ініціалізації (`static { ... }`) всередині Record?

**Відповідь:**
**Так, можна.**

Статичний блок ініціалізатора в `Record` працює точно так само, як у звичайному класі: він виконується рівно один раз потоком, що виконує ініціалізацію класу (`<clinit>`) відповідно до JLS §12.4. У ньому дозволено ініціалізувати складні статичні структури даних, налаштовувати регулярні вирази або виконувати попередні обчислення.

### 4. Чому оголошення мутабельного статичного стану (`public static Map<K, V> cache = ...`) всередині Record вважається грубим архітектурним антипатерном?

**Відповідь:**
Тому що фундаментальне призначення Record — бути **чистим, незмінним носієм даних (Value Object)**.

Впровадження глобального мутабельного стану всередину Record:
1. Ламає принцип єдиної відповідальності (SRP): структура даних починає відповідати за кешування та управління життєвим циклом глобальних ресурсів.
2. Створює вразливість до race conditions та memory leaks при конкурентному доступі із сотень потоків.
3. Робить юніт-тестування крихким через спільний стан між тестами.
Статичні поля в `Record` мають бути суворо `static final` і містити виключно незмінні константи або чисті функції.

## 🎯 Шпаргалка для інтерв'ю

### Головне про статичні члени в Record

- **Що дозволено**:
  - `static final` константи (`public static final int MAX = 100;`).
  - Статичні фабричні методи (`public static of(...)`).
  - Статичні блоки ініціалізації (`static { ... }`).
  - Вкладені статичні класи, рекорди та інтерфейси.
- **Що заборонено**:
  - Будь-які нестатичні (`instance`) поля.
- **Вкладені рекорди**: Завжди неявно `static` (немає посилання `this$0` на зовнішній клас).
- **Серіалізація та рівність**: Статичні поля **не беруть участі** в `equals()`, `hashCode()`, `toString()`, `Class.getRecordComponents()` та серіалізації.

### Антипатерни
- ❌ *Мутабельні статичні колекції (`static List<User> users`)*: руйнує ідею чистого DTO і створює витоки пам'яті.
- ❌ *Спроба зімітувати приховані поля екземпляра через `static ThreadLocal`*: небезпечний милиця, що призводить до race conditions і витоків потоків у Thread Pool.
