# Що таке пул потоків (Thread Pool)

---

## 🟢 Junior Level

### Коротка відповідь для співбесіди (30 секунд)
**Пул потоків (Thread Pool)** — це архітектурний шаблон і компонент середовища виконання Java, що являє собою керований набір попередньо створених робочих потоків, які багаторазово перевикористовуються для асинхронного виконання задач, що надходять.

У Java пул потоків представлений інтерфейсом `ExecutorService` та його базовою реалізацією **`ThreadPoolExecutor`** з пакета `java.util.concurrent`.

Створення окремого платформеного потоку операційної системи через `new Thread().start()` на кожну вхідну задачу у високонавантажених системах є неприпустимим:
1. **Виділення пам'яті:** кожен платформений потік резервує окремий стек викликів (~1 МБ за замовчуванням за прапорцем `-Xss`). Створення 10 000 потоків призведе до вичерпання оперативної пам'яті та аварійного падіння JVM із помилкою `OutOfMemoryError: unable to create native thread`.
2. **Накладні витрати ОС:** ініціалізація системного дескриптора ядра та перемикання контексту процесора (Context Switching) між тисячами потоків забирають більше ресурсів CPU, ніж корисна бізнес-логіка.

Пул потоків обмежує максимальну кількість активних потоків, організовує чергу очікування задач і повторно використовує вільні потоки.

---

### Базовий приклад на Java 21

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class ThreadPoolBasicDemo {
    public static void main(String[] args) throws InterruptedException {
        // Створення пулу фіксованого розміру на 4 робочі потоки
        ExecutorService executor = Executors.newFixedThreadPool(4);

        for (int i = 1; i <= 10; i++) {
            final int taskId = i;
            // Передача задачі на виконання в пул
            executor.submit(() -> {
                System.out.println("Задача " + taskId + " виконується потоком: " +
                        Thread.currentThread().getName());
            });
        }

        // Коректне завершення роботи пулу
        executor.shutdown();
        if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
            executor.shutdownNow();
        }
    }
}
```

## 🟡 Middle Level

### Анатомія конструктора `ThreadPoolExecutor`

Гнучка конфігурація пулу здійснюється через конструктор `ThreadPoolExecutor`:

```java
public ThreadPoolExecutor(
    int corePoolSize,                   // 1. Базова кількість постійно активних потоків
    int maximumPoolSize,                // 2. Максимальна межа потоків при перевантаженні
    long keepAliveTime,                 // 3. Час простою надлишкових потоків до знищення
    TimeUnit unit,                      // 4. Одиниця вимірювання keepAliveTime
    BlockingQueue<Runnable> workQueue,  // 5. Черга для очікування задач, що надходять
    ThreadFactory threadFactory,        // 6. Фабрика створення потоків (іменування, демони)
    RejectedExecutionHandler handler    // 7. Політика обробки переповнення
)
```

---

### Алгоритм прийому та розподілу задач (Критичне питання!)

Коли в метод `execute(Runnable)` надходить нова задача, `ThreadPoolExecutor` слідує суворому 4-етапному алгоритму:

```
                       Надходження задачі: execute(Runnable)
                                        │
                                        v
                Кількість активних потоків < corePoolSize?
                        │                           │
                    [Так]│                       [Ні]│
                        v                           v
               Створити новий потік          Черга workQueue повна?
              та запустити задачу                  │               │
                                                [Ні]│           [Так]│
                                                    v               v
                                             Помістити задачу   Кількість потоків < maximumPoolSize?
                                             в чергу очікування        │                      │
                                                                   [Так]│                  [Ні]│
                                                                        v                      v
                                                               Створити новий потік    Викликати обробник
                                                               понад corePoolSize      RejectedExecutionHandler
```

> [!IMPORTANT]
> **Золоте правило:** Додаткові потоки (між `corePoolSize` та `maximumPoolSize`) створюються віртуальною машиною **ТІЛЬКИ ТОДІ**, коли черга задач `workQueue` **повністю заповнена**! Якщо черга є необмеженою (`LinkedBlockingQueue` без ліміту), пул ніколи не виросте більше за `corePoolSize`.

---

### Політики відхилення задач (`RejectedExecutionHandler`)

Якщо черга заповнена, а кількість потоків досягла `maximumPoolSize` (або пул перебуває в стані `SHUTDOWN`), спрацьовує одна із вбудованих політик:

| Політика | Поведінка при переповненні | Сценарій застосування |
|---|---|---|
| **`AbortPolicy`** (дефолт) | Викидає виняток `RejectedExecutionException` | Критичні системи, де втрата задачі неприпустима |
| **`CallerRunsPolicy`** | Задача виконується синхронно в потоці, який викликав `execute()` | Створення природного зворотного тиску (Back-pressure) |
| **`DiscardPolicy`** | Задача мовчки відкидається без сповіщень та помилок | Некритичні метрики, телеметрія, логування |
| **`DiscardOldestPolicy`** | Видаляє найстарішу задачу з голови черги та пробує знову | Обробка найактуальніших даних (тікери акцій, сенсори) |

```java
// Налаштування пулу з політикою зворотного тиску (Back-pressure):
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4, 8, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

## 🔴 Senior Level

### Управління станом: Упаковка в `AtomicInteger ctl`

Для максимальної продуктивності в `ThreadPoolExecutor` об'єднано два параметри в одному атомарному слові `AtomicInteger ctl` (32 біти):
- **Старші 3 біти:** відображають поточну стадію життєвого циклу пулу.
- **Молодші 29 біт:** відображають точну кількість активних робочих потоків (`workerCount`, ліміт до $2^{29}-1 \approx 500$ млн).

```
   31 30 29 28 ...                           0
  ┌────────┬──────────────────────────────────┐
  │ Status │       workerCount (29 біт)       │
  └────────┴──────────────────────────────────┘
```

#### Фази життєвого циклу:
1. **`RUNNING` (`111...`):** нормальна робота, приймає нові задачі та обробляє чергу.
2. **`SHUTDOWN` (`000...`):** не приймає нові задачі, але зобов'язаний доробити задачі з черги.
3. **`STOP` (`001...`):** не приймає задачі, очищає чергу та перериває (`interrupt`) активні задачі.
4. **`TIDYING` (`010...`):** усі задачі завершені, кількість робочих потоків дорівнює 0, викликається хук `terminated()`.
5. **`TERMINATED` (`011...`):** метод `terminated()` завершено, пул повністю зупинено.

### Архітектура `Worker` і чому він наслідує `AQS`

Робочий потік всередині пулу інкапсульований у внутрішній клас `Worker`:
```java
private final class Worker extends AbstractQueuedSynchronizer implements Runnable { ... }
```

#### Навіщо `Worker` реалізує нереентерабельне блокування через AQS?
- Щоб запобігти перериванню потоку під час реального виконання бізнес-задачі!
- Метод пулу `interruptIdleWorkers()` намагається захопити блокування `Worker.tryLock()`.
- Якщо потік зараз виконує задачу, блокування зайняте, і метод його не перериває.
- Якщо потік заснув у черзі `workQueue.take()`, лок вільний, і потік коректно переривається для зменшення пулу.
- Нереентерабельність виключає повторне захоплення потоком свого ж лока при виклику керуючих методів пулу.

---

### Формули сайзингу пулів (Математика Браяна Гетца)

#### 1. CPU-bound задачі (математика, серіалізація, криптографія)
Процесор зайнятий на 100%. Зайві потоки викликають накладні витрати на зміну контексту:
$$N_{threads} = N_{cpu} + 1$$
*(Додатковий потік «+1» компенсує рідкісні переривання та page faults пам'яті).*

#### 2. I/O-bound задачі (БД, REST API, файлова система)
Потоки більшу частину часу простоюють в очікуванні відповідей зовнішніх систем:
$$N_{threads} = N_{cpu} \times U_{cpu} \times \left(1 + \frac{W}{C}\right)$$
Де:
- $N_{cpu}$ — кількість доступних логічних ядер процесора (`Runtime.getRuntime().availableProcessors()`).
- $U_{cpu}$ — цільова утилізація процесора ($0 \le U_{cpu} \le 1$, зазвичай $0.8–0.9$).
- $W$ (Wait Time) — час очікування відповіді мережею або з диска.
- $C$ (Compute Time) — час безпосереднього розрахунку на CPU.

### Небезпека `ThreadLocal` у пулах потоків

Оскільки потоки пулу повторно використовуються, значення `ThreadLocal`, записані однією задачею, **зберігаються в пам'яті потоку** при його поверненні в чергу очікування.

#### Наслідки:
1. **Витоки конфіденційності:** наступна задача іншого користувача, виконуючись на цьому ж потоці, може прочитати чужий контекст безпеки (`SecurityContextHolder`).
2. **Витоки пам'яті (Memory Leaks):** якщо в `ThreadLocal` зберігалися об'єкти, завантажені кастомним `ClassLoader`, збирач сміття не зможе вивантажити весь ClassLoader із Metaspace.

**Рішення:** гарантоване очищення в блоці `finally`:
```java
pool.submit(() -> {
    try {
        UserContext.set(currentUser);
        executeBusinessLogic();
    } finally {
        UserContext.remove(); // КРИТИЧНО ВАЖЛИВО!
    }
});
```

---

### Парадигма Virtual Threads у Java 21

У **Java 21** віртуальні потоки (Virtual Threads / JEP 444) змінили підхід до проєктування:
- Для I/O-bound задач традиційні пули потоків із `corePoolSize`/`maximumPoolSize` стають антипатерном.
- Замість пулу фіксованого розміру використовується фабрика **`Executors.newVirtualThreadPerTaskExecutor()`**, яка створює легкий віртуальний потік на кожну задачу.
- **Коли пули все ще потрібні:** для **CPU-bound задач** (щоб не перевантажувати планувальник ОС) і для **пулів ресурсів/з'єднань** (обмеження паралельних з'єднань до зовнішньої БД через `Semaphore`).

## 🎯 Шпаргалка для інтерв'ю

### 1. 30-секундний есенс (Elevator Pitch)
Пул потоків (`ThreadPoolExecutor`) керує життєвим циклом та повторним використанням потоків, вирішуючи проблеми витрат пам'яті (1 МБ на стек) та накладних витрат перемикання контексту ОС. Нові задачі спочатку займають потоки до `corePoolSize`, потім направляються у `workQueue`, і лише при переповненні черги створюються додаткові потоки до `maximumPoolSize`. При переповненні спрацьовує `RejectedExecutionHandler`. У Java 21 віртуальні потоки усувають потребу в пулінгу для I/O-задач, залишаючи пули переважно для CPU-навантажень та обмеження доступу до зовнішніх ресурсів.

### 2. 4 каверзних питання з глибокими відповідями

#### Питання 1: Чому `ThreadPoolExecutor` починає створювати потоки понад `corePoolSize` тільки ПІСЛЯ того, як повністю заповниться черга задач?
**Відповідь:**
Такою є архітектурна філософія: створення потоку ОС — це важка і дорога операція (виділення системного стека, реєстрація в ядрі ОС). Додавання задачі в чергу в пам'яті (`BlockingQueue`) — практично безкоштовна in-memory операція. Тому пул проєктується так, щоб максимально довго утилізувати наявні потоки ядра через чергу, і вдаватися до масштабування системних потоків лише в ситуації явного перевантаження, коли черга вичерпана.

#### Питання 2: У чому небезпека виклику `Executors.newFixedThreadPool(10)` у Production під високим навантаженням?
**Відповідь:**
Метод `Executors.newFixedThreadPool(n)` всередині створює екземпляр з **необмеженою чергою**: `new LinkedBlockingQueue<Runnable>()` з місткістю за замовчуванням `Integer.MAX_VALUE` ($2^{31}-1$). Якщо вхідний трафік перевищить швидкість обробки пулу, задачі почнуть безмежно накопичуватися в купі (Heap), що неминуче призведе до аварійного падіння застосунку з **`OutOfMemoryError: Java heap space`**.  
*Правило Production:* завжди створювати `ThreadPoolExecutor` вручну з обмеженою чергою (`ArrayBlockingQueue`) та явно заданою політикою відхилення.

#### Питання 3: Навіщо внутрішній клас `Worker` наслідується від `AbstractQueuedSynchronizer` (AQS), реалізуючи власний замок?
**Відповідь:**
`Worker` використовує AQS для реалізації **нереентерабельного блокування**, що сигналізує про статус виконання задачі. Коли робочий потік виконує задачу, він викликає `Worker.lock()`. Керуючі методи пулу (наприклад, `shutdown()` або зменшення пулу за таймаутом) викликають `Worker.tryLock()` перед відправкою переривання (`interrupt()`). Якщо замок зайнятий, потік вважається зайнятим і не переривається посеред виконання задачі. Нереентерабельність гарантує, що методи самого пулу не зможуть повторно увійти в замок.

#### Питання 4: Як правильно виконати зупинку (Graceful Shutdown) пулу потоків?
**Відповідь:**
Стандартний двофазний патерн із документації Oracle:
1. Викликати `executor.shutdown()` — пул припиняє прийом нових задач і завершує задачі з черги.
2. Почекати завершення через `executor.awaitTermination(timeout, unit)`.
3. Якщо таймаут минув — викликати `executor.shutdownNow()`, який скасовує очікуючі задачі з черги та розсилає `Thread.interrupt()` активним потокам.
4. Повторно почекати завершення через другий `awaitTermination()`.

### 3. Типові помилки та Red Flags

❌ **"Використання `Executors.newCachedThreadPool()` для відкритих веб-сервісів."**  
*Правильно:* `newCachedThreadPool()` має `maximumPoolSize = Integer.MAX_VALUE` із `SynchronousQueue`. При сплеску трафіку в 10 000 RPS він спробує створити 10 000 системних потоків, знищивши сервер через OOM.

❌ **"Створення нового екземпляра пулу локально всередині методу."**  
*Правильно:* Пул потоків — це довгоживучий важкий компонент. Створення пулу всередині методу призводить до витоку некерованих системних потоків при кожному виклику. Пул має бути синглтоном або керованим біном Spring.

❌ **"Забутий `ThreadLocal.remove()` при використанні пулів."**  
*Правильно:* Неочищений `ThreadLocal` призводить до витоку контекстів між незалежними запитами та витоків пам'яті в Metaspace.
