# Как правильно использовать @OneToMany и @ManyToOne

Связи **`@ManyToOne`** («многие к одному») и **`@OneToMany`** («один ко многим») являются самым распространенным способом моделирования реляционных ассоциаций в JPA и Hibernate. Ошибки в их настройке — наиболее частая причина деградации производительности в корпоративных приложениях: от скрытой проблемы $N+1$ и паразитных промежуточных таблиц (Join Tables) до падений JVM из-за раздувания коллекций в оперативной памяти.

---

## 🟢 Junior Level

### Кто кем владеет: Владелец связи (Owning Side) и Обратная сторона (Inverse Side)

В реляционных базах данных внешний ключ (**Foreign Key, FK**) физически всегда хранится **в таблице на стороне «многие»** (`order_items.order_id` ссылается на `orders.id`).

В JPA это разделение строго отражается в коде:
- **`@ManyToOne` — Владелец связи (Owning Side):** Находится в дочерней сущности. Именно эта сторона управляет физической колонкой внешнего ключа через `@JoinColumn`.
- **`@OneToMany` — Обратная сторона (Inverse Side):** Находится в родительской сущности. Она лишь ссылается на поле владельца через атрибут **`mappedBy`** и сама колонкой FK не управляет.

```java
// 1. Владелец связи (Child): содержит физический FK 'order_id'
@Entity
@Table(name = "order_items")
public class OrderItem {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // ВНИМАНИЕ: По умолчанию в JPA fetch = EAGER! Всегда явно указываем LAZY!
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id", nullable = false)
    private Order order;
}

// 2. Обратная сторона (Parent): mappedBy указывает на имя Java-поля 'order' в OrderItem
@Entity
@Table(name = "orders")
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>(); // Всегда инициализируем коллекцию!
}
```

### 3 критических правила Junior-уровня

1. **`FetchType.LAZY` на обеих сторонах:** `@OneToMany` по умолчанию ленивый, но `@ManyToOne` по спецификации JPA по умолчанию **`EAGER`**. Если не написать `fetch = FetchType.LAZY`, каждый запрос дочерней сущности приведет к немедленной загрузке родителя.
2. **Всегда инициализировать коллекцию:** Поле `@OneToMany` должно сразу инициализироваться пустым списком (`new ArrayList<>()`), иначе попытка добавить элемент до загрузки из БД выбросит `NullPointerException`.
3. **`mappedBy` обязателен:** Если забыть `mappedBy` на `@OneToMany`, Hibernate решит, что это связь многие-ко-многим, и автоматически создаст лишнюю связующую таблицу `orders_order_items`.

## 🟡 Middle Level

### Обязательные вспомогательные методы (Helper Methods)

В оперативной памяти JVM двунаправленная связь — это две независимые ссылки: `order.getItems()` и `item.getOrder()`. Механизм Dirty Checking Hibernate анализирует **только сторону владельца (`@ManyToOne`)**.

Если добавить элемент в коллекцию родителя, но забыть проставить обратную ссылку:
```java
// ❌ ГРУБАЯ ОШИБКА:
Order order = new Order();
OrderItem item = new OrderItem();
order.getItems().add(item); 
// item.getOrder() остался null! В БД уйдет order_id = NULL!
```

Чтобы исключить рассинхронизацию, родительская сущность должна инкапсулировать управление связью в единых хелпер-методах:

```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    // Хелпер добавления (синхронизирует обе стороны):
    public void addItem(OrderItem item) {
        this.items.add(item);
        item.setOrder(this);
    }

    // Хелпер удаления:
    public void removeItem(OrderItem item) {
        this.items.remove(item);
        item.setOrder(null);
    }
}
```

```java
// Использование в сервисе:
Order order = new Order();
order.addItem(new OrderItem("Товар 1")); // Обе стороны гарантированно согласованы!
entityManager.persist(order);
```

## 🔴 Senior Level

### Проблема однонаправленной связи `@OneToMany` (Unidirectional @OneToMany)

Иногда разработчики не хотят объявлять поле `@ManyToOne` в дочернем объекте и делают однонаправленную связь:

```java
// Кажущаяся простота: только родитель знает о детях
@Entity
public class Order {
    @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)
    @JoinColumn(name = "order_id") // Без mappedBy!
    private List<OrderItem> items = new ArrayList<>();
}
```

#### Скрытая катастрофа производительности (Лишний UPDATE):
Поскольку дочерний класс `OrderItem` ничего не знает о поле `order_id`, Hibernate при сохранении заказа выполняет следующую последовательность SQL:
1. `INSERT INTO orders ...` (сохраняет родителя).
2. `INSERT INTO order_items (name) VALUES ('Товар 1');` (вставляет дочернюю строку **с `order_id = NULL`**!).
3. `UPDATE order_items SET order_id = ? WHERE id = ?;` (**лишний UPDATE** для проставления внешнего ключа!).

Если в заказе 100 позиций, вместо 100 вставок Hibernate выполнит **100 INSERT + 100 дополнительных UPDATE**, нагружая журнал транзакций СУБД.
*Senior-стандарт:* Однонаправленных `@OneToMany` следует избегать. Всегда использовать либо двунаправленную связь с `mappedBy`, либо однонаправленный `@ManyToOne` со стороны ребенка.

```
            СРАВНЕНИЕ ГЕНЕРАЦИИ SQL ПРИ ВСТАВКЕ ЭЛЕМЕНТА
            
   1. Unidirectional @OneToMany (@JoinColumn):
      • SQL 1: INSERT INTO order_items (name) VALUES ('Item'); (FK is null!)
      • SQL 2: UPDATE order_items SET order_id = 1 WHERE id = 10; ──[ЛИШНИЙ UPDATE!]

   2. Bidirectional @ManyToOne + @OneToMany(mappedBy):
      • SQL 1: INSERT INTO order_items (order_id, name) VALUES (1, 'Item');
      (Сразу со значением внешнего ключа! Лишних запросов нет).
```

### Проблема высокой кардинальности (High-Cardinality Collections)

Что произойдет, если смаппить коллекцию с миллионом дочерних записей?
```java
@Entity
public class Company {
    @Id
    private Long id;

    // ❌ АРХИТЕКТУРНЫЙ КРАХ: У компании может быть 100 000 сотрудников!
    @OneToMany(mappedBy = "company")
    private List<Employee> employees = new ArrayList<>();
}
```

**Последствия в Production:**
1. Стоит вызвать `company.getEmployees().size()`, и Hibernate попытается материализовать 100 000 Java-объектов в кучу JVM, мгновенно вызвав `OutOfMemoryError`.
2. Невозможно применить пагинацию (`limit` / `offset`) к геттеру коллекции.

**DDD-решение (Domain-Driven Design):**
Полностью **удалить коллекцию `@OneToMany`** из класса `Company`. Связь должна остаться строго однонаправленной со стороны ребенка:
```java
@Entity
public class Employee {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "company_id")
    private Company company;
}
```
А выборку сотрудников осуществлять через Spring Data репозиторий с постраничным разбиением:
```java
public interface EmployeeRepository extends JpaRepository<Employee, Long> {
    Page<Employee> findByCompanyId(Long companyId, Pageable pageable);
}
```

## 4 Tricky Questions

### 1. Почему по спецификации JPA аннотация `@ManyToOne` по умолчанию имеет `FetchType.EAGER`, и к каким последствиям при выборке списка сущностей это приводит?

**Ответ:**
1. Исторически разработчики спецификации JPA посчитали, что одиночный связанный объект «легче» коллекции, и сделали дефолтом `EAGER`.
2. Если мы выполним JPQL-запрос `entityManager.createQuery("SELECT o FROM Order o", Order.class).getResultList()`, Hibernate загрузит список заказов.
3. Но поскольку связь `@ManyToOne User user` по умолчанию жадная, для каждого из $N$ заказов Hibernate выполнит отдельный SQL `SELECT * FROM users WHERE id = ?`.
4. Это порождает классическую катастрофу **$N+1$ запросов** прямо «из коробки».
5. **Правило:** Абсолютно каждый `@ManyToOne` в проекте обязан иметь явный `fetch = FetchType.LAZY`.

### 2. Что произойдет, если в двунаправленной связи мы добавили ребенка в коллекцию `order.getItems().add(item)`, но НЕ вызвали `item.setOrder(order)`, и сохранили заказ через `entityManager.persist(order)`?

**Ответ:**
1. Так как на связи стоит `mappedBy = "order"`, Hibernate при сбросе изменений в БД проверяет **только состояние полей сущности `OrderItem`**.
2. В поле `item.order` содержится `null`.
3. Hibernate сгенерирует `INSERT INTO order_items (order_id, ...) VALUES (NULL, ...)`.
4. Если в таблице колонка `order_id` помечена как `NOT NULL`, СУБД немедленно выбросит ошибку:
   `DataIntegrityViolationException: column "order_id" violates not-null constraint`.

### 3. Почему использование `java.util.Set` вместо `java.util.List` для `@OneToMany` связей предотвращает декартово произведение (Cartesian Product), но требует предельной аккуратности с `equals()` и `hashCode()`?

**Ответ:**
1. Если сущность загружает две коллекции `List` одновременно через `JOIN FETCH`, Hibernate выбрасывает исключение `MultipleBagFetchException` во избежание декартова умножения строк. Использование `Set` снимает это ограничение.
2. Однако сущности в `Set` идентифицируются по `equals()` и `hashCode()`. Если у сущности еще не сгенерирован ID (`id == null`), некорректная реализация `equals` (сравнивающая по полям или дефолтный `Object.hashCode()`) приведет к тому, что коллекция посчитает два разных несохраненных объекта дубликатами и потеряет один из них при добавлении в `Set`.

### 4. Можно ли использовать `@JoinColumn` одновременно с атрибутом `mappedBy` в одной аннотации `@OneToMany`?

**Ответ:**
1. **Категорически нет.** Эти атрибуты являются взаимоисключающими.
2. `mappedBy` сообщает: *«Я не управляю внешним ключом, смотри на поле в связанном классе»*.
3. `@JoinColumn` сообщает: *«Я управляю внешним ключом, вот имя физической колонки в таблице»*.
4. Попытка указать их одновременно приведет к исключению инициализации метамодели Hibernate:
   `org.hibernate.AnnotationException: Association has both mappedBy and @JoinColumn: com.example.Order.items`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «В связях `@ManyToOne` и `@OneToMany` владельцем внешнего ключа всегда является сторона `@ManyToOne` (дочерняя сущность). Сторона `@OneToMany` является обратной и обязана объявлять атрибут `mappedBy`. Критическое правило: `@ManyToOne` всегда должен быть `FetchType.LAZY`, так как по умолчанию в JPA он `EAGER`, что провоцирует проблему N+1. Для двунаправленных связей обязательны синхронизирующие хелпер-методы (`addItem`/`removeItem`), иначе внешний ключ в БД запишется как `NULL`. Однонаправленных `@OneToMany` без mappedBy следует избегать из-за лишних SQL `UPDATE`, а для высококардинальных связей (тысячи детей) коллекцию `@OneToMany` нужно удалять из модели и использовать репозитории с пагинацией».

### Ключевые метрики для Production-мониторинга
- **Количество SELECT при загрузке единичных сущностей**: проверка отсутствия забытых `EAGER` на `@ManyToOne`.
- **Количество UPDATE сразу после INSERT**: выявление неоптимальных однонаправленных связей `@OneToMany`.

### Красные флаги (Чего говорить НЕЛЬЗЯ)
- ❌ *«@ManyToOne по умолчанию ленивый, как и @OneToMany»* — Грубая ошибка. `@ManyToOne` по спецификации JPA по умолчанию `EAGER`!
- ❌ *«mappedBy можно указывать на аннотации @ManyToOne»* — У `@ManyToOne` нет атрибута `mappedBy`, он есть только на обратной стороне.
- ❌ *«Чтобы добавить ребенка, достаточно просто вызвать order.getItems().add(item)»* — В БД запишется `NULL`, если не вызвать `item.setOrder(order)`.
- ❌ *«Я храню список из 50 000 комментариев прямо в коллекции @OneToMany сущности Post»* — Это гарантированный `OutOfMemoryError` в проде.
