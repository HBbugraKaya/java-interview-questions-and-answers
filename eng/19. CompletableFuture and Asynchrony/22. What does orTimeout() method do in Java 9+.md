# What does orTimeout() method do in Java 9+

---

## 🟢 Junior Level

The **`orTimeout(long timeout, TimeUnit unit)`** method, introduced in Java 9, sets a non-blocking timeout deadline on an asynchronous `CompletableFuture`.

If the computation does not complete within the allotted duration, the `CompletableFuture` is **forcibly transitioned into an exceptional completion state with a `java.util.concurrent.TimeoutException`**.

### Basic Usage

```java
CompletableFuture<String> paymentFuture = paymentClient.chargeAsync(orderId);

// Limit payment processing window to 2 seconds:
paymentFuture.orTimeout(2, TimeUnit.SECONDS)
    .thenAccept(receipt -> System.out.println("Payment processed: " + receipt))
    .exceptionally(ex -> {
        // If 2 seconds elapse before completion, execution routes here:
        // ex.getCause() contains TimeoutException
        System.err.println("Payment timed out: " + ex.getMessage());
        return null;
    });
```

### Comparison with `completeOnTimeout()`

| Method | Outcome on Timeout Expiry | Primary Use Case |
| :--- | :--- | :--- |
| **`orTimeout(timeout, unit)`** | Throws **`TimeoutException`** | Critical operations (payments, orders, mutations) |
| **`completeOnTimeout(fallback, timeout, unit)`** | Completes successfully with **`fallback`** | Optional data (recommendations, cached profile) |

## 🟡 Middle Level

### Key Architectural Invariant: `orTimeout()` Returns `this`

Unlike transformation methods (`thenApply`, `thenCompose`) that create a new dependent stage node in the completion graph, `orTimeout()`:
- **Mutates the current instance** in-place and returns a reference to itself (`return this`).
- The timer callback is registered directly on the target object.
- If multiple `orTimeout()` calls are chained on the same `CompletableFuture` with varying durations, the **shortest timeout wins** because the first timer that fires completes the future via an atomic CAS operation.

### Exception Wrapping and Propagation

The resulting `TimeoutException` is wrapped inside an unchecked `CompletionException`:

```java
future.orTimeout(500, TimeUnit.MILLISECONDS)
    .handle((res, ex) -> {
        if (ex != null) {
            Throwable root = (ex instanceof CompletionException) ? ex.getCause() : ex;
            if (root instanceof TimeoutException) {
                log.warn("Downstream service timed out, activating fallback");
                return getFallbackData();
            }
            throw new CompletionException(ex);
        }
        return res;
    });
```

## 🔴 Senior Level

### HotSpot JVM Internals: The `Delayer` Architecture

Under the hood, `orTimeout()` does not create an operating system thread per request:
1. OpenJDK initializes a private singleton class `Delayer`:
   ```java
   static final class Delayer {
       static final ScheduledThreadPoolExecutor delayer;
       static {
           (delayer = new ScheduledThreadPoolExecutor(
               1, new DaemonThreadFactory())).setRemoveOnCancelPolicy(true);
       }
   }
   ```
2. The `orTimeout()` method enqueues a lightweight task into `delayer`:
   ```java
   delayer.schedule(new Timeout(this), timeout, unit);
   ```
3. When the scheduled delay expires, `Timeout` executes:
   ```java
   public void run() {
       if (f != null && !f.isDone())
           f.completeExceptionally(new TimeoutException());
   }
   ```
4. **Memory Leak Prevention**: `orTimeout` immediately registers an internal `Canceller` listener via `whenComplete`. If the target computation finishes normally in 10 ms under a 60 s timeout, `Canceller` calls `scheduledFuture.cancel(false)`. The `setRemoveOnCancelPolicy(true)` setting guarantees immediate eviction of the cancelled node from the scheduler's internal priority queue.

### Fatal Hazard: Blocking the JVM-Wide `Delayer` Thread

When a timeout expires, `Timeout.run()` executes **directly inside the single JVM-wide `Delayer` thread**.
If an immediate synchronous handler is registered after `orTimeout`:
```java
// CATASTROPHIC HAZARD FOR THE ENTIRE JVM:
future.orTimeout(1, TimeUnit.SECONDS)
    .exceptionally(ex -> {
        // Runs INSIDE the single shared Delayer thread!
        Thread.sleep(5000); // Freezes Delayer for 5 seconds!
        return fallback;
    });
```
Any blocking I/O, heavy calculation, or sleep inside this callback **blocks the global timer thread**. While it is blocked, no other `orTimeout()` or `completeOnTimeout()` timer across the entire application can fire!
*Remedy*: Always offload heavy error handling using `handleAsync(..., customExecutor)` or Java 12+ `exceptionallyAsync(..., customExecutor)`.

## 4 Tricky Questions

### 1. In which thread does the lambda inside `.exceptionally(...)` execute if `.orTimeout()` triggers?

**Answer:**
It executes **inside the single background thread of `CompletableFuture$Delayer`**!
When the timeout elapses, the scheduled task `Timeout.run()` runs on the `Delayer` daemon thread and invokes `completeExceptionally()`. This immediately unpacks the dependency stack and executes synchronous callbacks on the current thread (the `Delayer` thread). If this callback blocks or runs long-running computations, it starves the global timer scheduler for all threads in the JVM. To isolate it, use `handleAsync(..., dedicatedExecutor)` or `exceptionallyAsync(...)`.

### 2. Does `orTimeout()` cancel or interrupt the physical background worker task when it triggers?

**Answer:**
**No, it does not.**
`orTimeout()` strictly alters the state of the `CompletableFuture` object by transitioning it into an exceptionally completed state (`TimeoutException`). The worker thread running the background task (such as a slow SQL query or HTTP call) continues running until it finishes. To truly stop the workload, you must hook into the timeout event and explicitly cancel underlying resources (e.g., closing the network socket or interrupting the thread).

### 3. What happens if you call `cf.orTimeout(5, SECONDS)` and then `cf.orTimeout(2, SECONDS)` on the same instance?

**Answer:**
The **2-second timeout triggers**.
Both timer tasks are scheduled in the `Delayer` priority queue. After 2 seconds, the second task executes and transitions the future into `TimeoutException` via an atomic CAS operation. When the 5-second task fires later, it checks `f.isDone()`, sees that the future is already completed, and terminates as a no-op.

### 4. Does `orTimeout()` return a new CompletableFuture stage or modify the existing instance?

**Answer:**
It **mutates the existing instance and returns `this`**.
Unlike transformation methods such as `thenApply()` or `thenCompose()` which construct new downstream DAG nodes, `orTimeout()` is defined as:
```java
public CompletableFuture<T> orTimeout(long timeout, TimeUnit unit) {
    if (unit == null) throw new NullPointerException();
    if (result == null)
        whenComplete(new Canceller(Delayer.delay(new Timeout(this), timeout, unit)));
    return this;
}
```
This means the timeout is attached directly to the current future, and references to `this` will reflect that same timeout behavior.

## 🎯 Interview Cheat Sheet

### Summary in 60 Seconds
- Added in Java 9. Transitions `CompletableFuture` into `TimeoutException` if the deadline expires.
- Modifies the future in-place and returns `this`.
- Relies on a **single JVM-wide daemon thread** (`ScheduledThreadPoolExecutor` in `Delayer`), keeping resource overhead minimal.
- Automatically purges timer tasks on early completion via `setRemoveOnCancelPolicy(true)`.
- **Critical Trap**: Synchronous callbacks following a timeout execute inside the single `Delayer` thread; never perform blocking operations inside them.
- Timeouts do not interrupt or terminate the underlying thread pool worker task.

### Common Interview Traps
- Assuming `orTimeout()` was available in Java 8 (it was added in Java 9).
- Believing `orTimeout()` returns a new downstream future rather than mutating `this`.
- Performing blocking I/O or sleep inside a synchronous `.exceptionally()` chained after `orTimeout`.
