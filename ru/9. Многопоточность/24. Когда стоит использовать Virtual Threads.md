# Когда стоит использовать Virtual Threads

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**Virtual Threads (виртуальные потоки)** следует использовать тогда и только тогда, когда рабочая нагрузка является преимущественно **I/O-bound (ограничена операциями ввода-вывода)** и характеризуется **высоким уровнем параллелизма (High Concurrency)** — сотни, тысячи или миллионы одновременных задач. Типичные сценарии: веб-серверы, REST/gRPC API-шлюзы, микросервисы-оркестраторы, веб-краулеры и интеграционные сервисы, проводящие большую часть времени в ожидании ответов от сети, базы данных или очередей сообщений.

Виртуальные потоки **НЕ следует использовать** для:
1. **CPU-bound задач** (криптография, видеокодирование, машинное обучение, расчет матриц) — здесь виртуальный поток не размонтируется и создает лишь паразитные накладные расходы для планировщика JVM;
2. Систем с **низким уровнем параллелизма** (десятки запросов в минуту), где разница незаметна;
3. Legacy-систем с повсеместным использованием `synchronized` вокруг блокирующего ввода-вывода (из-за эффекта **Pinning**).

---

### Матрица применимости Virtual Threads

| Тип рабочей нагрузки / Сценарий | Использовать Virtual Threads? | Рекомендуемое решение | Почему |
|---|---|---|---|
| **Микросервис / REST API (I/O-bound)** | ✅ **Да (Идеально)** | `Thread-per-request` (Java 21) | Потоки дешевы, код простой и линейный |
| **API Gateway / Проксирование HTTP** | ✅ **Да (Идеально)** | `VirtualThreadPerTaskExecutor` | Огромный throughput при минимальном RAM |
| **Парсинг веб-сайтов (Web Scraping)** | ✅ **Да (Идеально)** | Virtual Threads + HTTP Client | Тысячи одновременных сетевых соединений |
| **Расчет криптографии / Хеширование** | ❌ **Нет** | `Executors.newFixedThreadPool(N)` | CPU-bound: ядра процессора загружены на 100% |
| **Рендеринг видео / Сжатие ZIP** | ❌ **Нет** | ForkJoinPool / FixedThreadPool | Нет точек блокировки для unmount |
| **GUI Event Loop (JavaFX, Swing)** | ❌ **Нет** | Единый Dedicated Event Thread | Нарушает архитектуру графической очереди |
| **Оркестрация параллельных запросов** | ⚠️ **Да, с лимитом** | Virtual Threads + `Semaphore` | Нужна защита внешних API и БД от перегрузки |

### Пример на Java 21: Параллельный микросервисный агрегатор

```java
import java.util.concurrent.Executors;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.URI;
import java.time.Duration;

public class MicroserviceAggregator {

    private final HttpClient httpClient = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(2))
            .build();

    // Идеальный кейс для Virtual Threads: веерный опрос 1 000 поставщиков
    public void aggregateSuppliersData() {
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 1; i <= 1_000; i++) {
                final int supplierId = i;
                executor.submit(() -> {
                    fetchSupplierCatalog(supplierId);
                });
            }
        } // Блок try автоматически дожидается завершения всех 1 000 виртуальных потоков!
    }

    private void fetchSupplierCatalog(int supplierId) {
        try {
            var request = HttpRequest.newBuilder()
                    .uri(URI.create("https://api.supplier" + supplierId + ".internal/catalog"))
                    .GET()
                    .build();

            // Блокирующий вызов сокета: виртуальный поток размонтируется!
            HttpResponse<String> response = httpClient.send(request, HttpResponse.BodyHandlers.ofString());
            System.out.println("Каталог " + supplierId + " получен, статус: " + response.statusCode());
        } catch (Exception e) {
            System.err.println("Ошибка опроса поставщика " + supplierId + ": " + e.getMessage());
        }
    }
}
```

## 🟡 Middle Level

### Интеграция в Spring Boot 3.2+: Магия одной строки

Начиная со Spring Boot 3.2 и Spring Framework 6.1, поддержка виртуальных потоков встроена в ядро:

```yaml
# application.yml
spring:
  threads:
    virtual:
      enabled: true
```

#### Что происходит под капотом при включении флага:
1. **Встроенный веб-сервер (Tomcat / Jetty):** стандартный пул потоков (`ThreadPoolExecutor` на 200 потоков) заменяется на `Executors.newVirtualThreadPerTaskExecutor()`. Каждый входящий HTTP-запрос теперь исполняется в изолированном виртуальном потоке.
2. **Асинхронные методы (`@Async`):** автоматически используют планировщик виртуальных потоков.
3. **Планировщик задач (`@Scheduled`):** запускает задачи на виртуальных потоках.
4. **Spring MVC:** традиционные блокирующие контроллеры приобретают производительность реактивного WebFlux без необходимости изменения сигнатур методов.

### Защита дефицитных ресурсов: Throttling через Semaphore

Раньше пул потоков непреднамеренно выполнял роль «предохранителя»: если в Tomcat было 200 потоков, сервер физически не мог отправить в базу данных более 200 одновременных запросов.

С виртуальными потоками этот ограничитель исчезает. Если на сервер поступит 50 000 запросов, они создадут 50 000 виртуальных потоков, которые одновременно обратятся к пулу HikariCP (размером, например, 30 соединений). Это мгновенно приведет к `ConnectionTimeoutException` и отказу базы данных.

```java
import java.util.concurrent.Semaphore;

public class DatabaseThrottlingService {

    // Пул БД вмещает 20 соединений. Ограничиваем конкурентный доступ 20 разрешениями:
    private final Semaphore dbSemaphore = new Semaphore(20);

    public String queryOrderDetails(long orderId) {
        try {
            // Ждем свободного слота. Вызов acquire() размонтирует виртуальный поток!
            dbSemaphore.acquire();
            try {
                return executeJdbcCall(orderId);
            } finally {
                dbSemaphore.release();
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("Запрос прерван", e);
        }
    }

    private String executeJdbcCall(long orderId) {
        // Блокирующий вызов через HikariCP + PostgreSQL JDBC Driver
        return "OrderDetails_" + orderId;
    }
}
```

### Аудит зависимостей на совместимость с Project Loom

Перед включением виртуальных потоков в production Senior-разработчик обязан провести аудит сторонних библиотек на предмет **Carrier Pinning**:

```bash
# Флаг JVM для трассировки пригвождения потоков в процессе тестирования:
java -Djdk.tracePinnedThreads=full -jar app.jar
```

#### Зоны риска в устаревших библиотеках:
1. **Старые JDBC драйверы:** версии MySQL Connector/J до 8.0.33 содержали методы `synchronized` на уровне сокетов. Современные версии (MySQL 8.3+, PostgreSQL 42.6+) очищены от проблемных мониторов.
2. **Классический `SimpleDateFormat`:** является потоконебезопасным и часто оборачивался разработчиками в `synchronized(lock)`. Следует перейти на потокобезопасный `java.time.format.DateTimeFormatter`.
3. **In-Memory кэши и пулы:** старые реализации пулов объектов (например, Apache Commons Pool версий 1.x) блокировали мониторы при ожидании ресурсов.

## 🔴 Senior Level

### Гибридная модель многозадачности (Hybrid Concurrency Architecture)

В реальных Enterprise-приложениях чистый I/O часто перемежается с интенсивными вычислениями. Назначение виртуальных потоков на CPU-bound расчеты приводит к **голоданию несущих потоков (Carrier Starvation)**:

```
                          [ Входящий HTTP-запрос ]
                                     │
                     (Обработка на Virtual Thread)
                                     │
              ┌──────────────────────┴──────────────────────┐
              ▼                                             ▼
       [ Сетевой I/O ]                             [ CPU-bound Задача ]
  (БД, внешний микросервис)                      (Генерация PDF, крипта)
              │                                             │
    (Unmount VT в кучу,                             (Делегирование в
    Carrier поток свободен)                      Dedicated FixedThreadPool)
                                                            │
                                              (Ожидание Future.get() на VT,
                                                 VT снова размонтируется!)
```

#### Паттерн делегирования тяжелых вычислений:

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class HybridOrderService {

    // Пул для CPU-bound задач строго по числу физических ядер:
    private static final ExecutorService CPU_INTENSIVE_POOL = 
            Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());

    public void processClientRequest() throws Exception {
        // 1. Быстрый сетевой I/O — выполняется прямо на Virtual Thread:
        String data = fetchRemoteData();

        // 2. Тяжелая криптографическая подпись (CPU-bound) — делегируется в CPU-пул:
        var future = CPU_INTENSIVE_POOL.submit(() -> computeCryptographicSignature(data));

        // 3. Ожидание результата future.get() на Virtual Thread РАЗМОНТИРУЕТ поток!
        // Carrier Thread освобождается, а CPU-ядра безопасно загружаются выделенным пулом:
        byte[] signature = future.get();

        // 4. Запись в БД (I/O) — снова на виртуальном потоке:
        saveToDatabase(signature);
    }

    private String fetchRemoteData() { return "Data"; }
    private byte[] computeCryptographicSignature(String data) { return new byte[0]; }
    private void saveToDatabase(byte[] sig) {}
}
```

### Анализ давления на сборщик мусора (GC Footprint Analysis)

Хотя стек виртуального потока дешев, создание 100 000 виртуальных потоков в секунду генерирует огромный поток короткоживущих объектов `StackChunk` и внутренних дескрипторов задач:

1. **Young Generation TLAB:** каждый Carrier Thread аллоцирует фреймы виртуальных потоков в своем Thread-Local Allocation Buffer (TLAB). Высокая частота создания/уничтожения потоков приводит к быстрому заполнению Eden-пространства.
2. **Выбор GC:** для приложений с массивным использованием виртуальных потоков настоятельно рекомендуется использовать **Generational ZGC** (Java 21+: `-XX:+UseZGC -XX:+ZGenerational`) либо современный **G1 GC**. Они минимизируют паузы Stop-The-World (STW) до субмиллисекундного диапазона даже при гигабайтных скоростях аллокации стеков.

## 🎯 Шпаргалка для интервью

### 1. 30-секундный эссенс (Elevator Pitch)
Виртуальные потоки в Java 21 предназначены для **высококонкурентных I/O-bound систем** (веб-серверы, API-шлюзы, микросервисы, интеграционные платформы), где потоки проводят львиную долю времени в ожидании внешних ответов. Они позволяют вернуться к модели Thread-per-Task вместо сложной реактивности. Виртуальные потоки **противопоказаны для CPU-bound вычислений** (где они создают оверхед без размонтирования), систем с низкой нагрузкой и legacy-кода с повсеместным `synchronized` вокруг блокирующих сокетов. Для защиты баз данных и внешних API от лавины виртуальных потоков обязательно используется `Semaphore`.

### 2. 4 каверзных вопроса с глубокими ответами

#### Вопрос 1: Что произойдет с пулом соединений HikariCP (20 соединений), если включить `spring.threads.virtual.enabled=true` и на сервис придет всплеск из 100 000 RPS?
**Ответ:**
Если не предпринять защитных мер, Tomcat создаст 100 000 виртуальных потоков, и все они одновременно запросят соединение у `HikariDataSource.getConnection()`. Пул HikariCP моментально исчерпает 20 доступных коннектов, а оставшиеся 99 980 потоков выстроятся в очередь ожидания таймаута (`connectionTimeout`, по умолчанию 30 сек). Через 30 секунд сервис захлебнется сотнями тысяч исключений `SQLTransientConnectionException: Connection is not available, request timed out`.  
*Архитектурное решение:* ограничить параллельный вход в секцию обращения к БД через `Semaphore(20)` или настроить внешний Rate Limiter на уровне Ingress/API Gateway.

#### Вопрос 2: Почему для задач машинного обучения, шифрования или сжатия данных использование виртуальных потоков ухудшает производительность по сравнению с `FixedThreadPool`?
**Ответ:**
Виртуальный поток освобождает процессорное ядро только в точках прерывания (кооперативная многозадачность при I/O или явных блокировках). В CPU-bound алгоритмах точек размонтирования нет: поток занимает Carrier Thread на 100% времени. Если запустить тысячи таких задач на виртуальных потоках, рантайм JVM будет тратить память на аллокацию сотен тысяч объектов `Thread` и `StackChunk` в Heap, перегружая сборщик мусора и очередь планировщика ForkJoinPool, не имея возможности выполнить больше вычислений, чем позволяет физическое число процессорных ядер.

#### Вопрос 3: Как организовать гибридную архитектуру сервиса, если один запрос требует и долгого сетевого вызова, и тяжелой криптографической обработки?
**Ответ:**
Применяется разделение ответственности (Hybrid Model): входящий запрос обрабатывается в виртуальном потоке, который выполняет ввод-вывод (чтение данных по сети, обращение к БД). Когда наступает фаза тяжелых вычислений, задача передается в выделенный пул потоков платформы `Executors.newFixedThreadPool(N)` (где $N$ равно числу ядер CPU). Виртуальный поток вызывает `future.get()` на задаче из CPU-пула. При вызове `get()` виртуальный поток корректно **размонтируется**, освобождая Carrier Thread до тех пор, пока вычисление в CPU-пуле не завершится.

#### Вопрос 4: Как флаг `-Djdk.tracePinnedThreads` и JFR-события помогают выявить скрытое блокирование Carrier Threads в сторонних библиотеках?
**Ответ:**
При передаче аргумента `-Djdk.tracePinnedThreads=full` JVM выводит в `stderr` полный стектрейс каждый раз, когда виртуальный поток блокируется внутри нативного метода или `synchronized`-блока, указывая точный класс и номер строки кода библиотеки.  
В production-окружении для этого используется Java Flight Recorder (JFR) без деградации производительности: фильтрация события `jdk.VirtualThreadPinned` с порогом длительности (`threshold=20ms`) позволяет в реальном времени мониторить проблемные места через Prometheus/Grafana или JDK Mission Control.

### 3. Типичные ошибки и Red Flags

❌ **"Включение виртуальных потоков решит проблемы медленной базы данных."**  
*Правильно:* Виртуальные потоки разгружают сервер от удержания памяти потоков ОС, но если SQL-запрос выполняется медленно, виртуальный поток просто будет дольше ждать. Без оптимизации индексов и запросов лавина виртуальных потоков лишь быстрее перегрузит СУБД.

❌ **"Использование пула виртуальных потоков вместо создания новых."**  
*Правильно:* Виртуальные потоки не должны пулиться. Их жизненный цикл краток: создание $\to$ выполнение задачи $\to$ удаление сборщиком мусора.

❌ **"Замена всех пулов потоков в приложении на виртуальные потоки без разбора."**  
*Правильно:* Пулы для CPU-bound задач обязаны оставаться `FixedThreadPool` на потоках платформы.
