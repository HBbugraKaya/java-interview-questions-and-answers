# Какие GC минимизируют stop-the-world паузы

---

## 🟢 Junior Level

Сборщики мусора со сверхнизкими задержками (**Low-Latency Garbage Collectors**) — это специализированные алгоритмы JVM, спроектированные для минимизации или практического устранения пауз **Stop-The-World (STW)**.

В современных микросервисах и веб-приложениях время отклика оценивается по жестким соглашениям об уровне сервиса (**SLA**) и процентилям задержки (**p99 / p99.9**). Если обычный GC ставит приложение на паузу на 500 мс, запросы клиентов встают в очередь, таймауты рвутся, а балансировщики начинают отключать узлы кластера.

---

### Топ-3 сборщика мусора для минимизации пауз:

1. **ZGC (Z Garbage Collector):**
   - **Паузы:** Гарантированно **$< 1$ мс** (в современных версиях обычно 0.1–0.4 мс).
   - **Размер кучи:** От 16 МБ до 16 Терабайт. Длительность пауз **не зависит** от размера кучи!
2. **Shenandoah GC:**
   - **Паузы:** Конкурентный сборщик от Red Hat с паузами **1–10 мс** (в последних версиях — до долей миллисекунды).
   - Поддерживает сжатые указатели (**Compressed OOPs**) на кучах до 32 ГБ.
3. **G1 GC (Garbage-First):**
   - **Паузы:** Настраиваемые мягкие паузы в диапазоне **20–200 мс** (`-XX:MaxGCPauseMillis=200`).
   - Компромиссный выбор по умолчанию в Java 9+, сочетающий высокую пропускную способность и контролируемые паузы.

---

### В чем секрет ультранизких пауз?
Традиционные сборщики мусора останавливают приложение на самую долгую фазу — **эвакуацию (перемещение) живых объектов** на новое место памяти. 

Сборщики **ZGC** и **Shenandoah** перемещают объекты **конкурентно (Concurrent Evacuation)** — в фоновых потоках, пока прикладные потоки продолжают исполнять бизнес-код. Потоки приложения останавливаются лишь на доли миллисекунды для быстрого сканирования корней GC Roots.

### Опасность: Сбой аллокации (Allocation Stall)

В сборщиках с конкурентным уплотнением (ZGC, Shenandoah) кроется опасная ловушка:
- Приложение генерирует объекты с огромной скоростью (**High Allocation Rate**).
- Фоновый сборщик мусора не успевает закончить разметку и эвакуацию до того, как свободная память исчерпается.
- **Allocation Stall:** Поток приложения, вызвавший `new Object()`, не может получить память. JVM **принудительно усыпляет поток** или заставляет его самостоятельно участвовать в эвакуации.
- *Результат:* Задержка ответа конкретного потока подскакивает на сотни миллисекунд, нарушая весь смысл использования low-latency GC!

---

### Спасение производительности: Поколенческие ZGC и Shenandoah в Java 21+

До Java 21 и ZGC, и Shenandoah были однопоколенными (Single-Generational), сканируя всю кучу целиком при каждом цикле.

В Java 21+ оба сборщика получили поколенческую архитектуру:
- **Generational ZGC (`-XX:+ZGenerational`):** Молодое поколение собирается в десятки раз чаще и быстрее. Нагрузка на ядра CPU снижена на **50%**, а риск Allocation Stall практически сведен к нулю.
- **Generational Shenandoah:** Аналогично фокусирует процессорное время на умирающих короткоживущих объектах.

## 🔴 Senior Level

### Физика накладных расходов: Барьеры записи против Барьеров чтения

Причина, по которой ZGC и Shenandoah уступают G1 по чистой пропускной способности (Throughput) на 5–15%, заключается в типе используемых барьеров:

```
┌────────────────────────────────────────────────────────┐
│ 1. Write Barrier (G1 GC):                              │
│    Срабатывает ТОЛЬКО при ЗАПИСИ: a.field = b;         │
│    Операций записи в коде всего ~10% от всех обращений │
│    Оверхед: ~1-2 такта процессора                      │
├────────────────────────────────────────────────────────┤
│ 2. Load Barrier (ZGC / Shenandoah):                    │
│    Срабатывает при КАЖДОМ ЧТЕНИИ ссылки: b = a.field;  │
│    Операций чтения в коде свыше ~90%!                  │
│    Оверхед: проверка битов цвета указателя (Colored)   │
│    и запуск Self-Healing при необходимости             │
└────────────────────────────────────────────────────────┘
```
Поскольку операции чтения ссылок в реальном бизнес-коде происходят в разы чаще операций записи, Load Barriers непрерывно утилизируют 5–15% мощностей CPU.

---

### Архитектурная матрица выбора: Когда НЕЛЬЗЯ использовать Low-Latency GC

Выбор ZGC или Shenandoah не должен быть «модным решением по умолчанию». Есть сценарии, где они строго противопоказаны:

1. **CPU-bound нагрузки:** Если процессор сервера уже утилизирован на 80–90% (криптография, сжатие, тяжелая математика), дополнительные 10–15% оверхеда на барьеры чтения приведут к деградации производительности всего сервиса.
2. **Пакетная обработка данных (Batch / ETL / Big Data):** Если сервис считает ночной расчет зарплат или строит отчет в Hadoop, время пауз никого не волнует. Главная метрика — время окончания задачи. **Parallel GC** выполнит расчет на 15–20% быстрее, чем ZGC.
3. **Микрокучи (< 4 ГБ RAM):** На небольших объемах памяти отсутствие сжатых указателей в ZGC раздувает ссылки с 4 до 8 байт, съедая до 30% полезного пространства. Для небольших сервисов G1 эффективнее.

---

### Рецепты тюнинга для ультранизких задержек

```bash
# 1. ZGC для жесткого SLA < 1 мс (Java 21+)
-XX:+UseZGC
-XX:+ZGenerational
-XX:ConcGCThreads=4               # Потоки для фоновой эвакуации (cores / 4)
-XX:SoftMaxHeapSize=12g           # Эластичное управление памятью в облаке
-Xmx16g -Xms16g

# 2. G1 GC для умеренного SLA 100 мс и высокого throughput
-XX:+UseG1GC
-XX:MaxGCPauseMillis=100          # Снижение дефолтной целевой паузы с 200 до 100 мс
-XX:+G1UseAdaptiveIHOP            # Адаптивный старт разметки
-XX:InitiatingHeapOccupancyPercent=45
```

## 🎯 Шпаргалка для интервью

### 30-секундный ответ (Elevator Pitch)
> «Главные сборщики мусора для минимизации пауз STW — это **ZGC** (паузы **< 1 мс** независимо от размера кучи) и **Shenandoah** (паузы **1–10 мс**), а также **G1** с настраиваемым таргетом (обычно **50–200 мс**). Сверхнизкие паузы в ZGC и Shenandoah достигаются за счет **конкурентной эвакуации (Concurrent Evacuation)**: пока приложение работает, объекты перемещаются в фоне благодаря барьерам чтения (**Load Barriers**) и цветным указателям (**Colored Pointers**). В Java 21+ переход ZGC на поколения (**Generational ZGC**) устранил проблему сбоев аллокации (**Allocation Stall**) и снизил потребление CPU. Платой за отсутствие пауз является снижение общей пропускной способности (Throughput) на 5–15%».

---

### 3–4 каверзных вопроса с ответами

1. **За счет чего ZGC и Shenandoah удерживают паузы менее 1 мс, тогда как у G1 они составляют 50–200 мс?**
   - *Ответ:* В сборщике G1 самая длинная операция — эвакуация (физическое перемещение живых объектов и обновление указателей) — выполняется во время паузы Stop-The-World. В ZGC и Shenandoah фаза эвакуации вынесена в полностью параллельный режим (Concurrent) и исполняется фоновыми потоками без остановки приложения. STW используется только для сверхкороткой фиксации корней GC Roots, занимающей доли миллисекунды.

2. **Почему барьеры чтения (Load Barriers) создают большую нагрузку на CPU, чем барьеры записи (Write Barriers)?**
   - *Ответ:* В типовом программном коде операции чтения полей объектов происходят в 5–10 раз чаще, чем операции модификации ссылок. Write Barrier в G1 срабатывает только при записи (`obj.field = value`). Load Barrier в ZGC обязан срабатывать при каждом разыменовании ссылки (`value = obj.field`), проверяя цвет указателя. Из-за огромного количества чтений постоянное выполнение машинных инструкций барьера отнимает от 5% до 15% циклов CPU.

3. **Что такое Allocation Stall в low-latency сборщиках и как с ним бороться?**
   - *Ответ:* Allocation Stall — это состояние, когда скорость генерации новых объектов приложением превышает скорость фоновой разметки и эвакуации сборщика мусора. Свободные страницы памяти заканчиваются до завершения цикла GC, в результате чего аллоцирующие потоки принудительно засыпают в ожидании освобождения памяти. Решения: переход на Generational ZGC в Java 21+, увеличение размера кучи Heap, выделение большего числа потоков сборщика (`-XX:ConcGCThreads`), либо оптимизация темпа аллокаций в коде.

4. **Почему для пакетной обработки данных (Batch Processing) выгоднее использовать Parallel GC, а не ZGC?**
   - *Ответ:* В пакетных расчетах задержки отдельных операций (Latency) не имеют значения, а критична общая скорость завершения задачи (Throughput). ZGC тратит до 15% процессорного времени на барьеры чтения и фоновые потоки эвакуации. Parallel GC не использует барьеры вовсе и отдает 100% мощности всех ядер процессора чистым вычислениям приложения, завершая пакетный расчет быстрее.

---

### Типичные ошибки и Red Flags

- 🚩 **Утверждение: «ZGC и Shenandoah полностью устраняют любые паузы STW»** (STW паузы присутствуют, но они микроскопичны: < 1 мс для сканирования GC Roots).
- 🚩 **Слепая уверенность: «ZGC бесплатный и не имеет недостатков»** (плата за паузы < 1 мс — потеря 5–15% Throughput и невозможность сжатия указателей).
- 🚩 **Использование ZGC на серверах с предельной загрузкой CPU (> 85%)** (барьеры усугубят дефицит процессорного времени).
- 🚩 **Установка `-XX:MaxGCPauseMillis=1ms` для G1 GC** (G1 не способен выдержать такую паузу и свалится в серию долгих Full GC).
