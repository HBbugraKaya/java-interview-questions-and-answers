# What are Compensating Transactions

---

## 🟢 Junior Level

A **Compensating Transaction** ($C_k$) is an explicit, forward-executing business operation that semantically reverses or neutralizes the effects of a previously committed local transaction ($T_k$) within a distributed Saga workflow.

```
Forward Execution (Success Path):
[Create Order (T1)] ──► [Charge Payment (T2)] ──► [Reserve Stock (T3): OUT OF STOCK! ❌]

Backward Compensation (Rollback Path):
[Cancel Order (C1)] ◄── [Refund Payment (C2)] ◄──┘ (Executed in strict reverse LIFO order)
```

### Key Differences from Classic SQL `ROLLBACK`

| Dimension | SQL `ROLLBACK` | Compensating Transaction ($C_k$) |
| :--- | :--- | :--- |
| **Execution Context** | Single relational database engine | Distributed across multiple microservice databases |
| **Data Visibility** | Changes were uncommitted and hidden in undo logs | Target data was **already committed** and visible to external users |
| **Database Operation** | Technical rollback discarding in-memory/WAL buffer | Brand-new `INSERT` or `UPDATE` transaction creating a corrective record |
| **Physical Mutation** | Memory/WAL state reverted prior to commit | Immutable business state update (e.g., status changed to `REFUNDED`) |
| **Order of Execution** | Internal database engine rollback | Strict reverse chronological order ($C_{k-1} \to \dots \to C_1$) |

### Real-World Operations vs Compensations

| Forward Transaction ($T_k$) | Compensating Transaction ($C_k$) |
| :--- | :--- |
| `chargeCreditCard($150)` | `refundCreditCard($150)` (new ledger refund entry) |
| `reserveInventory(productId, 5)` | `releaseInventory(productId, 5)` (increment available stock) |
| `createOrder(orderId)` | `updateOrderStatus(orderId, CANCELLED)` |
| `assignDriver(tripId, driverId)` | `unassignDriver(tripId, driverId, CANCELLED_BY_SYSTEM)` |

> [!NOTE]
> **Accounting Book Analogy:** You cannot erase pen ink from Page 1 of a physical accounting journal. Instead, accountants write a corrective credit or debit entry on Page 2. A compensating transaction is an explicit corrective ledger entry.

## 🟡 Middle Level

### 1. The Anatomy of a Saga: Three Transaction Types

In distributed systems, steps in a Saga are categorized into three distinct phases defined by the **Pivotal Transaction**:

```
[T1: Reserve Stock] ──► [T2: Apply Promo Code] ──► [T3: Charge Card (PIVOTAL)] ──► [T4: Generate Receipt]
        │                       │                                                         │
   Compensable             Compensable                        Point of No Return              Retriable
 (Has rollback C1)       (Has rollback C2)                 (Cannot be rolled back)       (Retried until success)
```

1. **Compensable Transactions:** Steps executed before the pivotal step. They can guaranteed to be rolled back semantically by executing a matching compensator ($C_k$).
2. **Pivotal Transaction:** The milestone or "point of no return". If this transaction commits, the Saga is committed to 100% completion. If it fails, the Saga aborts and triggers backward compensation ($C_{k-1} \dots C_1$). A pivotal transaction is never compensated.
3. **Retriable Transactions:** Steps executed after the pivotal step. They cannot be aborted or compensated. They must be guaranteed to eventually succeed through automated retries with exponential backoff (**Forward Recovery**).

### 2. Mandatory Rules for Compensating Transactions

#### Rule A: Strict Idempotency
Because messaging brokers (Kafka, RabbitMQ) provide **at-least-once** delivery guarantees, compensation commands may be redelivered multiple times due to network timeouts. A repeated compensation execution must never result in duplicate refunds or duplicate stock increments.

```java
@Service
@RequiredArgsConstructor
public class PaymentCompensationService {

    private final PaymentRepository paymentRepository;
    private final RefundLogRepository refundLogRepository;
    private final PaymentGatewayClient paymentGatewayClient;

    @Transactional
    public void refundPayment(UUID sagaId, UUID paymentId, BigDecimal amount) {
        // 1. Idempotency Check via Dedicated Saga Refund Log:
        if (refundLogRepository.existsBySagaId(sagaId)) {
            log.info("Saga {}: Refund for payment {} already completed. Skipping.", sagaId, paymentId);
            return;
        }

        // 2. Fetch and Lock Payment Record:
        Payment payment = paymentRepository.findByIdWithLock(paymentId)
            .orElseThrow(() -> new EntityNotFoundException("Payment not found: " + paymentId));

        if (payment.getStatus() == PaymentStatus.REFUNDED) {
            log.warn("Payment {} already marked as REFUNDED.", paymentId);
            return;
        }

        // 3. Execute Outbound Call to External Bank / Gateway:
        paymentGatewayClient.executeRefund(payment.getExternalTransactionId(), amount);

        // 4. Update Business State & Record Audit:
        payment.setStatus(PaymentStatus.REFUNDED);
        payment.setRefundedAt(Instant.now());
        paymentRepository.save(payment);

        refundLogRepository.save(new RefundLog(sagaId, paymentId, amount, Instant.now()));
    }
}
```

#### Rule B: Zero Business Validation Failures
A compensating transaction **must never fail due to business validation rules** (e.g., checking "user balance" or "account status"). All business validations must be fully verified during the forward transaction. A compensator can fail only due to transient infrastructure issues (database down, network timeout).

## 🔴 Senior Level

### 1. The Phantom Compensation (Out-of-Order Execution) Problem

In asynchronous distributed systems, network latency can cause a compensating transaction ($C_k$) to arrive and execute **before** its corresponding forward transaction ($T_k$).

**The Danger Scenario:**
1. The Orchestrator emits `HoldStock` ($T_k$) to the Inventory Service, but the packet experiences a 5-second network hiccup.
2. The Orchestrator reaches its timeout SLA (2 seconds), assumes failure, and broadcasts `ReleaseStock` ($C_k$).
3. The Inventory Service receives `ReleaseStock` first. Finding no existing reservation record, it returns `SUCCESS`.
4. A few seconds later, the delayed `HoldStock` packet finally arrives. It successfully reserves the stock and locks inventory forever for an order that was already cancelled!

```
Orchestrator                    Inventory Service
     │                                 │
     │─── T1: HoldStock (delayed) ────►│ (stuck in network buffer)
     │    [Timeout fires after 2s]     │
     │─── C1: ReleaseStock ───────────►│ (arrives first!)
     │                                 │ ──► No reservation found! (naive: returns OK)
     │                                 │
     │    (Delayed T1 arrives)         │
     │────────────────────────────────►│ ──► Creates reservation! LEAKED LOCK! ❌
```

#### Solution: Tombstone Record (Pre-Cancellation State)

When a compensation arrives and finds no active forward entity, it writes a **Tombstone** record marked `CANCELLED_BY_EARLY_COMPENSATION`. When the forward transaction arrives later, it detects the tombstone and immediately aborts.

```java
@Service
@Transactional
public class StockReservationService {

    private final ReservationRepository reservationRepo;
    private final ProductRepository productRepo;

    public void releaseReservation(UUID orderId, UUID productId, int count) {
        Optional<Reservation> opt = reservationRepo.findByOrderId(orderId);

        if (opt.isPresent()) {
            Reservation res = opt.get();
            if (res.getStatus() == ReservationStatus.ACTIVE) {
                res.setStatus(ReservationStatus.CANCELLED);
                productRepo.incrementStock(productId, count);
                reservationRepo.save(res);
            }
        } else {
            // Compensation arrived BEFORE forward action!
            // Plant a Tombstone to poison and block any late-arriving holdStock command:
            Reservation tombstone = Reservation.builder()
                .orderId(orderId)
                .productId(productId)
                .quantity(count)
                .status(ReservationStatus.CANCELLED_BY_EARLY_COMPENSATION)
                .createdAt(Instant.now())
                .build();
            reservationRepo.save(tombstone);
            log.warn("Tombstone created for early compensation on order {}", orderId);
        }
    }

    public void holdStock(UUID orderId, UUID productId, int count) {
        Optional<Reservation> opt = reservationRepo.findByOrderId(orderId);
        if (opt.isPresent()) {
            if (opt.get().getStatus() == ReservationStatus.CANCELLED_BY_EARLY_COMPENSATION) {
                log.warn("Late holdStock arrived for pre-cancelled order {}. Aborting forward execution.", orderId);
                return; // Suppress reservation
            }
            log.info("Duplicate holdStock received for order {}", orderId);
            return;
        }

        // Standard forward stock reservation:
        productRepo.decrementStock(productId, count);
        Reservation res = Reservation.builder()
            .orderId(orderId)
            .productId(productId)
            .quantity(count)
            .status(ReservationStatus.ACTIVE)
            .createdAt(Instant.now())
            .build();
        reservationRepo.save(res);
    }
}
```

### 2. Semantic Compensation vs Technical Rollback

Real-world operations often cannot be undone at the bit level:

- **Irreversible External Side Effects:** Sending an SMS, sending a push notification, physical wire transfer via clearinghouse, cutting physical goods in a warehouse.
- **Semantic Neutralization:**
  - Instead of un-sending an SMS $\to$ send a corrective notification: *"Order #1042 was cancelled; your card will be refunded within 3 days."*
  - Instead of waiving an unrefundable banking gateway transaction fee $\to$ absorb the fee as operating loss or issue promotional store credit.
  - Instead of executing SQL `DELETE` $\to$ append an inverse balancing entry to an immutable audit journal (Double-Entry Ledger).

### 3. Forward Recovery vs Backward Recovery

| Dimension | Backward Recovery (Compensation Flow) | Forward Recovery (Retry Flow) |
| :--- | :--- | :--- |
| **Strategy** | Abort Saga and unwind previous steps ($C_{k-1} \dots C_1$) | Persist and retry failed step ($T_k$) until it succeeds |
| **Applicable Phase** | Steps before the Pivotal Transaction | Steps on or after the Pivotal Transaction |
| **Trigger Cause** | Unrecoverable business rule failures (insufficient funds, out of stock) | Transient infrastructure errors (HTTP 503, network drop, DB deadlock) |
| **Implementation Complexity** | High: Every forward step requires custom, tested compensation logic | Moderate: Requires strict idempotency, exponential backoff, and dead-letter queues |
| **Customer Impact** | Order rejected or cancelled; customer notified of failure | Order delayed, but eventually completes successfully without cancellation |

## 4 Tricky Questions

### 1. What is a Pivotal Transaction and why is backward compensation impossible after it commits?
**Answer:**
A Pivotal Transaction is the critical boundary step in a Saga where the business process reaches its "point of no return". Once the pivotal transaction commits (e.g., executing an irrevocable wire transfer via SWIFT, or confirming a non-refundable external booking), the Saga is contractually and technically committed to completion. 
Reversing this step is either legally prohibited, technically impossible, or economically catastrophic. Consequently, the Saga switches permanently to **Forward Recovery**. All subsequent steps (receipt generation, CRM updates, driver dispatch) must be designed as retriable operations that retry indefinitely until successful, or fall back to an operator DLQ for manual intervention.

### 2. What happens when a compensating transaction fails permanently?
**Answer:**
A compensating transaction is never allowed to fail due to business constraints. If it fails due to infrastructure (e.g., downstream microservice database corruption or external gateway total outage):
1. **Exponential Backoff with Jitter:** The orchestrator retries the compensation according to a configured retry policy.
2. **Escalation to DLQ (Dead Letter Queue):** Once maximum retries are exhausted, the compensation event is pushed to a Dead Letter Topic and the Saga state is flagged as `COMPENSATION_STUCK` or `REQUIRES_MANUAL_INTERVENTION`.
3. **SRE Alerting & Manual Reconciliation:** A high-priority PagerDuty incident alerts on-call engineers. Back-office operations teams use administrative tooling to inspect the compensating payload and manually resolve the inconsistency against bank or warehouse portals.

### 3. In what order must compensations execute during parallel fork-join Saga branches?
**Answer:**
When a Saga executes parallel concurrent branches (Fork-Join), for example step $A$ triggers both $B_1$ (payment) and $B_2$ (inventory hold) concurrently, and $B_2$ fails while $B_1$ succeeds:
1. The coordinator must wait for $B_1$ to finish or explicitly cancel its active execution.
2. Compensations for the parallel branches ($C_{B_1}$) must execute first.
3. Multiple parallel compensations can run concurrently with each other if their operations are commutative and independent.
4. Only after all active parallel branch compensations have successfully completed can the coordinator invoke the compensation of the preceding parent step ($C_A$).

### 4. Why is executing a physical SQL `DELETE` strictly prohibited in compensating transactions?
**Answer:**
1. **Audit and Regulatory Compliance:** Financial compliance regulations (SOX, PCI-DSS, GDPR audit trails) mandate an unbroken history of all operations. Physical deletes destroy legal audit evidence.
2. **Dangling Foreign Key References:** Downstream or asynchronous reporting services may have already read the forward entity's ID. Deleting the row causes foreign key violations or broken references in dependent systems.
3. **Out-of-Order Race Hazards:** If the compensating `DELETE` arrives before a delayed forward `INSERT`, the `DELETE` finds nothing, and the subsequent `INSERT` creates an orphaned record permanently. A soft delete or status transition (`CANCELLED` / `Tombstone`) ensures out-of-order idempotency.

## 🎯 Interview Cheat Sheet

### Must Know
- **Definition:** A compensating transaction is an explicit business operation ($C_k$) that semantically neutralizes a previously committed local transaction ($T_k$) in a distributed Saga.
- **Not an SQL Rollback:** The previous transaction already committed its changes to disk; compensation executes a **new commit** that updates business state.
- **Execution Order:** Compensations execute in strict reverse chronological order (LIFO).
- **The 3 Golden Rules:**
  1. Must be **strictly idempotent** (safe to receive duplicate messages).
  2. Must **never fail on business validation rules**.
  3. Must handle **phantom compensations** (compensation arriving before forward action via Tombstones).
- **Pivotal Step:** Divides the Saga into Backward Recovery (pre-pivotal, cancellable) and Forward Recovery (post-pivotal, retriable only).

### Common Follow-up Questions
- *"Can a compensating transaction fail?"* $\to$ Never on business validation; only on infrastructure. Infrastructure failures are handled via retries with exponential backoff and DLQs.
- *"How do you handle irreversible real-world side effects (e.g. Sent email/SMS)?"* $\to$ You cannot un-send a message; send a follow-up corrective message explaining the cancellation.
- *"What is a Tombstone record?"* $\to$ A marker created when an out-of-order compensation arrives before its forward action, preventing the late forward action from creating orphaned resources.

### Red Flags (DO NOT Say)
- ❌ *"A compensating transaction performs an SQL rollback across microservices."* (Local transactions already committed; compensation is a new forward transaction).
- ❌ *"If a compensation fails, we rollback the compensation."* (A compensation cannot be rolled back; it retries until completion or manual operator intervention).
- ❌ *"To compensate a created order, we execute `repository.deleteById()`."* (Destroys audit trails, causes race conditions, and breaks referential integrity).
