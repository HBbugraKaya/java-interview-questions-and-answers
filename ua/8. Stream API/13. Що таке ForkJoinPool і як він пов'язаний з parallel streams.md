# Що таке ForkJoinPool і як він пов'язаний з parallel streams

---

## 🟢 Junior Level

### Коротка відповідь для співбесіди (30 секунд)
**`ForkJoinPool`** — це спеціалізований пул потоків (що з'явився в Java 7), спроєктований для ефективного розв'язання завдань за принципом **«Розділяй і володарюй» (Divide and Conquer)**. Він реалізує алгоритм **Work-Stealing (крадіжка роботи)**: у кожного робочого потоку є своя власна двостороння черга завдань (Deque), і якщо потік звільняється раніше за інших, він «краде» завдання з черг зайнятих сусідів.

Паралельні стріми (`parallelStream()`) не створюють нові потоки вручну, а за замовчуванням виконують усі проміжні та термінальні операції всередині єдиного статичного пулу **`ForkJoinPool.commonPool()`**. Його розмір дорівнює кількості доступних ядер мінус одне (`Runtime.getRuntime().availableProcessors() - 1`), оскільки викликаючий потік сам долучається до обчислень.

---

### Базовий приклад на Java 21

```java
import java.util.List;
import java.util.concurrent.ForkJoinPool;

public class ForkJoinStreamDemo {

    public static void main(String[] args) {
        List<Integer> numbers = List.of(1, 2, 3, 4, 5, 6, 7, 8);

        // Паралельний стрім автоматично виконується у ForkJoinPool.commonPool()
        long sum = numbers.parallelStream()
            .mapToLong(n -> {
                System.out.printf("Число: %d, Потік: %s%n",
                    n, Thread.currentThread().getName());
                return (long) n * n;
            })
            .sum();

        System.out.println("Сума квадратів: " + sum);

        // Перегляд характеристик спільного пулу
        ForkJoinPool common = ForkJoinPool.commonPool();
        System.out.printf("Паралелізм: %d, Розмір пулу: %d, Крадіжок завдань: %d%n",
            common.getParallelism(), common.getPoolSize(), common.getStealCount());
    }
}
```

## 🟡 Middle Level

### Відмінності між `ThreadPoolExecutor` та `ForkJoinPool`

| Характеристика | `ThreadPoolExecutor` | `ForkJoinPool` |
|---|---|---|
| **Черги завдань** | **Одна спільна** `BlockingQueue` на весь пул | **У кожного потоку своя** `WorkQueue` (двостороння черга — Deque) |
| **Рівень конкуренції** | Високий (усі потоки борються за блокування єдиної черги) | Мінімальний (потоки працюють локально у своїх чергах) |
| **Характер завдань** | Довгі, незалежні завдання (I/O, запити) | Дрібні, рекурсивно розгалужені підзавдання (CPU-Bound) |
| **Поведінка під час простою** | Потік блокується в очікуванні нового завдання | Потік шукає роботу в чергах сусідів (**Work-Stealing**) |

```
ThreadPoolExecutor:
[Worker 1] \
[Worker 2] ---> [ Єдина BlockingQueue ] (Високий Contention)
[Worker 3] /

ForkJoinPool (Work-Stealing):
Worker 1: [Deque 1] <── Pop/Push (LIFO)
Worker 2: [Deque 2]
Worker 3: (Порожньо) ──────> Steal (FIFO) з Deque 1 / Deque 2
```

---

### Як стрім взаємодіє зі сплітератором і пулом

1. **`Spliterator.trySplit()`**: вихідна колекція рекурсивно ділиться на дві частини.
2. **`ForkJoinTask`**: підзавдання оформлюються у спеціалізовані завдання `CountedCompleter` (наприклад, `ReduceTask`).
3. **`fork()`**: ліве підзавдання відправляється в локальну чергу поточного потоку, а праве обчислюється безпосередньо поточним потоком (зменшуючи оверхед на планування).
4. **`join()` / `onCompletion()`**: коли всі листки дерева завершують обчислення, результати об'єднуються функцією `combiner()`.

## 🔴 Senior Level

### Внутрішня будова: Lock-Free Deque, LIFO vs FIFO диспетчеризація

Кожна черга `WorkQueue` у `ForkJoinPool` реалізована як кільцевий масив з використанням атомарних CAS-операцій (`VarHandle` / `Unsafe`):
- **LIFO (Last-In, First-Out) для потоку-власника:** Потік додає (`push`) і забирає (`pop`) завдання з **голови** своєї черги. Це максимізує **кеш-локальність процесора (L1/L2)**: завдання, породжене останнім, працює з іще «гарячими» даними в кеші CPU.
- **FIFO (First-In, First-Out) для потоків-«злодіїв»:** Потоки, у яких закінчилася робота, крадуть завдання з **хвоста** чужих черг. У хвості лежать найстаріші підзавдання — а отже, найбільші (ще не розщеплені рекурсивно). Це мінімізує частоту крадіжок і знижує конкуренцію з власником черги.

---

### Механізм `ForkJoinPool.ManagedBlocker`

Що робити, якщо завдання у ForkJoinPool зобов'язане заблокуватися (наприклад, очікувати лок `ReentrantLock` або бар'єр `Phaser`)?
Звичайне блокування потоку зменшує активний паралелізм пулу. Для розв'язання цієї проблеми існує інтерфейс `ForkJoinPool.ManagedBlocker`:

```java
public static interface ManagedBlocker {
    boolean block() throws InterruptedException;
    boolean isReleasable();
}
```

Коли потік викликає `ForkJoinPool.managedBlock(blocker)`:
1. Пул перевіряє, чи заблоковане завдання.
2. Якщо так, пул **компенсує блокування**, тимчасово створюючи додатковий потік (spare worker thread), щоб підтримати цільове значення `parallelism`.
3. Після виходу з блокування зайвий потік відправляється в резерв або знищується.

> **Важливо:** Стандартні блокуючі виклики (`InputStream.read()`, мережеві виклики JDBC) **не реалізують `ManagedBlocker`**! Тому вони неминуче заморожують воркери пулу.

---

### Enterprise Trap: Starvation спільного `commonPool()` у Spring Boot

У типовому мікросервісі `commonPool()` ділять:
1. Усі виклики `parallelStream()`.
2. Усі асинхронні виклики `CompletableFuture.supplyAsync(...)` без явного зазначення `Executor`.

Якщо хоча б в одному ендпоінті розробник виконає блокуючий HTTP-запит усередині `parallelStream()`, усі потоки пулу виявляться заблокованими. У результаті в усьому мікросервісі перестануть виконуватися й інші паралельні стріми, і системні асинхронні ланцюжки.

**Рішення:** Ізолювати важкі завдання в кастомному пулі:

```java
ForkJoinPool customPool = new ForkJoinPool(4);
try {
    List<Item> result = customPool.submit(() ->
        items.parallelStream().map(this::heavyCpuCalculation).toList()
    ).get();
} finally {
    customPool.shutdown();
}
```

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь
> «`ForkJoinPool` — це пул потоків, створений для CPU-інтенсивних завдань з рекурсивним поділом («розділяй і володарюй»). Його ключова особливість — алгоритм Work-Stealing із персональними чергами (Deque) у кожного потоку. Власник бере завдання з голови за LIFO для кеш-локальності CPU, а інші потоки крадуть великі завдання з хвоста за FIFO. `parallelStream()` під капотом використовує статичний `ForkJoinPool.commonPool()`. Блокуюче введення-виведення всередині стрімів небезпечне тим, що вичерпує потоки спільного пулу для всього сервісу.»

---

### Архітектурна шпаргалка

| Механізм | Як працює | Навіщо зроблено |
|---|---|---|
| **Work-Stealing** | Потоки без роботи крадуть завдання в сусідів | Ідеальна утилізація всіх ядер CPU |
| **LIFO для власника** | Потік бере свіже завдання з голови черги | Гарячі дані в кеші L1/L2 процесора |
| **FIFO для злодіїв** | Крадіжка старого завдання з протилежного кінця | Забирається найбільший шматок роботи, немає CAS-конфлікту з власником |
| **ManagedBlocker** | Створює запасний потік при реєстрації блокування | Підтримка рівня паралелізму при явному очікуванні |
| **Size = Cores - 1** | Викликаючий потік також бере участь в обробці | Економія 1 потоку без зайвого перемикання контексту |

### Топ-4 каверзних запитання на інтерв'ю

#### 1. Чому потік-власник бере завдання зі своєї черги за принципом LIFO, а потоки-злодії крадуть за FIFO?
- Власник бере останнє додане завдання (LIFO), оскільки його аргументи та структури даних прямо зараз знаходяться в регістрах і L1/L2 кеші процесора.
- Потоки, що крадуть, забирають завдання з хвоста (FIFO), де лежать найперші, найбільші нерозщеплені шматки роботи. Це дозволяє злодієві виконати тривалу роботу без частих повторних звернень до чужої черги. Крім того, доступ із різних кінців черги мінімізує CAS-конфлікти.

#### 2. Що станеться, якщо у вебсервісі виконати `parallelStream()` з викликом зовнішнього REST API?
- Робочі потоки `ForkJoinPool.commonPool()` заблокуються на очікуванні мережевих сокетів. Оскільки `commonPool` один на всю JVM, усі інші паралельні стріми та завдання `CompletableFuture` стануть у чергу, що призведе до деградації латентності всього застосунку (Thread Starvation).

#### 3. Як запустити `parallelStream()` у кастомному `ForkJoinPool` і як рантайм дізнається, який пул використовувати?
- Запустити стрім усередині `customPool.submit(() -> stream.parallel()...).get()`. Рантайм стріма при старті термінальної операції викликає `ForkJoinTask.getPool()`, який повертає пул поточного потоку, якщо викликаючий потік є `ForkJoinWorkerThread`.

#### 4. Що таке `ManagedBlocker` і чи може він автоматично врятувати паралельний стрім із JDBC-запитами?
- `ManagedBlocker` — це інтерфейс, що повідомляє `ForkJoinPool` про неминуче блокування, аби пул міг динамічно тимчасово виділити компенсуючий потік. Проте стандартні драйвери JDBC та блокуючі потоки введення-виведення (I/O) його не реалізують. Автоматичної компенсації для них не відбудеться.

---

### Типові помилки та Red Flags
- 🚩 Запуск мережевих або дискових блокуючих викликів у `parallelStream()`, що використовує `commonPool()`.
- 🚩 Уявлення, ніби `ForkJoinPool` влаштований як `ThreadPoolExecutor` з єдиною блокуючою чергою.
- 🚩 Забування викликати `shutdown()` при створенні екземплярів `new ForkJoinPool()`.
- 🚩 Впевненість, що `ForkJoinPool.commonPool()` масштабується нескінченно при зростанні навантаження (його розмір фіксований кількістю ядер).
