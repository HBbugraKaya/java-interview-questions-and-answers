# What does map() operation do

---

## 🟢 Junior Level

### Short Interview Answer (30 seconds)
**`map(Function<? super T, ? extends R> mapper)`** is an **intermediate, lazy, and stateless** operation in the Java Stream API that performs a **1-to-1 transformation** on each element of the stream.

It accepts a functional interface `java.util.function.Function<T, R>` (method `R apply(T t)`), applies the specified transformation function to each incoming element individually, and emits the transformed result downstream. The resulting stream is of type `Stream<R>`. 

A fundamental invariant of `map()` is its **1-to-1 cardinality guarantee**: it never alters the total number of elements in the stream—one input element always yields exactly one output element.

---

### Canonical Java 21 Examples

```java
import java.util.List;

public class MapBasicsDemo {

    public record User(Long id, String email, String role) {}
    public record UserDto(Long id, String email) {}

    public static void main(String[] args) {
        List<User> users = List.of(
            new User(1L, "alice@example.com", "ADMIN"),
            new User(2L, "bob@example.com", "USER")
        );

        // 1. Transforming domain entities into presentation DTOs
        List<UserDto> dtos = users.stream()
            .map(u -> new UserDto(u.id(), u.email()))
            .toList();

        System.out.println("DTOs: " + dtos);

        // 2. Type transformation: String -> Integer (calculating string length)
        List<String> frameworks = List.of("Spring", "Quarkus", "Micronaut");
        List<Integer> lengths = frameworks.stream()
            .map(String::length)
            .toList();

        System.out.println("Lengths: " + lengths); // [6, 7, 9]
    }
}
```

## 🟡 Middle Level

### Under the Hood: `Sink.ChainedReference` in OpenJDK

In the OpenJDK implementation (`ReferencePipeline.java`), `map()` wraps downstream pipeline stages using a chained `Sink`:

```java
// Simplified OpenJDK ReferencePipeline.java logic:
@Override
public Sink<P_OUT> opWrapSink(int flags, Sink<P_OUT> downstream) {
    return new Sink.ChainedReference<P_OUT, P_OUT>(downstream) {
        @Override
        public void accept(P_OUT u) {
            // Evaluates mapper function and pushes transformed value downstream
            downstream.accept(mapper.apply(u));
        }
    };
}
```
Because stream execution is pull-based and fused, the mapping function processes elements **one at a time** as they are requested by the terminal operation, with zero intermediate collection allocation.

---

### Primitive Specializations: Eliminating Autoboxing Overhead

Using generic `map()` for numeric conversions causes the JVM to box each primitive into a heap wrapper object (`Integer`, `Long`, `Double`), triggering heavy GC allocation pressure:

```java
// ❌ INEFFICIENT: Allocates 1,000,000 Integer wrapper objects on the Heap (~24 MB)
Stream<Integer> boxedStream = words.stream().map(String::length);

// ✅ HIGH-PERFORMANCE: Specialized primitive stream (Zero heap allocations, CPU registers)
IntStream primitiveStream = words.stream().mapToInt(String::length);
int totalChars = primitiveStream.sum();
```

#### Primitive Stream Mappers:
- `mapToInt(ToIntFunction)` $\to$ returns `IntStream`
- `mapToLong(ToLongFunction)` $\to$ returns `LongStream`
- `mapToDouble(ToDoubleFunction)` $\to$ returns `DoubleStream`
- To convert back from primitive to object stream: `.boxed()` or `.mapToObj(IntFunction)`.

---

### Key Distinctions: `map()` vs. `flatMap()`

| Criterion | `map()` | `flatMap()` |
| :--- | :--- | :--- |
| **Function Signature** | `Function<T, R>` | `Function<T, Stream<R>>` |
| **Cardinality** | **Strictly 1-to-1** (1 input produces 1 output) | **1-to-Many ($0 \dots N$)** (1 input produces a stream) |
| **Structure Handling** | Preserves nesting (e.g., `List<List<T>>` $\to$ `Stream<List<T>>`) | Flattens nested structures into a single `Stream<T>` |
| **Element Modification** | Value transformation | Structural flattening and extraction |

---

### Functional Purity Requirements (Side-Effect-Free)

The mapper function supplied to `map()` must be a **pure function**:
- **No Mutation:** Do not mutate fields of the incoming object (`user.setStatus("ACTIVE")`). If data needs alteration, instantiate a new record or object copy.
- **No External State Dependency:** The function must not depend on mutable state that could change concurrently during stream traversal.
- **No Side-Effects:** Never perform I/O operations (HTTP calls, DB inserts) inside `map()`. For side-effects, use the terminal operation `forEach()`.

## 🔴 Senior Level

### Stream Characteristics: What Happens to Stream Flags?

`map()` has a distinct effect on pipeline optimization bitmasks:
1. **The `SIZED` Flag is PRESERVED:** Because `map()` guarantees a 1-to-1 relationship, the pipeline knows the exact output element count in advance. Terminal collectors (like `.toList()`) can pre-allocate backing arrays of exact size without dynamic resizing.
2. **The `DISTINCT` Flag is ALWAYS CLEARED (`NOT_DISTINCT`):** Even if the upstream stream was `DISTINCT`, mapping can produce identical output values (e.g., mapping distinct strings `"cat"` and `"dog"` to their lengths produces `3` and `3`).
3. **The `SORTED` Flag is ALWAYS CLEARED (`NOT_SORTED`):** The JVM cannot know whether the mapping function preserves natural or comparator order.

---

### Handling Checked Exceptions Inside `map` Lambdas

`java.util.function.Function`'s method `R apply(T t)` does not declare checked exceptions. Calling methods that throw checked exceptions (e.g., `Files.readString()`, `new URI()`) causes compilation errors.

#### Idiomatic Architectural Patterns:
```java
// Approach 1: Local wrapping into an Unchecked Exception
List<String> contents = filePaths.stream()
    .map(path -> {
        try {
            return Files.readString(path);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    })
    .toList();

// Approach 2: Functional Exception Wrapper (Either / Result Pattern)
public static <T, R> Function<T, R> uncheck(ThrowingFunction<T, R> f) {
    return t -> {
        try {
            return f.apply(t);
        } catch (Throwable ex) {
            SneakyThrows.sneakyThrow(ex);
            return null;
        }
    };
}
```

### The Downstream Null Propagation Hazard

If a mapper function returns `null`, `map()` does **not** discard it—the `null` reference travels downstream as an active stream element:

```java
// ❌ HIDDEN BUG: NullPointerException on subsequent stage!
List<String> cities = users.stream()
    .map(User::getAddress)  // Returns null if user has no address
    .map(Address::city)     // 💥 NullPointerException thrown when calling .city() on null!
    .toList();

// ✅ ROBUST PRODUCTION PATTERN: Explicit null-safety filter
List<String> cities = users.stream()
    .map(User::getAddress)
    .filter(Objects::nonNull)
    .map(Address::city)
    .filter(Objects::nonNull)
    .toList();
```

## 4 Tricky Questions

### 1. Why does `map()` preserve the `SIZED` flag, but always clear `DISTINCT` and `SORTED`?
**Answer:** 
- `SIZED` is preserved because `map()` is strictly a 1-to-1 operation; it can neither add nor drop elements.
- `DISTINCT` must be cleared because an arbitrary function can map different inputs to identical outputs (e.g., `user1` and `user2` both have age `25`).
- `SORTED` must be cleared because transformation functions do not guarantee monotonic order preservation (e.g., `map(x -> -x)` reverses the numerical ordering).

---

### 2. Can you use `map()` to filter out elements by returning `null`?
**Answer:** **No, absolutely not.** Returning `null` does not filter or discard the element; instead, it injects a `null` reference into the stream. Downstream operations that dereference the element will crash with a `NullPointerException`. To remove elements from a stream, always use `filter(Predicate)` or `flatMap()`.

---

### 3. What is the performance difference between `map(x -> x * 2)` and `mapToInt(x -> x * 2)` on an `ArrayList<Integer>`?
**Answer:** On a collection of 1,000,000 integers:
- `map(x -> x * 2)` requires unboxing the `Integer` to multiply, and then **allocating a brand-new `Integer` object on the heap** for the result (consuming ~24 MB of memory and triggering GC minor collections).
- `mapToInt(x -> x * 2)` unboxes once into a primitive `int` and keeps the values in raw CPU registers/arrays within an `IntStream`, resulting in **zero heap allocations** and significantly faster throughput.

---

### 4. What happens if the mapping function in a parallel stream accesses a non-thread-safe external object?
**Answer:** It introduces **race conditions and data corruption**. 
In a parallel stream, `map()` functions are executed concurrently across multiple threads in `ForkJoinPool.commonPool()`. If the mapping function reads from or writes to a non-thread-safe external object (e.g., a shared `SimpleDateFormat`, `HashMap`, or non-atomic counter), concurrent access leads to silent calculation errors, corrupted internal structures, or `ConcurrentModificationException`s.

### Key Takeaways
1. `map()` applies a 1-to-1 transformation, returning a new `Stream<R>` of identical length.
2. It preserves the `SIZED` characteristic flag, but always clears `SORTED` and `DISTINCT`.
3. Use primitive mappers (`mapToInt()`, `mapToLong()`) to prevent high GC allocation pressure from autoboxing.
4. Returning `null` from a mapper does not remove the element; it passes `null` downstream.
5. Functions passed to `map()` must remain pure, side-effect-free, and thread-safe.

### Red Flags to Avoid
- ❌ Attempting to filter elements by returning `null` inside `map()`.
- ❌ Mutating the input object's state inside `map()` instead of returning a new value.
- ❌ Using generic `Stream<Integer>` for heavy numeric processing instead of `IntStream`.
- ❌ Performing slow, blocking I/O calls (e.g., database queries) inside `map()`.
