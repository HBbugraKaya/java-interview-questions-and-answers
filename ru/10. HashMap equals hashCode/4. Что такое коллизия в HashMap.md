# Что такое коллизия в HashMap

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**Коллизия в `HashMap`** — это штатная ситуация, при которой два логически разных ключа (`k1.equals(k2) == false`) в результате вычислений претендуют на размещение в одной и той же корзине (ячейке внутреннего массива `table[index]`).

Коллизия **не является ошибкой или сбоем**. Она математически неизбежна, так как множество возможных объектов в памяти бесконечно, а размер массива корзин строго ограничен (по умолчанию 16). Для разрешения коллизий `HashMap` использует **метод цепочек (Separate Chaining)**: конфликтующие элементы выстраиваются в односвязный список внутри корзины. Начиная с Java 8, если длина цепочки в корзине достигает 8 элементов (при размере таблицы не менее 64), список трансформируется в красно-черное дерево, защищая систему от потери производительности.

---

### Два типа коллизий: Коллизия Хешей vs Коллизия Индексов

| Тип коллизии | Что произошло | Пример | Как часто случается |
|---|---|---|---|
| **Коллизия `hashCode()` (Hash Collision)** | Два разных объекта вернули абсолютно одинаковый 32-битный `int` | `"Aa".hashCode() == 2112`<br>`"BB".hashCode() == 2112` | Редко (при качественной реализации хеш-функции) |
| **Коллизия индексов (Bucket / Slot Collision)** | Хеш-коды у объектов разные, но операция `(n - 1) & hash` дала одинаковый индекс ячейки | `hash1 = 100` (`...01100100_b`)<br>`hash2 = 116` (`...01110100_b`)<br>Индекс при $n=16$: **4** | **Постоянно** (наиболее распространенный вид коллизии) |

### Демонстрация коллизий на Java 21

```java
import java.util.HashMap;

public class CollisionDemo {
    public static void main(String[] args) {
        HashMap<String, String> map = new HashMap<>();

        // 1. Истинная коллизия hashCode():
        // В алгоритме String.hashCode() строки "Aa" и "BB" дают один и тот же результат: 2112
        System.out.println("Aa hash: " + "Aa".hashCode()); // 2112
        System.out.println("BB hash: " + "BB".hashCode()); // 2112

        map.put("Aa", "FirstValue");
        map.put("BB", "SecondValue"); // Попадает в ту же корзину, что и "Aa"!

        // Оба значения успешно сохраняются и корректно извлекаются:
        System.out.println("Aa -> " + map.get("Aa")); // FirstValue
        System.out.println("BB -> " + map.get("BB")); // SecondValue

        // 2. Коллизия индексов (разные хеши, но один бакет):
        // Строки "FB" (hashCode = 2236) и "Ea" (hashCode = 2236)
        // Любые ключи с одинаковыми младшими битами делят один бакет
        System.out.println("Размер мапы: " + map.size()); // 2
    }
}
```

## 🟡 Middle Level

### Математическая неизбежность коллизий

Почему даже при идеальном коде коллизии гарантированно возникают:

#### 1. Принцип Дирихле (Pigeonhole Principle):
Диапазон типа `int` в Java ограничен $2^{32} \approx 4\,294\,967\,296$ значениями. Количество же возможных строковых объектов даже длиной до 10 символов превышает $10^{15}$. Невозможно отобразить бесконечное множество объектов в конечное 32-битное адресное пространство без дубликатов.

#### 2. Парадокс дней рождения (Birthday Paradox):
Теория вероятностей гласит: в группе всего из **23 человек** вероятность того, что у двоих совпадет день рождения (всего 365 вариантов), превышает **50%**.  
В `HashMap` с начальной емкостью $n = 16$ корзин вероятность возникновения хотя бы одной коллизии превышает **50% уже при добавлении всего 5 элементов**!

---

### Как `HashMap` находит нужный элемент среди коллизий

Когда в одной корзине находится несколько элементов, вызов `map.get(key)` итерируется по связному списку или дереву, выполняя двухэтапную проверку для каждого узла:

```java
// Исходный код HashMap HotSpot:
if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
    return p;
```

1. **Проверка по кэшированному хешу:** сравнивается примитив `p.hash == hash`. Если перемешанные хеши не совпадают, узел отбрасывается за 1 такт процессора.
2. **Проверка по ссылке:** `(k = p.key) == key`. Если ссылки указывают на один и тот же адрес в Heap, `equals()` даже не вызывается.
3. **Проверка по `equals()`:** только если хеши совпали, но ссылки разные, вызывается глубокое доменное сравнение `key.equals(k)`.

## 🔴 Senior Level

### Влияние коллизий на аппаратную производительность (Memory Wall & Cache Misses)

С точки зрения архитектуры современных процессоров (CPU Caching), коллизии вызывают колоссальную деградацию задержки (Latency):

```
Без коллизии (O(1)):
CPU ──► table[i] ──► Direct Hit (L1/L2 Cache) ──► Возврат значения (~1 нс)

При глубокой коллизии (O(n)):
CPU ──► table[i] ──► Node 1 ──(Pointer Chasing)──► Node 2 ──(RAM)──► Node 3...
   (Промахи кэша L1/L2/L3, загрузка линий кэша из RAM, вызовы virtual equals) (~50-100 нс)
```

Каждый узел `Node` аллоцируется сборщиком мусора в произвольном месте кучи. Обход связного списка коллизий — это классический **Pointer Chasing (погоня по указателям)**, который не поддается аппаратному префетчеру процессора (CPU Hardware Prefetcher), приводя к постоянным задержкам на ожидание шины оперативной памяти.

---

### Атака Hash Flooding DoS и защита через Treeification

В конце 2011 года исследователи информационной безопасности продемонстрировали уязвимость большинства веб-серверов: передача HTTP POST запроса с 10 000 параметров формы, чьи строковые имена генерировали одинаковый `hashCode()`.

#### Механика DoS-атаки в Java 7:
1. В Java 7 разрешение коллизий строилось строго на связных списках;
2. Добавление $N$ элементов в один бакет требовало $O(N)$ проверок на каждом шаге, превращая вставку пачки параметров в сложность **$O(N^2)$**;
3. Один HTTP-запрос размером в несколько сотен килобайт подвешивал ядро CPU сервера на десятки секунд.

#### Решение в Java 8+:
При достижении порога в 8 элементов список перестраивается в красно-черное дерево. Сложность вставки и поиска падает с $O(N)$ до **$O(\log N)$**, а суммарная обработка DoS-запроса занимает $O(N \log N)$ вместо $O(N^2)$, нейтрализуя вектор атаки.

---

### Алгоритм упорядочивания узлов в `TreeNode`: `Comparable` и `tieBreakOrder`

Красно-черное дерево требует строгого порядка элементов ($<$ или $>$). Как `HashMap` упорядочивает узлы, если их `hash` полностью совпадает?

1. **Интерфейс `Comparable`:**  
   Если класс ключа реализует `Comparable<K>` (как, например, `String`, `Integer`, `UUID`), узлы сравниваются вызовом `((Comparable)k).compareTo(x)`.
2. **Fallback через `tieBreakOrder`:**  
   Если ключи не реализуют `Comparable` или их `compareTo()` вернул 0 (но по `equals()` они не равны), `HashMap` использует метод `tieBreakOrder()`:
   ```java
   static int tieBreakOrder(Object a, Object b) {
       int d;
       if (a == null || b == null ||
           (d = a.getClass().getName().compareTo(b.getClass().getName())) == 0)
           d = (System.identityHashCode(a) <= System.identityHashCode(b) ? -1 : 1);
       return d;
   }
   ```
   В качестве финального арбитра используется **`System.identityHashCode()`** (исходный нативный хеш объекта из его Mark Word).

## 🎯 Шпаргалка для интервью

### 1. 30-секундный эссенс (Elevator Pitch)
Коллизия в `HashMap` — это ситуация, когда разные ключи (`equals == false`) попадают в один бакет. Бывает двух видов: совпадение `hashCode()` (редко) или совпадение индекса `(n - 1) & hash` (постоянно). Коллизии неизбежны из-за принципа Дирихле и парадокса дней рождения (при $n=16$ коллизия вероятнее 50% уже при 5 ключах). Для разрешения применяется метод цепочек: элементы связываются в список ($O(k)$), а при 8+ элементах и таблице $\ge 64$ конвертируются в красно-черное дерево ($O(\log k)$), что защищает систему от Hash Flooding DoS атак.

### 2. 4 каверзных вопроса с глубокими ответами

#### Вопрос 1: В чём принципиальная разница между коллизией хеш-кодов (`hashCode collision`) и коллизией корзин (`bucket collision`), и какая происходит чаще?
**Ответ:**
- **Коллизия `hashCode()`:** два разных объекта возвращают одинаковый 32-битный `int` из метода `hashCode()`. Происходит редко, если хеш-функция учитывает все значимые поля объекта.
- **Коллизия корзин:** два объекта имеют разные 32-битные `hashCode()`, но при наложении битовой маски `(table.length - 1) & hash` их младшие биты совпали, указав на один индекс массива.  
Коллизия корзин происходит на порядки чаще, так как емкость массива таблицы (16, 32, 64) многократно меньше диапазона чисел $2^{32}$.

#### Вопрос 2: Как парадокс дней рождения объясняет возникновение коллизий задолго до того, как таблица заполнится до порога ресайза?
**Ответ:**
Многие ошибочно полагают, что коллизии начинаются только при заполнении таблицы ближе к `threshold` (12 элементов из 16). Согласно теории вероятностей и парадоксу дней рождения, вероятность отсутствия коллизий при добавлении $k$ элементов в $n$ корзин равна:
$$P(\text{no collisions}) = \prod_{i=1}^{k-1} \left(1 - \frac{i}{n}\right)$$
Для таблицы из 16 корзин при $k = 5$ вероятность возникновения хотя бы одной коллизии составляет уже $\approx 51\%$. Коллизии — нормальное состояние таблицы с первых секунд ее наполнения.

#### Вопрос 3: Что произойдет при коллизии 8 элементов, если класс ключа НЕ реализует интерфейс `Comparable`?
**Ответ:**
Дерево `TreeNode` всё равно будет успешно построено. `HashMap` попытается найти метод `comparableClassFor(key)`. Если ключ не реализует `Comparable`, при вставке в дерево JVM сначала попытается рекурсивно обойти обе ветви узла, а в спорных случаях применит метод `tieBreakOrder()`: сравнит имена классов объектов, а при их совпадении упорядочит узлы по нативному адресу памяти через `System.identityHashCode()`. Однако накладные расходы на балансировку дерева без `Comparable` будут выше.

#### Вопрос 4: Как злоумышленник организует атаку Hash Flooding DoS, и как Java 8 гарантирует устойчивость приложения?
**Ответ:**
Злоумышленник генерирует тысячи строк с одинаковым `hashCode()` (в алгоритме Java `s[0]*31^(n-1) + ...` коллизии подбираются тривиально, например, перестановкой пар `"Aa"` и `"BB"`). Отправив форму с 20 000 таких параметров, он загоняет все элементы в один бакет веб-сервера. В Java 7 поиск и вставка элементов в список происходили за $O(n)$, превращая парсинг запроса в квадратичную сложность $O(n^2)$ со 100% блокировкой ядра процессора. В Java 8+ список древофицируется в красно-черное дерево, снижая сложность до $O(n \log n)$, что позволяет серверу обработать запрос за миллисекунды.

### 3. Типичные ошибки и Red Flags

❌ **"Коллизия означает, что разработчик допустил ошибку в `hashCode()`."**  
*Правильно:* Даже при эталонном `hashCode()` коллизии неизбежны из-за проекции 32-битного хеша на небольшой массив корзин (принцип Дирихле).

❌ **"Если в `HashMap` произошла коллизия, старый элемент перезаписывается новым."**  
*Правильно:* Перезапись значения происходит только тогда, когда совпали **и хеш, и `equals()`**. При коллизии (`equals == false`) оба элемента сохраняются в одной корзине.

❌ **"При коллизиях `HashMap` всегда работает за $O(n)$."**  
*Правильно:* В Java 8+ при росте цепочки свыше 8 элементов бакет трансформируется в дерево, гарантируя верхнюю границу сложности $O(\log n)$.
