# Can you reuse a Stream

---

## 🟢 Junior Level

### 30-Second Summary
**No. A Stream in Java is strictly a single-use, ephemeral computation pipeline.**

As soon as any **terminal operation** (e.g., `collect()`, `forEach()`, `count()`, `reduce()`, `findFirst()`) is invoked on a stream, the stream is considered **consumed and permanently closed**.

Any subsequent attempt to invoke another intermediate or terminal operation on that same stream instance immediately throws:
```text
java.lang.IllegalStateException: stream has already been operated upon or closed
```

To re-process or re-query the same data, you must **instantiate a fresh stream** from the original collection or backing source.

---

### Java 21 Code Examples

```java
import java.util.List;
import java.util.stream.Stream;

public class ReusingStreamDemo {

    public static void main(String[] args) {
        List<String> cities = List.of("London", "Tokyo", "New York");

        Stream<String> cityStream = cities.stream();

        // 1st terminal operation: Executes successfully
        cityStream.forEach(System.out::println);

        // 2nd terminal operation on the SAME stream instance:
        try {
            long count = cityStream.count(); // ❌ THROWS EXCEPTION!
        } catch (IllegalStateException e) {
            System.err.println("Caught Expected Error: " + e.getMessage());
            // stream has already been operated upon or closed
        }

        // ✅ IDIOMATIC SOLUTION: Re-create a fresh stream instance per traversal
        long validCount = cities.stream().count();
        System.out.println("Valid city count: " + validCount);
    }
}
```

## 🟡 Middle Level

### Under the Hood: `AbstractPipeline.linkedOrConsumed`

In the OpenJDK source code (`java.util.stream.AbstractPipeline`), each pipeline stage tracks its operational state via an internal boolean flag:

```java
// OpenJDK AbstractPipeline.java implementation fragment:
private boolean linkedOrConsumed;

final <R> R evaluate(TerminalOp<E_OUT, R> terminalOp) {
    if (linkedOrConsumed) {
        throw new IllegalStateException("stream has already been operated upon or closed");
    }
    linkedOrConsumed = true; // Irreversibly marks the stream as consumed!

    return isParallel()
           ? terminalOp.evaluateParallel(this, sourceSpliterator(terminalOp.getOpFlags()))
           : terminalOp.evaluateSequential(this, sourceSpliterator(terminalOp.getOpFlags()));
}
```

---

### Why Streams Are Single-Use by Architectural Design

Java language architects (led by Brian Goetz) designed streams as single-use pipelines for three essential reasons:

1. **Support for Non-Rewindable Sources:** Streams can be backed by one-way, non-buffered data sources like network sockets (`SocketChannel`), random number generators, or live event buses, which physically cannot be "rewound" without copying data.
2. **Low Memory Footprint:** If streams allowed multiple passes, the runtime would be forced to buffer all traversed and transformed elements in heap memory. This would eliminate the fundamental streaming advantage of near-zero memory consumption and cause `OutOfMemoryError` on large datasets.
3. **Concurrency Safety:** Single-use lifecycles prevent race conditions and thread re-entrancy bugs when worker threads in `ForkJoinPool` execute parallel stream subtasks.

### The `Supplier<Stream<T>>` Factory Pattern

When an algorithm requires regenerating a configured stream pipeline repeatedly without duplicating boilerplate logic, use a `Supplier`:

```java
import java.util.List;
import java.util.function.Supplier;
import java.util.stream.Stream;

public class StreamSupplierPatternDemo {

    public static void main(String[] args) {
        List<String> fruits = List.of("apple", "banana", "avocado", "apricot");

        // Factory producing a fresh, unconsumed stream on every get() call
        Supplier<Stream<String>> aFruitSupplier = () -> fruits.stream()
            .filter(f -> f.startsWith("a"));

        // 1st traversal
        aFruitSupplier.get().forEach(System.out::println);

        // 2nd traversal — brand-new stream instance, zero exceptions!
        long count = aFruitSupplier.get().count();
        System.out.println("Items starting with 'a': " + count);
    }
}
```

## 🔴 Senior Level

### API Design Code Smell: `Stream<T>` as a Public Method Parameter

Accepting an open `Stream<T>` as an argument in a public service or library method is a serious architectural anti-pattern:

```java
// ❌ ANTI-PATTERN: Accepting a Stream in public APIs
public void processOrders(Stream<Order> orderStream) {
    long total = orderStream.count(); // Stream is now consumed!
    // orderStream.forEach(this::save); // 💥 CRASHES AT RUNTIME!
}

// ✅ IDIOMATIC API DESIGN:
// 1. For in-memory data: Accept collections or iterables
public void processOrders(Collection<Order> orders) { /* ... */ }

// 2. For heavy/lazy generation: Accept a supplier factory
public void processOrders(Supplier<Stream<Order>> orderStreamSupplier) { /* ... */ }
```
The receiving method cannot verify if the caller has already consumed parts of the stream, closed it, or configured it with incompatible parallel flags.

### Operating System Resource Leaks with `AutoCloseable` Streams

Some stream sources hold underlying operating system resources:
- `Files.lines(Path)`
- `Files.walk(Path)`
- `Files.list(Path)`

These streams implement **`java.lang.AutoCloseable`** and register native file handles. **They must be enclosed in a `try-with-resources` block**:

```java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.stream.Stream;

public class StreamResourceLeakDemo {

    public static void readLog(Path path) throws IOException {
        // Enclose in try-with-resources to guarantee release of OS file descriptors:
        try (Stream<String> lines = Files.lines(path)) {
            lines.filter(l -> l.contains("ERROR"))
                 .forEach(System.out::println);
        } // lines.close() is guaranteed to execute upon exit
    }
}
```
If an I/O stream is abandoned without closing, the OS file descriptor remains locked until the garbage collector finalizer/cleaner triggers. Under high load, this causes `IOException: Too many open files`.

## 4 Tricky Questions

### 1. What happens under the hood when a developer attempts to execute a terminal operation on an already consumed stream?
**Answer:**
When any terminal operation executes, `AbstractPipeline.evaluate()` checks the private boolean field `linkedOrConsumed`.
- If `linkedOrConsumed` is already `true`, the method immediately throws an `IllegalStateException("stream has already been operated upon or closed")`.
- If `false`, it sets `linkedOrConsumed = true` and proceeds with execution.
This check is deterministic and irrevocable: there is no public API or internal mechanism to reset this flag back to `false`.

---

### 2. Why did the Java language architects decide against providing a `reset()` or `replay()` method on the `Stream` interface?
**Answer:**
Streams are designed around continuous flow processing, not in-memory storage.
1. Many stream sources are inherently non-rewindable (e.g., standard input `System.in`, network sockets, or non-deterministic random generators).
2. Implementing `reset()` would require buffering every single element passing through the pipeline in heap memory, defeating the primary purpose of streams: processing large or infinite datasets with minimal $O(1)$ intermediate memory overhead.

---

### 3. What hidden resource leak can occur when using the `Supplier<Stream<T>>` pattern with I/O streams?
**Answer:**
If the `Supplier` wraps an I/O-backed stream (e.g., `Supplier<Stream<String>> lines = () -> Files.lines(path)`), each call to `supplier.get()` opens a **brand-new operating system file descriptor**.

If callers invoke `supplier.get().forEach(...)` without enclosing each retrieved stream in a `try-with-resources` block, each iteration leaves an unclosed OS file handle dangling. Repeating this across requests rapidly exhausts the operating system's file handle table (`Too many open files`).

---

### 4. Why does `Stream<T>` not extend `Iterable<T>`, even though it defines an `iterator()` method?
**Answer:**
The `Iterable<T>` interface contract implies that clients can repeatedly call `iterator()` to perform multiple passes over the dataset (such as inside multiple `for-each` loops).

Because a `Stream` can only be traversed **once**, calling `stream.iterator()` consumes the stream. Invoking `stream.iterator()` a second time throws an `IllegalStateException`. Having `Stream` implement `Iterable` would violate the **Liskov Substitution Principle (LSP)**, as code expecting an `Iterable` would fail unexpectedly on subsequent traversals.

## 🎯 Interview Cheat Sheet

### `Iterable<T>` vs. `Stream<T>` Comparative Matrix
| Dimension | `Iterable<T>` (Collections) | `Stream<T>` (Pipelines) |
| :--- | :--- | :--- |
| **Traversals Allowed** | **Infinite** (Produces fresh iterator each time)| **Strictly Once** (Single-use) |
| **Data Storage** | Stores data in memory heap structures | Stores **no data** (Only computations) |
| **Evaluation Strategy**| Eager (Elements exist prior to iteration) | Lazy (Elements evaluated on demand) |
| **Parallel Execution** | Manual thread scheduling | Built-in via `.parallel()` |
| **Resource Management**| Pure heap memory | Can manage OS handles (`AutoCloseable`) |

---

### Key Takeaways
- **Strictly Single-Use:** Streams cannot be reused; doing so throws `IllegalStateException`.
- **Internal Guard:** `AbstractPipeline` enforces single-use via `linkedOrConsumed`.
- **Factory Solution:** Use `Supplier<Stream<T>>` to generate fresh streams on demand.
- **I/O Streams Must Be Closed:** Streams wrapping file descriptors (`Files.lines()`) must use `try-with-resources`.

---

### Red Flags & Anti-Patterns to Avoid
- ❌ **Storing a `Stream` in a class field for reuse:** Streams are consumed upon first terminal execution.
- ❌ **Accepting `Stream<T>` as a public method parameter:** Exposes APIs to unhandled lifecycle and state errors.
- ❌ **Searching for a non-existent `stream.reset()` method:** Streams cannot be reset.
- ❌ **Neglecting to close `Files.lines()` streams:** Causes OS file descriptor exhaustion (`Too many open files`).
