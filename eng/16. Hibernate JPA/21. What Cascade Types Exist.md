# What Cascade Types Exist

The **JPA (Jakarta Persistence)** specification and the **Hibernate** framework provide a set of cascading types that define which entity lifecycle management operations are automatically propagated from a parent entity to its associated child entities. Understanding each cascade type ensures the correct implementation of Domain-Driven Design (DDD) aggregate boundaries and prevents catastrophic accidental deletions of shared data.

---

## 🟢 Junior Level

### 6 Standard JPA `CascadeType` Values

The `jakarta.persistence.CascadeType` enum defines six fundamental cascading strategies:

| Cascade Type | Target `EntityManager` Call | Propagation Behavior |
| :--- | :--- | :--- |
| **`PERSIST`** | `entityManager.persist(parent)` | New child entities (`Transient`) are automatically passed to `persist()` and transition to `Managed`. |
| **`MERGE`** | `entityManager.merge(parent)` | Detached child entities (`Detached`) are merged back into the active persistence context. |
| **`REMOVE`** | `entityManager.remove(parent)` | Child records are physically deleted from the database when the parent is deleted. |
| **`REFRESH`** | `entityManager.refresh(parent)` | In-memory child entity state is forcefully refreshed from database rows. |
| **`DETACH`** | `entityManager.detach(parent)` | Associated child entities are evicted from the L1 cache, transitioning to `Detached`. |
| **`ALL`** | All operations simultaneously | Combines all five cascade strategies (`PERSIST`, `MERGE`, `REMOVE`, `REFRESH`, `DETACH`). |

```java
// Example: Combining specific cascade types safely:
@Entity
public class Document {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Persist and merge attachments with the document, but disallow cascading deletes:
    @OneToMany(mappedBy = "document", cascade = {CascadeType.PERSIST, CascadeType.MERGE})
    private List<Attachment> attachments = new ArrayList<>();
}
```

## 🟡 Middle Level

### Proprietary Hibernate Cascades (`org.hibernate.annotations.CascadeType`)

In addition to standard JPA, Hibernate provides vendor-specific cascading options through the `@org.hibernate.annotations.Cascade` annotation:

- **`SAVE_UPDATE`** *(Legacy Hibernate)*: Propagates non-standard `session.saveOrUpdate()` calls.
- **`LOCK`**: Propagates optimistic/pessimistic locks via `session.lock()` to associated entities.
- **`REPLICATE`**: Propagates cross-database data replication via `session.replicate()`.

*Best Practice:* Production architectures should strictly prefer the standard JPA `jakarta.persistence.CascadeType` over proprietary Hibernate annotations to preserve portability and consistency.

---

### Architectural Guideline: Composition vs. Association (DDD)

Cascade configuration must mirror the Domain-Driven Design model:

```
                    CASCADE STRATEGY BY RELATIONSHIP TYPE
                    
  1. COMPOSITION (Exclusive Ownership / Aggregate Root)
     Order ──────[1:N]──────► OrderItem
     Invoice ────[1:N]──────► InvoiceLine
     • Strategy: cascade = CascadeType.ALL, orphanRemoval = true
     • Rationale: An OrderItem has no meaning or lifecycle without its Order.
     
  2. ASSOCIATION (Shared Reference Between Independent Entities)
     Order ──────[N:1]──────► Customer
     Product ────[N:M]──────► Category
     • Strategy: NO cascade (or PERSIST/MERGE only where strictly necessary)
     • Rationale: Deleting an order must NEVER delete the customer!
```

## 🔴 Senior Level

### The Decoupled `PERSIST` and `MERGE` Trap

A subtle and frequent production bug occurs when developers configure `cascade = CascadeType.PERSIST` while omitting `CascadeType.MERGE`:

```java
@Entity
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(mappedBy = "order", cascade = CascadeType.PERSIST)
    private List<OrderItem> items = new ArrayList<>();
}
```

#### Runtime Scenario:
```java
// 1. Receive detached order (e.g., deserialized from REST payload)
Order detachedOrder = fetchOrderFromApi();
detachedOrder.getItems().get(0).setPrice(new BigDecimal("99.99"));

// 2. Merge within transactional service:
Order managedOrder = entityManager.merge(detachedOrder);
```
- Because the `items` collection only declares **`CascadeType.PERSIST`**, the `merge()` call **ignores the child collection**!
- The parent `Order` is updated in the database, but modified field values on `OrderItem` **are silently discarded and never written to the database**!
- **Rule:** When entities transition through detached states, `PERSIST` and `MERGE` should almost always be paired: `cascade = {CascadeType.PERSIST, CascadeType.MERGE}` (or `CascadeType.ALL`).

---

### The `CascadeType.REMOVE` Disaster on `@ManyToMany`

```java
@Entity
public class Student {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // ❌ CATASTROPHIC ANTI-PATTERN: Deleting a student deletes shared university courses!
    @ManyToMany(cascade = CascadeType.ALL)
    private List<Course> courses = new ArrayList<>();
}
```
If an administrative service deletes a single student via `entityManager.remove(student)`, Hibernate does not merely delete the join table link in `student_courses`—it **physically deletes the target `Course` rows from the database**! If `Course` also has reciprocal cascading to students, Hibernate cascades further, deleting every other student enrolled in that course.

*Senior Standard:* `CascadeType.REMOVE` is strictly prohibited on `@ManyToMany` relationships. Only `PERSIST` and `MERGE` are permissible.

## 4 Tricky Questions

### 1. If an association only has `CascadeType.PERSIST`, will saving a child via `repository.save(parent)` in Spring Data JPA work if the parent already exists in the database?

**Answer:**
1. **No, it will fail!**
2. In Spring Data JPA, `save(entity)` internally evaluates `entityInformation.isNew(entity)`.
3. Because the parent entity already has an ID assigned (`id != null`), Spring Data delegates to **`entityManager.merge(parent)`**, not `persist()`.
4. Since the association declares only `CascadeType.PERSIST`, the `merge()` operation does not propagate to the child collection. New child objects remain in the `Transient` state, and Hibernate throws:
   `org.hibernate.TransientPropertyValueException: object references an unsaved transient instance`.

---

### 2. What happens if a parent entity declares `CascadeType.ALL` on a child collection, but the database foreign key has an `ON DELETE RESTRICT` constraint?

**Answer:**
1. When invoking `entityManager.remove(parent)`, Hibernate traverses the cascade graph and enqueues individual SQL `DELETE` commands in the `ActionQueue` for every child entity first, and for the parent last.
2. Because Hibernate executes the SQL deletes for child records **before** deleting the parent row, the database-level `ON DELETE RESTRICT` constraint is **not violated**, and the operation succeeds.
3. A constraint violation would only occur if a raw native SQL delete was issued directly against the parent table without prior child deletion.

---

### 3. What happens to dirty in-memory child fields if you invoke `entityManager.refresh(parent)` on an association with `CascadeType.REFRESH`?

**Answer:**
1. The `REFRESH` operation propagates down the cascade tree to all managed child entities in the current session.
2. Hibernate issues individual SQL `SELECT` queries for each child entity: `SELECT * FROM child_table WHERE id = ?`.
3. Any in-memory dirty changes made to child entity fields in the JVM heap **are overwritten and discarded**, resetting the entities to the exact state currently stored in the database.

---

### 4. Why does `CascadeType.DETACH` fail to prevent `LazyInitializationException` after the session closes?

**Answer:**
1. `CascadeType.DETACH` only changes the persistence context status of entities from `Managed` to `Detached`.
2. If an associated lazy collection has not been loaded into memory prior to `detach()`, it remains an uninitialized `PersistentBag` proxy.
3. Detaching the parent severs its connection to the active Hibernate session and JDBC connection.
4. Calling `.get()` or iterating over the collection on the detached instance inevitably triggers a `LazyInitializationException`. `DETACH` affects persistence state, but does not fetch uninitialized data.

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
> "JPA provides 6 cascade types: `PERSIST`, `MERGE`, `REMOVE`, `REFRESH`, `DETACH`, and `ALL`. In enterprise architectures, cascading must strictly follow Domain-Driven Design aggregate boundaries: use `CascadeType.ALL` combined with `orphanRemoval = true` for strict compositions (`@OneToMany` such as `Order` -> `OrderItem`), where children have no independent lifecycle. Conversely, for `@ManyToOne` and `@ManyToMany` associations, `REMOVE` and `ALL` are strictly prohibited to prevent accidental deletion of shared domain entities. Crucially, `PERSIST` and `MERGE` operate independently: in Spring Data JPA, calling `save()` on an existing parent requires `CascadeType.MERGE` for child updates to persist."

---

### Key Production Metrics & Indicators
- **Cascade Graph Traversal Depth**: Monitored via APM tools; excessively deep cascade trees introduce significant latency during transaction commits.
- **Unintended SQL DELETE Rate**: Sudden spikes in delete statements indicating misconfigured cascade removal on shared associations.

---

### Red Flags (What NOT to Say)
- ❌ *"Always put `CascadeType.ALL` on every `@ManyToOne` mapping."* — Disastrous; deletes shared parent records when a child is removed.
- ❌ *"`CascadeType.PERSIST` automatically includes `CascadeType.MERGE`."* — False. They represent entirely independent entity lifecycle operations.
- ❌ *"Using `CascadeType.REMOVE` on `@ManyToMany` only removes entries from the join table."* — False. It physically deletes the target entity rows from their own primary tables.
- ❌ *"`CascadeType` rules are enforced directly by the database engine without Hibernate."* — JPA cascading is managed entirely in JVM memory by Hibernate's `ActionQueue`.
