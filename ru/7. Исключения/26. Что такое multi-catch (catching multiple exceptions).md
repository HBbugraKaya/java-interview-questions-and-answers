# Что такое multi-catch (catching multiple exceptions)

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
**Multi-Catch** — это синтаксическая конструкция Java (появившаяся в Java 7 в рамках Project Coin / JSR 334), позволяющая перехватывать несколько разнородных типов исключений в одном блоке `catch`, перечисляя их через символ вертикальной черты `|`: `catch (IOException | SQLException e)`.

Она решает проблему дублирования одинакового кода обработки для разных ошибок.

При использовании `multi-catch` действуют два строгих правила компилятора:
1. **Переменная `e` является неявно финальной (`final`):** ее значение нельзя переопределить (`e = new ...` вызовет ошибку компиляции).
2. **Типы исключений не должны наследоваться друг от друга:** запись `catch (FileNotFoundException | IOException e)` запрещена, так как дочерний тип уже включен в родительский.

---

### Базовый пример на Java 21

```java
import java.io.IOException;
import java.sql.SQLException;

public class MultiCatchExample {

    public void processData() {
        try {
            readExternalFile();
            saveToDatabase();
        } catch (IOException | SQLException e) {
            // Единая логика для обоих непересекающихся сбоев
            // e.getClass() вернет реальный тип возникшего исключения
            System.err.println("Infrastructure failure: " + e.getMessage());
            throw new ApplicationServiceException("Data processing failed", e);
        }
    }

    private void readExternalFile() throws IOException { }
    private void saveToDatabase() throws SQLException { }

    static class ApplicationServiceException extends RuntimeException {
        public ApplicationServiceException(String msg, Throwable cause) { super(msg, cause); }
    }
}
```

## 🟡 Middle Level

### Правило запрета наследования: почему нельзя `SubClass | SuperClass`?
Если в секции `multi-catch` указать классы, находящиеся в одной иерархии наследования, компилятор `javac` выдаст ошибку:
```java
// ❌ ОШИБКА КОМПИЛЯЦИИ:
// Alternatives in a multi-catch statement cannot be related by subclassing
// Alternative 'java.io.FileNotFoundException' is a subclass of 'java.io.IOException'
try {
    readFile();
} catch (FileNotFoundException | IOException e) {
    // ...
}
```

#### Причина запрета:
Конструкция `FileNotFoundException | IOException` избыточна (Redundant). Так как `FileNotFoundException` **уже является** `IOException`, тип `IOException` гарантированно перехватывает все подтипы. Спецификация Java (JLS §14.20) намеренно запрещает такое объединение, чтобы предотвратить появление логических ошибок и визуального мусора в кодовой базе.

*Как исправить:*
- Либо оставить только родительский класс: `catch (IOException e)` (если обработка одинакова).
- Либо разнести по отдельным блокам `catch`, поставив частный первым (если обработка различается).

---

### Почему переменная `e` в Multi-Catch строго `final`?
В обычном блоке `catch (IOException e)` переменная `e` формально не является финальной, и разработчик может переприсвоить ссылку: `e = new IOException()`.

В блоке `multi-catch` переменная `e` **всегда неявно объявлена как `final`**:
```java
try {
    run();
} catch (IOException | SQLException e) {
    // ❌ ОШИБКА КОМПИЛЯЦИИ:
    // Multi-catch parameter e is final and cannot be assigned
    // e = new IOException(); 
}
```
**Архитектурное обоснование:** Статический тип переменной `e` в `multi-catch` является синтетическим типом пересечения — наименьшим общим супертипом (Least Upper Bound). Если бы разрешалось присваивание `e = new IOException()`, возникла бы брешь в статической типизации: переменная `e` перестала бы соответствовать типу `SQLException`, если исходное исключение было именно им.

---

### Как Multi-Catch устроен в байткоде JVM
Несмотря на объединенный синтаксис исходного Java-кода, на уровне байткода виртуальной машины Java **нет специальной инструкции multi-catch**.

Компилятор генерирует в `Exception Table` метода **отдельные независимые строки** для каждого типа из списка `|`, но указывает для них **один и тот же адрес инструкции перехода (`target`)**:

```text
Exception table:
   from    to  target type
       0     8    12   Class java/io/IOException
       0     8    12   Class java/sql/SQLException
```
*Преимущество:* Исходный код чист и не содержит дублирования, а в байткоде генерируется ровно один экземпляр тела обработчика, уменьшая размер скомпилированного `.class`-файла.

## 🔴 Senior Level

### Precise Rethrow (Точный проброс исключений в Java 7+)
Одновременно с `multi-catch` в Java 7 была представлена мощная оптимизация анализа потока типов компилятора — **Precise Rethrow**:

```java
public class PreciseRethrowDemo {

    // В сигнатуре метода объявлены ТОЧНЫЕ типы, а не throws Exception!
    public void process() throws IOException, SQLException {
        try {
            if (System.currentTimeMillis() % 2 == 0) {
                throw new IOException("File error");
            } else {
                throw new SQLException("DB error");
            }
        } catch (Exception e) { // Перехватываем широкий тип Exception!
            System.err.println("Logging error before rethrow: " + e.getMessage());
            // Компилятор javac видит, что e не переприсваивалось (effectively final),
            // анализирует блок try и точно знает, что вылететь могут ТОЛЬКО IOException и SQLException!
            throw e; 
        }
    }
}
```
До Java 7 при перехвате `catch (Exception e)` повторный проброс `throw e` требовал обязательного объявления `throws Exception` в заголовке метода. Благодаря механизму Precise Rethrow компилятор сохраняет точную статическую типизацию.

---

### Канонический сценарий: Reflection API
До появления Multi-Catch работа со стандартным Reflection API превращалась в гигантские «лесенки» одинаковых обработчиков. С `multi-catch` код становится лаконичным:

```java
try {
    Class<?> clazz = Class.forName("com.service.Worker");
    Method method = clazz.getMethod("execute");
    method.invoke(clazz.getDeclaredConstructor().newInstance());
} catch (ClassNotFoundException | NoSuchMethodException | 
         InstantiationException | IllegalAccessException | 
         InvocationTargetException e) {
    log.error("Reflection initialization failed for reason: {}", e.getClass().getSimpleName(), e);
    throw new FrameworkInitException(e);
}
```

### Ловушка прерывания потока (`InterruptedException` в Multi-Catch)
Грубая ошибка — объединение `InterruptedException` с обычными исключениями ввода-вывода без восстановления флага:

```java
// ❌ СКРЫТЫЙ БАГ: потеря статуса прерывания!
try {
    Thread.sleep(100);
    socket.read();
} catch (InterruptedException | IOException e) {
    log.error("Error", e);
    // Если упал InterruptedException, поток очистил флаг прерывания!
    // Внешний пул потоков не узнает о необходимости остановки!
}

// ✅ ПРАВИЛЬНО:
try {
    Thread.sleep(100);
    socket.read();
} catch (InterruptedException | IOException e) {
    if (e instanceof InterruptedException) {
        Thread.currentThread().interrupt(); // Восстанавливаем статус!
    }
    log.error("Error", e);
}
```

## 🎯 Шпаргалка для интервью

### Вопросы для быстрой проверки
1. **Почему в `multi-catch` нельзя указать родительский и дочерний классы (например, `FileNotFoundException | IOException`)?**
   *Ответ:* Дочерний класс является подтипом родительского, поэтому родительский класс уже перехватывает все его экземпляры. Такое объявление избыточно и запрещено спецификацией языка (JLS §14.20).
2. **Почему переменная исключения `e` в `multi-catch` неявно объявлена как `final`?**
   *Ответ:* Потому что статическим типом переменной `e` является объединение типов (Least Upper Bound). Если бы разрешалось присваивание `e = new AnotherException()`, статическая типобезопасность остальных альтернатив была бы нарушена.
3. **Как виртуальная машина (JVM) исполняет блок `multi-catch` на уровне байткода?**
   *Ответ:* В таблице исключений метода (`Exception Table`) компилятор создает отдельные независимые записи для каждого класса, указанного в multi-catch, но направляет их на единый адрес байткода тела обработчика.
4. **Что такое Precise Rethrow в Java 7+?**
   *Ответ:* Это способность компилятора `javac` точно определять типы исключений при повторном `throw e` из блока `catch (Exception e)`. Если переменная `e` не переприсваивалась, компилятор анализирует блок `try` и требует указать в `throws` только реально возможные типы, а не общий `Exception`.

### Типичные ошибки и Red Flags
- ❌ **Попытка переприсвоить переменную `e` в блоке `multi-catch`:** Нарушает требование неявной финальности (`final`).
- ❌ **Объединение типов, связанных отношением наследования:** Не компилируется.
- ❌ **Объединение `InterruptedException` в `multi-catch` без восстановления флага:** Приводит к игнорированию команды отмены потока.
- ❌ **Утверждение: "Multi-Catch в байткоде генерирует общий класс-обертку":** В байткоде создаются обычные раздельные записи в `Exception Table`.
