# Чи можна використовувати примітивні типи як параметри дженериків

---

## 🟢 Junior Level

**Ні, не можна.** У сучасній Java дженерики можуть параметризуватися **тільки посилальними типами даних (Reference Types)**, що успадковуються від `java.lang.Object`.

Спроба передати примітивний тип (`int`, `double`, `boolean`, `char` тощо) як аргумент типу викличе помилку компіляції:

```java
// ❌ Помилки компіляції:
List<int> numbers = new ArrayList<>();       // Type argument cannot be of primitive type
Map<String, double> rates = new HashMap<>(); // Type argument cannot be of primitive type
Optional<boolean> flag = Optional.empty();   // Type argument cannot be of primitive type

// ✅ Рішення: використання відповідних посилальних класів-обгорток (Wrapper Classes):
List<Integer> numbers = new ArrayList<>();
Map<String, Double> rates = new HashMap<>();
Optional<Boolean> flag = Optional.empty();
```

### Таблиця примітивів та їхніх класів-обгорток

| Примітив | Клас-обгортка (`java.lang.*`) | Розмір примітива | Розмір обгортки в купі (64-bit JVM) |
| :--- | :--- | :--- | :--- |
| `byte` | `Byte` | 1 байт | 16–24 байти |
| `short` | `Short` | 2 байти | 16–24 байти |
| `int` | `Integer` | 4 байти | 16–24 байти |
| `long` | `Long` | 8 байтів | 24 байти |
| `float` | `Float` | 4 байти | 16–24 байти |
| `double` | `Double` | 8 байтів | 24 байти |
| `char` | `Character` | 2 байти | 16–24 байти |
| `boolean`| `Boolean` | 1 байт (у масивах) | 16–24 байти |

## 🟡 Middle Level

### 1. Архітектурна причина: Стирання типів у байткоді (Type Erasure)

Головна причина заборони примітивів полягає в моделі **Type Erasure** та системі команд JVM:

1. На рівні байткоду віртуальної машини змінна типу `T` стирається до `java.lang.Object`.
2. У JVM існує суворий поділ інструкцій:
   - Для посилальних об'єктів (`Object`) використовуються інструкції типу **`a`** (`aload`, `astore`, `areturn`). Посилання завжди займає один фіксований слот адресного простору (4 або 8 байтів).
   - Для примітивів використовуються спеціалізовані інструкції: **`i`** (`iload` для `int`), **`l`** (`lload` для `long`), **`d`** (`dload` для `double`). Більше того, `long` та `double` займають **два слоти** в стеку викликів!
3. Скомпільований метод `public Object get(int index)` фізично не може повернути в стек процесора примітивний `int` або `double` без пакування в об'єкт-обгортку.

### 2. Приховані пастки Автоупакування (Autoboxing / Unboxing)

Компілятор створює ілюзію прозорої роботи з примітивами завдяки механізму **автоупакування (autoboxing)**:

```java
List<Integer> list = new ArrayList<>();
list.add(42);         // Автоупакування: компілятор вставляє Integer.valueOf(42)
int val = list.get(0); // Розпакування (unboxing): компілятор вставляє list.get(0).intValue()
```

#### Пастка 1: NullPointerException при розпакуванні
Якщо елемент колекції дорівнює `null`, спроба розпакувати його в примітив призведе до прихованого `NullPointerException`:
```java
List<Integer> list = new ArrayList<>();
list.add(null);

int number = list.get(0); // 💥 NullPointerException! list.get(0) повернув null, виклик .intValue() падає!
```

#### Пастка 2: Порівняння через `==` та кеш обгорток
Клас `Integer` кешує значення в діапазоні від **-128 до 127** (через `IntegerCache`):
```java
Integer a = 127;
Integer b = 127;
System.out.println(a == b); // true (один і той самий об'єкт із кешу)

Integer c = 128;
Integer d = 128;
System.out.println(c == d); // ❌ false! Створено два різних об'єкти в купі!
```
Для порівняння обгорток завжди використовуйте метод **`.equals()`**.

## 🔴 Senior Level

### Проблема деградації продуктивності в Highload

Використання `List<Integer>` замість `int[]` у високонавантажених системах призводить до катастрофічного падіння ефективності:

1. **Витрата пам'яті (Memory Bloat)**:
   - Масив `int[1_000_000]` займає рівно **~4 МБ** неперервної пам'яті.
   - Список `ArrayList<Integer>` на 1 000 000 елементів займає **~32 МБ** (масив посилань на 8 МБ + 1 000 000 об'єктів `Integer` по 24 байти кожен). Витрата пам'яті зростає у **8 разів**!
2. **Промахи кешу процесора (CPU Cache Misses)**:
   При ітерації по примітивному масиву процесор апаратно передзавантажує сусідні байти у швидкий L1/L2 кеш (Spatial Locality). У випадку `ArrayList<Integer>` процесор читає посилання, після чого змушений стрибати по випадкових адресах купи, провокуючи затримки доступу до оперативної пам'яті (RAM Latency).
3. **Тиск на збирач сміття (GC Pressure)**:
   Мільйон короткоживучих об'єктів-обгорток засмічують `Eden Space`, викликаючи часті паузи Stop-the-World на збирання сміття.

#### Як вирішувати проблему в production:
- Використовувати **примітивні спеціалізації Streams**: `IntStream`, `LongStream`, `DoubleStream`.
- Використовувати спеціалізовані функціональні інтерфейси: `IntPredicate`, `ToIntFunction`, `LongConsumer`.
- Для великих обсягів даних застосовувати бібліотеки **примітивних колекцій**:
  - **fastutil** (`IntArrayList`, `Long2ObjectOpenHashMap`).
  - **Eclipse Collections** (`MutableIntList`).
  - **Agrona** / **Trove**.

### Майбутнє Java: Project Valhalla та Universal Generics

Головна мета **Project Valhalla (JEP 401)** — ліквідувати історичний розрив між примітивами та об'єктами під гаслом:
> *«Codes like a class, works like a code / value»*

1. **Value Classes (Identity-Free Types)**: типи, що не мають ідентичності (адреси об'єкта та заголовка). Вони незмінні і можуть зберігатися в пам'яті пласко (inlined у масиви), як звичайні примітиви.
2. **Universal Generics**: у майбутніх версіях Java дженерики зможуть параметризуватися примітивами та типами значень (`List<int>` або `List<Point.val>`), забезпечуючи щільне зберігання в пам'яті без автоупакування та зберігаючи типобезпеку.

## 4 Tricky Questions

### 1. Чому на рівні байткоду JVM фізично неможливо замінити `T` на `int` при реалізації дженериків через Type Erasure?
**Відповідь:** 
Тому що система команд байткоду JVM суворо типізована щодо типів даних на стеку операндів:
- Посилальні типи оперують командами сімейства `a` (`aload`, `astore`, `areturn`), розмір посилання фіксований (4 байти при Compressed OOPs або 8 байтів).
- Примітиви оперують спеціалізованими командами (`iload` для `int`/`boolean`/`byte`/`char`, `fload` для `float`, `lload` для `long`, `dload` для `double`). Типи `long` та `double` займають два слоти в стеку операндів.
При стиранні типів метод компілюється в одну універсальну сигнатуру: `public Object get(int i)` з інструкцією `areturn`. Цей скомпільований байткод фізично не може повернути примітивне 32-бітне число `int` або 64-бітний `double` без попереднього створення посилального об'єкта-обгортки на купі.

### 2. До якої прихованої помилки може призвести автоупакування в тернарному операторі: `Integer a = null; int x = condition ? a : 0;`?
**Відповідь:** 
Вираз завершиться винятком **`NullPointerException`**, якщо `condition == true`. 

У специфікації Java (JLS §15.25) для умовного оператора діє правило **Numeric Promotion**: якщо один з операндів є примітивним числом (`0`), а другий — числовою обгорткою (`Integer a`), то результуючий тип усього тернарного виразу приводиться до примітивного типу `int`. У результаті другий операнд неявно розгортається: `a.intValue()`. Оскільки `a == null`, при спробі виклику методу розпакування викидається `NullPointerException`.

### 3. Чи можна налаштувати розмір кешу для цілочисельних обгорток у JVM?
**Відповідь:** 
Так, але тільки для класу **`Integer`**. 

Діапазон кешування за замовчуванням становить від `-128` до `127`. Верхню межу кешу можна збільшити під час запуску JVM за допомогою прапорця:
`-XX:AutoBoxCacheMax=<size>` або системної властивості `-Djava.lang.Integer.IntegerCache.high=<size>`. 

Для інших типів (`Byte`, `Short`, `Long`, `Character`, `Boolean`) межі кешу жорстко зашиті в специфікації мови і зміні не підлягають. Для класів з плаваючою комою (`Float`, `Double`) кешування взагалі відсутнє.

### 4. Чим спеціалізовані інтерфейси на зразок `IntFunction<R>` кращі за стандартний `Function<Integer, R>`?
**Відповідь:** 
Інтерфейс `Function<Integer, R>` оголошує метод `R apply(Integer t)`, який вимагає передачі посилального об'єкта. При передачі примітивного `int` віртуальна машина змушена на кожен виклик виконувати операцію боксингу `Integer.valueOf(val)`. 

Інтерфейс `IntFunction<R>` оголошує метод `R apply(int value)`. Він приймає примітив `int` напряму через регістр процесора або стек операндів без створення проміжного об'єкта в купі, виключаючи виділення пам'яті, навантаження на збирач сміття та накладні витрати на виклики методів розпакування.

## 🎯 Шпаргалка для інтерв'ю

### Головне про примітиви в дженериках

- **Правило**: Примітиви в дженериках **заборонені**: `List<int>` не компілюється. Використовуються обгортки `List<Integer>`.
- **Причина**: Type Erasure стирає типи в `Object`. Примітиви не наслідують `Object` і вимагають інших інструкцій байткоду (`iload` замість `aload`).
- **Автоупакування**: Автоматичне перетворення `int` $\leftrightarrow$ `Integer`.
  - Небезпека: `NullPointerException` при розпакуванні `null`.
  - Кеш: `IntegerCache` від `-128` до `127` (налаштовується через `-XX:AutoBoxCacheMax`).
- **Highload оверхед**:
  - `Integer` важить 24 байти проти 4 байтів у `int` (у 6 разів більше пам'яті).
  - Руйнує кеш-локальність процесора (промахи CPU L1/L2).
- **Альтернативи в Highload**:
  - Примітивні стріми: `IntStream`, `LongStream`.
  - Примітивні бібліотеки: `fastutil`, `Eclipse Collections`.
- **Майбутнє**: Project Valhalla додасть Value Types та універсальні дженерики.
