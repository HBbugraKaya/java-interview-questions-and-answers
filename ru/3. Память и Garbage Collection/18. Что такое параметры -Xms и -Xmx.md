# Что такое параметры -Xms и -Xmx

---

## 🟢 Junior Level

Флаги `-Xms` и `-Xmx` — это базовые параметры виртуальной машины Java (JVM), управляющие размером кучи (**Java Heap**), в которой аллоцируются все объекты:

- **`-Xms<size>`** (*Memory Start*): начальный (минимальный) размер кучи при запуске JVM.
- **`-Xmx<size>`** (*Memory Maximum*): максимально допустимый размер кучи. При попытке приложения превысить этот лимит (и если Garbage Collector не смог освободить память) выбрасывается ошибка `java.lang.OutOfMemoryError: Java heap space`.

```bash
# Запуск приложения с начальной кучей 1 ГБ и максимальной 4 ГБ
java -Xms1g -Xmx4g -jar app.jar
```

### Суффиксы единиц измерения
- `k` или `K` — килобайты
- `m` или `M` — мегабайты
- `g` или `G` — гигабайты

```bash
java -Xms512m -Xmx2g -jar app.jar
```

### Значения по умолчанию (Ergonomics)
Если флаги не заданы явно, JVM рассчитывает их автоматически через механизм **JVM Ergonomics**, опираясь на доступную физическую RAM хоста или лимиты cgroups (контейнера):
- По умолчанию `-Xms` составляет примерно $1/64$ от физической памяти.
- По умолчанию `-Xmx` составляет примерно $1/4$ от физической памяти (но обычно не более 32 ГБ из-за ограничений Compressed OOPs).

## 🟡 Middle Level

### 1. Механика памяти: Reserved vs Committed

При запуске JVM с параметрами `-Xms` и `-Xmx` происходят два фундаментальных этапа работы с памятью операционной системы:

```
Виртуальное адресное пространство ОС:
[================== Reserved (-Xmx: 4 GB) ==================]
[=== Committed (-Xms: 1 GB) ===][........ Uncommitted ......]
  ↑ Реальные страницы RAM         ↑ Адреса зарезервированы,
                                    но страницы не выделены
```

1. **Reserved (Зарезервированная память):**
   При старте JVM выполняет системный вызов (`mmap` в Linux/POSIX с флагом `PROT_NONE` или `VirtualAlloc` с `MEM_RESERVE` в Windows) на полный размер `-Xmx`. Это непрерывный диапазон адресов виртуальной памяти, который резервируется за процессом, чтобы куча могла расти непрерывно. Физическая RAM при этом ещё не расходуется.
2. **Committed (Зафиксированная память):**
   Память в размере `-Xms` помечается как доступная для чтения и записи (`PROT_READ | PROT_WRITE` или `MEM_COMMIT`). ОС выделяет реальные физические страницы оперативной памяти по мере первого обращения к ним (lazy allocation / demand paging).

### 2. Почему в production рекомендуется `-Xms = -Xmx`?

Если `-Xms < -Xmx`, куча динамически растёт и сжимается в зависимости от загрузки, ориентируясь на флаги `-XX:MinHeapFreeRatio` (по умолчанию 40%) и `-XX:MaxHeapFreeRatio` (по умолчанию 70%):
- Когда доля свободной памяти после GC падает ниже `MinHeapFreeRatio`, JVM пытается расширить кучу до `-Xmx`.
- Перед расширением кучи JVM часто инициирует дополнительный сбор мусора (вплоть до Full GC в традиционных сборщиках), чтобы попытаться освободить место без обращения к ОС.
- Сам системный вызов `mmap/mprotect/VirtualAlloc` и аллокация страниц ОС порождают Stop-The-World паузы и латентность.

**Преимущества равенства `-Xms = -Xmx`:**
- **Предсказуемость:** размер кучи статичен с первой секунды работы;
- **Отсутствие пауз на ресайз:** JVM не тратит процессорное время и не тормозит потоки приложения запросами расширения кучи к ядру ОС;
- **Предотвращение OOM Killer:** если на хосте закончится память через 5 часов под нагрузкой, динамически растущая куча приведёт к аварийному завершению процесса операционной системой. Статический размер гарантирует, что если память есть на старте, приложение продолжит работу.

*Исключения:* CLI-утилиты, локальная разработка, серверless-функции (AWS Lambda) и микросервисы в динамических кластерах, где приоритетом является минимальное потребление RAM при простое.

### 3. Настройка памяти в контейнерах (Docker / Kubernetes)

Жестко задавать `-Xms` и `-Xmx` в мегабайтах внутри Dockerfile или deployment-манифестов — антипаттерн, так как при изменении лимитов пода в Kubernetes (`resources.limits.memory`) настройки JVM придётся менять вручную.

Начиная с Java 8u191 и Java 10+, JVM полностью поддерживает **Container Awareness (cgroups v1/v2)**. Для настройки памяти используют процентные соотношения:

```bash
# Рекомендуемый production-шаблон для микросервисов в контейнере:
java -XX:InitialRAMPercentage=75.0 \
     -XX:MaxRAMPercentage=75.0 \
     -XX:MinRAMPercentage=75.0 \
     -jar app.jar
```

- `-XX:MaxRAMPercentage=75.0`: выделяет 75% от общего лимита памяти контейнера под Java Heap.
- Оставшиеся 25% жизненно необходимы для **Non-Heap памяти** (Metaspace, Thread Stacks, Code Cache, GC-структур, Direct Memory) и ядра ОС.

## 🔴 Senior Level

### 1. Формула RSS: почему процесс потребляет больше `-Xmx`

Одна из частых аварий в Kubernetes — завершение пода по причине **OOMKilled (Exit Code 137)**, хотя метрики Heap показывают, что куча заполнена лишь наполовину.

Реальное потребление физической памяти процессом в ОС (**Resident Set Size — RSS**) рассчитывается по формуле:

$$\text{RSS} \approx \text{Heap (-Xmx)} + \text{Metaspace} + \text{CodeCache} + (\text{Threads} \times \text{-Xss}) + \text{DirectMemory} + \text{GC Overhead} + \text{Native Libraries}$$

```
+---------------------------------------------------------------+
|               Общий процесс JVM в ОС (RSS)                    |
| +-------------------------+ +-------------------------------+ |
| |        Java Heap        | |            Non-Heap           | |
| | (-Xms / -Xmx /          | | - Metaspace                   | |
| |  MaxRAMPercentage)      | | - Thread Stacks (-Xss)        | |
| |                         | | - Code Cache (JIT-код)        | |
| |                         | | - Direct Byte Buffers         | |
| |                         | | - GC Card Tables / Marks      | |
| |                         | | - Native memory (glibc malloc)| |
| +-------------------------+ +-------------------------------+ |
+---------------------------------------------------------------+
```

- **Thread Stacks:** каждый поток по умолчанию забирает 1 МБ памяти (`-Xss1m`). При 1000 потоков это 1 ГБ Native RAM вне кучи.
- **GC Overhead:** сборщики мусора хранят служебные структуры данных в native memory. Например, для G1 GC таблицы запомненных наборов (**RSet**) могут потреблять дополнительно до 10–15% от размера кучи.
- **Direct Memory:** буферы ввода-вывода (NIO `ByteBuffer.allocateDirect()`), активно используемые в Netty, gRPC, Kafka.
- **Инструмент контроля:** `-XX:NativeMemoryTracking=summary` и утилита `jcmd <pid> VM.native_memory summary`.

### 2. Граница 32 ГБ и Compressed OOPs

В 64-битных архитектурах указатели на объекты занимают 8 байт (64 бита), что увеличивает потребление кучи на 30–40% по сравнению с 32-битными системами. Для оптимизации JVM использует технологию **Compressed OOPs (Ordinary Object Pointers)** (`-XX:+UseCompressedOops`).

JVM хранит указатели не как байтовые адреса, а со сдвигом на 3 бита вправо (поскольку все объекты в Java выровнены по границе 8 байт). Это позволяет адресовать $2^{32} \times 8 = 32\text{ ГБ}$ памяти с помощью 32-битных указателей:

$$\text{Порог отключения Compressed OOPs} \approx 32\text{ ГБ}$$

> [!WARNING]
> Никогда не устанавливайте `-Xmx32g`!
> Если задать кучу ровно 32 ГБ (или 32768m), JVM выходит за диапазон адресации со сдвигом. Compressed OOPs **отключаются**, и JVM переходит на полноценные 64-битные указатели.
> В результате куча `-Xmx32g` вмещает **меньше реальных объектов**, чем куча `-Xmx31g`, а нагрузка на кэши процессора (L1/L2/L3) и пропускная способность шины памяти резко деградируют. Безопасный максимум для сжатых указателей обычно составляет около `31g` (или `31744m`).

### 3. Оптимизация запуска: `-XX:+AlwaysPreTouch`

По умолчанию ОС выделяет физическую память отложенно (*page fault on demand*). Когда Java-приложение запускается и начинает интенсивно обрабатывать запросы, каждое первое обращение к странице памяти вызывает прерывание процессора (page fault), вынуждая ядро ОС искать свободный физический фрейм и обнулять его. Это приводит к просадкам latency (*Tail Latency spikes*) в первые минуты работы приложения.

Флаг **`-XX:+AlwaysPreTouch`**:
- Заставляет JVM при старте во время инициализации кучи обойти все страницы памяти и записать в каждую нулевой байт.
- Выделение страниц происходит параллельно в несколько потоков (`-XX:PreTouchParallelChunkSize`).
- **Цена:** время старта JVM увеличивается (на куче в 64 ГБ старт может занять 5–15 секунд).
- **Выгода:** полное устранение page-fault задержек во время боевой работы сервиса.

### 4. Transparent Huge Pages (THP) и сборщики мусора

В Linux стандартный размер страницы виртуальной памяти равен 4 КБ. Huge Pages увеличивают этот размер до 2 МБ или 1 ГБ, уменьшая количество записей в TLB-кэше процессора (*Translation Lookaside Buffer*).

Однако механизм **Transparent Huge Pages (THP)** ядра Linux пытается объединять 4 КБ страницы в 2 МБ на лету с помощью фонового демона `khugepaged`. При работе с современными GC (особенно G1 GC, ZGC, Shenandoah) это вызывает катастрофические задержки:
- G1 оперирует небольшими регионами (1–32 МБ) и часто перемещает данные.
- Дефрагментация THP блокирует системные вызовы аллокации памяти, вызывая непредвиденные паузы Stop-the-World на десятки и сотни миллисекунд.
- **Рекомендация для High-Load:** отключать THP на уровне ОС (`echo madvise > /sys/kernel/mm/transparent_hugepage/enabled`) или использовать статические Huge Pages (`-XX:+UseLargePages`).

## 🎯 Шпаргалка для интервью

### 30-секундный ответ для собеседования
> «Параметры `-Xms` и `-Xmx` задают начальный и максимальный размер кучи JVM. `-Xmx` определяет границу зарезервированного виртуального адресного пространства (reserved), а `-Xms` — первоначально выделенную физическую память (committed). В production принято задавать `-Xms = -Xmx` (или `-XX:InitialRAMPercentage = -XX:MaxRAMPercentage`), чтобы устранить накладные расходы и GC-паузы на динамический ресайз кучи. Важно помнить, что общий процесс Java (RSS) всегда потребляет больше памяти, чем `-Xmx`, из-за Metaspace, Thread Stacks, Direct Buffers и служебных структур GC, поэтому под Heap в контейнерах выделяют не более 70–75% RAM».

### Вопросы повышенной сложности с ответами

1. **Что произойдёт, если задать `-Xms4g -Xmx4g`, но на сервере доступно всего 2 ГБ свободной физической памяти?**
   *Ответ:* Без флага `-XX:+AlwaysPreTouch` приложение успешно запустится, так как Linux выделит виртуальные адреса и зафиксирует их без мгновенной привязки к физическим фреймам (overcommit). Однако, как только JVM попытается фактически записать данные в память сверх 2 ГБ, ядро Linux завершит процесс сигналом SIGKILL через **OOM Killer**. С флагом `-XX:+AlwaysPreTouch` JVM упадёт сразу в момент старта с ошибкой нехватки памяти от ОС.

2. **Почему куча `-Xmx31g` может быть эффективнее, чем `-Xmx33g`?**
   *Ответ:* До границы ~32 ГБ JVM использует Compressed OOPs (сжатые 32-битные ссылки на объекты). При превышении этой границы (начиная примерно с 32 ГБ) сжатие отключается, и все ссылки становятся 64-битными (8 байт вместо 4). Это увеличивает размер графа объектов в памяти на 20–30%, вымывает кэши процессора и ухудшает производительность. Чтобы получить реальный выигрыш в полезной емкости после отключения Compressed OOPs, кучу нужно увеличивать сразу минимум до 40–48 ГБ.

3. **Почему контейнер в Kubernetes падает с Exit Code 137, если `-Xmx` равен лимиту памяти пода?**
   *Ответ:* Exit Code 137 означает отправку сигнала `SIGKILL` (128 + 9) системным механизмом Linux OOM Killer при превышении cgroups memory limit. Память процесса Java (RSS) складывается из Heap и Native Memory (Metaspace, стеки потоков `-Xss`, CodeCache, Direct Memory, таблицы GC). Если `-Xmx` равен лимиту контейнера, любая не-heap аллокация мгновенно вызовет превышение лимита cgroup и мгновенную смерть пода. Лимит кучи должен составлять 70–80% от лимита контейнера.

### Типичные ошибки и Red Flags
- ❌ **Считать, что `-Xmx` — это максимальный объём оперативной памяти, который может занять Java-приложение.** (Red Flag: непонимание архитектуры виртуальной машины, незнание Native Memory, Metaspace и Thread Stacks).
- ❌ **Выделять 95–100% памяти контейнера под `-Xmx` в Docker.** (Red Flag: гарантированный OOMKilled в продакшене).
- ❌ **Утверждать, что `-Xms` выделяет физическую память сразу при любых условиях.** (Заблуждение: без `-XX:+AlwaysPreTouch` физические страницы аллоцируются ОС лениво при первом чтении/записи).
- ❌ **Задавать размер кучи ровно 32 ГБ.** (Незнание механики Compressed OOPs).
