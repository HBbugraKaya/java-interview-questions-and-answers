# Как компилятор Java оптимизирует конкатенацию строк

---

## 🟢 Junior Level

Оптимизация конкатенации строк в Java — это многоуровневый процесс, распределенный между компилятором исходного кода (`javac`) и виртуальной машиной HotSpot JVM. Главная цель оптимизаций — свести к минимуму аллокации памяти в куче (Heap), избежать ненужных копирований массивов байтов и уменьшить нагрузку на сборщик мусора (GC).

### Суть в 30 секундах
Компилятор применяет две принципиальные стратегии оптимизации:
1. **На этапе компиляции (Compile-Time) — Свертка констант (Constant Folding):** Если компилятор видит склеивание строковых литералов или константных переменных (`final`), он складывает их прямо во время сборки кода. В скомпилированный `.class`-файл попадает одна готовая строка, а в рантайме процессор не тратит на это ни одного такта.
2. **Во время выполнения (Runtime) — Динамическая генерация кода (JEP 280):** Начиная с Java 9, для переменных компилятор `javac` больше не вшивает жесткий байткод со `StringBuilder`. Вместо этого генерируется инструкция `invokedynamic`, вызывающая фабрику `StringConcatFactory`. Фабрика вычисляет точный размер массива байтов, предотвращает промежуточные переаллокации и соединяет данные на уровне быстрых низкоуровневых инструкций.

```java
// 1. Оптимизация javac на этапе компиляции:
public static final String PREFIX = "ORDER_";
String id1 = PREFIX + "123" + "_PENDING"; 
// В байткод запишется: ldc "ORDER_123_PENDING" (0 вычислений в рантайме)

// 2. Оптимизация рантайма для динамических данных:
String generateKey(String entity, long id) {
    // В байткод генерируется invokedynamic makeConcatWithConstants
    // Примитив long форматируется напрямую в массив байт без боксинга в Long!
    return entity + ":" + id;
}
```

## 🟡 Middle Level

### Эволюция оптимизаций в версиях Java
Стратегия компилятора радикально менялась по мере развития платформы:
- **Java 1.0 – 1.4:** Выражение `a + b` компилировалось в `new StringBuffer().append(a).append(b).toString()`. Все вызовы были синхронизированными и медленными.
- **Java 5 – 8:** Замена на `new StringBuilder().append(a).append(b).toString()`. Синхронизация ушла, но байткод оставался жестко привязанным к классу `StringBuilder` с его дефолтной емкостью 16 символов, что приводило к лишним аллокациям при строках длиннее 16 символов.
- **Java 9+ (JEP 280: Indify String Concatenation):** Переход на `invokedynamic` и `StringConcatFactory`. Байткод стал компактным, стратегия генерации вынесена в рантайм, а аллокации стали строго однократными (Exact Sizing).

### Сравнение скомпилированного байткода
Для простого метода:
```java
public String concat(String first, int age) {
    return first + " is " + age;
}
```

**Байткод Java 8:**
```bytecode
0: new           #2  // class java/lang/StringBuilder
3: dup
4: invokespecial #3  // Method java/lang/StringBuilder."<init>":()V
7: aload_1
8: invokevirtual #4  // Method java/lang/StringBuilder.append:(Ljava/lang/String;)Ljava/lang/StringBuilder;
11: ldc           #5  // String  is 
13: invokevirtual #4  // Method java/lang/StringBuilder.append:(Ljava/lang/String;)Ljava/lang/StringBuilder;
16: iload_2
17: invokevirtual #6  // Method java/lang/StringBuilder.append:(I)Ljava/lang/StringBuilder;
20: invokevirtual #7  // Method java/lang/StringBuilder.toString:()Ljava/lang/String;
23: areturn
```
*Минусы:* 8 инструкций байткода, создание объекта `StringBuilder`, возможный resize буфера при вызове `append`.

**Байткод Java 9+ (Java 17/21):**
```bytecode
0: aload_1
1: iload_2
2: invokedynamic #7,  0 // InvokeDynamic #0:makeConcatWithConstants:(Ljava/lang/String;I)Ljava/lang/String;
7: areturn
```
*Плюсы:* Всего 3 инструкции. Байткод уменьшился в 3 раза. Создание промежуточного `StringBuilder` полностью отсутствует.

### Типичные ошибки понимания оптимизаций
1. **Заблуждение: «Компилятор оптимизирует `+=` в циклах»:**
   Компилятор оптимизирует только **отдельные выражения**. Конкатенация внутри цикла превращается в повторные вызовы `invokedynamic` на каждой итерации, что дает $O(N^2)$ аллокаций.
2. **Заблуждение: «`final` переменная всегда участвует в Constant Folding»:**
   Если `final` переменная инициализируется вызовом метода (`final String a = UUID.randomUUID().toString();`), компилятор не знает ее значения на этапе компиляции, и оптимизация Constant Folding не применяется.

## 🔴 Senior Level

### Архитектура `StringConcatFactory` и механизм рецептов
При генерации байткода `javac` формирует статическую метаинформацию — строку-рецепт (Recipe String) и передает ее в качестве статического аргумента Bootstrap-метода (BSM):
```java
public static CallSite makeConcatWithConstants(
    MethodHandles.Lookup lookup,
    String name,
    MethodType concatType,
    String recipe,
    Object... constants)
```
- Спецсимвол `\1` кодирует аргумент из стека (`aload`, `iload`).
- Спецсимвол `\2` кодирует константу из массива `constants`.

Например, для выражения `"User: " + user + " (id=" + id + ")"` рецепт выглядит как:
$$\text{Recipe} = \text{"User: \textbackslash 1 (id=\textbackslash 1)"}$$

### Стратегии генерации машинного кода в HotSpot
JVM управляет способом исполнения конкатенации через системное свойство:
`-Djava.lang.invoke.stringConcat=<strategy>`

| Стратегия | Принцип работы | Характеристики |
| :--- | :--- | :--- |
| **`INLINE_SIZED_EXACT`** *(По умолчанию)* | Генерирует высокооптимизированный `MethodHandle`, вычисляющий точную длину всех операндов, аллоцирующий `byte[]` нужного размера и раскладывающий данные байт за байтом. | Минимальное число инструкций, нулевые лишние копирования, нет промежуточных объектов в Heap. |
| **`METHOD_HANDLE_INLINE_SIZED_EXACT`** | Строит дерево комбинаторов `MethodHandle` (`filterArguments`, `foldArguments`). | Работает без генерации на лету анонимных классов, экономит Metaspace. |
| **`BC_SB` (Bytecode StringBuilder)** | Генерирует байткод на базе `StringBuilder`. | Резервный (fallback) режим для отладки или систем с жесткими ограничениями Metaspace. |

### Оптимизация примитивов без боксинга
В стратегии Java 8 при вызове `sb.append(age)` вызывался перегруженный метод, который внутри вызывал `Integer.toString(int)`. Это нередко приводило к созданию временной строки.
В `StringConcatFactory`:
1. Тип операнда передается в сигнатуре вызова как примитив (`I`, `J`, `Z`).
2. Генерируемый код напрямую вызывает алгоритм `Integer.stringSize(int)` для подсчета количества цифр.
3. Цифры записываются напрямую в итоговый массив байтов через внутренний метод `Integer.getChars(int, int, byte[])`.
4. **Результат:** Ноль аллокаций `java.lang.Integer` и ноль временных строковых объектов!

### Векторизация и SIMD в Compact Strings
Поскольку с Java 9 строки используют массив байт (`byte[] value`) и флаг кодировки (`coder`: 0 для Latin-1, 1 для UTF-16), `StringConcatFactory` учитывает флаги операндов:
- Если все операнды Latin-1, создается массив размера $\sum \text{length}_i$ с `coder = 0`.
- Если хотя бы один операнд UTF-16, размер удваивается, и `coder = 1`.
Копирование байтов выполняется через C2 intrinsic на базе векторных процессорных инструкций (AVX-2, AVX-512 на x86 или NEON на ARM64), копирующих по 32 или 64 байта за один такт процессора.

## 4 Tricky Questions

### 1. Почему создатели Java заменили генерацию `StringBuilder` на `invokedynamic` (JEP 280), вместо того чтобы научить `javac` сразу аллоцировать `byte[]` нужного размера?
**Ответ:**
Главная архитектурная причина — **развязка байткода и рантайма (Bytecode Decoupling)**:
1. Компилятор `javac` не должен знать деталей внутренней реализации HotSpot JVM. Если бы `javac` генерировал байткод прямого обращения к `byte[] value` и полю `coder`, этот байткод нарушил бы инкапсуляцию и перестал работать на других JVM или при изменении внутреннего представления `String`.
2. `invokedynamic` позволяет JVM обновлять стратегию конкатенации «на лету» без перекомпиляции прикладных библиотек. Например, при обновлении с Java 11 на Java 21 приложение автоматически получает ускоренные SIMD-инструкции копирования памяти, скомпилированные новым JIT-компилятором, хотя `.class`-файлы были собраны много лет назад.

### 2. Что произойдет на уровне байткода и рантайма при вычислении `String s = "A" + 1 + "B" + 2`?
**Ответ:**
Все операнды в данном выражении являются константами времени компиляции (Compile-Time Constants).
Согласно спецификации JLS §15.28, компилятор `javac` **целиком свернет это выражение во время компиляции (Constant Folding)**.
В байткоде не будет ни инструкции `invokedynamic`, ни вызова `StringConcatFactory`, ни `StringBuilder`. В пуле констант класса (`Constant Pool`) будет создана одна запись типа `CONSTANT_String_info` со значением `"A1B2"`, которая будет загружена одной командой `ldc #X`.

### 3. Как компилятор обрабатывает многострочные текстовые блоки (Text Blocks, Java 15+) и есть ли у них накладные расходы по сравнению с обычной конкатенацией?
**Ответ:**
Многострочные текстовые блоки `""" ... """` обрабатываются компилятором `javac` **исключительно на этапе компиляции**:
1. Компилятор определяет минимальный общий отступ всех непустых строк и удаляет его (Strip Incidental White Space).
2. Заменяет все переводы строк на единый стандартный символ `\n` независимо от операционной системы сборки.
3. Интерпретирует escape-последовательности (например, `\` для подавления переноса строки).
4. Результирующая строка помещается в Constant Pool как единый неделимый строковый литерал.
Накладные расходы в рантайме равны **абсолютному нулю** (0 аллокаций, 0 операций конкатенации), так как текстовый блок загружается в память командой `ldc` как готовый объект.

### 4. Какой оверхед дает первый вызов конкатенации через `invokedynamic` и почему его не стоит бояться?
**Ответ:**
При самом первом вызове конкретной инструкции `invokedynamic` происходит фаза **Bootstrap Linkage**:
1. JVM переключается на вызов метода `StringConcatFactory.makeConcatWithConstants`.
2. Фабрика генерирует код класса-адаптера или цепочку `MethodHandle`.
3. Точка вызова связывается в постоянный `CallSite`.
Это занимает порядка **1–5 микросекунд** процессорного времени (one-time cost). Однако при всех последующих миллиардах вызовов процессор исполняет сгенерированный машинный код напрямую. Более того, JIT-компилятор C2 инлайнит полученный `MethodHandle`, устраняя накладные расходы виртуальных вызовов, что в долгосрочной перспективе делает суммарную производительность на 50–70% выше старого `StringBuilder`.

## 🎯 Шпаргалка для интервью

### 30-секундный ответ
> «Компилятор Java оптимизирует конкатенацию строк на двух уровнях. Во-первых, литералы и `final`-константы склеиваются еще на этапе компиляции через Constant Folding, попадая в байткод как готовая строка. Во-вторых, для динамических переменных начиная с Java 9 компилятор генерирует инструкцию `invokedynamic` (`StringConcatFactory`, JEP 280), которая в рантайме точно рассчитывает размер итогового массива байтов, устраняет боксинг примитивов и создает строку за одну прямую аллокацию без использования промежуточных объектов `StringBuilder`».

### Ключевые тезисы для Senior-интервью
1. **JLS §15.28 Constant Folding:** Применяется только если операнды — константы времени компиляции (литералы, примитивы, `final` переменные без динамической инициализации).
2. **JEP 280 (Java 9+):** Замена жесткого байткода `StringBuilder` на `invokedynamic makeConcatWithConstants`.
3. **Recipe String:** Рецепт конкатенации со спецсимволами `\1` (динамические аргументы) и `\2` (константы).
4. **Точный расчет размера (Exact Sizing):** Отсутствие паразитных переаллокаций и копирований массивов.
5. **No Boxing:** Примитивы (`int`, `long`) конвертируются в массив байтов напрямую через `Integer.getChars()` без создания `Integer`.
6. **Циклы `+=`:** Не оптимизируются компилятором! Для циклов по-прежнему обязателен `StringBuilder`.

### Красные флаги (Чего говорить категорически нельзя)
- ❌ Утверждать, что `javac` в современных версиях Java переписывает конкатенацию в `StringBuilder` (в Java 9+ используется `invokedynamic`).
- ❌ Полагать, что `invokedynamic` спасает от медлительности конкатенации в циклах (в циклах `invokedynamic` вызывается заново на каждой итерации с $O(N^2)$ аллокациями).
- ❌ Думать, что текстовые блоки (`"""`) склеиваются в рантайме (они сворачиваются в литерал на этапе компиляции).
