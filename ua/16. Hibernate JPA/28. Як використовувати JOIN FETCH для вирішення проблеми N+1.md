# Як використовувати JOIN FETCH для вирішення проблеми N+1

Конструкція **`JOIN FETCH`** у JPQL/HQL — це фундаментальний інструмент оптимізації в JPA та Hibernate, призначений для ліквідації проблеми **$N+1$ запитів**. Вона наказує ORM-рушію не просто об'єднати таблиці на рівні бази даних, а й **за один єдиний SQL-запит ініціалізувати та матеріалізувати пов'язані дочірні сутності або колекції** прямо в кеші першого рівня L1, запобігаючи відкладеним поодиноким запитам при подальших зверненнях до гетерів.

---

## 🟢 Junior Level

### Як працює `JOIN FETCH`

Класична проблема $N+1$ виникає, коли при вибірці списку батьківських сутностей пов'язані дані підвантажуються ліниво окремими запитами в циклі:

```java
// ПРОБЛЕМА N+1:
// 1 запит: SELECT * FROM orders; (отримали 100 замовлень)
List<Order> orders = entityManager.createQuery("SELECT o FROM Order o", Order.class).getResultList();

for (Order order : orders) {
    // 100 окремих запитів: SELECT * FROM order_items WHERE order_id = ?;
    System.out.println(order.getItems().size()); 
}
// Разом: 1 + 100 = 101 запит до бази даних!
```

З використанням `JOIN FETCH` вся вибірка вкладається в **1 SQL-запит**:

```java
// РІШЕННЯ З JOIN FETCH:
List<Order> orders = entityManager.createQuery(
    "SELECT o FROM Order o JOIN FETCH o.items", 
    Order.class
).getResultList();

// Разом: РІВНО 1 SQL-запит із фізичним JOIN у СУБД!
// Колекції o.getItems() вже завантажені в пам'ять та ініціалізовані.
```

### Різниця між `JOIN` та `JOIN FETCH` у JPQL

| Конструкція | Що відбувається в БД | Що завантажується в пам'ять JVM | Проблема $N+1$ |
| :--- | :--- | :--- | :--- |
| **`JOIN`** | Генерує SQL `INNER JOIN` | Завантажує **тільки батьківські сутності**. Дочірні поля залишаються неініціалізованими проксі. | ❌ **Не вирішує** (при зверненні до гетера підуть $N$ запитів) |
| **`JOIN FETCH`** | Генерує SQL `INNER JOIN` | Завантажує **і батька, і пов'язані сутності**, одразу гідруючи поля та колекції. | ✅ **Повністю вирішує** за 1 запит |

## 🟡 Middle Level

### Еволюція `DISTINCT`: Hibernate 5 проти Hibernate 6

При виконанні SQL `JOIN` реляційна СУБД повертає декартів добуток рядків: якщо в замовленні 3 позиції, таблиця поверне 3 пласкі рядки з однаковими колонками замовлення.

- **У Hibernate 5.x:** Розробник був зобов'язаний вручну писати `SELECT DISTINCT o FROM Order o JOIN FETCH o.items`. Ключове слово `DISTINCT` слугувало інструкцією Hibernate: дедуплікувати посилання в оперативній пам'яті JVM, щоб `getResultList()` не повертав три однакові екземпляри `Order`.
- **У Hibernate 6.x:** Новий рушій запитів (Semantic Query Model) **виконує дедуплікацію коренів у пам'яті АВТОМАТИЧНО** для будь-яких запитів із колекційними `JOIN FETCH`! Писати `DISTINCT` у JPQL більше не потрібно, якщо тільки вам не потрібен реальний SQL `DISTINCT` на стороні СУБД.

### Катастрофа пагінації: `HHH000104: applying in memory!`

Найнебезпечніша помилка Middle-розробників — спроба пагінувати колекційний `JOIN FETCH`:

```java
// ❌ СМЕРТЕЛЬНО НЕБЕЗПЕЧНО ДЛЯ PRODUCTION:
TypedQuery<Order> query = entityManager.createQuery(
    "SELECT o FROM Order o JOIN FETCH o.items", 
    Order.class
);
query.setFirstResult(0);
query.setMaxResults(10); // Хочемо отримати перші 10 замовлень
List<Order> orders = query.getResultList();
```

#### Що відбувається всередині:
1. У SQL `LIMIT` та `OFFSET` працюють із **рядками результату**, а не із сутностями. Якщо замовлення містить 5 позицій, `LIMIT 10` поверне всього 2 замовлення і шматок третього!
2. Hibernate розуміє, що не може безпечно застосувати SQL `LIMIT`, і виводить у лог попередження:
   `WARN: HHH000104: firstResult/maxResults specified with collection fetch; applying in memory!`.
3. **Наслідок:** Hibernate **викачує АБСОЛЮТНО ВСЮ ТАБЛИЦЮ з бази даних у пам'ять JVM**, а обрізання до 10 елементів робить у Java-коді через `List.subList()`! На таблиці в мільйон рядків це миттєвий `OutOfMemoryError`.

## 🔴 Senior Level

### Двоетапна пагінація (Two-Phase Pagination Pattern)

Щоб безпечно пагінувати сутності разом із дочірніми колекціями, застосовується патерн розділення запитів:

```java
// Етап 1: Отримуємо тільки ID потрібної сторінки замовлень із реальним SQL LIMIT/OFFSET
List<Long> orderIds = entityManager.createQuery("""
    SELECT o.id FROM Order o 
    ORDER BY o.createdAt DESC
    """, Long.class)
    .setFirstResult(page * size)
    .setMaxResults(size)
    .getResultList();

// Етап 2: Викачуємо повні дані замовлень із колекціями тільки для цих 10 ID
List<Order> orders = entityManager.createQuery("""
    SELECT o FROM Order o 
    JOIN FETCH o.items 
    WHERE o.id IN (:ids) 
    ORDER BY o.createdAt DESC
    """, Order.class)
    .setParameter("ids", orderIds)
    .getResultList();
```
СУБД швидко відпрацьовує індексний `LIMIT/OFFSET`, а другий запит завантажує рівно 10 замовлень без викачування таблиці в пам'ять.

### Помилка `MultipleBagFetchException`

Спроба одночасно завантажити дві колекції типу `List` (`java.util.List` у Hibernate трактується як `Bag` — несортована колекція з дублікатами):

```java
// ❌ ВИКИНЕ ВИНЯТОК ПРИ СТАРТІ:
@Query("SELECT o FROM Order o JOIN FETCH o.items JOIN FETCH o.payments")
List<Order> findFullOrders();
```
Hibernate викидає:
`org.hibernate.loader.MultipleBagFetchException: cannot simultaneously fetch multiple bags: [com.example.Order.items, com.example.Order.payments]`.

#### Причина:
Об'єднання двох колекцій через `JOIN` породжує декартове множення ($N \times M$ рядків). Hibernate не може однозначно відновити початкову кількість елементів у списках `List` без унікальних ключів.

#### 3 способи вирішення:
1. **Замінити `List` на `Set`:** Для колекцій типу `java.util.Set` Hibernate дозволяє множинний `JOIN FETCH`, проте ризик величезного декартового добутку в мережі залишається.
2. **Використовувати `@BatchSize`:** Зробити `JOIN FETCH` для першої колекції (`items`), а для другої (`payments`) налаштувати `@BatchSize(size = 50)`.
3. **Розбити на два послідовні запити** в межах однієї транзакції (кеш L1 збере сутності докупи).

## 4 Tricky Questions

### 1. Що означає попередження `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory!` і чому воно неприпустиме в production?

**Відповідь:**
1. Це попередження означає, що Hibernate вимкнув генерацію SQL-конструкцій `LIMIT` та `OFFSET` у базі даних.
2. Замість цього Hibernate виконав повний запит до всієї таблиці без обмежень, завантажив усі рядки таблиці та пов'язані колекції в пам'ять JVM і виконав пагінацію вручну в купі.
3. У продакшені це призводить до катастрофічного споживання пам'яті, затримок на Full GC та неминучого падіння застосунку з `java.lang.OutOfMemoryError`.

### 2. Чому в Hibernate 6 ключове слово `DISTINCT` у запитах із `JOIN FETCH` більше не потрібне для усунення дублікатів у Java-коді?

**Відповідь:**
1. У Hibernate 5 дедуплікація сутностей у пам'яті активувалася виключно прапорцем `DISTINCT` у HQL-запиті (`QueryHints.HINT_PASS_DISTINCT_THROUGH`).
2. У Hibernate 6 рушій SQM розділяє поняття *семантичного DISTINCT* (у Java) та *SQL DISTINCT* (у базі).
3. За замовчуванням Hibernate 6 завжди автоматично дедуплікує кореневі сутності в пам'яті при обробці колекційних джойнів, позбавляючи розробників необхідності засмічувати JPQL ключовим словом `DISTINCT`.

### 3. Чим відрізняється `EntityGraph` з хінтом `fetchgraph` від `loadgraph` при заміні `JOIN FETCH`?

**Відповідь:**
1. **`jakarta.persistence.fetchgraph`:** Розглядає вказані в графі атрибути як `EAGER`, а **всі інші атрибути сутності примусово переводить у `LAZY`** (навіть ті, які в класі сутності були оголошені як `EAGER`).
2. **`jakarta.persistence.loadgraph`:** Розглядає вказані в графі атрибути як `EAGER`, а всі інші атрибути завантажує відповідно до їхніх **дефолтних налаштувань у сутності** (статичні `EAGER` залишаються жадібними).

### 4. Чи можна використовувати `JOIN FETCH` для зв'язку `@ManyToOne`, і чи виникають при цьому проблеми з пагінацією та декартовим добутком?

**Відповідь:**
1. **Так, можна і треба!** `JOIN FETCH` для зв'язків `@ManyToOne` та `@OneToOne` є ідеальним вирішенням проблеми $N+1$.
2. На відміну від колекцій (`@OneToMany`), зв'язок `@ManyToOne` повертає суворо **один рядок на один батьківський об'єкт** (кардинальність $1:1$).
3. Декартів добуток не виникає, дублікати не плодяться, а СУБД **абсолютно коректно застосовує `LIMIT` та `OFFSET`** прямо в SQL-запиті без будь-якого in-memory оверхеду.

## 🎯 Шпаргалка для інтерв'ю

### 30-секундна відповідь (Elevator Pitch)
> «Конструкція `JOIN FETCH` у JPQL/HQL вирішує проблему $N+1$, завантажуючи пов'язані сутності або колекції за один SQL-запит разом із батьком. Головні правила та обмеження:
> 1) Ніколи не використовувати пагінацію (`Pageable`, `setFirstResult`) разом із колекційним `JOIN FETCH`, інакше Hibernate вивантажить усю таблицю в пам'ять JVM (`HHH000104`); правильне рішення — двоетапна пагінація за ID.
> 2) Не робити `JOIN FETCH` кількох колекцій типу `List` одночасно через помилку `MultipleBagFetchException` та декартів добуток; для другої колекції використовується `@BatchSize`.
> 3) У Hibernate 6 ключове слово `DISTINCT` для видалення дублікатів у пам'яті більше не потрібне, дедуплікація виконується автоматично».

### Ключові метрики для Production-моніторингу
- **Кількість попереджень `HHH000104` у логах застосунку**: критичний маркер некоректної пагінації в пам'яті.
- **Розмір мережевого пакета JDBC (Row Fetch Size)**: сплески обсягу трафіку вказують на декартове множення при множинних джойнах.

### Червоні прапорці (Чого говорити НЕ МОЖНА)
- ❌ *«Звичайний JOIN і JOIN FETCH роблять одне й те саме»* — Звичайний `JOIN` не ініціалізує пов'язані сутності та залишає $N+1$.
- ❌ *«Пагінація зі Spring Data Pageable чудово працює з JOIN FETCH колекції»* — Викличе in-memory пагінацію всієї таблиці та OOM.
- ❌ *«Я роблю JOIN FETCH одразу для 4 колекцій в одному запиті»* — Викличе або `MultipleBagFetchException`, або гігабайти декартового добутку.
- ❌ *«Для зв'язку @ManyToOne не можна використовувати JOIN FETCH»* — Навпаки, для `@ManyToOne` він абсолютно безпечний і не ламає пагінацію.
