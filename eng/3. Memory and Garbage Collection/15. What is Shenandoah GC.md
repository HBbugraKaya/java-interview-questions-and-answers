# What is Shenandoah GC

---

## 🟢 Junior Level

**Shenandoah GC** is an open-source, ultra-low latency Garbage Collector originally developed by Red Hat and integrated into OpenJDK. It is designed to achieve **sub-millisecond to low single-digit millisecond (1–10 ms) Stop-The-World (STW) pause times** across heaps ranging from a few gigabytes to multiple terabytes.

---

### Real-World Analogy
Think of **relocating an entire corporate department to a new office building**:
- Under **G1 GC**, moving day requires declaring a mandatory company-wide holiday (a Stop-The-World pause). All employees must stop working while movers pack desks, load trucks, and set up the new office before employees can log back in.
- Under **Shenandoah GC**, movers pack and relocate desks **concurrently while employees continue typing on their laptops**. If an employee reaches for their desk phone while it is on the elevator, a receptionist transparently redirects the call to their mobile phone (**Load-Reference Barrier**). The only interruptions are two brief 30-second standup meetings to announce moving start and completion.

---

### Key Architectural Innovation: Concurrent Evacuation

The fundamental difference between G1 GC and Shenandoah lies in the **Evacuation (Compaction) Phase**:
- **G1 GC:** Executes concurrent marking, but **evacuation is strictly Stop-The-World**. If G1 needs to evacuate 2 GB of surviving live objects, all application mutator threads are frozen for 50–200 ms.
- **Shenandoah GC:** Executes **both marking and evacuation concurrently** alongside application threads. Live objects are copied to clean regions while the application processes incoming HTTP requests, keeping STW pauses consistently below 10 ms regardless of heap size.

```
┌────────────────────────────────────────────────────────┐
│           G1 GC vs. Shenandoah Pause Mechanics         │
├────────────────────────────────────────────────────────┤
│ G1 GC:       [ Marking (Conc) ] ──> [ Evacuation (STW Pause: 50-200ms) ]
│ Shenandoah:  [ Marking (Conc) ] ──> [ Evacuation (CONCURRENT: 0ms STW) ]
└────────────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### Evolution of Barriers: Brooks Pointers vs. Load-Reference Barriers (LRB)

Shenandoah's ability to move objects concurrently without thread synchronization conflicts evolved through two distinct generations:

```
┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
│            Legacy Brooks Pointers (Java 12–13)         │          Modern Load-Reference Barriers (Java 14+)     │
├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
│ • Added an 8-byte forwarding pointer to EVERY header   │ • Completely eliminated the extra 8-byte header field  │
│ • Pointed to itself (`obj.forwardee = obj`)            │ • Forwarding pointer is encoded temporarily directly   │
│ • Relocation updated pointer via atomic CAS            │   into the existing Mark Word during evacuation        │
│ • Fatal Flaw: 10%–20% heap memory overhead bloat!      │ • Zero object header bloat; uses JIT LRB on reads      │
└────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

#### How Modern Load-Reference Barriers (LRB) Work:
When an application thread dereferences an object pointer (`obj.field`), the JIT-compiled Load-Reference Barrier checks whether the object resides in a region currently undergoing evacuation (in the Collection Set):
- If the object has already been copied, the barrier fetches the updated address from the Mark Word's forwarding entry and returns the new copy.
- If the object has not yet been evacuated, the thread assists the GC by copying the object itself using an atomic CAS operation, ensuring live mutators never observe stale object states.

---

### Shenandoah Operational Lifecycle

Shenandoah alternates through 8 coordinated phases, of which **only 4 are brief STW pauses** (lasting ~0.5 ms to 1 ms each):

```
1. Init Mark (STW, ~0.5ms) ──────────> Scans initial GC Roots
2. Concurrent Marking ───────────────> Traces live object graph (SATB)
3. Final Mark (STW, ~1.0ms) ─────────> Drains SATB buffers; selects Collection Set (CSet)
4. Concurrent Evacuation ────────────> Copies live objects to clean regions concurrently
5. Init Update Refs (STW, ~0.5ms) ───> Prepares memory for reference updates
6. Concurrent Update References ─────> Rewires pointers across the heap concurrently
7. Final Update Refs (STW, ~0.5ms) ──> Rewires pointers in GC Roots
8. Concurrent Cleanup ───────────────> Reclaims completely empty regions in background
```

### Shenandoah vs. ZGC: Architectural Comparison

| Dimension | Shenandoah GC | ZGC |
|---|---|---|
| **Primary Developer** | Red Hat / OpenJDK Community | Oracle |
| **Barrier Mechanism** | **Load-Reference Barriers (LRB)** | Colored Pointers + Load Barriers |
| **Compressed OOPs** | **Fully Supported** (`-XX:+UseCompressedOops`) | **Not Supported** (Strictly 64-bit pointers) |

## 🔴 Senior Level

### The Graceful Degradation Model: Pacing, Degenerated GC, and Full GC

When application allocation rates outpace background GC evacuation speed, Shenandoah does not immediately crash or freeze into a multi-second Full GC. It transitions through three progressive defense tiers:

```
[ 1. Normal Concurrent Mode ] ──(<10ms Pauses)──> Optimal low-latency operation
              │ (Allocation rate begins outpacing concurrent evacuation)
              ▼
[ 2. Pacing (Allocation Stalling) ] ──> Threads slowed down by a few milliseconds
              │ (Free memory runs out midway through a concurrent phase)
              ▼
[ 3. Degenerated GC Mode ] ──(STW: 50-150ms)──> Pauses mutators to finish phase
              │ (Allocation fails completely during degenerated phase)
              ▼
[ 4. Full GC Mode ] ──(Multi-Second STW)──> Emergency multi-threaded Mark-Compact
```

1. **Pacing:** Shenandoah dynamically throttles runaway allocating threads for a few milliseconds, granting concurrent worker threads time to reclaim memory without pausing the JVM.
2. **Degenerated GC:** If free memory is completely exhausted during a concurrent phase (e.g., during Concurrent Evacuation), Shenandoah **does not discard its progress**. Instead, it triggers a brief Stop-The-World pause and finishes *only the remaining portion* of the active phase using all CPU cores in parallel. A Degenerated GC typically completes in **50–150 ms**, completely avoiding a catastrophic Full GC.
3. **Full GC:** The final safety net. If Degenerated GC fails to free sufficient headroom, Shenandoah executes a full parallel Mark-Compact sweep across the entire heap.

---

### Generational Shenandoah (Java 21+)

Historically, Shenandoah was single-generational, requiring whole-heap scans.

Introduced experimentally in Java 21, **Generational Shenandoah** splits the heap into Young and Old generations:
- Ephemeral objects are collected frequently in lightweight Young cycles.
- Slashes background GC CPU overhead by up to **50%**.
- Virtually eliminates Degenerated GC and allocation pacing events under high allocation churn.

## 4 Tricky Questions

### 1. How does Shenandoah GC achieve sub-millisecond pause times compared to G1 GC?
**Answer:** The primary reason G1 GC pause times scale with the volume of live data is that G1 performs object evacuation (copying surviving objects to clean regions) while all application mutator threads are stopped in a Stop-The-World pause. In contrast, Shenandoah GC moves live objects and updates their reference pointers **concurrently** in the background while application threads continue executing. Shenandoah's STW pauses are restricted to scanning thread stack roots and phase handshakes, each taking less than 1 millisecond regardless of whether the heap is 4 GB or 100 GB.

---

### 2. What were Brooks Pointers, and why did modern Shenandoah replace them with Load-Reference Barriers (LRB)?
**Answer:** In early versions of Shenandoah (Java 12–13), every object header was modified to include an additional 8-byte reference field called a **Brooks Pointer** that initially pointed to the object itself. When an object was relocated, the collector used an atomic CAS operation to update this forwarding pointer to the new copy. While conceptually simple, adding 8 bytes to every single object inflated total heap memory consumption by 10% to 20%. In Java 14, Shenandoah replaced Brooks Pointers with modern **Load-Reference Barriers (LRB)**: the forwarding address is written temporarily into the existing 64-bit **Mark Word** only during the evacuation window, completely eliminating object header memory overhead.

---

### 3. What is a Degenerated GC in Shenandoah, and how does it save the application from a multi-second Full GC?
**Answer:** A Degenerated GC is a graceful degradation fallback triggered when available heap memory is exhausted in the middle of a concurrent collection phase (e.g., during Concurrent Evacuation). Rather than discarding all completed work and restarting an expensive multi-second Full GC from scratch, Shenandoah halts application mutator threads in a Stop-The-World pause and uses all available CPU cores to finish *only the unfinished remainder of that specific phase*. Once the phase completes, application threads immediately resume. A Degenerated GC typically resolves in 50 to 150 ms, shielding the application from multi-second Full GC freezes.

---

### 4. What key architectural advantage does Shenandoah hold over ZGC on heaps between 4 GB and 32 GB?
**Answer:** On heaps below 32 GB, Shenandoah fully supports **Compressed OOPs** (`-XX:+UseCompressedOops`), allowing all object reference pointers to remain 32 bits (4 bytes) wide. In contrast, ZGC uses **Colored Pointers**, which mandate 64-bit pointers to store GC color metadata bits in bits 42–45, making Compressed OOPs impossible. Consequently, on heaps under 32 GB, object references in ZGC consume 8 bytes each, resulting in 20–30% higher memory density overhead and higher L1/L2/L3 CPU cache miss rates compared to Shenandoah. Furthermore, Shenandoah works on standard OS pages without virtual memory multi-mapping, providing superior compatibility with minimal container runtimes like Alpine Linux (`musl libc`).

### Key Architectural Takeaways
- **Concurrent Evacuation:** Copies live objects and rewires reference pointers without halting application mutator threads.
- **Load-Reference Barriers (LRB):** Replaced legacy Brooks Pointers in Java 14; encodes forwarding pointers in the Mark Word with zero header bloat.
- **Compressed OOPs Supported:** Retains 4-byte references below 32 GB, providing superior memory density and cache hit rates over ZGC.
- **Degenerated GC:** Graceful fallback that pauses mutators to finish the active phase in 50–150 ms, avoiding monolithic Full GCs.
- **Alpine / Musl Portability:** Compatible across diverse operating systems and minimal C-runtime container images.
- **Generational Shenandoah (Java 21+):** Partitions Young and Old generations, halving CPU consumption.

---

### Red Flags & Anti-Patterns
- 🚩 **Claiming "Shenandoah uses Colored Pointers like ZGC":** Shenandoah uses standard references with Load-Reference Barriers; only ZGC uses Colored Pointers.
- 🚩 **Assuming Shenandoah has zero Stop-The-World pauses:** Shenandoah relies on 4 micro-pauses (Init Mark, Final Mark, Init Update Refs, Final Update Refs), each lasting $<1\text{ ms}$.
- 🚩 **Asserting that Shenandoah does not support Compressed OOPs:** Shenandoah fully supports Compressed OOPs on heaps $< 32\text{ GB}$.
- 🚩 **Treating Degenerated GC as an emergency crash:** Degenerated GC is a design feature that prevents Full GCs by finishing an evacuation in ~100 ms.
- 🚩 **Confusing Brooks Pointers with modern LRBs:** Brooks Pointers were deprecated and eliminated in Java 14.
