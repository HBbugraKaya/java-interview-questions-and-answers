# Если два объекта равны по equals(), что можно сказать об их hashCode()

---

## 🟢 Junior Level

### Краткий ответ для собеседования (30 секунд)
Если два объекта равны по методу `equals()` (`o1.equals(o2) == true`), то их хеш-коды **ОБЯЗАНЫ быть абсолютно одинаковыми** (`o1.hashCode() == o2.hashCode()`).

Это строгое требование спецификации языка Java (`java.lang.Object`). Оно обусловлено архитектурой хеш-таблиц: поиск в `HashMap` и `HashSet` является **двухэтапным**:
1. **Первый этап (грубый и быстрый):** по значению `hashCode()` определяется номер корзины (бакета).
2. **Второй этап (точный):** внутри найденной корзины ищется конкретный узел вызовом `equals()`.

Если для равных объектов вернуть разные хеш-коды, `HashMap` вычислит разные индексы корзин. В результате поиск добавленного ранее объекта будет производиться в совершенно другой корзине, и метод `get()` вернет `null`, а `HashSet` сохранит дубликат.

---

### Сравнительная таблица следствий и зависимостей

| Утверждение | Истинность | Почему | Следствие в архитектуре |
|---|---|---|---|
| **$A.\text{equals}(B) \implies \text{hash}(A) == \text{hash}(B)$** | ✅ **ИСТИНА (Обязательно)** | Прямое требование контракта Java | Гарантирует поиск в одной корзине |
| **$\text{hash}(A) == \text{hash}(B) \implies A.\text{equals}(B)$** | ❌ **ЛОЖЬ (Не обязательно)** | Коллизия (разные объекты делят один хеш) | Разрешается цепочками или деревьями |
| **$A.\text{equals}(B) == \text{false} \implies \text{hash}(A) \ne \text{hash}(B)$** | ❌ **ЛОЖЬ** | Хеши могут совпадать у неравных объектов | Обычная коллизия |
| **$\text{hash}(A) \ne \text{hash}(B) \implies A.\text{equals}(B) == \text{false}$** | ✅ **ИСТИНА (Контрапозиция)** | Разные хеши гарантируют неравенство | Мгновенный отсев чужих объектов за 1 такт |

### Демонстрация на Java 21

```java
import java.util.HashMap;
import java.util.Objects;

public class EqualsHashCodeContractDemo {

    public record CorrectUser(int id, String name) {}

    public static void main(String[] args) {
        // Создаем два логически эквивалентных объекта в разных участках памяти кучи
        CorrectUser u1 = new CorrectUser(101, "Alice");
        CorrectUser u2 = new CorrectUser(101, "Alice");

        // 1. Проверяем равенство по equals
        System.out.println("u1.equals(u2): " + u1.equals(u2)); // true

        // 2. Их hashCode() ОБЯЗАНЫ совпадать:
        System.out.println("Хеши совпадают: " + (u1.hashCode() == u2.hashCode())); // true

        // 3. Корректная работа в HashMap:
        HashMap<CorrectUser, String> cache = new HashMap<>();
        cache.put(u1, "VIP-Session");

        // Извлекаем значение по ВТОРОМУ объекту-ключу u2:
        String session = cache.get(u2);
        System.out.println("Полученная сессия: " + session); // "VIP-Session" (найдено!)
    }
}
```

## 🟡 Middle Level

### Фатальные последствия нарушения правила: $equals \implies hashCode$

Если разработчик переопределит `equals()`, но оставит дефолтный `hashCode()` от класса `Object`, каждый новый экземпляр класса будет получать уникальный `identityHashCode` на основе адреса в памяти.

#### Что ломается в системе:
1. **Потеря элементов в `HashMap` (`map.get(key) == null`):**
   ```java
   Map<MyKey, String> map = new HashMap<>();
   map.put(new MyKey(1), "Found");
   map.get(new MyKey(1)); // Вернет null!
   ```
   Первый ключ попал, например, в корзину 3. Второй ключ (хотя равен первому) вычислил другой хеш и полез в корзину 11, которая оказалась пустой.
2. **Дублирование данных в `HashSet`:**  
   Множество `Set` обязано гарантировать отсутствие дубликатов. Однако `HashSet` построен поверх `HashMap`. Если хеши объектов различаются, они попадут в разные корзины и оба добавятся в коллекцию. В результате `set.size()` вырастет, нарушив бизнес-логику домена.
3. **Утечки памяти (Memory Leaks):**  
   Вызов `map.remove(new MyKey(1))` не сможет найти ноду в целевой корзине и вернет `null`. Старый объект навсегда останется висеть в памяти внутри мапы.

### Хеширование специфических примитивов в JDK: `Double` и `Float`

При ручной реализации `hashCode()` для дробных чисел нельзя просто приводить `double` к `int` (`(int) value`), так как числа `1.2` и `1.8` дадут один и тот же хеш `1`.

В JDK используется битовое преобразование IEEE 754:
```java
// Из реализации Double.hashCode():
public static int hashCode(double value) {
    long bits = doubleToLongBits(value);
    return (int)(bits ^ (bits >>> 32));
}
```
Метод `Double.doubleToLongBits()` приводит все вариации `NaN` к единому каноническому битовому представлению, исключая скрытые коллизии и гарантируя, что `Double.valueOf(Double.NaN).equals(...)` согласуется с `hashCode()`.

## 🔴 Senior Level

### Эффект Гейзенбага (Heisenbug) в Highload-системах

Самое коварное свойство нарушения контракта $equals \implies hashCode$ заключается в том, что **ошибка часто не воспроизводится в модульных тестах и маскируется в локальной разработке**:

```
Пусть объект A равен объекту B, но:
hash(A) = 17 (0001 0001_b)
hash(B) = 33 (0010 0001_b)
```

1. **В локальном тесте (таблица емкостью 16):**
   - Индекс для A: `17 & 15 = 1`
   - Индекс для B: `33 & 15 = 1`
   - **Случайное совпадение корзины!** Хеши были разными, но битовая маска `0000 1111` отбросила старшие биты. Объекты попали в одну корзину, метод `equals()` внутри бакета вернул `true`, и тест **успешно прошел**! Разработчик уверен, что код работает.
2. **В Production под нагрузкой:**
   - Количество элементов превышает `threshold`, и `HashMap` удваивает емкость до 32 (`n - 1 = 31 = 0001 1111_b`).
   - Индекс для A: `17 & 31 = 17`
   - Индекс для B: `33 & 31 = 1`
   - Объекты **разлетаются по разным корзинам**. Продакшен внезапно начинает возвращать `null` и терять заказы клиентов. Такие ошибки называют «Гейзенбагами», так как они зависят от динамического состояния среды исполнения.

### Оптимизация отсева по контрапозиции: $\text{hash}_1 \ne \text{hash}_2 \implies o_1 \ne o_2$

По законам математической логики прямое утверждение:
$$A \implies B \quad (equals \implies hashCode)$$
строго эквивалентно закону контрапозиции:
$$\neg B \implies \neg A \quad (hash_A \ne hash_B \implies !equals)$$

Это логическое следствие является фундаментом производительности всей платформы Java:
```java
// Проверка узла в HashMap HotSpot:
if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
```
Благодаря гарантии контрапозиции JVM сравнивает два 32-битных регистра процессора (`p.hash == hash`). Если они не равны, среда исполнения **математически гарантирует**, что объекты не равны по `equals()`, не тратя время на вызов тяжелого виртуального метода `equals()`.

## 🎯 Шпаргалка для интервью

### 1. 30-секундный эссенс (Elevator Pitch)
Если два объекта равны по `equals()`, их `hashCode()` **обязаны быть абсолютно равны**. Обратное неверно: одинаковые хеш-коды не гарантируют равенство объектов (это коллизия). Если равные объекты возвращают разные хеш-коды, они попадут в разные корзины `HashMap`: метод `get()` вернет `null`, а в `HashSet` появятся дубликаты. Контрапозиция правила ($hash_1 \ne hash_2 \implies o_1 \ne o_2$) позволяет `HashMap` отсекать несовпадающие объекты за 1 такт процессора до вызова `equals()`.

### 2. 4 каверзных вопроса с глубокими ответами

#### Вопрос 1: Что произойдет в `HashSet`, если добавить два объекта, у которых `equals() == true`, но `hashCode()` возвращает разные значения?
**Ответ:**
Коллекция `HashSet` внутри использует `HashMap`, сохраняя элементы в качестве ключей (со значением-заглушкой `PRESENT`). При попытке добавить второй объект `HashSet` вычислит его `hashCode()`. Так как хеш отличается от первого, мапа поместит второй объект в другую корзину. В результате `HashSet` успешно сохранит **оба логически одинаковых объекта**, прямо нарушив контракт множества об уникальности элементов, а метод `set.size()` вернет 2 вместо 1.

#### Вопрос 2: Как эффект случайного совпадения корзины маскирует нарушение контракта `hashCode()` в тестах, и почему он «взрывается» в проде?
**Ответ:**
В маленьких мапах (емкость 16) индекс корзины определяется младшими 4 битами (`& 15`). Если у равных объектов разные хеши случайно совпали в младших 4 битах (например, 17 и 33), они попадут в одну корзину. Внутри бакета метод `equals()` найдет совпадение, и юнит-тест успешно пройдет. Однако в продакшене при росте коллекции происходит ресайз таблицы (до 32, 64 и выше). Маска начинает учитывать 5-й и 6-й биты, объекты гарантированно разлетаются по разным бакетам, и функционал внезапно ломается.

#### Вопрос 3: Обязаны ли два объекта с одинаковым `hashCode()` быть равны по `equals()`?
**Ответ:**
Категорически **нет**. Совпадение хешей у неравных объектов называется **коллизией**. Диапазон `hashCode()` ограничен 32 битами ($4.3 \times 10^9$), а количество возможных объектов бесконечно (принцип Дирихле). Одинаковый хеш обязывает `HashMap` лишь поместить их в одну корзину, где они будут различаться вызовом `equals()`.

#### Вопрос 4: Как правильно реализовать `hashCode()` для полей типов `double` и `float`?
**Ответ:**
Нельзя выполнять простое приведение к `int` (потеря точности) или использовать сравнение через `==`. Для `float` используется `Float.floatToIntBits(f)`, а для `double` — `Double.doubleToLongBits(d)` со сверткой `(int)(bits ^ (bits >>> 32))`. Эти методы нормализуют специальное значение `NaN` (Not a Number) и разделяют `+0.0` и `-0.0`, обеспечивая строгое соответствие между `Double.equals()` и `hashCode()`.

### 3. Типичные ошибки и Red Flags

❌ **"Если объекты равны по equals, их хеши МОГУТ быть одинаковыми (желательно)."**  
*Правильно:* Они **ОБЯЗАНЫ** быть строго одинаковыми. Это жесткий контракт спецификации.

❌ **"Если хеши одинаковые, то и объекты равны по equals."**  
*Правильно:* Это ошибка реверсии причины и следствия. Одинаковый хеш — это всего лишь коллизия.

❌ **"Использование адреса в памяти в качестве основы для бизнес-хеша."**  
*Правильно:* Бизнес-хеш должен строиться только на тех полях, которые участвуют в `equals()`.
