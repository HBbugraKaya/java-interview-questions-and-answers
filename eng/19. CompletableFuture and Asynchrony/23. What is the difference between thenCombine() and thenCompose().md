# What is the difference between thenCombine() and thenCompose()

---

## 🟢 Junior Level

Both methods link two `CompletableFuture` computations, but they serve fundamentally different purposes:

- **`thenCombine()`** is used for **parallel combination of two independent tasks**. Both tasks run concurrently, and their finished results are combined via a third function (analogous to `zip`).
- **`thenCompose()`** is used for **sequential chaining of two dependent tasks**. The second task starts only after the first has completed, consuming the first task's output as its input argument (analogous to `flatMap`).

### Visual and Practical Comparison

```java
// 1. thenCombine: Tasks are INDEPENDENT (executed in PARALLEL)
CompletableFuture<Double> usdRateFuture = CompletableFuture.supplyAsync(() -> getUsdRate());
CompletableFuture<Double> eurRateFuture = CompletableFuture.supplyAsync(() -> getEurRate());

CompletableFuture<String> ratesReport = usdRateFuture.thenCombine(
    eurRateFuture,
    (usd, eur) -> "USD: " + usd + ", EUR: " + eur
);
// Total Latency = max(time_usd, time_eur)

// 2. thenCompose: Task 2 DEPENDS on Task 1 (executed SEQUENTIALLY)
CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> fetchUser(userId));

CompletableFuture<List<Order>> ordersFuture = userFuture.thenCompose(
    user -> fetchOrdersAsync(user.getAccountId()) // Requires accountId from user!
);
// Total Latency = time_user + time_orders
```

## 🟡 Middle Level

### Comparative Matrix

| Characteristic | `thenCombine` | `thenCompose` |
| :--- | :--- | :--- |
| **Functional Abstraction** | Applicative Functor (`zipWith` / `liftA2`) | Monad (`bind` / `flatMap`) |
| **Argument Signature** | `CompletionStage<U>`, `BiFunction<T, U, V>` | `Function<T, CompletionStage<U>>` |
| **Data Dependency** | Tasks are independent | Task 2 depends on result of Task 1 |
| **Execution Flow** | Concurrent / Parallel | Strictly sequential |
| **Total Latency** | $\max(T_1, T_2) + T_{\text{combiner}}$ | $T_1 + T_2$ |
| **Paired Variants** | `thenAcceptBoth`, `runAfterBoth` | — |

### Common Performance Anti-Pattern: Accidental Serialization

A frequent junior mistake is using `thenCompose` when operations are independent, accidentally turning parallel requests into slow sequential calls and doubling latency:

```java
// ❌ ANTI-PATTERN: Weather and traffic are independent, yet executed sequentially!
CompletableFuture<Dashboard> bad = fetchWeatherAsync()
    .thenCompose(weather -> fetchTrafficAsync()
        .thenApply(traffic -> new Dashboard(weather, traffic)));
// Latency = 200 ms + 200 ms = 400 ms

// ✅ CORRECT: Fire both requests simultaneously and combine
CompletableFuture<Weather> weatherF = fetchWeatherAsync();
CompletableFuture<Traffic> trafficF = fetchTrafficAsync();

CompletableFuture<Dashboard> good = weatherF.thenCombine(
    trafficF, 
    (weather, traffic) -> new Dashboard(weather, traffic)
);
// Latency = max(200 ms, 200 ms) = 200 ms (50% reduction!)
```

## 🔴 Senior Level

### Failure Semantics: Task Isolation and Background Work

The critical architectural difference emerges in failure modes:

1. **In `thenCompose` (Fail-Early)**:
   - If the upstream future fails exceptionally, the function generating the second future is **never invoked**.
   - The downstream network call is never initiated, saving downstream compute and network bandwidth.
2. **In `thenCombine` (Background Leaks)**:
   - Both futures `cf1` and `cf2` are launched concurrently in worker thread pools.
   - If `cf1` throws an exception after 10 ms, the resulting composite future immediately transitions to `CompletionException`.
   - **However, `cf2` continues executing in the background until completion!** `thenCombine` does not automatically cancel sibling futures upon failure.

### Internal Mechanics: `BiApply` vs. `UniCompose`

- **`thenCombine`** allocates an internal `BiApply` completion node attached to the dependency stacks of **both** upstream futures. The combining `BiFunction` is triggered only when both upstream stages transition to completed states.
- **`thenCompose`** allocates a `UniCompose` completion node. Upon upstream completion, it executes the mapping function to produce a second `CompletionStage`, then sets up a nested completion relay that unwraps the nested stage into the resulting `CompletableFuture`.

## 4 Tricky Questions

### 1. Which category theory abstractions correspond to `thenCompose` and `thenCombine`?

**Answer:**
- **`thenCompose`** implements the **Monad** interface: the `bind` (or `flatMap`) operation. It takes a function $T \to M[U]$ and flattens the nested context from $M[M[U]]$ into $M[U]$.
- **`thenCombine`** implements the **Applicative Functor** interface: the `liftA2` / `zipWith` operation. It takes two independent contexts $M[T]$ and $M[U]$ and combines their encapsulated values using a pure binary function $(T, U) \to V$ into $M[V]$.

### 2. If `cf1.thenCombine(cf2, (a, b) -> a + b)` is executed, and `cf1` throws an exception, what happens to `cf2`?

**Answer:**
`cf2` **continues executing in the background until completion**.
The resulting composite future completes immediately with `CompletionException` wrapping `cf1`'s exception, but `thenCombine` does not propagate cancellation to `cf2`. If `cf2` is performing expensive network I/O or database mutations, it will execute fully unless cancelled manually via error-handling hooks.

### 3. Can `thenCombine` be syntactically emulated using `thenCompose`? What are the latency consequences?

**Answer:**
Yes, syntactically:
```java
cf1.thenCompose(r1 -> cf2.thenApply(r2 -> combine(r1, r2)));
```
If `cf2` was already launched before the `thenCompose` statement, both futures run concurrently, achieving the same $\max(t_1, t_2)$ latency.
However, if `cf2` is instantiated **inside** the lambda closure:
```java
cf1.thenCompose(r1 -> fetchCf2Async().thenApply(r2 -> combine(r1, r2)));
```
The second operation will not launch until `cf1` completes, serializing execution and increasing latency to $t_1 + t_2$.

### 4. In which thread will the combiner function `(a, b) -> ...` in `thenCombine` execute?

**Answer:**
It executes on the thread that completes the **last (slowest)** of the two futures.
When the first future finishes, it marks its slot in the internal `BiApply` node and terminates. When the second future finishes, its completing thread detects that both operands are ready and executes the combiner lambda. If both futures are already complete at registration time, the combiner executes synchronously on the calling thread. For dedicated execution, use `thenCombineAsync(cf2, fn, executor)`.

## 🎯 Interview Cheat Sheet

### Summary in 60 Seconds
- **`thenCombine`** = parallel, independent, merges two results (`zip` / Applicative Functor). Latency = $\max(t_1, t_2)$.
- **`thenCompose`** = sequential, dependent, launches stage 2 using stage 1's result (`flatMap` / Monad). Latency = $t_1 + t_2$.
- If `thenCompose` upstream fails, stage 2 never starts.
- If `thenCombine` branch 1 fails, branch 2 still runs to completion in the background.
- Using `thenCompose` for independent tasks is a performance defect that serializes requests and inflates latency.

### Common Interview Traps
- Using `thenCompose` where operations could run in parallel with `thenCombine`.
- Assuming `thenCombine` automatically aborts sibling operations when one throws an error.
- Confusing function signatures: `thenCombine` accepts `BiFunction<T, U, V>`, while `thenCompose` accepts `Function<T, CompletionStage<U>>`.
