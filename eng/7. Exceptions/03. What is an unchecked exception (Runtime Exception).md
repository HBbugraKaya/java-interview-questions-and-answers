# What is an unchecked exception (Runtime Exception)

---

## 🟢 Junior Level

An **unchecked exception** in Java is any exceptional condition that the `javac` compiler **does not require** to be explicitly caught inside a `try-catch` block or declared in the method signature via the `throws` keyword.

In the Java type hierarchy, unchecked exceptions comprise the class **`java.lang.RuntimeException`** and all of its subclasses (along with the system-level `java.lang.Error` branch).

```
                         java.lang.Throwable
                                  │
                 ┌────────────────┴────────────────┐
                 ▼                                 ▼
         java.lang.Error                 java.lang.Exception
          (Unchecked)                     (Checked by default)
                                                   │
                                                   ▼
                                        java.lang.RuntimeException
                                               (Unchecked)
                                                   │
       ┌───────────────────┬───────────────────────┼───────────────────────┐
       ▼                   ▼                       ▼                       ▼
NullPointerException  IllegalArgumentException  IllegalStateException  IndexOutOfBoundsException
```

### Common Causes of Unchecked Exceptions

Unchecked exceptions generally arise from two root scenarios:

1. **Programming Bugs (Code Defects):**
   - **`NullPointerException` (NPE):** Attempting to invoke a method or access a field on a `null` object reference.
   - **`IndexOutOfBoundsException`:** Accessing an invalid index in an array, string, or collection (`list.get(10)` on a list of size 5).
   - **`ClassCastException`:** Attempting to cast an object reference to an incompatible type at runtime.
   - **`ArithmeticException`:** Illegal arithmetic operations, such as integer division by zero (`10 / 0`).

2. **Method Contract Violations:**
   - **`IllegalArgumentException`:** An inappropriate or invalid argument was passed to a method (e.g., negative balance, percentage $> 100$).
   - **`IllegalStateException`:** A method was invoked while the underlying object was in an inappropriate state (e.g., reading from an already closed stream).
   - **`UnsupportedOperationException`:** Invoking a mutator method on an unmodifiable collection (e.g., `List.of().add("item")`).

### Basic Code Example

```java
public class UncheckedBasics {

    // The method does NOT require `throws IllegalArgumentException`
    public void setDiscountPercentage(int percentage) {
        if (percentage < 0 || percentage > 100) {
            throw new IllegalArgumentException("Discount must be between 0 and 100%");
        }
        // Business logic execution...
    }

    public static void main(String[] args) {
        UncheckedBasics service = new UncheckedBasics();
        // The compiler does not enforce try-catch handling
        service.setDiscountPercentage(150); // Throws IllegalArgumentException at runtime
    }
}
```

## 🟡 Middle Level

### Domain Unchecked Exceptions and the Fail-Fast Principle

In modern enterprise architectures, unchecked exceptions are divided into two distinct classifications:
1. **Technical Code Defects** (`NullPointerException`, `IndexOutOfBoundsException`): These should **never** be caught in business logic; they must be prevented and resolved via code bugfixes.
2. **Domain Business Exceptions** (`UserNotFoundException`, `OrderAlreadyProcessedException`, `InsufficientFundsException`): These intentionally extend `RuntimeException` to signal standard business domain rule violations without polluting method signatures.

#### The Fail-Fast Principle
Methods should validate incoming parameters at the earliest possible entry point and immediately throw an unchecked exception if preconditions are violated, preventing corrupted state from propagating deeper into databases or internal services:

```java
import java.util.Objects;

public Order processOrder(Long userId, OrderRequest request) {
    Objects.requireNonNull(userId, "User ID must not be null");
    Objects.requireNonNull(request, "Order request must not be null");

    if (request.items().isEmpty()) {
        throw new IllegalArgumentException("Order must contain at least one item");
    }

    return orderRepository.save(new Order(userId, request.items()));
}
```

### Centralized Error Handling in Spring Boot (`@RestControllerAdvice`)

Because `RuntimeException` instances bubble up the call stack freely through all architectural layers (Repository $\to$ Service $\to$ Controller), Spring applications eliminate verbose boilerplate `try-catch` blocks.

All domain exceptions are intercepted centrally by a **`@RestControllerAdvice`** component and transformed into standardized RFC 9457 `ProblemDetail` HTTP responses:

```java
package com.example.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.net.URI;
import java.time.Instant;

@RestControllerAdvice
public class GlobalErrorHandlingAdvice {

    // Intercept domain business exception: 404 Not Found
    @ExceptionHandler(EntityNotFoundException.class)
    public ProblemDetail handleNotFound(EntityNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Resource Not Found");
        problem.setType(URI.create("https://api.example.com/errors/not-found"));
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }

    // Intercept client contract violations: 400 Bad Request
    @ExceptionHandler(IllegalArgumentException.class)
    public ProblemDetail handleBadRequest(IllegalArgumentException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, ex.getMessage());
        problem.setTitle("Invalid Request Argument");
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }
}
```

## 🔴 Senior Level

### Anti-Pattern: "Exceptions as Control Flow"

Using exceptions for routine conditional branching is one of the most detrimental performance anti-patterns in Java:

```java
// ❌ HORRIBLE ANTI-PATTERN: Using exceptions for regular conditional flow
public boolean userExists(Long userId) {
    try {
        userService.findById(userId); // Throws UserNotFoundException if missing
        return true;
    } catch (UserNotFoundException ex) {
        return false; // Catastrophic CPU degradation under high load!
    }
}

// ✅ HIGH-PERFORMANCE: Query existence or return Optional
public boolean userExists(Long userId) {
    return userRepository.existsById(userId);
}
```

#### Why This Crushes Highload Systems
- Calling `existsById()` is a straightforward database/cache lookup and boolean check.
- Throwing `UserNotFoundException` invokes the native method **`Throwable.fillInStackTrace()`**. The JVM suspends thread execution, walks the entire call stack frame by frame, and populates class names, method names, and line numbers from JVM metadata. Under a load of 50,000 RPS, this causes near 100% CPU saturation and massive GC pressure.

### The Hidden Hazards of Uncaught `RuntimeException` in Thread Pools

In multi-threaded concurrency, unhandled unchecked exceptions pose severe operational risks:

1. **Silent Task Disappearance in `ExecutorService.submit()`:**  
   When a task submitted via `executor.submit(Callable)` throws an unhandled `RuntimeException`, the executor catches the exception and stores it internally inside the returned `Future`. If the developer never calls `future.get()`, **the error is silently swallowed forever**, leaving no trace in application log files!
2. **Permanent Scheduler Termination in `ScheduledExecutorService`:**  
   If an unhandled `RuntimeException` escapes a periodic task scheduled via `scheduleAtFixedRate()` or `scheduleWithFixedDelay()`, the scheduler suppresses the exception, terminates the task permanently, and **never runs subsequent iterations again**, without logging anything!

#### Robust Solution: Defensive Try-Catch and `UncaughtExceptionHandler`
```java
// 1. Always enclose periodic scheduled tasks in a top-level try-catch
scheduler.scheduleAtFixedRate(() -> {
    try {
        syncPeriodicData();
    } catch (Throwable t) {
        log.error("Unhandled error in scheduled task", t);
    }
}, 0, 5, TimeUnit.MINUTES);

// 2. Register a global fallback handler for worker threads
Thread.setDefaultUncaughtExceptionHandler((thread, throwable) -> {
    log.error("CRITICAL: Uncaught exception on thread: {}", thread.getName(), throwable);
});
```

### Stackless Runtime Exceptions for Hot Paths

For latency-critical gateways, rate limiters, or authentication filters where exceptions are used strictly as an abort signal without requiring a stack trace, use pre-instantiated stackless singletons:

```java
package com.example.exception;

public class FastValidationException extends RuntimeException {

    // Pre-allocated singleton eliminates CPU stack walking and GC pressure
    public static final FastValidationException TOKEN_EXPIRED =
            new FastValidationException("Security token expired");

    public FastValidationException(String message) {
        // (message, cause, enableSuppression = false, writableStackTrace = false)
        super(message, null, false, false);
    }
}
```

## 4 Tricky Questions

### 1. What happens if a periodic task in `ScheduledExecutorService.scheduleAtFixedRate()` throws an unhandled `RuntimeException`?

**Answer:**  
The periodic execution of the task terminates permanently. The scheduler suppresses the exception, marks the internal future as completed exceptionally, and silently cancels all future scheduled executions of that task without writing anything to the logs. To prevent this silent failure, the task's runnable body must always be wrapped in a top-level `try-catch (Throwable t)` block with logging.

### 2. Why is "Exceptions as Control Flow" considered a severe anti-pattern in Java?

**Answer:**  
First, it violates readability and principle of least surprise by obscuring standard business branching logic. Second, it causes severe performance degradation: creating an exception triggers `Throwable.fillInStackTrace()`, which halts the thread and walks every stack frame in the call hierarchy to extract debug metadata. This operation is $100\times\text{--}1000\times$ slower than checking conditions via `if-else` or `Optional.isPresent()`.

### 3. Should standard runtime exceptions like `NullPointerException` or `IndexOutOfBoundsException` be caught in application code?

**Answer:**  
No. Catching `NullPointerException` or `IndexOutOfBoundsException` directly in application logic is an anti-pattern. These exceptions represent programmer bugs and defective code that must be resolved via code fixes and defensive input validation (`Objects.requireNonNull()`, bounds checking, `@NotNull` annotations, or `Optional`), rather than being caught and hidden.

### 4. How does the 4-argument `Throwable` constructor optimize high-throughput architectures?

**Answer:**  
By passing `writableStackTrace = false` into `super(message, null, false, false)`, the JVM completely bypasses the expensive native call to `fillInStackTrace()`. The exception object is allocated as a lightweight object without capturing call frames, yielding a 30x–50x speedup in exception instantiation and eliminating CPU throttling under high concurrency.

## 🎯 Interview Cheat Sheet

### 30-Second Summary
> **Unchecked exceptions** (`RuntimeException` and subclasses) are exceptions where the `javac` compiler does not enforce handling or method declaration (`throws`).
>
> They are categorized into:
> 1. **Code Defects / Bugs** (`NullPointerException`, `IndexOutOfBoundsException`), which must be resolved via bug fixes, not caught.
> 2. **Domain Business Exceptions** (`UserNotFoundException`, `InsufficientFundsException`), which represent business failures.
>
> Modern enterprise frameworks (Spring Boot, Hibernate) use unchecked exceptions exclusively because they do not pollute method signatures, work seamlessly with Stream API/lambdas, and are easily captured centrally via `@RestControllerAdvice`.

### Key Pitfalls
- **Scheduler Death:** An unhandled `RuntimeException` inside `ScheduledExecutorService.scheduleAtFixedRate()` silently terminates all future runs.
- **Future Swallowing:** Unhandled runtime exceptions in `executor.submit()` are buried unless `future.get()` is invoked.
- **Control Flow Abuse:** Never use exceptions for normal branching logic due to `fillInStackTrace()` CPU overhead.

### Red Flags (What to Avoid)
- ❌ *"Unchecked exceptions can never be caught in a try-catch block."* (They can be caught and handled just like checked exceptions).
- ❌ *"If an object might be null, wrap it in `try { obj.call(); } catch (NullPointerException e) {}`."* (Severe anti-pattern; check for null defensively).
- ❌ *"RuntimeException and Error are the exact same thing."* (`Error` indicates fatal JVM-level failures like `OutOfMemoryError`; `RuntimeException` indicates application-level conditions).
- ❌ *"Throwing exceptions is cheap and has no performance penalty in Java."* (Stack trace generation via `fillInStackTrace()` is very CPU-intensive).
